    36. I/O 모델: 블로킹 vs 논블로킹, 동기 vs 비동기¶

    원리 동작을 예측하고 이상을 알아챌 수 있어야 하는 항목

    파일을 읽거나 네트워크로 요청을 보내면 답이 오기까지 CPU 기준으로는 아주 오래 걸린다. 그동안 스레드는 무엇을 할까? 멈춰서 기다릴 수도, 계속 물어볼 수도, 다른 일을 하다가 알림을 받을 수도 있다. 이렇게 기다리는 방법을 I/O 모델이라 한다. 웹 서버가 요청 수만 개를 받는 방법, JavaScript와 C#의 async가 하는 일이 모두 이 위에 있다. 이 PC에서 같은 요청을 네 가지 방법으로 처리해 비교한다.

    이 항목에서 배우는 것¶

    • 블로킹/논블로킹과 동기/비동기가 각각 무엇을 묻는 구분인지 설명할 수 있다.
    • 같은 요청을 블로킹, 폴링, 비동기로 처리할 때 걸리는 시간과 쓰는 CPU를 예측할 수 있다.
    • 요청이 많을 때 스레드를 늘리는 방법과 비동기 방법의 차이를 설명할 수 있다.

    1. 블로킹과 동기는 서로 다른 질문이다¶

    • 블로킹/논블로킹은 "결과가 날 때까지 함수가 안 돌아오는가"를 묻는다. 블로킹이면 스레드가 멈추고(32번(CPU 스케줄링과 컨텍스트 스위칭)의 대기 상태), 논블로킹이면 아직이어도 "아직"이라는 표시와 함께 바로 돌아온다.
    • 동기/비동기는 "결과를 누가 챙기는가"를 묻는다. 동기는 내가 함수를 불러 결과를 받아 오고, 비동기는 일을 걸어 두면 끝났을 때 운영체제가 알려 준다.
    • 보통의 ReadFile은 동기·블로킹, 논블로킹 소켓을 계속 확인하는 폴링은 동기·논블로킹, 겹친 I/O는 비동기다. 겹친 I/O를 여러 개 걸어 두고 알림이 올 때까지 함께 기다리는 WaitForMultipleObjects는 기다리는 동안 돌아오지 않으므로 비동기·블로킹 칸이다.

    2. 함수가 언제 돌아오는지가 다르다¶

    • 블로킹으로 부르면 답이 올 때까지 스레드가 잠든다. CPU는 쓰지 않지만 그 스레드는 다른 일을 못 한다.
    • 논블로킹으로 부르면 바로 돌아오지만 "아직"이다(문제 1). 다시 물어봐야 하고, 쉬지 않고 물으면 기다리는 내내 CPU를 쓴다.
    • 비동기로 걸어 두면 함수가 바로 "걸었다"며 돌아오고(문제 2), 스레드는 다른 일을 하다가 끝났다는 알림을 받는다. 기다림을 운영체제에 맡기는 것이다.

    3. 기다림을 겹쳐야 빨리 끝난다¶

    직접 해 보기요청 여러 개 기다리기요청 묶음과 처리 방법(하나씩 블로킹, 폴링, 비동기 알림, 스레드 여러 개) 단추를 눌러, 전체 시간과 기다리는 동안 쓰는 CPU, 스레드 수가 어떻게 바뀌는지 본다
    새 창에서 크게 열기
    • 답이 30, 120, 60ms 뒤에 오는 요청 셋을 이 PC에서 처리했다. 하나를 보내고 답을 받은 뒤 다음을 보내면 211~213ms로 셋의 합이다. 셋을 다 보내 두고 함께 기다린 폴링, 비동기, 스레드 셋은 모두 약 121ms로 가장 늦은 요청만큼이었다.
    • 블로킹 함수 하나는 한 번에 하나만 기다린다. 셋을 다 보내 두어도 120ms짜리에서 멈춰 있는 동안에는 먼저 온 60ms 답을 처리하지 못한다. 그래서 여럿을 함께 기다리려면 계속 묻거나(폴링), 알림을 받거나(비동기), 스레드를 늘린다.
    • 다른 점은 비용이다. 폴링은 기다리는 내내 코어 하나를 썼고(CPU 119~120ms), 비동기는 0.1~0.2ms였다. 스레드 셋은 CPU는 안 쓰지만 요청마다 스레드와 1MiB 스택 예약이 든다(30번(프로그램, 프로세스, 스레드)).
    • 그래서 동시 접속이 많은 웹 서버는 스레드 몇 개로 많은 요청을 걸어 두고 알림을 받는다. Windows의 I/O 완료 포트(IOCP)는 읽기가 끝나면, 리눅스의 epoll은 읽을 준비가 되면 알린다. Node.js와 C#의 async/await가 이것들 위에서 돈다(33번(동시성과 병렬성)의 동시성).

    예측해 보기¶

    문제 1. 논블로킹으로 바꾼 소켓에서, 상대가 아직 아무것도 보내지 않았을 때 recv를 부른다. 그다음 상대가 2바이트를 보내고 다시 부른다. 무엇이 출력될까?

    #include <stdio.h>
#include <winsock2.h>
#pragma comment(lib, "ws2_32.lib")

int main(void) {
    WSADATA wsa;
    WSAStartup(MAKEWORD(2, 2), &wsa);
    SOCKET ls = socket(AF_INET, SOCK_STREAM, 0);
    struct sockaddr_in a = { 0 };
    a.sin_family = AF_INET;
    a.sin_addr.s_addr = htonl(INADDR_LOOPBACK);
    bind(ls, (struct sockaddr *)&a, sizeof a);
    int len = sizeof a;
    getsockname(ls, (struct sockaddr *)&a, &len);
    listen(ls, 1);
    SOCKET c = socket(AF_INET, SOCK_STREAM, 0);   /* 같은 프로그램 안에서 클라이언트(c)와 서버(s)를 잇는다 */
    connect(c, (struct sockaddr *)&a, sizeof a);
    SOCKET s = accept(ls, NULL, NULL);

    u_long on = 1;
    ioctlsocket(s, FIONBIO, &on);              /* 논블로킹으로 바꾼다 */
    char buf[16];
    int r = recv(s, buf, sizeof buf, 0);       /* 아직 아무도 보내지 않았다 */
    printf("%d %d\n", r, WSAGetLastError());
    send(c, "hi", 2, 0);
    Sleep(50);
    r = recv(s, buf, sizeof buf, 0);
    printf("%d\n", r);
    closesocket(s); closesocket(c); closesocket(ls);
    WSACleanup();
    return 0;
}
    정답과 해설 
    -1 10035
2

    처음 recv는 기다리지 않고 바로 −1(SOCKET_ERROR)을 돌려준다. 오류 번호 10035는 WSAEWOULDBLOCK, 곧 "블로킹이었다면 기다렸을 것"이라는 뜻이다. 진짜 오류가 아니라 "아직"이다. 보낸 뒤에 다시 부르면 2바이트를 받는다. 블로킹 소켓이었다면 첫 recv에서 영원히 멈췄을 것이다.

    문제 2. 겹친 I/O(FILE_FLAG_OVERLAPPED)로 연 파이프에서, 아직 아무도 쓰지 않았을 때 ReadFile을 부른다. 그다음 상대가 "answer"를 쓰고, GetOverlappedResult로 결과를 받는다. 무엇이 출력될까?

    #include <stdio.h>
#include <windows.h>

int main(void) {
    HANDLE rd = CreateNamedPipeA("\\\\.\\pipe\\cs36p", PIPE_ACCESS_INBOUND | FILE_FLAG_OVERLAPPED,
                                 PIPE_TYPE_BYTE, 1, 4096, 4096, 0, NULL);
    HANDLE wr = CreateFileA("\\\\.\\pipe\\cs36p", GENERIC_WRITE, 0, NULL, OPEN_EXISTING, 0, NULL);
    char buf[16];
    OVERLAPPED ov = { 0 };
    ov.hEvent = CreateEventA(NULL, TRUE, FALSE, NULL);
    BOOL ok = ReadFile(rd, buf, sizeof buf, NULL, &ov);        /* 아직 쓴 사람이 없다 */
    printf("%d %lu\n", ok, GetLastError());
    DWORD w, n;
    WriteFile(wr, "answer", 6, &w, NULL);                      /* 이제 답이 온다 */
    GetOverlappedResult(rd, &ov, &n, TRUE);                    /* 끝날 때까지 기다려 결과를 받는다 */
    printf("%lu %.*s\n", n, (int)n, buf);
    return 0;
}
    정답과 해설 
    0 997
6 answer

    ReadFile은 기다리지 않고 0(실패처럼 보이는 값)을 돌려주고, 오류 번호는 997(ERROR_IO_PENDING), 곧 "걸어 두었다, 진행 중이다"이다. 읽기는 운영체제가 맡아 두고, 데이터가 오면 ov.hEvent를 켠다. 프로그램은 그사이 다른 일을 할 수 있다. GetOverlappedResult의 마지막 인자를 TRUE로 주면 끝날 때까지 기다렸다가 받은 바이트 수를 알려 준다.

    문제 3. 답이 각각 100ms 뒤에 오는 요청 다섯 개를, 스레드 하나로 하나씩 블로킹으로 처리하면 몇 ms쯤 걸릴까? 비동기로 다섯 개를 걸어 두고 알림을 기다리면?

    정답과 해설

    블로킹은 약 500ms, 비동기는 약 100ms. 스레드 하나가 하나씩 블로킹으로 처리하면, 앞 요청의 답을 기다리며 멈춘 동안 다음 요청을 보내지 못해 기다림이 더해진다. 비동기는 다섯 개를 다 걸어 두고 함께 기다리므로 가장 늦은 하나만큼 걸린다. 위젯의 "100ms 다섯 개"에서 확인할 수 있다.

    직접 해보기¶

    실습: 내 PC에서 네 방법 비교하기

    1. "더 알아보기"의 측정 프로그램을 내 PC에서 실행해, 네 방법의 전체 시간과 CPU를 확인한다.
    2. 요청을 셋에서 다섯으로 늘리고(K를 5로, delay_ms를 30, 120, 60, 90, 45로) 결과를 예측한 뒤 실행한다.
    3. 폴링 방법의 반복 안에 Sleep(1)을 넣고 다시 잰다. CPU와 전체 시간이 어떻게 바뀌는지 본다.
    확인할 점
    • 2에서 하나씩 블로킹은 다섯의 합(345ms)에 가까운 약 349ms, 나머지 셋은 가장 긴 요청만큼인 약 121ms였다(이 PC에서 3번). 스레드 방법은 스레드 다섯이 든다.
    • 3에서 이 측정 프로그램은 timeBeginPeriod(1)을 켜 두어서 Sleep(1)이 1.4~1.7ms씩 쉰다(32번(CPU 스케줄링과 컨텍스트 스위칭)). 이 PC에서 CPU는 0.8~1.6ms로 줄고 전체 시간은 약 121ms 그대로였다. 켜지 않으면 Sleep(1)이 15.3~15.4ms씩 쉬어서(32번(CPU 스케줄링과 컨텍스트 스위칭)) 답을 그만큼 늦게 알아챌 수 있다.

    AI와 함께 확인하기¶

    AI 활용 과제: 기다리는 반복문의 CPU

    1. AI에게 "C(Windows)로, 다른 스레드가 파이프에 쓸 때까지 PeekNamedPipe로 확인하며 기다리는 코드"를 짜 달라고 한다.
    2. 실행하기 전에, 120ms 동안 기다릴 때 이 코드가 CPU를 얼마나 쓸지 예측한다.
    3. QueryThreadCycleTime으로 기다리는 동안 쓴 CPU 사이클을 재고, AI의 답과 대조한다. 바꿀 방법을 물어 그 방법으로도 잰다.
    확인할 점
    • 쉬지 않고 묻는 반복문은 이 PC에서 답이 오기까지 132~135ms 기다리는 동안 4.2억~4.3억 사이클을 썼다. 이 PC의 TSC(3,187MHz)로 바꾸면 130~134ms로 기다린 시간과 거의 같다. 기다린 내내 코어 하나를 통째로 쓴 것이다. 120ms를 부탁한 Sleep이 시계 틱 때문에 조금 더 잤다(32번(CPU 스케줄링과 컨텍스트 스위칭)).
    • Sleep(1)을 넣으라는 답이 흔하다. 사이클은 약 100만으로 줄었지만, 묻는 횟수가 9~10번뿐이었다. 시계 틱(15.625ms)마다 한 번씩 물어서 답을 그만큼 늦게 알아챌 수 있다.
    • 나은 답은 기다리는 일을 운영체제에 맡기는 것이다. 블로킹 ReadFile 하나면 충분하고, 여럿을 함께 기다리려면 겹친 I/O와 이벤트(WaitForMultipleObjects)나 완료 포트를 쓴다. 기다리는 동안 CPU를 거의 쓰지 않고, 답이 오는 즉시 깨어난다.

    더 알아보기¶

    웹 서버와 C10K

    한 서버가 동시 접속 1만 개(C10K)를 받는 방법이 1990년대 말 큰 문제였다. 접속마다 스레드를 두면 스레드 1만 개의 스택과 컨텍스트 스위칭(32번(CPU 스케줄링과 컨텍스트 스위칭))이 부담이 된다. 그래서 스레드 몇 개가 많은 소켓을 걸어 두고, 알림이 온 것만 골라 처리하는 방식이 자리 잡았다. select와 epoll은 "읽을 준비가 됐다"를, IOCP는 "읽기가 끝났다"를 알린다. Nginx와 Node.js가 이 방식이고, 언어의 async/await는 이 방식을 순서대로 읽히는 코드로 쓰게 해 준다.

    select와 epoll은 어느 칸인가

    2×2 분류는 자료마다 조금씩 다르다. select와 epoll은 소켓 여러 개를 걸어 두고 읽을 준비가 된 소켓을 알려 준다. 알려 주는 것은 준비됐다는 사실뿐이라, 데이터는 그다음 recv를 불러 내가 받아 온다. 그래서 이 항목의 기준(결과를 누가 받아 오나)으로는 동기이고, 유닉스 네트워크 프로그래밍 교재도 "I/O 다중화"라는 동기 방식으로 따로 센다. 알림을 받는다는 점만 보고 비동기·블로킹 칸에 넣는 자료도 있다. 이름보다 "함수가 언제 돌아오는가"와 "데이터를 누가 옮기는가"를 따지면 헷갈리지 않는다.

    이 항목의 측정 프로그램

    3절의 값은 이 PC(Core i9-14900KF, DDR5 64GB, Windows 11)에서 아래 프로그램을 cl /O2로 빌드해 5번 실행한 범위다. CPU 시간은 QueryThreadCycleTime으로 잰 사이클을 TSC(CPU의 시간 기록 계수기)가 1ms에 세는 수로 나눈 값이다. 이 PC에서 QueryThreadCycleTime은 TSC와 같은 속도(3,187MHz)로 센다. 200ms 동안 쉬지 않고 돌며 견주니 스레드의 사이클이 TSC가 센 수의 0.988~0.996이었다.

    /* 36번 측정: 보내면 30ms, 120ms, 60ms 뒤에 답이 오는 요청 셋을 네 가지 방법으로 처리한다 */
#include <stdio.h>
#include <intrin.h>
#include <windows.h>
#pragma comment(lib, "winmm.lib")

#define K 3
static const int delay_ms[K] = { 30, 120, 60 };
static HANDLE wr[K], rd[K], srv[K];

static DWORD WINAPI server(LPVOID arg) {
    int i = (int)(INT_PTR)arg;
    DWORD w;
    Sleep(delay_ms[i]);                    /* 답이 늦게 온다 (네트워크, 디스크) */
    WriteFile(wr[i], "answer", 6, &w, NULL);
    return 0;
}

static void send_request(int i) { srv[i] = CreateThread(NULL, 0, server, (LPVOID)(INT_PTR)i, 0, NULL); }

static void make_pipes(BOOL overlapped) {
    static int serial;
    for (int i = 0; i < K; i++) {
        char name[64];
        sprintf_s(name, sizeof name, "\\\\.\\pipe\\cs36_%lu_%d", GetCurrentProcessId(), serial++);
        rd[i] = CreateNamedPipeA(name, PIPE_ACCESS_INBOUND | (overlapped ? FILE_FLAG_OVERLAPPED : 0),
                                 PIPE_TYPE_BYTE, 1, 4096, 4096, 0, NULL);
        wr[i] = CreateFileA(name, GENERIC_WRITE, 0, NULL, OPEN_EXISTING, 0, NULL);
    }
}

static double cycles_per_ms;
static double cpu_ms(void) {
    ULONG64 c;
    QueryThreadCycleTime(GetCurrentThread(), &c);
    return (double)c / cycles_per_ms;
}

static DWORD WINAPI blocking_reader(LPVOID arg) {
    char buf[16]; DWORD n;
    ReadFile(rd[(int)(INT_PTR)arg], buf, sizeof buf, &n, NULL);
    return 0;
}

int main(void) {
    timeBeginPeriod(1);                     /* Sleep을 1ms 단위로 (32번 항목) */
    LARGE_INTEGER f, a, b;
    QueryPerformanceFrequency(&f);
    QueryPerformanceCounter(&a);            /* 사이클을 ms로 바꾸는 비율: 50ms 동안 TSC가 센 수 */
    unsigned __int64 r0 = __rdtsc();
    Sleep(50);
    unsigned __int64 r1 = __rdtsc();
    QueryPerformanceCounter(&b);
    cycles_per_ms = (double)(r1 - r0) / ((double)(b.QuadPart - a.QuadPart) * 1000.0 / f.QuadPart);

    char buf[16];
    DWORD n;
    const char *name[] = { "blocking, one by one", "non-blocking polling", "async notification", "three blocking threads" };
    for (int model = 0; model < 4; model++) {
        make_pipes(model == 2);
        double c0 = cpu_ms();
        QueryPerformanceCounter(&a);
        if (model == 0) {                   /* 동기·블로킹: 보내고 답이 올 때까지 기다리고, 그다음을 보낸다 */
            for (int i = 0; i < K; i++) { send_request(i); ReadFile(rd[i], buf, sizeof buf, &n, NULL); }
        } else if (model == 1) {            /* 동기·논블로킹: 다 보내 두고, 왔는지 계속 물어본다 */
            for (int i = 0; i < K; i++) send_request(i);
            int done[K] = { 0 }, left = K;
            while (left)
                for (int i = 0; i < K; i++) {
                    DWORD avail = 0;
                    if (!done[i] && PeekNamedPipe(rd[i], NULL, 0, NULL, &avail, NULL) && avail) {
                        ReadFile(rd[i], buf, sizeof buf, &n, NULL);
                        done[i] = 1; left--;
                    }
                }
        } else if (model == 2) {            /* 비동기: 다 보내고 읽기를 걸어 둔 뒤, 끝났다는 알림을 기다린다 */
            OVERLAPPED ov[K] = { 0 };
            HANDLE ev[K];
            char bufs[K][16];
            for (int i = 0; i < K; i++) {
                send_request(i);
                ev[i] = ov[i].hEvent = CreateEventA(NULL, TRUE, FALSE, NULL);
                ReadFile(rd[i], bufs[i], sizeof bufs[i], NULL, &ov[i]);   /* 바로 돌아온다 (ERROR_IO_PENDING) */
            }
            WaitForMultipleObjects(K, ev, TRUE, INFINITE);
        } else {                            /* 스레드 셋이 하나씩 맡아 블로킹으로 기다린다 */
            HANDLE r[K];
            for (int i = 0; i < K; i++) { send_request(i); r[i] = CreateThread(NULL, 0, blocking_reader, (LPVOID)(INT_PTR)i, 0, NULL); }
            WaitForMultipleObjects(K, r, TRUE, INFINITE);
        }
        QueryPerformanceCounter(&b);
        double c1 = cpu_ms();
        WaitForMultipleObjects(K, srv, TRUE, INFINITE);
        printf("%-22s total %5.1f ms, main cpu %6.2f ms\n", name[model],
               (double)(b.QuadPart - a.QuadPart) * 1000.0 / f.QuadPart, c1 - c0);
    }
    timeEndPeriod(1);
    return 0;
}

    정리¶

    • 블로킹/논블로킹은 "결과가 날 때까지 함수가 안 돌아오는가", 동기/비동기는 "결과를 누가 챙기는가"를 묻는다.
    • 하나씩 블로킹으로 처리하면 기다림이 더해진다. 기다림을 겹치면 빨리 끝나는데, 폴링은 기다리는 내내 CPU를 쓰고 비동기는 CPU를 거의 쓰지 않는다.
    • 요청이 많으면 요청마다 스레드를 두기보다, 적은 스레드로 많은 I/O를 걸어 두고 알림을 받는다(IOCP, epoll, async/await).
