    34. 스레드 동기화: 임계 영역, 뮤텍스, 세마포어. 경쟁 상태를 직접 재현하고 고치기¶

    직접 AI 없이 직접 할 수 있어야 하는 항목

    스레드 둘이 같은 변수를 각각 100만 번씩 1 늘리면 200만이 될까? 이 PC에서 해 보니 100만을 조금 넘는 수가 실행할 때마다 다르게 나왔다. Release로 빌드하면 늘 정확히 100만이 나와서, 실행마다 같으니 경쟁 상태처럼 보이지도 않았다. 동시성 버그는 테스트를 통과하다가 운영 중에 가끔 터지고, AI가 짠 코드에서도 가장 알아채기 어렵다. 직접형 항목이므로 경쟁 상태를 직접 만들고, 잠금으로 고치고, 그 비용을 재 본다.

    이 항목에서 배우는 것¶

    • count++ 같은 한 줄이 왜 스레드 사이에서 깨지는지 기계어 단계로 설명할 수 있다.
    • 임계 영역을 잠금(CRITICAL_SECTION, SRWLOCK)이나 원자적 연산(InterlockedIncrement)으로 직접 보호할 수 있다.
    • 세마포어로 동시에 들어가는 스레드 수를 제한하고, 잠금 방법마다 비용이 다름을 설명할 수 있다.

    1. count++는 세 단계라 다른 스레드가 끼어든다¶

    #include <stdio.h>
#include <windows.h>

int count = 0;

DWORD WINAPI add(LPVOID arg) {
    (void)arg;
    for (int i = 0; i < 1000000; i++)
        count++;                 /* 읽고, 1 더하고, 쓴다 */
    return 0;
}

int main(void) {
    HANDLE t[2];
    for (int i = 0; i < 2; i++)
        t[i] = CreateThread(NULL, 0, add, NULL, 0, NULL);
    WaitForMultipleObjects(2, t, TRUE, INFINITE);
    printf("%d\n", count);
    return 0;
}
    • count++는 기계어로 "메모리에서 레지스터로 읽기, 1 더하기, 메모리에 쓰기"의 세 단계다. 한 스레드가 읽고 쓰기 전에 다른 스레드가 같은 값을 읽으면, 늦게 쓴 쪽이 먼저 쓴 결과를 덮어쓴다. 이렇게 결과가 실행 순서에 따라 달라지는 상황이 경쟁 상태(race condition)다.
    • 위 프로그램을 기본 옵션(cl)으로 빌드하자 1,002,041~1,047,073으로 실행마다 달랐다. Visual Studio Debug와 같은 옵션에서도 1,000,000~1,229,841이었다.
    • 여러 스레드가 함께 쓰는 데이터를 다루는 코드 부분을 임계 영역(critical section)이라 한다. 임계 영역에는 한 번에 한 스레드만 들어가게 해야 한다.

    2. 한 번에 한 스레드만 들어가게 잠근다¶

    두 스레드의 "한 단계"를 원하는 차례로 눌러 결과를 1로 만들어 보고, 잠금과 InterlockedIncrement로 바꿔 같은 차례를 눌러 본다.

    직접 해 보기count++ 한 단계씩스레드 T1과 T2의 count++를 읽기, 더하기, 쓰기 한 단계씩 원하는 차례로 눌러 보며, 값을 잃어버리는 순서를 직접 만들고 잠금과 원자적 연산으로 막아 본다
    새 창에서 크게 열기
    • 뮤텍스(mutex, 상호 배제 잠금)는 한 번에 한 스레드만 쥘 수 있는 잠금이다. 임계 영역에 들어가기 전에 잠그고 나올 때 푼다. 다른 스레드가 쥐고 있으면 풀릴 때까지 기다린다. Windows에서는 CRITICAL_SECTION과 SRWLOCK이 한 프로세스 안의 스레드끼리 쓰는 뮤텍스다.
    • 정수 하나를 늘리는 정도라면 원자적 연산이 더 간단하다. InterlockedIncrement는 읽기, 더하기, 쓰기를 다른 코어가 끼어들 수 없는 명령 하나(lock inc)로 한다.
    • 잠금은 임계 영역 전체를 감싸야 한다. 잔액을 확인하는 줄과 빼는 줄을 따로 잠그면, 그 사이에 다른 스레드가 끼어든다(아래 "AI와 함께 확인하기").
    #include <windows.h>

int count;
CRITICAL_SECTION cs;                     /* 쓰기 전에 InitializeCriticalSection(&cs) */

DWORD WINAPI add_locked(LPVOID arg) {
    (void)arg;
    for (int i = 0; i < 1000000; i++) {
        EnterCriticalSection(&cs);       /* 잠그기: 다른 스레드가 쥐고 있으면 기다린다 */
        count++;                         /* 임계 영역 */
        LeaveCriticalSection(&cs);       /* 풀기 */
    }
    return 0;
}

    3. 세마포어는 N개까지 들여보내고, 잠금에는 비용이 든다¶

    • 세마포어는 "남은 자리 수"를 세는 잠금이다. 값이 3이면 세 스레드까지 들어가고, 넷째는 누군가 나올 때까지 기다린다. 동시 다운로드나 데이터베이스 연결처럼 "한꺼번에 몇 개까지"를 정할 때 쓴다(문제 3). 값이 1인 세마포어는 뮤텍스처럼 동작한다.
    • 잠금은 공짜가 아니다. 스레드 둘이 100만 번씩 늘릴 때 잠그지 않으면 1.7~2.6ms였지만 답이 틀렸다. SRWLOCK과 InterlockedIncrement는 20~26ms, CRITICAL_SECTION은 46~91ms였다.
    • Windows의 뮤텍스 커널 객체(CreateMutex)는 프로세스끼리도 쓸 수 있는 대신 4.1~4.3초가 걸렸다. 혼자 잠그고 풀면 200만 번에 0.43~0.44초라서, 큰 몫은 시스템 콜(29번(운영체제의 본질))이 아니다. 풀 때마다 기다리던 스레드가 잠금을 넘겨받아, 두 스레드가 번갈아 잠들고 깨어나기 때문으로 보인다(32번(CPU 스케줄링과 컨텍스트 스위칭)). 한 프로세스 안에서는 SRWLOCK이나 CRITICAL_SECTION을 쓴다.

    예측해 보기¶

    문제 1. 1절의 프로그램을 Visual Studio의 Debug와 Release로 빌드하면 각각 무엇이 나올까? 실행할 때마다 같을까?

    정답과 해설

    Debug와 같은 옵션에서는 이 PC에서 1,000,000~1,229,841로 실행마다 달랐다. Release(/O2)에서는 여덟 번 모두 정확히 1,000,000이었다. 최적화한 기계어를 보면 count를 레지스터에 한 번 읽어 두고 반복 안에서는 레지스터만 늘린 뒤, 끝에 한 번 쓴다. 두 스레드가 모두 0을 읽고 각자 1,000,000을 쓰니 늘 1,000,000이다. 실행마다 같은 답이 나와도 틀린 답일 수 있다. 원인은 최적화가 아니라 잠그지 않은 것이다.

    문제 2. 1절의 count++를 InterlockedIncrement((LONG *)&count)로 바꾸면 무엇이 출력될까?

    #include <stdio.h>
#include <windows.h>

LONG count = 0;

DWORD WINAPI add(LPVOID arg) {
    (void)arg;
    for (int i = 0; i < 1000000; i++)
        InterlockedIncrement(&count);    /* 읽기, 더하기, 쓰기를 한 명령으로 */
    return 0;
}

int main(void) {
    HANDLE t[2];
    for (int i = 0; i < 2; i++)
        t[i] = CreateThread(NULL, 0, add, NULL, 0, NULL);
    WaitForMultipleObjects(2, t, TRUE, INFINITE);
    printf("%ld\n", count);
    return 0;
}
    정답과 해설

    2000000. 원자적 연산은 다른 스레드가 사이에 끼어들 수 없다. 몇 번을 실행해도, Debug든 Release든 2,000,000이다.

    문제 3. 스레드 10개가 값이 3인 세마포어를 거쳐 50ms짜리 일을 한다. 동시에 일한 스레드는 가장 많을 때 몇 개일까?

    #include <stdio.h>
#include <windows.h>

static HANDLE sem;
static volatile LONG active, most;

static DWORD WINAPI worker(LPVOID arg) {
    (void)arg;
    WaitForSingleObject(sem, INFINITE);          /* 자리가 날 때까지 기다린다 (값 1 줄이기) */
    LONG now = InterlockedIncrement(&active);
    for (LONG m = most; now > m; m = most)       /* 지금까지 가장 많이 함께 일한 수 */
        InterlockedCompareExchange(&most, now, m);
    Sleep(50);                                   /* 다운로드 같은 일 */
    InterlockedDecrement(&active);
    ReleaseSemaphore(sem, 1, NULL);              /* 자리를 돌려준다 (값 1 늘리기) */
    return 0;
}

int main(void) {
    sem = CreateSemaphoreA(NULL, 3, 3, NULL);    /* 동시에 3개까지 */
    HANDLE t[10];
    for (int i = 0; i < 10; i++)
        t[i] = CreateThread(NULL, 0, worker, NULL, 0, NULL);
    WaitForMultipleObjects(10, t, TRUE, INFINITE);
    printf("%ld\n", most);
    return 0;
}
    정답과 해설

    3. 세마포어의 값이 3이라 넷째 스레드부터는 앞의 셋 중 하나가 자리를 돌려줄 때까지 기다린다. 10개가 3개씩 차례로 일하므로 전체로는 50ms짜리 일을 네 번 한 만큼 걸린다.

    직접 해보기¶

    실습: 경쟁 상태를 만들고 고치기

    1. 1절의 프로그램을 Visual Studio에서 Debug와 Release로 각각 5번 실행하고 결과를 적는다.
    2. add 안의 count++를 CRITICAL_SECTION으로 보호해 늘 2,000,000이 나오게 고친다. main에서 스레드를 만들기 전에 InitializeCriticalSection을 부른다.
    3. 계좌 둘(a, b, 처음 각각 1000)이 있다. 스레드 하나는 a에서 b로 1씩 10만 번, 다른 스레드는 b에서 a로 1씩 10만 번 옮긴다. 먼저 잠금 없이 실행해 a, b, a + b를 찍고, 잠금으로 고쳐 늘 1000 1000 2000이 나오게 한다.
    정답
    1. Debug는 100만을 조금 넘는 수가 실행마다 다르게, Release는 늘 1,000,000이 나온다(1절).

    2. 예시. 잠금은 반복 전체가 아니라 count++ 한 줄을 감싸도 된다. 반복 전체를 감싸면 한 스레드가 100만 번을 다 끝낸 뒤 다른 스레드가 들어가 사실상 차례로 돈다.

      #include <stdio.h>
#include <windows.h>

int count = 0;
CRITICAL_SECTION cs;

DWORD WINAPI add(LPVOID arg) {
    (void)arg;
    for (int i = 0; i < 1000000; i++) {
        EnterCriticalSection(&cs);
        count++;
        LeaveCriticalSection(&cs);
    }
    return 0;
}

int main(void) {
    InitializeCriticalSection(&cs);
    HANDLE t[2];
    for (int i = 0; i < 2; i++)
        t[i] = CreateThread(NULL, 0, add, NULL, 0, NULL);
    WaitForMultipleObjects(2, t, TRUE, INFINITE);
    DeleteCriticalSection(&cs);
    printf("%d\n", count);   /* 2000000 */
    return 0;
}

    3. 예시. 빼기와 더하기를 한 잠금 안에 넣는다. 잠금 없이 실행하면 이 PC에서 a가 84,947, b가 −82,988(합 1,959)이거나 합이 −105,089가 되는 등 실행마다 엉망이었다. 합이 우연히 2000인 실행에서도 a와 b는 1000이 아니었다.

      #include <stdio.h>
#include <windows.h>

int a = 1000, b = 1000;      /* 두 계좌. 합은 늘 2000이어야 한다 */
CRITICAL_SECTION cs;

void move(int *from, int *to) {
    EnterCriticalSection(&cs);
    *from -= 1;
    *to += 1;
    LeaveCriticalSection(&cs);
}

DWORD WINAPI a_to_b(LPVOID arg) { (void)arg; for (int i = 0; i < 100000; i++) move(&a, &b); return 0; }
DWORD WINAPI b_to_a(LPVOID arg) { (void)arg; for (int i = 0; i < 100000; i++) move(&b, &a); return 0; }

int main(void) {
    InitializeCriticalSection(&cs);
    HANDLE t[2] = { CreateThread(NULL, 0, a_to_b, NULL, 0, NULL), CreateThread(NULL, 0, b_to_a, NULL, 0, NULL) };
    WaitForMultipleObjects(2, t, TRUE, INFINITE);
    printf("%d %d %d\n", a, b, a + b);
    return 0;
}

      1000 1000 2000

      계좌마다 잠금을 따로 두고 두 잠금을 차례로 잡으면, 두 스레드가 서로 반대 순서로 잡다가 영원히 기다리게 될 수 있다. 다음 항목(35번(교착 상태))의 교착 상태다.

    AI와 함께 확인하기¶

    AI 활용 과제: 잔액이 있을 때만 빼는 함수

    1. AI에게 "C(Windows 스레드)로, 잔액이 1 이상일 때만 1을 빼고 성공 여부를 돌려주는 스레드 안전한 withdraw 함수"를 짜 달라고 한다.
    2. 잔액 100,000에서 스레드 8개가 각각 withdraw를 10만 번 부르는 시험 코드를 만든다. 실행하기 전에, 끝난 뒤 잔액과 성공 횟수를 예측한다.
    3. 실행해 대조한다. 잔액이 0이 아니거나 성공이 100,000번이 아니면 결과를 보여 주고 고치게 한다.
    확인할 점
    • 바른 답은 잔액 0, 성공 100,000번이다.
    • "잔액이 1 이상인가"를 잠금 밖에서 확인하고 빼기만 잠그는 코드가 흔하다. 이 PC에서 그렇게 짜자 잔액이 −5~−7, 성공이 100,005~100,007번이었다. 확인한 뒤 빼기 전에 다른 스레드가 마지막 1을 먼저 빼 갔기 때문이다. 확인과 빼기를 한 잠금 안에 넣어야 한다.
    • volatile을 붙여서 해결했다고 하는 답도 틀렸다. volatile은 컴파일러가 값을 레지스터에 두지 못하게 할 뿐, 읽기와 쓰기 사이에 다른 스레드가 끼어드는 것을 막지 못한다. 아래 측정 프로그램의 count도 volatile인데 잠그지 않으면 1,021,676~1,749,808이 나왔다.
    • 실행해서 맞았다고 끝내지 않는다. 경쟁 상태는 가끔만 드러나므로, 스레드 수와 반복 횟수를 늘려 여러 번 돌려 본다.

    더 알아보기¶

    잠금이 없어도 되는 경우

    모든 스레드가 읽기만 하는 데이터는 잠글 필요가 없다. 한 스레드만 쓰고 나머지는 읽는 경우는 잠가야 한다. 여러 값으로 된 데이터라면 읽는 쪽이 반쯤 바뀐 값을 볼 수 있기 때문이다. SRWLOCK은 읽기 잠금(AcquireSRWLockShared)과 쓰기 잠금을 나눠서, 읽는 스레드 여럿이 함께 들어가고 쓰는 스레드는 혼자 들어가게 한다. 데이터를 스레드마다 따로 두었다가 마지막에 합치면 잠금 자체를 없앨 수도 있다.

    이 항목의 측정 프로그램

    3절과 그림의 값은 이 PC(Core i9-14900KF, DDR5 64GB, Windows 11)에서 아래 프로그램을 cl /O2로 빌드해 5번씩 실행한 범위다. 측정 1은 스레드 둘이 서로 다투며 잠그는 경우라서, 다투는 스레드가 없을 때보다 느리다. 측정 2는 뮤텍스를 혼자 잠그고 풀 때(0.43~0.44초)와 둘이 다툴 때(이 프로그램으로는 3.8~4.2초)를 견준다.

    /* 34번 측정 1: 스레드 둘이 공유 변수를 100만 번씩 늘릴 때, 고치는 방법별 결과와 걸린 시간 */
#include <stdio.h>
#include <windows.h>

#define N 1000000
static volatile LONG count;
static int mode;
static CRITICAL_SECTION cs;
static SRWLOCK srw = SRWLOCK_INIT;
static HANDLE mtx;

static DWORD WINAPI add(LPVOID arg) {
    (void)arg;
    for (int i = 0; i < N; i++) {
        switch (mode) {
        case 0: count++; break;
        case 1: EnterCriticalSection(&cs); count++; LeaveCriticalSection(&cs); break;
        case 2: AcquireSRWLockExclusive(&srw); count++; ReleaseSRWLockExclusive(&srw); break;
        case 3: InterlockedIncrement(&count); break;
        case 4: WaitForSingleObject(mtx, INFINITE); count++; ReleaseMutex(mtx); break;
        }
    }
    return 0;
}

int main(void) {
    const char *name[] = { "none", "critical section", "srwlock", "interlocked", "mutex" };
    InitializeCriticalSection(&cs);
    mtx = CreateMutexA(NULL, FALSE, NULL);
    LARGE_INTEGER f, a, b;
    QueryPerformanceFrequency(&f);
    for (mode = 0; mode < 5; mode++) {
        count = 0;
        HANDLE t[2];
        QueryPerformanceCounter(&a);
        for (int i = 0; i < 2; i++) t[i] = CreateThread(NULL, 0, add, NULL, 0, NULL);
        WaitForMultipleObjects(2, t, TRUE, INFINITE);
        QueryPerformanceCounter(&b);
        printf("%-16s %8ld  %8.1f ms\n", name[mode], count, (double)(b.QuadPart - a.QuadPart) * 1000.0 / f.QuadPart);
        CloseHandle(t[0]); CloseHandle(t[1]);
    }
    return 0;
}

    /* 34번 측정 2: 뮤텍스를 200만 번 잠그고 풀 때, 스레드 하나가 혼자 할 때와 둘이 100만 번씩 다툴 때 */
#include <stdio.h>
#include <windows.h>

static HANDLE mtx;
static volatile LONG count;
static int per;

static DWORD WINAPI add(LPVOID arg) {
    (void)arg;
    for (int i = 0; i < per; i++) {
        WaitForSingleObject(mtx, INFINITE);
        count++;
        ReleaseMutex(mtx);
    }
    return 0;
}

int main(void) {
    mtx = CreateMutexA(NULL, FALSE, NULL);
    LARGE_INTEGER f, a, b;
    QueryPerformanceFrequency(&f);
    for (int n = 1; n <= 2; n++) {
        count = 0;
        per = 2000000 / n;
        HANDLE t[2];
        QueryPerformanceCounter(&a);
        for (int i = 0; i < n; i++) t[i] = CreateThread(NULL, 0, add, NULL, 0, NULL);
        WaitForMultipleObjects(n, t, TRUE, INFINITE);
        QueryPerformanceCounter(&b);
        printf("%d thread(s) %8ld  %8.1f ms\n", n, count, (double)(b.QuadPart - a.QuadPart) * 1000.0 / f.QuadPart);
        for (int i = 0; i < n; i++) CloseHandle(t[i]);
    }
    return 0;
}

    정리¶

    • count++는 읽기, 더하기, 쓰기의 세 단계라 스레드 사이에서 끼어들 수 있다. 결과가 실행 순서에 따라 달라지는 것이 경쟁 상태다.
    • 함께 쓰는 데이터를 다루는 임계 영역은 잠금(CRITICAL_SECTION, SRWLOCK)으로 감싸거나 원자적 연산(InterlockedIncrement)으로 바꾼다. 확인과 변경은 한 잠금 안에 넣는다.
    • 세마포어는 N개까지 들여보낸다. 잠금은 비용이 있고, 커널 객체인 뮤텍스는 프로세스 안의 잠금보다 훨씬 비싸다.
