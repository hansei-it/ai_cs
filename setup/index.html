    실습 환경¶

    이 강의의 예제는 C, C#, Python, SQL, JavaScript로 직접 실행해 확인한다. 이 페이지는 그 환경을 내 PC에 똑같이 만드는 방법이다. 본문의 숫자와 메시지는 아래 환경에서 확인했다. 버전이 조금 달라도 실습에는 지장이 없다.

    • Windows 11, Visual Studio Community 2026 (18.10, C 컴파일러 MSVC 19.51)
    • .NET SDK 10.0.401
    • Python 3.14.0 (SQLite 3.50.4가 들어 있다)
    • MySQL 8.4.11 (53·54번만)
    • Node.js v24.10.0, Chrome 155 (섹션 7)
    • Git 2.51.1 (76번, 섹션 10)
    • Docker Desktop 4.48.0(엔진 28.5.1), WSL 2.6.1 (섹션 11)

    1. 설치할 것¶

    • Visual Studio Community 2026: 설치 프로그램(Visual Studio Installer)의 워크로드에서 두 가지를 고른다.
      • C++를 사용한 데스크톱 개발: C 예제를 컴파일하는 MSVC와 링커가 들어 있다.
      • .NET 데스크톱 개발: C# 예제를 빌드하고 실행하는 .NET SDK가 함께 깔린다. 18번의 ASP.NET Core 예제도 이 SDK에 들어 있는 웹 앱 템플릿(dotnet new web)으로 만든다.
    • Python 3.14: python.org의 Downloads → Windows 페이지에서 Python 3.14의 최신 릴리스(2026년 10월 현재 3.14.8)를 찾아 Windows installer (64-bit)를 받는다. 페이지 맨 위의 "Python install manager"와 3.15는 이 강의를 확인한 환경과 다르다. 설치 첫 화면에서 Add python.exe to PATH를 켠다. 켜지 않으면 명령 프롬프트에서 python을 입력했을 때 Microsoft Store가 열린다.

    설치가 끝나면 명령 프롬프트에서 확인한다. dotnet --list-sdks에 10.0으로 시작하는 줄이 있고, python --version이 Python 3.14로 시작하면 된다.

    > dotnet --list-sdks
10.0.401 [C:\Program Files\dotnet\sdk]
> python --version
Python 3.14.0

    2. C 소스는 서명 있는 UTF-8로 저장한다¶

    • 이 강의의 C 예제는 소스를 서명 있는 UTF-8(파일 맨 앞에 EF BB BF 세 바이트가 붙은 UTF-8)로 저장하고, 컴파일 옵션은 기본값으로 둔다. 컴파일러는 서명을 보고 소스를 UTF-8로 읽은 뒤, 문자열은 Windows의 기본 인코딩인 CP949로 바꿔 넣는다. 그래서 콘솔에 한글이 그대로 보인다.
    • 서명이 없으면 컴파일러가 소스를 CP949로 읽는다. 경고 C4819가 나고 한글 문자열은 이미 깨져 있다.
    • UTF-8 바이트 자체를 다루는 4번 항목만 /utf-8을 켠다. 이때 콘솔에 한글을 바르게 보이려면 프로그램 처음에 SetConsoleOutputCP(CP_UTF8);(windows.h)를 부른다.

    Visual Studio에서 C 프로젝트를 만드는 순서는 다음과 같다.

    1. "새 프로젝트 만들기"에서 C++의 빈 프로젝트를 고른다. Visual Studio에는 C 전용 템플릿이 없지만, 파일 이름이 .c로 끝나면 C로 컴파일한다.
    2. 솔루션 탐색기에서 프로젝트를 오른쪽 클릭해 추가 → 새 항목 → C++ 파일(.cpp)을 고르고, 이름을 main.c로 바꿔 만든다.
    3. 파일 → 다른 이름으로 저장에서 [저장] 단추 옆의 화살표를 눌러 인코딩하여 저장을 고르고, 인코딩을 유니코드(서명 있는 UTF-8) - 코드 페이지 65001로 정한다. 파일마다 처음 한 번 하면 된다.

    저장한 파일에 서명이 있는지는 PowerShell에서 확인한다. 00000000으로 시작하는 줄의 첫 세 바이트가 EF BB BF이면 서명이 있다. Windows PowerShell 5.1에서는 그 앞에 파일 경로(Path:) 줄과 열 번호(00 01 02 …) 줄이 먼저 나온다.

    3. 구성, 플랫폼, 컴파일 옵션¶

    • Debug와 Release, x64와 x86: 도구 모음의 솔루션 구성 상자(Debug, Release)와 솔루션 플랫폼 상자(x64, x86)에서 고른다. Debug는 최적화를 끄고(/Od) 실행 중 검사(/RTC1)와 디버그용 C 런타임(디버그 힙)을 쓰는 구성이고, Release는 최적화(/O2)를 켠 구성이다. 본문의 결과는 x64 기준이다. 32비트와 비교하는 곳(8·10번)과 Debug와 Release의 결과가 다른 곳(9·11번)은 본문에 둘 다 적었다.
    • 옵션 넣기: 솔루션 탐색기에서 프로젝트를 오른쪽 클릭 → 속성 → 구성 속성 → C/C++ → 명령줄 → 추가 옵션에 /utf-8 같은 옵션을 넣는다. 넣기 전에 속성 창 맨 위의 구성 상자를 모든 구성, 플랫폼 상자를 모든 플랫폼으로 바꾼다. 그대로 두면 지금 고른 조합(예: Debug와 x64)에만 들어가서, 8·10번처럼 x86으로 바꾸거나 9·11번처럼 Release로 바꾸면 옵션이 빠진다. 32비트는 솔루션 플랫폼 상자에서는 x86, 속성 창에서는 Win32로 보인다.
    • SDL 검사: 새로 만든 프로젝트는 C/C++ → 일반 → SDL 검사가 켜져 있다. 그래서 초기화하지 않은 변수(C4700)나 strcpy(C4996) 같은 경고가 오류가 되어 빌드가 멈춘다(10·11번).
    • 스택 크기: 링커 → 시스템 → 스택 예약 크기에서 바꾼다(9번).
    • 실행: 디버그 메뉴의 디버그하지 않고 시작(Ctrl+F5)으로 실행한다. 프로그램이 끝나도 콘솔 창이 남고, 마지막 줄에 종료 코드가 나온다. 8~11번에서 일부러 멈추는 예제의 0xC0000005 같은 값을 여기서 읽는다. 디버깅 시작(F5)으로 실행하면 멈추는 줄에서 디버거가 서고, 11번 실습 3의 누수 보고처럼 디버그 메시지가 출력 창에 나온다.

    4. 명령줄에서 cl과 dumpbin 쓰기¶

    6·7번처럼 컴파일 단계를 하나씩 보거나 실행 파일을 들여다볼 때는 명령줄을 쓴다.

    • 시작 메뉴의 x64 Native Tools Command Prompt for VS를 연다. 그 안에서 cl(컴파일), link(링크), dumpbin(실행 파일 보기)을 바로 쓸 수 있다.
    • 이 창은 Visual Studio 설치 폴더에서 시작하는데, 그곳에는 파일을 만들 수 없다. 먼저 cd /d D:\실습처럼 작업 폴더로 옮긴다(/d는 드라이브도 바꾼다).
    • 시작 메뉴에 함께 있는 "Developer Command Prompt for VS"와 "Developer PowerShell for VS", Visual Studio의 보기 → 터미널은 32비트(x86)용이 기본이다. 어느 창이든 cl만 입력해 보고, 첫 줄 끝이 for x64인지 확인한다. 이 PC에서 6번의 add 함수가 x64 프롬프트에서는 8D 04 11 C3, 이 프롬프트에서는 8B 44 24 04 03 44 24 08 C3이 되었다. 본문의 명령줄 결과는 x64 기준이다.
    • 명령줄 cl의 기본 옵션은 Visual Studio 프로젝트와 다르다. 최적화와 SDL 검사가 꺼져 있고, C 런타임을 실행 파일 안에 넣는다(/MT, 7번).

    5. C#, Python, SQL¶

    • C#: 명령 프롬프트에서 dotnet new console -o Hello로 프로젝트를 만들고, cd Hello 뒤 dotnet run으로 실행한다. 실행 시간을 잴 때는 dotnet run -c Release로 Release 빌드를 쓴다(12번). Visual Studio에서는 "새 프로젝트 만들기"에서 C#의 콘솔 앱을 고른다. 새 프로젝트는 null 검사(<Nullable>enable</Nullable>)가 켜져 있어서 16번의 경고 CS8602를 볼 수 있다.
    • Python: 예제는 .py 파일로 저장해 python 파일이름.py로 실행한다. 패키지를 쓰는 항목(16·17번)은 프로젝트 폴더에서 python -m venv venv로 가상 환경을 만들고 켠다(venv\Scripts\activate). PowerShell의 실행 정책 때문에 켜기가 막히면 가상 환경의 Python을 직접 부른다. 설치는 venv\Scripts\python -m pip install mypy, 실행은 venv\Scripts\python -m mypy 파일이름.py다.
    • SQL(섹션 6): 데이터베이스 항목의 SQL은 Python에 든 SQLite로 실행한다. 따로 설치할 것이 없다(python -m sqlite3는 Python 3.12부터 있다). 명령 프롬프트에서 python -m sqlite3 school.db를 실행하면 sqlite>가 나오고, SQL을 붙여 넣으면 결과가 행마다 (1, '김하나')처럼 나온다. .quit로 끝낸다. 파일 이름을 빼면 끝낼 때 사라지는 메모리 DB다. 한 줄에 문장을 둘 쓰면 ProgrammingError: You can only execute one statement at a time.이 나므로, AI가 만든 SQL을 붙여 넣을 때도 한 줄에 문장 하나씩 둔다.
    C#과 Python의 한글 출력

    C#의 Console.WriteLine은 문자열을 콘솔의 코드 페이지(949)에 맞춰 바꿔 내보내고, Python의 print는 Windows의 유니코드 콘솔 기능으로 글자를 그대로 넘긴다. 이 PC의 코드 페이지 949 콘솔에서 둘 다 한글이 바르게 보였다. 컴파일할 때 정해진 바이트를 그대로 내보내는 C와 달리 /utf-8 같은 문제가 없다.

    6. MySQL (53·54번)¶

    락과 격리 수준을 다루는 53·54번만 MySQL 8.4를 쓴다. 두 연결이 같은 행을 고칠 때 행 잠금과 격리 수준에 따라 무엇이 보이는지를 봐야 하는데, SQLite는 쓰는 동안 파일 전체를 잠그고 격리 수준을 고를 수 없어서다.

    • 설치: dev.mysql.com의 MySQL Community Server 다운로드 페이지에서 "Select Version"을 8.4로 시작하는 LTS로 바꾸고(맨 위에는 더 새 버전이 먼저 나온다), "Windows (x86, 64-bit), MSI Installer"를 받아 설치한다. 설치가 끝나면 이어서 뜨는 MySQL Configurator에서 root 비밀번호를 정하고, Windows 서비스로 등록한다.
    • 접속: 명령 프롬프트를 둘 열고, 각각 "C:\Program Files\MySQL\MySQL Server 8.4\bin\mysql.exe" -u root -p로 접속한다. 비밀번호를 넣으면 mysql>이 나온다. 두 창이 53·54번의 세션 A와 B다.
    • Docker를 쓴다면: 설치 대신 docker run -d --name cs-mysql -e MYSQL_ROOT_PASSWORD=비밀번호 -p 127.0.0.1:3306:3306 mysql:8.4로 띄운다(비밀번호는 영문과 숫자로 바꾼다). 처음 띄우면 준비하는 데 시간이 걸리므로, docker logs cs-mysql에 port: 3306이 붙은 ready for connections 줄이 보인 뒤에 접속한다(처음 준비할 때 잠깐 뜨는 port: 0 줄은 아직이다). 창마다 docker exec -it -e LANG=C.UTF-8 cs-mysql mysql -u root -p로 접속한다. 컨테이너의 문자 설정(LANG)이 비어 있어서, 한글을 입력할 수 있게 UTF-8을 함께 준다. 이 강의의 MySQL 결과는 이 방법(MySQL 8.4.11)으로 확인했다.
    • 끝낼 때: 창을 그냥 닫지 말고 exit로 나온다. 특히 Docker로 접속한 창은 닫아도 컨테이너 안의 접속이 남을 수 있다. 이 PC에서 창의 docker 명령을 끝내도 서버의 접속은 남아 있었다. 열린 트랜잭션이 있으면 그 잠금도 남아, 다른 창의 문장이 기다리게 된다.

    접속한 뒤 SELECT @@version, @@transaction_isolation;을 실행해 8.4로 시작하는 버전과 REPEATABLE-READ가 나오면 된다.

    7. JavaScript (섹션 7)¶

    웹 섹션의 예제는 JavaScript다. 화면과 DOM이 필요한 예제는 브라우저에서, 그 밖의 예제와 서버는 Node.js로 실행한다. npm으로 받는 외부 패키지는 쓰지 않는다.

    • 브라우저 콘솔: Chrome이나 Edge에서 F12를 눌러 개발자 도구를 열고 콘솔(Console) 탭에 코드를 붙여 넣은 뒤 Enter를 누른다. 처음 붙여 넣을 때 브라우저가 경고하며 정해진 글을 입력하라고 하면, 안내대로 입력하고 다시 붙여 넣는다.
    • HTML 파일: 메모장이나 VS Code에서 index.html처럼 저장하고(UTF-8), 탐색기에서 두 번 누르면 브라우저로 열린다. 파일을 고쳤으면 브라우저에서 F5로 새로 고친다.
    • Node.js: nodejs.org의 다운로드 페이지에서 버전 목록의 24로 시작하는 LTS(2026년 10월 현재 v24.22.0)를 고른 채 Windows 설치 프로그램 (.msi) 단추로 받아 설치한다. 2026년 10월 28일부터는 v26이 새 LTS가 되지만, 이 강의는 v24로 확인했다. 새 명령 프롬프트에서 node --version으로 확인하고, 예제는 .js 파일로 저장해 node 파일이름.js로 실행한다. 이 PC의 명령 프롬프트(코드 페이지 949)에서 한글 출력이 바르게 보였다.
    • 파일에 import, export, 최상위 await가 있으면 Node 24는 그 파일을 ES 모듈로 읽는다. 이때는 require를 쓸 수 없다. npm init으로 package.json을 만든 폴더에서는 그 안의 "type" 값을 따르므로 다르게 읽힐 수 있다. 이 강의의 Node 결과는 v24.10.0, 브라우저 결과는 Chrome 155에서 확인했다.

    8. Git (76번, 섹션 10)¶

    76번과 소프트웨어 공학 섹션의 Git 실습은 PowerShell이나 명령 프롬프트에서 git 명령으로 한다. 76번의 파일 만들기 명령(Set-Content, $env:)은 PowerShell용이다.

    • 설치: git-scm.com의 Install → Windows 페이지에서 "Click here to download"를 눌러 최신 x64 판(Git for Windows/x64 Setup, 2026년 10월 현재 2.56.0)을 받는다. 이 강의는 Git 2.51.1로 확인했다. 설치 화면은 기본값을 그대로 두고 진행해도 되지만, 편집기를 고르는 화면(Choosing the default editor used by Git)의 기본값은 Vim이다. 익숙하지 않다면 그 화면에서 메모장(Notepad)처럼 쉬운 편집기를 고른다. 설치 뒤에는 git config --global core.editor notepad로 바꿀 수 있다. 이 강의의 git 명령은 -m과 --no-edit를 붙여 편집기를 열지 않는다.
    • 확인: 새 PowerShell 창에서 git --version이 git version 2.으로 시작하면 된다. 설치 전에 열어 둔 창에서는 git을 찾지 못하므로 창을 새로 연다.
    • 이름과 메일: 커밋에 남을 이름과 메일을 처음에 한 번 정한다. 정하지 않으면 첫 커밋에서 멈추고 정하라고 한다.
    git config --global user.name "홍길동"
git config --global user.email "gildong@example.com"
    • 이 PC의 Git for Windows에서는 git의 메시지가 영어로 나왔다. 한글 커밋 메시지와 파일 속 한글은 PowerShell 창의 git log와 git diff에서 바르게 보였다.

    9. Docker (섹션 11)¶

    91번은 컨테이너를 실제로 띄워 본다. 설치하지 못한 경우에도 본문에 이 PC의 결과가 있어 따라갈 수 있다.

    • 설치: Docker 문서의 "Install Docker Desktop on Windows" 페이지에서 Docker Desktop for Windows - x86_64를 받아 설치한다. WSL 2를 쓰는 기본값을 그대로 둔다. 요구사항 목록은 Windows 11 64비트 Pro, Enterprise, Education 판 23H2(빌드 22631) 이상, 메모리 8GB, BIOS/UEFI에서 켠 하드웨어 가상화, WSL 2.1.5 이상이다. 같은 문서의 참고에 따르면 Home과 Education 판은 리눅스 컨테이너만 돌릴 수 있는데, 이 강의는 리눅스 컨테이너만 쓴다.
    • WSL: PowerShell에서 wsl --version으로 판을 본다. 2.1.5보다 낮으면 wsl --update로 올린다. WSL이 없으면 관리자 권한 PowerShell에서 wsl --install로 깔고 PC를 다시 시작한다.
    • 처음 켜기: Docker Desktop을 처음 켜면 서비스 약관이 나온다. Accept를 눌러야 엔진이 뜬다.
    • 라이선스: Docker Desktop은 개인, 교육, 비영리 오픈 소스, 작은 회사(직원 250명 미만이면서 연 매출 1천만 달러 미만)에는 무료다. 수업 실습은 교육에 해당한다.
    • 확인: Docker Desktop을 켠 뒤 PowerShell에서 docker version을 실행해 Server: 부분이 나오면 된다. 엔진이 아직 뜨지 않았으면 오류가 나니 잠시 뒤 다시 한다.
    • 정리: 실습에서 만든 이미지는 docker rmi 이미지이름으로 지운다. 받아 온 기본 이미지(alpine:3.22 12.8MB, python:3.14-slim 178MB)도 더 쓰지 않으면 같은 명령으로 지운다. 이미지를 지워도 빌드 캐시는 남는다. 차지한 양은 docker system df의 Build Cache 줄로 보고, 빌드 캐시만 지우려면 docker builder prune을 쓴다. docker system prune처럼 한꺼번에 지우는 명령은 다른 실습이나 프로젝트의 컨테이너와 이미지까지 지울 수 있어 쓰지 않는다.

    환경 점검¶

    실습: 내 PC의 C 환경 확인하기

    1. 2절의 순서대로 빈 프로젝트에 main.c를 서명 있는 UTF-8로 만들고, 아래 프로그램을 실행한다. 빌드할 때 경고가 나는지도 본다.
    2. 파일 이름을 main.cpp로 바꿔 다시 실행한다. 어느 줄이 바뀌는지 본다.
    3. 다시 main.c로 돌리고, 추가 옵션에 /utf-8을 넣어 실행한다. 어느 줄이 바뀌는지 본다.
    #include <stdio.h>
#include <string.h>

int main(void) {
    const char *s = "한글";
    printf("%zu\n", strlen(s));
    for (size_t i = 0; i < strlen(s); i++)
        printf("%02X ", (unsigned char)s[i]);   /* 문자열에 들어간 바이트 */
    printf("\n");
    printf("%zu\n", sizeof('a'));
    return 0;
}
    확인할 점 
    4
C7 D1 B1 DB
4
    • 1에서 위처럼 나오고 경고가 없으면 C 환경이 강의와 같다. 둘째 줄은 "한글"이 CP949로 들어간 바이트다(한 = C7 D1, 글 = B1 DB).
    • 둘째 줄이 3F 9C EA 3F이고 빌드할 때 경고 C4819가 났으면 파일이 서명 없이 저장된 것이다. 첫 줄은 똑같이 4라서 바이트를 봐야 안다. 2절의 3번으로 다시 저장한다.
    • 2에서는 셋째 줄이 1이 된다. 파일 이름이 .cpp면 C++로 컴파일하는데, C에서 'a'는 int(4바이트)이고 C++에서는 char(1바이트)다. 이 강의의 C 예제는 .c 파일로 실행한다.
    • 3에서는 첫 줄이 6, 둘째 줄이 ED 95 9C EA B8 80이 된다. 한글이 UTF-8 3바이트씩으로 들어간다(4번 항목). 3에서도 4와 C7 D1 B1 DB 그대로이고 경고 C4828이 나면, 파일이 서명 없는 CP949(ANSI)로 저장된 것이다. 옵션이 기본값일 때는 차이가 없지만 /utf-8을 켜는 4번에서 틀리므로, 2절의 3번으로 다시 저장한다.
