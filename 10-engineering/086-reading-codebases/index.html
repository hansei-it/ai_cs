    86. 대규모 코드베이스 읽기: 처음 보는 프로젝트의 구조 파악과 탐색¶

    직접 AI 없이 직접 할 수 있어야 하는 항목

    일은 대개 빈 파일이 아니라 남이 쓴 큰 코드에서 시작한다. AI가 코드를 많이 쓸수록, 내가 쓰지 않은 코드를 빨리 읽고 믿을 수 있는지 판단하는 일이 늘어난다. 직접형 항목이므로 섹션 5와 8에서 써 온 Python의 http.server를 처음 보는 코드베이스로 삼아, 지도를 그리고 질문을 따라 실제 소스를 읽는다. 표준 라이브러리의 소스는 Python을 설치한 PC에 이미 있다(실습 환경).

    이 항목에서 배우는 것¶

    • 처음 보는 코드에서 파일, 크기, 클래스와 그 부모 관계로 지도를 그릴 수 있다.
    • 질문 하나를 정하고 검색, 호출 스택으로 답을 찾아갈 수 있다.
    • 글자 검색이 못 찾는 길(이름을 만들어 부르는 코드)을 실행해서 확인할 수 있다.

    1. 다 읽지 않는다: 지도를 그리고 질문 하나를 따라간다¶

    • 먼저 돌려 보고, 파일과 크기, 클래스의 부모 관계로 지도를 그린다. 지도가 있어야 길을 잃지 않는다.
    • 그다음 "답이 하나인 질문"을 정한다. "이 코드가 어떻게 동작하나"는 너무 넓고, "do_GET은 누가 부르나"는 답이 하나다.
    • 질문 하나에 필요한 길만 읽고, 다음 질문으로 지도를 넓힌다.

    2. 내 코드는 큰 코드의 작은 끝에 붙어 있다¶

    • 섹션 5와 8에서 짠 서버는 do_GET 같은 메서드 몇 개를 덮어썼을 뿐이다. 나머지는 표준 라이브러리 두 파일, 2,000줄이 넘는 코드가 했다.
    • 물려받은 클래스의 메서드를 덮어쓰면, 그 메서드를 부르는 쪽(부모 클래스의 코드)이 내 코드를 부른다. 그래서 "누가 부르나"를 알려면 부모 클래스를 읽어야 한다.

    3. 검색이 못 찾는 길은 실행해서 본다¶

    직접 해 보기요청 하나의 길 따라가기HTTPServer와 ThreadingHTTPServer를 골라, GET 요청 하나가 do_GET에 닿기까지 지나는 함수를 한 칸씩 따라가고, 칸을 눌러 파일 이름, 줄 번호, 하는 일을 본다
    새 창에서 크게 열기
    • 이름이나 글자로 찾는 검색은 가장 빠른 도구지만, 메서드 이름을 문자열로 만들어 부르는 코드는 찾지 못한다(문제 1).
    • 그럴 때는 그 함수 안에서 호출 스택을 찍거나 디버거로 멈춰(85번(디버깅 방법론)), 실제로 지나온 길을 본다. 위젯이 그렇게 찍은 길이다(문제 3).

    예측해 보기¶

    문제 1. http/server.py에서 do_GET이라는 글자를 찾으면 몇 곳이 나올까? 그 가운데 do_GET을 부르는 줄이 있을까?

    정답과 해설

    한 곳이고, 부르는 줄은 없다. 나온 한 곳은 SimpleHTTPRequestHandler가 do_GET을 정의하는 줄(723줄)이다. 부르는 쪽은 handle_one_request(444줄부터)다. 요청 줄에서 읽은 메서드 이름 앞에 'do_'를 붙여 이름을 만들고(466줄), getattr로 그 이름의 메서드를 찾아(472줄) 부른다(473줄). 이름이 실행할 때 만들어지므로 do_GET이라는 글자는 코드에 없다. 그래서 POST 요청이 오면 같은 줄이 do_POST를 부르고, 없으면 501(Not Implemented)을 돌려준다. 줄 번호는 이 PC의 Python 3.14.0 기준이다. 실습 환경 페이지대로 3.14.8을 깔았다면 723·444·466·472·473줄이 738·459·481·487·488줄이다.

    문제 2. 65번(수직 확장 vs 수평 확장)에서 서버 클래스에 request_queue_size = 128을 적어 연결이 끊기는 것을 막았다. 이 이름은 socketserver.py의 어디서 쓰일까?

    정답과 해설

    TCPServer가 클래스 변수로 기본값 5를 두고(444줄), 서버를 켤 때 server_activate(481줄)가 소켓의 listen에 그 값을 넘긴다(487줄). listen의 값은 운영체제가 받아 두는, 아직 서버가 꺼내 가지 않은 연결의 대기열 길이다. 65번에서는 손님 64명이 한꺼번에 연결해 5로는 넘쳤다. 자식 클래스에 같은 이름을 적으면 self.request_queue_size가 자식의 값을 찾으므로, 부모의 코드를 고치지 않고 값만 바꿀 수 있다. 덮어쓸 수 있는 이름이 무엇인지는 문서보다 부모 클래스의 코드가 정확히 알려 준다. socketserver.py의 이 줄 번호는 3.14.0과 3.14.8이 같다.

    문제 3. 위젯에서 서버를 HTTPServer에서 ThreadingHTTPServer로 바꾸면, do_GET까지의 호출 스택은 어떻게 달라질까? 누르기 전에 적어 본다.

    정답과 해설

    serve_forever, _handle_request_noblock, process_request가 사라지고 process_request_thread가 나타난다. 11칸이 9칸이 된다. ThreadingHTTPServer가 함께 물려받은 ThreadingMixIn의 process_request는 요청을 직접 처리하지 않고, 새 스레드를 만들어 process_request_thread를 맡긴다. 호출 스택은 스레드마다 따로라서, 처리하는 스레드의 스택에는 요청을 받은 스레드의 serve_forever가 없고, 스레드를 시작하는 세 칸 다음 process_request_thread부터 이어진다. 위젯의 두 스택은 이 PC에서 두 서버로 실제 요청을 보내 찍은 것이다.

    직접 해보기¶

    실습: http.server의 지도를 그리고 질문 하나 따라가기

    1. 아래 map.py를 실행해 두 모듈의 위치와 줄 수, 클래스와 그 부모 클래스를 본다. 출력으로 2절 그림 같은 지도를 종이에 그린다.
    2. 질문을 하나 정한다: "섹션 8에서 log_message를 덮어써 비워 두면 왜 접속 기록이 터미널에 안 찍혔나?" PowerShell에서 아래처럼 log_message를 찾고, 나온 줄마다 정의인지, 부르는 곳인지, 설명 글(주석이나 문서 문자열)인지 가린다.
    3. 부르는 곳의 함수를 다시 찾아 거슬러 올라가, do_GET 안의 send_response에서 터미널에 글자가 찍히기까지의 길을 줄 번호와 함께 적는다.
    4. 아래 trace_get.py를 실행해 do_GET까지 지나온 길을 찍고, 위젯과 지도에 견준다.
    $f = python -c "import http.server; print(http.server.__file__)"
Select-String -Path $f -Pattern "log_message"


    # map.py: 처음 보는 모듈의 지도를 그린다. 파일 위치와 줄 수, 클래스와 그 부모 클래스, 클래스가 시작하는 줄
import http.server
import inspect
import socketserver

for m in (socketserver, http.server):
    lines = open(m.__file__, encoding="utf-8").read().splitlines()
    print(f"{m.__name__}: {m.__file__} ({len(lines)}줄)")
    for name, cls in inspect.getmembers(m, inspect.isclass):
        if cls.__module__ == m.__name__ and not name.startswith("_"):
            bases = ", ".join(b.__name__ for b in cls.__bases__)
            print(f"  {inspect.getsourcelines(cls)[1]:>4}줄  {name}({bases})")


    # trace_get.py: do_GET이 불릴 때까지 어떤 함수들을 지나왔는지 찍는다
import http.client
import os
import threading
import traceback
from http.server import BaseHTTPRequestHandler, HTTPServer


class Handler(BaseHTTPRequestHandler):
    def do_GET(self):
        for f in traceback.extract_stack():           # 바깥부터 지금 줄까지의 호출 스택
            print(f"{os.path.basename(f.filename)}:{f.lineno} {f.name}")
        self.send_response(204)
        self.end_headers()

    def log_message(self, *args):
        pass


server = HTTPServer(("127.0.0.1", 0), Handler)
threading.Thread(target=server.serve_forever, daemon=True).start()
c = http.client.HTTPConnection("127.0.0.1", server.server_address[1])
c.request("GET", "/")
c.getresponse().read()
server.shutdown()

    확인할 점

    이 PC(Python 3.14.0)의 결과다. 경로는 Python을 설치한 곳에 따라 다르다. 실습 환경 페이지대로 3.14.8을 깔았다면 http/server.py가 1,445줄이고, 앞쪽 다섯 클래스(137~195줄)는 4줄 뒤(150줄 → 154줄), 그 밖의 줄은 대개 15줄 뒤다(624줄 → 639줄, 1297줄만 1323줄). socketserver.py는 같고 threading.py는 1줄 뒤다. 판이 바뀌면 줄 번호가 움직이는 것도 코드를 읽을 때 늘 겪는 일이니, 내 파일에서 찾은 줄로 읽는다.

    • 1단계: socketserver.py는 863줄, http/server.py는 1,419줄이었다. map.py는 클래스를 이름 차례로 찍는다. 예를 들어 150줄 ThreadingHTTPServer(ThreadingMixIn, HTTPServer), 195줄 BaseHTTPRequestHandler(StreamRequestHandler)가 나온다.
    • 2단계: log_message는 일곱 줄에서 나왔다. 624줄이 정의(def log_message)이고, 602줄(log_request 안)과 617줄(log_error 안)이 부르는 곳, 609줄과 611줄은 log_error의 문서 문자열(docstring, 함수 설명 글), 1268줄과 1297줄은 CGI 처리기 안이다.
    • 3단계: send_response가 550줄에서 log_request를 부르고, log_request가 602줄에서 log_message를 부르며, log_message가 645줄에서 sys.stderr에 한 줄을 쓴다. 자식 클래스가 log_message를 비워 두면 self.log_message가 자식의 빈 메서드를 찾아 이 마지막 단계가 사라진다. 오류 기록(log_error)도 같은 메서드를 지나므로 함께 사라진다는 것까지 읽힌다. 접속 기록만 끄려면 log_request를 덮어쓴다.
    • 4단계의 출력이다. 위젯의 HTTPServer 길과 같다.
    threading.py:1043 _bootstrap

    3.14.8에서는 threading.py의 세 줄이 1044, 1082, 1024줄, server.py의 두 줄이 500, 488줄이 된다.

    AI와 함께 확인하기¶

    AI 활용 과제: AI의 코드 설명을 근거로 확인하기

    1. AI에게 "Python의 http.server에서 do_GET은 어느 함수가 어떻게 부르나? 파일 이름과 줄 번호를 함께 알려 줘"라고 묻는다.
    2. AI가 댄 함수 이름과 줄 번호를 내 PC의 파일에서 직접 열어 확인한다.
    3. 틀린 곳이 있으면 실습의 trace_get.py 출력을 AI에게 보여 주고, 설명을 고치게 한다.
    확인할 점
    • 함수 이름과 동작(이름을 만들어 getattr로 부른다)은 대개 맞게 설명한다. 그러나 줄 번호는 AI가 배운 Python 판과 내 판이 달라 어긋나거나 지어낸 값이기 쉽다. 줄 번호와 인용은 늘 내 파일에서 확인한다.
    • "handle이 do_GET을 부른다"처럼 중간 단계를 건너뛴 설명인지 본다. handle은 do_GET을 직접 부르지 않으니 간접적으로만 맞는 말이고, 그대로 믿으면 handle_one_request를 들여다봐야 할 때(예: 501이 나는 까닭을 찾을 때) 찾지 못한다. 실행해서 찍은 스택이 가장 정확한 근거다.
    • 큰 코드베이스 전체를 AI에게 요약시킬 때도 "어느 파일 몇 줄 근거로"를 요구하고, 그 근거를 열어 본다. 근거를 대지 못하는 설명은 가설로만 쓴다.

    더 알아보기¶

    테스트 코드와 문서도 지도다

    처음 보는 프로젝트에서는 테스트 코드가 "이 코드를 어떻게 쓰는지"를 가장 정확히 보여 준다. CPython 저장소에는 http.server의 테스트가 Lib/test/test_httpservers.py에 있다. README, 문서의 예제, 커밋 기록(git log -- 파일)도 "왜 이렇게 짰나"를 알려 준다(83번(Git 실천)). 편집기의 "정의로 이동", "참조 찾기" 기능은 검색보다 정확하지만, 이름을 만들어 부르는 코드 앞에서는 검색과 마찬가지로 길을 잃는다.

    읽기 전에 돌려 보기

    코드를 읽기 전에 돌려 보고, 작은 입력으로 결과를 바꿔 보는 것이 지도를 빨리 만든다. 이 항목의 trace_get.py처럼 궁금한 함수 안에 한 줄을 넣어 찍어 보는 것도 읽기의 한 방법이다. 다만 남의 코드(표준 라이브러리 파일)를 직접 고치지는 않는다. 내 코드 쪽(덮어쓴 메서드)에서 찍는다.

    정리¶

    • 처음 보는 코드는 다 읽지 않는다. 돌려 보고, 파일과 클래스 관계로 지도를 그리고, 답이 하나인 질문을 따라간다.
    • 덮어쓴 메서드는 부모 클래스의 코드가 부른다. "누가 부르나"는 부모 클래스에서 찾는다.
    • 검색이 못 찾는 길(이름을 만들어 부르는 코드)은 실행해서 호출 스택으로 본다. AI의 설명도 파일과 줄 번호로 확인한다.
