    89. 지속적 통합과 배포(CI/CD): 빌드-테스트-배포 자동화 파이프라인¶

    원리 동작을 예측하고 이상을 알아챌 수 있어야 하는 항목

    AI 덕에 코드는 빨리 늘지만, 늘어난 코드를 사람이 매번 손으로 검사할 수는 없다. CI(지속적 통합)는 합칠 때마다 기계가 같은 검사를 되풀이하게 하고, CD(지속적 전달·배포)는 검사를 통과한 것을 같은 방법으로 내보낸다. 이 항목은 파이프라인이 무엇을 왜 하는지, 단계의 차례가 무엇을 바꾸는지 예측해 본다. 83번(Git 실천)의 shop 저장소(FREESHIP을 더한 order.py와 81번(요구사항과 명세)의 테스트 7개)를 그대로 쓰고, 예제는 Python이다.

    이 항목에서 배우는 것¶

    • CI가 합칠 때마다 깨끗한 환경에서 같은 검사를 되풀이하는 까닭을 설명할 수 있다.
    • 파이프라인 단계의 차례가 실패를 알기까지의 시간에 주는 영향을 예측할 수 있다.
    • 지속적 전달과 지속적 배포의 차이, 한 번 만든 산출물을 옮기는 까닭을 설명할 수 있다.

    1. CI는 합칠 때마다 깨끗한 환경에서 같은 검사를 한다¶

    • "내 컴퓨터에서는 되는데"의 까닭은 대개 내 컴퓨터에만 있는 것이다. 커밋하지 않은 파일, 따로 깐 패키지, 다른 Python 판이 그렇다. CI는 저장소를 빈 폴더에 새로 받아 잠금 파일(17번(패키지 생태계와 의존성 관리))대로 설치하고 검사한다(문제 1).
    • 합칠 때마다 검사하므로, 실패하면 방금 합친 작은 바뀜에서 원인을 찾는다. main이 깨지면 다른 일보다 먼저 고친다.

    2. 빨리 끝나고 자주 실패하는 검사를 앞에 둔다¶

    직접 해 보기파이프라인 단계의 차례CI 파이프라인의 다섯 단계를 위아래로 옮겨 차례를 바꾸고, 한 번 돌릴 때 평균 시간과 실패했을 때 알기까지 걸리는 평균 시간이 어떻게 바뀌는지 본다
    새 창에서 크게 열기
    • 단계가 하나 실패하면 뒤 단계는 돌지 않는다. 모두 통과할 때 걸리는 시간은 차례와 상관없지만, 실패를 알기까지 기다리는 시간은 차례가 정한다(문제 2).
    • 결과를 믿을 수 있어야 파이프라인이 쓸모 있다. 까닭 없이 가끔 실패하는 테스트는 빨간 불을 무시하게 만든다(문제 3).

    3. 배포는 한 번 만든 산출물을 단계마다 옮긴다¶

    • 지속적 전달은 언제든 내보낼 수 있게 준비해 두고 사람이 승인해 내보낸다. 지속적 배포는 검사를 모두 통과하면 사람 없이 운영까지 나간다.
    • 빌드는 한 번만 하고, 스테이징에서 확인한 그 산출물을 운영으로 옮긴다. 운영에는 카나리로 조금씩 내보내고(71번(이중화와 무중단 배포)) 지표(72번(관측성))가 나쁘면 되돌린다. 파이프라인은 실행마다 어느 커밋을 언제 어디로 내보냈는지 기록을 남긴다. 장애 때 무엇이 나갔는지 찾거나(73번(장애 대응과 포스트모템)) 82번(설계 결정 기록(ADR))의 다시 볼 조건을 셀 때 이 기록을 본다.

    예측해 보기¶

    문제 1. 82번(설계 결정 기록(ADR))의 대안 B처럼 쿠폰 표를 코드에서 coupons.json 파일로 옮겼다. order.py의 COUPONS 줄을 아래처럼 고쳐 커밋했지만 coupons.json은 git add하지 않았다. 내 폴더에서 python -m unittest는 통과한다. 저장소를 빈 폴더에 새로 받아 검사하는 ci.py(더 알아보기)를 돌리면 어떻게 될까?

    import json

with open("coupons.json", encoding="utf-8") as f:     # 쿠폰 → 할인율(%). coupons.json에는 {"WELCOME10": 10, "FREESHIP": 0}
    COUPONS = json.load(f)
    정답과 해설

    테스트 단계에서 실패한다. 이 PC에서 실행한 결과다.

    [1/4] 깨끗한 폴더에 받기: 통과
[2/4] 문법 검사: 통과
[3/4] 테스트: 실패
      FileNotFoundError: [Errno 2] No such file or directory: 'coupons.json'
파이프라인 실패: 고친 뒤 다시 커밋한다

    git status --short가 ?? coupons.json(git이 모르는 파일)을 보이고 있었다. 내 폴더에는 그 파일이 있어 테스트가 통과했지만, 커밋하지 않은 파일은 새로 받은 저장소에 없다. coupons.json을 커밋하자 네 단계가 모두 통과했다. 그래서 ?? __pycache__/처럼 저장소에 넣으면 안 되는 것은 .gitignore에 적어 git status를 깨끗이 둔다. 그래야 새로 생긴 ??가 눈에 띈다.

    문제 2. 위젯의 처음 차례(빌드 → 통합 테스트 → 단위 테스트 → 정적 검사 → 배포 확인)에서, 실패했을 때 알기까지의 평균 시간을 가장 줄이는 차례는 무엇일까? 그 시간은 처음보다 얼마나 줄까? 순서 제약(통합 테스트는 빌드 뒤, 배포 확인은 맨 끝)을 지킨다.

    정답과 해설

    정적 검사 → 단위 테스트 → 빌드 → 통합 테스트 → 배포 확인이다. 실패를 알기까지 평균 12분 43초에서 6분 18초로 절반쯤이 된다. 모두 통과할 때(23분 30초)와 어딘가에서 실패할 확률(36.6%)은 차례와 상관없다. 짧고 자주 실패하는 검사(정적 검사 30초에 10%)를 앞에 둘수록 실패가 일찍 드러나 기다림이 준다. 걸리는 시간에 견준 실패 비율이 큰 단계부터 두면 된다. 통합 테스트는 빌드보다 그 비율이 크지만, 빌드 결과가 있어야 해서 뒤에 둔다. 위젯의 값은 같은 규칙을 Python으로 따로 계산해(분수로) 가능한 차례 열두 가지를 모두 견준 결과와 같다.

    문제 3. 까닭 없이 5%의 확률로 실패하는 테스트가 하나 있다. CI를 하루 40번 돌리면 이 테스트 때문에 거짓으로 실패하는 일이 평균 몇 번일까? 하루에 한 번이라도 거짓 실패가 날 확률은?

    runs = 40                                        # 하루에 CI를 돌리는 횟수
flaky = 0.05                                     # 그 테스트가 까닭 없이 실패하는 비율
print(runs * flaky, round(1 - (1 - flaky) ** runs, 2))
    정답과 해설

    2.0 0.87. 하루 평균 두 번, 87%의 날에 한 번 이상 거짓 실패가 난다. 그러면 사람들은 "또 그 테스트겠지" 하고 빨간 불을 다시 돌리거나 무시하고, 진짜 실패도 함께 놓친다. 까닭 없이 실패하는 테스트(flaky test)는 시각, 난수, 순서, 네트워크처럼 테스트가 정하지 않은 것에 기대는 경우가 많다(84번(테스트 설계)의 시험하기 쉬운 코드). 발견하면 따로 떼어 두고 바로 고친다.

    AI와 함께 확인하기¶

    AI 활용 과제: AI가 짠 CI 설정 검토하기

    1. AI에게 "이 저장소(order.py, test_order.py)의 GitHub Actions 워크플로를 짜 줘"라고 한다.
    2. 받은 파일에서 저장소 받기, Python 판 정하기, 의존성 설치, 테스트 실행의 단계를 찾아 표시하고, 실패하면 거기서 멈추는지 본다.
    3. 아래 확인할 점과 견주어 고칠 곳을 적고, AI에게 근거와 함께 고치게 한다.
    확인할 점
    • actions/checkout@v2처럼 오래된 판을 쓰지 않았는지 본다. AI가 배운 시점의 예가 섞일 수 있다. 2026년 10월 현재 actions/checkout과 actions/setup-python의 최신 판은 v7이었다. 판은 공식 저장소의 릴리스에서 확인한다.
    • 의존성을 pip install 패키지처럼 판 없이 설치하면 어제와 오늘 다른 판이 깔려 같은 커밋이 다르게 끝난다. 잠금 파일로 설치하게 한다(17번(패키지 생태계와 의존성 관리)).
    • 비밀번호나 API 키를 설정 파일에 그대로 적는 답이 있다. 비밀값은 저장소에 넣지 않고 CI의 비밀값 저장소로 넘긴다.
    • 테스트가 실패해도 다음 단계로 넘어가게 하는 설정(continue-on-error나 || true)이 있으면 파이프라인이 늘 초록이 된다. 그 줄이 왜 있는지 묻는다.

    문제 1의 ci.py

    CI 서비스가 하는 일을 작게 흉내 낸 것이다. 저장소 폴더에서 python ci.py로 실행한다. 지금 쓰는 Python으로 검사하므로 다른 Python 판이나 따로 깐 패키지의 문제는 잡지 못한다. 실제 CI는 판을 정한 깨끗한 가상 머신이나 컨테이너에서 처음부터 설치한다. ci.py도 저장소에 커밋해 두면 git status에 ?? ci.py가 남지 않는다.

    # ci.py: 저장소를 빈 폴더에 새로 받아 문법 검사 → 테스트 → 산출물 만들기를 차례로 한다. 하나라도 실패하면 거기서 멈춘다
import os
import shutil
import stat
import subprocess
import sys
import tempfile
from pathlib import Path

repo = Path.cwd()
work = Path(tempfile.mkdtemp(prefix="ci-"))
src = work / "src"
STEPS = [
    ("깨끗한 폴더에 받기", ["git", "clone", "-q", str(repo), str(src)], work),     # 커밋한 파일만 받는다
    ("문법 검사", [sys.executable, "-m", "compileall", "-q", "."], src),
    ("테스트", [sys.executable, "-m", "unittest", "-q"], src),
    ("산출물 만들기", ["git", "archive", "--format=zip", "-o", str(work / "order.zip"), "HEAD"], src),
]
ok = True
for i, (name, cmd, cwd) in enumerate(STEPS, 1):
    r = subprocess.run(cmd, cwd=cwd, capture_output=True, text=True)
    print(f"[{i}/{len(STEPS)}] {name}: {'통과' if r.returncode == 0 else '실패'}")
    if r.returncode != 0:
        lines = (r.stdout + r.stderr).strip().splitlines()
        print("      " + ([l for l in lines if "Error" in l] or lines[-1:])[-1])   # 실패한 까닭 한 줄
        ok = False
        break
shutil.rmtree(work, onexc=lambda func, path, exc: (os.chmod(path, stat.S_IWRITE), func(path)))   # 흉내라 산출물까지 함께 지운다. git이 만든 읽기 전용 파일도
print("파이프라인 성공" if ok else "파이프라인 실패: 고친 뒤 다시 커밋한다")
sys.exit(0 if ok else 1)

    GitHub Actions로 쓴 같은 파이프라인

    저장소를 GitHub에 올렸다면 .github/workflows/ci.yml에 아래처럼 적어 push마다 같은 일을 시킬 수 있다. 이 강의는 GitHub 저장소를 쓰지 않아 이 파일은 실행해 보지 않았고, actions/checkout과 actions/setup-python의 판(v7)과 Python 3.14가 있는지만 2026년 10월에 확인했다.

    name: ci
on: [push, pull_request]
jobs:
  test:
    runs-on: windows-latest
    steps:
      - uses: actions/checkout@v7          # 저장소를 새로 받는다
      - uses: actions/setup-python@v7
        with:
          python-version: "3.14"
      - run: python -m compileall -q .
      - run: python -m unittest -v

    정리¶

    • CI는 합칠 때마다 저장소를 새로 받아 같은 검사를 자동으로 되풀이한다. 내 컴퓨터에만 있는 것(커밋하지 않은 파일, 패키지)에 기대는 문제를 잡는다.
    • 단계의 차례는 실패를 알기까지의 시간을 정한다. 빨리 끝나고 자주 실패하는 검사를 앞에 두고, 결과를 믿을 수 있게 까닭 없이 실패하는 테스트를 없앤다.
    • 빌드는 한 번 하고 같은 산출물을 옮긴다. 지속적 전달은 사람이, 지속적 배포는 검사가 운영으로 내보낼지 정한다.
