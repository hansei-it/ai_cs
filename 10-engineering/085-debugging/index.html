    85. 디버깅 방법론: 재현과 최소화, 가설 세우고 검증하기, 디버거와 로그, git bisect¶

    직접 AI 없이 직접 할 수 있어야 하는 항목

    버그를 고치는 시간의 대부분은 고치는 데가 아니라 찾는 데 든다. 찾는 일은 감이 아니라 차례가 있는 실험이다. AI에게 "이 버그 고쳐 줘"라고 할 때도, AI가 내놓은 까닭이 맞는지는 같은 실험으로 확인한다. 직접형 항목이므로 C 프로그램의 버그를 Visual Studio 디버거로 찾고, 커밋 기록에서 버그가 들어온 커밋을 git bisect로 찾는다(실습 환경).

    이 항목에서 배우는 것¶

    • 버그를 재현하고, 재현하는 입력을 가장 작게 줄일 수 있다.
    • 가설을 하나씩 세우고 디버거(중단점, 지역 창, 호출 스택)와 로그로 확인할 수 있다.
    • git bisect run으로 버그가 처음 들어온 커밋을 찾을 수 있다.

    1. 재현하고, 줄이고, 가설 하나씩 확인한다¶

    • 먼저 버그를 늘 다시 일으키는 입력과 차례를 찾는다. 재현이 안 되면 고쳤는지도 알 수 없다.
    • 그 입력을 가장 작게 줄인다. 원인이 좁혀지고, 줄인 입력은 그대로 테스트가 된다(문제 2).
    • 가설은 하나씩 세우고, 확인할 때 바꾸는 것도 하나뿐이어야 결과를 읽을 수 있다.

    2. 디버거는 코드를 고치지 않고 실행 중의 값을 보여 준다¶

    • 중단점(F9)을 건 줄에서 실행이 멈추고, 지역 창은 그때의 변수 값을, 호출 스택 창은 어느 함수가 어느 함수를 불러 여기까지 왔는지 보여 준다.
    • 중단점에 조건을 붙이면 반복 1,000번 가운데 문제의 순간에만 멈춘다. F10은 한 줄씩, F11은 함수 안으로 들어가며 실행한다.
    • printf로 남기는 로그는 디버거를 붙일 수 없는 곳(서버, 다른 사람의 PC)에서 쓴다. 기록이 남아 나중에도 볼 수 있다(72번(관측성)).

    3. 언제부터 망가졌는지는 커밋을 반으로 나눠 찾는다¶

    직접 해 보기반으로 나눠 망가진 커밋 찾기커밋 수를 고르고 가운데 커밋이나 원하는 커밋을 시험해, 처음 망가진 커밋을 몇 번 만에 찾는지와 하나씩 시험할 때의 횟수를 견준다
    새 창에서 크게 열기
    • 예전에는 되던 것이 지금 안 되면, 그 사이 어느 커밋이 망가뜨렸다. 가운데 커밋을 시험해 좋으면 뒤쪽을, 나쁘면 앞쪽을 다시 나눈다(문제 3).
    • git bisect가 이 일을 해 주고, git bisect run에 테스트 명령을 주면 시험까지 알아서 한다. 커밋이 작을수록 찾은 커밋 안에서 원인이 잘 보인다(83번(Git 실천)).

    예측해 보기¶

    문제 1. 60점 이상인 점수의 평균을 구하는 프로그램이다. 50, 70, 90, 40을 넣으면 무엇이 출력될까? 70과 90의 평균인 80.0이 나와야 한다.

    #include <stdio.h>

/* 60점 이상인 점수의 평균을 돌려준다 */
double passing_average(const int *scores, int n) {
    int sum = 0, count = 0;
    for (int i = 0; i < n; i++)
        if (scores[i] >= 60)
            sum += scores[i];
            count++;
    return count ? (double)sum / count : 0.0;
}

int main(void) {
    int scores[] = {50, 70, 90, 40};
    printf("%.1f\n", passing_average(scores, 4));
    return 0;
}
    정답과 해설

    160.0. 80.0의 두 배다. 합은 맞게 160인데 나누는 수가 2가 아니라는 뜻이다. 기본 경고 수준(/W3)에서 컴파일러는 아무 경고도 내지 않았다. 왜 그런지는 직접 해보기에서 디버거로 찾는다.

    문제 2. 문제 1의 버그를 재현하는 가장 작은 입력을 찾는다. 점수 하나짜리 {70}이나 {50}으로 줄여도 버그가 보일까?

    정답과 해설

    보이지 않는다. {70}은 70.0, {50}은 0.0으로 우연히 맞다. 합격 점수가 둘인 {70, 90}부터 160.0으로 틀린다. 입력을 줄이다 버그가 사라지면, 방금 뺀 것이 원인과 이어져 있다는 단서다. 여기서는 "합격 점수가 둘 이상"이 조건이었다. 줄인 입력 {70, 90} → 80.0이 이 버그의 테스트가 된다.

    #include <stdio.h>

double passing_average(const int *scores, int n) {
    int sum = 0, count = 0;
    for (int i = 0; i < n; i++)
        if (scores[i] >= 60)
            sum += scores[i];
            count++;
    return count ? (double)sum / count : 0.0;
}

int main(void) {
    int one[] = {70}, two[] = {70, 90}, low[] = {50};
    printf("%.1f\n", passing_average(one, 1));   /* 70.0 */
    printf("%.1f\n", passing_average(two, 2));   /* 160.0 */
    printf("%.1f\n", passing_average(low, 1));   /* 0.0 */
    return 0;
}

    문제 3. 커밋 1,000개가 있다. 커밋 1에서는 테스트가 통과했고 커밋 1,000에서는 실패한다. 그 사이 어딘가에서 처음 실패하기 시작했다. 늘 가운데를 시험하면 많아야 몇 번 시험해야 찾을까? 앞에서부터 하나씩 시험하면 많아야 몇 번일까?

    정답과 해설

    가운데를 시험하면 많아야 10번, 하나씩이면 많아야 998번이다. 시험할 때마다 후보가 절반으로 줄어, 후보 999개가 2¹⁰ = 1,024보다 적으므로 10번이면 하나로 줄어든다. 위젯과 같은 규칙을 Python으로 따로 짜서 처음 망가진 커밋을 2번부터 1,000번까지 모두 넣어 보니, 가운데 시험은 가장 많을 때 10번(평균 9.97번), 하나씩은 998번(평균 500번)이었다. 커밋 12개인 실습에서는 많아야 4번이다.

    직접 해보기¶

    실습 A: 디버거로 원인 찾기

    1. Visual Studio에서 빈 프로젝트를 만들고 문제 1의 프로그램을 main.c(서명 있는 UTF-8)로 저장한다. Ctrl+F5로 실행해 160.0을 확인한다.
    2. 가설을 하나 적는다. 예: "합이 160이 맞다면, 나누는 count가 2가 아니다."
    3. return 줄에 중단점을 걸고(F9) F5로 실행한다. 멈추면 지역 창에서 sum과 count를 본다.
    4. 다음 가설을 적고 확인한다. 예: "count++가 합격 점수마다 실행되지 않는다." count++; 줄에 중단점을 걸고 처음부터 다시 실행해, 그 줄에서 몇 번 멈추는지와 멈췄을 때 i가 지역 창에 있는지 본다.
    5. 원인을 고치고 {70, 90}과 {50, 70, 90, 40}이 80.0인지 확인한다.

    실습 B: git bisect로 버그가 들어온 커밋 찾기

    1. 시작 메뉴의 "x64 Native Tools Command Prompt for VS"를 열고, cd /d로 빈 폴더에 옮긴 뒤(실습 환경 4절) 아래 make_history.py를 실행한다. stats 폴더에 stats.c를 12번 고친 커밋 기록과 test.bat이 생긴다. 첫 커밋에서는 80.0이 나왔고, 지금은 160.0이 나온다.

    2. cd stats 다음에 아래 명령으로 찾는다. HEAD~11은 첫 커밋이다. test.bat은 stats.c를 컴파일해 실행하고, 출력에 80.0인 줄이 있으면 0(좋음), 없으면 1(나쁨)로 끝난다.

      git bisect start
git bisect bad
git bisect good HEAD~11
git bisect run ./test.bat

    3. 찾은 커밋을 git show 커밋해시로 보고, 실습 A에서 찾은 원인과 같은지 견준다. 끝나면 git bisect reset으로 원래 자리(main)로 돌아간다.

    # make_history.py: 85번 실습용 저장소(stats 폴더)를 만든다. stats.c를 12번 고쳐 커밋하는데, 그 가운데 한 커밋이 버그를 넣는다

    else:

                f"        if (scores[i] >= {P})\n            sum += scores[i];\n            count++;\n"
                "    return count ? (double)sum / count : 0.0;\n}\n")
    if v >= 2:

    if v >= 3:
        out += "\nint min_score(const int *s, int n) {\n    int m = s[0];\n    for (int i = 1; i < n; i++)\n        if (s[i] < m) m = s[i];\n    return m;\n}\n"
    if v >= 4:
        name = "count_passing" if v >= 12 else "passing_count"
        out += f"\nint {name}(const int *s, int n) {{\n    int c = 0;\n    for (int i = 0; i < n; i++)\n        if (s[i] >= {P}) c++;\n    return c;\n}}\n"
    if v >= 5:
        out += "\n" + ("/* 90점 이상 A, 80점 이상 B, 70점 이상 C, 합격 기준 이상 D, 그 아래 F */\n" if v >= 9 else "")
        out += f"char grade(int s) {{\n    return s >= 90 ? 'A' : s >= 80 ? 'B' : s >= 70 ? 'C' : s >= {P} ? 'D' : 'F';\n}}\n"
    out += "\nint main(void) {\n" + ("    /* 점수 넷의 통계를 한 줄씩 찍는다 */\n" if v >= 11 else "") + "    int scores[] = {50, 70, 90, 40};\n"
    out += "    printf(\"%.1f\\n\", passing_average(scores, 4));\n"
    if v >= 2:
        out += "    printf(\"%d\\n\", max_score(scores, 4));\n" if v < 10 else "    printf(\"%d %d\\n\", max_score(scores, 4), min_score(scores, 4));\n"
    if 3 <= v < 10:
        out += "    printf(\"%d\\n\", min_score(scores, 4));\n"
    if v >= 4:
        out += f"    printf(\"%d\\n\", {'count_passing' if v >= 12 else 'passing_count'}(scores, 4));\n"
    if v >= 5:
        out += "    printf(\"%c\\n\", grade(scores[2]));\n"
    return out + "    return 0;\n}\n"

def run(*args):
    r = subprocess.run(["git", *args], cwd=repo, capture_output=True, text=True, errors="replace")
    if r.returncode != 0:                   # 예: git에 이름과 메일을 정하지 않았으면 그 안내가 보인다
        sys.exit(r.stderr)


run("init", "-b", "main")
for v, msg in enumerate(MESSAGES, 1):
    (repo / "stats.c").write_text(source(v), encoding="utf-8-sig")   # 서명 있는 UTF-8
    run("add", "stats.c")
    run("commit", "-m", msg)
(repo / "test.bat").write_text("@echo off\ncl /nologo /W3 stats.c >nul 2>&1 || exit /b 125\nstats.exe | findstr /x /l \"80.0\" >nul\n",
                             encoding="ascii", newline="\r\n")

    확인할 점
    • 실습 A의 3단계: return 줄에서 멈추면 sum은 160, count는 1이다. 가설대로 나누는 수가 틀렸다. 같은 자리에 printf를 넣어 실행해도 같은 값이 찍혔다.
    • 4단계: count++; 줄에서는 반복이 다 끝난 뒤에 한 번만 멈추고, 지역 창에 i가 없다. i는 for의 변수인데 그 줄이 for 밖에 있다는 뜻이다. for와 if가 중괄호 없이 바로 다음 문장 하나만 거느려, count++;는 들여쓰기와 달리 반복이 끝난 뒤 한 번 실행된다. for와 if를 중괄호로 묶어 고친다.
    #include <stdio.h>

double passing_average(const int *scores, int n) {
    int sum = 0, count = 0;
    for (int i = 0; i < n; i++) {
        if (scores[i] >= 60) {
            sum += scores[i];
            count++;
        }
    }
    return count ? (double)sum / count : 0.0;
}

int main(void) {
    int two[] = {70, 90}, scores[] = {50, 70, 90, 40};
    printf("%.1f\n", passing_average(two, 2));      /* 80.0 */
    printf("%.1f\n", passing_average(scores, 4));   /* 80.0 */
    return 0;
}
    • 실습 B: 이 PC에서 git bisect run ./test.bat이 커밋 넷(합격 기준을 상수로, 학점 기준 주석, 중괄호 정리, 평균 함수 주석 다듬기)을 시험한 뒤 ... is the first bad commit과 함께 "중괄호 정리" 커밋을 찾았다. 해시는 저마다 다르다. 이름이 "정리"인 커밋이 동작을 바꿨다. 정리한다며 동작을 바꾸는 일은 사람에게도 AI에게도 흔하다.
    • git bisect run test.bat처럼 ./ 없이 적으면 test.bat: command not found가 나오고 error: bogus exit code 127 for good revision으로 멈췄다. git은 명령을 자기 셸(sh)로 실행하는데, 그 셸은 지금 폴더에서 명령을 찾지 않는다. 멈춘 뒤에도 bisect는 그대로 남아 있으니 git bisect run ./test.bat을 다시 실행하면 된다.
    • x64 창이 아닌 곳에서 실행하면 cl을 찾지 못해 모든 커밋이 "시험할 수 없음"으로 건너뛰어지고, We cannot bisect more!와 error: bisect run cannot continue any more로 끝났다. git bisect reset으로 돌아간 뒤 x64 창에서 다시 한다.
    • test.bat의 exit /b 125는 컴파일이 안 되는 커밋을 "시험할 수 없음"으로 건너뛰라는 약속이다. 컴파일 실패를 "나쁨"으로 세면 엉뚱한 커밋을 범인으로 찾는다.

    AI와 함께 확인하기¶

    AI 활용 과제: AI의 디버깅 답을 가설로 다루기

    1. 문제 1의 프로그램과 "80.0이 나와야 하는데 160.0이 나온다"를 AI에게 주고 까닭과 고친 코드를 묻는다.
    2. AI의 답을 "가설"로 적고, 실습 A처럼 중단점이나 printf로 그 가설이 맞는지 확인한다.
    3. AI가 고친 코드를 줄인 입력 {70, 90}과 원래 입력으로 실행해 본다. 다른 곳까지 바꿨다면 diff(83번(Git 실천))로 바뀐 곳을 모두 확인한다.
    확인할 점
    • 이런 짧은 코드에서는 AI가 까닭(중괄호 없는 for)을 바로 짚는 일이 많다. 그래도 확인은 내 몫이다. 짚은 줄에서 실제로 무슨 일이 일어나는지 디버거로 보면, 다음에 비슷한 버그를 혼자 찾을 수 있다.
    • 까닭을 모르는 채로 "이렇게 바꾸면 된다"만 내놓는 답도 있다. 증상(결과 숫자)만 맞추는 고침은 다른 입력에서 다시 틀린다. 줄인 입력과 원래 입력을 함께 시험한다.
    • 실제 프로그램의 버그는 코드 한 조각만 보고 찾기 어렵다. AI에게는 재현하는 가장 작은 입력과 실제 출력, 기대한 출력을 함께 주면 답이 정확해진다. 재현과 줄이기는 AI를 쓸 때도 먼저 할 일이다.

    더 알아보기¶

    고무 오리 디버깅과 가설 적기

    프로그래머들은 책상 위의 고무 오리에게 코드를 한 줄씩 설명하다가 버그를 찾는다고 말한다. 남에게 설명하려면 "여기서 이 값은 이래야 한다"는 가정을 말로 꺼내야 하고, 그때 틀린 가정이 드러난다. 가설을 종이에 적는 것도 같은 효과가 있다. 확인한 가설과 결과를 적어 두면, 같은 가설을 두 번 확인하는 일도 막는다.

    중괄호 없는 if와 for

    C에서 if, for, while은 중괄호가 없으면 바로 다음 문장 하나만 거느린다. 들여쓰기는 컴파일러에게 아무 뜻이 없다. 그래서 문장을 하나 더 넣거나 정리하다 이런 버그가 생긴다. 한 줄짜리여도 중괄호를 쓰는 규칙을 두는 팀이 많다. GCC와 Clang은 -Wmisleading-indentation으로 들여쓰기와 실제 구조가 다른 곳을 경고하지만, 이 PC의 MSVC는 문제 1의 코드에 /W4, /Wall, /analyze를 켜도 경고하지 않았다.

    정리¶

    • 디버깅은 실험이다. 재현하고, 입력을 줄이고, 가설을 하나씩 세워 확인한다. 줄인 입력은 테스트로 남긴다.
    • 디버거는 코드를 고치지 않고 실행 중의 값(지역 창)과 부른 길(호출 스택)을 보여 준다. 조건부 중단점으로 문제의 순간에만 멈춘다.
    • 예전에는 되던 것은 git bisect로 커밋을 반으로 나눠 찾는다. 커밋 1,000개도 10번 안에 찾는다.
