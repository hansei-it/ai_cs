    83. Git 실천: diff 읽기, 작은 단위 커밋, 되돌리기, PR 리뷰, 브랜치 전략(Git-Flow와 트렁크 기반 비교)¶

    직접 AI 없이 직접 할 수 있어야 하는 항목

    AI가 한 번에 여러 줄, 여러 파일을 고치는 환경에서 Git은 기록 도구라기보다 안전장치다. 무엇이 바뀌었는지 diff로 읽고, 한 가지 일씩 커밋하고, 잘못되면 되돌린다. 직접형 항목이므로 81번(요구사항과 명세)·84번(테스트 설계)의 order.py를 저장소에 넣고, AI가 고친 diff를 리뷰하고, 실수한 커밋을 되돌려 본다. 명령은 PowerShell에서 실행한다(Git 설치는 실습 환경).

    이 항목에서 배우는 것¶

    • git diff의 출력을 읽고, AI가 바꾼 코드에서 요청하지 않은 바뀜을 찾을 수 있다.
    • 한 가지 일만 담은 커밋을 만들고, 공유했는지에 따라 되돌리는 방법(restore, revert, reset)을 고를 수 있다.
    • Git-Flow와 트렁크 기반 전략의 차이, PR 리뷰의 역할을 설명할 수 있다.

    1. AI가 바꾼 코드는 diff로 읽는다¶

    • git status --short로 바뀐 파일을, git diff로 줄 단위의 바뀜을 본다. AI가 "쿠폰 하나만 더했다"고 말해도, 실제로 바뀐 것은 diff가 말한다.
    • 한 줄 안의 작은 바뀜은 git diff --word-diff가 바뀐 낱말만 [-지운-]{+더한+}로 보여 준다.
    • 리뷰할 때는 요청한 바뀜인지, 테스트가 함께 있는지, 요청하지 않은 바뀜(지운 주석, 바뀐 비교 연산자, 서식)이 섞였는지 본다(문제 1).

    2. 커밋은 작게, 되돌리기는 공유했는지로 고른다¶

    직접 해 보기되돌리기 연습실수한 커밋 C를 이미 push했는지 고르고 git 명령(restore, add, commit, revert, reset --soft, reset --hard, push)을 눌러, 원격, 내 기록, 스테이지, 작업 폴더가 어떻게 바뀌고 무엇이 사라지는지 본다
    새 창에서 크게 열기
    • 커밋 하나에 일 하나만 담는다. 기능과 이름 바꾸기와 서식 정리가 한 커밋에 섞이면 리뷰하기 어렵고, 그중 하나만 되돌릴 수 없다.
    • 아직 커밋하지 않은 바뀜은 git restore로 버린다. git이 저장한 적이 없어 되찾을 수 없다.
    • 이미 push해 함께 쓰는 커밋은 git revert로 되돌린다. 거꾸로 적용한 새 커밋을 더할 뿐 기록을 지우지 않는다. git reset은 기록을 고쳐 쓰므로 아직 내 컴퓨터에만 있는 커밋에 쓴다(문제 2).

    3. 브랜치 전략은 얼마나 자주 합치느냐의 선택이다¶

    • Git-Flow는 늘 있는 main과 develop에 기능, 릴리스, 핫픽스 브랜치를 그때그때 갈라 합치며 정해진 때 판을 낸다. 트렁크 기반은 짧은 브랜치를 길어야 하루 이틀 안에 main에 합친다.
    • AI 덕에 코드가 빨리 늘수록, 오래 떨어져 있던 브랜치를 합치는 일이 커진다. 작은 PR을 자주 합치고 자동 테스트(89번(CI/CD))가 매번 확인하게 하는 쪽이 요즘 서비스에서 흔하다.
    • PR(풀 리퀘스트) 리뷰는 diff를 읽고 질문하는 자리다. AI가 만든 PR도 사람이 리뷰하고, 승인한 사람도 결과를 함께 책임진다.

    예측해 보기¶

    문제 1. 1절 그림의 diff에서 요청하지 않은 바뀜을 모두 찾는다. 이대로 커밋하면 81번의 테스트 가운데 무엇이 실패할까?

    정답과 해설

    두 곳이다. paid >= 30000이 paid > 30000으로 바뀌었고, 줄 끝의 주석 # 무료 배송은 할인 뒤 금액으로 정한다가 사라졌다. 요청한 FREESHIP 조건과 같은 줄에 섞여 있어 줄 단위로 보면 놓치기 쉽다. git diff --word-diff로 보면 바뀐 낱말만 드러난다.

    shipping = 0 if paid [->=-]{+>+} 30000 {+or coupon == "FREESHIP"+} else 3000[-# 무료 배송은 할인 뒤 금액으로 정한다-]

    이대로면 test_딱_3만_원이 AssertionError: 33000 != 30000으로 실패한다(이 PC에서 실행해 확인). 딱 30,000원이면 무료인데 >로 바뀌어 배송비를 받는다. 81번에서 경계를 수용 기준에 넣어 둔 덕에 잡힌다. 지운 주석은 테스트로 잡히지 않으므로 리뷰에서 잡아야 한다.

    문제 2. 위젯에서 "C를 이미 push했다"를 고른다. 실수한 C를 없애려고 git reset --hard HEAD~1 다음에 git push를 하면 어떻게 될까? 대신 git revert --no-edit HEAD 다음에 git push를 하면? 누르기 전에 적어 본다.

    정답과 해설

    reset 쪽은 push가 거절된다(! [rejected] main -> main (non-fast-forward)). revert 쪽은 push가 되어 원격과 내 기록이 모두 A─B─C─Revert "C"가 된다. reset은 내 기록에서 C를 뺐지만 원격에는 C가 남아 있어, git은 원격의 커밋을 잃게 하는 push를 거절한다. 게다가 --hard는 아직 커밋하지 않은 README.md의 고친 내용까지 지웠다. revert는 C의 바뀜을 거꾸로 적용한 새 커밋을 더할 뿐이라, 같은 원격을 쓰는 다른 사람의 기록과도 어긋나지 않고 README.md의 고친 내용도 남는다. 거절된 push를 git push --force로 밀어붙이면 원격의 C가 지워지고, 그사이 C 위에 작업한 사람의 기록이 어긋난다. 위젯의 결과는 실제 git(2.51.1)으로 원격 저장소까지 만들어 같은 명령을 실행해 얻은 결과와 같다.

    직접 해보기¶

    실습: AI가 고친 diff를 리뷰하고, 실수한 커밋 되돌리기

    1. 새 폴더 shop에서 저장소를 만들고, 81번(요구사항과 명세)에서 고친 order.py와 test_order.py를 저장해 첫 커밋을 한다. git에 이름과 메일을 정하지 않았다면 먼저 정한다(실습 환경 8절).

      git init -b main
git add order.py test_order.py
git commit -m "주문 금액 계산과 수용 기준 테스트"

    2. AI에게 "FREESHIP 쿠폰을 더해 줘(할인 없이 배송비만 면제)"라고 해서 받은 아래 코드로 order.py를 바꾼다. git status --short, git diff, git diff --word-diff로 읽고, python -m unittest test_order로 테스트를 돌린다.

    3. 요청하지 않은 바뀜을 고친다. 다시 git diff로 요청한 바뀜만 남았는지 보고, 테스트가 통과하면 git commit -am "FREESHIP 쿠폰: 할인 없이 배송비만 면제"로 커밋한다.
    4. 일부러 실수한다. 할인 상한 5000을 6000으로 바꿔 git commit -am "할인 상한을 6000원으로"로 커밋하고 테스트를 돌린다. git revert --no-edit HEAD로 되돌리고 git log --oneline과 테스트로 확인한다.
    # order.py
COUPONS = {"WELCOME10": 10, "FREESHIP": 0}           # 쿠폰 → 할인율(%)


def order_total(items, coupon=None):
    """items: [(가격, 수량), ...]. 결제할 금액(원)을 돌려준다."""
    if not items:
        raise ValueError("빈 장바구니는 주문할 수 없습니다")
    for price, qty in items:
        if price < 0 or qty <= 0:
            raise ValueError("가격과 수량을 확인하세요")
    if coupon is not None and coupon not in COUPONS:
        raise ValueError(f"모르는 쿠폰: {coupon}")
    subtotal = sum(price * qty for price, qty in items)
    discount = min(subtotal * COUPONS[coupon] // 100, 5000) if coupon else 0
    paid = subtotal - discount
    shipping = 0 if paid > 30000 or coupon == "FREESHIP" else 3000
    return paid + shipping
    확인할 점

    이 PC에서 차례대로 실행한 결과다. 커밋 해시(앞의 7자리)는 저마다 다르다.

    • 2단계: git status --short는 M order.py(고쳤지만 아직 스테이지에 올리지 않음)를 보였다. git diff의 두 번째 묶음은 1절 그림과 같고, 테스트는 F......, FAILED (failures=1)로 test_딱_3만_원이 실패했다(문제 1).
    • 3단계: shipping 줄을 shipping = 0 if paid >= 30000 or coupon == "FREESHIP" else 3000 # 무료 배송은 할인 뒤 금액으로 정한다로 고치자 diff에는 COUPONS 줄과 shipping 줄의 요청한 바뀜만 남았고, 테스트 7개가 통과했다(OK).
    • 4단계: 6000원으로 바꾼 커밋 뒤에는 test_할인_상한이 AssertionError: 54000 != 55000으로 실패했고, revert 뒤에는 다시 7개가 통과했다. PowerShell 창의 git log --oneline은 이랬다.
    f2cadd2 (HEAD -> main) Revert "할인 상한을 6000원으로"
9a6f3b7 할인 상한을 6000원으로
2357ec5 FREESHIP 쿠폰: 할인 없이 배송비만 면제
e01b7ad 주문 금액 계산과 수용 기준 테스트
    • 실수한 커밋도 기록에 남는다. 지운 것이 아니라 되돌렸기 때문에, 나중에 "왜 6000원이었다가 5000원이 되었나"를 기록으로 알 수 있다. 커밋 메시지는 무엇을 왜 했는지 한 줄로 쓴다. "수정", "작업 중"은 나중에 아무것도 알려 주지 않는다.
    • git add, git diff, git commit -am에서 LF will be replaced by CRLF 경고가 나올 수 있다. 작업 폴더의 이 파일은 줄 끝이 LF인데, git이 다음에 이 파일을 다시 쓸 때 Windows 방식(CRLF)으로 바꾼다는 안내다. 저장소에는 LF로 들어가므로 그대로 두어도 된다. 테스트를 돌린 뒤 git status --short에 보이는 ?? __pycache__/는 Python이 만든 캐시라 커밋하지 않는다. .gitignore 파일에 __pycache__/를 적어 두면 목록에서 사라진다(89번(CI/CD)).
    • 3단계에서 고칠 줄이 여럿이었다면 git add -p로 바뀐 묶음마다 올릴지 물어보게 해서, 기능과 정리를 다른 커밋으로 나눌 수 있다.

    AI와 함께 확인하기¶

    AI 활용 과제: AI가 만든 커밋을 리뷰어처럼 읽기

    1. 실습 저장소에서 AI에게 "FREESHIP 쿠폰의 테스트를 더하고, 코드를 깔끔하게 정리해 줘"라고 시킨다.
    2. 커밋하기 전에 git diff --stat으로 바뀐 파일과 줄 수를, git diff로 내용을 본다. 바뀜을 "기능", "테스트", "정리", "요청하지 않은 것"으로 나눠 적는다.
    3. 나눈 대로 커밋을 둘 이상으로 나눠 만든다(git add -p). 요청하지 않은 바뀜은 버리거나 AI에게 까닭을 묻는다.
    확인할 점
    • "깔끔하게 정리"를 함께 시키면 AI는 변수 이름, 따옴표, 줄 바꿈까지 고치는 일이 많다. 그러면 기능의 diff가 서식 바뀜에 묻힌다. 기능과 정리는 따로 시키고 따로 커밋한다.
    • 정리 커밋은 동작이 바뀌지 않아야 한다. 정리 커밋 앞뒤로 테스트를 돌려 둘 다 통과하는지 본다(87번(코드 리뷰와 리팩토링)의 리팩토링).
    • AI가 테스트를 고쳐 실패를 없애는 경우가 있다. diff에서 test_ 파일의 기대값이 바뀌었으면 코드가 아니라 테스트를 고친 것이니 반드시 까닭을 확인한다.

    더 알아보기¶

    되돌리기를 고르는 기준

    아직 커밋하지 않은 바뀜을 버릴 때는 git restore 파일, 스테이지에서만 내릴 때는 git restore --staged 파일을 쓴다. 내 컴퓨터에만 있는 커밋을 고쳐 다시 만들 때는 git reset --soft HEAD~1(바뀜은 스테이지에 남는다)이나 git commit --amend -m "고친 메시지"를 쓴다. 이미 push한 커밋은 git revert로 되돌린다. git reset --hard는 커밋하지 않은 바뀜을 지우므로 쓰기 전에 git status로 무엇이 사라질지 본다. 지운 커밋은 한동안 git reflog에 남아 찾을 수 있지만, 커밋하지 않은 바뀜은 어디에도 남지 않는다.

    git bisect: 언제부터 망가졌는지 찾기

    테스트가 언제부터 실패했는지 모를 때는 git bisect가 커밋 기록을 반으로 나눠 가며 처음 망가진 커밋을 찾는다. 작은 커밋이 많을수록 찾은 커밋 안에서 원인을 좁히기 쉽다. 디버깅에서 다시 다룬다(85번(디버깅 방법론)).

    정리¶

    • AI가 바꾼 코드는 diff로 읽는다. 요청하지 않은 바뀜(연산자, 지운 주석, 서식)은 --word-diff로 낱말까지 본다.
    • 커밋 하나에는 일 하나만 담는다. 커밋하지 않은 바뀜은 restore, 공유한 커밋은 revert, 내 컴퓨터에만 있는 커밋은 reset으로 되돌린다.
    • 브랜치 전략은 합치는 주기의 선택이다. 작은 PR을 자주 합치고, PR은 diff를 읽고 질문하는 리뷰를 거친다.
