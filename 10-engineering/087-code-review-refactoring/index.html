    87. 코드 리뷰와 리팩토링: 코드 스멜, 기술 부채, 린터와 정적 분석 도구 활용¶

    직접 AI 없이 직접 할 수 있어야 하는 항목

    AI가 코드를 쓰는 속도가 빨라질수록, 그 코드를 받아들일지 정하는 리뷰가 더 중요해진다. 리뷰는 남의 흠을 찾는 일이 아니라 코드가 맞는지, 앞으로 고치기 쉬운지를 함께 확인하는 일이다. 직접형 항목이므로 C# 코드를 .NET SDK에 든 분석기로 검사하고, 도구가 못 잡는 냄새를 리뷰로 찾아, 동작을 바꾸지 않고 고친다(리팩토링). 예제는 .NET 10 콘솔 프로그램이다(실습 환경).

    이 항목에서 배우는 것¶

    • 리뷰에서 볼 것의 차례(동작, 테스트, 읽기 쉬움, 서식)를 알고, 자리와 까닭이 있는 댓글을 쓸 수 있다.
    • 정적 분석 도구를 켜서 경고를 읽고, 도구가 못 잡는 냄새를 찾을 수 있다.
    • 냄새를 리팩토링으로 고치되, 한 걸음마다 동작이 그대로인지 확인할 수 있다.

    1. 리뷰는 동작부터 보고, 서식은 도구에 맡긴다¶

    • 리뷰에서 가장 먼저 볼 것은 동작이 맞는지와 그것을 지키는 테스트가 있는지다(81번(요구사항과 명세), 84번(테스트 설계)). 서식은 마지막이고, 사람이 아니라 도구가 맞춘다.
    • 댓글은 자리(몇째 줄), 까닭, 제안을 담고, 사람이 아니라 코드에 대해 쓴다. 고칠지 말지는 함께 정한다.

    2. 분석기는 켜 둔 규칙을 빠짐없이 잡고, 사람은 의도를 읽는다¶

    직접 해 보기도구가 잡는 것, 사람이 잡는 것분석 모드(기본, Recommended, All)를 골라 같은 C# 코드에서 .NET 분석기가 내는 경고를 줄마다 보고, 사람의 리뷰가 찾아야 하는 냄새를 겹쳐 본다
    새 창에서 크게 열기
    • 정적 분석은 코드를 실행하지 않고 읽어서 실수와 위험한 쓰임을 찾는다. .NET SDK에는 분석기가 들어 있어, 프로젝트 파일에 AnalysisMode를 적으면 dotnet build가 경고를 낸다(문제 1).
    • .NET SDK의 분석기는 All로 올려도 중복된 분기, 아무 말도 하지 않는 이름, 한 메서드에 섞인 일처럼 의도를 읽어야 하는 냄새는 잡지 않았다(문제 2). 냄새를 내버려 두면 고칠 때마다 비용이 붙는다(기술 부채).

    3. 리팩토링은 동작을 바꾸지 않고 구조만 바꾼다¶

    • 냄새마다 이름이 있는 고치는 방법(리팩토링)이 있다. 표로 바꾸기, 상수로 이름 붙이기, 이름 바꾸기, 메서드 나누기가 흔하다.
    • 리팩토링은 동작을 바꾸지 않아야 한다. 한 걸음씩 고치고, 걸음마다 실행해 같은 결과인지 본다. 동작을 바꾸는 일은 따로 커밋한다(문제 3, 83번(Git 실천)).

    예측해 보기¶

    리뷰를 받을 코드다. dotnet new console로 만든 프로젝트의 Program.cs에서 원래 내용을 모두 지우고 넣는다. 그래야 경고의 줄 번호가 본문과 같다.

    var calc = new OrderCalculator();
Console.WriteLine(calc.Calc([(25000, 1)], "", false));          // "결제 금액: 28,000원"
Console.WriteLine(calc.Calc([(33000, 1)], "WELCOME10", false)); // "결제 금액: 32,700원"
Console.WriteLine(calc.Calc([(60000, 1)], "VIP20", true));      // "결제 금액: 57,500원"

public class OrderCalculator
{
    public string Calc(List<(int, int)> items, string coupon, bool express)
    {
        int total = 0;
        for (int i = 0; i < items.Count; i++)
        {
            total = total + items[i].Item1 * items[i].Item2;
        }
        int d = 0;
        if (coupon == "WELCOME10")
        {
            d = total * 10 / 100;
            if (d > 5000) d = 5000;
        }
        if (coupon == "VIP20")
        {
            d = total * 20 / 100;
            if (d > 5000) d = 5000;
        }
        int ship = 3000;
        if (total - d >= 30000) ship = 0;
        if (express) ship = ship + 2500;
        string result = "결제 금액: " + (total - d + ship).ToString("N0") + "원";
        return result;
    }
}

    문제 1. 이 코드를 dotnet build로 빌드하면 경고가 몇 개 나올까? 프로젝트 파일에 <AnalysisMode>Recommended</AnalysisMode>를 넣으면? 위젯을 누르기 전에 적어 본다.

    정답과 해설

    기본 설정에서는 0개, Recommended에서는 3개다. 이 PC의 .NET 10 SDK에서 Recommended는 CA1050(클래스를 네임스페이스 안에), CA1822(Calc를 static으로), CA1305(ToString("N0")의 결과가 PC의 지역 설정에 따라 다름)를 냈다. All로 올리면 3개가 더해져 6개였다. 기본 설정은 아주 확실한 문제만 경고하도록 많은 규칙을 꺼 둔다. 경고가 없다고 코드가 좋은 것이 아니고, 어느 규칙을 켤지는 팀이 정해 프로젝트 파일에 적어 둔다. 그래야 모두의 PC와 CI(89번(CI/CD))에서 같은 경고가 나온다.

    문제 2. 분석기를 All로 올려도 잡히지 않는 이 코드의 냄새를 셋 이상 찾는다. 줄 번호와 함께 적는다.

    정답과 해설

    쿠폰마다 되풀이되는 if 블록(16~25줄), 이름 없는 수 5000·3000·30000·2500(19·24·26~28줄), 무엇인지 말하지 않는 이름 Calc·d·ship(8·15·26줄), 금액 계산과 문장 만들기를 한 메서드가 하는 것(29줄)이다. 넷 모두 문법이나 쓰임의 규칙이 아니라 "이 코드가 무엇을 하려는가"를 읽어야 보이는 것이라, .NET 분석기는 All에서도 잡지 않았다. 쿠폰이 하나 더 생기면 블록을 또 복사하게 되고, 상한을 바꿀 때 5000 두 곳 가운데 하나를 빠뜨리기 쉽다. 이렇게 고칠 때마다 붙는 비용이 기술 부채다.

    문제 3. AI에게 이 코드를 "깔끔하게 리팩토링해 줘"라고 했더니, 쿠폰을 사전으로 바꾸면서 모르는 쿠폰이면 예외를 던지게 고쳤다. 이것은 리팩토링일까?

    정답과 해설

    아니다. 동작이 바뀌었다. 원래 코드는 모르는 쿠폰(빈 문자열 포함)이면 할인 없이 계산했다. 예외를 던지는 쪽이 더 나을 수도 있지만(81번(요구사항과 명세)에서는 그렇게 정했다), 그것은 명세를 바꾸는 결정이라 리팩토링과 섞으면 안 된다. 섞이면 리뷰어가 구조 정리 속에서 동작 바뀜을 놓치고, 문제가 생겨도 무엇이 원인인지 가리기 어렵다. 구조 정리와 동작 바뀜은 다른 커밋으로, 동작 바뀜에는 테스트를 함께 둔다. AI가 "정리"하며 동작까지 바꾸는 일은 흔하니 diff를 읽어 확인한다(83번(Git 실천)).

    직접 해보기¶

    실습: 분석기를 켜고, 리뷰하고, 리팩토링하기

    1. dotnet new console -o shop으로 프로젝트를 만들고 cd shop으로 들어간다. Program.cs의 내용을 모두 지우고 위의 코드를 넣어 dotnet run으로 세 줄의 결과를 적어 둔다. 리팩토링한 뒤에도 같아야 하는 기준이다.
    2. dotnet build로 경고를 본다. shop.csproj의 <PropertyGroup> 안에 <AnalysisMode>Recommended</AnalysisMode>를 넣고 다시 빌드한다. 다음에 All로 바꿔 빌드한다.
    3. 문제 2처럼 분석기가 못 잡는 냄새를 찾아, 리뷰 댓글 셋을 1절의 좋은 예처럼 줄 번호, 까닭, 제안을 담아 쓴다.
    4. 냄새를 하나씩 고친다. 하나 고칠 때마다 dotnet run으로 1단계의 세 줄과 같은지 본다. 다 고치면 All로 빌드해 경고가 남았는지 본다.
    5. 4단계를 마친 코드의 들여쓰기를 일부러 흐트러뜨리고 dotnet format whitespace --verify-no-changes를 실행해 본 뒤, dotnet format whitespace로 맞춘다.
    확인할 점
    • 2단계: 기본 설정은 경고 0개, Recommended는 3개, All은 6개였다(이 PC의 .NET SDK 10.0.401). Recommended의 경고는 이렇게 나온다(앞의 경로, 뒤의 도움말 주소와 프로젝트 이름은 줄였다). 경고 문장은 PC의 언어 설정을 따른다.
    Program.cs(6,14): warning CA1050: 네임스페이스에서 형식을 선언하세요.
Program.cs(8,19): warning CA1822: 'Calc' 멤버는 인스턴스 데이터에 액세스하지 않으며 static으로 표시할 수 있습니다.
Program.cs(29,37): warning CA1305: 'int.ToString(string)'의 동작은 현재 사용자의 로캘 설정에 따라 다를 수 있습니다. …
    • 4단계: 한 예다. 쿠폰 표, 상수, 이름 바꾸기, 메서드 나누기를 하고 분석기의 지적(네임스페이스, static, 문화권, internal, 읽기 전용 목록, null 확인)도 반영했다. 결과 세 줄은 그대로였고, Recommended와 All 모두 경고 0개였다.
    using System.Globalization;
using Shop;

Console.WriteLine(OrderCalculator.Describe([(25000, 1)], "", express: false));          // "결제 금액: 28,000원"
Console.WriteLine(OrderCalculator.Describe([(33000, 1)], "WELCOME10", express: false)); // "결제 금액: 32,700원"
Console.WriteLine(OrderCalculator.Describe([(60000, 1)], "VIP20", express: true));      // "결제 금액: 57,500원"

namespace Shop
{
    internal static class OrderCalculator
    {
        const int FreeShippingFrom = 30000;          // 할인 뒤 금액이 이만큼 이상이면 배송비 0원
        const int ShippingFee = 3000;
        const int ExpressFee = 2500;
        const int MaxDiscount = 5000;
        static readonly Dictionary<string, int> CouponPercent = new() { ["WELCOME10"] = 10, ["VIP20"] = 20 };
        static readonly CultureInfo Korean = CultureInfo.GetCultureInfo("ko-KR");

        public static int Total(IReadOnlyList<(int Price, int Quantity)> items, string coupon, bool express)
        {
            ArgumentNullException.ThrowIfNull(items);
            int subtotal = items.Sum(x => x.Price * x.Quantity);
            int discount = CouponPercent.TryGetValue(coupon, out int percent) ? Math.Min(subtotal * percent / 100, MaxDiscount) : 0;
            int paid = subtotal - discount;
            int shipping = paid >= FreeShippingFrom ? 0 : ShippingFee;
            return paid + shipping + (express ? ExpressFee : 0);
        }

        public static string Describe(IReadOnlyList<(int Price, int Quantity)> items, string coupon, bool express)
            => $"결제 금액: {Total(items, coupon, express).ToString("N0", Korean)}원";
    }
}
    • 모르는 쿠폰은 여전히 할인 없이 계산한다(TryGetValue가 거짓). 동작을 그대로 두는 것이 리팩토링의 약속이다. 다만 이 PC에서 따로 시험하니 계약 밖의 입력에서는 달라졌다. 쿠폰에 null을 넘기면 원래 코드는 28,000원을 냈지만 고친 코드는 ArgumentNullException을 던졌고, 합계가 int를 넘으면 원래 코드는 음수 금액을, 고친 코드(Sum)는 OverflowException을 냈다. 이런 작은 동작 바뀜도 PR 설명에 적어 리뷰어가 판단하게 한다. Total이 금액만 돌려주게 나뉘어, 이제 금액을 문장 없이 시험할 수 있다(84번(테스트 설계)).
    • 5단계: dotnet format whitespace --verify-no-changes는 흐트러진 곳마다 error WHITESPACE: 공백 서식을 수정하세요.를 줄과 칸과 함께 찍고 0이 아닌 종료 코드(2)로 끝났다. dotnet format whitespace를 실행하자 들여쓰기와 빈칸이 4단계의 코드와 똑같이 맞춰졌다. whitespace를 빼면 프로젝트에 켜 둔 분석기가 고칠 수 있는 것까지 함께 고친다. 이 PC에서 리팩토링 전 코드에 AnalysisMode를 All로 두고 dotnet format을 실행하니 public class가 internal class로 바뀌었다(CA1515). 이 확인을 CI에 넣으면 서식 이야기가 리뷰에서 사라진다(89번(CI/CD)).

    AI와 함께 확인하기¶

    AI 활용 과제: AI를 리뷰어로 쓰고, AI의 리뷰를 리뷰하기

    1. 리뷰 받을 코드를 AI에게 주고 "이 코드를 리뷰해 줘. 줄 번호와 까닭을 붙여서"라고 한다.
    2. AI의 지적을 "동작", "테스트", "읽기 쉬움", "서식"으로 나누고, 분석기 경고와 겹치는 것, 내가 찾은 냄새와 겹치는 것을 표시한다.
    3. AI의 지적 가운데 틀린 것(그런 줄이 없거나, 동작을 바꾸자는 제안을 리팩토링이라 부르는 것)을 찾는다.
    확인할 점
    • AI는 냄새(중복, 마법의 수, 이름)는 대개 잘 짚는다. 그러나 줄 번호를 틀리게 대거나, 문제가 아닌 것을 문제라고 단정하기도 한다. 지적마다 코드의 그 줄을 확인한다.
    • "모르는 쿠폰은 예외를 던져야 한다"처럼 정책을 바꾸자는 제안을 리팩토링 목록에 섞는 일이 흔하다(문제 3). 좋은 제안이라도 명세를 정하는 사람에게 묻고 따로 다룬다.
    • AI의 리뷰는 사람 리뷰어 한 명을 더한 것처럼 쓴다. 승인은 사람이 하고, 승인한 사람이 결과를 함께 책임진다.

    더 알아보기¶

    분석 규칙을 프로젝트에 적어 두기

    AnalysisMode 말고도 .editorconfig 파일에 규칙마다 심각도를 적을 수 있다(dotnet_diagnostic.CA1305.severity = error처럼). 팀이 동의한 규칙을 파일로 저장소에 넣어 두면, 모든 사람의 빌드와 CI가 같은 기준으로 검사한다. 처음부터 모든 규칙을 켜면 경고가 수백 개가 되어 아무도 읽지 않으니, 중요한 규칙부터 켜고 경고를 0개로 유지하는 편이 낫다.

    다른 언어의 린터와 정적 분석기

    Python에는 Ruff, Pylint, 타입 검사기 mypy가 있고, JavaScript에는 ESLint, C에는 컴파일러 경고(/W4)와 Visual Studio의 코드 분석(/analyze)이 있다. 이름은 달라도 하는 일은 같다. 켜 둔 규칙에 걸리는 실수를 사람보다 먼저, 빠짐없이 잡는다. 마법의 수(Ruff의 PLR2004, ESLint의 no-magic-numbers)나 중복 코드(Pylint의 R0801)처럼 냄새의 일부를 규칙으로 잡는 린터도 있다. 그래도 이 코드가 무엇을 하려는지는 사람이 읽는다. 이 강의는 설치가 필요 없는 .NET SDK의 분석기로 같은 생각을 보였다.

    정리¶

    • 리뷰는 동작과 테스트부터 보고, 서식은 도구에 맡긴다. 댓글은 자리, 까닭, 제안을 담아 코드에 대해 쓴다.
    • 분석기는 켜 둔 규칙에 걸리는 것을 빠짐없이 잡고, 중복이나 이름 같은 냄새는 사람이 리뷰로 찾는다. 어느 규칙을 켤지는 팀이 프로젝트 파일에 적는다.
    • 리팩토링은 동작을 바꾸지 않고 구조만 바꾼다. 한 걸음마다 실행해 같은 결과인지 보고, 동작 바뀜은 따로 다룬다.
