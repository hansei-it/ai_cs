    84. 테스트 설계: 단위/통합 테스트, 경계값, 속성 기반 테스트, TDD, AI가 만든 테스트의 실효성 판별¶

    직접 AI 없이 직접 할 수 있어야 하는 항목

    81번(요구사항과 명세)에서 수용 기준을 테스트로 옮겼다. 테스트는 많이 쓴다고 좋은 것이 아니라, 버그가 있을 때 실패해야 쓸모가 있다. AI는 테스트도 금방 만들어 주지만, 그 테스트가 버그를 잡는지는 따로 확인해야 한다. 직접형 항목이므로 81번의 order_total로 테스트의 범위, 입력 고르기, TDD의 순서, 테스트의 실효성을 직접 시험한다. 예제는 Python 표준 라이브러리의 unittest와 random만 쓴다.

    이 항목에서 쓰는 order.py (81번에서 고친 것) 
    # order.py
COUPONS = {"WELCOME10": 10}                          # 쿠폰 → 할인율(%)


def order_total(items, coupon=None):
    """items: [(가격, 수량), ...]. 결제할 금액(원)을 돌려준다."""
    if not items:
        raise ValueError("빈 장바구니는 주문할 수 없습니다")
    for price, qty in items:
        if price < 0 or qty <= 0:
            raise ValueError("가격과 수량을 확인하세요")
    if coupon is not None and coupon not in COUPONS:
        raise ValueError(f"모르는 쿠폰: {coupon}")
    subtotal = sum(price * qty for price, qty in items)
    discount = min(subtotal * COUPONS[coupon] // 100, 5000) if coupon else 0
    paid = subtotal - discount
    shipping = 0 if paid >= 30000 else 3000          # 무료 배송은 할인 뒤 금액으로 정한다
    return paid + shipping

    이 항목에서 배우는 것¶

    • 단위 테스트와 통합 테스트가 저마다 무엇을 잡는지 구분하고, 둘을 섞는 비율을 정할 수 있다.
    • 경계값과 성질(속성 기반 테스트)로 시험할 입력을 고를 수 있다.
    • 일부러 넣은 버그(변이)로 테스트의 실효성을 확인하고, TDD로 기능을 더할 수 있다.

    1. 단위 테스트는 빠르고 좁게, 통합 테스트는 이어 붙인 곳을 본다¶

    • 단위 테스트는 함수 하나를 바로 부른다. 이 PC에서 81번의 테스트 7개가 0.1ms 안에 끝났다. 실패하면 어느 규칙이 틀렸는지 바로 안다.
    • 통합 테스트는 서버를 띄우고 HTTP로 주문을 보낸다. 상태 코드, JSON의 키 이름처럼 이어 붙인 곳의 실수를 잡지만 테스트 2개에 15ms쯤 걸리고(요청 두 번은 1.5ms쯤, 나머지는 서버를 띄우고 내리는 시간), 실패하면 원인이 넓다.
    • 그래서 규칙의 경계와 예외는 단위 테스트로 촘촘히, 이어 붙인 곳은 통합 테스트 몇 개로 확인한다.

    2. 입력은 경계값과 성질로 고른다¶

    • 같은 결과가 나오는 입력 무리마다 대표 하나, 그리고 무리의 경계 양쪽과 경계 자체를 고른다. "바로 위"는 결과가 처음 달라지는 값으로 고른다(문제 1).
    • 속성 기반 테스트는 답 하나하나 대신 "늘 성립해야 할 성질"을 적고 무작위 입력 수천 개로 확인한다. 깨지는 예를 찾으면 가장 작은 예로 줄여 보여 준다(문제 2).

    3. 좋은 테스트는 버그가 있을 때 실패한다¶

    직접 해 보기테스트가 버그를 잡나테스트를 골라, 코드의 몇 줄을 실행하는지(줄 커버리지)와 코드에 일부러 넣은 버그(변이) 여섯 가운데 몇 개에서 테스트가 실패하는지 견준다
    새 창에서 크게 열기
    • 테스트가 코드의 많은 줄을 실행해도(커버리지), 결과를 제대로 확인하지 않으면 버그를 잡지 못한다(문제 3).
    • 코드에 일부러 작은 버그(변이)를 넣고 테스트가 실패하는지 보면 테스트의 실효성을 잴 수 있다. AI가 만든 테스트도 이렇게 확인한다.
    • TDD는 이것을 처음부터 한다. 실패하는 테스트를 먼저 쓰고(빨강), 통과할 만큼 고치고(초록), 정리한다(리팩터). 먼저 실패하는 것을 봐야 그 테스트가 버그를 잡을 수 있다는 것을 안다(직접 해보기).

    예측해 보기¶

    문제 1. 할인 상한(최대 5,000원)을 시험하려고 상품 금액의 경계 양쪽과 경계 자체를 고른다. 경계는 50,000원이다. "바로 위"는 50,001원이면 될까?

    정답과 해설

    아니다. 49,999원, 50,000원, 50,010원을 고른다. 10%에서 1원 미만을 버리므로 50,001~50,009원의 할인은 50,000원과 같은 5,000원이다. 상한을 빠뜨린 구현도 이 구간에서는 5,000원을 깎아, 50,001원으로는 그 버그를 잡지 못한다. 할인이 처음으로 5,000원을 넘는 50,010원이 상한의 "바로 위"다.

    for s in [49999, 50000, 50001, 50009, 50010]:
    print(s, s // 10, min(s // 10, 5000))       # 상품 금액, 상한 없는 할인, 상한 있는 할인

    49999 4999 4999
50000 5000 5000
50001 5000 5000
50009 5000 5000
50010 5001 5000

    문제 2. 아래 속성 기반 테스트는 "1,000원어치를 더 담으면 결제 금액이 줄지 않는다"는 성질을 무작위 상품 금액 2,000개로 확인하고, 깨지는 예를 찾으면 더 작은 값으로 줄인다. 이 성질은 성립할까? 깨진다면 줄인 예는 얼마일까? (order.py와 같은 폴더에서 따로 실행하려면 맨 위에 from order import order_total을 더한다.)

    import random


def shrink(fails, s):                              # 깨지는 예를 더 작은 값으로 줄인다
    while s > 1 and fails(s - 1):
        s -= 1
    return s


rng = random.Random(84)                            # 시드를 정해 두면 같은 예를 다시 얻는다
for coupon in [None, "WELCOME10"]:
    def fails(s):                                  # 성질: 1,000원어치를 더 담으면 결제 금액이 줄지 않는다
        return order_total([(s + 1000, 1)], coupon) < order_total([(s, 1)], coupon)
    tried = [rng.randint(1, 100_000) for _ in range(2000)]
    found = next((s for s in tried if fails(s)), None)
    print(coupon, found, shrink(fails, found) if found else None)
    정답과 해설 
    None 29012 29000
WELCOME10 33016 32333

    깨진다. 쿠폰 없이 29,000원이면 배송비를 더해 32,000원인데, 1,000원어치를 더 담아 30,000원이 되면 배송비가 빠져 30,000원이다. 쿠폰이 있으면 32,333원(32,100원)에서 33,333원(30,000원)으로 줄었다. 버그가 아니라 무료 배송 기준이 만든 결과라 정책을 정한 사람에게 확인한다. 의도한 것이면 성질을 고친다. "1,000원어치를 더 담아도 배송비 3,000원보다 많이 줄지는 않는다"로 바꾸면 1원부터 100,000원까지 모두 성립했다(가장 크게 준 것이 쿠폰 없이 2,000원, 쿠폰과 함께 2,100원). 속성 기반 테스트는 버그뿐 아니라 명세가 미처 생각하지 못한 결과도 드러낸다.

    문제 3. 위젯에서 AI가 만든 테스트 넷(T1~T4)만 고르면, 12줄 가운데 몇 줄을 실행하고 변이 여섯 가운데 몇 개를 잡을까? 고르기 전에 적어 본다.

    정답과 해설

    9줄(75%)을 실행하지만 변이는 하나(M5)만 잡는다. T1~T3은 결과를 제대로 확인하지 않는다. 정수인지, 쿠폰을 쓰면 싸지는지, 예외 없이 끝나는지만 본다. T4만 정확한 값을 보는데, 25,000원은 경계에도 할인에도 걸리지 않아 배송비 숫자를 바꾼 M5만 잡는다. 실행하지 않은 세 줄은 모두 예외를 던지는 줄이다. T5~T10을 더하면 12줄을 모두 실행하고 여섯을 모두 잡는다. 위젯의 결과는 같은 구현과 변이를 Python으로 짜서 변이마다 테스트를 돌려 얻은 결과와 같다.

    직접 해보기¶

    실습: TDD로 쿠폰을 더하고, 변이로 내 테스트 시험하기

    1. 위의 order.py와 81번(요구사항과 명세)의 test_order.py(테스트 7개)를 새 폴더에 둔다. 83번(Git 실천)의 shop 저장소에는 FREESHIP이 이미 들어 있어 빨강을 볼 수 없다.
    2. 새 요구사항: "FREESHIP 쿠폰은 할인 없이 배송비만 받지 않는다." 코드보다 먼저 test_order.py에 테스트 둘을 더하고 실행해 실패(빨강)를 본다. 실패한 까닭이 내가 예상한 까닭인지 확인한다.
    3. 테스트가 통과할 만큼만 order.py를 고친다(초록).
    4. 쿠폰 표가 할인율과 배송비 면제를 함께 담게 정리하고(리팩터), 테스트를 다시 돌려 모두 통과하는지 본다.
    5. 변이로 내 테스트를 시험한다. order.py의 paid >= 30000을 paid > 30000으로, 5000을 6000으로 하나씩 바꿔 실행하고 되돌린다. 실패하지 않는 변이가 있으면 그 변이를 잡는 테스트를 더한다.
    확인할 점

    한 예다. 2단계에서 OrderTotal 클래스에 더한 테스트다.

        def test_FREESHIP_배송비만_면제(self):            # 할인 없이 배송비만 받지 않는다
        self.assertEqual(order_total([(25000, 1)], "FREESHIP"), 25000)

    def test_FREESHIP_이미_무료여도_같다(self):
        self.assertEqual(order_total([(40000, 1)], "FREESHIP"), 40000)

    • 빨강: 이 PC에서 EE......., FAILED (errors=2)였다. 두 테스트 모두 ValueError: 모르는 쿠폰: FREESHIP로 멈췄다. FAIL(값이 다름)이 아니라 ERROR(예외)라는 점까지 예상과 맞는지 본다. 엉뚱한 까닭으로 실패하는 테스트는 고친 뒤에도 엉뚱한 까닭으로 통과할 수 있다.
    • 초록: COUPONS에 "FREESHIP": 0을 넣고 배송비 줄을 shipping = 0 if paid >= 30000 or coupon == "FREESHIP" else 3000으로 바꾸면 9개가 모두 통과했다. 이 단계에서는 깔끔함보다 통과가 먼저다.
    • 리팩터: 쿠폰 이름을 코드에 직접 적는 대신 표가 성질을 담게 바꿨다. 테스트 9개가 그대로 통과해 동작이 바뀌지 않았음을 확인했다.
    COUPONS = {"WELCOME10": (10, False), "FREESHIP": (0, True)}    # 쿠폰 → (할인율 %, 배송비 면제)


def order_total(items, coupon=None):
    """items: [(가격, 수량), ...]. 결제할 금액(원)을 돌려준다."""
    if not items:
        raise ValueError("빈 장바구니는 주문할 수 없습니다")
    for price, qty in items:
        if price < 0 or qty <= 0:
            raise ValueError("가격과 수량을 확인하세요")
    if coupon is not None and coupon not in COUPONS:
        raise ValueError(f"모르는 쿠폰: {coupon}")
    rate, free_ship = COUPONS[coupon] if coupon else (0, False)
    subtotal = sum(price * qty for price, qty in items)
    paid = subtotal - min(subtotal * rate // 100, 5000)
    shipping = 0 if free_ship or paid >= 30000 else 3000
    return paid + shipping

    고친 함수를 불러 확인한 결과다. 이 줄은 order.py에 넣지 않는다(넣으면 테스트가 order.py를 불러올 때마다 찍힌다). 같은 폴더에서 from order import order_total 다음에 실행한다.

    print(order_total([(25000, 1)], "FREESHIP"), order_total([(33000, 1)], "WELCOME10"))   # "25000 32700"
    • 변이: >로 바꾸면 test_딱_3만_원이 AssertionError: 33000 != 30000으로, 6000으로 바꾸면 test_할인_상한이 AssertionError: 54000 != 55000으로 실패했다. 둘 다 잡았다. 81번에서 경계와 상한을 수용 기준에 넣어 둔 덕이다.

    AI와 함께 확인하기¶

    AI 활용 과제: AI가 만든 테스트의 실효성 재기

    1. AI에게 order.py를 주고 "이 함수의 단위 테스트를 unittest로 짜 줘"라고 한다.
    2. 받은 테스트가 원래 구현에서 모두 통과하는지 먼저 본다.
    3. 위젯의 변이 M1~M6을 order.py의 같은 문장에 하나씩 넣고(위젯의 줄 번호는 위젯에 보인 코드의 것이다) 테스트가 실패하는지 표로 적는다. 살아남은 변이를 AI에게 보여 주고 그 변이를 잡는 테스트를 더하게 한다.
    확인할 점
    • 기대값을 구현과 같은 식으로 계산하는 테스트가 흔하다(expected = subtotal - min(subtotal // 10, 5000) + ...). 구현이 틀리면 기대값도 같이 틀려 늘 통과한다. 기대값은 명세에서 손으로 구한 숫자로 적는다.
    • 결과의 형만 보거나(정수인가), 예외가 없는지만 보거나, 보통 경우만 고른 테스트는 커버리지를 높이지만 변이를 거의 잡지 못한다(문제 3).
    • AI에게 테스트를 더하게 할 때 "살아남은 변이"를 구체적으로 보여 주면, 경계 값처럼 필요한 입력을 정확히 고른다.

    통합 테스트와 시간 재기

    1절의 통합 테스트와 측정 프로그램이다. 시간은 이 PC(Core i9-14900KF, DDR5 64GB, Windows 11, Python 3.14.0)에서 timing.py를 5번 실행한 범위다. 단위 테스트 7개는 20번 가운데 가운데값이 0.07~0.08ms, 통합 테스트 2개는 15.31~15.57ms였다. 처음에는 통합 테스트가 510ms가 넘게 걸렸는데, 서버를 내리는 shutdown()이 serve_forever가 멈추라는 요청을 확인할 때(기본 0.5초마다)까지 기다렸기 때문이다. 확인 간격을 0.01초로 줄여 다시 쟀다. 단계별로 나눠 재면(20번의 가운데값, 3번 실행) 서버 띄우기 0.6ms, 요청 두 번 1.5ms, 서버 내리기 13.3~13.5ms였다. 통합 테스트가 느린 것은 HTTP 요청보다 서버를 띄우고 내리는 일 때문이라, 테스트 클래스마다 서버를 한 번만 띄운다.

    # test_api.py: 통합 테스트. 주문 서버를 띄워 HTTP로 주문을 보내고, 응답의 상태 코드와 JSON을 본다
import http.client
import json
import threading
import unittest
from http.server import BaseHTTPRequestHandler, ThreadingHTTPServer

from order import order_total


class OrderAPI(BaseHTTPRequestHandler):           # POST /orders {"items": [[가격, 수량], ...], "coupon": ...}
    def do_POST(self):
        body = json.loads(self.rfile.read(int(self.headers["Content-Length"])))
        try:
            status, reply = 200, {"total": order_total([tuple(x) for x in body["items"]], body.get("coupon"))}
        except ValueError as e:
            status, reply = 400, {"error": str(e)}
        data = json.dumps(reply, ensure_ascii=False).encode()
        self.send_response(status)
        self.send_header("Content-Type", "application/json; charset=utf-8")
        self.send_header("Content-Length", str(len(data)))
        self.end_headers()
        self.wfile.write(data)

    def log_message(self, *a):
        pass


class OrderAPITest(unittest.TestCase):
    @classmethod
    def setUpClass(cls):                           # 테스트 클래스마다 서버를 한 번 띄운다
        cls.server = ThreadingHTTPServer(("127.0.0.1", 0), OrderAPI)
        threading.Thread(target=cls.server.serve_forever, args=(0.01,), daemon=True).start()   # 0.01초마다 멈추라는 요청을 본다

    @classmethod
    def tearDownClass(cls):
        cls.server.shutdown()
        cls.server.server_close()

    def post(self, payload):
        c = http.client.HTTPConnection("127.0.0.1", self.server.server_address[1])
        c.request("POST", "/orders", json.dumps(payload), {"Content-Type": "application/json"})
        r = c.getresponse()
        reply = json.loads(r.read())
        c.close()
        return r.status, reply

    def test_쿠폰_주문(self):
        self.assertEqual(self.post({"items": [[33000, 1]], "coupon": "WELCOME10"}), (200, {"total": 32700}))

    def test_빈_장바구니는_400(self):
        status, reply = self.post({"items": []})
        self.assertEqual(status, 400)
        self.assertIn("빈 장바구니", reply["error"])


if __name__ == "__main__":
    unittest.main()


    # timing.py: 단위 테스트(test_order.py, 7개)와 통합 테스트(test_api.py, 2개)를 따로 20번씩 돌려 걸린 시간을 잰다
import io
import time
import unittest

for name in ["test_order", "test_api"]:
    times = []
    for _ in range(20):
        suite = unittest.defaultTestLoader.loadTestsFromName(name)
        t = time.perf_counter()
        result = unittest.TextTestRunner(stream=io.StringIO()).run(suite)
        times.append((time.perf_counter() - t) * 1000)
        assert result.wasSuccessful()
    times.sort()
    print(f"{name}: 테스트 {result.testsRun}개, 20번 가운데 가운데값 {times[10]:.2f} ms (가장 빠른 {times[0]:.2f}, 가장 느린 {times[-1]:.2f})")

    가짜 객체와 시험하기 쉬운 코드

    결제 API, DB, 현재 시각, 난수처럼 테스트할 때마다 달라지거나 느린 것에 기대는 코드는 단위 테스트가 어렵다. 그런 것을 인자로 받게 짜면 테스트에서 가짜(테스트 대역)를 넣을 수 있다. 문제 2가 random.Random(84)를 만들어 쓰고, 67번(요청 경로의 구성 요소)의 토큰 버킷이 시각을 인자로 받은 것과 같은 생각이다(15번(SOLID 원칙과 디자인 패턴)에서 저장소를 생성자로 받은 것과 같다. 쓸 것을 밖에서 넘겨주는 이 방식을 18번(라이브러리와 프레임워크의 차이)의 의존성 주입이라 한다). 다만 가짜는 진짜와 조금씩 달라질 수 있어, 진짜와 이어 붙인 곳은 통합 테스트로 따로 확인한다.

    정리¶

    • 단위 테스트는 빠르고 실패한 곳이 분명하다. 규칙의 경계와 예외는 단위 테스트로 촘촘히, 이어 붙인 곳은 통합 테스트 몇 개로 확인한다.
    • 입력은 무리의 대표, 경계의 양쪽과 경계 자체로 고르고, 늘 성립해야 할 성질은 무작위 입력으로 확인한다.
    • 커버리지는 실행한 줄을 셀 뿐이다. 일부러 넣은 버그를 잡는지(변이)로 테스트를 재고, TDD로 실패를 먼저 본다.
