    88. 성능 측정과 프로파일링: 추측 대신 측정으로 병목 찾기¶

    직접 AI 없이 직접 할 수 있어야 하는 항목

    AI에게 "이 코드를 빠르게 해 줘"라고 하면 코드는 금방 바뀐다. 그런데 어디가 느린지 재지 않고 바꾼 코드는 느리지 않은 곳을 고치기 쉽고, 빨라졌는지도 모른다. 직접형 항목이므로 주문 기록 보고서 프로그램을 프로파일러로 재어 병목을 찾고, 고치고, 결과가 같은지 견주고, 다시 잰다. 예제는 Python이다(실습 환경).

    이 항목에서 배우는 것¶

    • 프로파일러 결과에서 자기 시간과 부른 함수까지의 시간을 읽고 병목을 찾을 수 있다.
    • 시간을 같은 조건으로 여러 번 재고, 흔들림보다 작은 차이를 가려낼 수 있다.
    • 병목 하나를 고친 뒤 결과가 같은지 확인하고 다시 재어 효과를 말할 수 있다.

    1. 느린 곳은 짐작하지 말고 프로파일러로 찾는다¶

    직접 해 보기어디가 느릴까: 짐작과 프로파일러report.py에서 가장 오래 걸릴 것 같은 함수를 눌러 짐작한 뒤 프로파일러로 재어 견주고, 병목을 사전으로 고친 판을 다시 재어 본다
    새 창에서 크게 열기
    • 프로파일러는 함수마다 몇 번 불렸고 얼마나 걸렸는지 센다. Python에 든 cProfile은 python -m cProfile -s tottime report.py로 바로 쓴다.
    • 자기 시간(tottime)은 그 함수 안의 코드만, 부른 함수까지(cumtime)는 그 함수가 부른 함수의 시간까지 더한 것이다. 부른 함수까지는 큰데 자기 시간이 작으면, 그 함수가 부르는 쪽으로 따라 내려간다(문제 1).
    • 짐작은 파일 읽기나 정렬처럼 무거워 보이는 곳으로 가기 쉽다. 이 프로그램의 시간은 네 줄짜리 함수에서 쓰였다.

    2. 시간은 프로파일러 없이, 같은 조건으로 여러 번 잰다¶

    • 같은 코드도 잴 때마다 다르다. 한 번씩 잰 값으로 고치기 전과 뒤를 견주면 흔들림을 개선으로 착각한다(문제 3).
    • 프로파일러는 함수를 부를 때마다 기록하느라 프로그램을 느리게 한다. 프로파일러로는 어디를 찾고, 얼마는 프로파일러 없이 time.perf_counter로 잰다(문제 2).

    3. 가장 큰 곳 하나를 고치고, 결과가 같은지 보고, 다시 잰다¶

    • 전체의 4%인 곳을 아무리 빠르게 해도 4%까지만 준다(33번(동시성과 병렬성)의 암달의 법칙). 가장 큰 곳부터 하나씩 고친다.
    • 빨라진 코드가 다른 답을 내면 고친 것이 아니다. 고치기 전 출력을 저장해 두고 견준다(84번(테스트 설계)의 테스트가 있으면 더 좋다).
    • 목표("1초 안에")를 먼저 정하고, 닿으면 멈춘다. 재지 않고 빠르게 만든 코드는 대개 읽기만 어려워진다.

    예측해 보기¶

    문제 1. 아래는 실습의 report.py를 python -m cProfile -s tottime report.py로 잰 결과의 앞부분이다. totals는 tottime이 0.026초인데 cumtime은 1.197초다. 무슨 뜻이고, 무엇을 고쳐야 할까?

             304582 function calls (304576 primitive calls) in 1.247 seconds

   Ordered by: internal time

   ncalls  tottime  percall  cumtime  percall filename:lineno(function)
   100000    0.583    0.000    1.165    0.000 report.py:10(customer_no)
   100000    0.582    0.000    0.582    0.000 {method 'index' of 'list' objects}
        1    0.044    0.044    0.044    0.044 report.py:5(read_orders)
        1    0.026    0.026    1.197    1.197 report.py:16(totals)
   100051    0.007    0.000    0.007    0.000 {built-in method builtins.len}
    정답과 해설

    totals 자신의 코드(반복과 더하기)는 0.026초뿐이고, 나머지는 totals가 부른 customer_no 안에서 쓰였다. customer_no는 10만 번 불려 부른 함수까지 1.165초이고, 그 가운데 0.582초가 list.index, 0.583초가 customer_no 자신의 코드다. 자기 시간의 대부분은 name not in customers다. in은 함수 호출이 아니라서 cProfile에 따로 줄이 나오지 않고 그 줄이 있는 함수의 자기 시간에 들어간다. in과 index는 둘 다 손님 2,000명의 목록을 앞에서부터 훑는다(22번(해시 테이블)의 해시 테이블과 견준다). 그러니 고칠 곳은 totals의 반복이 아니라 손님을 찾는 방법이다. 표를 cumtime으로 정렬해(-s cumtime) 위에서부터 따라 내려가도 같은 곳에 닿는다.

    문제 2. 손님을 사전으로 찾게 고친 판을 cProfile로 재니 totals의 cumtime이 0.020초로 나왔다. 같은 totals를 프로파일러 없이 재면 얼마쯤일까? (가) 0.020초쯤 (나) 그보다 훨씬 짧다 (다) 그보다 훨씬 길다

    # 고친 report.py와 같은 폴더에서: 프로파일러 없이 totals만 7번 재어 가장 짧은 값을 본다
import time

from report import read_orders, totals

orders = read_orders("orders.csv")
times = []
for _ in range(7):
    start = time.perf_counter()
    totals(orders)
    times.append(time.perf_counter() - start)
print(f"{min(times):.4f}")
    정답과 해설

    (나) 0.006초쯤이다. 이 PC에서 여러 번 실행해 0.0056~0.0059초였다. 프로파일러가 3배 넘게 부풀렸다. 고친 totals는 dict.get을 10만 번 부르는데, cProfile은 부를 때마다 시각을 재고 표에 적는다. 그 일이 dict.get 자체보다 크다. 원래 판은 cProfile의 1.247초와 프로파일러 없이 잰 1.15~1.18초가 크게 다르지 않았다. 시간이 in과 index가 목록을 길게 훑는 데 쓰여, 부른 횟수에 견주어 계산이 컸기 때문이다. 작은 함수를 많이 부르는 코드일수록 프로파일러가 많이 부풀린다. 그래서 프로파일러로는 어디가 큰지를 보고, 시간 자체는 프로파일러 없이 잰다.

    문제 3. AI가 "csv.reader 대신 split(",")을 쓰면 빨라진다"며 원래 판의 read_orders를 아래처럼 바꿨다. 바꾸기 전과 뒤에 보고서 계산을 한 번씩만 재어 1.253초와 1.168초를 얻었다. 7% 빨라졌다고 할 수 있을까?

    def read_orders(path):                           # AI가 바꾼 판
    with open(path) as f:
        return [(name, int(price), int(qty)) for name, price, qty in (line.rstrip("\n").split(",") for line in f)]
    정답과 해설

    할 수 없다. 1.253초와 1.168초는 사실 아무것도 바꾸지 않은 같은 코드를 연달아 잰 값이다(그림의 1번째 실행의 두 값). 이 PC에서 따로 재 보니 read_orders는 0.034~0.035초에서 0.033초로 0.001~0.002초 줄었고, 전체(1.17초쯤)로는 0.2%였다. 7번 잰 가장 짧은 값도 1.167초와 1.165초로 흔들림 안에 묻혔다. 전체의 4%인 곳이라 아무리 빨라져도 4%를 넘지 못한다. 게다가 split은 손님 이름에 쉼표가 있으면 틀린다. CSV는 쉼표가 든 값을 따옴표로 감싸는데, split은 따옴표를 모른다.

    import csv
import io

line = '"김, 하나",12000,2\n'  # 이름에 쉼표가 있는 주문 한 줄
print(next(csv.reader(io.StringIO(line))))  # ['김, 하나', '12000', '2']
name, price, qty = line.rstrip("\n").split(",")  # ValueError: too many values to unpack (expected 3, got 4)

    빨라지지 않았는데 틀릴 수 있는 코드가 된 것이다.

    직접 해보기¶

    실습: 재고, 고치고, 견주고, 다시 재기

    1. 새 폴더에 아래 세 파일을 저장하고, 명령 프롬프트에서 python make_orders.py로 orders.csv(주문 10만 줄, 약 1.6MB)를 만든다. 몇 번을 만들어도 같은 내용이다.
    2. python report.py > before.txt로 고치기 전 출력을 저장하고, python bench.py로 시간을 잰다.
    3. python -m cProfile -s tottime report.py로 가장 큰 곳을 찾는다. 위젯에서 한 짐작과 견준다.
    4. 가장 큰 곳 하나만 고친다. python report.py > after.txt로 다시 저장하고 fc before.txt after.txt로 출력이 같은지 본다(명령 프롬프트에서 한다. PowerShell에서 fc는 다른 명령이라 fc.exe로 쓴다).
    5. python bench.py로 다시 재어 몇 배 빨라졌는지 적는다. 이제 가장 큰 곳은 어디인가? 더 고칠지는 무엇으로 정할까?

    # make_orders.py: 연습용 주문 기록 orders.csv를 만든다(손님 2,000명, 주문 100,000건). 몇 번을 실행해도 같은 내용이다
import random

random.seed(88)
names = [f"손님{i:04d}" for i in range(2000)]
with open("orders.csv", "w", newline="") as f:
    for _ in range(100_000):
        f.write(f"{random.choice(names)},{random.randrange(1000, 50001, 100)},{random.randint(1, 5)}\n")


    # report.py: 주문 기록(orders.csv)에서 손님별 매출을 모아 상위 5명을 보여 준다
import csv


def read_orders(path):
    with open(path, newline="") as f:
        return [(name, int(price), int(qty)) for name, price, qty in csv.reader(f)]


def customer_no(customers, name):                # 손님 이름 → 번호. 처음 보는 손님이면 번호를 새로 준다
    if name not in customers:
        customers.append(name)
    return customers.index(name)


def totals(orders):
    customers, sums = [], []
    for name, price, qty in orders:
        no = customer_no(customers, name)
        if no == len(sums):
            sums.append(0)
        sums[no] += price * qty
    return customers, sums


def top(customers, sums, k=5):
    return sorted(zip(sums, customers), reverse=True)[:k]


def main():
    orders = read_orders("orders.csv")
    customers, sums = totals(orders)
    for total, name in top(customers, sums):
        print(f"{name} {total:,}원")


if __name__ == "__main__":
    main()

    AI와 함께 확인하기¶

    AI 활용 과제: \"빠르게 해 줘\"의 결과를 재어 보기

    1. 원래 report.py를 AI에게 주고 "이 코드를 빠르게 해 줘"라고만 한다.
    2. 받은 코드에서 바뀐 곳을 모두 찾고, 그 가운데 cProfile이 가리킨 곳이 있는지 본다.
    3. 바뀐 곳을 하나씩 따로 적용하며 fc로 출력을 견주고 bench.py로 잰다. 효과가 흔들림보다 작은 고침은 되돌린다.
    확인할 점
    • AI는 대개 재지 않고 고친다. 사전으로 바꾸는 큰 고침에 split, 컴프리헨션 같은 작은 고침을 섞어 내는 경우가 많다. 하나씩 재면 효과는 거의 다 사전에서 나온다(문제 3).
    • 상위 손님을 sorted(sums.items(), key=lambda kv: kv[1], reverse=True)로 고르는 답이 흔하다. 원래 코드는 매출이 같으면 이름의 역순으로 놓고, 이 코드는 처음 나온 차례로 놓는다. 이 자료의 상위 5명에는 매출이 같은 손님이 없어 fc로는 드러나지 않는다. 출력이 같다는 것은 이 입력에서 같다는 뜻일 뿐이다. 매출이 같은 손님을 넣은 작은 입력으로 테스트를 더한다(84번(테스트 설계)).
    • pandas 같은 외부 패키지를 쓰자는 답은 설치(17번(패키지 생태계와 의존성 관리))와 공급망(77번(의존성 공급망 보안))의 비용까지 함께 따진다. 표준 라이브러리로 고친 판이 이미 0.04초다.

    더 알아보기¶

    누가 불렀나 보기: pstats

    결과를 파일로 저장하면 정렬을 바꿔 가며 다시 볼 수 있다. python -m cProfile -o p.out report.py로 저장하고 python -m pstats p.out을 실행하면 명령을 받는 창이 열린다. 이 PC에서 sort cumtime, stats 4는 부른 함수까지가 큰 차례로 네 줄을 보였고, callers index는 list.index를 부른 곳이 report.py:10(customer_no)이고 10만 번이라고 보였다. quit으로 끝낸다. 큰 프로그램에서는 이렇게 부른 쪽을 따라 올라가며 병목이 어느 길로 불리는지 찾는다.

    샘플링 프로파일러

    cProfile은 모든 호출을 기록한다. 그래서 부른 횟수는 정확하지만 문제 2처럼 작은 함수를 많이 부르는 코드를 느리게 한다. 샘플링 프로파일러는 일정한 간격으로 프로그램이 지금 무엇을 실행 중인지 엿보고 그 횟수를 센다. 부담이 작아서 운영 중인 서버에도 붙여 본다(72번(관측성)의 관측성). py-spy가 Python의 예이고(외부 도구), Visual Studio의 프로파일러에도 이 방식으로 C와 C# 프로그램의 CPU 시간을 재는 도구가 있다. 어느 쪽이든 "어디가 큰가"를 보는 도구이고, 고친 뒤의 시간은 따로 잰다.

    정리¶

    • 느린 곳은 짐작하지 말고 프로파일러로 찾는다. 부른 함수까지의 시간이 큰 곳에서 자기 시간이 큰 곳으로 따라 내려간다.
    • 프로파일러는 어디인지 찾는 도구다. 시간은 프로파일러 없이 같은 조건으로 여러 번 재고, 흔들림보다 작은 차이는 차이로 보지 않는다.
    • 가장 큰 곳 하나를 고치고, 출력이 같은지 견주고, 다시 잰다. 목표에 닿으면 멈춘다.
