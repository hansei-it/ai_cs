    81. 요구사항 분석과 명세 작성: 완료 조건, 예외 상황, 수용 기준 정의¶

    직접 AI 없이 직접 할 수 있어야 하는 항목

    AI에게 "3만 원 이상이면 배송비 무료로 해 줘"라고 하면 코드는 몇 초 만에 나온다. 그런데 그 코드가 맞는지는 코드가 아니라 요구사항이 정한다. 요구사항이 정하지 않은 것은 AI가 대신 정하고, 그 결정은 코드 속에 조용히 숨는다. 직접형 항목이므로 한 줄 요구사항에서 질문을 뽑고, 명세를 쓰고, 수용 기준을 실행되는 테스트로 바꿔 AI가 짠 코드를 직접 시험한다. 예제는 Python이다(실습 환경).

    이 항목에서 배우는 것¶

    • 한 줄 요구사항에서 정해지지 않은 결정을 질문으로 뽑을 수 있다.
    • 명세를 완료 조건, 예외 상황, 수용 기준(구체적인 예)으로 쓸 수 있다.
    • 수용 기준을 테스트로 바꾸고, 구현이 명세와 다르게 가정한 곳을 찾을 수 있다.

    1. 한 줄 요구사항에는 정하지 않은 결정이 숨어 있다¶

    • "3만 원 이상이면 배송비 무료, 신규 회원 쿠폰은 10% 할인, 최대 5천 원"은 분명해 보이지만, 그림처럼 적어도 여섯 가지가 정해지지 않았다.
    • 묻지 않으면 구현하는 사람이나 AI가 하나를 고른다. 고른 결과는 >=인지 >인지 같은 한 글자라 리뷰에서도 잘 안 보인다.
    • 질문은 답할 사람(기획자, 고객)에게 묻고, 받은 답을 명세에 적는다.

    2. 명세는 완료 조건, 예외 상황, 수용 기준으로 적는다¶

    • 완료 조건은 무엇이 되면 끝인지, 예외 상황은 잘못된 입력이나 실패가 오면 무엇을 하는지 적는다. "빠르게"처럼 잴 수 없는 말 대신 숫자로 쓴다.
    • 수용 기준은 "이 입력이면 이 결과"라는 구체적인 예다. 말로 쓴 규칙은 읽는 사람마다 다르게 읽히지만, 예는 그보다 훨씬 덜 갈린다.

    3. 수용 기준은 해석이 갈리는 곳을 짚는 예로 고른다¶

    직접 해 보기예로 해석의 차이 잡기수용 기준으로 쓸 예(상품 금액과 쿠폰)를 골라, 명세와 가정을 달리한 AI 구현 셋의 결제 금액을 견주고 몇 개의 잘못된 구현을 잡아내는지 본다
    새 창에서 크게 열기
    • 위젯의 세 구현은 같은 한 줄 요구사항으로 만들었지만 저마다 하나를 다르게 가정했다. 예를 골라 셋을 모두 잡아 본다.
    • 보통 경우만 적으면 잘못된 구현도 통과한다. 경계 값 자체와 조합(쿠폰 + 경계)이 해석의 차이를 드러낸다(문제 2).
    • 고른 예는 그대로 테스트 코드가 된다. 명세가 실행되는 것이다(직접 해보기, 84번(테스트 설계)).

    예측해 보기¶

    문제 1. 같은 요구사항으로 만든 두 함수에 상품 33,000원과 쿠폰을 넣는다. 무엇이 출력될까? 어느 쪽이 맞을까?

    def total_a(subtotal, coupon):                   # 할인 전 금액으로 배송비를 정한다
    discount = min(subtotal // 10, 5000) if coupon else 0
    shipping = 0 if subtotal >= 30000 else 3000
    return subtotal - discount + shipping


def total_b(subtotal, coupon):                   # 할인 뒤 금액으로 배송비를 정한다
    discount = min(subtotal // 10, 5000) if coupon else 0
    paid = subtotal - discount
    return paid + (0 if paid >= 30000 else 3000)


print(total_a(33000, True), total_b(33000, True))
    정답과 해설

    29700 32700. 할인 3,300원을 빼면 29,700원이다. total_a는 할인 전 33,000원을 보고 배송비를 받지 않았고, total_b는 할인 뒤 29,700원을 보고 3,000원을 받았다. 어느 쪽이 맞는지는 코드로는 알 수 없다. 요구사항이 정하지 않았기 때문이다. 손님 쪽에서 보면 3,000원 차이이고, 회사 쪽에서 보면 쿠폰 때문에 3만 원 아래로 내려간 주문마다 배송비를 대신 내는 정책 결정이다. 개발자가 아니라 정책을 정하는 사람에게 물어 명세에 적는다.

    문제 2. 위젯에서 25,000원, 29,999원, 50,000원 + 쿠폰을 수용 기준으로 골랐다. 세 구현 가운데 몇 개를 잡을까? 셋을 모두 잡으려면 어떤 예가 필요할까? 위젯을 누르기 전에 적어 본다.

    정답과 해설

    하나도 못 잡는다. 29,999원은 경계 바로 아래라 "이상"이든 "초과"든 배송비를 받는다. 50,000원 + 쿠폰은 10%가 정확히 5,000원이라 상한이 있든 없든 같다. 경계 근처라도 해석이 갈리는 바로 그 값을 짚어야 한다. 딱 30,000원(이상과 초과가 갈린다), 33,000원 + 쿠폰(할인이 금액을 경계 아래로 내린다), 60,000원 + 쿠폰(할인이 상한을 넘는다)의 셋이면 모두 잡는다. 이 PC에서 같은 규칙을 Python으로 따로 짜서 여덟 가지 예로 위젯과 같은 결과를 얻었다.

    직접 해보기¶

    실습: 수용 기준으로 AI가 짠 코드 시험하기

    1. 아래 order.py를 저장한다. AI에게 한 줄 요구사항만 주고 받은 코드다.
    2. 기획자에게 물어 받은 아래 결정표를 보고, 수용 기준을 "입력 → 기대 결과"로 여섯 개 이상 적는다. 보통 경우, 경계, 조합, 예외 상황을 하나 이상씩 넣는다.
    3. 수용 기준을 test_order.py에 unittest로 옮기고, 같은 폴더에서 python -m unittest -v test_order로 실행한다.
    4. 실패한 기준마다 구현이 무엇을 다르게 가정했는지 한 줄로 적는다. 코드를 고치기 전에, 틀린 것이 구현인지 명세인지 먼저 판단한다.
    # order.py: AI에게 "3만 원 이상이면 배송비 무료, 신규 회원 쿠폰은 10% 할인, 최대 5천 원"이라고만 말하고 받은 코드
def order_total(items, coupon=None):
    """items: [(가격, 수량), ...]. 결제할 금액(원)을 돌려준다."""
    for price, qty in items:
        if price < 0 or qty <= 0:
            raise ValueError("가격과 수량을 확인하세요")
    subtotal = sum(price * qty for price, qty in items)
    discount = min(subtotal // 10, 5000) if coupon == "WELCOME10" else 0
    shipping = 0 if subtotal >= 30000 else 3000
    return subtotal - discount + shipping
    질문 기획자의 답
    무료가 아니면 배송비는? 3,000원
    딱 30,000원이면? 무료다(이상)
    할인 전 금액인가, 뒤 금액인가? 쿠폰 할인 뒤 금액으로 정한다
    10% 할인의 1원 미만은? 버린다. 할인은 최대 5,000원
    빈 장바구니는? 주문할 수 없다(ValueError)
    수량 0 이하, 음수 가격은? 주문할 수 없다(ValueError)
    모르는 쿠폰은? 주문할 수 없다(ValueError). 손님이 잘못 적은 것을 알려야 한다
    확인할 점

    한 예다. 수용 기준 하나가 테스트 하나다.

    # test_order.py: 결정표에서 고른 수용 기준을 옮긴 테스트
import unittest

from order import order_total


class OrderTotal(unittest.TestCase):
    def test_보통_경우(self):  # 25,000원 → 배송비 3,000원
        self.assertEqual(order_total([(25000, 1)]), 28000)

    def test_딱_3만_원(self):  # 30,000원 이상이면 무료
        self.assertEqual(order_total([(10000, 3)]), 30000)

    def test_할인_뒤_3만_원_아래(self):  # 33,000원 − 3,300원 = 29,700원 → 배송비 3,000원
        self.assertEqual(order_total([(33000, 1)], "WELCOME10"), 32700)

    def test_할인_상한(self):  # 60,000원의 10%는 6,000원이지만 5,000원까지
        self.assertEqual(order_total([(60000, 1)], "WELCOME10"), 55000)

    def test_빈_장바구니(self):
        with self.assertRaises(ValueError):
            order_total([])

    def test_수량_0(self):
        with self.assertRaises(ValueError):
            order_total([(1000, 0)])

    def test_모르는_쿠폰(self):
        with self.assertRaises(ValueError):
            order_total([(25000, 1)], "WELCOME100")


if __name__ == "__main__":
    unittest.main()

    • 이 PC에서 실행하니 7개 가운데 3개가 실패했다(FAILED (failures=3)). test_할인_뒤_3만_원_아래는 AssertionError: 29700 != 32700, test_빈_장바구니와 test_모르는_쿠폰은 AssertionError: ValueError not raised였다.
    • 구현이 다르게 가정한 것은 셋이다. 무료 배송을 할인 전 금액으로 정했고, 빈 장바구니에는 배송비 3,000원만 받는 주문을 만들고, 모르는 쿠폰은 말없이 할인 없이 넘겼다. 셋 다 요구사항 한 줄에는 없던 결정이라, AI가 틀렸다기보다 묻지 않은 결과다.
    • 1원 미만 버림(order_total([(25009, 1)], "WELCOME10")은 25,509원. 반올림하면 25,508원이다)과 음수 가격도 수용 기준으로 더할 수 있다. 이 PC에서 둘은 AI 구현도 통과해, 실패한 테스트는 그대로 3개였다.
    • 보통 경우, 딱 3만 원, 할인 상한, 수량 0은 통과했다. 통과한 테스트도 남겨 둔다. 고치다가 다른 곳을 망가뜨리지 않았는지 지켜 준다.
    • 결정표대로 고친 구현이다. 같은 테스트 7개가 모두 통과했다(OK).
    # order.py
COUPONS = {"WELCOME10": 10}                          # 쿠폰 → 할인율(%)


def order_total(items, coupon=None):
    """items: [(가격, 수량), ...]. 결제할 금액(원)을 돌려준다."""
    if not items:
        raise ValueError("빈 장바구니는 주문할 수 없습니다")
    for price, qty in items:
        if price < 0 or qty <= 0:
            raise ValueError("가격과 수량을 확인하세요")
    if coupon is not None and coupon not in COUPONS:
        raise ValueError(f"모르는 쿠폰: {coupon}")
    subtotal = sum(price * qty for price, qty in items)
    discount = min(subtotal * COUPONS[coupon] // 100, 5000) if coupon else 0
    paid = subtotal - discount
    shipping = 0 if paid >= 30000 else 3000          # 무료 배송은 할인 뒤 금액으로 정한다
    return paid + shipping

    고친 함수를 불러 확인한 결과다. 이 줄은 order.py에 넣지 않고, 같은 폴더에서 from order import order_total 다음에 실행한다.

    print(order_total([(33000, 1)], "WELCOME10"))        # 32700

    AI와 함께 확인하기¶

    AI 활용 과제: AI가 조용히 정한 가정 찾기

    1. 실습의 한 줄 요구사항만 AI에게 주고 Python 함수를 짜게 한다.
    2. 받은 코드에서 요구사항에 없던 결정(비교 연산자, 반올림, 빈 입력과 잘못된 입력의 처리)을 모두 찾아 표시한다.
    3. 같은 AI에게 "이 요구사항에서 정해지지 않은 것을 질문 목록으로 만들어 줘"라고 한다. 내가 찾은 것과 AI의 목록을 견주고, 서로 빠뜨린 것을 적는다.
    확인할 점
    • 코드를 짤 때 AI가 질문하지 않고 하나를 골랐는지 본다. 그 결정이 주석에 적혀 있지 않으면 코드만 읽어서는 결정인지 실수인지 알 수 없다. 명세에 없는 결정은 주석이나 질문 목록으로 드러내게 시킨다.
    • AI의 질문 목록에 경계와 할인 기준뿐 아니라 빈 장바구니, 모르는 쿠폰, 동시에 두 쿠폰처럼 "잘못된 입력"과 응답 시간 같은 비기능 요구사항이 들어 있는지 본다.
    • AI가 만든 질문에 AI가 스스로 답하게 두지 않는다. 답은 정책을 정하는 사람에게 받는다.

    더 알아보기¶

    Given-When-Then: 수용 기준을 쓰는 형식

    수용 기준을 "주어진 상황(Given), 일이 일어나면(When), 결과는(Then)"의 세 줄로 쓰는 형식이 널리 쓰인다. "장바구니에 33,000원 상품이 있고(Given), WELCOME10 쿠폰으로 주문하면(When), 결제 금액은 32,700원이다(Then)." 기획자와 개발자가 같은 문장을 읽고, Cucumber 같은 도구는 문장의 단계마다 이어 줄 코드를 짜 두면 이 문장을 테스트로 실행한다. 형식보다 중요한 것은 구체적인 숫자가 든 예라는 점이다.

    비기능 요구사항도 잴 수 있게 쓴다

    "주문이 빨라야 한다", "장애가 나면 안 된다"는 완료 조건이 될 수 없다. "주문 계산 API의 p99가 300ms 이하"(72번(관측성)), "한 달 가용성 99.9%"(71번(이중화와 무중단 배포))처럼 재는 방법과 숫자를 함께 적어야 다 되었는지 판단할 수 있다. 보안 요구사항도 "로그에 카드 번호를 남기지 않는다"처럼 확인할 수 있는 문장으로 쓴다.

    정리¶

    • 한 줄 요구사항에는 정하지 않은 결정이 숨어 있고, 묻지 않으면 구현한 사람이나 AI가 조용히 정한다. 질문으로 뽑아 답할 사람에게 묻는다.
    • 명세는 완료 조건, 예외 상황, 수용 기준으로 쓴다. 수용 기준은 말이 아니라 구체적인 예이고, 경계와 조합을 짚는 예로 고른다.
    • 수용 기준은 그대로 테스트가 된다. AI가 짠 코드는 명세에서 나온 테스트로 시험한다.
