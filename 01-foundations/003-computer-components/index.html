    3. 컴퓨터 핵심 구성 요소: CPU(ALU·제어장치·레지스터), 버스, 주기억장치, 입출력장치¶

    원리 동작을 예측하고 이상을 알아챌 수 있어야 하는 항목

    2번(소프트웨어 동작의 물리적 본질)에서 본 가져오기 → 해석 → 실행을 여러 부품이 나눠 맡는다. 부품 지도 한 장, 직접 눌러 보는 덧셈기, 입출력을 기다리는 두 방법을 차례로 본다.

    이 항목에서 배우는 것¶

    • 제어장치, ALU, 레지스터, 주기억장치, 버스, 입출력장치가 하는 일을 설명할 수 있다.
    • 8비트 덧셈에서 캐리와 오버플로가 언제 켜지는지 예측하고, 둘을 구분할 수 있다.
    • 입출력을 기다리는 폴링과 인터럽트의 차이를 설명할 수 있다.

    1. 부품은 버스로 이어져 있다¶

    • CPU: 제어장치는 명령어를 해석해 지시하고, ALU는 계산하고, 레지스터(PC, IR, ACC)는 지금 다루는 값을 담는다.
    • 주기억장치(메모리): 실행 중인 프로그램과 데이터를 담는다. 전원이 꺼지면 지워지므로, 프로그램은 SSD에 두었다가 실행할 때 옮겨 온다.
    • 버스: 부품 사이에 주소, 데이터, 제어 신호를 나르는 통로다.

    명령어를 가져오는 일도 메모리 읽기라서, 메모리 접근은 실행한 명령어 수보다 많다. 아래 덧셈 예제는 명령어 5개를 실행하며 메모리에 8번 접근한다(읽기 7번, 쓰기 1번). "한 단계"를 누르면 쓰이는 부품과 버스에 불이 켜진다.

    직접 해 보기토이 CPU‘한 단계’를 눌러 CPU가 명령어를 가져오고, 해석하고, 실행하는 모습을 본다. 메모리 칸도 고칠 수 있다
    새 창에서 크게 열기

    2. ALU는 계산하고 표시를 남긴다¶

    ALU는 결과와 함께 결과의 성질을 나타내는 표시(플래그)를 남기고, 다음 명령어는 이 표시를 보고 건너뛸지 정한다. 네 표시 중 헷갈리기 쉬운 것은 두 넘침이다.

    • C(캐리): 부호 없는 수로 보면 0~255를 넘었다.
    • V(오버플로): 부호 있는 수로 보면 −128~127을 넘었다.
    직접 해 보기8비트 덧셈기와 상태 표시두 수를 바꾸거나 예시를 눌러, 8비트 덧셈의 결과와 캐리·오버플로·0·음수 표시가 어떻게 켜지는지 본다
    새 창에서 크게 열기

    255 + 1은 8비트에 0만 남는다. 부호 없는 수로는 256이라 C가 켜지고, 부호 있는 수로는 −1 + 1 = 0이라 V는 꺼진다. ALU는 비트를 더할 뿐 어느 쪽으로 읽을지 모른다. 그래서 두 넘침을 모두 표시하고, 어느 쪽을 볼지는 프로그램이 정한다(4번(데이터 표현)의 2의 보수).

    예측해 보기. 127 + 1, 200 + 100, 100 + 100, 128 + 128에서 켜지는 표시를 먼저 적은 뒤, 위젯의 예시 버튼으로 확인한다.

    정답과 해설
    계산 결과 켜지는 표시 부호 있는 수로 읽으면
    127 + 1 128 V, N 127 + 1 = 128은 범위 밖이라 −128이 남는다
    200 + 100 44 C −56 + 100 = 44, 범위 안이다
    100 + 100 200 V, N 100 + 100 = 200은 범위 밖이라 −56이 남는다
    128 + 128 0 C, V, Z −128 + (−128) = −256은 범위 밖이라 0이 남는다

    200 + 100은 캐리만 켜진다. 넘침을 모두 "오버플로"라고 뭉뚱그리는 설명이 많은데, 부호 있는 수로는 범위 안이다. 모두 실제 x86-64 CPU에서 확인한 값이다.

    3. 느린 장치는 신호로 알린다¶

    입출력장치는 CPU보다 훨씬 느리고, 언제 일이 생길지 모른다. CPU가 기다리는 방법은 두 가지다.

    • 폴링: CPU가 장치에 "준비됐나?"를 되풀이해 묻는다. 간단하지만 묻는 동안 다른 일을 하지 못한다.
    • 인터럽트: 장치가 준비되면 CPU에 신호를 보낸다. CPU는 하던 명령어를 마치고 PC를 저장한 뒤 처리 코드로 건너뛰었다가, 끝나면 원래 자리로 돌아온다.

    인터럽트도 결국 PC를 바꾸는 일이다. 운영체제가 인터럽트를 다루는 방법은 29번(운영체제의 본질)에서 다룬다.

    예측해 보기¶

    문제 1. 2번(소프트웨어 동작의 물리적 본질)의 카운트다운 예제(명령어 15개를 실행한다)는 메모리를 몇 번 읽고 몇 번 쓰는가? 위 토이 CPU에서 "카운트다운"을 불러와 확인한다.

    정답과 해설

    읽기 19번, 쓰기 0번. 명령어 15개를 가져오는 데 15번, LOAD 13 1번, SUB 14 3번을 읽는다. STORE가 없으니 쓰기는 없다. 계산하는 명령어보다 가져오는 일이 메모리를 더 많이 쓴다.

    문제 2. 다음 중 버스를 쓰지 않는 것을 모두 고른다.

    1. LOAD 13의 가져오기 단계
    2. JMP 1의 실행 단계
    3. STORE 15의 실행 단계
    4. 모든 명령어의 해석 단계
    5. OUT의 실행 단계
    정답과 해설

    2와 4. JMP의 실행은 PC 값만 바꾸고, 해석은 제어장치가 IR을 보는 일이라 둘 다 CPU 안에서 끝난다. 가져오기와 STORE는 메모리를 쓰고, OUT은 입출력장치로 값을 보낸다.

    직접 해보기¶

    실습: 부품과 버스 따라가기

    1. 덧셈 예제에서 STORE 15(2번 칸)를 실행하는 세 단계 동안, 단계마다 쓰이는 부품, 주소 버스와 데이터 버스에 실리는 값, 읽기인지 쓰기인지를 표로 적는다. 토이 CPU의 "한 단계"로 확인한다.
    2. 2번(소프트웨어 동작의 물리적 본질)의 "직접 해보기" 곱셈 프로그램(명령어 34개를 실행한다)이 메모리를 몇 번 읽고 몇 번 쓰는지 계산한다.
    정답

    1. 데이터 버스 값은 16진수다.

      단계 쓰이는 부품 주소 버스 데이터 버스 제어 신호
      가져오기 PC, 메모리, IR 2 2F 읽기
      해석 IR, 제어장치 (쓰지 않음) (쓰지 않음)
      실행 ACC, 메모리 15 0C (12) 쓰기

    2. 읽기 51번, 쓰기 8번. 가져오기 34번, 반복 한 번에 LOAD 15, ADD 13, LOAD 14, SUB 12의 읽기 4번씩 4번 반복해 16번, 마지막 LOAD 15 1번이다. 쓰기는 반복 한 번에 STORE 2번씩 4번이다.

    AI와 함께 확인하기¶

    AI 활용 과제: 엇갈리는 설명을 실험으로 판정하기

    1. AI에게 "8비트 덧셈 255 + 1, 127 + 1, 200 + 100, 100 + 100의 캐리 플래그와 오버플로 플래그"를 묻는다. 새 대화나 다른 AI에게도 물어 답을 비교한다.
    2. 아래 C 프로그램의 출력을 먼저 예측한 뒤 실행해, 엇갈린 답 중 어느 쪽이 맞는지 판정한다.
    3. 틀린 설명이 있으면 실행 결과를 보여 주고, 어디서 잘못 생각했는지 설명하게 한다.
    #include <stdio.h>

/* a + b를 8비트로 더했을 때의 결과와 네 가지 표시 */
void check(int a, int b) {
    int sum = a + b;                         /* 0~510 */
    int r = sum % 256;                       /* 8비트에 남는 값 */
    int sa = a >= 128 ? a - 256 : a;         /* 부호 있는 수로 읽기 */
    int sb = b >= 128 ? b - 256 : b;
    int carry = sum > 255;                   /* 부호 없는 넘침 */
    int overflow = sa + sb < -128 || sa + sb > 127;   /* 부호 있는 넘침 */
    printf("%3d + %3d = %3d  C=%d V=%d Z=%d N=%d\n",
           a, b, r, carry, overflow, r == 0, r >= 128);
}

int main(void) {
    check(255, 1);
    check(127, 1);
    check(200, 100);
    check(100, 100);
    return 0;
}
    실행 결과와 확인할 점 
    255 +   1 =   0  C=1 V=0 Z=1 N=0
127 +   1 = 128  C=0 V=1 Z=0 N=1
200 + 100 =  44  C=1 V=0 Z=0 N=0
100 + 100 = 200  C=0 V=1 Z=0 N=1
    • 이 결과는 실제 x86-64 CPU의 CF, OF, ZF, SF와 같다.
    • 자주 엇갈리는 곳은 200 + 100(캐리만 켜진다)과 127 + 1(부호 있는 수로는 넘친다)이다. 캐리와 오버플로를 "넘침" 하나로 섞어 설명하는지 본다.
    • 이 프로그램은 표시를 정의대로 계산한다. 정의와 실제 CPU가 같다는 것은 이 항목을 쓰면서 확인했다.

    더 알아보기¶

    주소 버스의 폭, 그리고 64비트 CPU

    주소 버스가 n비트면 서로 다른 주소를 \(2^n\)개 만들 수 있다. 메모리는 보통 1바이트마다 주소를 하나씩 붙이므로, 다룰 수 있는 메모리는 \(2^n\)바이트다. 토이 CPU는 주소가 4비트라서 16칸이다.

    주소 비트 수 주소 개수 (바이트) 다른 단위로
    4 16 토이 CPU
    16 65,536 64KiB
    20 1,048,576 1MiB (1978년의 인텔 8086)
    32 4,294,967,296 4GiB
    64 \(2^{64}\) 16EiB

    KiB, GiB, EiB는 1,024배씩 커지는 단위다(1KiB = 1,024바이트, 1GiB = \(2^{30}\)바이트). 32비트 주소로는 4GiB보다 큰 메모리를 한꺼번에 가리킬 수 없다. 실제 64비트 CPU는 \(2^{64}\)바이트를 다 쓰지 않고 그보다 적은 주소만 쓴다(8번(프로세스의 메모리 레이아웃)).

    "64비트 CPU"의 64는 주로 레지스터의 크기, 즉 한 번에 다루는 정수와 주소의 크기다. 큰 메모리와 큰 정수를 다룰 때 유리하지만, "32비트 CPU보다 두 배 빠르다"는 뜻은 아니다. 속도는 클럭, 한 박자에 처리하는 명령어 수, 메모리를 기다리는 시간(5번(메모리 계층 구조)) 같은 여러 요인으로 정해진다.

    실제 CPU는 캐리와 오버플로 중 무엇을 볼지 어떻게 고르나

    C의 a < b를 Visual Studio 2026으로 컴파일하면, 두 수를 빼 보고 표시만 남기는 cmp 명령어는 같고 그 뒤가 다르다. unsigned이면 C를 보는 setb, int이면 V와 N을 보는 setl이 붙는다. 같은 비트, 같은 뺄셈인데 변수의 타입이 어느 표시를 볼지 정한다.

    메모리를 늘리면 빨라질까

    가장 크게 빨라지는 것은 메모리가 모자라 운영체제가 저장 장치를 메모리 대신 쓰고 있을 때다(37번(가상 메모리)). 메모리가 이미 충분하면 대부분의 프로그램은 더 늘려도 빨라지지 않는다. 계산이 느린 프로그램이라면 메모리가 아니라 CPU가 문제다.

    데이터가 많은 장치: DMA

    디스크나 네트워크처럼 옮길 데이터가 많으면, 장치가 CPU를 거치지 않고 메모리에 직접 쓴다(DMA, 직접 메모리 접근). CPU는 그동안 다른 일을 하고, 다 끝나면 장치가 인터럽트로 알린다.

    정리¶

    • CPU(제어장치, ALU, 레지스터), 메모리, 입출력장치는 버스로 이어진다. 명령어를 가져오는 것도 메모리 읽기다.
    • 캐리는 부호 없는 넘침, 오버플로는 부호 있는 넘침이다. 어느 쪽을 볼지는 프로그램이 정한다.
    • 느린 장치는 인터럽트로 알린다. 폴링은 기다리는 동안 CPU를 쓴다.
