    5. 메모리 계층 구조: 속도, 비용, 용량의 트레이드오프¶

    원리 동작을 예측하고 이상을 알아챌 수 있어야 하는 항목

    빠르고, 크고, 싼 메모리는 없다. 그래서 컴퓨터는 작고 빠른 층부터 크고 느린 층까지 겹쳐 쓴다. 이 PC에서 잰 값으로 층의 차이를 보고, 캐시가 줄 단위로 채워지는 모습을 직접 따라가 본다.

    이 항목에서 배우는 것¶

    • 캐시, 메모리, 저장 장치가 속도와 용량에서 얼마나 다른지 설명할 수 있다.
    • 같은 계산이라도 메모리를 읽는 순서에 따라 속도가 달라지는 이유를 캐시 줄로 설명할 수 있다.
    • 적중률로 평균 접근 시간을 계산하고, 적중률의 작은 차이가 성능을 크게 바꾼다는 것을 예측할 수 있다.

    1. 아래층일수록 크고 느리다¶

    • CPU 안의 레지스터 바로 아래에 캐시(L1, L2, L3)가 있고, 그 아래가 메모리, 맨 아래가 SSD나 HDD 같은 저장 장치다. 전원이 꺼져도 남는 것은 저장 장치뿐이다.
    • 아래층일수록 용량은 커지고 시간은 늘어난다. 1ns를 1초로 늘리면 L1은 약 1초, 메모리는 약 1.5분, SSD는 16시간이 넘고, HDD는 두 달이 넘는다.
    • 빠른 메모리를 크게 만들지 않는 이유는 둘이다. 빠른 메모리는 1비트에 드는 부품이 많아 비싸고, 크게 만들면 신호가 멀리 가야 해서 느려진다. 그래서 작은 캐시를 CPU 바로 옆에 둔다.

    2. 캐시는 줄 단위로 가져온다¶

    CPU는 값을 찾을 때 L1부터 보고, 없으면 아래층으로 내려간다. 아래층에서 가져올 때는 값 하나가 아니라 옆 값까지 묶은 캐시 줄(실제 CPU는 64바이트)을 통째로 가져온다. 그래서 방금 읽은 값의 옆을 곧 읽으면(공간 지역성), 한 번 가져온 줄로 여러 번 적중한다.

    C의 2차원 배열은 한 행의 칸들이 메모리에 나란히 놓인다. 아래 위젯에서 같은 배열을 행 순서와 열 순서로 읽어 본다. 보기 쉽게 캐시 줄은 4칸, 캐시는 4줄로 줄였다.

    직접 해 보기캐시 줄과 읽는 순서행 순서나 열 순서를 고르고 ‘한 칸’이나 ‘재생’을 눌러, 캐시가 줄 단위로 채워지고 놓침이 생기는 모습을 본다
    새 창에서 크게 열기

    예측해 보기. 캐시가 4줄일 때, 64칸을 행 순서로 읽으면 놓침은 몇 번일까? 열 순서로 읽으면? 먼저 적은 뒤 위젯의 "끝까지"로 확인한다.

    정답과 해설

    행 순서 16번, 열 순서 64번. 행 순서는 줄 하나를 가져와 4칸을 연달아 쓰므로 줄마다 한 번만 놓친다. 열 순서는 칸마다 다른 줄로 건너뛰고, 그 줄로 돌아오기 전에 다른 줄들에 밀려 캐시에서 나간다. 그래서 모든 칸에서 놓친다.

    실제로도 그렇다. 이 PC에서 64MiB 배열을 두 순서로 읽으면 행 순서는 약 12ms, 열 순서는 약 130~180ms가 걸린다. 계산 횟수는 같은데 열 배 넘게 차이 난다.

    이 PC에서 잰 프로그램 
    #include <stdio.h>
#include <time.h>

#define N 4096
static int a[N][N];   /* 4096 × 4096칸 × 4바이트 = 64MiB */

int main(void) {
    for (int i = 0; i < N; i++)
        for (int j = 0; j < N; j++)
            a[i][j] = i * 3 + j;

    unsigned h1 = 0, h2 = 0;
    clock_t t0 = clock();
    for (int i = 0; i < N; i++)          /* 행 순서: 옆 칸으로 */
        for (int j = 0; j < N; j++)
            h1 = h1 * 31 + a[i][j];
    clock_t t1 = clock();
    for (int j = 0; j < N; j++)          /* 열 순서: 아래 칸으로 */
        for (int i = 0; i < N; i++)
            h2 = h2 * 31 + a[i][j];
    clock_t t2 = clock();

    printf("행 순서 %ld ms, 열 순서 %ld ms\n",
           (long)((t1 - t0) * 1000 / CLOCKS_PER_SEC), (long)((t2 - t1) * 1000 / CLOCKS_PER_SEC));
    printf("(%u %u)\n", h1, h2);          /* 결과를 써야 최적화로 반복이 사라지지 않는다 */
    return 0;
}

    int는 4바이트라서 64바이트 캐시 줄 하나에 16칸이 들어간다. h = h * 31 + 값처럼 더하는 순서에 따라 결과가 달라지는 계산을 쓴 이유는 아래 "AI와 함께 확인하기"에서 다룬다.

    3. 평균 접근 시간은 적중률이 정한다¶

    캐시 하나(1ns)와 메모리(100ns)만 있다고 해 보자. 적중률이 h이면, 언제나 캐시를 먼저 보고(1ns) 못 찾은 비율(1 − h)만큼 메모리까지 간다(100ns).

    평균 접근 시간 = 1 + (1 − h) × 100 (ns)

    적중률이 95%면 1 + 0.05 × 100 = 6ns, 99%면 2ns다. 4%p 차이가 세 배 차이가 된다. 못 찾은 비율에 느린 층의 시간이 곱해지기 때문이다. 아래 계산기에서 층마다 시간과 적중률을 바꿔 본다. 시간은 이 PC에서 잰 값과 비슷한 크기로 두었고, 적중률은 예시 값이다.

    직접 해 보기평균 접근 시간 계산기층마다 걸리는 시간과 적중률을 바꿔 평균 접근 시간이 어떻게 변하는지 본다
    새 창에서 크게 열기

    예측해 보기¶

    문제 1. 캐시(1ns)는 있는데 적중률이 0%라면 평균 접근 시간은 얼마인가? 캐시가 아예 없을 때(언제나 메모리 100ns)와 비교하면 어떤가? 계산기의 "캐시 하나" 예시에서 적중률을 0%로 내려 확인한다.

    정답과 해설

    101ns. 캐시가 아예 없을 때보다 1ns 느리다. 캐시를 찾아보는 1ns는 못 찾아도 든다. 캐시는 지역성이 있어야 이득이다.

    문제 2. 캐시 줄 위젯에서 캐시를 8줄로 늘리면, 열 순서로 읽을 때 놓침은 몇 번이 될까? 예측한 뒤 확인한다.

    정답과 해설

    16번, 행 순서와 같다. 0번 열을 읽으며 가져온 8줄(각 행의 앞 4칸)이 모두 캐시에 남아 있어서, 1~3번 열은 모두 적중한다. 4번 열에서 뒤쪽 8줄을 가져오면 5~7번 열도 적중한다. 열 순서가 느린 것은 같은 줄로 다시 돌아올 때까지 그 줄을 붙잡아 둘 만큼 캐시가 크지 않을 때다. 위젯의 배열은 행이 8개라 8줄이면 충분했다. 2절의 4096 × 4096 배열은 한 열을 내려가는 동안 4,096줄(256KiB)을 거치는데, 이는 L1 캐시(48KiB, 768줄)보다 훨씬 많다.

    직접 해보기¶

    실습: 내 PC의 메모리 계층 재기

    1. 아래 프로그램을 Visual Studio에서 Release로 실행해, 크기별로 값 하나를 읽는 시간을 적는다. 실행에 몇 초 걸린다.
    2. 작업 관리자 → 성능 → CPU에서 내 PC의 L1, L2, L3 캐시 크기를 확인하고, 시간이 크게 뛰는 크기가 캐시 크기와 맞는지 본다. 작업 관리자의 L1, L2는 보통 모든 코어를 더한 크기이므로 코어 수로 나눠 어림한다. L3는 모든 코어가 함께 쓰는 크기 그대로다.
    3. 2절의 행/열 프로그램도 실행해 두 시간의 비를 구하고, 이 PC의 결과(약 12ms 대 130~180ms)와 비교한다.
    #include <stdio.h>
#include <stdlib.h>
#include <windows.h>

/* 64바이트(캐시 줄 하나)짜리 칸. 다음 칸의 주소만 담는다 */
typedef struct cell { struct cell *next; char pad[56]; } cell;

/* bytes 크기의 칸들을 무작위 순서로 한 바퀴 이어 놓고, 따라가며 한 번 읽는 데 걸리는 시간(ns) */
double measure(size_t bytes) {
    size_t n = bytes / sizeof(cell);
    cell *c = malloc(n * sizeof(cell));
    size_t *order = malloc(n * sizeof(size_t));
    for (size_t i = 0; i < n; i++) order[i] = i;
    srand(1);
    for (size_t i = n - 1; i > 0; i--) {             /* 순서 섞기 */
        size_t j = ((size_t)rand() * (RAND_MAX + 1) + rand()) % (i + 1);
        size_t t = order[i]; order[i] = order[j]; order[j] = t;
    }
    for (size_t i = 0; i < n; i++) c[order[i]].next = &c[order[(i + 1) % n]];
    free(order);

    cell *p = &c[0];
    for (size_t i = 0; i < n; i++) p = p->next;      /* 한 바퀴 미리 돌기 */
    size_t steps = 20000000;
    LARGE_INTEGER f, t0, t1;
    QueryPerformanceFrequency(&f);
    QueryPerformanceCounter(&t0);
    for (size_t i = 0; i < steps; i++) p = p->next;
    QueryPerformanceCounter(&t1);
    if (p == NULL) printf("?");                       /* 최적화로 반복이 사라지지 않게 */
    free(c);
    return (double)(t1.QuadPart - t0.QuadPart) * 1e9 / f.QuadPart / steps;
}

int main(void) {
    SetThreadAffinityMask(GetCurrentThread(), 1);    /* 0번 CPU에서만 실행 */
    size_t kib[] = { 16, 256, 1024, 8192, 65536, 262144 };
    for (int i = 0; i < 6; i++)
        printf("%7zu KiB: %6.1f ns\n", kib[i], measure(kib[i] * 1024));
    return 0;
}
    이 PC에서 실행한 결과와 읽는 법
    크기 이 PC (열 번 실행한 범위) 이 크기가 들어가는 층
    16KiB 0.9ns L1 (48KiB)
    256KiB 2.8~3.0ns L2 (2MiB)
    1,024KiB 3.7~6.1ns L2 (2MiB)
    8,192KiB 15~28ns L3 (36MiB)
    65,536KiB 87~93ns 메모리
    262,144KiB 95~99ns 메모리
    • 칸들을 무작위 순서로 이어 놓았기 때문에, 다음 칸을 미리 가져오는 CPU의 기능이 통하지 않는다. 그래서 각 층에서 기다리는 시간이 그대로 드러난다.
    • 0번 CPU에 고정하는 이유는, 이 PC의 CPU처럼 캐시 크기가 서로 다른 코어가 섞인 CPU에서는 실행 도중 코어가 바뀌면 값이 흔들리기 때문이다.
    • 이 측정은 메모리를 기다리는 시간만 재므로 Debug로 실행해도 값이 거의 같다.
    • 같은 PC에서도 실행할 때마다 값이 흔들린다. 특히 L3는 모든 코어가 함께 쓰므로 다른 프로그램의 영향을 받는다. 몇 번 실행해서 범위로 본다.

    AI와 함께 확인하기¶

    AI 활용 과제: AI가 짠 성능 측정 코드 검증하기

    1. AI에게 "C에서 2차원 배열을 행 순서와 열 순서로 읽는 속도를 비교하는 프로그램"을 짜 달라고 한다.
    2. 실행하기 전에 두 시간의 비를 예측해 적는다.
    3. Visual Studio에서 Debug와 Release로 각각 실행한다. 두 빌드의 결과가 크게 다르면, AI에게 묻기 전에 먼저 이유를 추측해 본다.
    4. 측정 코드가 정말 원하는 것을 재고 있는지 아래 "확인할 점"을 기준으로 판정한다.
    확인할 점
    • 이런 비교 코드는 흔히 두 순서로 배열의 합(sum += a[i][j])을 구한다. 이 코드를 이 PC에서 Release로 실행하면 열 순서도 행 순서만큼 빠르게 나왔다(3~4ms). Debug에서는 행 9ms, 열 180ms였다.
    • Release에서 차이가 사라진 것은 캐시가 좋아져서가 아니다. 덧셈은 순서를 바꿔도 결과가 같으므로, 최적화 컴파일러가 열 순서 반복을 옮기고 합쳐서 시간을 재는 두 clock() 사이에 아무 반복도 남기지 않았다. 기계어 목록 파일(/FAs)에서 확인할 수 있다.
    • 측정 코드는 그 자체를 검증해야 한다. 계산 결과를 출력에 쓰기, 순서가 결과에 영향을 주는 계산 쓰기, Debug와 Release 비교하기, 결과가 상식(캐시 줄 크기, 데이터 크기)과 맞는지 따져 보기가 기본이다.
    • 2절의 프로그램이 h = h * 31 + 값을 쓰는 것도 이 때문이다. 이 계산은 순서를 바꾸면 결과가 달라져서, 컴파일러가 반복 순서를 바꿀 수 없다.

    더 알아보기¶

    빠른 메모리가 비싼 이유: SRAM과 DRAM

    캐시에 쓰는 SRAM은 1비트에 트랜지스터 6개 정도가 들고, 주기억장치에 쓰는 DRAM은 트랜지스터 1개와 축전기 1개로 1비트를 담는다. DRAM이 훨씬 촘촘하고 싸지만, 축전기에 담긴 작은 전하를 읽어 내는 데 시간이 걸리고, 전하가 새어 나가므로 주기적으로 다시 채워야 한다.

    크기 자체도 속도를 떨어뜨린다. 메모리가 클수록 원하는 칸까지 신호가 가는 거리가 길어진다. 2번(소프트웨어 동작의 물리적 본질)에서 본 것처럼 3GHz의 한 클럭 동안 빛도 10cm밖에 못 간다.

    그림의 값은 어떻게 쟀나

    캐시와 메모리는 위 "직접 해보기"의 프로그램으로 크기를 바꿔 가며 무작위 순서로 따라 읽는 시간을 쟀다. SSD(C:, NVMe)와 HDD(E:, SATA)는 아래 프로그램으로, 운영체제의 캐시를 거치지 않고 1GiB 파일에서 4KiB씩 무작위로 3,000번 읽은 평균을 쟀다. 값은 열 번 잰 범위다(SSD는 한 번 72.5µs로 크게 벗어나 뺐다). HDD는 파일이 1GiB라 헤드가 디스크의 좁은 범위 안에서만 움직인 값이다. CPU와 메모리, 저장 장치가 다르면 값도 크게 다르다. 정확한 숫자보다 크기의 차이(몇 배, 몇백 배)를 기억하면 된다.

    Visual Studio에서 그냥 실행하면 TEMP 폴더가 있는 드라이브를 재고, 명령줄에서 storage.exe E:\처럼 폴더를 주면 그 드라이브를 잰다. 1GiB 파일을 썼다가 지우므로 빈 공간이 1GiB 넘게 있어야 한다.

    /* 5번 측정: 저장 장치에서 4KiB를 무작위 자리에서 3,000번 읽은 평균 시간
   운영체제의 파일 캐시를 거치지 않고(FILE_FLAG_NO_BUFFERING) 1GiB 파일을 쓴 뒤 읽는다.
   잴 드라이브의 폴더를 인자로 준다(없으면 TEMP 폴더). 파일은 끝나면 지운다 */
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <windows.h>

#define MB (1 << 20)
#define FILE_MB 1024
#define READS 3000

int main(int argc, char **argv) {
    char path[MAX_PATH];
    if (argc > 1) lstrcpynA(path, argv[1], MAX_PATH - 32);
    else GetTempPathA(MAX_PATH, path);
    size_t len = strlen(path);
    if (len > 0 && path[len - 1] != '\\') lstrcatA(path, "\\");
    lstrcatA(path, "storage-test.bin");

    HANDLE h = CreateFileA(path, GENERIC_WRITE, 0, NULL, CREATE_ALWAYS, FILE_FLAG_NO_BUFFERING | FILE_FLAG_WRITE_THROUGH, NULL);
    if (h == INVALID_HANDLE_VALUE) {
        printf("파일을 만들지 못했다: %s\n", path);
        return 1;
    }
    char *buf = VirtualAlloc(NULL, MB, MEM_RESERVE | MEM_COMMIT, PAGE_READWRITE);   /* 페이지 경계에 맞춘 버퍼 */
    srand(GetTickCount());
    for (int k = 0; k < MB; k++)
        buf[k] = (char)rand();
    for (int i = 0; i < FILE_MB; i++) {
        DWORD w;
        buf[0] = (char)i;
        WriteFile(h, buf, MB, &w, NULL);
    }
    CloseHandle(h);

    h = CreateFileA(path, GENERIC_READ, 0, NULL, OPEN_EXISTING, FILE_FLAG_NO_BUFFERING, NULL);
    LONGLONG blocks = (LONGLONG)FILE_MB * MB / 4096;
    LARGE_INTEGER f, t0, t1, at;
    QueryPerformanceFrequency(&f);
    QueryPerformanceCounter(&t0);
    for (int i = 0; i < READS; i++) {
        DWORD r;
        at.QuadPart = (((LONGLONG)rand() << 15 | rand()) % blocks) * 4096;   /* 4KiB 경계의 무작위 자리 */
        SetFilePointerEx(h, at, NULL, FILE_BEGIN);
        ReadFile(h, buf, 4096, &r, NULL);
    }
    QueryPerformanceCounter(&t1);
    CloseHandle(h);
    DeleteFileA(path);
    printf("4KiB 무작위 읽기 %d번 평균 %.1f us\n", READS, (double)(t1.QuadPart - t0.QuadPart) * 1e6 / (double)f.QuadPart / READS);
    return 0;
}
    SSD를 메모리 대신 쓰면

    이 PC에서 SSD에서 4KiB를 읽는 데 약 60µs, 메모리에서 값 하나를 읽는 데 약 0.1µs가 걸렸다. 약 600배다. HDD는 6.1~7.1ms로 SSD보다 다시 100배쯤 느렸다. 메모리가 모자라 운영체제가 SSD를 메모리처럼 쓰기 시작하면 프로그램이 눈에 띄게 느려지는 이유다(37번(가상 메모리)).

    정리¶

    • 메모리는 레지스터, 캐시, 메모리, 저장 장치의 층으로 이루어진다. 아래층일수록 크고 싸지만 느리다.
    • 캐시는 줄 단위로 가져온다. 옆 칸을 차례로 읽으면 적중이 많고, 멀리 건너뛰며 읽으면 놓침이 많아 같은 계산도 느려진다(이 PC의 64MiB 배열은 열 배 넘게).
    • 평균 접근 시간은 적중률의 작은 차이에도 크게 바뀐다.
    • 성능을 재는 코드도 검증해야 한다. 최적화 컴파일러는 측정하려던 일을 옮기거나 없앨 수 있다.
