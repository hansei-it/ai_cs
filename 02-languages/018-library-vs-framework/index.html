    18. 라이브러리와 프레임워크의 차이: 제어의 역전(IoC)¶

    원리 동작을 예측하고 이상을 알아챌 수 있어야 하는 항목

    라이브러리와 프레임워크는 둘 다 남이 만든 코드지만, 쓰는 방식이 반대다. 라이브러리는 내가 필요할 때 부르고, 프레임워크는 내 코드를 언제 부를지 스스로 정한다. 이 차이를 알면 "내 함수는 누가 부르지?", "왜 이 이름으로 만들어야 하지?", "객체를 누가 만들어 넣어 주지?"가 풀린다. 예제는 C#이다.

    이 항목에서 배우는 것¶

    • 라이브러리와 프레임워크를 "누가 누구를 부르는가"로 구분할 수 있다.
    • 제어의 역전이 무엇이고, 프레임워크를 쓰면 코드의 모양이 왜 정해지는지 설명할 수 있다.
    • 프레임워크가 객체를 만들어 넘겨 주는 의존성 주입을 알아볼 수 있다.

    1. 라이브러리는 내가 부르고, 프레임워크는 나를 부른다¶

    • 라이브러리는 내 코드가 부른다. string.Join을 언제 부를지, 무엇을 넘길지 내가 정하고, 일을 마치면 흐름이 내게 돌아온다.
    • 프레임워크는 흐름을 쥐고 있다가 정해진 때에 내 코드를 부른다. 웹 프레임워크는 요청이 올 때마다 내 처리 함수를 부르고, 나는 그 함수가 언제 불릴지 정하지 않는다.
    • 이렇게 흐름의 주인이 바뀌는 것을 제어의 역전(IoC)이라 한다. "전화하지 마세요, 우리가 전화합니다"라는 말로 흔히 설명한다.

    두 예제를 한 단계씩 따라가며 스택에서 누가 누구를 부르는지 본다. 두 번째 예제의 MiniApp은 프레임워크가 하는 일을 15줄짜리 클래스로 흉내 낸 것이다.

    직접 해 보기누가 누구를 부르나라이브러리를 쓰는 코드와 작은 프레임워크에 맡기는 코드를 골라 ‘한 단계’를 눌러, 스택에서 누가 누구를 부르는지 본다
    새 창에서 크게 열기

    2. 흐름을 넘기면 규칙을 따른다¶

    프레임워크가 내 코드를 부르려면 어디에 무엇이 있는지 알아야 한다. 그래서 프레임워크를 쓰면 코드의 모양이 정해진다.

    • 등록: MiniApp의 OnStart, ASP.NET Core의 app.MapGet("/hello", …)처럼 "이럴 때는 이 함수"를 미리 알려 준다.
    • 이름과 주소의 약속: 이 강의 사이트도 MkDocs라는 프레임워크로 만든다. hooks/curriculum.py에 on_nav처럼 MkDocs가 정한 이름으로 함수를 만들어 두면 빌드하는 동안 알맞은 때에 불린다. on_navv처럼 이름을 틀리면 이 PC에서 빌드가 KeyError: 'navv'로 멈췄다(그림 왼쪽).
    • 틀려도 조용한 경우: ASP.NET Core에서 /hello로 등록하고 /helo로 요청하면 404만 돌아오고 처리 함수는 불리지 않았다(그림 오른쪽). 오류 메시지 없이 내 코드가 안 돈다면 등록한 이름과 주소부터 본다.
    • 흐름을 돌려받지 못한다: 위젯의 Run이 끝나야 after Run이 나왔다. 실제 웹 서버의 app.Run()은 끄기 전까지 끝나지 않는다. 그 뒤에 쓴 코드는 서버가 멈출 때까지 실행되지 않는다.

    3. 프레임워크가 객체를 만들어 넘긴다¶

    15번(SOLID 원칙과 디자인 패턴)에서 OrderService는 쓸 객체를 직접 만들지 않고 생성자로 받았고, 만들어 넘기는 일은 Program이 손으로 했다. 이렇게 쓸 객체를 밖에서 만들어 넘겨 주는 것을 의존성 주입(DI)이라 한다. 프레임워크는 이 일까지 맡는다. 무엇을 넘길지 등록만 해 두면, 프레임워크의 DI 컨테이너가 내 함수를 부를 때 필요한 객체를 만들어 넣어 준다.

    var builder = WebApplication.CreateBuilder(args);
builder.Services.AddSingleton<IGreeter, KoreanGreeter>();   // IGreeter가 필요하면 KoreanGreeter를 넘겨라

var app = builder.Build();
app.MapGet("/hello", (IGreeter greeter) => greeter.Greet()); // greeter는 프레임워크가 넣어 준다
app.Run();

interface IGreeter { string Greet(); }
class KoreanGreeter : IGreeter { public string Greet() => "hello from greeter"; }

    이 코드를 ASP.NET Core 웹 앱(dotnet new web)으로 실행하고 /hello에 요청을 보내면 "hello from greeter"가 돌아온다. 처리 함수 어디에도 new KoreanGreeter()가 없다. 시험할 때는 등록만 가짜로 바꾸면 된다.

    예측해 보기¶

    문제 1. 위젯의 두 번째 예제에서 app.Run([...]) 줄을 지우면 무엇이 출력될까?

    정답과 해설

    before Run과 after Run 두 줄만 나온다. OnStart와 OnRequest는 함수를 등록만 할 뿐 부르지 않는다. 흐름을 프레임워크에 넘기는 Run이 없으면 등록한 내 코드는 끝내 불리지 않는다. 프레임워크를 쓰는 코드에서 "함수를 만들었는데 실행이 안 된다"면, 등록했는지, 프레임워크가 그 함수를 부를 조건이 됐는지부터 본다.

    문제 2. 다음을 라이브러리와 프레임워크로 나눈다. 판단 근거는 "누가 누구를 부르는가"다.

    1. JsonSerializer.Serialize(order)로 객체를 JSON 문자열로 바꾼다.
    2. ASP.NET Core가 요청 주소에 맞는 처리 함수를 부른다.
    3. Math.Sqrt(2)로 제곱근을 구한다.
    4. MkDocs가 빌드하는 동안 hooks/curriculum.py의 on_nav를 부른다.
    정답과 해설

    라이브러리: 1, 3. 프레임워크: 2, 4. 1과 3은 내가 필요할 때 부르고 결과를 받아 온다. 2와 4는 프레임워크가 흐름을 쥐고 정해진 때에 내 코드를 부른다. 크기나 이름("Framework"가 붙었는지)이 아니라 누가 흐름을 쥐는지로 가른다.

    직접 해보기¶

    실습: 아주 작은 테스트 프레임워크

    테스트 프레임워크도 제어의 역전이다. 내가 시험 코드를 등록하면 프레임워크가 하나씩 불러 결과를 모은다.

    1. 아래 TestRunner를 실행해 결과를 확인한다.
    2. 시험 하나가 예외를 던져도 나머지 시험이 계속 돌도록 Run을 고친다(try/catch). 예외를 던진 시험은 ERROR로 표시한다.
    3. 내 코드(시험 함수)는 누가 부르는지, Run 안의 어느 줄인지 말로 설명한다.
    var runner = new TestRunner();
runner.Add("1 + 1 == 2", () => 1 + 1 == 2);
runner.Add("empty sum == 0", () => new List<int>().Sum() == 0);
runner.Add("7 / 2 == 3.5", () => 7 / 2 == 3.5);
runner.Run();

class TestRunner
{
    private readonly List<(string Name, Func<bool> Test)> tests = new();
    public void Add(string name, Func<bool> test) => tests.Add((name, test));
    public void Run()
    {
        int passed = 0;
        foreach (var (name, test) in tests)
        {
            bool ok = test();               // 프레임워크가 내 시험 코드를 부른다
            Console.WriteLine($"{(ok ? "PASS" : "FAIL")} {name}");
            if (ok) passed++;
        }
        Console.WriteLine($"{passed}/{tests.Count}");
    }
}
    실행 결과와 확인할 점 
    PASS 1 + 1 == 2
PASS empty sum == 0
FAIL 7 / 2 == 3.5
2/3
    • 세 번째는 정수 나눗셈이라 7 / 2가 3이다(1번(AI 시대 컴퓨터 전공자는 무엇을 배우는가)). 시험이 제 할 일을 했다.
    • 내 시험 함수는 Run 안의 test() 줄에서 프레임워크가 부른다. 실제 테스트 프레임워크(xUnit, NUnit)도 이렇게 내 시험 메서드를 찾아 부르기 때문에 Main을 쓰지 않는다.

    AI와 함께 확인하기¶

    AI 활용 과제: 구분하는 기준 판정하기

    1. AI에게 "라이브러리와 프레임워크의 차이를 예를 들어 설명해 달라"고 한다.
    2. AI가 든 기준을 적는다. 크기, 기능 수, 이름, 회사 같은 기준이 섞여 있는지 본다.
    3. 위젯의 두 예제와 문제 2의 네 가지를 AI의 기준으로 나눠 보고, "누가 누구를 부르는가"로 나눈 결과와 다르면 그 차이를 AI에게 설명하게 한다.
    확인할 점
    • "프레임워크는 크고 라이브러리는 작다"는 기준은 틀리기 쉽다. 15줄짜리 MiniApp도 흐름을 쥐면 프레임워크다.
    • 같은 도구 안에 둘이 섞여 있기도 하다. ASP.NET Core 앱은 프레임워크가 흐름을 쥐지만, 그 앱 안에서 부르는 JsonSerializer(.NET 기본 라이브러리)는 내가 부르는 라이브러리다.
    • 기준을 하나로 정하면 처음 보는 도구도 판단할 수 있다: 그 도구가 내 코드를 부르는가, 내가 그 도구를 부르는가.

    정리¶

    • 라이브러리는 내 코드가 부르고, 프레임워크는 흐름을 쥐고 내 코드를 부른다. 흐름의 주인이 바뀌는 것이 제어의 역전이다.
    • 프레임워크를 쓰면 등록 방법, 함수 이름, 주소 같은 규칙을 따라야 한다. 규칙을 어기면 오류로 멈추기도 하고, 오류 없이 내 코드가 불리지 않기도 한다.
    • 의존성 주입은 쓸 객체를 밖에서 만들어 넘겨 주는 것이다. 프레임워크를 쓰면 무엇을 넘길지 등록만 하고, 만들어 넘기는 일은 프레임워크가 맡는다.
