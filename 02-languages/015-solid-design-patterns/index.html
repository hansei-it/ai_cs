    15. SOLID 원칙과 디자인 패턴: AI 코드의 과잉 설계와 결합도를 판별하는 기준¶

    원리 동작을 예측하고 이상을 알아챌 수 있어야 하는 항목

    설계 원칙과 디자인 패턴은 "나중에 바꾸기 쉬운 코드"를 위한 것이다. AI가 짠 코드는 두 방향으로 어긋나기 쉽다. 하나는 클래스끼리 단단히 묶여 하나를 바꾸면 여럿을 고쳐야 하는 코드, 다른 하나는 바뀔 일이 없는데도 패턴을 겹겹이 쌓은 코드다. 이 항목은 둘을 가르는 기준을 "무엇을 바꿀 때 몇 곳을 고치는가"로 잡는다. 예제는 C#이다.

    이 항목에서 배우는 것¶

    • 결합도를 "무엇을 바꿀 때 몇 곳을 고치는가"로 재고, 두 설계를 비교할 수 있다.
    • SOLID 다섯 원칙이 각각 어떤 문제를 막는지 설명하고, 어긴 신호를 코드에서 찾을 수 있다.
    • 디자인 패턴이 값을 하는 경우와 과잉 설계인 경우를 가릴 수 있다.

    1. 좋은 설계는 바꿀 때 덜 고친다¶

    주문을 저장하고 알림을 보내는 같은 기능을 두 가지로 짰다. 첫 번째는 OrderService가 쓸 객체를 직접 만들고, 두 번째는 약속(인터페이스)만 알고 무엇을 쓸지는 밖에서 넘겨받는다. 클래스마다 파일 하나로 나눴다고 하고, 바꿀 일을 골라 두 설계에서 고칠 파일을 비교해 본다.

    직접 해 보기바꿀 때 고칠 파일바꿀 일을 고르면, 쓸 객체를 직접 만드는 설계와 약속(인터페이스)에 의존하는 설계에서 각각 어느 파일을 고쳐야 하는지 비교해 보여 준다
    새 창에서 크게 열기

    구현을 갈아 끼울 때 두 번째 설계는 주문 처리 코드(OrderService)를 건드리지 않고 객체를 만들어 넘기는 곳만 고친다. 가짜로 시험할 때는 고칠 곳이 없다. 하지만 약속 자체(메서드 이름)를 바꿀 때는 약속을 정의한 파일까지 고쳐야 해서 더 많다. 설계에는 공짜가 없고, 어떤 변화가 자주 일어날지에 맞춰 고른다.

    첫 번째 설계의 코드다.

    class OrderService
{
    private readonly SqlOrderRepository repo = new();   // 쓸 객체를 직접 만든다
    private readonly EmailSender sender = new();
    public void Place(string id, int amount)
    {
        repo.Save(id, amount);
        sender.Send($"order {id}");
    }
}
class SqlOrderRepository
{
    public void Save(string id, int amount) => Console.WriteLine($"db {id} {amount}");
}
class EmailSender
{
    public void Send(string msg) => Console.WriteLine($"mail {msg}");
}

    두 번째 설계의 코드다. 시험할 때는 가짜 저장소를 넘긴다.

    var service = new OrderService(new SqlOrderRepository(), new EmailSender());
service.Place("A-1", 12000);

var fake = new FakeRepository();                          // 시험할 때는 가짜를 넘긴다
var tested = new OrderService(fake, new SilentSender());
tested.Place("T-1", 500);
Console.WriteLine(fake.Saved.Count);

interface IOrderRepository { void Save(string id, int amount); }
interface IMessageSender { void Send(string msg); }

class OrderService(IOrderRepository repo, IMessageSender sender)
{
    public void Place(string id, int amount)
    {
        repo.Save(id, amount);
        sender.Send($"order {id}");
    }
}
class SqlOrderRepository : IOrderRepository
{
    public void Save(string id, int amount) => Console.WriteLine($"db {id} {amount}");
}
class EmailSender : IMessageSender
{
    public void Send(string msg) => Console.WriteLine($"mail {msg}");
}
class FakeRepository : IOrderRepository
{
    public List<string> Saved = new();
    public void Save(string id, int amount) => Saved.Add(id);
}
class SilentSender : IMessageSender
{
    public void Send(string msg) { }
}
    실행 결과 
    db A-1 12000
mail order A-1
1

    2. SOLID: 바꾸기 어렵게 만드는 다섯 가지¶

    다섯 원칙은 모두 "하나를 바꿀 때 다른 것이 깨지거나 함께 고쳐야 하는 일"을 줄이려는 것이다. 1절의 두 번째 설계는 D(의존성 역전)를, 14번(객체 지향 4대 특징과 인터페이스)의 IShape에 새 도형을 더해도 반복문을 고치지 않은 것은 O(개방-폐쇄)를 따른 것이다.

    예측해 보기. 정사각형은 직사각형의 한 종류이니 Square가 Rectangle을 물려받게 했다. 무엇이 출력될까?

    Rectangle r = new Square();
r.Width = 5;
r.Height = 2;
Console.WriteLine(r.Area());

class Rectangle
{
    public virtual int Width { get; set; }
    public virtual int Height { get; set; }
    public int Area() => Width * Height;
}
class Square : Rectangle
{
    public override int Width { get => base.Width; set { base.Width = value; base.Height = value; } }
    public override int Height { get => base.Height; set { base.Width = value; base.Height = value; } }
}
    정답과 해설

    4. Square는 가로와 세로를 늘 같게 맞춘다. 높이를 2로 넣는 순간 가로도 2가 되어 넓이가 4다. Rectangle을 쓰는 코드는 "가로 5, 세로 2면 넓이 10"을 믿는데, 그 자리에 Square가 들어가면 약속이 깨진다. 컴파일도 실행도 오류 없이 지나간다. L(리스코프 치환)을 어긴 대표적인 예다. 수학의 "~의 한 종류"가 코드의 상속과 늘 맞지는 않는다.

    3. 패턴은 이유가 있을 때만¶

    Console.WriteLine(Discount("VIP", 30000));    // 3000
Console.WriteLine(Discount("GOLD", 30000));   // 1500
Console.WriteLine(Discount("NEW", 30000));    // 0

static int Discount(string grade, int price) => grade switch
{
    "VIP" => price * 10 / 100,
    "GOLD" => price * 5 / 100,
    _ => 0,
};
    • 디자인 패턴은 자주 나오는 설계 문제에 붙인 이름 있는 해법이다. 할인 규칙마다 클래스를 두는 전략 패턴, 무엇을 만들지 정하는 일을 맡기는 팩토리 패턴이 그 예다.
    • AI에게 "확장 가능하게" 짜 달라고 하면 위 6줄짜리 함수 대신 인터페이스 2개와 클래스 5개, 33줄짜리 코드가 나오기 쉽다(아래 접힌 코드). 결과는 같다.
    • 패턴이 값을 하는 때는 따로 있다. 규칙마다 계산이 길고, 여러 사람이 따로 규칙을 더하고, 실행 중에 규칙을 바꿔 끼워야 할 때다. 그런 이유가 지금 없으면 짧은 코드가 읽기도, 고치기도 쉽다.
    전략 + 팩토리로 짠 같은 기능 
    var calc = new DiscountCalculator(new DiscountStrategyFactory());
Console.WriteLine(calc.Calculate("VIP", 30000));    // 3000
Console.WriteLine(calc.Calculate("GOLD", 30000));   // 1500
Console.WriteLine(calc.Calculate("NEW", 30000));    // 0

interface IDiscountStrategy
{
    int Apply(int price);
}
class VipDiscount : IDiscountStrategy
{
    public int Apply(int price) => price * 10 / 100;
}
class GoldDiscount : IDiscountStrategy
{
    public int Apply(int price) => price * 5 / 100;
}
class NoDiscount : IDiscountStrategy
{
    public int Apply(int price) => 0;
}
interface IDiscountStrategyFactory
{
    IDiscountStrategy Create(string grade);
}
class DiscountStrategyFactory : IDiscountStrategyFactory
{
    public IDiscountStrategy Create(string grade) => grade switch
    {
        "VIP" => new VipDiscount(),
        "GOLD" => new GoldDiscount(),
        _ => new NoDiscount(),
    };
}
class DiscountCalculator(IDiscountStrategyFactory factory)
{
    public int Calculate(string grade, int price) => factory.Create(grade).Apply(price);
}

    예측해 보기¶

    문제 1. SILVER 등급(3% 할인)을 더한다. 3절의 switch 함수와 접힌 전략·팩토리 코드에서 각각 몇 곳을 고치거나 새로 써야 할까?

    정답과 해설

    switch 함수는 한 곳(갈래 한 줄), 전략·팩토리는 두 곳(새 SilverDiscount 클래스와 팩토리의 갈래 한 줄)이다. 패턴을 쓰면 "기존 클래스는 고치지 않는다"는 장점이 있지만, 이 정도 규칙에서는 팩토리의 switch가 결국 같은 일을 한다. 고칠 곳이 줄지 않았다면 그 패턴은 아직 값을 하지 않는 것이다.

    문제 2. 다음 중 인터페이스를 따로 만들 이유가 분명한 경우를 모두 고른다.

    1. 결제 수단이 카드 하나뿐이고 앞으로도 늘릴 계획이 없다.
    2. 외부 결제 서버를 부르는 코드를, 시험할 때는 실제 결제 없이 돌려야 한다.
    3. 알림을 메일, 문자, 앱 푸시 중 사용자가 고른 것으로 보낸다.
    정답과 해설

    2와 3. 2는 시험할 때 가짜로 바꿔 끼울 자리가 필요하다(1절의 FakeRepository). 3은 실행 중에 구현을 골라야 한다. 1은 구현이 하나뿐이고 바꿀 이유도 없어서, 인터페이스는 파일 수만 늘린다. 이유가 생길 때 만들어도 늦지 않다.

    직접 해보기¶

    실습: 결합도를 낮추고 시험하기

    1. 1절 첫 번째 설계의 OrderService를 두 번째 설계처럼 바꾼다. 인터페이스 두 개를 만들고, 쓸 객체를 생성자로 받는다.
    2. DB와 메일 없이 OrderService.Place를 시험하는 코드를 짠다. 가짜 저장소에 주문이 하나 저장되었는지 확인한다.
    3. 3절의 switch 함수에 SILVER(3%)를 더하고, 30000원에 900이 나오는지 확인한다.
    확인할 점
    • 1, 2의 답은 1절 두 번째 코드와 같다. OrderService 안에 new SqlOrderRepository()가 남아 있으면 아직 묶여 있는 것이다.
    • 3은 "SILVER" => price * 3 / 100, 한 줄이다.

    AI와 함께 확인하기¶

    AI 활용 과제: 과잉 설계 판정하기

    1. AI에게 "회원 등급별 할인을 계산하는 C# 코드를 확장 가능하게 설계해 달라. 등급은 VIP 10%, GOLD 5%, 나머지 0%"라고 한다.
    2. 나온 코드의 클래스·인터페이스 수와 줄 수를 세고, 3절의 switch 함수와 같은 결과를 내는지 같은 입력으로 실행해 본다.
    3. "지금 이 설계가 값을 하는 이유"를 AI에게 묻고, 이 항목의 기준(고칠 곳이 줄어드는가, 구현이 둘 이상인가, 시험할 때 바꿔 끼우는가)으로 판정한다. 과하면 단순하게 줄이게 한다.
    확인할 점
    • 전략, 팩토리, 추상 클래스, 설정 파일까지 나오는 경우가 많다. 등급 세 개를 위한 코드가 수십 줄이면 의심한다.
    • 줄인 코드가 원래 코드와 같은 입력에서 같은 결과를 내는지 실행으로 확인한다. 줄이는 과정에서 경계 값(등급 이름의 대소문자, 0원)이 달라지기 쉽다.
    • 반대로 결제처럼 외부 시스템과 이어진 부분은 인터페이스 하나가 시험을 크게 쉽게 만든다. "패턴은 나쁘다"가 아니라 "이유가 있는가"를 묻는다.

    정리¶

    • 결합도는 "무엇을 바꿀 때 몇 곳을 고치는가"로 잰다. 약속에 의존하면 구현을 갈아 끼우기 쉽고, 약속을 바꾸기는 어려워진다.
    • SOLID는 하나를 바꿀 때 다른 것이 깨지거나 함께 고쳐야 하는 일을 줄이려는 다섯 원칙이다. 상속은 부모의 약속을 지킬 때만 쓴다.
    • 디자인 패턴은 이유가 있을 때 쓴다. 같은 결과를 내는 더 짧은 코드가 있고 고칠 곳이 줄지 않는다면 과잉 설계다.
