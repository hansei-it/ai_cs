    7. 소스코드가 기계어가 되기까지: 전처리, 컴파일, 어셈블, 링킹¶

    원리 동작을 예측하고 이상을 알아챌 수 있어야 하는 항목

    Visual Studio에서 "빌드"를 누르면 한 번에 끝나는 것 같지만, 안에서는 네 단계가 차례로 일어난다. 단계마다 다루는 것이 달라서 나오는 오류도 다르다. 오류가 어느 단계에서 났는지 알면 고칠 곳이 보인다.

    이 항목에서 배우는 것¶

    • 전처리, 컴파일, 어셈블, 링크가 각각 무엇을 받아 무엇을 만드는지 설명할 수 있다.
    • 매크로가 글자 바꾸기라서 생기는 실수를 예측할 수 있다.
    • 빌드 오류 메시지를 보고 어느 단계에서 났는지 가려낼 수 있다.

    1. 빌드는 네 단계다¶

    #include <stdio.h>

int add(int a, int b);   /* 선언만 있다. 정의는 util.c에 */

int main(void) {
    printf("%d\n", add(2, 3));
    return 0;
}

    /* util.c */
int add(int a, int b) {
    return a + b;
}
    1. 전처리: #include, #define처럼 #으로 시작하는 줄을 처리해 글자를 바꾼다. 8줄짜리 main.c가 stdio.h를 펼쳐 넣어 10,763줄이 된다.
    2. 컴파일: C 문법과 타입을 검사하고 기계어 명령으로 바꾼다.
    3. 어셈블: 기계어 바이트와 이름표(기호표)를 담은 오브젝트 파일(.obj)을 만든다. Visual Studio의 컴파일러는 2와 3을 한 번에 해서, 어셈블리는 /FA로 보고 싶을 때만 파일로 남는다.
    4. 링크: 여러 .obj와 라이브러리를 이어 실행 파일 하나로 만든다.

    파일마다 1~3을 따로 하고, 마지막에 링크에서 합친다. 그래서 파일 하나를 고치면 그 파일만 다시 컴파일하고 링크하면 된다.

    2. 전처리는 글자 바꾸기다¶

    전처리기는 C 문법을 모른다. #include는 그 파일의 내용을 그 자리에 붙여 넣고, #define은 이름을 정해 둔 글자로 바꿔 넣는다.

    예측해 보기. 무엇이 출력될까? 먼저 적은 뒤 그림에서 확인한다.

    #define SQUARE(x) x * x
printf("%d\n", SQUARE(1 + 2));
    정답과 해설

    5. 전처리기는 x 자리에 1 + 2라는 글자를 그대로 끼워 넣어 1 + 2 * 1 + 2를 만든다. 곱셈이 먼저라 5다. 매크로를 쓸 때는 인자와 전체를 괄호로 감싼다(((x) * (x))). C에서는 매크로 대신 함수를 쓰면 이런 실수가 없다.

    3. 링크는 이름을 주소로 잇는다¶

    • 컴파일러는 파일 하나만 본다. main.c에서 add를 부르려면 선언(int add(int a, int b);)만 있으면 된다. main.obj에는 "add가 필요하다"는 표시만 남는다.
    • 링커는 모든 .obj와 라이브러리를 모아, 필요한 이름마다 정의를 하나씩 찾아 잇는다. 못 찾으면 LNK2019, 둘 이상이면 LNK2005다.
    • 오류 메시지 앞머리로 단계를 안다. #include할 파일을 못 찾는 C1083은 전처리, C로 시작하는 나머지 번호는 대부분 컴파일, LNK는 링크에서 난다.

    아래 메시지는 Visual Studio 2026이 실제로 낸 것이다. 어느 단계에서 났는지 골라 본다.

    직접 해 보기빌드 오류는 어느 단계에서 났을까Visual Studio가 낸 실제 오류 메시지를 읽고 전처리·컴파일·링크 중 어느 단계에서 났는지 골라, 고칠 곳을 찾는 연습을 한다
    새 창에서 크게 열기

    예측해 보기¶

    문제 1. 1절의 main.c만 cl /c main.c로 컴파일하면 성공할까? 이어서 util.obj 없이 main.obj만 링크하면?

    정답과 해설

    컴파일은 성공하고, 링크에서 LNK2019가 난다. main.c에는 add의 선언이 있으니 컴파일러는 만족한다. 링커는 add의 정의를 어디서도 찾지 못해 "addmain 함수에서 참조되는 확인할 수 없는 외부 기호"를 낸다. 한국어판은 기호 이름(add)과 그것을 부른 함수 이름(main)이 붙어서 나온다.

    문제 2. add 함수의 정의(본문까지)를 util.h에 넣고, main.c와 other.c 두 파일이 모두 #include "util.h"를 했다. 빌드하면 어떻게 될까?

    정답과 해설

    링크에서 LNK2005("add이(가) main.obj에 이미 정의되어 있습니다")가 난다. #include는 글자를 붙여 넣으므로 add의 정의가 main.obj와 other.obj 둘에 들어간다. 두 파일 각각의 컴파일은 문제가 없다. 헤더에는 선언만 두고, 정의는 .c 파일 하나에 둔다.

    직접 해보기¶

    실습: 단계를 하나씩 손으로 실행하기

    1. 1절의 main.c와 util.c를 만든다.
    2. 시작 메뉴의 "x64 Native Tools Command Prompt for VS"(64비트용 명령 프롬프트, 실습 환경 4절)에서 아래를 차례로 실행하고, 단계마다 생긴 파일을 확인한다.
    3. link main.obj처럼 util.obj를 빼고 링크해 오류 메시지를 읽는다.
    cl /P main.c                        전처리만: main.i
find /c /v "" main.i                main.i의 줄 수
cl /c main.c util.c                 컴파일과 어셈블: main.obj, util.obj
dumpbin /symbols main.obj | findstr add
link main.obj util.obj              링크: main.exe
main
    이 PC에서 본 결과
    • main.i는 10,763줄이었다(Windows SDK 버전에 따라 조금 다르다). 맨 아래에 main 함수가 있고, 그 위는 모두 stdio.h와 그 헤더가 다시 불러온 헤더들이다.
    • dumpbin의 add 줄에 UNDEF가 보인다. util.obj를 같은 방법으로 보면 add가 SECT3(코드가 있는 구역)에 정의되어 있다.
    • main을 실행하면 5가 출력된다.

    AI와 함께 확인하기¶

    AI 활용 과제: 링크 오류 해결책 판정하기

    1. main.c만 프로젝트에 있고 util.c가 빠진 상태에서 난 LNK2019 메시지와 main.c 코드를 AI에게 주고 해결 방법을 묻는다.
    2. AI가 제안한 방법을 하나씩 실제로 해 보고, 오류가 사라지는지 확인한다.
    3. 사라지지 않는 제안이 있으면, 그 방법이 어느 단계(전처리, 컴파일, 링크)에 작용하는지 따져 AI에게 설명한다.
    확인할 점
    • "util.h를 #include하라"는 제안이 자주 나온다. 선언은 이미 있으므로 컴파일은 원래 성공했다. 헤더는 전처리와 컴파일을 만족시킬 뿐, 링커에게 정의를 주지 못한다. 오류는 그대로다.
    • "main.c에 add를 다시 정의하라"는 제안은 오류를 없애지만, util.c를 나중에 프로젝트에 넣는 순간 LNK2005가 난다.
    • 맞는 해결은 add를 정의한 util.c를 프로젝트(빌드 대상)에 넣는 것이다. 라이브러리 함수라면 그 .lib를 링크 대상에 넣는다.

    더 알아보기¶

    printf 한 줄인데 실행 파일이 137KB?

    1절의 main.exe는 140,288바이트였다. 명령줄의 cl은 기본으로 C 런타임 라이브러리의 코드를 실행 파일 안에 복사해 넣는다(/MT, libucrt.lib). /MD로 빌드하면 런타임은 Windows에 있는 DLL을 실행할 때 불러 쓰고, 실행 파일에는 연결 정보(ucrt.lib)만 들어가서 같은 프로그램이 9,728바이트가 된다. 앞의 방식을 정적 링크, 뒤의 방식을 동적 링크라 한다. Visual Studio에서 새로 만든 프로젝트는 /MD(Debug는 /MDd)가 기본이다.

    printf는 어디에 정의되어 있나

    dumpbin /symbols main.obj에서 printf는 UNDEF가 아니라 main.obj 안에 정의되어 있다. 요즘의 stdio.h는 printf를 헤더 안의 짧은 함수로 두고, 실제 출력은 라이브러리 함수 __stdio_common_vfprintf에 맡긴다. 그래서 링커가 찾는 이름은 printf가 아니라 이 함수다.

    정리¶

    • 빌드는 전처리 → 컴파일 → 어셈블(파일마다) → 링크(모아서)다.
    • 전처리는 C 문법을 모르는 글자 바꾸기다. 매크로는 괄호로 감싸거나 함수로 바꾼다.
    • 선언은 컴파일러를, 정의는 링커를 만족시킨다. 정의가 없으면 LNK2019, 둘이면 LNK2005다.
    • 오류 번호의 앞머리(C, LNK)가 어느 단계를 볼지 알려 준다.

    관련 항목¶
