    9. 함수 호출과 메모리: 콜 스택, 스택 프레임, 스택 오버플로¶

    직접 AI 없이 직접 할 수 있어야 하는 항목

    함수를 부르면 그 함수가 쓸 칸이 스택에 생기고, 돌아오면 사라진다. 이 단순한 규칙에서 "매개변수를 바꿨는데 왜 그대로지?", "끝난 함수의 변수를 읽으면 왜 이상한 값이 나오지?", "재귀가 왜 갑자기 죽지?"의 답이 모두 나온다. 직접형 항목이므로 스택을 손으로 그릴 수 있을 때까지 연습한다.

    이 항목에서 배우는 것¶

    • 함수를 부르고 돌아올 때 스택 프레임이 쌓이고 걷히는 과정을 손으로 따라갈 수 있다.
    • 매개변수가 복사본이라는 것과, 끝난 함수의 지역 변수를 쓰면 안 되는 이유를 설명할 수 있다.
    • 스택 오버플로가 언제 생기는지 예측하고 피할 수 있다.

    1. 함수를 부를 때마다 프레임이 쌓인다¶

    • 함수를 부르면 스택 프레임이 하나 쌓인다. 프레임에는 돌아갈 곳, 매개변수(넘겨받은 값의 복사본), 지역 변수가 들어간다.
    • 함수가 돌아오면 그 프레임이 걷히고, 돌아갈 곳에 적힌 자리에서 이어서 실행한다. 나중에 쌓인 프레임이 먼저 걷힌다.
    • 재귀 함수는 같은 함수의 프레임이 여러 개 쌓인다. fact(3), fact(2), fact(1)의 n은 이름만 같고 서로 다른 칸이다.

    아래에서 fact(3)을 한 줄씩 실행해 본다. 프레임이 가장 많이 쌓였을 때 몇 개인지, 돌아올 때 값이 어떻게 전해지는지 본다.

    직접 해 보기콜 스택 따라가기예제를 고르고 ‘한 단계’를 눌러, 함수를 부를 때마다 스택에 프레임이 쌓이고 돌아오면 사라지는 모습을 한 줄씩 본다
    새 창에서 크게 열기

    2. 매개변수는 복사본이고, 끝난 프레임은 믿을 수 없다¶

    예측해 보기. 무엇이 출력될까? 먼저 적은 뒤 위젯의 "매개변수는 복사본" 예제로 확인한다.

    #include <stdio.h>

void swap(int a, int b) {
    int t = a;
    a = b;
    b = t;
}

int main(void) {
    int x = 1, y = 2;
    swap(x, y);
    printf("%d %d\n", x, y);
    return 0;
}
    정답과 해설

    1 2. swap의 a, b는 x, y의 값을 복사해 받은 다른 칸이다. swap 안에서는 a와 b가 바뀌지만, 그 프레임은 돌아오면서 걷힌다. 호출한 쪽의 변수를 바꾸려면 값이 아니라 주소를 넘겨야 한다(10번(메모리 참조의 본질)).

    직접 해 보기콜 스택 따라가기예제를 고르고 ‘한 단계’를 눌러, 함수를 부를 때마다 스택에 프레임이 쌓이고 돌아오면 사라지는 모습을 한 줄씩 본다
    새 창에서 크게 열기

    끝난 함수의 지역 변수도 같은 이유로 쓸 수 없다. 프레임이 걷혀도 그 자리의 값은 바로 지워지지 않지만, 다음에 부르는 함수의 프레임이 그 자리를 다시 쓴다. 위젯의 "끝난 함수의 지역 변수" 예제는 지역 변수의 주소를 돌려준 뒤 다른 함수를 부르고 다시 읽는다. 이 PC에서 마지막 줄은 Debug 설정에서 7, Release 설정에서 42가 나왔다. 결과가 정해지지 않은 정의되지 않은 동작이다. Visual Studio는 지역 변수의 주소를 돌려주는 줄에 경고 C4172를 낸다.

    3. 스택은 작다¶

    • Windows 프로그램의 스택은 기본 1MiB다. 프레임이 쌓여 이 크기를 넘으면 스택 오버플로로 프로그램이 멈춘다(종료 코드 0xC00000FD).
    • 멈추는 깊이는 프레임 크기에 따라 다르다. 디버깅을 돕는 여분의 칸이 붙는 Debug 설정이 훨씬 얕다.
    • 큰 배열을 지역 변수로 만들어도 넘친다. 큰 데이터는 힙(11번(힙 메모리 관리))이나 전역에 두고, 깊이를 알 수 없는 재귀는 반복문으로 바꾼다.

    예측해 보기¶

    문제 1. Visual Studio의 Debug 설정으로 실행하면 무엇이 출력되고 어떻게 끝날까? Visual Studio는 이 코드에 어떤 경고를 낼까?

    #include <stdio.h>

int count_down(int n) {
    return count_down(n - 1);
}

int main(void) {
    printf("start\n");
    fflush(stdout);
    printf("%d\n", count_down(10));
    return 0;
}
    정답과 해설

    start. 그다음 count_down이 멈추는 조건 없이 자신을 부르다가 스택이 넘쳐 멈춘다(0xC00000FD). 컴파일러가 미리 알아채고 경고 C4717("'count_down': 모든 제어 경로에서 재귀적입니다. 함수로 인해 런타임 스택 오버플로가 발생합니다.")을 낸다. Release 설정(/O2)에서는 컴파일러가 이 재귀를 반복문으로 바꿔서, 스택이 넘치지 않고 start만 출력한 채 끝없이 돌았다. 경고는 두 설정 모두 나온다. 재귀 함수에는 멈추는 조건이 있어야 하고, 그 조건에 실제로 닿아야 한다.

    문제 2. 2MiB짜리 지역 배열을 만드는 아래 프로그램을 Debug 설정으로 실행하면 start를 출력할까?

    #include <stdio.h>

int main(void) {
    char buf[2 * 1024 * 1024];   /* 2MiB 지역 배열 */
    printf("start\n");
    buf[0] = 1;
    printf("%d\n", buf[0]);
    return 0;
}
    정답과 해설

    아무것도 출력하지 못하고 스택 오버플로(0xC00000FD)로 멈춘다. main의 프레임에 2MiB 배열이 들어가야 하는데 스택은 1MiB다. 프레임을 만드는 순간, 곧 main의 첫 줄을 실행하기도 전에 넘친다. static char buf[...]로 바꾸거나 malloc으로 받으면 된다. 링크 옵션 /STACK:4194304로 스택을 4MiB로 키우면 이 PC에서 start와 1이 출력됐다. Release 설정(/O2)에서는 컴파일러가 거의 쓰지 않는 배열을 없애 버려서 그대로 start와 1이 출력됐다. 같은 코드가 설정에 따라 멈추기도 하고 아니기도 하니, 큰 지역 배열은 Release에서 괜찮았다고 안심하지 않는다.

    직접 해보기¶

    실습: AI 없이, 종이에 스택 그리기

    1. main이 sum(3)을 부른다. 스택이 가장 깊을 때의 모습을 그린다. 프레임마다 함수 이름, n의 값, 돌아갈 곳을 적는다.
    2. 각 sum이 돌려주는 값을 돌아오는 순서대로 적는다.
    3. 아래 두 번째 프로그램의 출력을 순서대로 적는다. 그다음 실행해서 맞춰 본다.
    long long sum(int n) {
    if (n == 0)
        return 0;
    return n + sum(n - 1);
}

    #include <stdio.h>

void c(void) {
    printf("c\n");
}

void b(void) {
    printf("b start\n");
    c();
    printf("b end\n");
}

void a(void) {
    printf("a start\n");
    b();
    printf("a end\n");
}

int main(void) {
    a();
    return 0;
}
    정답
    1. 위에서부터 main, sum(3)(돌아갈 곳: main), sum(2)(돌아갈 곳: sum 4행), sum(1), sum(0). 프레임 5개다.
    2. sum(0)이 0, sum(1)이 1, sum(2)가 3, sum(3)이 6을 돌려준다. 먼저 쌓인 sum(3)이 가장 늦게 돌아온다.

    3. 실행 결과:

      a start
b start
c
b end
a end

    AI와 함께 확인하기¶

    AI 활용 과제: 작은 입력에서만 맞는 재귀

    1. AI에게 "1부터 n까지의 합을 재귀로 구하는 C 함수"를 짜 달라고 한다.
    2. n = 3, 100, 100000으로 실행해 본다. Debug와 Release 둘 다 해 본다.
    3. 멈추는 입력이 있으면 AI에게 결과를 보여 주고, 반복문으로 고치게 한 뒤 다시 실행한다.
    확인할 점
    • 위의 sum처럼 짠 재귀는 n = 3, 100에서는 맞다. 이 PC에서 n = 100000은 Debug와 Release 모두 스택 오버플로로 멈췄다. 프레임 10만 개는 Release의 48바이트 프레임으로도 약 4.6MiB라 1MiB 스택을 넘는다.
    • 작은 입력의 테스트만으로는 이 문제가 드러나지 않는다. 입력의 크기가 재귀의 깊이가 되는 함수는 큰 입력으로 시험한다.
    • 반복문으로 고치면 스택이 늘지 않는다. 1부터 100000까지의 합은 5000050000이라 int가 아니라 long long에 담아야 한다는 것도 확인한다(4번(데이터 표현)).

    더 알아보기¶

    이 항목의 측정값

    끝없이 자신을 부르는 함수를 __try/__except로 감싸 스택 오버플로를 잡고 그때까지의 호출 횟수를 셌다. 프레임 크기는 이웃한 두 호출의 지역 변수 주소 차이다. Visual Studio의 Debug 설정과 같은 옵션(/Od /RTC1 /ZI /JMC)에서 288바이트, 3,580번이었고, Release(/O2)에서 48바이트, 21,464~21,493번이었다. 명령줄 cl의 기본 옵션으로는 64바이트, 16,124번이었다. dumpbin /headers로 보면 실행 파일에 적힌 스택 예약 크기가 0x100000(1MiB)이다.

    x64의 실제 프레임

    이 항목의 그림은 프레임을 단순하게 그렸다. x64 Windows에서는 매개변수 네 개까지를 레지스터로 넘기고, 호출하는 쪽이 그 매개변수를 위한 자리(32바이트)를 미리 마련해 둔다. 돌아갈 곳(주소)은 call 명령어가 스택에 넣는다. 자세한 배치는 Microsoft Learn: x64 호출 규칙에 있다.

    정리¶

    • 함수를 부르면 돌아갈 곳, 매개변수, 지역 변수를 담은 프레임이 스택에 쌓이고, 돌아오면 걷힌다.
    • 매개변수는 복사본이다. 끝난 함수의 지역 변수는 다른 프레임이 덮어쓰므로 주소를 돌려주면 안 된다.
    • 스택은 기본 1MiB다. 끝없는 재귀나 큰 지역 배열은 스택 오버플로(0xC00000FD)로 멈춘다.
