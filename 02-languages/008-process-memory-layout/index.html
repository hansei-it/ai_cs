    8. 프로세스의 메모리 레이아웃(Code, Data, BSS, Heap, Stack)과 주소 공간(32/64비트의 차이)¶

    원리 동작을 예측하고 이상을 알아챌 수 있어야 하는 항목

    프로그램을 실행하면 운영체제가 그 프로그램만의 메모리 공간을 마련해 준다. 실행 중인 프로그램을 프로세스라 한다. 그 안에서 코드와 변수는 성격에 따라 다른 영역에 놓이고, 영역마다 언제까지 있는지와 무엇을 할 수 있는지가 다르다. 이 PC에서 실제로 찍은 주소로 확인한다.

    이 항목에서 배우는 것¶

    • 코드, 전역 데이터(데이터와 BSS), 힙, 스택에 각각 무엇이 놓이고 언제까지 있는지 설명할 수 있다.
    • 변수의 실제 주소를 찍어 보고, 주소가 실행할 때마다 바뀌는 이유를 설명할 수 있다.
    • 32비트와 64비트 프로그램의 포인터 크기와 쓸 수 있는 메모리가 어떻게 다른지 설명할 수 있다.

    1. 메모리는 네 영역으로 나뉜다¶

    • 코드와 전역 데이터는 실행 파일에 들어 있다가 그대로 메모리에 올라온다. 전역 데이터는 초기값이 있는 것(데이터)과 없는 것(BSS)으로 나뉜다. BSS는 "0으로 채울 크기"만 적혀 있어 실행 파일에서 자리를 차지하지 않는다. 이 PC의 실행 파일에서는 둘이 같은 .data 구역에 있었다(문제 1).
    • 힙과 스택은 실행하면서 생긴다. 힙은 프로그램이 요청할 때마다 늘고(11번(힙 메모리 관리)), 스택은 함수를 부를 때마다 쌓였다가 돌아오면 줄어든다(9번(함수 호출과 메모리)).
    • 영역마다 권한이 다르다. 실행할 수 있는 것은 코드 영역뿐이다. 2번(소프트웨어 동작의 물리적 본질)에서 데이터가 명령어로 실행되면 생기는 위험을 봤는데, 운영체제는 데이터를 담는 영역을 "실행 금지"로 표시해 이를 막는다(DEP).

    아래 프로그램은 영역마다 변수를 하나씩 두고 주소를 찍는다.

    #include <stdio.h>
#include <stdlib.h>

int count = 7;   /* 초기값이 있는 전역 변수 */
int total;       /* 초기값이 없는 전역 변수 */

int main(void) {
    int local = 1;                   /* 지역 변수 */
    int *p = malloc(sizeof(int));    /* 동적 할당 */
    printf("main  %p\n", (void *)main);
    printf("count %p\n", (void *)&count);
    printf("total %p\n", (void *)&total);
    printf("heap  %p\n", (void *)p);
    printf("local %p\n", (void *)&local);
    free(p);
    return 0;
}

    2. 실제 주소는 운영체제가 정한다¶

    위 프로그램을 이 PC에서 64비트와 32비트로 빌드해 세 번씩 실행한 결과다. "다시 실행"을 누르며 무엇이 바뀌는지 본다.

    직접 해 보기변수는 메모리 어디에 있을까‘다시 실행’과 32·64비트를 바꿔 가며, 이 PC에서 실제로 찍힌 변수 주소가 어느 영역에 어떤 순서로 놓이는지 본다
    새 창에서 크게 열기
    • 교과서에서 흔히 보는 그림은 코드가 가장 낮은 주소, 스택이 가장 높은 주소에 있다. 이 PC의 64비트 프로그램은 거꾸로, 스택이 가장 낮고 실행 파일(코드, 데이터, BSS)이 가장 높았다. 영역의 종류와 역할은 같지만, 어디에 둘지는 운영체제가 정한다.
    • 다시 실행하면 힙과 스택의 주소가 바뀐다. 운영체제가 일부러 주소를 흩어 놓는 ASLR(주소 공간 배치 무작위화) 때문이다. 공격자가 노릴 주소를 미리 알 수 없게 한다.
    • 코드와 전역 변수의 주소는 세 번 모두 같았다. 실행 파일의 위치도 ASLR로 무작위로 정하지만, Windows는 한 번 정한 위치를 재부팅할 때까지 다시 쓰기 때문이다. 실행 파일을 복사해 이름을 바꾸면 다른 주소에 올라간다.

    3. 64비트는 주소 공간이 넓다¶

    • 64비트 프로그램의 포인터는 8바이트, 32비트 프로그램은 4바이트다.
    • 32비트 프로그램이 쓸 수 있는 주소는 약 2GiB다. 64비트 프로그램은 약 128TiB로, 위젯에서 힙과 실행 파일 사이가 126TiB나 떨어져 있던 것도 이 넓은 공간 덕분이다.
    • 3번(컴퓨터 핵심 구성 요소)에서 "64비트 CPU는 \(2^{64}\)바이트를 다 쓰지 않는다"고 했다. x86-64 CPU는 보통 주소를 48비트까지만 쓰고(256TiB), Windows는 그 아래 절반을 프로그램에 준다.

    예측해 보기¶

    문제 1. 아래 bss1.c와, 배열 줄만 static char big[1000000] = { 1 };로 바꾼 data1.c를 명령줄에서 cl bss1.c, cl data1.c로 컴파일했다. 두 실행 파일의 크기는 얼마나 다를까?

    #include <stdio.h>

static char big[1000000];           /* data1.c에서는 = { 1 } */

int main(void) {
    printf("%d\n", big[0]);         /* 0 */
    return 0;
}
    정답과 해설

    약 1MB 차이다. 이 PC에서 bss1.exe는 140,288바이트, data1.exe는 1,140,224바이트였다. 초기값이 있으면 그 값(첫 바이트 1, 나머지 0)을 실행 파일에 모두 담아야 한다. 초기값이 없으면 BSS라서 "1,000,000바이트를 0으로 채운다"는 정보만 남는다. bss1.exe를 dumpbin /headers로 보면 .data 구역의 메모리 크기(virtual size)는 1MB 가까이인데 파일 속 크기(size of raw data)는 3,072바이트다. big을 한 번도 쓰지 않으면 컴파일러가 배열을 버려서 두 파일의 크기가 같아진다.

    문제 2. 아래 프로그램은 6번(언어의 추상화 계층과 실행 방식)에서 본 덧셈 기계어 8D 04 11 C3을 힙에 복사한 뒤 함수처럼 부른다. 무엇이 출력될까?

    #include <stdio.h>
#include <stdlib.h>
#include <string.h>

typedef int (*func)(int, int);

int main(void) {
    unsigned char code[] = { 0x8D, 0x04, 0x11, 0xC3 };  /* lea eax, [rcx+rdx]; ret */
    void *mem = malloc(sizeof code);                    /* 힙에 자리를 받아 */
    memcpy(mem, code, sizeof code);                     /* 기계어를 복사한다 */
    printf("copied\n");
    fflush(stdout);
    printf("%d\n", ((func)mem)(2, 3));                  /* 그 자리를 함수로 부른다 */
    return 0;
}
    정답과 해설

    copied. 그다음 줄에서 프로그램이 멈춘다(종료 코드 0xC0000005, 접근 위반). 기계어는 맞지만 힙은 실행 금지 영역이라, CPU가 그 자리의 명령어를 가져오려는 순간 운영체제가 막는다. 실행해도 된다고 표시한 메모리를 따로 받으면 5가 나온다(아래 "더 알아보기").

    문제 3. 아래 구조체 하나의 크기는 64비트에서 몇 바이트일까? 32비트로 빌드하면?

    #include <stdio.h>

struct node {
    int value;
    struct node *next;
};

int main(void) {
    printf("%zu %zu\n", sizeof(void *), sizeof(struct node));
    return 0;
}
    정답과 해설

    8 16. 64비트에서 포인터는 8바이트이고, 8바이트 값은 8의 배수 주소에 놓이도록 int(4바이트) 뒤에 4바이트를 비워 둔다. 그래서 4 + 4 + 8 = 16이다. 32비트로 빌드하면 4 8이 나온다. 포인터가 많은 자료구조(연결 리스트, 트리)는 64비트에서 메모리를 거의 두 배 쓴다.

    직접 해보기¶

    실습: 내 PC의 메모리 지도 그리기

    1. 1절의 프로그램을 Visual Studio에서 세 번 실행하고, 주소를 큰 것부터 적는다. 실행마다 바뀌는 것과 그대로인 것을 표시한다.
    2. 도구 모음의 솔루션 플랫폼을 x64에서 x86으로 바꿔 다시 빌드하고 실행한다. 주소의 자릿수와 순서를 x64와 비교한다.
    3. 위 문제 3의 프로그램을 x64와 x86에서 실행해 결과를 확인한다.
    확인할 점
    • x64에서는 주소가 16자리(8바이트), x86에서는 8자리(4바이트)로 찍힌다.
    • 힙과 스택은 실행할 때마다 바뀌고, 코드와 전역 변수는 그대로다. 순서는 위젯에서 본 이 PC의 결과와 다를 수 있다. x86에서는 이 PC에서도 실행할 때마다 스택이 실행 파일보다 아래에 오기도, 위에 오기도 했다.

    AI와 함께 확인하기¶

    AI 활용 과제: 메모리 배치 설명을 실제 주소로 판정하기

    1. AI에게 "C 프로그램에서 코드, 전역 변수, 힙, 스택은 메모리의 어디에, 어떤 순서로 놓이는가"를 묻고 그림으로 그려 달라고 한다.
    2. 1절의 프로그램을 내 PC에서 실행해 찍힌 주소와 AI의 그림을 대조한다.
    3. 다른 점이 있으면 실행 결과를 보여 주고, 왜 다른지 설명하게 한다.
    확인할 점
    • "코드는 낮은 주소, 스택은 높은 주소에서 아래로 자란다"는 리눅스의 전통적인 배치를 그대로 설명하는 답이 많다. 이 PC의 Windows 64비트에서는 스택이 가장 낮은 주소에 있었다.
    • 그 설명 중 "스택은 낮은 주소 쪽으로 자란다"는 Windows에서도 맞다. 함수 안에서 다른 함수를 부르면, 안쪽 함수의 지역 변수가 이 PC에서 64바이트 낮은 주소에 놓였다(명령줄 cl 기본 옵션. Debug 설정은 프레임이 커서 더 멀다).
    • 영역의 종류와 역할은 운영체제와 상관없이 같고, 배치는 운영체제와 설정이 정한다. AI가 특정 운영체제의 배치를 일반 규칙처럼 말하는지 본다.

    더 알아보기¶

    실행해도 되는 메모리를 따로 받으면

    Windows의 VirtualAlloc으로 "읽기·쓰기·실행" 권한(PAGE_EXECUTE_READWRITE)이 붙은 메모리를 받으면, 같은 기계어가 실행되어 5를 돌려준다. 6번(언어의 추상화 계층과 실행 방식)의 JIT 컴파일러가 하는 일이 바로 이것이다. 실행 중에 기계어를 만들어 실행할 수 있는 메모리에 써 넣고 부른다.

    #include <stdio.h>
#include <string.h>
#include <windows.h>

typedef int (*func)(int, int);

int main(void) {
    unsigned char code[] = { 0x8D, 0x04, 0x11, 0xC3 };
    void *mem = VirtualAlloc(NULL, sizeof code, MEM_COMMIT | MEM_RESERVE, PAGE_EXECUTE_READWRITE);
    memcpy(mem, code, sizeof code);
    printf("%d\n", ((func)mem)(2, 3));   /* 5 */
    VirtualFree(mem, 0, MEM_RELEASE);
    return 0;
}
    32비트 프로그램이 4GiB를 쓰려면

    32비트 프로그램을 링크 옵션 /LARGEADDRESSAWARE로 빌드하면, 64비트 Windows에서는 주소를 0xFFFEFFFF까지(약 4GiB) 쓸 수 있다. 이 PC에서 GetSystemInfo로 확인했다. 그래도 4GiB가 한계라서, 큰 메모리를 쓰는 프로그램은 64비트로 만든다.

    정리¶

    • 프로세스의 메모리는 코드, 전역 데이터(실행 파일에서 온다)와 힙, 스택(실행하며 생긴다)의 네 영역으로 나뉜다. 전역 데이터는 초기값이 있는 데이터와 0으로 시작하는 BSS로 다시 나뉜다. 실행할 수 있는 것은 코드뿐이다.
    • 영역의 역할은 같지만 배치는 운영체제가 정한다. 힙과 스택의 주소는 ASLR로 실행마다 바뀐다.
    • 64비트는 포인터가 8바이트이고 프로그램이 쓸 수 있는 주소가 약 128TiB다. 32비트는 4바이트, 약 2GiB다.
