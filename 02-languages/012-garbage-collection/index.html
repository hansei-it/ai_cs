    12. 가비지 컬렉션: 참조 카운팅, Tracing GC(Generational GC), STW¶

    원리 동작을 예측하고 이상을 알아챌 수 있어야 하는 항목

    11번(힙 메모리 관리)에서 C는 받은 메모리를 사람이 직접 돌려줘야 했다. C#, Java, Python 같은 언어는 가비지 컬렉터(GC) 가 더 쓰지 않는 객체를 찾아 대신 돌려준다. 누수와 이중 해제의 상당 부분이 사라지지만, GC가 "더 쓰지 않는다"를 어떻게 판단하는지 모르면 GC가 있어도 메모리가 새고, 프로그램이 잠깐씩 멈추는 이유도 알 수 없다. 이 항목의 예제는 C#(.NET 10)이다.

    이 항목에서 배우는 것¶

    • GC가 어떤 객체를 쓰레기로 판단하는지(루트에서 닿는가) 설명할 수 있다.
    • 참조 카운팅과 추적(마크 앤 스윕) 방식의 차이, 특히 순환 참조에서의 차이를 예측할 수 있다.
    • 세대별 GC가 왜 빠른지, GC가 프로그램을 멈추는(STW) 시간이 무엇에 따라 달라지는지 설명할 수 있다.

    1. 루트에서 닿지 않는 객체가 쓰레기다¶

    • 루트는 호출 스택에 있는 함수들의 지역 변수, static 필드처럼 프로그램이 바로 쓸 수 있는 참조다.
    • 루트에서 참조를 따라가 닿는 객체는 앞으로 쓰일 수 있으니 살려 둔다. 닿지 않는 객체는 프로그램이 다시 쓸 방법이 없으니 쓰레기다.
    • 거꾸로 말하면, 다 쓴 객체라도 루트에서 닿으면 GC는 치우지 않는다. static 목록에 계속 넣기만 하는 캐시가 GC 언어의 대표적인 누수다.

    2. 참조 카운팅과 추적¶

    두 방식이 있다.

    • 참조 카운팅: 객체마다 자신을 가리키는 참조 수를 센다. 0이 되는 순간 바로 치운다. Python(CPython)의 기본 방식이다.
    • 추적: 가끔 멈춰서 루트에서부터 닿는 객체에 표시(마크)하고, 표시가 없는 객체를 한꺼번에 치운다(스윕). 이 가장 단순한 형태를 마크 앤 스윕이라 한다. .NET과 Java도 추적 방식이고, 치운 뒤 살아남은 객체를 한쪽으로 모으는 압축까지 한다.

    아래 위젯에서 b → C 참조를 끊어 C와 D를 루트에서 떼어 낸 뒤, 두 방식을 각각 돌려 본다.

    직접 해 보기GC 실험실화살표를 눌러 참조를 끊은 뒤 ‘참조 카운팅’과 ‘마크 앤 스윕’을 각각 돌려, 어떤 객체가 치워지고 어떤 객체가 남는지 비교한다
    새 창에서 크게 열기

    서로 가리키는 객체는 참조 수가 0이 되지 않아 참조 카운팅만으로는 치울 수 없다. 그래서 Python은 순환을 찾는 수집기를 따로 두고 가끔 돌린다. 이 PC의 Python 3.14에서 그 수집기를 끄면(gc.disable()) 서로 가리키는 두 객체가 지워지지 않았고, gc.collect()를 부르자 지워졌다. 추적 방식인 .NET은 순환도 처음부터 치운다(아래 문제 2).

    3. 세대로 나눠 자주, 짧게 멈춘다¶

    • 추적 GC는 표시하는 동안 객체가 바뀌지 않도록 프로그램을 잠깐 멈춘다. 이것을 STW(Stop-The-World)라 한다. 살아 있는 객체가 많을수록 표시할 것이 많아 오래 멈춘다.
    • 대부분의 객체는 만들어지자마자 버려진다. 그래서 .NET은 객체를 세대로 나누고, 새 객체만 모아 둔 0세대를 자주 수집한다. 0세대는 작아서 빨리 끝난다.
    • 오래 사는 객체가 쌓인 2세대까지 모두 보는 전체 수집은 드물게 하지만, 한 번 하면 오래 걸린다. 게임이나 실시간 서비스가 큰 객체 구조를 오래 들고 있으면 이 멈춤이 끊김으로 보인다. 그래서 .NET은 평소 2세대의 표시를 대부분 프로그램과 함께 돌린다(백그라운드 GC). 그림의 전체 수집 시간은 GC.Collect()로 프로그램을 멈추고 한 번에 수집하게 한 값이다.

    예측해 보기¶

    문제 1. 무엇이 출력될까? GC.GetGeneration은 객체가 몇 세대에 있는지 알려 주고, GC.Collect()는 수집을 바로 한 번 시킨다.

    var obj = new object();
Console.WriteLine(GC.GetGeneration(obj));
GC.Collect();
Console.WriteLine(GC.GetGeneration(obj));
GC.Collect();
Console.WriteLine(GC.GetGeneration(obj));
GC.Collect();
Console.WriteLine(GC.GetGeneration(obj));
    정답과 해설 
    0
1
2
2

    obj는 마지막 줄까지 쓰이니 루트에서 닿는다. 수집에서 살아남을 때마다 한 세대씩 올라가고, 2세대가 마지막이다.

    문제 2. MakeCycle은 서로 가리키는 두 객체를 만들고, 그중 하나를 약한 참조(WeakReference, GC가 치우는 것을 막지 않는 참조)로만 돌려준다. 무엇이 출력될까?

    using System.Runtime.CompilerServices;

WeakReference w = MakeCycle();
GC.Collect();
Console.WriteLine(w.IsAlive);

[MethodImpl(MethodImplOptions.NoInlining)]
static WeakReference MakeCycle()
{
    var a = new Node();
    var b = new Node();
    a.Next = b;
    b.Next = a;    // 서로 가리킨다
    return new WeakReference(a);
}

class Node { public Node? Next; }
    정답과 해설

    False. MakeCycle이 끝나면 a와 b를 가리키는 루트가 없다. 둘은 서로 가리키지만 마크 단계에서 닿지 않으니 치워진다. 참조 카운팅이라면 둘의 참조 수가 1씩 남아 치우지 못한다.

    문제 3. 1MiB 배열 100개를 static 목록에 넣었다. 수집을 시켜도 늘어난 메모리는 몇 MiB일까?

    long before = GC.GetTotalMemory(true);
for (int i = 0; i < 100; i++)
    Cache.Items.Add(new byte[1024 * 1024]);
long after = GC.GetTotalMemory(true);   // true: 재기 전에 수집을 한다
Console.WriteLine((after - before) / (1024 * 1024));

static class Cache
{
    public static List<byte[]> Items = new();
}
    정답과 해설

    100. 배열들은 static 필드(루트)에서 닿으므로 쓰레기가 아니다. GC는 "다시 쓸 일이 없는 것"이 아니라 "닿을 수 없는 것"만 치운다. 다 쓴 항목은 목록에서 빼거나, 개수에 상한을 두는 캐시를 쓴다.

    직접 해보기¶

    실습: 수집 횟수와 멈춤 시간 재기

    1. 아래 "더 알아보기"의 측정 프로그램을 Release로 실행해, 짧게 사는 객체를 1,000만 개 만들 때 0·1·2세대 수집이 각각 몇 번 일어나는지 본다.
    2. 만든 객체를 버리지 않고 목록에 모두 넣도록 바꿔 다시 실행한다. 수집 횟수, 세대, 멈춤 시간이 어떻게 달라지는지 적는다.
    3. 그 결과로 "왜 오래 사는 객체가 많으면 GC가 느려지는가"를 두 문장으로 설명한다.
    확인할 점
    • 이 PC에서 버리는 경우는 0세대 수집 12번, 1·2세대 0번, 멈춤 합계 0.1~0.2ms였다. 수집할 때마다 0세대에 살아 있는 객체가 거의 없어서다.
    • 모두 목록에 넣으면 살아남는 객체가 1세대, 2세대로 옮겨지면서 상위 세대 수집이 생기고 멈춤 시간이 크게 늘어난다. 정확한 숫자는 PC와 .NET 버전에 따라 다르다.
    • 표시(마크)할 객체 수가 멈춤 시간을 정한다. 이 PC에서 살아 있는 객체 500만 개를 두고 GC.Collect()로 전체 수집을 한 번 시키면 약 47~50ms 멈췄다.

    AI와 함께 확인하기¶

    AI 활용 과제: \"GC가 있으니 누수는 없다\" 판정하기

    1. AI에게 "C#은 가비지 컬렉터가 있으니 메모리 누수가 생기지 않는가?"를 묻는다.
    2. AI가 누수가 생기는 예를 들면 그 코드를 실행하고, GC.GetTotalMemory(true)로 메모리가 실제로 줄지 않는지 확인한다.
    3. "생기지 않는다"고 하면 문제 3의 코드를 보여 주고 설명하게 한다.
    확인할 점
    • GC는 닿을 수 없는 객체만 치운다. static 목록, 끝나지 않는 이벤트 구독, 끝없이 커지는 캐시처럼 루트에서 닿는 채로 남겨 둔 객체는 GC가 있어도 샌다.
    • 파일, 네트워크 연결 같은 운영체제 자원은 GC가 언제 돌지 모르니 using(Dispose)으로 바로 닫는다. GC는 메모리를 위한 것이다.
    • AI가 "GC.Collect()를 자주 부르면 해결된다"고 하면 의심한다. 닿을 수 있는 객체는 몇 번을 불러도 치워지지 않고, 전체 수집을 억지로 시키면 멈춤만 늘어난다.

    var p = new Point(i, i);   // 반복 한 번 쓰고 버린다
    sum += p.X;
}
Console.WriteLine($"sum {sum}, {sw.ElapsedMilliseconds} ms");
Console.WriteLine($"gen0 {GC.CollectionCount(0) - g0}, gen1 {GC.CollectionCount(1) - g1}, gen2 {GC.CollectionCount(2) - g2}");
Console.WriteLine($"pause {(GC.GetTotalPauseDuration() - pause0).TotalMilliseconds:F1} ms");

class Point(int x, int y) { public int X = x; public int Y = y; }

    이 PC(Core i9-14900KF)에서 .NET 10 Release로 세 번 실행해 0세대 수집 12번, 멈춤 합계 0.1~0.2ms, 반복 전체 24~25ms였다.

    Python의 참조 카운팅을 눈으로 보기 
    import gc, weakref

class Node:
    pass

gc.disable()           # 순환 수집기를 잠시 끈다
a, b = Node(), Node()
a.next, b.next = b, a  # 서로 가리킨다
w = weakref.ref(a)
del a, b
print(w() is not None) # True: 참조 수가 0이 되지 않아 남는다
gc.collect()
print(w() is not None) # False: 순환 수집기가 지웠다

    정리¶

    • GC는 루트에서 참조를 따라 닿지 않는 객체를 쓰레기로 보고 치운다. 닿는 객체는 다 썼어도 치우지 않는다.
    • 참조 카운팅은 0이 되면 바로 치우지만 순환을 못 치운다. 추적(가장 단순한 형태가 마크 앤 스윕)은 순환도 치우지만 표시하는 동안 멈춘다.
    • 세대별 GC는 새 객체를 자주, 짧게 수집한다. 오래 사는 객체가 많을수록 전체 수집의 멈춤이 길다.
