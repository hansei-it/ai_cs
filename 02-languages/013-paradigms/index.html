    13. 프로그래밍 패러다임: 절차 지향, 객체 지향, 함수형의 문제 해결 관점¶

    원리 동작을 예측하고 이상을 알아챌 수 있어야 하는 항목

    같은 문제도 "어떤 순서로 할까", "누가 맡을까", "데이터를 어떻게 바꿔 갈까" 중 무엇을 먼저 묻느냐에 따라 코드의 모양이 달라진다. 이것을 패러다임이라 한다. 패러다임마다 잘 드러나는 실수와 잘 숨는 실수가 다르다. AI가 코드를 이 모양에서 저 모양으로 바꿔 줄 때 무엇이 함께 바뀌는지도 알아야 한다. 이 항목의 예제는 C#이다.

    이 항목에서 배우는 것¶

    • 절차형, 객체지향, 함수형이 문제를 보는 관점을 구분할 수 있다.
    • 바깥의 값을 바꾸는 코드(부수 효과)와 새 값을 만드는 코드의 차이를 예측할 수 있다.
    • 같은 일을 하는 코드를 다른 패러다임으로 바꿨을 때 동작이 그대로인지 확인할 수 있다.

    1. 같은 문제를 세 관점으로¶

    주문 금액 가운데 10,000원 이상인 것만 더한다. 세 코드 모두 47000을 출력한다.

    int[] amounts = { 12000, 8000, 25000, 9900, 10000 };
int total = 0;
for (int i = 0; i < amounts.Length; i++)    // 절차형: 순서대로, 변수를 바꿔 가며
{
    if (amounts[i] >= 10000)
        total += amounts[i];
}
Console.WriteLine(total);   // 47000

    var book = new OrderBook();                 // 객체지향: 주문 장부가 합계를 맡는다
book.Add(new Order("A", 12000));
book.Add(new Order("B", 8000));
book.Add(new Order("C", 25000));
book.Add(new Order("D", 9900));
book.Add(new Order("E", 10000));
Console.WriteLine(book.TotalOver(10000));   // 47000

record Order(string Id, int Amount);

class OrderBook
{
    private readonly List<Order> orders = new();
    public void Add(Order o) => orders.Add(o);
    public int TotalOver(int min)
    {
        int sum = 0;
        foreach (var o in orders)
            if (o.Amount >= min) sum += o.Amount;
        return sum;
    }
}

    int[] amounts = { 12000, 8000, 25000, 9900, 10000 };
int total = amounts.Where(a => a >= 10000).Sum();   // 함수형: 거르고, 더한다
Console.WriteLine(total);   // 47000

    객체지향 코드의 TotalOver 안은 다시 절차형이다. 패러다임은 언어가 아니라 코드를 짜는 관점이라, 한 프로그램 안에서 섞인다.

    2. 값을 바꾸느냐, 새 값을 만드느냐¶

    절차형은 변수에 값을 거듭 넣어 답을 만든다. 함수형은 이미 있는 값을 바꾸지 않고, 바꾼 결과를 새 값으로 만든다. 아래에서 두 방식을 한 단계씩 비교한다.

    직접 해 보기상태를 바꾸는 코드와 데이터가 흐르는 코드절차형과 함수형을 골라 ‘한 단계’를 눌러, 같은 합계를 변수를 바꿔 가며 구하는 모습과 데이터가 단계를 지나며 구해지는 모습을 비교한다
    새 창에서 크게 열기

    위젯의 total처럼 함수 안에서만 쓰는 변수를 바꾸는 것은 바깥에서 보이지 않는다. 문제는 함수가 돌려주는 값 말고 바깥의 것(받은 목록, 전역 변수, 화면 출력)을 바꿀 때다. 이것을 부수 효과라 하고, 그 값을 함께 쓰는 다른 코드에 영향을 준다.

    예측해 보기. 무엇이 출력될까?

    var prices = new List<int> { 1000, 2000 };
var withTax = AddTax(prices);
Console.WriteLine(prices[0]);

static List<int> AddTax(List<int> list)
{
    for (int i = 0; i < list.Count; i++)
        list[i] = list[i] * 110 / 100;
    return list;
}
    정답과 해설

    1100. List<int>는 참조 타입이라(10번(메모리 참조의 본질)) AddTax가 받은 list는 prices와 같은 목록이다. 함수가 그 목록을 직접 바꾸고 같은 목록을 돌려준다. 호출한 쪽은 원래 가격을 잃는다. prices.Select(p => p * 110 / 100).ToList()처럼 새 목록을 만들면 prices[0]은 1000 그대로다.

    3. 섞어 쓸 때 조심할 곳¶

    • 함수형의 장점은 값이 바뀌지 않아 코드 한 곳만 보고 결과를 알 수 있다는 것이다. 여러 스레드가 함께 읽어도 안전하다(34번(스레드 동기화)).
    • 대신 C#의 LINQ는 지연 실행이다. Where는 거르는 방법을 정해 둘 뿐이고, 결과를 실제로 꺼낼 때(Sum, Count, foreach) 거른다. 그 사이에 원본이 바뀌면 결과도 바뀐다(아래 문제 1).
    • 패러다임을 바꾸면 경계에서의 동작이 바뀔 수 있다. 반복문을 LINQ로 바꾸는 리팩터링은 흔히 AI에게 맡기는 일이지만, 빈 목록 같은 경계 입력에서 결과를 다시 확인해야 한다(아래 "AI와 함께 확인하기").

    예측해 보기¶

    문제 1. 무엇이 출력될까?

    var nums = new List<int> { 1, 2, 3 };
var big = nums.Where(n => n > 1);
nums.Add(4);
Console.WriteLine(big.Count());
    정답과 해설

    3. big은 "1보다 큰 것"이라는 질의일 뿐 결과를 담아 두지 않았다. Count()를 부르는 순간 그때의 nums(1, 2, 3, 4)를 거른다. 그 순간의 결과를 고정하려면 nums.Where(n => n > 1).ToList()로 목록을 만들어 둔다.

    문제 2. 다음 중 함수형(값을 바꾸지 않는 변환)이 특히 잘 맞는 일을 모두 고른다.

    1. 로그 100만 줄에서 오류만 골라 시간대별로 센다.
    2. 게임에서 캐릭터 50개가 서로 부딪히며 체력이 깎인다.
    3. 여러 스레드가 같은 설정 값을 동시에 읽는다.
    정답과 해설

    1과 3. 1은 "거르고, 묶고, 센다"는 데이터 변환이라 파이프라인으로 쓰기 좋다. 3은 값이 바뀌지 않으면 동시에 읽어도 충돌이 없다. 2는 상태(체력)를 가진 것들이 주고받는 일이라 객체로 나누는 편이 자연스럽다. 어느 한 관점이 늘 맞지는 않고, 큰 프로그램은 부분마다 관점을 고른다.

    직접 해보기¶

    실습: 같은 문제를 세 방식으로

    1. 학생 점수 목록에서 60점 이상인 점수의 평균을 구한다. 절차형(for 문), 객체지향(점수를 가진 Student와 평균을 내는 Classroom 객체), 함수형(LINQ) 세 가지로 짠다.
    2. 점수 { 90, 45, 70, 60, 30 }으로 세 코드의 결과가 같은지 확인한다.
    3. 점수가 모두 60점 미만이거나 목록이 비었을 때 세 코드가 각각 어떻게 동작하는지 확인하고, 같은 결과가 나오도록 맞춘다.
    확인할 점
    • 세 코드 모두 (90 + 70 + 60) / 3 = 73.33…을 내야 한다.
    • 60점 이상이 하나도 없으면 LINQ의 Average()는 예외를 던진다. 반복문은 짜는 사람이 정한 대로(0을 돌려주거나 0으로 나누거나) 동작한다. 어느 쪽이 맞는지는 문제의 요구가 정한다.

    AI와 함께 확인하기¶

    AI 활용 과제: 반복문을 LINQ로 바꾼 리팩터링 판정하기

    1. 아래 LoopAverage를 AI에게 주고 "같은 일을 하는 LINQ 한 줄로 바꿔 달라"고 한다.
    2. 원래 코드와 AI의 코드를 빈 목록, 값 하나, 여러 값으로 실행해 결과를 비교한다.
    3. 다른 결과가 나오면 그 입력을 AI에게 보여 주고 원래 동작과 같게 고치게 한다.
    double LoopAverage(List<int> xs)
{
    int sum = 0, count = 0;
    foreach (var x in xs) { sum += x; count++; }
    return count == 0 ? 0 : (double)sum / count;
}

Console.WriteLine(LoopAverage(new List<int> { 10, 20 }));   // 15
    확인할 점

    • AI는 흔히 xs.Average()로 바꾼다. 값이 있으면 같지만, 빈 목록에서 원래 코드는 0을 돌려주고 Average()는 "Sequence contains no elements" 예외를 던진다. 이 PC의 .NET 10에서 아래 코드로 확인했다.

      double LoopAverage(List<int> xs)
{
    int sum = 0, count = 0;
    foreach (var x in xs) { sum += x; count++; }
    return count == 0 ? 0 : (double)sum / count;
}

var empty = new List<int>();
Console.WriteLine(LoopAverage(empty));                 // 0
try
{
    Console.WriteLine(empty.Average());
}
catch (InvalidOperationException e)
{
    Console.WriteLine(e.Message);                      // "Sequence contains no elements"
}
Console.WriteLine(empty.DefaultIfEmpty().Average());   // 0

    • 원래 동작을 지키려면 xs.DefaultIfEmpty().Average()(빈 목록이면 0 하나로 본다)나 xs.Count == 0 ? 0 : xs.Average()로 쓴다.

    • "같은 일을 하는 코드로 바꿨다"는 말은 경계 입력까지 실행해 본 뒤에 믿는다.

    더 알아보기¶

    객체지향은 다음 항목에서

    객체로 묶는 이유(캡슐화)와 객체를 갈아 끼우는 방법(다형성, 인터페이스)은 14번(객체 지향 4대 특징과 인터페이스), 객체를 나누는 기준과 과하게 나눈 설계를 알아보는 법은 15번(SOLID 원칙과 디자인 패턴)에서 다룬다.

    정리¶

    • 절차형은 순서와 변수 변경으로, 객체지향은 데이터와 그 책임을 묶은 객체로, 함수형은 값을 바꾸지 않는 변환의 연결로 문제를 푼다.
    • 받은 목록처럼 바깥의 값을 바꾸는 함수는 그 값을 함께 쓰는 곳에 영향을 준다(부수 효과). 새 값을 만드는 함수는 그렇지 않다.
    • LINQ는 지연 실행이고, 패러다임을 바꾸면 경계 입력에서 동작이 달라질 수 있다. 바꾼 뒤에는 경계 입력으로 확인한다.

    관련 항목¶

    • 10번(메모리 참조의 본질): 참조 타입을 넘기면 같은 객체를 함께 본다
    • 14번(객체 지향 4대 특징과 인터페이스): 객체지향의 네 가지 특징과 인터페이스
    • 15번(SOLID 원칙과 디자인 패턴): 객체를 나누는 원칙과 디자인 패턴
    • 34번(스레드 동기화): 여러 스레드가 같은 값을 바꿀 때 생기는 경쟁 상태
