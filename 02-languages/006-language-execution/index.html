    6. 언어의 추상화 계층과 실행 방식: 기계어·어셈블리부터 네이티브 컴파일, 인터프리터, 가상머신/JIT까지¶

    원리 동작을 예측하고 이상을 알아챌 수 있어야 하는 항목

    CPU가 실행할 수 있는 것은 기계어뿐이다. 사람이 쓴 코드가 기계어가 되는 방법과 때는 언어마다 다르다. 덧셈 함수 하나를 C, Python, C#으로 따라가 보고, 그 차이가 실행 시간을 어떻게 바꾸는지 잰 값으로 본다.

    이 항목에서 배우는 것¶

    • 고급 언어, 어셈블리, 기계어의 관계를 설명할 수 있다.
    • 네이티브 컴파일, 인터프리터, 가상 머신과 JIT가 각각 언제 기계어를 만드는지 구분할 수 있다.
    • 실행 방식에 따라 시작 시간과 반복 계산의 속도가 어떻게 달라지는지 예측할 수 있다.

    1. CPU가 읽는 것은 기계어뿐이다¶

    • 기계어는 CPU가 읽는 숫자다. 2번(소프트웨어 동작의 물리적 본질)의 토이 CPU 명령어처럼, 실제 CPU의 명령어도 숫자다. 8D 04 11은 x86-64 CPU에서 "두 값을 더해 넣는다"는 뜻이다.
    • 어셈블리는 기계어를 사람이 읽을 수 있게 한 줄씩 글자로 옮긴 것이다. CPU 종류마다 다르다.
    • 고급 언어(C, Python, C#)는 CPU 종류와 상관없이 사람이 생각하는 방식으로 쓴다. 한 줄이 기계어 몇 개가 될지는 번역하는 프로그램이 정한다(7번(소스코드가 기계어가 되기까지)).

    위층으로 갈수록 세부를 감추고 사람에게 가까워진다. 이것을 추상화라 한다.

    2. 기계어가 되는 때가 언어마다 다르다¶

    • 네이티브 컴파일 (C): 실행하기 전에 컴파일러가 모두 기계어로 바꿔 실행 파일을 만든다. 실행할 때는 번역이 없다. 대신 그 실행 파일은 만든 CPU와 운영체제에서만 돈다.
    • 인터프리터 (Python): 빌드 단계가 없다. 실행할 때 소스를 바이트코드로 바꾸고, 인터프리터라는 프로그램이 바이트코드를 하나씩 읽어 처리한다. 덧셈 하나에도 "다음 바이트코드가 무엇인지 보고, 해당하는 처리로 건너뛰는" 일이 붙는다.
    • 가상 머신과 JIT (C#): 빌드할 때 CPU와 상관없는 중간 언어(IL)로 바꿔 둔다. 실행할 때 .NET 런타임의 JIT 컴파일러가 IL을 그 PC의 기계어로 바꾼다.

    C#의 Add를 실제로 따라가 보면, JIT는 처음에 최적화 없이 18바이트 기계어를 빨리 만들어 쓴다. 호출이 쌓이자 최적화해 다시 컴파일했고, 그 결과는 C 컴파일러가 만든 8D 04 11 C3과 똑같았다.

    3. 실행 방식이 속도를 바꾼다¶

    0부터 N−1까지 i % 7을 더하는 같은 프로그램을 세 언어로 짜서 시작부터 끝까지 걸린 시간을 쟀다. 반복 횟수와 빌드 시간 포함 여부를 바꿔 보며 어느 쪽이 먼저 끝나는지 본다.

    직접 해 보기반복 횟수와 실행 시간반복 횟수를 고르고 ‘빌드 시간 포함’을 켜고 끄며, C·Python·C# 중 어느 쪽이 먼저 끝나는지 본다
    새 창에서 크게 열기
    • 반복이 길면 반복 한 번의 비용이 차이를 만든다. 1억 번에서 Python은 C의 약 58배가 걸렸다. 바이트코드를 하나씩 해석하는 비용이다. C#은 JIT가 만든 기계어로 돌아 C에 가깝다.
    • 반복이 짧으면 프로그램을 시작하는 시간이 대부분이다. C#은 런타임을 준비하느라 C보다 늦게 시작한다.
    • 빌드까지 포함하면 한 번 돌리고 마는 짧은 일은 빌드가 없는 Python이 유리하다.

    어느 방식이 "빠른 언어"인지는 일의 길이에 따라 다르다. 실행 방식은 속도와 함께 이식성(다른 CPU에서 도는가)과 개발 속도(고치고 바로 돌려 보는가)도 바꾼다.

    예측해 보기¶

    문제 1. 반복이 1만 번이면 Python과 C# 중 어느 쪽이 먼저 끝날까? 빌드 시간은 빼고 생각한다. 예측한 뒤 위젯에서 확인한다.

    정답과 해설

    Python(약 19ms)이 C#(약 35ms)보다 먼저 끝난다. 1만 번은 어느 언어에서도 1ms가 안 걸리는 짧은 일이라, 프로그램을 시작하는 시간이 결과를 정한다. C#은 .NET 런타임을 띄우고 JIT를 준비하는 시간이 Python보다 길다. 100만 번부터는 C#이 앞선다.

    문제 2. C의 loop.exe, C#의 빌드 폴더(bin/Release/net10.0, 안에 Loop.dll이 있다), Python의 loop.py를 리눅스가 깔린 ARM CPU 컴퓨터로 복사했다. 그대로 실행할 수 있는 것은 무엇일까? (그 컴퓨터에는 .NET 런타임과 Python이 깔려 있다.)

    정답과 해설

    C#의 빌드 폴더와 loop.py. loop.exe는 x64 CPU의 기계어이고 Windows 실행 파일 형식이라 ARM 리눅스에서는 그대로 돌지 않는다. 다시 컴파일해야 한다. Loop.dll은 CPU와 상관없는 IL만 담고 있어서(dumpbin /clrheader로 보면 "IL Only"), 그 컴퓨터의 JIT가 ARM 기계어로 바꿔 실행한다(dotnet Loop.dll). 단, Loop.dll 하나만 복사하면 어떤 .NET 런타임으로 돌릴지 적힌 Loop.runtimeconfig.json이 없어 실행이 실패했다(이 PC에서 확인). loop.py는 그 컴퓨터의 Python이 읽어 실행한다.

    문제 3. C#의 Add를 프로그램에서 딱 한 번만 호출하면, CPU가 실행하는 것은 그림의 어느 기계어일까?

    정답과 해설

    최적화하지 않은 처음 기계어(18바이트). JIT는 처음 부를 때 빨리 만드는 쪽을 고른다. 여러 번 불리는 함수만 시간을 들여 최적화해 다시 컴파일한다. 한 번 쓰고 마는 함수까지 최적화하면 컴파일 시간이 아깝기 때문이다. 단, 한 번만 불려도 안에서 오래 도는 반복문은 도는 도중에 최적화한 기계어로 갈아탄다(OSR). 위젯의 C# 반복은 한 번만 불리는 Main 안에 있는데도 이렇게 최적화되어 C에 가깝게 빨랐다.

    직접 해보기¶

    실습: 세 언어의 번역 결과 직접 보기

    1. C: 아래 add 함수를 add.c로 저장하고, 시작 메뉴의 "x64 Native Tools Command Prompt for VS"(64비트용 명령 프롬프트, 실습 환경 4절)에서 cl /c /O2 /FAcs add.c로 컴파일한다. 생긴 add.cod 파일에서 어셈블리와 기계어 바이트를 찾는다.
    2. Python: 같은 함수를 Python으로 쓰고 import dis, dis.dis(add)로 바이트코드를 본다.
    3. C#: 같은 함수를 여러 번 부르는 콘솔 프로그램을 Release로 빌드하고, 환경 변수 DOTNET_JitDisasm을 Add로 정한 뒤 실행해 JIT가 만든 기계어를 본다.
    int add(int a, int b) {
    return a + b;
}
    이 PC에서 본 결과
    1. add.cod에 8d 04 11 lea eax, DWORD PTR [rcx+rdx]와 c3 ret 0이 있다. Debug 설정(/Od)으로 컴파일하면 명령어가 더 많아진다.
    2. Python 3.14에서는 LOAD_FAST_BORROW_LOAD_FAST_BORROW (a, b), BINARY_OP 0 (+), RETURN_VALUE가 나온다. 이름은 Python 버전마다 조금씩 다르다.
    3. (Tier0) 표시가 붙은 18바이트 코드가 먼저 나오고, 호출이 쌓이면 (Tier1) 표시와 함께 lea eax, [rcx+rdx], ret 두 줄(8D0411, C3)이 나온다. 함수를 1,000번씩 부르고 잠깐 쉬기를 몇 번 되풀이했을 때 나왔다. JIT는 다시 컴파일하는 일을 뒤에서 조금 늦게 한다.

    AI와 함께 확인하기¶

    AI 활용 과제: \"컴파일 언어냐, 인터프리터 언어냐\" 판정하기

    1. AI에게 "C, Python, C#을 컴파일 언어와 인터프리터 언어로 나눠 달라"고 한다.
    2. AI의 분류를 이 항목의 실험으로 확인한다. Python은 바이트코드로 바꾸는가? C#은 몇 번 번역되는가?
    3. 둘로 딱 나뉘지 않는 언어가 있으면, 실험 결과를 근거로 AI에게 다시 설명하게 한다.
    확인할 점
    • "Python은 컴파일하지 않는 인터프리터 언어"라는 답이 많다. Python도 실행 전에 소스를 바이트코드로 컴파일한다. 다른 파일에서 import한 모듈은 __pycache__ 폴더에 바이트코드 파일(이름.cpython-314.pyc)로 남는다. 바이트코드를 기계어로 바꾸지 않고 인터프리터가 처리할 뿐이다.
    • C#은 두 번 번역된다. 빌드할 때 IL로, 실행할 때 JIT가 기계어로. "C#은 컴파일 언어"라고만 하면 반쪽 답이다.
    • 컴파일이냐 인터프리터냐는 언어가 아니라 실행 방식(구현)의 성질이다. 같은 언어도 실행 방식이 여럿일 수 있다(아래 "더 알아보기").

    더 알아보기¶

    잰 프로그램과 조건

    이 PC(인텔 Core i9-14900KF, Windows 11)에서 프로그램마다 7번 실행한 중앙값이다(Python 1억 번은 3번). 두 번 되풀이해 재도 거의 같았다. C는 Visual Studio 2026의 cl /O2, Python은 3.14, C#은 .NET 10의 Release 빌드다. 빌드 시간은 소스를 고친 뒤 cl(약 94ms)과 dotnet build(약 0.9초)에 걸린 시간이다.

    #include <stdio.h>
#include <stdlib.h>

int main(int argc, char **argv) {
    int n = argc > 1 ? atoi(argv[1]) : 10000000;   /* 반복 횟수는 실행할 때 받는다 */
    long long sum = 0;
    for (int i = 0; i < n; i++)
        sum += i % 7;
    printf("%lld\n", sum);    /* 29999994: n이 1000만일 때. 결과를 써야 반복이 사라지지 않는다 */
    return 0;
}

    Python은 for i in range(n): s += i % 7, C#은 C와 같은 for 문이다. 반복 횟수를 실행할 때 받는 것도, 결과를 출력하는 것도 컴파일러가 계산을 미리 해 버리거나 없애지 못하게 하기 위해서다(5번(메모리 계층 구조)의 측정 함정).

    Python에도 JIT가, C#에도 미리 컴파일이
    • Python 3.13부터 실험 단계의 JIT가 들어 있다. 이 PC의 Python 3.14에서는 기본으로 꺼져 있고(sys._jit.is_enabled()가 False), 환경 변수 PYTHON_JIT=1로 켜도 위의 1000만 번 반복은 약 0.4초로 거의 같았다.
    • C#도 dotnet publish -r win-x64 -p:PublishAot=true로 실행 전에 기계어로 모두 바꾸는 AOT(Ahead-Of-Time) 컴파일을 할 수 있다. 이 PC에서 "hi"만 출력하는 프로그램의 시작 시간이 약 23ms에서 약 8ms로 줄었다(C는 약 4ms). 위젯의 C# 반복 프로그램은 인자를 읽고 시간을 재는 코드까지 JIT해야 해서, 1번만 반복해도 약 30ms였다. 대신 실행 파일이 그 CPU와 운영체제에 묶인다.
    • Python의 무거운 계산은 흔히 C로 만든 라이브러리(NumPy 등)가 대신한다. 반복을 Python 바이트코드로 돌리지 않고 기계어로 도는 코드에 맡기는 방법이다.

    정리¶

    • CPU는 기계어만 실행한다. 어셈블리는 기계어를 글자로 옮긴 것이고, 고급 언어는 CPU와 상관없이 쓴다.
    • 네이티브 컴파일은 실행 전에, JIT는 실행 중에 기계어를 만든다. 인터프리터는 바이트코드를 기계어로 바꾸지 않고 하나씩 처리한다.
    • 짧은 일은 시작 시간이, 긴 일은 반복 한 번의 비용이 실행 시간을 정한다. 이 PC에서 Python의 반복은 C보다 약 58배 느렸다.
