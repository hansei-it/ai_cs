    16. 타입 시스템(정적/동적): AI가 생성한 코드를 기계적으로 검증하는 첫 번째 안전망¶

    원리 동작을 예측하고 이상을 알아챌 수 있어야 하는 항목

    AI가 짠 코드를 한 줄씩 읽기 전에, 기계가 공짜로 해 주는 검사가 있다. 타입 검사다. 정수를 돌려줘야 할 자리에서 문자열을 돌려주거나, 없을 수도 있는 값을 그대로 쓰는 실수를 사람이 읽기 전에 잡는다. 언어마다 이 검사를 하는 시점이 다르고, 타입이 잡지 못하는 실수도 있다. 이 항목은 C#과 Python을 견줘 그 차이를 본다.

    이 항목에서 배우는 것¶

    • 정적 타입 검사와 동적 타입 검사가 실수를 잡는 시점의 차이를 설명할 수 있다.
    • 같은 실수가 C#, Python, Python의 정적 검사 도구(mypy)에서 각각 언제 어떻게 드러나는지 예측할 수 있다.
    • 타입이 더 많은 실수를 잡도록 코드를 짜고, 타입이 잡지 못하는 실수를 구분할 수 있다.

    1. 정적 타입은 실행 전에, 동적 타입은 그 줄에서¶

    • 정적 타입 언어(C#, Java, C)는 변수와 함수의 타입을 코드에 적고, 컴파일러가 실행 전에 맞는지 검사한다. 맞지 않으면 실행 파일이 만들어지지 않는다.
    • 동적 타입 언어(Python, JavaScript)는 실행하면서 그 값의 타입을 본다. 실수가 있는 줄을 실제로 실행할 때까지 아무 말이 없다.
    • 그래서 동적 타입 언어의 실수는 드물게 실행되는 분기에 숨는다. 테스트가 그 분기를 지나지 않으면 사용자에게 나간 뒤에 드러난다.

    예측해 보기. 섬 지역 배송비를 문자열로 잘못 돌려주는 Python 코드다. 무엇이 출력될까?

    def shipping_fee(total: int, is_island: bool) -> int:
    if is_island:
        return "5000"        # 문자열로 잘못 썼다
    return 0 if total >= 30000 else 3000

print(shipping_fee(40000, False) + 1000)
print(shipping_fee(10000, True) + 1000)
    정답과 해설

    첫 줄은 1000을 출력하고, 둘째 줄에서 TypeError: can only concatenate str (not "int") to str로 멈춘다. 첫 호출은 문제의 분기를 지나지 않아 멀쩡하다. 타입 표시(-> int)를 붙였지만 Python은 실행할 때 이 표시를 검사하지 않는다. 같은 코드를 C#으로 쓰면 return "5000"; 줄이 컴파일 오류 CS0029("암시적으로 'string' 형식을 'int' 형식으로 변환할 수 없습니다.")라서 아예 실행 파일이 만들어지지 않는다.

    2. 같은 실수, 다른 시점¶

    네 가지 실수를 세 방식으로 실제로 빌드하고 실행하고 검사했다. 칸을 눌러 메시지를 본다.

    직접 해 보기실수는 언제 잡히나표의 칸을 눌러, 같은 실수를 C# 컴파일러, Python 실행, Python의 정적 검사(mypy)가 각각 언제 어떤 메시지로 잡는지 본다 (모두 이 PC에서 실행한 결과)
    새 창에서 크게 열기
    • C#은 "없을 수도 있는 값"(string?)을 그대로 쓰면 경고 CS8602만 내고 빌드한다. 경고를 지나치면 실행 중에 NullReferenceException이 난다.
    • Python도 타입 표시를 붙이고 mypy 같은 정적 검사 도구를 돌리면 실행 전에 잡는다. 이 PC에서 mypy 2.4.0은 등급을 문자열로 받을 때 두 실수를, enum으로 받을 때 세 실수를 실행 전에 찾았다.
    • 등급을 문자열로 받으면 "vip" 같은 오타는 어느 도구도 잡지 못한다. 가능한 값을 enum으로 정해 두면 오타가 타입 오류가 된다.
    • 둘 다 int인 가로와 세로의 순서가 바뀐 것은 타입으로는 구별할 수 없다. 이런 실수는 테스트가 잡는다(84번(테스트 설계)).

    3. 타입이 더 많이 잡게 하라¶

    • 경고를 오류로 바꾼다. C# 프로젝트 파일에 <WarningsAsErrors>nullable</WarningsAsErrors>를 넣으면 CS8602가 오류가 되어 빌드가 멈춘다. 이 PC에서 확인했다.
    • 값의 범위를 타입으로 좁힌다. 문자열 대신 enum, 아무 정수 대신 Meter처럼 뜻을 담은 타입을 쓰면 엉뚱한 값을 넣는 실수가 컴파일 오류가 된다.
    • Python은 타입 표시와 검사 도구를 함께 쓴다. 타입 표시가 없는 함수는 mypy가 기본 설정에서 검사하지 않는다. 검사하더라도 무엇을 돌려줘야 하는지 적혀 있지 않으니 문자열을 돌려줘도 틀렸다고 할 근거가 없다(아래 "AI와 함께 확인하기").

    예측해 보기¶

    문제 1. 아래 C# 코드는 빌드될까? 실행하면 어떻게 될까?

    string? name = FindUser(3);
Console.WriteLine(name.Length);

static string? FindUser(int id) => id == 1 ? "kim" : null;
    정답과 해설

    경고 CS8602("null 가능 참조에 대한 역참조입니다.")를 내고 빌드된다. 실행하면 NullReferenceException으로 멈춘다. FindUser(3)은 null을 돌려주고, null의 Length를 읽으려 했다. C#은 string?이라는 표시로 위험을 알려 주지만 경고일 뿐이다. if (name is null)로 먼저 확인하거나, 경고를 오류로 바꿔 빌드를 막는다.

    문제 2. 다음 중 타입 검사(C# 컴파일러나 mypy)로 잡을 수 있는 실수를 모두 고른다.

    1. 금액을 돌려줘야 하는 함수가 한 분기에서 문자열을 돌려준다.
    2. 할인율 10%를 1%로 잘못 계산했다(price * 1 / 100).
    3. enum Grade에 없는 Grade.Silver를 썼다.
    4. Transfer(from, to)를 Transfer(to, from)으로 불렀다. 둘 다 Account다.
    정답과 해설

    1과 3. 1은 돌려주는 값의 타입이, 3은 존재하지 않는 이름이 틀렸다. 2는 타입이 맞는 계산 실수이고, 4는 같은 타입끼리 순서가 바뀐 것이라 타입으로는 구별할 수 없다. 둘은 테스트로 잡는다.

    직접 해보기¶

    실습: 타입이 잡게 만들기

    1. 1절의 Python 코드를 파일로 저장하고 pip install mypy 뒤 mypy 파일이름.py로 검사한다(가상 환경을 켜지 못했을 때는 실습 환경 5절). 오류 메시지가 가리키는 줄을 고치고 다시 검사한다.
    2. 2절 위젯의 "없을 수도 있는 값" C# 코드를 Visual Studio에서 빌드해 경고를 확인한다. 프로젝트 파일에 <WarningsAsErrors>nullable</WarningsAsErrors>를 넣어 다시 빌드한다.
    3. 경고가 사라지도록 name이 null일 때의 처리를 넣는다.
    확인할 점
    • mypy는 Incompatible return value type (got "str", expected "int")를 3번 줄에 보고한다. return 5000으로 고치면 "Success: no issues found"가 나온다.
    • 2에서 같은 CS8602가 경고에서 오류로 바뀌어 빌드가 멈춘다.
    • 3은 예를 들어 Console.WriteLine(name is null ? 0 : name.Length);다. 컴파일러가 null인 경우를 거른 뒤라는 것을 알아 경고가 사라진다.

    AI와 함께 확인하기¶

    AI 활용 과제: 타입 표시 없는 코드와 mypy

    1. AI에게 "주문 총액과 섬 여부를 받아 배송비를 돌려주는 Python 함수"를 타입 표시 없이 짜 달라고 하고, 1절처럼 한 분기에 일부러 문자열을 돌려주도록 고친다.
    2. mypy로 검사해 본다. 이어서 mypy --strict로 검사한다.
    3. AI에게 이 함수에 타입 표시를 붙이게 하고 다시 검사한다. AI가 오류를 없애려고 Any를 쓰지 않았는지 본다.
    확인할 점
    • 타입 표시가 없는 함수는 mypy가 기본 설정에서 검사하지 않고, -> int 같은 표시가 없으니 무엇을 돌려줘야 하는지도 모른다. 이 PC에서 문자열을 돌려주는 분기가 있어도 "Success: no issues found"가 나왔다. "검사를 통과했다"가 "버그가 없다"는 뜻이 아니다.
    • --strict는 "Function is missing a type annotation"으로 타입 표시가 빠진 것부터 알려 준다.
    • AI가 -> Any나 # type: ignore로 경고를 덮으면 검사의 의미가 사라진다. 타입 표시는 실제로 돌려주는 값과 맞아야 한다.

    더 알아보기¶

    JavaScript와 TypeScript

    웹에서 쓰는 JavaScript도 동적 타입이다. TypeScript는 JavaScript에 타입 표시와 정적 검사를 더한 언어로, Python의 타입 표시와 mypy 관계와 비슷하다. 웹 섹션(59번(HTML, CSS, JavaScript))에서 다시 만난다.

    정리¶

    • 정적 타입 검사는 실행 전에, 동적 타입 검사는 그 줄을 실행할 때 실수를 드러낸다. 드문 분기의 실수는 동적 타입에서 숨기 쉽다.
    • C#의 null 경고, Python의 타입 표시와 mypy처럼 검사를 실행 전으로 당기는 도구를 쓰고, 경고를 오류로 다룬다.
    • enum과 뜻을 담은 타입으로 타입이 잡을 수 있는 실수를 늘린다. 같은 타입끼리의 순서, 계산 실수는 타입이 못 잡으므로 테스트로 잡는다.

    관련 항목¶

    • 4번(데이터 표현): 같은 비트도 타입에 따라 다르게 읽힌다
    • 14번(객체 지향 4대 특징과 인터페이스): 변수의 타입이 부를 수 있는 것을 정한다
    • 84번(테스트 설계): 타입이 못 잡는 실수를 잡는 테스트 설계
    • 87번(코드 리뷰와 리팩토링): 정적 분석 도구와 린터
