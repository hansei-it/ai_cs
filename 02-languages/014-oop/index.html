    14. 객체 지향 4대 특징(추상화·캡슐화·상속·다형성)과 인터페이스의 본질¶

    직접 AI 없이 직접 할 수 있어야 하는 항목

    객체지향은 데이터와 그 데이터를 다루는 규칙을 객체로 묶고, 객체끼리 약속(인터페이스)만 보고 일하게 하는 방법이다. 네 가지 특징을 외우는 것보다 "변수의 타입이 부를 수 있는 것을 정하고, 객체의 타입이 실행할 코드를 정한다(인터페이스 멤버와 override한 메서드)"는 한 가지 규칙을 손으로 따라갈 수 있어야 AI가 짠 클래스를 판단할 수 있다. 직접형 항목이고, 예제는 C#이다.

    이 항목에서 배우는 것¶

    • 캡슐화로 객체가 스스로 규칙을 지키게 하는 클래스를 짤 수 있다.
    • 인터페이스로 약속을 정하고, 그 약속을 지키는 클래스를 여럿 만들어 갈아 끼울 수 있다.
    • 변수의 타입과 객체의 타입을 구분해, 어떤 호출이 막히고 어떤 코드가 실행될지 예측할 수 있다.

    1. 객체는 데이터와 규칙을 함께 지킨다¶

    var acc = new Account();
acc.Deposit(1000);
Console.WriteLine(acc.Withdraw(3000));   // False
Console.WriteLine(acc.Balance);          // 1000

class Account
{
    public decimal Balance { get; private set; }   // 밖에서는 읽기만 한다
    public void Deposit(decimal amount)
    {
        if (amount > 0) Balance += amount;
    }
    public bool Withdraw(decimal amount)
    {
        if (amount <= 0 || amount > Balance) return false;   // 규칙을 객체가 지킨다
        Balance -= amount;
        return true;
    }
}
    • 캡슐화: 잔액은 Deposit과 Withdraw를 거쳐서만 바뀐다. 잔액이 음수가 되는 일을 객체가 막으므로, 이 클래스를 쓰는 수백 곳이 저마다 검사할 필요가 없다.
    • 밖에서 acc.Balance = -500;을 쓰면 컴파일 오류 CS0272("set 접근자에 액세스할 수 없으므로 'Account.Balance' 속성 또는 인덱서는 이 컨텍스트에서 사용할 수 없습니다.")가 난다. 규칙을 어기는 코드를 컴파일러가 막아 준다.

    2. 인터페이스는 약속이고, 실행할 코드는 객체가 정한다¶

    List<IShape> shapes = [new Circle(1), new Square(2)];
double total = 0;
foreach (var s in shapes)
    total += s.Area();
Console.WriteLine(total);   // 7.141592653589793

interface IShape { double Area(); }
class Circle(double r) : IShape { public double Area() => Math.PI * r * r; }
class Square(double s) : IShape { public double Area() => s * s; }
    • 추상화: IShape는 "넓이를 구할 수 있다"는 약속만 드러낸다. 반복문은 원인지 정사각형인지 모른다.
    • 다형성: 같은 s.Area()가 원에서는 원의 넓이를, 정사각형에서는 정사각형의 넓이를 구한다. 실행할 코드를 객체의 실제 타입이 정하기 때문이다.
    • 변수의 타입은 반대로 부를 수 있는 것을 정한다. IShape 변수에 원을 넣어도 원에만 있는 멤버(아래 위젯의 Radius)는 부를 수 없다. 컴파일러는 변수의 타입만 보기 때문이다.

    아래에서 변수 타입, 넣을 객체, 부를 멤버를 바꿔 보며 이 두 규칙을 확인한다. 40가지 조합 모두 실제로 컴파일하고 실행한 결과다.

    직접 해 보기변수의 타입과 객체의 타입변수 타입, 넣을 객체, 부를 멤버를 골라, 컴파일러가 막는 경우와 실제로 실행되는 코드를 본다 (모든 조합을 .NET 10으로 컴파일해 얻은 결과)

    3. 상속은 물려받고 고쳐 쓰는 것이다¶

    상속은 부모 클래스의 것을 물려받고, 바꾸고 싶은 메서드만 다시 정의한다. 부모가 virtual로 "바꿔도 된다"고 열어 두고, 자식이 override로 바꾼다.

    예측해 보기. 두 줄에 무엇이 출력될까?

    Animal a = new Dog();
a.Speak();
Animal b = new Cat();
b.Speak();

class Animal
{
    public virtual void Speak() => Console.WriteLine("...");
}
class Dog : Animal
{
    public override void Speak() => Console.WriteLine("멍");
}
class Cat : Animal
{
    public new void Speak() => Console.WriteLine("야옹");
}
    정답과 해설 
    멍
...

    Dog는 override로 Speak를 바꿨으니, Animal 변수로 불러도 객체의 실제 타입인 Dog의 코드가 실행된다. Cat의 new는 "이름만 같은 다른 메서드"를 만든다. Animal 변수로 부르면 Animal의 것이 실행되고, Cat 변수로 불러야 "야옹"이 나온다. override도 new도 쓰지 않으면 경고 CS0114("'Cat.Speak()'은(는) 상속된 'Animal.Speak()' 멤버를 숨깁니다…")가 나오고 new와 같게 동작한다. 경고를 지나치면 다형성이 조용히 깨진다.

    상속은 부모와 자식을 단단히 묶는다. 부모를 고치면 모든 자식이 영향을 받는다. 그래서 "할 수 있는 일"만 나누면 되는 경우는 상속보다 인터페이스를 먼저 생각한다(15번(SOLID 원칙과 디자인 패턴)).

    직접 해보기¶

    실습: AI 없이 클래스와 인터페이스 짜기

    1. 2절의 IShape를 지키는 Triangle(밑변, 높이)을 만들고 목록에 new Triangle(3, 4)를 더한다. 반복문은 고치지 않고 합계를 출력한다.
    2. Account에 다른 계좌로 보내는 bool Transfer(Account to, decimal amount)를 더한다. 보내는 쪽 잔액이 모자라면 두 계좌 모두 그대로여야 한다.
    3. 3절의 Cat이 Animal 변수로 불러도 "야옹"을 내도록 고친다.
    정답

    1. 합계는 13.141592653589793이다. 반복문을 고치지 않고 새 도형을 더한 것이 인터페이스의 쓸모다.

      List<IShape> shapes = [new Circle(1), new Square(2), new Triangle(3, 4)];
double total = 0;
foreach (var s in shapes)
    total += s.Area();
Console.WriteLine(total);   // 13.141592653589793

interface IShape { double Area(); }
class Circle(double r) : IShape { public double Area() => Math.PI * r * r; }
class Square(double s) : IShape { public double Area() => s * s; }
class Triangle(double b, double h) : IShape { public double Area() => b * h / 2; }

    2. 먼저 보내는 쪽에서 빼 보고, 성공했을 때만 받는 쪽에 넣는다.

      var a = new Account();
var b = new Account();
a.Deposit(1000);
Console.WriteLine(a.Transfer(b, 3000));   // False
Console.WriteLine(a.Transfer(b, 400));    // True
Console.WriteLine(a.Balance);             // 600
Console.WriteLine(b.Balance);             // 400

class Account
{
    public decimal Balance { get; private set; }
    public void Deposit(decimal amount)
    {
        if (amount > 0) Balance += amount;
    }
    public bool Withdraw(decimal amount)
    {
        if (amount <= 0 || amount > Balance) return false;
        Balance -= amount;
        return true;
    }
    public bool Transfer(Account to, decimal amount)
    {
        if (!Withdraw(amount)) return false;
        to.Deposit(amount);
        return true;
    }
}

    3. Cat의 new를 override로 바꾼다. 그러면 b.Speak()가 "야옹"을 출력한다.

    AI와 함께 확인하기¶

    AI 활용 과제: AI가 만든 클래스의 캡슐화 점검

    1. AI에게 "은행 계좌 클래스(입금, 출금, 잔액)와, 계좌를 물려받는 적금 계좌 클래스(출금 규칙이 다르다)"를 C#으로 짜 달라고 한다.
    2. 클래스 밖에서 잔액에 음수를 직접 넣는 코드를 써 보고 컴파일되는지 확인한다.
    3. 적금 계좌 객체를 계좌 타입 변수에 넣고 출금을 불러, 적금 계좌의 규칙이 실행되는지 확인한다.
    확인할 점
    • public decimal Balance { get; set; }처럼 setter가 열려 있으면 밖에서 Balance = -500이 컴파일된다. 규칙이 메서드 안에 있어도 우회할 길이 열린 것이다. private set이나 읽기 전용 속성으로 막는다.
    • 자식 클래스의 출금 메서드에 override가 빠지고 경고 CS0114(부모에 virtual이 있을 때)나 CS0108(없을 때)이 났다면, 부모 타입 변수로 부를 때 부모의 규칙이 실행된다. 부모 메서드에 virtual이 있는지, 자식에 override가 있는지 함께 본다.
    • 빌드 경고를 읽는다. 경고 없이 빌드되는지가 AI 코드를 받아들이기 전의 첫 확인이다.

    정리¶

    • 캡슐화는 데이터와 규칙을 함께 숨겨, 규칙을 거쳐서만 상태가 바뀌게 한다.
    • 인터페이스는 "무엇을 할 수 있는가"의 약속이다. 쓰는 코드는 약속만 알고, 구현은 갈아 끼운다.
    • 변수의 타입은 부를 수 있는 것을, 객체의 타입은 실행할 코드를 정한다. 단, 부모의 메서드는 virtual로 열고 override로 바꿔야 다형성이 동작한다.
