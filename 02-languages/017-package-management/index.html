    17. 패키지 생태계와 의존성 관리: 패키지 매니저, 시맨틱 버저닝, 잠금 파일(lock file)¶

    원리 동작을 예측하고 이상을 알아챌 수 있어야 하는 항목

    요즘 프로그램은 대부분 남이 만든 코드(패키지) 위에 선다. 설치 명령 한 줄이 수십 개의 패키지를 끌어오고, 그 패키지들의 버전이 바뀌면 내 코드를 한 글자도 고치지 않아도 동작이 바뀐다. 이 항목은 Python의 패키지 매니저 pip로, 버전 범위를 읽는 법과 "어제와 같은 것"을 다시 설치하는 법을 본다. AI가 추천하는 패키지를 믿어도 되는지는 77번(의존성 공급망 보안)에서 이어서 다룬다.

    이 항목에서 배우는 것¶

    • 패키지 매니저가 의존성을 따라 여러 패키지를 설치한다는 것을 설명할 수 있다.
    • 시맨틱 버저닝과 버전 범위를 읽고, 어떤 버전이 설치될지 예측할 수 있다.
    • 잠금 파일이 왜 필요한지 설명하고, 같은 환경을 다시 만들 수 있다.

    1. 한 줄이 여러 패키지를 끌어온다¶

    • 패키지 매니저(Python의 pip, JavaScript의 npm, .NET의 NuGet)는 패키지를 내려받고, 그 패키지가 필요로 하는 패키지(의존성)까지 따라가 설치한다.
    • 새 가상 환경에서 pip install requests를 하면 requests와 그것이 쓰는 certifi, charset-normalizer, idna, urllib3까지 5개가 깔린다(2026-10-14, requests 2.34.2).
    • 이 강의 사이트도 requirements.txt에 두 줄만 적었는데, 가상 환경에는 pip 자신을 빼고 패키지가 29개 깔려 있다. 내가 쓰는 코드의 대부분은 내가 고른 적 없는 패키지다.

    2. 버전 번호에는 약속이 있다¶

    requirements.txt의 버전 범위는 "어느 버전까지 받아들일지"를 정한다. pip은 범위에 맞는 버전 가운데 가장 높은 것을 설치한다. 아래에서 범위를 바꿔 가며 mkdocs의 실제 배포 버전 가운데 어느 것이 설치될지 본다.

    직접 해 보기버전 범위와 설치될 버전requirements.txt에 쓸 버전 범위를 고르거나 직접 써서, mkdocs의 실제 배포 버전 가운데 어느 것이 맞고 pip이 무엇을 설치할지 본다
    새 창에서 크게 열기
    • ==1.6.1은 그 버전 하나만 받는다. 언제 설치해도 같다.
    • >=1.6은 위쪽이 열려 있다. 지금은 1.6.1이 설치되지만, 2.0.0이 나오는 날부터는 2.0.0이 설치된다. 주 버전이 바뀌면 호환되지 않을 수 있다.
    • >=1.6,<2(~=1.6과 같다)는 "부 버전과 수 버전은 받되 주 버전은 넘지 않는다"는 흔한 절충이다. ~=1.6.0은 더 좁혀 1.6.x만 받는다.
    • 모든 패키지가 이 약속을 따르지는 않는다. 3절의 certifi(2026.7.22)처럼 날짜를 버전으로 쓰는 패키지도 있으니, 범위를 정하기 전에 그 패키지의 버전 규칙을 확인한다.

    이 강의 사이트가 mkdocs==1.6.1로 고정한 데에도 이유가 있다. 사이트를 만드는 테마 쪽에서 MkDocs 2.0이 플러그인을 지원하지 않을 것이라고 알렸고, 이 사이트는 플러그인(훅)으로 목록 표를 만든다.

    3. 같은 것을 다시 깔려면 잠금 파일¶

    • 범위만 적어 두면 설치하는 날마다 다른 조합이 깔릴 수 있다. 1절 그림의 27개는 버전을 적지 않았으니 특히 그렇다. "내 PC에서는 되는데"의 흔한 원인이다.
    • 잠금 파일은 실제로 깔린 모든 패키지의 정확한 버전을 적어 둔 목록이다. pip에서는 pip freeze의 출력이 그 역할을 한다. 다른 PC에서 pip install -r로 그 목록을 설치하면 같은 조합이 깔린다.
    • npm은 package-lock.json을 자동으로 만들고, .NET은 설정하면 packages.lock.json을 만든다. 잠금 파일은 저장소에 함께 커밋한다.
    > pip freeze
certifi==2026.7.22
charset-normalizer==3.5.2
idna==3.20
requests==2.34.2
urllib3==2.8.0

    예측해 보기¶

    문제 1. requirements.txt에 mkdocs>=3이라고 쓰고 pip install -r requirements.txt를 하면 어떻게 될까? 위젯에 >=3을 써 넣고 확인한다.

    정답과 해설

    설치하지 못하고 멈춘다. 3 이상의 mkdocs는 없다. 이 PC에서 pip은 "ERROR: Could not find a version that satisfies the requirement mkdocs>=3 (from versions: …)"와 "ERROR: No matching distribution found for mkdocs>=3"를 냈다. AI가 존재하지 않는 버전이나 패키지를 적어 줄 때도 같은 오류가 난다.

    문제 2. 두 사람이 같은 requirements.txt(requests>=2.31)로 한 사람은 2024년에, 다른 사람은 오늘 설치했다. 두 사람이 받은 requests는 같을까? 같게 하려면 무엇을 저장소에 넣어야 할까?

    정답과 해설

    다를 수 있다. >=2.31은 위쪽이 열려 있어 그날의 최신 버전을 받는다(3.0이 나오면 3.0). 오늘(2026-10-14) 설치하면 2.34.2다. requests가 끌어오는 urllib3 같은 패키지도 날마다 달라질 수 있다. 처음 설치한 사람이 pip freeze로 만든 목록(잠금 파일)을 저장소에 넣고, 다른 사람이 그 목록으로 설치하면 같아진다.

    직접 해보기¶

    실습: 환경을 만들고 똑같이 다시 만들기

    1. 빈 폴더에서 python -m venv venv로 가상 환경을 만들고 켠 뒤(venv\Scripts\activate), pip install requests를 한다. PowerShell의 실행 정책 때문에 켜기가 막히면, 켜지 않고 venv\Scripts\python -m pip install requests처럼 가상 환경의 Python을 직접 불러도 된다(실습 환경 5절).
    2. pip list로 깔린 패키지 수를 세고, pip show requests의 Requires 줄과 비교한다.
    3. pip freeze > requirements.lock으로 잠금 파일을 만든다. 다른 폴더에 새 가상 환경을 만들어 pip install -r requirements.lock을 하고, 두 환경의 pip freeze 출력이 같은지 비교한다.
    확인할 점
    • 2026-10-14 기준으로 pip 자신을 빼고 5개가 깔렸고, Requires: certifi, charset_normalizer, idna, urllib3였다. 설치하는 날에 따라 버전 숫자는 다를 수 있다.
    • 잠금 파일로 설치한 두 환경의 pip freeze 출력은 줄마다 같아야 한다.

    AI와 함께 확인하기¶

    AI 활용 과제: AI가 추천한 패키지 확인하기

    1. AI에게 "Python으로 엑셀 파일을 읽는 패키지와 설치 명령"을 묻는다.
    2. 추천한 패키지가 실제로 있는지, 적어 준 버전이 있는지 pip index versions 패키지이름으로 확인한다. 설치하지 않고 버전 목록만 본다.
    3. 패키지 페이지(pypi.org)에서 마지막 배포 날짜, 라이선스, 저장소 주소를 확인하고, AI의 설명과 다른 점을 적는다.
    확인할 점
    • AI는 그럴듯한 이름의 없는 패키지나 없는 버전을 적기도 한다. 없는 이름을 누군가 먼저 등록해 악성 코드를 넣어 두는 공격도 있으므로, 설치하기 전에 존재와 출처부터 확인한다(77번(의존성 공급망 보안)).
    • 오래전에 멈춘 패키지, 라이선스가 맞지 않는 패키지는 존재해도 쓰지 않는 편이 낫다.
    • 버전을 적어 준다면 그 버전이 실제 목록에 있는지, 범위가 주 버전을 넘지 않는지 본다.

    더 알아보기¶

    가상 환경을 쓰는 이유

    가상 환경 없이 pip install을 하면 PC 전체에서 쓰는 Python에 패키지가 깔린다. 프로젝트마다 필요한 버전이 다르면 서로 부딪힌다. 가상 환경은 프로젝트 폴더마다 따로 패키지를 둔다. 이 강의 사이트도 .venv 폴더의 가상 환경에서 빌드한다.

    정리¶

    • 패키지 매니저는 의존성을 따라 여러 패키지를 설치한다. 내가 적은 몇 줄이 수십 개를 끌어온다.
    • 시맨틱 버저닝의 주.부.수 버전은 호환에 대한 약속이다(따르지 않는 패키지도 있다). 버전 범위는 위쪽을 막아 주 버전을 넘지 않게 적는다.
    • 같은 환경을 다시 만들려면 모든 패키지의 정확한 버전을 적은 잠금 파일을 저장소에 넣는다.

    관련 항목¶

    • 7번(소스코드가 기계어가 되기까지): 다른 사람이 만든 라이브러리를 링크하는 일
    • 18번(라이브러리와 프레임워크의 차이): 가져다 쓰는 코드가 라이브러리인지 프레임워크인지
    • 77번(의존성 공급망 보안): AI가 추천한 패키지의 실재, 유지보수, 라이선스 확인
