    92. 배포 플랫폼: 컨테이너 오케스트레이션(쿠버네티스)과 서버리스¶

    위임 AI에 맡기고 실행·테스트로 확인하면 되는 항목

    컨테이너(91번(가상머신과 컨테이너)) 수십 개를 서버 여러 대에 나눠 띄우고, 죽으면 다시 띄우고, 새 판으로 바꿔 끼우는 일은 사람이 손으로 하기 어렵다. 쿠버네티스는 그 일을 맡고, 서버리스는 서버 자체를 맡는다. 위임형 항목이므로 설정 파일(매니페스트)은 AI에게 맡기되, 쿠버네티스가 그 파일을 어떻게 다루는지와 서버리스가 언제 느리고 비싼지를 이해하고, 받은 설정을 점검하는 법을 익힌다. 쿠버네티스는 설치하지 않고 작게 흉내 낸다.

    이 항목에서 배우는 것¶

    • 쿠버네티스가 원하는 상태를 받아 실제 상태를 맞추는 방식(조정 루프)을 설명할 수 있다.
    • 서버리스에서 콜드 스타트가 언제 생기는지 예측할 수 있다.
    • AI가 쓴 매니페스트를 점검표로 확인하고 고칠 곳을 찾을 수 있다.

    1. 쿠버네티스는 원하는 상태를 받아 실제 상태를 맞춘다¶

    직접 해 보기원하는 상태에 맞추는 조정 루프파드를 지우거나 노드를 끄거나 원하는 수와 판을 바꾼 뒤 '조정 루프 한 번'을 눌러, 쿠버네티스가 실제 상태를 원하는 상태로 한 단계씩 맞추는 모습을 본다
    새 창에서 크게 열기
    • 사람은 "이 컨테이너를 3개, v1으로"라는 원하는 상태만 적는다. 쿠버네티스의 조정 루프는 실제 상태를 계속 보고, 차이가 있으면 메운다. 파드(컨테이너를 감싼 실행 단위)가 죽어도, 노드(서버)가 꺼져도 다시 띄운다(문제 1).
    • 판을 바꾸면 새 판을 하나씩 띄우고, 준비된 만큼 옛 판을 내린다. 그래서 바꾸는 동안에도 서비스가 멈추지 않는다(71번(이중화와 무중단 배포)).

    2. 서버리스는 요청이 올 때만 돌고, 쉬고 나면 콜드 스타트를 치른다¶

    • 서버리스는 함수나 컨테이너만 올리면 요청이 올 때 실행 환경을 띄우고, 쓴 시간만큼 값을 받는다. 서버의 대수와 운영체제는 클라우드가 맡는다(90번(클라우드 서비스 모델)).
    • 한동안 요청이 없으면 실행 환경을 내린다. 그 뒤 첫 요청, 요청이 몰려 환경을 더 띄울 때, 새 판을 올린 직후의 요청은 환경부터 띄우느라 늦다(콜드 스타트, 문제 2). 요청이 드물면 싸고, 늘 바쁘면 서버를 두는 쪽이 싸다.

    3. 매니페스트는 AI에게 맡기되, 받아들이기 전에 점검한다¶

    • 쿠버네티스는 매니페스트에 적힌 대로 충실히 지킨다. 파드를 하나만 적으면 하나만, 비밀번호를 그대로 적으면 그대로 둔다.
    • 필드 이름과 들여쓰기는 AI가 대개 맞추고, 틀린 필드나 없어진 apiVersion은 클러스터에 미리 물어보는 kubectl apply --dry-run=server가 잡는다. 사람은 이 서비스에 맞는 값인지(몇 개, 어느 판, 얼마의 메모리, 준비는 어떻게 아는지)를 본다(문제 3).

    예측해 보기¶

    문제 1. 위젯의 처음 상태(노드 A, B, C에 v1 파드가 하나씩)에서 노드 A를 끈다. 조정 루프를 한 번 돌리면 무엇을 할까? 새 파드는 어느 노드에 뜰까?

    정답과 해설

    실제 2개가 원하는 3개보다 적으므로 새 파드 p4를 노드 B에 띄운다. 위젯은 켜진 노드 가운데 파드가 가장 적은 곳을 고르고, 같으면 이름 차례로 고른다. B와 C에 하나씩 있으니 B다. p4는 다음 단계에 준비되어 다시 3개가 된다. 누구도 "p4를 띄워라"라고 명령하지 않았다. 원하는 상태와 실제 상태의 차이가 할 일을 정한다. 실제 쿠버네티스는 노드가 응답하지 않으면 기본으로 5분쯤 기다린 뒤 그 위의 파드를 지우고 다른 노드에 새로 띄우며, 띄울 노드도 남은 자원과 여러 규칙으로 고른다.

    문제 2. 서버리스 함수에 요청이 아래 시각(분)에 온다. 마지막 요청 뒤 10분 넘게 쉬면 실행 환경을 내린다고 할 때, 콜드 스타트는 몇 번일까? 쉬는 시간을 30분으로 늘리면?

    def cold_starts(requests, idle):                 # 마지막 요청 뒤 idle분을 넘게 쉬면 실행 환경을 내린다
    count, last = 0, None
    for t in requests:
        if last is None or t - last > idle:
            count += 1
        last = t
    return count


requests = [0, 3, 4, 30, 31, 55, 120]
for idle in (10, 30):
    print(idle, cold_starts(requests, idle))
    정답과 해설 
    10 4
30 2

    10분이면 0, 30, 55, 120분의 요청이 콜드 스타트다. 30분이면 30분과 55분 요청은 떠 있는 환경이 받고, 0분과 120분만 남는다. 콜드 스타트가 줄어든 대신, 쉬는 실행 환경이 클라우드의 자원을 더 오래 차지한다. 요청이 없어도 실행 환경을 늘 띄워 두는 것은 돈을 받고 해 주기도 한다(AWS Lambda의 프로비저닝된 동시성, Cloud Run의 최소 인스턴스). 이 PC에서 새 Python 프로세스는 이미 떠 있는 프로세스의 함수 호출보다 2만 배쯤 걸렸다(그림, 더 알아보기). 실제 콜드 스타트의 길이는 언어와 패키지 크기, 클라우드에 따라 다르니 재어 본다.

    문제 3. 매니페스트에 준비 확인(readinessProbe)이 없다. 위젯처럼 판을 v1에서 v2로 바꿀 때 무슨 일이 생길 수 있을까?

    정답과 해설

    아직 요청을 받을 준비가 안 된 새 파드로 요청이 가고, 옛 파드는 너무 일찍 내려가 잠깐 오류가 난다. 위젯의 "시작 중"은 컨테이너가 떴지만 아직 요청을 받을 수 없는 때다. 준비 확인이 없으면 쿠버네티스는 컨테이너가 뜨자마자 준비된 것으로 본다. DB에 연결하거나 데이터를 읽는 데 시간이 걸리는 서비스라면, 그동안 온 요청이 실패한다. readinessProbe에 /health 같은 주소를 적어 두면 그 주소가 성공을 돌려줄 때부터 요청을 보낸다(71번(이중화와 무중단 배포)의 헬스 체크).

    직접 해보기¶

    실습: AI가 쓴 매니페스트를 점검하고 고치기

    1. 아래 order-api.yaml(3절 그림의 매니페스트)과 review.py를 같은 폴더에 저장하고 python review.py order-api.yaml을 실행한다. 다섯 곳이 모두 나오는지 본다.
    2. 다섯 곳을 고친다. AI에게 고치게 해도 되지만, 값(파드 수, 이미지 판, 메모리)은 내가 정해 준다. 비밀번호는 order-db라는 Secret의 password에서 받게 한다.
    3. 고친 파일에 review.py를 다시 돌려 "다섯 곳 모두 통과"가 나오는지 본다. 그리고 스크립트가 보지 못하는 것을 하나 이상 적는다.

    # review.py: 쿠버네티스 매니페스트(YAML 글)에서 사람이 볼 다섯 곳을 먼저 훑는다. 실행: python review.py order-api.yaml
import re
import sys

text = open(sys.argv[1], encoding="utf-8").read()
code = re.sub(r"#.*", "", text)                  # 주석은 빼고 본다
problems = []
replicas = re.search(r"^\s*replicas:\s*(\d+)\s*$", code, re.M)
if not replicas or int(replicas[1]) < 2:         # 적지 않으면 쿠버네티스는 1개로 본다
    problems.append("① 파드가 둘보다 적다(replicas)")
for image in re.findall(r"^\s*-?\s*image:\s*(\S+)", code, re.M):
    image = image.strip("\"'")
    if ":" not in image.split("/")[-1] or image.endswith(":latest"):
        problems.append(f"② 이미지 판이 정해지지 않았다({image})")
if re.search(r"name:\s*\S*(PASSWORD|PASSWD|SECRET|TOKEN|API_?KEY)\S*\s*\n\s*value:", code, re.I):
    problems.append("③ 비밀값을 그대로 적었다(value:)")
if not re.search(r"^\s*resources:\s*$", code, re.M):
    problems.append("④ 자원 요청과 한도(resources)가 없다")
if not re.search(r"^\s*readinessProbe:\s*$", code, re.M):
    problems.append("⑤ 준비 확인(readinessProbe)이 없다")
print("\n".join(problems) if problems else "다섯 곳 모두 통과")

    확인할 점
    • 1단계: 이 PC에서 다섯 줄이 모두 나왔다(①부터 ⑤까지, ②는 shop/order-api:latest).

    • 2단계: 고친 한 예다. 이 파일도 클러스터에 올려 보지 않았고, 필드 이름은 쿠버네티스 문서(v1.37)와 대조했다. review.py는 "다섯 곳 모두 통과"를 찍었다.

    AI와 함께 확인하기¶

    AI 활용 과제: 서버리스로 옮길지 AI와 따져 보기

    1. AI에게 "섹션 8의 주문 서비스를 서버리스로 옮기면 좋을까?"라고 묻는다.
    2. 답이 근거로 든 것을 요청의 모양(얼마나 자주, 몰리는 때), 응답 시간 요구, 비용으로 나누어 적는다.
    3. 내 서비스의 요청 기록이 있다고 보고, 문제 2의 함수로 콜드 스타트 횟수를 세어 답과 견준다.
    확인할 점
    • 요청의 모양을 묻지 않고 "서버리스가 싸다", "확장이 쉽다"로 결론을 냈는지 본다. 늘 바쁜 서비스는 서버를 두는 쪽이 싸다(90번(클라우드 서비스 모델)의 문제 3과 같은 계산).
    • 콜드 스타트와 실행 시간 제한, DB 연결 수처럼 서버리스에서 새로 생기는 제약을 말했는지 본다. 요청마다 새 환경이 뜨면 DB 연결이 한꺼번에 늘 수 있다.
    • 특정 클라우드의 숫자(시간 제한, 요금)를 들었다면 날짜와 출처를 묻고 공식 문서에서 확인한다.

    더 알아보기¶

    쿠버네티스가 맡는 일과 사람이 정하는 일

    쿠버네티스는 파드를 어느 노드에 띄울지(스케줄링), 죽으면 다시 띄우기, 판 바꾸기, 같은 파드 여럿 앞에 하나의 주소를 두기(서비스)를 맡는다. 몇 개를 띄울지, 메모리를 얼마나 줄지, 언제 준비된 것인지, 누구에게 무엇을 허락할지는 사람이 매니페스트에 적는다. 부하에 따라 파드 수를 늘리고 줄이는 일도 맡길 수 있지만, 무엇을 보고 늘릴지(CPU, 요청 수)는 사람이 정한다(65번(수직 확장 vs 수평 확장)). 이 항목의 위젯은 그 가운데 조정 루프만 작게 흉내 냈다.

    판 바꾸기의 기본값

    쿠버네티스의 Deployment는 판을 바꿀 때 한 번에 더 띄울 수 있는 파드(maxSurge)와 한 번에 쉬게 할 수 있는 파드(maxUnavailable)를 정한다. 문서에 적힌 기본값은 둘 다 25%이고, 더 띄우는 수는 올림, 쉬게 하는 수는 내림으로 센다. 그래서 파드 3개면 하나 더 띄우고 하나도 쉬게 하지 않는다. 위젯과 같다. 남는 자리가 없으면 새 판을 띄우지 못해 멈추고, 쿠버네티스는 기본으로 600초 동안 나아가지 못하면 멈췄다고 알린다. 위젯에서 노드 B와 C를 끄고 판을 바꿔 보면 같은 일이 보인다.

    그림의 시간은 어떻게 쟀나

    2절 그림의 세 값은 아래 프로그램으로 이 PC(Core i9-14900KF, DDR5 64GB, NVMe SSD, Windows 11, Python 3.14.0, Docker Desktop 4.48.0)에서 쟀다. 따뜻한 호출은 10만 번 부른 평균의 가장 짧은 값, 프로세스와 컨테이너는 10번 띄운 가운데 가장 짧은 값과 가운데값을 찍는다. 그림에는 날을 달리해 여러 번 실행한 범위를 적었다. 컨테이너를 재려면 Docker가 있어야 한다(실습 환경 9절).

    # measure.py: 떠 있는 함수 호출, 새 Python 프로세스, 새 컨테이너를 띄우는 시간을 잰다
import json
import statistics
import subprocess
import sys
import time
import timeit


def handler(event):                              # 주문 금액을 계산해 JSON으로 돌려주는 작은 처리 함수
    total = sum(p * q for p, q in event["items"])
    return json.dumps({"total": total})


ev = {"items": [[25000, 1], [3000, 2]]}
warm = min(timeit.repeat(lambda: handler(ev), number=100_000, repeat=5)) / 100_000
print(f"따뜻한 호출: {warm * 1e6:.1f}us")
for name, cmd in [("새 Python 프로세스", [sys.executable, "-c", "pass"]),
                  ("새 컨테이너", ["docker", "run", "--rm", "python:3.14-slim", "python", "-c", "pass"])]:
    ts = []
    for _ in range(10):
        start = time.perf_counter()
        subprocess.run(cmd, check=True, capture_output=True)
        ts.append((time.perf_counter() - start) * 1000)
    print(f"{name}: 가장 짧은 값 {min(ts):.0f}ms, 가운데값 {statistics.median(ts):.0f}ms")

    정리¶

    • 쿠버네티스는 원하는 상태를 받아, 조정 루프로 실제 상태를 계속 맞춘다. 죽은 파드를 다시 띄우고, 판을 하나씩 바꾼다.
    • 서버리스는 요청이 올 때만 돌고 쓴 만큼 받는다. 쉬고 난 뒤의 첫 요청은 콜드 스타트로 늦다.
    • 매니페스트는 AI가 빨리 쓰지만, 파드 수, 이미지 판, 비밀값, 자원, 준비 확인은 사람이 점검한다.
