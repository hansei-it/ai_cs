    91. 인프라 가상화: 하이퍼바이저 기반 가상머신 vs 컨테이너(Docker)¶

    원리 동작을 예측하고 이상을 알아챌 수 있어야 하는 항목

    클라우드에서 "서버 한 대"를 빌리면, 대개 진짜 기계가 아니라 가상머신이나 컨테이너를 받는다. 둘 다 한 기계를 여럿으로 나눠 쓰는 방법이지만 나누는 자리가 다르고, 그 차이가 무게, 뜨는 시간, 격리의 세기를 정한다. 원리형 항목이므로 결과를 먼저 예측하고, 이 PC의 Docker Desktop으로 컨테이너를 실제로 띄워 맞춰 본다. Docker는 실습 환경 9절을 따라 깐다.

    이 항목에서 배우는 것¶

    • 가상머신과 컨테이너가 무엇을 나눠 쓰고 무엇을 따로 갖는지 설명할 수 있다.
    • 컨테이너가 커널을 나눠 쓰는, 격리된 프로세스라는 것을 실험 결과로 예측할 수 있다.
    • 이미지의 층과 빌드 캐시 때문에 Dockerfile의 차례가 빌드 시간을 바꾸는 것을 예측할 수 있다.

    1. 가상머신은 운영체제까지 따로 갖고, 컨테이너는 커널을 나눠 쓴다¶

    • 가상머신은 하이퍼바이저가 나눠 준 가상 하드웨어(CPU, 메모리, 디스크) 위에 운영체제를 통째로 올린다. 커널까지 따로라 격리가 강하고 다른 운영체제도 돌리지만, 무겁고 부팅이 필요하다.
    • 컨테이너는 운영체제 커널 하나를 나눠 쓰고, 프로그램과 그 라이브러리만 따로 묶는다. 이 PC에서 컨테이너 하나를 띄우고 끝내는 데 0.3~0.4초가 걸렸다(Python 프로세스 하나는 0.02초쯤, 더 알아보기).
    • Windows의 Docker Desktop은 WSL2라는 가벼운 가상머신 안의 리눅스 커널에서 컨테이너를 돌린다. 클라우드도 가상머신 위에 컨테이너를 겹쳐 쓰는 일이 흔하다(문제 1).

    2. 컨테이너는 보이는 것과 쓰는 양을 나눈 프로세스다¶

    • 커널의 네임스페이스가 보이는 것(프로세스 목록, 이름, 파일 시스템, 네트워크)을 나누고, cgroup이 쓰는 양(메모리, CPU, 프로세스 수)을 묶는다. 컨테이너 안에서는 내 명령의 PID(프로세스 번호)가 1이고, 다른 프로세스는 보이지 않는다(30번(프로그램, 프로세스, 스레드)).
    • 메모리 한도를 넘으면 커널이 그 프로세스를 강제로 끝낸다. 메모리 한도에는 스왑(디스크로 내보낸 메모리, 37번(가상 메모리)의 페이징 파일)이 함께 걸린다(문제 2). CPU 한도는 느리게 할 뿐이고, 프로세스 수 한도는 새 프로세스를 만들지 못하게 한다.

    3. 이미지는 층을 쌓고, 바뀐 층부터 다시 만든다¶

    직접 해 보기바뀐 층부터 다시 만든다Dockerfile의 두 차례(A, B) 가운데 하나를 고르고 app.py나 make_db.py를 고친 뒤 다시 빌드해, 어느 층을 캐시에서 가져오고 어느 층을 다시 만드는지와 걸린 시간을 본다
    새 창에서 크게 열기
    • 이미지는 파일 층을 쌓은 것이다. Dockerfile에서 파일을 바꾸는 줄(WORKDIR, COPY, RUN)마다 층이 하나 쌓이고, ENTRYPOINT 같은 설정 줄은 층을 만들지 않는다. 같은 이미지로 띄운 컨테이너는 몇 개든 같은 파일에서 시작한다. 그래서 89번(CI/CD)의 "한 번 만든 산출물을 옮긴다"를 이미지로 한다.
    • 다시 빌드할 때는 입력이 바뀐 줄부터 아래를 모두 다시 만들고, 위는 캐시에서 가져온다. 무겁고 잘 바뀌지 않는 단계(실제 프로젝트에서는 흔히 의존성 설치, 여기서는 DB 만들기)를 위에, 자주 바뀌는 코드를 아래에 둔다(문제 3).

    예측해 보기¶

    문제 1. Alpine 이미지와 Debian 기반의 Python 이미지로 컨테이너를 하나씩 띄워, 커널의 판(uname -r)과 배포판 이름을 찍는다. 두 줄씩 무엇이 나올까? 어느 쪽이 같고 어느 쪽이 다를까?

    docker run --rm alpine:3.22 sh -c "uname -r; grep PRETTY_NAME /etc/os-release"
docker run --rm python:3.14-slim sh -c "uname -r; grep PRETTY_NAME /etc/os-release"
    정답과 해설 
    6.6.87.2-microsoft-standard-WSL2
PRETTY_NAME="Alpine Linux v3.22"
6.6.87.2-microsoft-standard-WSL2
PRETTY_NAME="Debian GNU/Linux 13 (trixie)"

    커널은 같고 배포판은 다르다. 두 컨테이너는 같은 리눅스 커널 하나를 나눠 쓰고, 이미지에 든 파일(명령, 라이브러리, /etc/os-release)만 다르다. 커널 이름의 microsoft-standard-WSL2는 그 커널이 Windows가 아니라 WSL2 가상머신 안의 리눅스 커널이라는 뜻이다. 이 PC의 Windows는 따로 10.0.26300판이다. 그래서 컨테이너 안에서 커널의 판을 바꾸거나 Windows 프로그램을 돌릴 수는 없다. 다른 커널이 필요하면 가상머신을 쓴다.

    문제 2. 메모리를 64MB로 묶은 컨테이너에서 100MB를 채운다. 어떻게 될까? 메모리와 스왑을 합쳐 64MB로 묶어 스왑을 막으면?

    docker run --rm --memory 64m python:3.14-slim python -c "a = b'x' * (100 * 1024 * 1024); print(len(a))"
docker run --rm --memory 64m --memory-swap 64m python:3.14-slim python -c "a = b'x' * (100 * 1024 * 1024); print(len(a))"
    정답과 해설

    첫 줄은 104857600을 찍고 정상으로 끝나고, 둘째 줄은 아무것도 찍지 못하고 종료 코드 137로 끝난다. --memory 64m만 주면 Docker는 같은 양의 스왑을 더 허락한다(호스트에 스왑이 있을 때. WSL2에는 기본으로 있다). 컨테이너 안의 /sys/fs/cgroup/memory.max와 memory.swap.max가 둘 다 67108864(64MiB)였다. 그래서 100MB는 메모리 64MB와 스왑에 걸쳐 들어가고, 이 PC에서 200MB로 늘리자 그때는 강제로 끝났다. --memory-swap 64m은 메모리와 스왑을 합쳐 64MB라는 뜻이라 스왑이 0이 되고(memory.swap.max가 0), 100MB를 채우는 도중에 커널이 프로세스를 끝냈다. 137은 128 + 9로, 9번 신호(SIGKILL, 강제 종료)로 끝났다는 뜻이다. PowerShell에서는 $LASTEXITCODE로 본다. 한도를 정할 때는 스왑까지 정해야 하고, 스왑을 쓰는 동안은 느려진다는 것도 함께 따진다.

    문제 3. 위젯의 Dockerfile A와 B로 처음 빌드하면 둘 다 3초쯤 걸린다. app.py만 고치고 다시 빌드하면 각각 몇 초쯤 걸릴까? 위젯을 누르기 전에 적어 본다.

    정답과 해설

    A는 다시 2.9~3.2초, B는 0.4~0.5초다. A의 COPY . .는 app.py도 읽으므로 이 층이 바뀌고, 그 아래의 DB 만들기(1.2~1.3초와 33MB 층 저장)를 다시 한다. B는 make_db.py만 복사한 층과 DB 층이 그대로라 캐시에서 가져오고, 마지막 COPY app.py .만 다시 한다. 이 PC에서 경우마다 10번 잰 값이다(Docker Desktop 4.48.0, Core i9-14900KF, DDR5 64GB, NVMe SSD). 개발자의 PC와 캐시를 이어 쓰게 설정한 CI(89번(CI/CD))에서는 빌드가 하루에도 수십 번 돌아 이 차이가 쌓인다. 매번 빈 기계에서 시작하는 CI는 캐시가 없어 A와 B 모두 처음 빌드와 같다.

    직접 해보기¶

    실습: 컨테이너를 띄우고, 이미지를 만들어 다시 빌드하기

    1. Docker Desktop을 켜고 PowerShell에서 문제 1, 2의 명령을 실행해 예측과 견준다. 처음에는 이미지를 받느라 Unable to find image, Pull complete 같은 줄이 먼저 나온다. 문제 2의 둘째 명령 뒤에 $LASTEXITCODE를 찍는다.
    2. 빈 폴더에 아래 make_db.py, app.py와 Dockerfile B를 확장자 없는 Dockerfile이라는 이름으로 저장하고(메모장에서는 파일 형식을 "모든 파일"로 두고 저장한 뒤, dir로 Dockerfile.txt가 아닌지 본다) docker build -t cs-shop .으로 이미지를 만든다. docker run --rm cs-shop 42로 상품 하나를 찍는다.
    3. app.py의 출력을 조금 고치고(영문으로. 컨테이너가 찍는 한글은 창에서 깨질 수 있다) (Measure-Command { docker build -t cs-shop . }).TotalSeconds로 다시 빌드하는 시간을 잰다. 이번에는 make_db.py에 주석 한 줄을 더하고 잰다. 위젯과 견준다.
    4. docker history cs-shop으로 층마다의 크기를 보고, 끝나면 docker rmi cs-shop으로 지운다.

    # make_db.py: 상품 100만 개의 표를 SQLite DB(products.db)로 만든다. 이미지를 만들 때 한 번 돈다
import random
import sqlite3

random.seed(91)
db = sqlite3.connect("products.db")
db.execute("CREATE TABLE product (id INTEGER PRIMARY KEY, name TEXT, price INTEGER)")
db.executemany("INSERT INTO product VALUES (?, ?, ?)",
               ((i, f"P{i:07d}", random.randrange(1000, 100001, 100)) for i in range(1, 1_000_001)))
db.execute("CREATE INDEX product_price ON product(price)")
db.commit()


    # app.py: 상품 번호를 받아 이름과 가격을 보여 준다
import sqlite3
import sys

db = sqlite3.connect("products.db")
pid = int(sys.argv[1]) if len(sys.argv) > 1 else 1
name, price = db.execute("SELECT name, price FROM product WHERE id = ?", (pid,)).fetchone()
print(f"{name} {price:,}")

    Dockerfile A:

    FROM python:3.14-slim
WORKDIR /app
COPY . .
RUN python make_db.py
ENTRYPOINT ["python", "app.py"]

    Dockerfile B:

    FROM python:3.14-slim
WORKDIR /app
COPY make_db.py .
RUN python make_db.py
COPY app.py .
ENTRYPOINT ["python", "app.py"]

    컨테이너 안의 출력은 영문과 숫자로만 해서 Windows 창의 글자 설정과 상관없이 보이게 했다.

    확인할 점
    • 2단계: 이 PC에서 docker run --rm cs-shop 42는 P0000042 31,900을 찍었다. 이미지는 python:3.14-slim(Python 3.14.8) 위에 층이 넷(WORKDIR, COPY, RUN, COPY) 더해졌고, docker history에서 더한 층 가운데 DB를 만든 층이 32.9MB로 가장 컸다. IMAGE 칸의 <missing>은 그 층에 따로 붙은 이미지 ID가 없다는 뜻으로, 오류가 아니다.
    • 3단계: 위젯의 값과 같은 쪽이어야 한다. app.py만 고치면 B는 1초 안에 끝나고, make_db.py를 고치면 그 파일을 복사하는 층부터 DB 층까지 다시 만들어 3초쯤 걸린다.
    • 고쳤다가 예전 내용으로 되돌리면 그 내용으로 만든 적이 있는 층을 캐시에서 다시 쓴다. 캐시는 파일의 이름이나 시각이 아니라 내용으로 찾는다.

    AI와 함께 확인하기¶

    AI 활용 과제: AI가 쓴 Dockerfile 검토하기

    1. 실습의 make_db.py, app.py를 주고 AI에게 "이 프로그램의 Dockerfile을 써 줘"라고 한다.
    2. 받은 Dockerfile을 빌드하고, app.py만 고쳐 다시 빌드하는 시간을 잰다.
    3. 아래 확인할 점과 견주어 고칠 곳을 적고, 근거와 함께 AI에게 고치게 한다.
    확인할 점
    • COPY . .를 무거운 단계보다 앞에 두었는지 본다. 그러면 코드만 고쳐도 무거운 단계를 매번 다시 한다(문제 3).
    • 기본 이미지의 판을 정했는지 본다. python:latest처럼 두면 같은 Dockerfile이 다른 날 다른 이미지가 된다(17번(패키지 생태계와 의존성 관리)의 잠금과 같은 문제). python:3.14-slim처럼 적어도 패치 판이 오르면 바뀌므로, 똑같은 이미지로 묶으려면 python:3.14-slim@sha256:…처럼 내용의 해시(다이제스트)를 붙인다.
    • 비밀번호나 API 키를 ENV나 COPY로 이미지에 넣지 않았는지 본다. 이미지의 층은 그대로 남아 이미지를 받은 누구나 꺼내 볼 수 있다.
    • 빌드에 필요 없는 파일(.git, 테스트 데이터, 비밀값 파일)이 COPY . .로 들어가지 않게 .dockerignore를 두었는지 본다.

    더 알아보기¶

    가상머신은 어디서 무겁나

    가상머신에는 대개 메모리를 미리 떼어 주고, 켤 때 운영체제를 처음부터 부팅한다. 대신 커널까지 따로라, 한 가상머신의 커널 결함이 다른 가상머신에 미치기 어렵다. 그래서 클라우드는 서로 모르는 손님의 코드를 가상머신으로 갈라 놓고, 그 안에서 컨테이너를 돌린다. 서버리스처럼 남의 코드를 아주 짧게 돌리는 곳에서는 몇 분의 1초 만에 뜨도록 줄인 가벼운 가상머신(예: Firecracker)을 쓰기도 한다(92번(쿠버네티스와 서버리스)). 가상머신이라도 게스트의 명령을 하나씩 흉내 내어 돌리지는 않는다. CPU의 가상화 기능(실습 환경 9절의 하드웨어 가상화)으로 게스트의 명령도 CPU에서 바로 돌고, 하이퍼바이저는 장치를 다루는 일처럼 하드웨어에 닿는 때에 끼어든다.

    뜨는 시간은 어떻게 쟀나

    1절의 시간은 이 PC(Core i9-14900KF, DDR5 64GB, NVMe SSD, Docker Desktop 4.48.0)의 PowerShell에서 아래 명령을 10번씩 실행해 잰 범위다. 이미지는 미리 받아 두었다. 컨테이너 하나를 띄울 때는 네임스페이스와 cgroup을 만들고, 이미지의 층을 겹쳐 파일 시스템을 꾸리고, Windows의 docker 명령이 WSL2 안의 Docker 엔진에 일을 맡긴다. 30번(프로그램, 프로세스, 스레드)에서 C로 만든 빈 프로세스는 3.8~3.9ms였다.

    (Measure-Command { docker run --rm alpine:3.22 true }).TotalSeconds
(Measure-Command { python -c pass }).TotalSeconds
    컨테이너와 Windows

    컨테이너는 커널을 나눠 쓰므로 리눅스 컨테이너에는 리눅스 커널이 있어야 한다. Windows의 Docker Desktop이 WSL2라는 가상머신을 쓰는 까닭이다. Windows 커널을 나눠 쓰는 Windows 컨테이너도 있지만 이 강의에서는 쓰지 않는다. 컨테이너가 "어디서나 똑같이 돈다"는 말은 같은 종류의 커널 위라는 조건이 붙는다.

    정리¶

    • 가상머신은 가상 하드웨어 위에 운영체제를 통째로 올린다. 컨테이너는 커널 하나를 나눠 쓰고 프로그램과 라이브러리만 따로 가져 가볍다.
    • 컨테이너는 네임스페이스로 보이는 것을, cgroup으로 쓰는 양을 나눈 프로세스다. 메모리 한도를 넘으면 커널이 끝낸다.
    • 이미지는 층을 쌓고, 바뀐 층부터 다시 만든다. 무거운 단계는 위에, 자주 바뀌는 코드는 아래에 둔다.
