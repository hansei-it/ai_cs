    96. 작업 분해와 맥락 제공: 문제를 쪼개고 AI에게 일을 맡기는 방법¶

    직접 AI 없이 직접 할 수 있어야 하는 항목

    95번(AI 기능의 평가)까지는 AI를 기능으로 넣는 쪽을 봤다. 이제 AI에게 일을 맡기는 쪽이다. AI는 큰 일도 한 번에 해 주지만, 크게 맡길수록 무엇이 틀렸는지 찾기 어렵고, 내 저장소의 사정을 모르면 그럴듯한 기본값으로 채운다(93번(LLM의 동작 원리)). 직접형 항목이므로 섹션 10에서 이어 온 주문 금액 계산(order.py)에 쿠폰 만료일을 더하는 일을 쪼개고, 작업 지시서를 써서 맡기고, 완료 기준으로 확인한다. 본문의 "받은 답"은 흔한 어긋남을 담아 이 강의가 쓴 예다.

    이 항목에서 배우는 것¶

    • 큰 일을 확인할 수 있는 작은 일로 쪼개고 차례를 정할 수 있다.
    • 목표, 맥락, 꼴(함수 이름과 인자), 규칙, 제약, 완료 기준을 담은 작업 지시서를 쓸 수 있다.
    • 조각마다 맡기고, 읽고, 확인하고, 커밋하는 고리를 돌릴 수 있다.

    1. 큰 일은 확인할 수 있는 작은 일로 쪼갠다¶

    • 조각마다 "끝났다는 기준"이 있어야 한다. 쪼갤 때 먼저 묻는다. 이 조각이 맞았는지 무엇으로 알 수 있나? 답이 없으면 더 쪼개거나 기준부터 만든다. 기준은 테스트일 수도(84번(테스트 설계)), 사람이 정해 남긴 결정 기록일 수도(82번(설계 결정 기록(ADR))) 있다.
    • 차례는 먼저 있어야 하는 것부터 정한다. 판단 함수가 있어야 주문 계산에 이을 수 있다. 한 조각의 변경은 한 번에 읽을 수 있는 크기로 둔다.

    2. 맥락은 AI가 모르는 것을 적어 주는 것이다¶

    직접 해 보기맥락이 빠지면 무엇이 깨질까작업 지시서에 넣을 맥락 다섯 가지를 켜고 끄며, 받은 답의 코드가 어떻게 바뀌고 완료 기준의 어느 줄이 깨지는지 본다
    새 창에서 크게 열기
    • AI는 붙여 주지 않은 코드와, 코드에 적히지 않은 규칙(경계, 쓸 수 있는 패키지)을 모른다. 빠진 것은 그럴듯한 기본값으로 채운다. 위젯에서 '모두 넣기'를 누른 뒤 하나씩 빼 보면 빠진 것마다 깨지는 곳이 다르다.
    • 그래서 작업 지시서에 목표, 맥락(기존 코드), 꼴(함수 이름과 인자), 규칙(경계와 예외), 제약, 완료 기준을 적는다. 넓게 보면 꼴, 규칙, 제약도 모두 AI가 모르는 맥락이다(위젯의 다섯 가지). 완료 기준은 81번(요구사항과 명세)의 수용 기준(구체적인 예)을 나와 AI가 함께 돌릴 수 있는 명령으로 만든 것이다. Anthropic의 문서도 Claude를 "맥락이 부족한, 뛰어나지만 새로 입사한 직원"이라고 생각하라고 하고, 테스트처럼 AI가 직접 돌릴 수 있는 확인 방법을 주라고 권한다. 앞에서 막히면 뒤의 어긋남은 드러나지 않으므로, 하나를 고친 뒤에도 기준을 다시 돌린다(문제 1).

    3. 한 조각씩 맡기고, 읽고, 확인하고, 남긴다¶

    • 조각 하나를 맡기고, 바뀐 곳을 읽고(git status --short로 새 파일까지 보고 git diff로 고친 줄을 읽는다), 완료 기준을 돌리고, 통과하면 커밋한다(83번(Git 실천)). 틀리면 그 조각만 되돌리고(고친 파일은 git restore, 새 파일은 지운다) 빠진 맥락을 채워 다시 맡긴다.
    • 큰 일은 계획(쪼갠 목록)부터 받아 보고, 내가 고친 뒤 조각을 맡긴다. 코딩 에이전트의 사용 안내도 탐색, 계획, 구현, 커밋의 차례를 권한다. 쪼개는 일까지 AI에게 맡겨도, 조각마다 기준이 있는지 확인하는 것은 내 몫이다.

    예측해 보기¶

    문제는 실습의 order.py, check_expiry.py와 같은 폴더에서 푼다.

    문제 1. "WELCOME10 쿠폰에 만료일(2026-12-31)을 두고, 쿠폰을 쓸 수 있는지 판단하는 is_valid 함수를 만들어 줘" 한 줄로 맡겨 받은 답은 함수의 꼴이 달라 완료 기준의 다섯 줄이 모두 TypeError로 실패했다(실습 확인할 점의 expiry_first.py). 그래서 함수의 꼴을 더 알려 주고 다시 받은 답이 아래와 같다. 완료 기준을 돌리면(python check_expiry.py expiry_mid나 아래 코드) 몇 줄이 통과할까?

    # expiry_mid.py: 함수의 꼴을 더 알려 주고 받은 답(예)
from datetime import date

EXPIRES = {"WELCOME10": date(2026, 12, 31)}


def is_valid(code, today):
    return today < EXPIRES[code]

    from check_expiry import check

check("expiry_mid")
    정답과 해설 
    통과 WELCOME10 2026-12-30 True
실패 WELCOME10 2026-12-31 False
통과 WELCOME10 2027-01-01 False
실패 FREESHIP 2030-01-01 KeyError
실패 NOPE 2026-10-01 KeyError

    두 줄만 통과한다. 꼴을 맞추자, 그 뒤에 가려져 있던 어긋남 둘이 드러났다. 만료일 당일(12월 31일)에는 못 쓰게 했고(<), 만료일이 없는 FREESHIP과 없는 쿠폰 NOPE에서는 표에 없는 키를 찾다 KeyError가 난다. 꼴을 알려 주지 않았을 때는 이 둘이 보이지 않았다. 하나를 고칠 때마다 완료 기준 전체를 다시 돌려야 하는 까닭이다. 위젯에서 '모두 넣기'를 누른 뒤 경계 규칙과 예외 규칙만 빼면 같은 결과가 나온다(위젯의 흉내는 제약이 빠지면 dateutil을 쓰므로, 꼴만 켜면 불러오기에서 막힌다).

    문제 2. 작업 지시서에 "WELCOME10은 12월 31일까지 쓸 수 있다"라고만 적었다. 이 문장으로 판단 함수가 하나로 정해질까?

    정답과 해설

    정해지지 않는다. "까지"가 31일을 포함하는지부터 읽는 사람마다 다를 수 있다(문제 1의 답은 빼는 쪽으로 읽었다). 날짜만이 아니라 시각도 있다. 서버가 협정 세계시(UTC)로 날짜를 세면, 한국 시각으로는 오전 9시에 날짜가 바뀐다(63번(JSON과 직렬화)). 그래서 규칙을 말로 적는 것에 더해, 완료 기준에 경계의 예(12월 30일, 31일, 1월 1일)를 넣어 해석을 못 박는다. 실습의 check_expiry.py가 31일을 True로 둔 것이 그 결정이다. 시각과 시간대를 어떻게 셀지는 사람이 정하고 기록한다(82번(설계 결정 기록(ADR))).

    직접 해보기¶

    실습: 쿠폰 만료 기능을 쪼개서 맡기기

    1. 83번(Git 실천)의 shop 저장소에 아래 check_expiry.py를 저장하고 커밋한다(git add check_expiry.py, git commit -m "쿠폰 만료 판단의 완료 기준"). 저장소가 없으면 새 폴더에 아래 order.py(83번(Git 실천)의 실습을 마친 판)도 저장하고, 83번(Git 실천) 실습 1단계처럼 저장소를 만들어 두 파일을 커밋한다.
    2. 1절 그림처럼 쿠폰 만료 기능을 조각으로 쪼개고, 조각마다 끝났다는 기준을 적는다.
    3. ① 조각은 "만료일은 expiry.py의 EXPIRES 표에 둔다"로 정했다고 하자. ② 조각을 "WELCOME10 쿠폰에 만료일(2026-12-31)을 두고, 쿠폰을 쓸 수 있는지 판단하는 is_valid 함수를 만들어 줘" 한 줄로 맡겼더니 받은 답이 확인할 점의 expiry_first.py다. 저장하고 python check_expiry.py expiry_first를 돌려, 무엇이 빠졌는지 적는다.
    4. 같은 조각을 아래 작업 지시서로 다시 맡겼더니 받은 답이 확인할 점의 expiry.py다. 저장하고 python check_expiry.py expiry를 돌린다. 통과하면 바뀐 곳을 읽고 커밋한다.

    작업 지시서(② 조각):

    목표: WELCOME10 쿠폰에 만료일(2026-12-31)을 두고, 쿠폰을 쓸 수 있는지 판단하는 함수만 만든다.
맥락: 아래 order.py의 COUPONS 표를 쓴다. 새 파일 expiry.py에 둔다. 완료 기준인 check_expiry.py도 붙인다.
꼴: is_valid(code, today) -> bool. today는 datetime.date로 받는다(함수 안에서 오늘을 읽지 않는다).
규칙: 만료일 당일까지 쓸 수 있다. 만료일이 없는 쿠폰은 늘 쓸 수 있다. COUPONS에 없는 쿠폰은 False다.
제약: Python 3.14 표준 라이브러리만 쓴다. order.py와 check_expiry.py는 고치지 않는다.
완료 기준: python check_expiry.py expiry가 다섯 줄 모두 "통과"를 찍는다.


    # order.py
COUPONS = {"WELCOME10": 10, "FREESHIP": 0}           # 쿠폰 → 할인율(%)


def order_total(items, coupon=None):
    """items: [(가격, 수량), ...]. 결제할 금액(원)을 돌려준다."""
    if not items:
        raise ValueError("빈 장바구니는 주문할 수 없습니다")
    for price, qty in items:
        if price < 0 or qty <= 0:
            raise ValueError("가격과 수량을 확인하세요")
    if coupon is not None and coupon not in COUPONS:
        raise ValueError(f"모르는 쿠폰: {coupon}")
    subtotal = sum(price * qty for price, qty in items)
    discount = min(subtotal * COUPONS[coupon] // 100, 5000) if coupon else 0
    paid = subtotal - discount
    shipping = 0 if paid >= 30000 or coupon == "FREESHIP" else 3000   # 무료 배송은 할인 뒤 금액으로 정한다
    return paid + shipping

import importlib
import sys
from datetime import date

CASES = [("WELCOME10", date(2026, 12, 30), True), ("WELCOME10", date(2026, 12, 31), True),
         ("WELCOME10", date(2027, 1, 1), False), ("FREESHIP", date(2030, 1, 1), True),
         ("NOPE", date(2026, 10, 1), False)]             # (쿠폰, 오늘, 쓸 수 있나)


def check(module_name):
    try:
        is_valid = importlib.import_module(module_name).is_valid
    except Exception as e:                           # 불러오지 못하거나 이름이 다르면 거기서 끝난다
        print("실패 불러오기", type(e).__name__, e)
        return
    for code, today, want in CASES:
        try:
            got = is_valid(code, today)
        except Exception as e:                       # 오류도 결과로 적는다
            got = type(e).__name__
        print("통과" if got == want else "실패", code, today, got)


if __name__ == "__main__":
    check(sys.argv[1])

from datetime import date

from order import COUPONS

EXPIRES = {"WELCOME10": date(2026, 12, 31)}           # 만료일이 없는 쿠폰은 늘 쓸 수 있다


def is_valid(code, today):
    if code not in COUPONS:
        return False
    expires = EXPIRES.get(code)
    return expires is None or today <= expires

    • 지시서로 받은 답도 읽어 본다. git status --short로 새 파일(??)과 고친 파일(M)을 보고, git diff로 고친 줄을 읽는다. order.py나 check_expiry.py가 M으로 나오면 제약을 어긴 것이다. 맡긴 ② 조각 밖의 일(주문 계산에 잇기)을 하지 않았는지, 완료 기준을 붙여 주었으므로 다섯 경우만 맞추려고 쿠폰 이름이나 날짜를 if로 박아 넣지 않았는지도 본다. 통과하면 이 조각만 커밋하고(git add expiry.py) ③ 조각으로 간다. 통과하지 않으면 실패한 줄을 보고 빠진 맥락을 지시서에 채워 다시 맡긴다(3절).

    AI와 함께 확인하기¶

    AI 활용 과제: 계획부터 받아 보기

    1. AI에게 "order.py에 쿠폰 만료 기능을 넣으려 한다. 코드는 쓰지 말고, 조각으로 나눈 계획과 조각마다 끝났다는 기준을 먼저 적어 줘"라고 하고 order.py를 붙인다.
    2. 받은 계획을 실습 2단계에서 내가 쪼갠 목록과 견주고, 기준이 없는 조각, 너무 큰 조각, 차례가 거꾸로 된 조각, 사람이 정해야 할 결정을 표시한다.
    3. 고친 계획에서 AI에게 맡길 첫 조각만 맡기고, 3절의 고리를 한 번 돈다.
    확인할 점
    • "테스트를 작성한다"가 마지막 조각 하나로 몰려 있으면, 앞 조각들은 기준 없이 끝난 셈이다. 조각마다 기준을 붙인다.
    • "만료 처리 구현"처럼 한 조각이 판단, 연결, 안내를 모두 품으면 더 쪼갠다.
    • 만료일을 어디에 둘지(코드, 설정 파일, DB), 만료된 쿠폰을 쓰려 하면 거절할지 할인만 안 할지는 AI가 정해 버리기 쉽다. 그런 조각은 사람이 정하고 기록한다(82번(설계 결정 기록(ADR))).

    더 알아보기¶

    맥락을 저장소에 적어 두기

    매번 같은 맥락(코드 규칙, 실행 명령, 쓰면 안 되는 패키지)을 지시서에 다시 적는 대신, 저장소에 맥락 파일을 두는 도구가 많다. 예를 들어 Claude Code는 대화를 시작할 때마다 저장소의 CLAUDE.md를 읽는다. 이 강의의 원고 저장소에도 그런 파일이 있어, 예제 언어, 검사 명령, 확인한 값만 쓴다는 규칙을 적어 둔다. 맥락 파일도 코드처럼 리뷰하고 고친다. 틀린 맥락은 맥락이 없는 것보다 나쁘다.

    쪼개기는 사람 사이의 일에도 같다

    작업 지시서에 적는 여섯 가지(목표, 맥락, 꼴, 규칙, 제약, 완료 기준)는 사람에게 일을 맡길 때 쓰는 이슈나 티켓의 내용과 같다. 81번(요구사항과 명세)의 수용 기준, 기능을 작은 조각으로 나누어 조각마다 끝내는 80번(소프트웨어 개발 생명주기)의 반복형과도 이어진다. AI에게 잘 맡기는 사람은 팀원에게도 잘 맡긴다.

    정리¶

    • 큰 일은 끝났다는 기준이 있는 작은 조각으로 쪼개고, 먼저 있어야 하는 것부터 차례를 정한다.
    • 작업 지시서에 목표, 맥락, 꼴, 규칙, 제약, 완료 기준을 적는다. 빠진 것은 AI가 그럴듯한 기본값으로 채운다.
    • 한 조각씩 맡기고, 바뀐 곳을 읽고, 완료 기준을 돌리고, 커밋한다. 하나를 고치면 기준을 다시 돌린다.
