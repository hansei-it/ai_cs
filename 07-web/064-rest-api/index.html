    64. REST API 설계: 인터페이스 계약을 명세로 정의하기¶

    직접 AI 없이 직접 할 수 있어야 하는 항목

    프론트엔드와 백엔드, 서비스와 서비스는 API로 만난다. API는 "이 주소에 이것을 보내면 이것이 온다"는 약속(계약)이다. 약속이 말로만 있으면 양쪽이 다르게 이해하고, AI가 짠 서버와 클라이언트도 서로 어긋난다. 직접형 항목이므로 계약을 명세로 먼저 적고, 그 명세로 시험하며 서버를 직접 짠다. 서버는 Node의 기본 http 모듈로 짠다(실습 환경). HTTP의 메서드와 상태 코드의 기본은 43번(HTTP)에서 다뤘다.

    이 항목에서 배우는 것¶

    • 자원과 메서드, 상태 코드로 API를 설계하고, 같은 요청을 다시 보내도 되는지 말할 수 있다.
    • 요청과 응답의 모양, 오류의 상태 코드와 본문을 명세로 적을 수 있다.
    • 명세로 서버를 시험해(계약 테스트) 어긋난 곳을 찾고 고칠 수 있다.

    1. 주소는 자원을, 메서드는 동작을, 상태 코드는 결과를 말한다¶

    • REST 방식의 API는 다룰 대상(자원)을 주소로 둔다. 할 일 모음은 /todos, 할 일 하나는 /todos/7이다. 무엇을 할지는 주소가 아니라 메서드로 말한다.
    • 성공에도 뜻이 있다. 새로 만들었으면 201과 새 주소(Location 머리), 지웠고 돌려줄 본문이 없으면 204다.
    • 같은 요청을 여러 번 보내도 결과가 같은 성질을 멱등성이라 한다. GET, PUT, DELETE는 멱등이라 응답을 못 받았을 때 다시 보내도 된다. POST는 그렇지 않다(문제 1).

    2. 계약을 명세로 먼저 쓰고, 그 명세로 서버를 시험한다¶

    직접 해 보기명세로 서버 시험하기서버 셋 가운데 하나를 골라 '계약 테스트'을 누르면, 명세에 적힌 요청을 차례로 보내 상태 코드와 응답 모양이 명세와 같은지 줄마다 보여 준다. 줄을 누르면 응답 본문이 보인다
    새 창에서 크게 열기
    • 명세는 요청마다 무엇을 보내고 무엇을 받는지 적은 문서다. 업계에서는 OpenAPI 형식을 많이 쓴다(더 알아보기). 이 항목은 같은 생각을 자바스크립트 객체로 작게 적는다.
    • 명세가 있으면 서버와 클라이언트를 따로, 동시에 짤 수 있다. 서버는 명세의 요청을 보내 응답을 견주는 계약 테스트로 확인한다(위젯).
    • AI에게 서버를 맡겨도 명세는 사람이 정하고, 받아들일지는 계약 테스트로 정한다. 위젯의 두 서버처럼 상태 코드 하나, 필드 이름 하나가 어긋나는 일이 흔하다.

    3. 오류도 계약이다: 무엇이 잘못됐는지 상태 코드와 본문으로 알린다¶

    • 4xx 안에서도 까닭을 가른다. 본문을 읽을 수 없으면 400, 자원이 없으면 404, 값이 규칙에 어긋나면 422, 지금 상태와 부딪치면 409다.
    • 오류 본문의 모양도 정해 둔다. RFC 9457의 문제 상세(type, title, status, detail 등)처럼 한 모양으로 보내면 클라이언트가 모든 오류를 한 방법으로 다룬다. 이 항목처럼 type을 빼면 title에는 상태 코드의 이름(Not Found 등)을 쓰고, 자세한 까닭은 detail에 쓴다.
    • 이미 쓰는 명세를 바꿀 때는 옛 클라이언트를 생각한다. 필드를 더하는 것은 대개 괜찮지만, 이름을 바꾸거나 지우면 옛 클라이언트가 깨진다(문제 2). 그럴 때는 새 필드를 더해 한동안 함께 보내거나, 주소에 판을 붙인다(/v2/todos).

    예측해 보기¶

    문제 1. 응답을 못 받은 클라이언트가 같은 요청을 한 번 더 보냈다. POST와 PUT을 흉내 낸 아래 코드에서 할 일은 모두 몇 개가 될까?

    const store = new Map();
let nextId = 1;
const api = {
  post(todo) { const id = nextId++; store.set(id, { id, ...todo }); },   // POST /todos: 새 할 일을 만든다
  put(id, todo) { store.set(id, { id, ...todo }); },                     // PUT /todos/{id}: 그 자리를 이 내용으로 바꾼다
};

api.post({ title: "우유 사기" });
api.post({ title: "우유 사기" });            // 응답을 못 받아 같은 요청을 다시 보냈다
api.put(7, { title: "빵 사기" });
api.put(7, { title: "빵 사기" });            // 응답을 못 받아 같은 요청을 다시 보냈다
console.log(store.size);
    정답과 해설

    3. POST는 보낼 때마다 새 할 일을 만들어 "우유 사기"가 둘이 되었다. PUT은 7번 자리를 같은 내용으로 두 번 바꾸었을 뿐이라 하나다. 그래서 PUT과 DELETE는 다시 보내도 되지만, POST를 다시 보내면 주문이 두 번 들어가는 일이 생긴다. 결제처럼 POST를 다시 보내야 하는 API는 요청마다 고유한 키를 함께 보내 서버가 같은 요청을 알아보게 한다(70번(분산 시스템의 근본 문제)).

    문제 2. 서버가 새 판에서 done을 completed로 이름만 바꿨다. 옛 클라이언트는 남은 할 일의 수를 센다. 바꾸기 전과 뒤에 무엇이 출력될까?

    const before = '[{"id":1,"title":"우유","done":true},{"id":2,"title":"빵","done":false},{"id":3,"title":"쌀","done":true}]';
const after = '[{"id":1,"title":"우유","completed":true},{"id":2,"title":"빵","completed":false},{"id":3,"title":"쌀","completed":true}]';
const left = text => JSON.parse(text).filter(t => !t.done).length;   // 옛 클라이언트: 남은 할 일 수
console.log(left(before), left(after));
    정답과 해설

    1 3. 바꾼 뒤에는 t.done이 없어서 undefined이고, !undefined는 true라 셋 모두 남은 할 일로 세었다. 오류는 나지 않는다. 필드 이름 하나가 클라이언트를 조용히 틀리게 만든다. 계약 테스트는 응답의 모양을 명세와 견주므로 이런 바뀜을 서버 쪽에서 먼저 잡는다(위젯의 "필드 이름을 바꾼 서버").

    문제 3. 클라이언트는 응답의 상태 코드(res.ok)를 보고 성공을 가른다. 한 서버는 없는 할 일에 200과 {"error": …}를, 다른 서버는 404와 문제 상세를 돌려준다. 무엇이 출력될까?

    async function showTodo(res) {                // res: fetch가 돌려준 응답
  if (!res.ok) return `오류 ${res.status}`;
  const todo = await res.json();
  return `제목: ${todo.title}`;
}

const reply = (status, body) => new Response(JSON.stringify(body), { status });
(async () => {
  console.log(await showTodo(reply(200, { error: "없는 할 일" })));                         // AI가 짠 서버
  console.log(await showTodo(reply(404, { title: "Not Found", status: 404, detail: "id 99인 할 일이 없다" })));  // 명세대로 짠 서버
})();
    정답과 해설 
    제목: undefined
오류 404

    200이면 res.ok가 true라 클라이언트는 성공으로 보고 본문을 할 일로 읽었다. 본문에 title이 없어 undefined를 보였다. 오류를 200으로 보내면 상태 코드를 보는 클라이언트, 기록 도구, 캐시가 모두 성공으로 안다. 실패는 4xx나 5xx로 보낸다.

    직접 해보기¶

    실습: 명세대로 할 일 API 짜기

    1. 아래 todo-api.js를 node todo-api.js로 실행한다. 명세(SPEC)의 요청 10개 가운데 GET /todos만 통과한다.
    2. 서버의 빈 곳을 채워 10개가 모두 통과하게 한다. 상태 코드와 응답 모양(Todo, Problem)은 명세를 그대로 따른다.
    3. 요구사항이 늘었다. "같은 제목의 할 일은 두 번 만들 수 없다(409)." 명세의 첫 POST 바로 다음에 시험 한 줄을 먼저 더해 실패하는 것을 보고, 서버를 고쳐 통과시킨다. 시험 줄은 앞 줄들이 남긴 서버의 상태를 이어서 쓴다.
    // todo-api.js: 할 일 API의 명세, 명세로 서버를 시험하는 코드, 그리고 서버
const http = require("node:http");

// ---- 명세: 무엇을 보내면 무엇이 오는가 ----
const Todo = { id: "number", title: "string", done: "boolean" };
const Problem = { title: "string", status: "number", detail: "string" };   // 오류 본문의 모양(RFC 9457). type을 빼면 title은 상태 코드의 이름이다
const SPEC = [
  // 메서드, 경로, 보낼 본문, 명세의 상태 코드, 명세의 응답 모양
  ["POST", "/todos", { title: "우유 사기" }, 201, Todo],
  ["POST", "/todos", { title: "" }, 422, Problem],
  ["POST", "/todos", "{제목", 400, Problem],
  ["GET", "/todos", null, 200, [Todo]],
  ["GET", "/todos/1", null, 200, Todo],
  ["GET", "/todos/99", null, 404, Problem],
  ["PATCH", "/todos/1", { done: "yes" }, 422, Problem],
  ["PATCH", "/todos/1", { done: true }, 200, Todo],
  ["DELETE", "/todos/1", null, 204, null],
  ["DELETE", "/todos/1", null, 404, Problem],
];

function matches(value, shape) {             // 값이 명세의 모양과 같은가
  if (shape === null) return value === null;
  if (Array.isArray(shape)) return Array.isArray(value) && value.every(v => matches(v, shape[0]));
  if (typeof shape === "string") return typeof value === shape;
  return value !== null && typeof value === "object" && Object.entries(shape).every(([k, s]) => matches(value[k], s));
}

async function contractTest(base) {          // 명세의 요청을 차례로 보내 상태 코드와 모양을 견준다
  for (const [method, path, body, status, shape] of SPEC) {
    const res = await fetch(base + path, {
      method, headers: { "Content-Type": "application/json" },
      body: body === null ? undefined : typeof body === "string" ? body : JSON.stringify(body),
    });
    const text = await res.text();
    let data;
    try { data = text === "" ? null : JSON.parse(text); } catch { data = undefined; }
    const ok = res.status === status && matches(data, shape);
    console.log(`${ok ? "통과" : "실패"} ${method} ${path} → ${res.status}${ok ? "" : ` (명세는 ${status})`}`);
  }
}

// ---- 서버 ----
const todos = new Map();                     // id → { id, title, done }
let nextId = 1;

function send(res, status, data, headers = {}) {
  if (data === null) { res.writeHead(status, headers); return res.end(); }
  const type = status >= 400 ? "application/problem+json" : "application/json";
  res.writeHead(status, { "Content-Type": `${type}; charset=utf-8`, ...headers });
  res.end(JSON.stringify(data));
}
const problem = (res, status, title, detail) => send(res, status, { title, status, detail });

async function readJson(req) {
  req.setEncoding("utf8");                  // 조각의 경계에 걸린 한글이 깨지지 않게 글자로 받는다
  let text = "";
  for await (const chunk of req) text += chunk;
  return JSON.parse(text);                   // JSON이 아니면 SyntaxError
}

const server = http.createServer(async (req, res) => {
  if (req.method === "GET" && req.url === "/todos") return send(res, 200, [...todos.values()]);
  // 여기를 채운다: POST /todos, GET·PATCH·DELETE /todos/{id}, 그리고 명세의 오류들
  return problem(res, 501, "Not Implemented", `아직 만들지 않았다: ${req.method} ${req.url}`);
});

server.listen(0, "127.0.0.1", async () => {  // 0번은 빈 포트를 아무거나 쓴다
  await contractTest(`http://127.0.0.1:${server.address().port}`);
  server.close();
});

    3까지 마친 한 예다. 명세에 한 줄을 더했고, 서버는 3절 그림의 차례(400, 404, 422, 409)로 오류를 가른다.

    // todo-api.js: 할 일 API의 명세, 명세로 서버를 시험하는 코드, 그리고 서버
const http = require("node:http");

// ---- 명세: 무엇을 보내면 무엇이 오는가 ----
const Todo = { id: "number", title: "string", done: "boolean" };
const Problem = { title: "string", status: "number", detail: "string" };   // 오류 본문의 모양(RFC 9457). type을 빼면 title은 상태 코드의 이름이다
const SPEC = [
  // 메서드, 경로, 보낼 본문, 명세의 상태 코드, 명세의 응답 모양
  ["POST", "/todos", { title: "우유 사기" }, 201, Todo],
  ["POST", "/todos", { title: "우유 사기" }, 409, Problem],     // 3에서 더한 줄: 같은 제목은 두 번 만들 수 없다
  ["POST", "/todos", { title: "" }, 422, Problem],
  ["POST", "/todos", "{제목", 400, Problem],
  ["GET", "/todos", null, 200, [Todo]],
  ["GET", "/todos/1", null, 200, Todo],
  ["GET", "/todos/99", null, 404, Problem],
  ["PATCH", "/todos/1", { done: "yes" }, 422, Problem],
  ["PATCH", "/todos/1", { done: true }, 200, Todo],
  ["DELETE", "/todos/1", null, 204, null],
  ["DELETE", "/todos/1", null, 404, Problem],
];

const todos = new Map();                     // id → { id, title, done }

function send(res, status, data, headers = {}) {

const problem = (res, status, title, detail) => send(res, status, { title, status, detail });

async function readJson(req) {
  req.setEncoding("utf8");                  // 조각의 경계에 걸린 한글이 깨지지 않게 글자로 받는다
  let text = "";
  for await (const chunk of req) text += chunk;
  return JSON.parse(text);                   // JSON이 아니면 SyntaxError
}

const server = http.createServer(async (req, res) => {
  const m = req.url.match(/^\/todos(?:\/(\d+))?$/);
  if (!m) return problem(res, 404, "Not Found", `없는 주소: ${req.url}`);
  let body = null;
  if (req.method === "POST" || req.method === "PATCH") {
    try { body = await readJson(req); } catch { return problem(res, 400, "Bad Request", "본문을 JSON으로 읽지 못했다"); }
  }
  if (m[1] === undefined) {                  // /todos: 할 일 전체
    if (req.method === "GET") return send(res, 200, [...todos.values()]);
    if (req.method === "POST") {
      const title = body && body.title;
      if (typeof title !== "string" || title.length < 1 || title.length > 100) return problem(res, 422, "Unprocessable Content", "title은 1~100자의 문자열이다");
      if ([...todos.values()].some(t => t.title === title)) return problem(res, 409, "Conflict", `같은 제목이 이미 있다: ${title}`);
      const todo = { id: nextId++, title, done: false };
      todos.set(todo.id, todo);
      return send(res, 201, todo, { Location: `/todos/${todo.id}` });
    }
    return send(res, 405, null, { Allow: "GET, POST" });
  }
  const todo = todos.get(Number(m[1]));      // /todos/{id}: 할 일 하나
  if (!todo) return problem(res, 404, "Not Found", `id ${m[1]}인 할 일이 없다`);
  if (req.method === "GET") return send(res, 200, todo);
  if (req.method === "PATCH") {               // 이 명세의 PATCH는 done만 바꾼다
    if (typeof body?.done !== "boolean") return problem(res, 422, "Unprocessable Content", "done은 true나 false다");
    todo.done = body.done;
    return send(res, 200, todo);
  }
  if (req.method === "DELETE") { todos.delete(todo.id); return send(res, 204, null); }
  return send(res, 405, null, { Allow: "GET, PATCH, DELETE" });
});

server.listen(0, "127.0.0.1", async () => {  // 0번은 빈 포트를 아무거나 쓴다
  await contractTest(`http://127.0.0.1:${server.address().port}`);
  server.close();
});

    • PATCH에 {"done": "yes"}를 보내면 JSON 자체는 맞으므로 400이 아니라 422다. 무엇이 잘못됐는지에 따라 코드를 가르면 클라이언트가 고칠 곳을 안다.
    • 같은 DELETE를 두 번 보내면 둘째는 404다. 응답 코드는 달라도 "그 할 일이 없는 상태"라는 결과는 같으므로 DELETE는 멱등이다.

    AI와 함께 확인하기¶

    AI 활용 과제: AI가 짠 서버를 명세로 받아들이기

    1. 실습의 명세(Todo, Problem, SPEC)를 AI에게 주고 "이 명세대로 Node의 http 모듈로 서버를 짜 줘. 외부 패키지는 쓰지 않는다"라고 한다.
    2. 받은 서버를 실습 파일의 서버 자리에 넣고 계약 테스트를 돌린다.
    3. 실패한 줄을 AI에게 그대로 보여 주고 고치게 한다. 모두 통과할 때까지 되풀이하고, 무엇이 어긋났는지 적는다.
    확인할 점
    • 명세에 적힌 것을 다르게 정한 곳을 찾는다. 201 대신 200, 빈 제목을 받아 줌, 틀린 JSON에 400 대신 500, 없는 자원에 200과 {"error"}가 흔하다(위젯의 "AI가 처음 짠 서버"). 틀린 JSON의 예외를 아무도 잡지 않으면 node:http 서버는 500도 보내지 못하고 프로세스가 끝나, 계약 테스트도 중간에 멈춘다.
    • 계약 테스트는 명세에 적은 것만 확인한다. 101자 제목, 명세에 없는 메서드(405), 201의 Location 머리, 오류의 Content-Type처럼 시험에 없는 것은 틀려도 모른다. 놓친 경우를 찾으면 명세와 시험에 더한다.
    • 시험이 실패할 때 AI가 시험이나 명세를 고쳐 통과시키지 않게 한다. 계약은 사람이 정하고, 서버가 계약에 맞춘다.

    PUT과 PATCH

    GET처럼 서버의 상태를 바꾸지 않는 메서드를 안전한(safe) 메서드라 한다. 안전한 메서드는 모두 멱등이지만, PUT과 DELETE는 멱등이어도 상태를 바꾸므로 안전하지 않다. PUT은 그 자원을 보낸 내용으로 통째로 바꾼다. 보내지 않은 필드는 사라진다. 일부만 바꾸려면 PATCH를 쓴다. 같은 PATCH를 두 번 보내도 결과가 같을 수도 있지만({"done": true}), "1 늘리기"처럼 보낼 때마다 결과가 달라지는 PATCH도 만들 수 있어서 HTTP 표준은 PATCH를 멱등이라고 정하지 않는다.

    정리¶

    • 주소에는 자원을, 동작은 메서드로, 결과는 상태 코드로 말한다. GET, PUT, DELETE는 다시 보내도 결과가 같고 POST는 아니다.
    • 무엇을 보내고 무엇을 받는지, 오류에는 어떤 코드와 본문을 보내는지를 명세로 먼저 정한다. 서버는 명세로 시험해(계약 테스트) 받아들인다.
    • 필드 이름 하나, 상태 코드 하나가 클라이언트를 조용히 틀리게 만든다. 이미 쓰는 명세는 옛 클라이언트가 깨지지 않게 바꾼다.
