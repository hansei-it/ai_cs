    61. 브라우저 렌더링 경로(Critical Rendering Path)와 Virtual DOM의 탄생 배경¶

    원리 동작을 예측하고 이상을 알아챌 수 있어야 하는 항목

    브라우저는 받은 HTML과 CSS로 화면을 그린 뒤에도, 자바스크립트가 DOM을 고칠 때마다 다시 그린다. 무엇을 고치느냐에 따라 다시 하는 일의 양이 크게 다르고, 코드의 차례 하나로 100배 가까이 느려지기도 한다. 이 항목은 화면을 그리는 단계를 보고, DOM을 고칠 때 드는 비용을 이 PC의 Chrome에서 잰 뒤, 그 비용을 줄이려고 나온 가상 DOM(Virtual DOM)의 생각을 본다. HTML을 받아 읽는 동안의 일은 44번(URL 입력부터 렌더링까지)에서 다뤘다.

    이 항목에서 배우는 것¶

    • DOM과 CSSOM에서 스타일 계산, 레이아웃, 페인트, 합성을 거쳐 화면이 되는 차례를 설명할 수 있다.
    • 무엇을 바꾸면 어느 단계부터 다시 하는지, 읽기와 쓰기를 섞으면 왜 느려지는지 예측할 수 있다.
    • 가상 DOM이 해결하려는 문제와 그 비용을 설명할 수 있다.

    1. DOM과 CSSOM을 합쳐 배치를 재고, 칠하고, 겹쳐서 화면을 만든다¶

    • 브라우저는 HTML을 DOM 트리로, CSS를 CSSOM으로 읽는다. 둘을 합쳐 요소마다 스타일을 정하고(스타일 계산), 위치와 크기를 재고(레이아웃), 픽셀을 칠하고(페인트), 층을 겹쳐 화면에 낸다(합성). 처음 화면을 그리기까지 꼭 거치는 이 차례를 렌더링 경로(Critical Rendering Path)라 한다.
    • DOM이나 스타일을 고치면 이 단계를 다시 한다. 크기가 바뀌면 레이아웃부터, 색만 바뀌면 페인트부터 다시 한다. 이미 걸린 transform이나 opacity(1보다 작은 값)의 값을 바꾸면 레이아웃과 페인트를 건너뛰어 가장 싸다. 처음 걸 때는 다시 하므로, 움직일 요소에는 미리 걸어 두거나 will-change로 알린다. 움직이는 효과는 left 대신 transform으로 만든다.
    • 다시 그리는 일은 코드(태스크)가 끝난 뒤, 다음 화면을 그릴 차례(보통 1초에 60번)가 오면 한 번 한다(60번(이벤트 루프와 비동기)). 한 태스크 안에서 여러 번 고치면 무엇이 그려질지는 문제 1에서 본다.

    2. 읽기와 쓰기를 번갈아 하면 레이아웃을 몇 번이고 다시 한다¶

    직접 해 보기읽기와 쓰기가 부르는 레이아웃상자 수와 코드의 모양(번갈아 읽고 쓰기, 모아서, style 읽기)을 골라, 어느 읽기에서 브라우저가 레이아웃을 다시 계산해야 하는지와 그 횟수를 본다
    새 창에서 크게 열기
    • 크기를 바꾼(쓴) 뒤에 offsetWidth처럼 레이아웃이 필요한 값을 읽으면, 브라우저는 다음 화면을 기다리지 못하고 그 자리에서 레이아웃을 다시 한다(강제 레이아웃).
    • 상자마다 읽고 쓰기를 번갈아 하면 상자 수만큼 레이아웃을 한다. 이 PC의 Chrome에서 상자 1,000개를 이렇게 하니 188~219ms, 모두 읽은 뒤 모두 쓰니 2.1~2.4ms였다.
    • 코드가 짧아도 이런 차례가 반복문이나 여러 함수에 흩어져 있으면 알아채기 어렵다. 개발자 도구의 성능(Performance) 탭에서 레이아웃이 몇 번 되풀이되는지 본다(직접 해보기).

    3. 가상 DOM은 새 화면을 값으로 만들어 견주고, 다른 곳만 고친다¶

    • 화면이 복잡해지면 "무엇이 바뀌었으니 DOM의 어디를 고친다"를 손으로 맞추기 어렵다. 그렇다고 상태가 바뀔 때마다 innerHTML로 통째로 다시 만들면 느리다. 그때 사용자가 입력하던 값은 어떻게 될까(문제 2).
    • 가상 DOM은 화면을 자바스크립트 값으로 먼저 만든다. 상태가 바뀌면 새 화면 값을 통째로 다시 만들되, 앞의 값과 견주어 다른 곳만 실제 DOM에 고친다. React가 이 방법을 널리 퍼뜨렸다.
    • 견주는 일도 비용이라, 바뀐 곳을 직접 고치는 것보다 빠르지는 않다. 대신 "상태에 맞는 화면 전체"만 쓰면 되어 코드가 단순해진다. 목록을 견줄 때는 항목마다 키를 주어야 엉뚱한 곳을 고치지 않는다(문제 3).

    예측해 보기¶

    문제 1. 한 태스크 안에서 글자를 세 번 바꾼다. 다음 화면을 그리기 직전(requestAnimationFrame)에 글자는 무엇이고, 무엇이 먼저 찍힐까?

    <p id="msg">처음</p>

    const msg = document.getElementById("msg");
requestAnimationFrame(() => console.log("그리기 직전:", msg.textContent));
msg.textContent = "하나";
msg.textContent = "둘";
msg.textContent = "셋";
console.log("코드 끝");
    정답과 해설 
    코드 끝
그리기 직전: 셋

    브라우저는 코드(태스크)가 끝난 뒤에 화면을 그린다. requestAnimationFrame의 콜백은 그리기 직전에 돌고, 그때 글자는 이미 "셋"이다. "하나"와 "둘"은 화면에 한 번도 그려지지 않는다. 진행 상황을 보여 주려고 긴 반복문 안에서 글자를 바꿔도 화면은 반복문이 끝날 때까지 그대로인 까닭이다. 이 PC의 Chrome에서 확인했다.

    문제 2. 사용자가 입력칸에 이름을 넣었다. 문단의 글자를 바꾸려고 innerHTML로 통째로 다시 만들었다. 무엇이 출력될까?

    <div id="app"><input id="name"><p>안녕</p></div>

    const input = document.getElementById("name");
input.value = "김하나";                              // 사용자가 입력했다고 하자
const app = document.getElementById("app");
app.innerHTML = app.innerHTML.replace("안녕", "반갑다");
console.log(document.getElementById("name").value === "", input.isConnected);
    정답과 해설

    true false. innerHTML로 다시 만들면 안의 요소가 모두 새것이 된다. 입력한 값은 요소의 속성(attribute)이 아니라 그 요소 객체가 들고 있던 것이라, 글로 바꿨다 다시 만드는 사이에 사라졌다. 옛 입력칸은 문서에서 떨어져 나갔고(isConnected가 false), 포커스와 스크롤 위치도 함께 잃는다. 바뀐 곳만 고치면 이런 일이 없다(3절 그림).

    문제 3. 목록 둘을 자리끼리 견주어(키 없이) 바꿀 곳을 세는 함수다. 끝에 하나를 더할 때와 맨 앞에 하나를 더할 때, 고칠 곳은 각각 몇 개일까?

    function diffByIndex(before, after) {      // 자리끼리 견준다(키 없음)
  const ops = [];
  for (let i = 0; i < Math.max(before.length, after.length); i++) {
    if (before[i] === undefined) ops.push(`넣기 ${after[i]}`);
    else if (after[i] === undefined) ops.push(`지우기 ${before[i]}`);
    else if (before[i] !== after[i]) ops.push(`바꾸기 ${before[i]}→${after[i]}`);
  }
  return ops;
}

console.log(diffByIndex(["우유", "빵", "쌀"], ["우유", "빵", "쌀", "달걀"]).length);
console.log(diffByIndex(["우유", "빵", "쌀"], ["달걀", "우유", "빵", "쌀"]).length);
    정답과 해설 
    1
4

    맨 앞에 넣으면 모든 자리의 글자가 한 칸씩 밀려 "바꾸기"가 셋, "넣기"가 하나다. 실제로는 하나를 넣었을 뿐인데 모든 줄을 고친다. 줄의 요소는 제자리에 남고 글자만 밀리므로, 줄에 붙어 있던 상태(입력칸의 값, 체크 표시)가 엉뚱한 항목에 붙는다. 그래서 React 같은 라이브러리는 목록의 항목마다 바뀌지 않는 키(예: 할 일의 id)를 달게 하고, 키로 같은 항목을 찾아 견준다. 그러면 맨 앞에 하나를 넣는 일 하나로 끝난다.

    직접 해보기¶

    실습: 개발자 도구로 레이아웃 되풀이를 찾고 고치기

    1. "더 알아보기"의 측정 페이지를 measure.html로 저장하고, Chrome에서 주소 끝에 ?test=interleave를 붙여 연다(예: file:///C:/실습/measure.html?test=interleave). 개발자 도구의 콘솔에서 걸린 시간을 적는다.
    2. 개발자 도구의 성능 탭에서 녹화를 시작하고 페이지를 새로 고친 뒤 중지한다. 한 작업 안에서 레이아웃(Layout)이 몇 번 되풀이되는지 찾는다.
    3. ?test=batch로 바꿔 같은 일을 한다. 두 코드(TESTS.interleave, TESTS.batch)를 견주어 무엇이 달라 빨라졌는지 적는다.
    4. ?test=innerHTML, ?test=vdom, ?test=direct도 열어 시간과 입력칸에 남은 글자를 견준다.
    확인할 점
    • 이 PC의 Chrome에서 15번 열어 보니 interleave 188~219ms(맨 처음 한 번은 285ms), batch 2.1~2.4ms였다. interleave는 상자마다 쓴 뒤 바로 다음 상자의 너비를 읽어, 읽을 때마다 레이아웃을 다시 했다(1,000번). batch는 모두 읽은 뒤 모두 써서 레이아웃이 한 번이다.
    • innerHTML 10.7~11.6ms(입력칸이 비고 포커스를 잃음), vdom 0.7~1.0ms, direct 0.5~0.6ms였다. 견주는 일이 더해진 vdom이 direct보다 빠르지는 않다.
    • 읽기와 쓰기를 떼어 놓기 어려우면, 쓰기를 requestAnimationFrame 안으로 미뤄 다음 화면 직전에 몰아서 한다.

    AI와 함께 확인하기¶

    AI 활용 과제: AI가 만든 화면 갱신 코드에서 레이아웃 되풀이 찾기

    1. AI에게 "카드 100장의 높이를 가장 높은 카드에 맞추는 자바스크립트 함수를 짜 줘. 창 크기가 바뀔 때마다 부른다"라고 한다.
    2. 받은 코드에서 레이아웃이 필요한 값을 읽는 곳(offsetHeight, getBoundingClientRect)과 스타일을 쓰는 곳을 표시하고, 반복문 안에서 둘이 번갈아 나오는지 본다.
    3. 번갈아 나오면 읽기를 먼저 다 하고 쓰기를 나중에 하게 고치게 하고, 성능 탭에서 레이아웃 횟수를 견준다.
    확인할 점
    • 카드마다 높이를 auto로 되돌리고(쓰기) 바로 offsetHeight를 읽는 코드가 흔하다. 카드 수만큼 레이아웃을 한다. 모두 되돌리기, 모두 읽기, 모두 쓰기의 세 단계로 나누면 강제 레이아웃은 한 번이다.
    • 더 좋은 답은 자바스크립트를 쓰지 않는 것이다. CSS grid의 grid-auto-rows: 1fr처럼 모든 줄의 높이를 가장 높은 줄에 맞추면 브라우저가 레이아웃 한 번에 처리한다(flex는 한 줄 안에서만 높이를 맞춘다). AI에게 "CSS만으로 할 수 있나"를 물어본다.
    • 창 크기가 바뀔 때 부르는 함수는 짧은 사이에 수십 번 불린다. 그 안에서 레이아웃을 되풀이하면 창을 움직일 때 화면이 끊긴다.

    더 알아보기¶

    가상 DOM 없이 바뀔 곳을 미리 정하는 방법

    가상 DOM은 실행할 때마다 새 화면 값을 만들고 견준다. Svelte 같은 도구는 컴파일할 때 "이 값이 바뀌면 DOM의 이곳을 고친다"를 미리 정해 두어, 실행할 때 견주는 일을 하지 않는다. 어느 쪽이든 목표는 같다. 개발자는 상태에 맞는 화면을 쓰고, 도구가 DOM을 바꿀 최소의 일을 찾는다.

    이 항목의 측정 페이지

    1절 그림과 2절의 레이아웃 횟수는 맨 아래의 stages.mjs로 센 것이다(3번 모두 같았다). 시간은 이 PC(Core i9-14900KF, DDR5 64GB, Windows 11, Chrome 155)의 헤드리스 Chrome으로 아래 페이지를 방법마다 새로 열어 15번 잰 범위다(맨 처음 한 번처럼 크게 벗어난 값은 따로 적었다). 첫 화면을 다 그린 뒤 한 번만 재고, 레이아웃까지 끝내도록 마지막에 document.body.offsetHeight를 읽는다.

const TESTS = {
  interleave() {                             // 상자마다 읽고 바로 쓴다
    for (const b of document.querySelectorAll(".box")) { const w = b.offsetWidth; b.style.width = (w + 1) + "px"; }
  },
  batch() {                                  // 모두 읽은 뒤 모두 쓴다
    const boxes = [...document.querySelectorAll(".box")];
    const ws = boxes.map(b => b.offsetWidth);
    boxes.forEach((b, i) => { b.style.width = (ws[i] + 1) + "px"; });
  },
  innerHTML() {                              // 한 줄을 바꾸려고 통째로 다시 만든다
    const items = Array.from({ length: N }, (_, i) => i === 500 ? "할 일 500 (끝남)" : `할 일 ${i}`);
    document.getElementById("app").innerHTML = '<input id="q"><ul id="list">' + items.map(s => `<li>${s}</li>`).join("") + "</ul>";
  },
  vdom() {                                   // 앞뒤 목록을 값으로 견주고 다른 줄만 고친다
    const before = Array.from({ length: N }, (_, i) => `할 일 ${i}`);
    const after = before.map((s, i) => i === 500 ? "할 일 500 (끝남)" : s);
    const lis = document.getElementById("list").children;
    for (let i = 0; i < after.length; i++) if (after[i] !== before[i]) lis[i].textContent = after[i];
  },
  direct() {                                 // 바뀐 줄을 직접 고친다
    document.getElementById("list").children[500].textContent = "할 일 500 (끝남)";
  },
};
const q = document.getElementById("q");
q.value = "김하나";                            // 사용자가 입력하던 중이라고 하자
q.focus();
requestAnimationFrame(() => requestAnimationFrame(() => {   // 첫 화면을 다 그린 뒤
  const name = new URLSearchParams(location.search).get("test");
  const t = performance.now();
  TESTS[name]();
  document.body.offsetHeight;                 // 스타일과 레이아웃까지 끝내게 한다
  const ms = performance.now() - t;
  const q2 = document.getElementById("q");

    stages.mjs는 헤드리스 Chrome을 띄워 개발자 도구 프로토콜로 몰고, 값 하나를 바꾼 뒤 다음 화면까지의 trace에서 Layout과 Paint 기록을 센다. 2절은 Performance.getMetrics의 LayoutCount로 센다. node stages.mjs로 실행한다.

    // stages.mjs: 61번 1절 그림과 2절의 횟수를 센다. 헤드리스 Chrome에서 값 하나를 바꾸고, 다음 화면까지 Layout과 Paint 기록을 센다
// 실행: node stages.mjs  (Chrome이 다른 곳에 깔려 있으면 CHROME을 고친다)
import { spawn } from "node:child_process";
import { mkdtempSync } from "node:fs";
import { tmpdir } from "node:os";
import { join } from "node:path";

const CHROME = "C:/Program Files/Google/Chrome/Application/chrome.exe";
const PORT = 9333;
const chrome = spawn(CHROME, ["--headless=new", `--remote-debugging-port=${PORT}`, `--user-data-dir=${mkdtempSync(join(tmpdir(), "cs61-"))}`, "about:blank"]);
const sleep = ms => new Promise(r => setTimeout(r, ms));
let target;
while (!target) {
  try { target = (await (await fetch(`http://127.0.0.1:${PORT}/json/list`)).json()).find(t => t.type === "page"); } catch { await sleep(200); }
}
const ws = new WebSocket(target.webSocketDebuggerUrl);
await new Promise(r => ws.addEventListener("open", r, { once: true }));
let seq = 0;
const waiting = new Map(), events = [], on = {};
ws.addEventListener("message", ev => {
  const m = JSON.parse(ev.data);
  if (m.id) return waiting.get(m.id)(m.result);
  if (m.method === "Tracing.dataCollected") events.push(...m.params.value);
  on[m.method]?.();
});
const send = (method, params = {}) => new Promise(r => { waiting.set(++seq, r); ws.send(JSON.stringify({ id: seq, method, params })); });
const run = async code => (await send("Runtime.evaluate", { expression: code, awaitPromise: true })).result;
const NEXT_FRAME = "new Promise(r => requestAnimationFrame(() => requestAnimationFrame(r)))";
const layoutCount = async () => (await send("Performance.getMetrics")).metrics.find(m => m.name === "LayoutCount").value;
await send("Page.enable"); await send("Performance.enable");

async function open(css, body) {                 // 페이지를 열고 첫 화면을 다 그릴 때까지 기다린다
  const loaded = new Promise(r => { on["Page.loadEventFired"] = r; });
  await send("Page.navigate", { url: "data:text/html;charset=utf-8," + encodeURIComponent(`<style>${css}</style>${body}`) });
  await loaded;
  await run(NEXT_FRAME);
}

// 1절: 값 하나를 바꾸고 다음 화면까지 Layout과 Paint가 몇 번 있었나
const BOX = "#box { width: 100px; height: 100px; background: #36c; }";
const CASES = [
  ["width를 바꿨다", "", "box.style.width = '150px'"],
  ["background-color를 바꿨다", "", "box.style.background = '#c63'"],
  ["이미 있는 transform 값을 바꿨다", "#box { transform: translateX(10px); }", "box.style.transform = 'translateX(50px)'"],
  ["1보다 작은 opacity 값을 바꿨다", "#box { opacity: 0.9; }", "box.style.opacity = '0.5'"],
  ["transform을 처음 붙였다", "", "box.style.transform = 'translateX(50px)'"],
  ["opacity를 1에서 처음 내렸다", "", "box.style.opacity = '0.5'"],
  ["will-change를 준 요소에 transform을 처음 붙였다", "#box { will-change: transform; }", "box.style.transform = 'translateX(50px)'"],
];
for (const [name, css, code] of CASES) {
  await open(BOX + css, '<div id="box"></div><p>글자</p>');
  events.length = 0;
  const done = new Promise(r => { on["Tracing.tracingComplete"] = r; });
  await send("Tracing.start", { categories: "devtools.timeline", transferMode: "ReportEvents" });
  await run(`const box = document.getElementById("box"); ${code}; ${NEXT_FRAME}`);
  await send("Tracing.end");
  await done;
  const count = n => events.filter(e => e.name === n && (e.ph === "X" || e.ph === "B")).length;
  console.log(`${name}: Layout ${count("Layout")}, Paint ${count("Paint")}`);
}

// 2절: 상자 N개의 너비를 읽고 쓸 때, 다음 화면까지 레이아웃을 몇 번 했나
const CODE = {
  interleave: `for (const b of document.querySelectorAll(".box")) { const w = b.offsetWidth; b.style.width = (w + 1) + "px"; }`,
  batch: `{ const bs = [...document.querySelectorAll(".box")]; const ws = bs.map(b => b.offsetWidth); bs.forEach((b, i) => { b.style.width = (ws[i] + 1) + "px"; }); }`,
};
for (const n of [5, 1000]) {
  for (const [name, code] of Object.entries(CODE)) {
    await open(".box { width: 100px; height: 4px; margin: 1px; background: #36c; }", '<div class="box"></div>'.repeat(n));
    const before = await layoutCount();
    await run(`${code}; ${NEXT_FRAME}`);
    console.log(`상자 ${n}개 ${name}: 레이아웃 ${(await layoutCount()) - before}번`);

}

    정리¶

    • 화면은 DOM과 CSSOM에서 스타일 계산, 레이아웃, 페인트, 합성을 거쳐 나온다. 크기를 바꾸면 레이아웃부터, 색은 페인트부터 다시 하고, 이미 걸린 transform과 opacity의 값을 바꾸면 합성만 다시 한다.
    • 쓴 뒤에 레이아웃이 필요한 값을 읽으면 그 자리에서 레이아웃을 다시 한다. 읽기를 모으고 쓰기를 모으면 100배 가까이 빨라진다.
    • 가상 DOM은 새 화면을 값으로 만들어 견주고 다른 곳만 고친다. 통째로 다시 만드는 것보다 빠르고 사용자의 상태를 지키지만, 바뀐 곳을 직접 고치는 것보다 빠르지는 않다.
