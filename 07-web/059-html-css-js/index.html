    59. 웹의 기본 구성: HTML(구조), CSS(스타일), JavaScript(동작)의 상호작용¶

    위임 AI에 맡기고 실행·테스트로 확인하면 되는 항목

    웹 화면 하나는 세 언어가 함께 만든다. HTML은 무엇이 있는지, CSS는 어떻게 보이는지, JavaScript는 어떻게 움직이는지를 맡는다. 위임형 항목이므로 화면을 만드는 코드는 AI에게 맡기되, 브라우저에서 실행하고 개발자 도구로 확인해 받아들인다. 이 항목은 그 확인에 필요한 만큼만 세 언어가 만나는 원리를 보고, AI가 만든 페이지를 점검하는 방법을 익힌다. 예제는 Chrome의 개발자 도구에서 실행한다(실습 환경).

    이 항목에서 배우는 것¶

    • HTML, CSS, JavaScript가 맡는 일과, 셋이 DOM에서 만나는 방식을 설명할 수 있다.
    • CSS 규칙이 겹칠 때 무엇이 이기는지, 이벤트가 어느 요소로 전해지는지 개발자 도구로 확인할 수 있다.
    • AI가 만든 페이지를 실행해 구조, 키보드 사용, 사용자 입력의 처리를 점검하고 그 결과를 기록할 수 있다.

    1. HTML은 DOM 트리가 되고, CSS는 모양을, JavaScript는 동작을 붙인다¶

    • 브라우저는 HTML을 읽어 DOM 트리를 만든다. CSS 규칙은 선택자로 요소를 골라 모양을 정하고, JavaScript는 DOM을 고치며 이벤트에 답한다. 셋은 DOM 하나에서 만난다.
    • HTML은 모양이 아니라 뜻을 적는다. 누르는 것은 <button>, 입력칸은 <label>과 함께 쓴다. <div>를 CSS로 단추처럼 꾸며 클릭을 걸면 화면에서는 같아 보여도 Tab 키로 갈 수 없다(이 PC의 Chrome에서 <div>의 tabIndex는 -1, <button>은 0이었다).
    • 개발자 도구(F12)의 요소(Elements) 탭은 지금의 DOM과 요소에 걸린 CSS 규칙을, 콘솔 탭은 오류를 보여 준다. AI가 만든 페이지는 여기서 확인한다.

    2. CSS 규칙이 겹치면 더 구체적인 선택자가, 같으면 나중 것이 이긴다¶

    직접 해 보기겹친 CSS 규칙 가운데 무엇이 이기나같은 단추에 걸린 CSS 규칙 다섯을 켜고 끄며, 단추의 글자색을 정하는 규칙이 어느 것인지와 그 까닭(명시도, 나중에 쓴 것)을 본다
    새 창에서 크게 열기
    • 한 요소에 같은 속성을 정하는 규칙이 여럿이면, 선택자의 명시도가 높은 것이 이긴다. id가 class보다, class가 태그 이름보다 세다. 명시도가 같으면 나중에 쓴 규칙이 이긴다.
    • AI에게 "색을 바꿔 줘"라고 해서 받은 규칙이 듣지 않으면 개발자 도구의 스타일(Styles) 칸을 본다. 그 선언에 줄이 그어져 있으면 더 센 규칙에 진 것이고, 규칙이 아예 없으면 선택자가 그 요소를 고르지 못한 것이다.
    • !important로 이기게 할 수는 있지만, 그러면 그 규칙을 다시 이길 방법이 줄어든다. 선택자를 정리하는 쪽으로 고친다.

    3. 이벤트는 누른 요소에서 시작해 조상으로 올라간다¶

    • 단추를 누르면 그 클릭은 단추의 조상(목록, 문서)에게도 차례로 전해진다(버블링). 그래서 목록에 처리 함수를 하나만 걸어 두어도 안의 모든 단추를 받는다(이벤트 위임). 나중에 더한 항목도 따로 걸 필요가 없다.
    • 사용자가 넣은 글을 화면에 보일 때는 textContent로 넣는다. innerHTML로 넣으면 무엇이 달라지는지는 문제 3에서 본다.
    • AI가 만든 코드에서 innerHTML +=로 목록을 늘리는 곳, 요소마다 onclick을 다는 곳을 찾는다. 위임과 textContent로 바꾼다.

    문제 3. 사용자가 이름 칸에 아래 글을 넣었다. 한 번은 textContent로, 한 번은 innerHTML로 화면에 넣는다. 무엇이 찍힐까?

    <p id="out"></p>

    const name = '<img src="x" onerror="console.log(\'스크립트가 돌았다\')">김하나';   // 사용자가 이름 칸에 넣은 글

    0 true
1 김하나
스크립트가 돌았다

    textContent는 글을 글자 그대로 넣어 요소가 생기지 않았다. innerHTML은 글을 HTML로 읽어 <img> 요소를 만들었고, 그림을 불러오지 못하자 onerror에 적힌 코드가 돌았다. 사용자가 넣은 글로 남의 화면에서 스크립트를 돌리는 공격(XSS)이 이렇게 된다(74번(웹 취약점과 방어)). 사용자가 넣은 글은 textContent로 넣는다. 그림 불러오기는 나중에 끝나므로 onerror는 동기 코드의 출력이 다 나온 뒤에 돌았다(60번(이벤트 루프와 비동기)). innerHTML로 넣은 <script> 요소는 돌지 않지만, onerror 같은 속성에 적은 코드는 돈다. 이 PC의 Chrome에서 확인했다.

    AI와 함께 확인하기¶

    AI 활용 과제: 내 요구사항으로 페이지를 맡기고 받아들이기

    1. 만들 페이지(예: 동아리 가입 신청서)의 요구사항을 다섯 줄 안팎으로 적고, AI에게 "HTML 파일 하나로, 외부 라이브러리 없이" 만들게 한다.
    2. 받기 전에 확인할 것을 정한다. 요구사항마다 어떻게 해 보면 되는지 한 줄씩, 그리고 실습의 점검(키보드, 사용자 입력, 이름표, 좁은 화면, 콘솔 오류)을 넣는다.
    3. 하나씩 해 보고 결과를 표로 적는다. 어긋난 것은 AI에게 보여 주고 고치게 한 뒤 다시 해 본다.
    확인할 점
    • 요구사항을 그대로 옮긴 확인 항목만으로는 부족하다. AI는 요구에 적지 않은 것(키보드로 쓰기, 사용자 글의 처리, 좁은 화면)을 대개 빠뜨린다. 이 항목의 점검을 늘 함께 한다.
    • "됐다"는 AI의 말이 아니라, 내가 해 본 결과로 받아들인다. 고친 뒤에는 앞에서 통과한 항목도 다시 해 본다. 한 곳을 고치며 다른 곳이 깨지는 일이 흔하다.
    • 보낼 데이터가 있으면 서버와 주고받는 모양(JSON)과 오류 처리를 확인한다(63번(JSON과 직렬화), 64번(REST API 설계)).

    더 알아보기¶

    개발자 도구에서 자주 쓰는 곳

    요소 탭에서 요소를 고르면 오른쪽 스타일 칸에 그 요소에 걸린 규칙이 이기는 차례로 보이고, 진 선언에는 줄이 그어져 있다. 콘솔 탭의 붉은 줄은 오류다. 요소를 고른 뒤 콘솔에서 $0이라고 치면 그 요소를 자바스크립트로 다룰 수 있다. 기기 툴바(Ctrl+Shift+M)를 켜서 휴대폰 폭에서 보기를 확인한다. 개발자 도구는 브라우저의 언어를 따르므로, 영어 화면이면 요소는 Elements, 콘솔은 Console, 스타일은 Styles다.

    접근성: 화면을 보지 않고 쓰는 사람도 쓸 수 있게

    화면 낭독기를 쓰는 사람은 <button>을 "단추"로, <label>을 그 입력칸의 이름으로 듣는다. <div>에 클릭만 건 것은 낭독기에게 그냥 글자다. 뜻에 맞는 요소를 쓰는 것만으로도 키보드와 낭독기 사용자의 많은 문제가 풀린다. 더 꼼꼼한 점검은 Chrome 개발자 도구의 Lighthouse에서 접근성 검사를 돌려 본다.

    정리¶

    • HTML은 DOM 트리가 되고, CSS는 선택자로 요소를 골라 모양을 붙이고, JavaScript는 DOM을 고치며 이벤트에 답한다. 셋은 DOM에서 만난다.
    • 규칙이 겹치면 명시도가 높은 것, 같으면 나중 것이 이긴다. 이벤트는 누른 요소에서 조상으로 올라가서, 목록 하나에 걸어 모두 받을 수 있다.
    • AI가 만든 페이지는 실행해서 받아들인다. 뜻에 맞는 요소, 키보드로 쓰기, 사용자 글은 textContent로, 좁은 화면, 콘솔 오류를 확인하고 결과를 기록한다.
