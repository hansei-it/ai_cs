    62. 컴포넌트 기반 UI와 상태 관리, 렌더링 패러다임(CSR vs SSR)¶

    원리 동작을 예측하고 이상을 알아챌 수 있어야 하는 항목

    61번(브라우저 렌더링 경로)에서 본 것처럼 화면이 커지면 바꿀 곳을 손으로 맞추기 어렵다. 그래서 요즘 웹 화면은 작은 조각(컴포넌트)을 모아 짜고, 데이터(상태)가 바뀌면 화면을 다시 그리게 한다. 그 화면을 브라우저에서 그릴지(CSR), 서버에서 그려 보낼지(SSR)도 정해야 한다. 이 항목은 React 같은 라이브러리 없이 순수 자바스크립트로 작게 만들어 그 원리를 보고, 두 방식의 차이를 이 PC의 Chrome에서 잰다.

    이 항목에서 배우는 것¶

    • 컴포넌트가 받은 값으로 화면 조각을 돌려주는 함수라는 것과, 상태를 한곳에 두는 까닭을 설명할 수 있다.
    • 상태를 제자리에서 고치거나 같은 값을 두 곳에 둘 때 생기는 문제를 예측할 수 있다.
    • CSR과 SSR이 화면을 언제 보이고 언제 동작하게 하는지 견주고, 상황에 맞게 고를 수 있다.

    1. 컴포넌트는 받은 값으로 화면 조각을 돌려주는 함수다¶

    • 컴포넌트는 받은 값(props)으로 화면 조각을 돌려주는 함수다. 할 일 하나를 그리는 Item, 목록을 그리는 List, 그것을 모은 App처럼 작은 것을 모아 큰 화면을 만든다.
    • 바뀌는 데이터를 상태라 한다. 상태는 한곳(여기서는 App)에 두고, 아래 컴포넌트에는 값으로 내려 준다. 아래에서 일이 생기면(체크했다) 위로 알리고, 상태를 가진 쪽이 상태를 바꾼 뒤 다시 그린다.
    • 그래서 화면은 늘 "상태를 넣은 함수의 결과"다(화면 = f(상태)). 같은 상태면 같은 화면이 나오니, 화면이 이상하면 상태를 보면 된다.

    2. 상태는 새것으로 바꾸고, 계산할 수 있는 값은 저장하지 않는다¶

    직접 해 보기상태가 바뀌면 다시 그리는 컴포넌트장바구니의 단추를 눌러 상태를 바꾸며, 어느 컴포넌트가 다시 그려지는지와 합계를 따로 저장할 때(복사본)와 계산할 때 화면이 어떻게 달라지는지 본다
    새 창에서 크게 열기
    • 다시 그리는 비용을 줄이려고, 받은 값이 앞과 같으면 다시 그리지 않는 방법을 많이 쓴다. 이때 "같다"는 대개 같은 객체인지(===)로 본다. 그래서 상태는 제자리에서 고치지 않고 새 객체로 바꾼다(문제 1).
    • 합계나 남은 일의 수처럼 상태에서 계산할 수 있는 값을 따로 저장하면, 원래 값을 바꿀 때마다 그것도 맞춰야 한다. 한 곳이라도 잊으면 화면이 어긋난다(위젯의 "상태에 따로 저장한다"). 그릴 때 계산한다.
    • 이 규칙은 React처럼 같은 객체인지로 바뀜을 아는 라이브러리의 상태 관리와 같은 생각이다. Vue처럼 고치는 것을 지켜보는 라이브러리는 제자리에서 고쳐도 되지만, "상태는 한곳, 계산할 값은 계산하기"는 어디서나 같다.

    3. CSR은 브라우저가, SSR은 서버가 HTML을 만든다¶

    • CSR(클라이언트 사이드 렌더링)은 거의 빈 HTML을 보내고, 브라우저에서 자바스크립트가 데이터를 받아 화면을 그린다. SSR(서버 사이드 렌더링)은 서버가 같은 컴포넌트로 HTML을 만들어 보낸다.
    • 느린 휴대폰과 망을 흉내 낸 조건에서 SSR은 목록이 304~328ms에 보였고, CSR은 672~716ms에 보였다. CSR은 HTML, 자바스크립트, 데이터를 차례로 받아야 그릴 수 있다.
    • SSR도 단추는 자바스크립트가 와서 이벤트를 연결한 뒤(하이드레이션)에야 동작한다. 첫 화면이 빨라야 하고 검색에 잡혀야 하는 글은 SSR, 로그인한 뒤 오래 쓰는 관리 화면은 CSR이 흔하다.

    예측해 보기¶

    문제 1. 받은 값이 앞과 같은 객체면 다시 그리지 않는 컴포넌트다. 할 일을 제자리에서 고친 뒤와, 새 배열을 만든 뒤에 무엇이 출력될까?

    let renders = 0;
function memo(component) {                      // 받은 값이 앞과 같은 객체면(===) 다시 그리지 않고 앞의 결과를 쓴다
  let lastProps, lastOut;
  return props => {
    if (props === lastProps) return lastOut;
    renders++;
    lastProps = props;
    return (lastOut = component(props));
  };
}

const List = memo(todos => todos.map(t => (t.done ? "✓ " : "· ") + t.title).join(" / "));
const todos = [{ title: "우유", done: false }, { title: "빵", done: false }];
console.log(List(todos));
todos[0].done = true;                           // 제자리에서 고쳤다
console.log(List(todos));
const next = todos.map(t => (t.title === "우유" ? { ...t, done: true } : t));   // 새 배열로 만들었다(바뀐 항목만 새 객체)
console.log(List(next), renders);
    정답과 해설 
    · 우유 / · 빵
· 우유 / · 빵
✓ 우유 / · 빵 2

    제자리에서 고친 배열은 앞과 같은 객체라서, 컴포넌트는 바뀐 것이 없다고 보고 앞의 화면을 그대로 썼다. 상태는 바뀌었는데 화면은 그대로인 버그다. 새 배열을 만들어 넘기자 다시 그려 "✓ 우유"가 나왔다. React에서 items.push(x); setItems(items)처럼 쓰면 화면이 바뀌지 않는 까닭도 같다. setItems([...items, x])처럼 새 배열을 넘긴다. 바뀐 항목만 새 객체로 만들고 나머지는 그대로 두어야, 항목마다 같은지를 보는 컴포넌트가 바뀐 줄만 다시 그린다.

    문제 2. 자바스크립트를 끈 브라우저로 3절의 두 페이지를 열면, 할 일 200개 가운데 몇 개가 보일까? 자바스크립트를 실행하지 않고 HTML만 읽는 검색 엔진의 수집기라면 어떨까?

    정답과 해설

    CSR은 0개, SSR은 200개다. 이 PC의 Chrome에서 자바스크립트를 끄고 열어 확인했다. CSR 페이지의 HTML에는 빈 <div id="app"></div>만 있고, 목록은 자바스크립트가 데이터를 받아 그린다. SSR 페이지의 HTML에는 목록이 이미 들어 있다. HTML만 읽는 수집기에게 CSR 페이지는 빈 페이지다. 다만 SSR 페이지도 단추는 동작하지 않는다. 이벤트를 연결하는 것은 자바스크립트이기 때문이다.

    문제 3. 같은 목록 페이지를 사용자 1,000명이 연다. CSR과 SSR에서 목록의 HTML을 만드는 일은 각각 누가, 몇 번 할까? 서버가 결과를 저장해 두지(캐시) 않는다고 하자.

    정답과 해설

    CSR은 사용자의 기기 1,000대가 한 번씩, SSR은 서버가 1,000번 만든다. CSR의 서버는 데이터(JSON)만 보내고, 화면을 그리는 일은 기기마다 나눠 한다. SSR은 첫 화면이 빠른 대신 그 일을 서버가 모두 진다. 그렇다고 기기의 일이 없어지지는 않는다. React 같은 라이브러리의 하이드레이션은 브라우저에서 컴포넌트를 다시 실행해 받은 HTML과 맞춰 보므로, 화면이 크면 기기도 그만큼 일한다(이 항목의 예는 이벤트만 연결한다). 사용자가 많아지면 서버를 늘리거나, 모두에게 같은 페이지는 미리 만들어 두거나(정적 생성), 만든 결과를 저장해 두고 다시 쓴다(캐시). 어디서 그릴지는 속도, 검색, 서버 비용을 함께 보고 정한다.

    직접 해보기¶

    실습: 상태를 한곳에 둔 할 일 앱 고치기

    1. 아래 코드를 todo.html로 저장해 Chrome에서 연다. 체크하면 setState가 상태를 새것으로 바꾸고 화면을 다시 그린다. 상태를 바꾸는 곳은 setState 하나뿐이다.
    2. 목록 위에 "남은 일 n개"를 보이게 한다. 상태에 숫자를 따로 두지 말고, App에서 todos로 계산한다.
    3. 목록 아래에 "모두 끝내기" 단추를 더한다. 할 일을 제자리에서 고치지 말고 새 배열을 만들어 setState에 넘긴다.

    이 연습은 짧게 쓰려고 innerHTML로 통째로 다시 그린다. 큰 화면에서는 61번(브라우저 렌더링 경로)처럼 바뀐 곳만 고치는 방법을 쓴다. 제목이 사용자가 넣은 글이면 59번(HTML, CSS, JavaScript)의 문제 3처럼 스크립트가 돌 수 있으므로, 실제로는 글을 textContent로 넣거나 이스케이프해 주는 라이브러리를 쓴다.

    AI와 함께 확인하기¶

    AI 활용 과제: AI가 만든 컴포넌트에서 상태 문제 찾기

    1. AI에게 "React로 장바구니를 만들어 줘. 상품을 담고, 수량을 바꾸고, 합계를 보여 준다"라고 한다. 받은 코드는 실행하지 않고 읽기만 한다(React를 설치할 필요가 없다).
    2. 받은 코드에서 상태(useState)를 모두 적고, 그 가운데 다른 상태에서 계산할 수 있는 것이 있는지 본다.
    3. 상태를 바꾸는 곳마다 새 객체를 만드는지, 제자리에서 고치는지 표시한다. 문제가 있으면 AI에게 보여 주고 고치게 한다.
    확인할 점
    • 합계를 const [total, setTotal] = useState(0)처럼 따로 두고 담을 때만 더하는 코드가 흔하다. 수량을 바꾸거나 지울 때 맞추는 것을 잊으면 위젯처럼 어긋난다. const total = items.reduce(…)처럼 그릴 때 계산하게 한다.
    • items.push(item); setItems(items)나 item.qty++처럼 제자리에서 고치는 코드는 화면이 바뀌지 않거나 엉뚱하게 바뀐다(문제 1). 새 배열과 새 객체로 바꾼다.
    • 목록을 그릴 때 항목마다 바뀌지 않는 key(상품 id)를 다는지 본다. 배열의 자리(index)를 키로 쓰면 앞에 하나를 넣을 때 엉뚱한 줄을 고친다(61번(브라우저 렌더링 경로)의 문제 3).

    더 알아보기¶

    SSR 말고 미리 만들어 두기

    모든 사용자에게 같은 페이지(블로그 글, 설명서)는 요청마다 만들 필요가 없다. 빌드할 때 HTML을 미리 만들어 두고 파일로 보내는 것을 정적 생성(SSG)이라 한다. 이 강의 사이트도 MkDocs가 Markdown을 미리 HTML로 만들어 둔 것이다. 사용자마다 다른 부분(로그인 정보)만 브라우저에서 그리게 섞어 쓰기도 한다.

async function open(path, noJs) {
  const port = 9500 + Math.floor(Math.random() * 400);
  const profile = mkdtempSync(join(tmpdir(), "cs62-"));
  const chrome = spawn(CHROME, ["--headless=new", `--remote-debugging-port=${port}`, `--user-data-dir=${profile}`, "--no-first-run", "about:blank"], { stdio: "ignore" });
  let page;
  for (let i = 0; i < 100 && !page; i++) {
    try { page = (await (await fetch(`http://127.0.0.1:${port}/json/list`)).json()).find(t => t.type === "page"); } catch {}
    if (!page) await sleep(150);
  }
  const ws = new WebSocket(page.webSocketDebuggerUrl);
  await new Promise(r => ws.addEventListener("open", r, { once: true }));
  let seq = 0, t0 = null, loaded;
  const pending = new Map(), net = {};
  const onLoad = new Promise(r => { loaded = r; });
  ws.addEventListener("message", ev => {
    const m = JSON.parse(ev.data);
    if (m.id) { pending.get(m.id)?.(m.result); pending.delete(m.id); return; }
    if (m.method === "Page.loadEventFired") loaded();
    if (m.method === "Network.requestWillBeSent") { net[m.params.requestId] = { url: new URL(m.params.request.url).pathname }; t0 ??= m.params.timestamp; }
    if (m.method === "Network.loadingFinished" && net[m.params.requestId]) net[m.params.requestId].end = Math.round((m.params.timestamp - t0) * 1000);
  });
  const send = (method, params = {}) => new Promise(r => { const id = ++seq; pending.set(id, r); ws.send(JSON.stringify({ id, method, params })); });
  const js = async e => (await send("Runtime.evaluate", { expression: e, returnByValue: true })).result.value;
  await send("Page.enable"); await send("Network.enable"); await send("Runtime.enable");
  await send("Network.setCacheDisabled", { cacheDisabled: true });
  await send("Network.emulateNetworkConditions", { offline: false, latency: 150, downloadThroughput: 1.6 * 1024 * 1024 / 8, uploadThroughput: 750 * 1024 / 8 });
  await send("Emulation.setCPUThrottlingRate", { rate: 4 });
  if (noJs) await send("Emulation.setScriptExecutionDisabled", { value: true });
  await send("Page.navigate", { url: `http://127.0.0.1:8062${path}` });
  await onLoad;
  await sleep(1500);
  const r = await js(`({
    fcp: performance.getEntriesByName("first-contentful-paint")[0]?.startTime,
    interactive: performance.getEntriesByName("interactive")[0]?.startTime,
    items: document.querySelectorAll("li").length })`);
  r.requests = Object.values(net).filter(n => n.url !== "/favicon.ico").map(n => `${n.url} ${n.end}ms`).join(", ");
  ws.close(); chrome.kill(); await sleep(300);
  try { rmSync(profile, { recursive: true, force: true }); } catch {}
  return r;
}

    정리¶

    • 컴포넌트는 받은 값으로 화면 조각을 돌려주는 함수이고, 화면은 상태를 넣은 결과다. 상태는 한곳에 두고, 아래로는 값을, 위로는 일을 알린다.
    • 상태는 제자리에서 고치지 말고 새것으로 바꾼다. 상태에서 계산할 수 있는 값은 저장하지 않고 그릴 때 계산한다.
    • CSR은 브라우저가 그려 첫 화면이 늦고 HTML에 내용이 없다. SSR은 서버가 그려 첫 화면이 빠르지만 하이드레이션 전에는 동작하지 않고, 서버가 그 일을 진다.
