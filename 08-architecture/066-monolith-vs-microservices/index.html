    66. 아키텍처 스타일: 모놀리식 vs 마이크로서비스¶

    원리 동작을 예측하고 이상을 알아챌 수 있어야 하는 항목

    주문 서비스가 커지면 재고, 결제, 알림 같은 기능을 한 프로그램에 계속 넣을지(모놀리식), 기능마다 따로 떼어 낼지(마이크로서비스) 정해야 한다. 마이크로서비스는 유행처럼 들리지만, 함수 호출을 네트워크 호출로 바꾸는 값을 치른다. 이 항목은 그 값을 이 PC에서 재고, 언제 나눌 만한지 본다. 65번(수직 확장 vs 수평 확장)의 수평 확장과는 다른 이야기다. 모놀리스도 여러 대로 늘릴 수 있다.

    이 항목에서 배우는 것¶

    • 모놀리식과 마이크로서비스의 구조와 장단점을 설명할 수 있다.
    • 서비스를 거치는 호출이 늘 때 지연과 실패가 어떻게 쌓이는지 예측할 수 있다.
    • 서비스마다 데이터를 나눌 때 생기는 문제와, 나누는 기준을 설명할 수 있다.

    1. 모놀리스는 함수를 부르고, 마이크로서비스는 네트워크로 부른다¶

    • 모놀리식은 모든 기능을 한 프로그램에 두고 한 번에 배포한다. 기능 사이는 함수 호출이고 DB도 하나다. 처음 만들고 고치기가 가장 단순하다.
    • 마이크로서비스는 기능마다 따로 배포하는 작은 서비스로 나누고, 서비스 사이는 HTTP나 메시지로 부른다(69번(비동기 메시징)). 팀마다 따로 배포하고, 필요한 서비스만 따로 늘린다(65번(수직 확장 vs 수평 확장)).
    • 대신 함수 호출이 네트워크 호출이 된다. 네트워크 호출은 느리고, 실패할 수 있다(2절).

    2. 네트워크 호출은 함수 호출보다 수천 배 느리고, 실패가 쌓인다¶

    직접 해 보기서비스를 거칠수록 느려지고 실패한다주문 하나가 거치는 서비스 수, 부르는 방법(함수, HTTP), 차례로 부를지 함께 부를지, 실패하면 다시 부를지를 골라, 부르는 데 드는 시간과 주문 10만 건 가운데 실패하는 수를 본다
    새 창에서 크게 열기
    • 이 PC에서 재고를 묻는 일을 함수로 부르면 0.038~0.047µs, 같은 PC의 다른 프로세스에 HTTP로 물으면 연결을 이어 쓸 때 92.9~98.2µs, 매번 새로 연결하면 544.2~552.2µs였다. 서로 다른 기계라면 네트워크를 지나는 시간이 더해진다.
    • 주문 하나가 서비스 5개를 차례로 부르면 시간은 다섯 배로 쌓이고, 하나라도 실패하면 주문이 실패한다. 서비스가 늘면 실패가 얼마나 쌓이는지는 문제 1에서 어림한다.
    • 서로 기다릴 필요가 없는 호출은 함께 부르고(문제 2), 여러 개를 물을 때는 한 번에 묶는다(문제 3). 실패하면 다시 부르되, 두 번 하면 안 되는 일은 멱등성을 갖춘다(70번(분산 시스템의 근본 문제)).

    3. 데이터를 서비스마다 나누면, 남의 데이터는 API로 묻는다¶

    • 마이크로서비스는 데이터도 서비스마다 따로 가진다. 다른 서비스의 DB를 직접 읽으면 그 서비스가 표를 바꿀 때 몰래 깨진다. 그래서 서비스 사이에는 조인(JOIN)이 없고, 여러 서비스에 걸친 일을 DB 트랜잭션 하나로 묶을 수도 없다(53번(트랜잭션과 락)). 여러 DB에 걸친 트랜잭션(2단계 커밋)도 있지만, 느리고 한쪽이 멈추면 다른 쪽이 잠금을 쥔 채 기다려서 잘 쓰지 않는다.
    • 나누는 기준은 기술이 아니라 함께 바뀌는 것과 그것을 맡는 팀이다. 함께 바뀌고 함께 읽는 기능을 서로 다른 서비스에 두면, 바꿀 때마다 여러 서비스를 함께 배포해야 해서 나눈 의미가 없다. 팀이 하나뿐이라면 모듈을 잘 나눈 모놀리스로 시작하는 편이 대개 낫다.

    예측해 보기¶

    문제 1. 주문 하나를 처리하려고 서비스 5개를 차례로 부른다. 서비스마다 1,000번에 1번 실패한다(성공률 99.9%). 주문 10만 건 가운데 몇 건이 실패할까? 실패하면 한 번 다시 부르면 어떻게 될까? 위젯으로 확인하기 전에 어림해 본다.

    정답과 해설

    약 499건이다. 한 번 다시 부르면 0.5건으로 준다. 주문이 성공하려면 다섯 번이 모두 성공해야 하므로 성공률은 0.999⁵ ≈ 0.99501이다. 서비스 하나는 99.9%인데 주문은 99.5%가 되었다. 다시 부르면 한 번의 실패 확률이 0.001에서 0.000001(0.001²)로 줄어 10만 건에 0.5건이 된다. 다만 이것은 실패가 우연히, 서로 상관없이 일어날 때의 이야기다. 서비스가 아예 멈췄다면 다시 불러도 또 실패하고, 다시 부르는 요청이 멈춘 서비스를 더 괴롭힌다(70번(분산 시스템의 근본 문제), 71번(이중화와 무중단 배포)).

    문제 2. 주문 화면을 그리려고 재고, 가격, 리뷰 서비스를 부른다. 서비스는 20ms 뒤에 답한다고 하자. 차례로 부를 때와 함께 부를 때, 걸린 시간(10ms 단위로 반올림한 ms)은 각각 얼마일까?

    import time
from concurrent.futures import ThreadPoolExecutor


def call(service):                               # 다른 서비스를 부르고 답을 기다린다(20ms라고 하자)
    time.sleep(0.02)
    return service


services = ["재고", "가격", "리뷰"]

t = time.perf_counter()
answers = [call(s) for s in services]            # 하나씩 차례로 부른다
print(round((time.perf_counter() - t) * 1000, -1))

t = time.perf_counter()
with ThreadPoolExecutor() as pool:
    answers = list(pool.map(call, services))     # 셋을 함께 부른다
print(round((time.perf_counter() - t) * 1000, -1))
    정답과 해설 
    60.0
20.0

    차례로 부르면 기다림이 더해져 60ms, 함께 부르면 가장 긴 하나만큼인 20ms다(이 PC에서 20번 모두 같았다). 세 서비스의 답이 서로 필요 없으니 함께 불러도 된다. 앞의 답으로 다음 요청을 정해야 할 때만 차례로 부른다. 이 PC의 Windows에서 Python의 time.sleep(0.02)는 50번 재니 20.04~20.67ms로 거의 20ms를 지켰다. 자바스크립트의 타이머가 15.6ms 눈금으로 늦게 돈 것(60번(이벤트 루프와 비동기))과 다르다.

    문제 3. 주문 목록 100개에 손님 이름을 붙인다. 주문 서비스는 손님 서비스에 HTTP로 묻는다. 두 방법으로 몇 번을 부를까?

    users = {i: f"손님{i}" for i in range(1, 101)}     # 손님 서비스가 가진 데이터
calls = 0


def get_user(uid):                               # 손님 서비스에 한 명을 묻는다(HTTP 한 번)
    global calls
    calls += 1
    return users[uid]


def get_users(uids):                             # 여러 명을 한 번에 묻는다(HTTP 한 번)
    global calls
    calls += 1
    return {u: users[u] for u in uids}


orders = [{"id": i, "user": i % 100 + 1} for i in range(100)]   # 주문 서비스가 가진 데이터

names = [get_user(o["user"]) for o in orders]
print(calls)

calls = 0
found = get_users({o["user"] for o in orders})
names = [found[o["user"]] for o in orders]
print(calls)
    정답과 해설 
    100
1

    주문마다 하나씩 물으면 100번이다. 이 PC에서 HTTP 한 번이 93~98µs였으니 묻는 데만 10ms쯤 쓴다. 손님이 있는 서비스가 다른 기계라면 그보다 훨씬 길다. 한 번에 묶어 물으면 한 번이다. 56번(애플리케이션과 DB 연동)의 N+1 문제가 서비스 사이에서 다시 나타난 것이다. 모놀리스였다면 손님 표와 조인하는 SQL 한 줄로 끝났을 일이다.

    AI와 함께 확인하기¶

    AI 활용 과제: AI가 나눈 서비스 경계 검토하기

    1. AI에게 "작은 쇼핑몰(상품, 장바구니, 주문, 결제, 배송, 회원)을 마이크로서비스로 설계해 줘. 서비스 목록과 서비스 사이의 호출을 적어 줘"라고 한다.
    2. 주문 하나를 처리할 때 몇 개의 서비스를 차례로 부르는지 세고, 위젯으로 시간과 실패를 어림한다.
    3. 서비스마다 어떤 데이터를 가지는지, 다른 서비스의 DB를 읽는 곳이 있는지, 한 트랜잭션이 필요한 일(결제와 주문 확정)이 서비스 경계를 넘는지 표시한다. 문제가 있으면 AI에게 보여 주고 경계를 다시 긋게 한다.
    확인할 점
    • 명사마다 서비스를 하나씩 만드는 답이 흔하다. 주문 하나에 서비스 대여섯 개를 차례로 부르는 구조면 시간은 더해지고 성공률은 곱해져 낮아진다(문제 1). 함께 바뀌는 기능은 한 서비스로 합치게 한다.
    • 여러 서비스가 같은 DB를 함께 쓰는 설계는 배포만 나눈 모놀리스다. 표 하나를 바꿀 때 여러 서비스가 함께 깨진다.
    • 결제와 주문 확정처럼 함께 성공하거나 함께 실패해야 하는 일이 서비스 경계를 넘으면, 한 트랜잭션으로 묶을 수 없어 따로 맞추는 방법(되돌리는 단계를 두는 사가)이 필요하다. 그 비용을 질 만한지 묻는다. 팀과 사용자가 적다면 "모놀리스로 시작하자"가 좋은 답일 수 있다.

    더 알아보기¶

    콘웨이의 법칙: 시스템은 조직을 닮는다

    "시스템의 구조는 그것을 만든 조직의 소통 구조를 닮는다"는 관찰이 있다(멜빈 콘웨이, 1968). 팀 다섯이 한 프로그램을 함께 고치면 서로 기다리느라 배포가 느려지고, 그래서 팀마다 서비스를 나누게 된다. 거꾸로 팀이 하나인데 서비스를 열 개로 나누면, 한 팀이 열 개를 함께 배포하고 지키느라 바빠진다. 서비스를 나누는 일은 조직을 나누는 일과 함께 정한다.

    매번 새로 연결하면 포트가 모자란다

    측정 프로그램을 처음 짤 때는 매번 새로 연결한 뒤 클라이언트가 먼저 연결을 닫았다. 2,000번씩 되풀이하자 두 번째 실행부터 OSError: [WinError 10048](주소를 하나만 쓸 수 있다)로 멈췄다. 먼저 닫는 쪽에 연결이 TIME_WAIT로 한동안 남는데(41번(전송 계층 (TCP·UDP))), 같은 서버로 가는 연결에 쓸 클라이언트 쪽 포트가 모자랐기 때문이다. 아래 프로그램은 Connection: close를 보내 서버가 먼저 닫게 했다. 서비스 사이에 매번 새로 연결하는 코드는 느릴 뿐 아니라 이렇게 바쁠 때 실패한다. 연결을 이어 쓰는(연결 풀) 쪽이 낫다(56번(애플리케이션과 DB 연동)).

    이 항목의 측정 프로그램

    2절의 값은 이 PC(Core i9-14900KF, DDR5 64GB, Windows 11, Python 3.14.0)에서 아래 프로그램을 5번 실행한 범위다. 재고 서비스를 다른 프로세스로 띄우고 127.0.0.1에서 HTTP로 묻는다. 연결을 이어 쓸 때는 5번 가운데 한 번 181.3µs로 크게 벗어나 뺐다.

    # 66번 측정: 재고를 묻는 일을 함수로 부를 때와, 같은 PC의 다른 프로세스(재고 서비스)에 HTTP로 물을 때 걸리는 시간
# (1) 함수 호출: 100만 번 부른 시간 ÷ 100만 (2) HTTP, 연결을 이어 쓸 때 (3) HTTP, 부를 때마다 새로 연결할 때: 2,000번의 중앙값
# 실행: python call_measure.py
import http.client
import json
import statistics
import subprocess
import sys
import time
from http.server import BaseHTTPRequestHandler, ThreadingHTTPServer

STOCK = {"apple": 12, "milk": 3}


def stock(item):                          # 재고 확인: 모놀리스라면 같은 프로그램 안의 함수
    return STOCK.get(item, 0)


class StockService(BaseHTTPRequestHandler):  # 마이크로서비스라면 다른 프로세스에서 도는 재고 서비스
    protocol_version = "HTTP/1.1"
    def do_GET(self):
        body = json.dumps({"stock": stock(self.path.rsplit("/", 1)[1])}).encode()
        self.send_response(200)
        self.send_header("Content-Type", "application/json")
        self.send_header("Content-Length", str(len(body)))
        self.end_headers()
        self.wfile.write(body)
    def log_message(self, *a):
        pass


def median_us(fn, n=2000):
    xs = []
    for _ in range(n):
        t = time.perf_counter()
        fn()
        xs.append(time.perf_counter() - t)
    return statistics.median(xs) * 1e6


if sys.argv[1:2] == ["serve"]:
    ThreadingHTTPServer(("127.0.0.1", 18660), StockService).serve_forever()
else:
    proc = subprocess.Popen([sys.executable, __file__, "serve"])
    time.sleep(1.0)
    kept = http.client.HTTPConnection("127.0.0.1", 18660)

    def http_kept():
        kept.request("GET", "/stock/apple")
        return json.loads(kept.getresponse().read())["stock"]

    def http_new():
        c = http.client.HTTPConnection("127.0.0.1", 18660)
        c.request("GET", "/stock/apple", headers={"Connection": "close"})   # 서버가 먼저 닫게 한다(아래 설명)
        r = json.loads(c.getresponse().read())["stock"]
        c.close()
        return r

    try:
        t = time.perf_counter()
        for _ in range(1_000_000):
            stock("apple")
        print(f"함수 호출: {(time.perf_counter() - t) * 1e6 / 1_000_000:.3f} µs")
        for name, fn in [("HTTP, 연결 이어 쓰기", http_kept), ("HTTP, 매번 새 연결", http_new)]:
            fn()                          # 데우기
            print(f"{name}: {median_us(fn):.1f} µs")
    finally:
        proc.kill()
        proc.wait()

    정리¶

    • 모놀리스는 한 프로그램, 한 배포, 한 DB다. 처음 만들고 고치기가 가장 단순하다.
    • 마이크로서비스는 팀마다 따로 배포하고 확장하지만, 함수 호출이 수천 배 느린 네트워크 호출이 되고 실패가 쌓인다. 함께 부르기, 묶어 부르기, 안전한 재시도로 줄인다.
    • 서비스마다 데이터를 따로 가지므로 조인과 트랜잭션이 경계를 넘지 못한다. 함께 바뀌는 것은 함께 둔다.
