    70. 분산 시스템의 근본 문제: 부분 실패, 재시도와 멱등성, 일관성과 가용성의 트레이드오프¶

    원리 동작을 예측하고 이상을 알아챌 수 있어야 하는 항목

    프로그램 하나 안에서 함수를 부르면 성공하거나 예외가 난다. 네트워크 너머의 서비스를 부르면 셋째 결과가 생긴다. "모른다"이다. 서버 여러 대가 함께 일하는 분산 시스템에서는 일부만 실패하는 일(부분 실패)이 늘 일어나고, 그때 무엇을 할지 미리 정해 두어야 한다. 이 항목은 주문 서비스에서 응답을 잃는 상황을 실제로 만들어 보고, 다시 보내기와 멱등성, 복제본 사이의 선택을 본다. 64번(REST API 설계)에서 POST를 다시 보내면 주문이 둘이 된다고 한 이야기의 해결책이 여기 있다.

    이 항목에서 배우는 것¶

    • 답이 오지 않을 때 일어날 수 있는 경우와, 그것을 구별할 수 없는 까닭을 설명할 수 있다.
    • 다시 보내기가 언제 중복을 만드는지 예측하고, 멱등 키로 막을 수 있다.
    • 네트워크가 끊길 때 일관성과 가용성 가운데 하나를 골라야 하는 까닭(CAP)을 설명할 수 있다.

    1. 답이 오지 않으면 무슨 일이 있었는지 알 수 없다¶

    • 요청이 가다 사라졌을 수도, 서버가 아직 처리 중일 수도, 처리했는데 응답이 사라졌을 수도 있다. 손님에게는 셋이 똑같이 "답이 없다"로 보인다.
    • 그래서 네트워크 호출에는 기다리는 시간(타임아웃)을 꼭 정한다. 정하지 않으면 답하지 않는 서버 하나 때문에 손님과 서버의 스레드가 끝없이 묶이고, 그 서버를 부르는 서비스까지 멈춘다.
    • 타임아웃이 났을 때 다시 보낼지 말지는 그 요청이 두 번 처리되어도 괜찮은지에 달렸다(2절).

    2. 다시 보낼 때는 멱등 키를 함께 보낸다¶

    직접 해 보기다시 보내면 주문이 몇 개 생기나어디서 실패하는지(요청이 사라짐, 첫 요청만 느림, 처리 뒤 응답이 사라짐), 다시 보낼지, 멱등 키를 보낼지를 골라, 주고받은 차례와 만들어진 주문 수, 손님이 본 결과를 본다
    새 창에서 크게 열기
    • 같은 요청을 여러 번 해도 한 번 한 것과 결과가 같으면 멱등하다. GET, PUT, DELETE는 그렇게 설계하고, 주문을 만드는 POST는 그렇지 않다(64번(REST API 설계)).
    • 그래서 손님이 주문마다 이름표(멱등 키)를 정해 함께 보내고, 다시 보낼 때도 같은 키를 쓴다. 서버는 키를 기억해 두었다가 같은 키가 다시 오면 새로 만들지 않는다. 결제 API들이 Idempotency-Key 머리로 이 방법을 쓴다.
    • 다시 보낼 때는 간격을 두 배씩 늘리고(지수 백오프), 손님마다 무작위로 흩뜨린다(지터). 멈췄다 살아난 서버에 모두가 같은 순간 다시 보내면 서버가 다시 쓰러진다.

    3. 네트워크가 끊기면 일관성과 가용성 가운데 하나를 고른다¶

    • 데이터를 여러 서버에 복제해 두면 한 대가 죽어도 버틴다(서버 이중화는 71번(이중화와 무중단 배포)). 그런데 복제본 사이의 네트워크가 끊기면(분단), 한쪽이 받은 쓰기를 다른 쪽이 모른다.
    • 이때 낡을 수 있는 값으로라도 답할지(가용성), 맞는다고 확인할 수 없으면 답하지 않을지(일관성) 골라야 한다. 분단이 일어난 동안에는 둘을 함께 가질 수 없다는 것이 CAP 정리다. 여기서 일관성은 "어느 복제본이 답하든 최신 값이다(최신인지 모르면 답하지 않는다)"는 뜻으로, 트랜잭션의 일관성(제약을 지킨다, 53번(트랜잭션과 락))과 다르다.
    • 무엇을 고를지는 기술이 아니라 업무가 정한다. 잔액이 틀리는 것보다 잠깐 답하지 않는 편이 나은 일도 있고, 그 반대인 일도 있다. 네트워크가 다시 이어진 뒤의 모습은 문제 2에서 본다.

    예측해 보기¶

    문제 1. 주문 서비스가 첫 주문을 저장한 뒤 응답을 잃는다(망이 끊겼다고 하자). 손님은 응답이 없으면 한 번 다시 보낸다. 키 없이 보낼 때와 멱등 키와 함께 보낼 때, 손님이 받은 응답과 저장된 주문 수는?

    import http.client
import json
import threading
from http.server import BaseHTTPRequestHandler, ThreadingHTTPServer

orders = []                                      # 주문 서비스의 DB
seen = {}                                        # 멱등 키 → 처음 보낸 응답
lose_next_reply = True                           # 이번 응답을 잃는다(망이 끊겼다고 하자)


class OrderService(BaseHTTPRequestHandler):
    protocol_version = "HTTP/1.1"

    def do_POST(self):
        global lose_next_reply
        key = self.headers.get("Idempotency-Key")
        body = self.rfile.read(int(self.headers["Content-Length"]))
        if key in seen:                          # 같은 키로 다시 왔다: 새로 만들지 않고 처음 답을 준다
            reply = seen[key]
        else:
            orders.append(json.loads(body))      # 주문을 저장했다
            reply = json.dumps({"id": len(orders)}).encode()
            if key:
                seen[key] = reply
        if lose_next_reply:                      # 저장은 했지만 응답이 손님에게 가지 못한다
            lose_next_reply = False
            self.close_connection = True
            return
        self.send_response(201)
        self.send_header("Content-Length", str(len(reply)))
        self.end_headers()
        self.wfile.write(reply)

    def log_message(self, *a):
        pass


def place_order(port, key=None):                 # 응답을 못 받으면 한 번 다시 보낸다
    headers = {"Content-Type": "application/json"}
    if key:
        headers["Idempotency-Key"] = key
    for attempt in range(2):
        conn = http.client.HTTPConnection("127.0.0.1", port, timeout=2)
        try:
            conn.request("POST", "/orders", json.dumps({"item": "우유", "qty": 1}), headers)
            return json.loads(conn.getresponse().read())
        except (http.client.RemoteDisconnected, ConnectionError, TimeoutError):
            continue                             # 응답이 없다: 처리됐는지 모르니 다시 보낸다
        finally:
            conn.close()


server = ThreadingHTTPServer(("127.0.0.1", 0), OrderService)
threading.Thread(target=server.serve_forever, daemon=True).start()
port = server.server_address[1]

print(place_order(port), len(orders))            # 키 없이

orders.clear()
lose_next_reply = True
print(place_order(port, key="a1b2"), len(orders))   # 손님이 정한 키와 함께
server.shutdown()
    정답과 해설 
    {'id': 2} 2
{'id': 1} 1

    키 없이 다시 보내자 서버는 새 주문으로 알고 하나 더 만들었다. 손님은 2번 주문만 알지만, 1번도 저장되어 있다. 결제였다면 두 번 결제된 것이다. 키와 함께 보내면 서버가 a1b2를 기억하고 있다가 처음의 응답(주문 1)을 다시 주었다(이 PC에서 10번 모두 같았다). 키는 손님이 주문마다 새로 정하고(보통 UUID처럼 겹치지 않는 값), 다시 보낼 때만 같은 키를 쓴다. 이 서버는 seen을 메모리에 두었지만, 실제로는 주문과 키를 같은 DB 트랜잭션에 함께 저장해야 서버가 그 사이에 죽어도 어긋나지 않는다.

    문제 2. 복제본 A와 B 사이가 끊긴 동안 재고가 하나 팔렸다. 그 뒤 다시 이어져 쿠폰이 쓰였다. A와 B는 무엇을 가지고 있을까?

    a, b = {}, {}                                    # 같은 데이터를 담은 복제본 둘(서로 다른 서버)
linked = True                                    # A와 B 사이의 네트워크


def write(key, value):                           # 쓰기는 A가 받고, 이어져 있으면 B에도 복사한다
    a[key] = value
    if linked:
        b[key] = value


write("재고", 5)
linked = False                                   # A와 B 사이가 끊겼다
write("재고", 4)                                  # 그사이 하나가 팔렸다
linked = True                                    # 다시 이어졌다
write("쿠폰", 1)                                  # 이어진 뒤의 쓰기
print(a)
print(b)
    정답과 해설 
    {'재고': 4, '쿠폰': 1}
{'재고': 5, '쿠폰': 1}

    다시 이어진 뒤의 쓰기는 B에도 갔지만, 끊긴 동안의 쓰기는 B가 끝내 모른다. 네트워크가 돌아왔다고 데이터가 저절로 맞춰지지 않는다. 그래서 복제 시스템은 쓰기를 기록(로그)에 남겨 두었다가 이어지면 밀린 것을 보내 주거나(58번(백업과 복구)의 WAL과 같은 생각), 주기적으로 둘을 견주어 맞춘다. 양쪽 모두 쓰기를 받았다면 어느 값이 맞는지 정하는 규칙(나중에 쓴 것이 이긴다 등)도 필요하다.

    문제 3. 위젯에서 "첫 요청만 느림(3초)"을 고르고 한 번 다시 보낸다. 키가 없을 때와 있을 때 주문은 몇 개일까? 서버가 키를 받자마자가 아니라 주문을 저장한 뒤에야 적는다면 어떻게 될까?

    정답과 해설

    키가 없으면 2개, 있으면 1개다. 저장한 뒤에야 키를 적으면 키가 있어도 2개가 된다. 손님이 2초에 다시 보낸 요청이 왔을 때 첫 요청은 아직 처리 중이다. 서버가 처리를 마친 뒤에야 키를 적는다면, 둘째 요청이 왔을 때 키가 아직 없어 새 주문으로 처리한다. 그래서 서버는 요청을 받자마자 "이 키는 처리 중"이라고 적어 두고, 같은 키가 오면 끝날 때까지 기다리게 하거나 "처리 중"이라고 답한다. 문제 1의 서버도 저장한 뒤에 키를 적으므로 이 경우에는 막지 못한다. 문제 1은 응답을 잃는 경우만 시험한 것이다.

    AI와 함께 확인하기¶

    AI 활용 과제: AI가 붙인 재시도 검토하기

    1. AI에게 "결제 API를 부르는 Python 함수에 실패하면 다시 시도하는 기능을 붙여 줘"라고 한다.
    2. 받은 코드에서 타임아웃, 다시 보내는 조건(어떤 오류에서), 횟수와 간격, 멱등 키를 찾아 표로 적는다.
    3. 응답을 잃는 경우와 서버가 느린 경우에 결제가 몇 번 일어날지 따지고, 문제가 있으면 AI에게 그 경우를 보여 주고 고치게 한다.
    확인할 점
    • 타임아웃이 없는 코드가 흔하다. 서버가 느리면 영원히 기다린다. requests, http.client, urllib 모두 기본으로 타임아웃이 없거나 아주 길다.
    • 모든 예외에서 다시 보내는 코드는 400, 422 같은 손님 쪽 잘못도 다시 보낸다. 다시 보내도 결과가 같은 오류(4xx)는 다시 보내지 않고, 타임아웃, 연결 실패, 503처럼 잠시 뒤 나아질 수 있는 것만 다시 보낸다. 4xx 가운데 429(너무 많은 요청)는 Retry-After만큼 기다렸다가, 408(요청 시간 초과)은 다시 보내도 된다.
    • 결제 같은 POST를 키 없이 다시 보내면 두 번 결제될 수 있다(문제 1). 키를 주문마다 만들고, 다시 보낼 때 같은 키를 쓰는지 본다. 다시 보낼 때마다 새 키를 만드는 실수도 흔하다.
    • 간격 없이 바로 다시 보내거나, 모두 같은 간격으로 보내는 코드는 회복 중인 서버를 다시 쓰러뜨린다. 간격을 늘리고 흩뜨리는지 본다.

    더 알아보기¶

    지수 백오프와 지터

    다시 보낼 때마다 기다리는 시간을 두 배로 늘린다(0.1초, 0.2초, 0.4초, …). 여기에 손님마다 0과 그 시간 사이의 무작위 값을 쓰면(지터), 동시에 실패한 손님들이 동시에 다시 보내지 않고 흩어진다. 횟수에도 끝을 둔다. 끝없이 다시 보내는 손님 수천 명은 그 자체로 공격과 같다.

    import random

def backoff(attempt, base=0.1, cap=5.0):     # attempt번째 다시 보낼 때 기다릴 시간(초)
    return random.uniform(0, min(cap, base * 2 ** attempt))
    정확히 한 번은 어렵다

    메시지를 "정확히 한 번" 전달하는 방법은 네트워크만으로는 없다. 보내는 쪽은 받았다는 답을 받아야 알 수 있는데, 그 답도 잃을 수 있기 때문이다. 실제 시스템은 "적어도 한 번" 보내고 받는 쪽이 중복을 알아보게(멱등하게) 해서, 결과가 한 번 처리된 것과 같게 만든다(69번(비동기 메시징)). "정확히 한 번"이라고 광고하는 도구도 대개 이 둘을 묶은 것이다.

    정리¶

    • 네트워크 호출의 결과는 성공, 실패, 모름 셋이다. 모름에 대비해 타임아웃을 정한다.
    • 다시 보내면 중복이 생길 수 있다. 두 번 처리되면 안 되는 요청은 멱등 키를 보내고, 서버는 받자마자 키를 적어 둔다. 간격을 늘리고 흩뜨려 다시 보낸다.
    • 네트워크가 끊기면 낡은 값으로라도 답할지(가용성), 답하지 않을지(일관성) 고른다. 다시 이어져도 어긋난 데이터는 저절로 맞춰지지 않는다.
