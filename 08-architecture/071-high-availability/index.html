    71. 서비스 무중단 운영: 이중화(Failover)와 무중단 배포(Rolling, Blue/Green, Canary)¶

    원리 동작을 예측하고 이상을 알아챌 수 있어야 하는 항목

    서버는 언젠가 죽고, 새 판은 자주 내보내야 한다. 그때마다 서비스가 멈추면 손님은 떠난다. 무중단 운영은 서버를 여러 대 두어 하나가 죽어도 나머지가 받게 하고(이중화), 새 판을 조금씩 내보내 문제가 있으면 일찍 되돌리는 것이다. 이 항목은 로드밸런서의 헬스 체크를 Python으로 짜서 서버 하나를 실제로 멈춰 보고, 세 가지 배포 방법을 견준다. 65번(수직 확장 vs 수평 확장)의 수평 확장과 67번(요청 경로의 구성 요소)의 로드밸런서 위에 서 있는 이야기다.

    이 항목에서 배우는 것¶

    • 이중화된 서버 하나가 죽을 때 로드밸런서가 알아채기까지 무슨 일이 생기는지 설명할 수 있다.
    • 롤링, 블루/그린, 카나리 배포의 차이와, 버그 있는 판을 내보낼 때의 피해를 예측할 수 있다.
    • 배포 중 옛 판과 새 판이 함께 도는 동안 깨지지 않게 바꾸는 방법을 설명할 수 있다.

    1. 하나가 죽으면, 알아채고 뺄 때까지 요청이 실패한다¶

    • 로드밸런서는 서버마다 주기적으로 "살아 있나"를 묻는다(헬스 체크). 답이 없으면 그 서버를 빼고 나머지에만 보낸다(페일오버).
    • 서버가 죽은 순간부터 다음 헬스 체크까지는 로드밸런서가 모르고 계속 보낸다. 이 PC에서 1초마다 체크하는 로드밸런서 앞에서 응답을 받을 때마다 20ms 쉬고 다시 요청하며 서버 하나를 체크 바로 뒤에 멈추니(가장 나쁜 때), 다음 체크가 그 서버를 빼기까지 요청 5~6개가 실패했다.
    • 로드밸런서가 실패한 요청을 다른 서버로 다시 보내면 손님이 보는 실패는 없어지지만 그 요청은 늦어진다. 다시 보내도 되는 요청인지는 70번(분산 시스템의 근본 문제)의 멱등성 이야기다. 헬스 체크 간격을 바꾸면 어떻게 되는지는 문제 1에서 본다.

    2. 새 판은 조금씩 내보내고, 문제가 보이면 되돌린다¶

    직접 해 보기새 판을 내보내는 세 가지 방법배포 방법(롤링, 블루/그린, 카나리)과 새 판에 버그가 있는지를 골라, 1분마다 새 판이 받는 요청의 몫과 실패한 요청 수, 배포를 마치는 때, 필요한 서버 수를 본다
    새 창에서 크게 열기
    • 롤링은 서버를 한 대씩 새 판으로 바꾼다. 서버를 더 두지 않아도 되지만, 다 바꾸는 동안 옛 판과 새 판이 함께 돈다.
    • 블루/그린은 새 판(그린)을 따로 모두 띄워 둔 뒤 로드밸런서가 한꺼번에 넘긴다. 되돌리기는 다시 넘기기만 하면 되지만, 배포하는 동안 서버가 두 배 든다.
    • 카나리는 새 판을 서버 한 대(요청의 일부)에만 먼저 내보내 지켜본다. 오류율이 오르면 그 한 대만 뺀다. 지표를 지켜보고 있어야 쓸 수 있다(72번(관측성)).

    3. 옛 판과 새 판이 함께 도는 동안에도 깨지지 않게 바꾼다¶

    • 어느 배포 방법이든 옛 판과 새 판이 같은 DB와 같은 메시지를 함께 쓰는 때가 있다(롤링과 카나리는 배포하는 동안, 블루/그린은 넘기기 전에 DB를 바꿀 때와 되돌릴 때). 새 판이 데이터의 모양을 한 번에 바꾸면 어떻게 되는지는 문제 3에서 본다.
    • 그래서 바꾸는 일을 여러 번의 배포로 나눈다. 먼저 새 모양을 더하고(넓히기), 데이터를 옮기고, 모든 서버가 새 판이 된 뒤에 옛 모양을 지운다(좁히기). 되돌릴 일이 생겨도 옛 판이 계속 돌 수 있다.

    예측해 보기¶

    문제 1. 1절의 실험에서 헬스 체크를 1초마다가 아니라 0.2초마다 하게 바꾼다. 로드밸런서가 다른 서버로 다시 보내지 않을 때 실패한 요청은 몇 개쯤일까? 헬스 체크를 아주 자주(예: 1ms마다) 하면 무엇이 나쁠까?

    정답과 해설

    2~3개다. 이 PC에서 5번 재니 모두 2~3개였다(1초마다일 때는 5~6개). 서버가 멈춘 뒤 다음 체크까지의 틈이 0.2초로 짧아졌다. 그래도 0이 되지는 않는다. 그 틈에, 그리고 다음 체크가 멈춘 서버의 답을 0.2초 기다리는 동안 그 서버로 간 요청은 실패한다. 체크를 아주 자주 하면 서버마다 헬스 체크에 답하느라 일이 늘고, 잠깐 느렸을 뿐인 서버를 죽었다고 빼 버리기 쉽다. 그래서 보통 몇 번 연속 실패해야 빼고, 몇 번 연속 성공해야 다시 넣는다.

    문제 2. 위젯에서 새 판에 버그가 있다고 놓는다. 세 방법 가운데 실패한 요청이 가장 많은 것과 가장 적은 것은 무엇이고, 각각 몇 개일까? 누르기 전에 계산해 본다.

    정답과 해설

    블루/그린이 400개로 가장 많고, 카나리가 40개로 가장 적다. 롤링은 80개다. 블루/그린은 모든 요청을 한꺼번에 새 판으로 넘겨, 알아채기까지 2분 동안 1분에 1,000개 × 20% = 200개씩 실패했다. 카나리는 요청의 10%만 새 판으로 가서 1분에 20개씩, 2분에 40개다. 롤링은 1분에 10%, 20%로 늘다가 2분에 알아채 1대씩 되돌리는 동안 10%가 더 갔다(20 + 40 + 20 = 80). 버그가 없을 때는 거꾸로 블루/그린이 가장 빨리 끝나고(0분), 카나리가 가장 늦다(13분). 빨리 내보내는 것과 피해를 줄이는 것을 맞바꾼다.

    문제 3. 롤링 배포 중이라 옛 판과 새 판이 함께 돈다. 새 판은 주문의 done을 completed로 이름만 바꿨다. 주문 1은 옛 판이, 주문 2는 새 판이 만들었다. 두 판이 두 주문을 읽으면 무엇이 출력될까?

    def create_v1(db, oid):                          # 옛 판: 주문에 done을 저장한다
    db[oid] = {"done": False}


def create_v2(db, oid):                          # 새 판: 이름을 completed로 바꿨다
    db[oid] = {"completed": False}


def show_v1(db, oid):
    return db[oid]["done"]


def show_v2(db, oid):
    return db[oid]["completed"]


db = {}
create_v1(db, 1)                                 # 롤링 배포 중이라 옛 판과 새 판이 함께 돈다
create_v2(db, 2)
for oid in [1, 2]:
    for name, show in [("옛 판", show_v1), ("새 판", show_v2)]:
        try:
            print(oid, name, show(db, oid))
        except KeyError as e:
            print(oid, name, "KeyError", e)
    정답과 해설 
    1 옛 판 False
1 새 판 KeyError 'completed'
2 옛 판 KeyError 'done'
2 새 판 False

    넷 가운데 둘이 실패했다. 손님이 어느 서버에 닿느냐에 따라 주문이 보이기도 하고 오류가 나기도 한다. 배포를 마치면 옛 판은 없어지지만, 그 전에 옛 판이 만든 주문 1은 새 판에서 계속 오류다. 새 판이 두 이름을 모두 읽고 함께 쓰게 하고(넓히기), 옛 주문을 옮긴 뒤, 마지막 배포에서 done을 지운다(3절 그림). 64번(REST API 설계)의 API 필드 이름 바꾸기와 같은 문제다.

    AI와 함께 확인하기¶

    AI 활용 과제: AI가 쓴 배포 절차 검토하기

    1. AI에게 "주문 표의 status 열을 state로 바꾸는 배포 계획을 써 줘. 서버 10대에 롤링 배포한다"라고 한다.
    2. 계획의 각 단계에서 옛 판과 새 판이 함께 돌 때 서로의 데이터를 읽을 수 있는지 표로 따진다.
    3. 중간에 되돌려야 할 때 옛 판이 계속 돌 수 있는지 확인하고, 안 되는 단계가 있으면 AI에게 보여 주고 단계를 나누게 한다.
    확인할 점
    • "열 이름을 바꾸고 새 판을 배포한다" 한 단계로 끝내는 계획이 흔하다. 롤링 중에는 옛 판이 없는 열을 찾아 오류가 난다(문제 3).
    • DB를 먼저 바꾸고 서버를 나중에 바꾸든, 그 반대든 한 번에 하면 그 사이에 깨진다. 새 열을 더하고, 두 열에 함께 쓰고, 데이터를 옮기고, 읽는 곳을 바꾸고, 옛 열을 지우는 여러 단계여야 한다.
    • 되돌리기를 생각했는지 본다. 옛 열을 지운 뒤에는 옛 판으로 되돌릴 수 없다. 그래서 지우기는 맨 마지막, 새 판이 충분히 안정된 뒤에 한다.

    더 알아보기¶

    가용성 숫자: 99.9%와 99.99%

    가용성 99.9%는 1년에 8.76시간, 99.99%는 52.6분까지 멈춰도 된다는 뜻이다(1년 8,760시간 × 0.1%, × 0.01%). 9가 하나 늘 때마다 허락된 시간은 10분의 1이 된다. 서버를 두 대로 늘리는 것만으로는 부족하고, 헬스 체크, 배포 방법, 장애를 알아채고 되돌리는 시간까지 모두 줄여야 한다. 66번(모놀리식 vs 마이크로서비스)처럼 여러 서비스를 차례로 부르면 가용성이 곱해져 낮아지는 것도 함께 따진다.

    이 항목의 측정 프로그램

    1절과 문제 1의 값은 이 PC(Core i9-14900KF, DDR5 64GB, Windows 11, Python 3.14.0)에서 아래 프로그램을 헬스 체크 간격마다 5번 실행한 범위다(python failover.py 1.0, python failover.py 0.2). 다시 보내지 않으면 1초마다일 때 요청 51~62개 가운데 5~6개가, 0.2초마다일 때 70~83개 가운데 2~3개가 실패했다. 다시 보내면 둘 다 0개였지만 가장 느린 응답이 205~246ms였다. 멈춘 서버를 기다리는 시간(0.2초)만큼 늦어진 것이다. 서버는 1초가 지난 뒤 첫 헬스 체크 바로 다음에 멈춰, 다음 체크까지 가장 오래 모르게 했다. 처음에는 정해진 시각(1.05초)에 멈췄는데, 0.2초마다일 때는 체크가 마침 그 시각에 닿느냐에 따라 실패가 0개에서 3개까지 흔들렸다.

    처음에는 로드밸런서도 손님도 0.5초를 기다리게 짰는데, 손님이 먼저 타임아웃으로 멈췄다. 이 PC(Windows)는 닫힌 포트에 연결하면 거절을 받고도 2초쯤 다시 시도해(41번(전송 계층 (TCP·UDP))), 로드밸런서가 멈춘 서버에 연결하는 데 0.5초를 다 썼기 때문이다. 그래서 로드밸런서가 서버를 기다리는 시간을 손님이 로드밸런서를 기다리는 시간보다 짧게 했다. 바깥 쪽 타임아웃이 안쪽보다 길어야 안쪽에서 다른 서버로 다시 보낼 시간이 남는다.

    # 71번 측정: 서버 A, B 앞의 로드밸런서가 정해진 간격(기본 1초)마다 헬스 체크를 한다.
# 1초가 지난 뒤 첫 헬스 체크 바로 다음에 B를 멈춘다(다음 체크까지 가장 오래 모르는, 가장 나쁜 때).
# 손님은 응답을 받을 때마다 20ms 쉬고 다시 요청한다(3초 동안). 로드밸런서가 B를 빼기 전까지 실패한 요청 수를 센다.
# (1) 실패하면 그대로 502를 준다 (2) 실패하면 다른 살아 있는 서버로 한 번 다시 보낸다
# 로드밸런서가 서버를 기다리는 시간은 0.2초, 손님이 로드밸런서를 기다리는 시간은 2초다
# 실행: python failover.py [헬스 체크 간격(초), 기본 1.0]
import http.client
import sys
import itertools
import threading
import time
from http.server import BaseHTTPRequestHandler, ThreadingHTTPServer


def handler(answer):
    class H(BaseHTTPRequestHandler):
        protocol_version = "HTTP/1.1"
        def do_GET(self):
            body = answer(self.path).encode()
            self.send_response(200)
            self.send_header("Content-Length", str(len(body)))
            self.end_headers()
            self.wfile.write(body)
        def log_message(self, *a):
            pass
    return H


def start(answer):
    s = ThreadingHTTPServer(("127.0.0.1", 0), handler(answer))
    threading.Thread(target=s.serve_forever, daemon=True).start()
    return s


def ask(port, path, timeout=0.2):
    c = http.client.HTTPConnection("127.0.0.1", port, timeout=timeout)
    try:
        c.request("GET", path)
        return c.getresponse().read().decode()
    finally:
        c.close()


def run(retry, interval):
    a, b = start(lambda p: "A"), start(lambda p: "B")
    backends = {"A": a.server_address[1], "B": b.server_address[1]}
    healthy = dict.fromkeys(backends, True)
    turn = itertools.count()
    stop = threading.Event()
    t0 = time.perf_counter()
    killed = []

    def kill_b():
        b.shutdown(); b.server_close()

    def health_check():                          # interval초마다 /health를 물어 답이 없으면 뺀다
        while not stop.is_set():
            for name, port in backends.items():
                try:
                    ask(port, "/health")
                    healthy[name] = True
                except (OSError, http.client.HTTPException):
                    healthy[name] = False
            if not killed and time.perf_counter() - t0 >= 1.0:   # 1초가 지난 뒤 첫 체크 바로 다음에 B를 멈춘다
                killed.append(True)
                threading.Thread(target=kill_b, daemon=True).start()
            stop.wait(interval)

    def forward(path):                           # 살아 있다고 아는 서버를 차례로 고른다
        names = [n for n in backends if healthy[n]]
        first = names[next(turn) % len(names)]
        tries = [first] + ([n for n in names if n != first] if retry else [])
        for name in tries:
            try:
                return ask(backends[name], path)
            except (OSError, http.client.HTTPException):   # 연결 실패, 타임아웃, 닫힌 포트에 잘못 이어진 연결
                continue
        return "502"

    lb = start(forward)
    threading.Thread(target=health_check, daemon=True).start()
    answers, slowest = [], 0.0
    while time.perf_counter() - t0 < 3.0:
        t = time.perf_counter()
        answers.append(ask(lb.server_address[1], "/orders", timeout=2.0))
        slowest = max(slowest, time.perf_counter() - t)
        time.sleep(0.02)
    stop.set()
    lb.shutdown(); a.shutdown()
    return answers.count("502"), len(answers), slowest


interval = float(sys.argv[1]) if len(sys.argv) > 1 else 1.0
for retry in [False, True]:
    failed, total, slowest = run(retry, interval)
    print(f"다른 서버로 다시 보내기 {retry}: 요청 {total}개 가운데 실패 {failed}개, 가장 느린 응답 {slowest * 1000:.0f} ms")

    정리¶

    • 이중화는 한 대가 죽으면 헬스 체크가 알아채고 뺄 때까지 잠깐 실패한다. 체크 간격과 로드밸런서의 다시 보내기로 그 틈을 줄인다.
    • 롤링은 서버를 더 두지 않고, 블루/그린은 되돌리기가 빠르고, 카나리는 버그의 피해가 가장 작다. 빨리 내보내는 것과 피해를 줄이는 것을 맞바꾼다.
    • 배포 중에는 옛 판과 새 판이 함께 돈다. 데이터의 모양은 넓히기, 옮기기, 좁히기의 여러 배포로 바꾼다.
