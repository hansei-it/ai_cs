    65. 시스템 규모 확장: 수직 확장(Scale-up) vs 수평 확장(Scale-out)¶

    원리 동작을 예측하고 이상을 알아챌 수 있어야 하는 항목

    손님이 늘면 서버 한 대로는 감당하지 못한다. 서버를 더 큰 기계로 바꿀 수도 있고(수직 확장), 같은 서버를 여러 대 둘 수도 있다(수평 확장). 섹션 8은 작은 주문 서비스를 이 PC에서 띄워 항목마다 아키텍처와 운영의 문제 하나씩을 본다. 이 항목에서는 주문 서버와 DB를 따로 띄워, 서버를 늘릴 때 처리량이 어떻게 바뀌는지 잰다. 예제는 Python 표준 라이브러리만 쓴다(실습 환경).

    이 항목에서 배우는 것¶

    • 수직 확장과 수평 확장의 장단점을 설명할 수 있다.
    • 처리량이 어느 자원에서 막히는지(병목) 예측하고, 서버를 늘려도 빨라지지 않는 경우를 알아볼 수 있다.
    • 수평 확장을 하려면 상태를 서버 밖에 두어야 하는 까닭을 설명할 수 있다.

    1. 서버 한 대를 키우거나, 같은 서버를 여러 대 둔다¶

    • 수직 확장은 서버를 CPU와 메모리가 더 큰 기계로 바꾼다. 코드를 거의 고칠 필요가 없지만(늘어난 코어는 프로그램이 일을 나눠 써야 쓰인다), 살 수 있는 가장 큰 기계가 상한이고 그 한 대가 멈추면 서비스 전체가 멈춘다.
    • 수평 확장은 같은 서버를 여러 대 두고 로드밸런서가 요청을 나눠 준다(67번(요청 경로의 구성 요소)). 서버를 더하는 만큼 늘고 한 대가 죽어도 나머지가 받는다. 대신 서버들이 함께 쓰는 DB가 다음 병목이 되고, 상태를 서버 밖에 두어야 한다(3절).
    • 클라우드에서는 손님이 몰릴 때만 서버를 늘렸다 줄이는 자동 확장을 쓴다(92번(쿠버네티스와 서버리스)). 수평 확장이 되는 구조여야 쓸 수 있다.

    2. 기다림이 많은 서버는 동시 처리 수만큼 빨라지다가, 함께 쓰는 곳에서 막힌다¶

    직접 해 보기서버를 늘리면 얼마나 빨라지나서버 수, 서버마다 동시에 처리하는 요청 수, DB가 동시에 처리하는 질의 수를 골라, 1초에 처리하는 주문 수와 막히는 곳(병목), 손님이 기다리는 시간을 본다
    새 창에서 크게 열기
    • 주문 서버는 요청 하나에 52ms쯤 걸리는데, 그 가운데 50ms가 DB의 답을 기다리는 시간이다. 그래서 CPU의 빠르기보다 동시에 몇 개를 처리하느냐가 처리량을 정한다. 이 PC에서 서버 한 대가 동시에 1개씩 처리하면 1초에 19.1~19.2개, 16개씩 처리하면 305.9~313.6개였다.
    • 서버를 늘려도 마찬가지다. 동시 4개짜리 서버를 1대에서 2대로 늘리니 1초에 76.6~77.8개에서 154.6~156.8개로 두 배가 되었다(DB 동시 처리 100개). 4대, 8대로 더 늘리면 어떻게 될지는 문제 1에서 본다.
    • 병목은 옮겨 다닌다. 한 곳을 늘리면 다음으로 좁은 곳이 막힌다. 어디를 늘릴지는 추측하지 말고 재 보고 정한다(88번(성능 측정과 프로파일링)).

    3. 여러 대로 나누려면 상태를 서버 밖에 둔다¶

    • 로그인 정보나 장바구니를 서버 메모리에 두면, 다음 요청이 다른 서버로 갈 때 어떻게 될까(문제 2).
    • 수평 확장할 서버는 요청 사이에 기억하는 것이 없게(무상태) 만든다. 상태는 서버들이 함께 쓰는 저장소(DB, Redis 같은 캐시 서버)나 서명한 토큰(47번(쿠키, 세션, 토큰(JWT)))에 둔다.

    예측해 보기¶

    문제 1. 위젯에서 동시 4개짜리 서버, DB 동시 처리 10개로 놓고 서버를 1대, 2대, 4대, 8대로 늘린다. 1초에 처리하는 주문 수는 어떻게 바뀔까? 위젯을 누르기 전에 먼저 적어 본다.

    정답과 해설

    2대까지는 두 배씩 늘지만, 4대부터는 1초에 196개 근처에서 멈춘다. 이 PC에서 잰 값은 1대 77.0~78.1개, 2대 153.2~156.7개, 4대 195.3~196.0개, 8대 195.5~195.9개였다. DB가 질의를 10개까지만 동시에 처리하고 질의마다 51ms쯤 걸리므로, DB가 1초에 받을 수 있는 질의는 10 ÷ 0.051 ≈ 196개다. 서버를 8대로 늘려도 처리량은 그대로이고, 늘린 서버의 값만 든다. 위젯에서 손님이 기다리는 시간도 4대와 8대가 같다. 줄이 서버 앞에서 DB 앞으로 옮겨 갔을 뿐이다. 이때는 DB가 동시에 더 처리하게 키우거나(더 큰 DB, 읽기 전용 복제본), DB에 묻는 일을 줄여야(캐시, 68번(캐싱 전략과 캐시 무효화)) 빨라진다. 주문 서버가 DB 연결만 더 여는 것은 DB에 여력이 있을 때만 듣는다(56번(애플리케이션과 DB 연동)).

    문제 2. 로드밸런서가 요청을 서버 A와 B에 차례로 나눠 준다. 서버는 로그인 정보를 자기 메모리에 둔다. 무엇이 출력될까?

    class Server:
    def __init__(self, name):
        self.name = name
        self.sessions = {}                       # 로그인 정보를 이 서버의 메모리에 둔다

    def handle(self, cookie, path):
        if path == "/login":
            self.sessions[cookie] = "김하나"
            return f"{self.name}: 로그인했다"
        return f"{self.name}: {self.sessions.get(cookie, '로그인하세요')}"


servers = [Server("A"), Server("B")]
for i, path in enumerate(["/login", "/cart", "/cart", "/orders"]):
    print(servers[i % 2].handle("s1", path))     # 로드밸런서가 요청을 차례로 나눠 준다
    정답과 해설 
    A: 로그인했다
B: 로그인하세요
A: 김하나
B: 로그인하세요

    로그인을 받은 서버 A만 s1을 안다. B로 간 요청은 로그인하지 않은 손님으로 보인다. 손님에게는 화면이 한 번씩 로그인 창으로 바뀌는 버그다. 서버가 한 대일 때는 드러나지 않다가 서버를 늘리는 순간 나타난다. 두 서버가 같은 저장소를 보게 하면(아래처럼 sessions를 함께 쓰면) 로그인 뒤의 세 요청이 모두 김하나다.

    shared = {}                                      # 두 서버가 함께 쓰는 세션 저장소
servers = [Server("A"), Server("B")]
for server in servers:
    server.sessions = shared
for i, path in enumerate(["/login", "/cart", "/cart", "/orders"]):
    print(servers[i % 2].handle("s1", path))

    A: 로그인했다
B: 김하나
A: 김하나
B: 김하나

    문제 3. 동시 4개짜리 서버 한 대, DB 동시 처리 100개다. 서버를 CPU가 두 배 빠른 기계로 바꾸면(수직 확장) 1초에 처리하는 주문 수는 얼마나 늘까?

    정답과 해설

    거의 늘지 않는다. 이 PC에서 주문 서버는 요청 하나에 CPU를 0.44~0.59ms 썼다(5번 잰 범위). 요청 하나에 걸리는 52ms의 1% 안팎이다. CPU가 두 배 빨라져도 요청 하나가 0.2~0.3ms 짧아질 뿐이라 처리량은 1% 안쪽으로 는다. 나머지 시간은 DB를 기다린다. 이런 서버는 큰 기계로 바꾸기보다 동시에 처리하는 수를 늘리거나(위젯의 동시 처리) 기다림 자체를 줄여야 빨라진다. 수직 확장이 효과가 있는지도 어디서 시간을 쓰는지 재 보고 정한다.

    AI와 함께 확인하기¶

    AI 활용 과제: 확장 계획의 가정 검증하기

    1. AI에게 "주문 API가 1초에 150건을 넘으면 느려진다. 1초에 1,000건을 받으려면 서버를 몇 대로 늘려야 하나?"라고 묻는다.
    2. 답이 무엇을 가정했는지 적는다. 서버 한 대의 처리량, 함께 쓰는 DB의 한계, 로그인 정보 같은 상태를 어디에 두는지.
    3. 위젯이나 측정 프로그램으로 그 가정이 맞는지 확인하고, 빠진 병목을 AI에게 보여 주고 다시 계획하게 한다.
    확인할 점
    • "한 대가 150건이니 7대"처럼 서버 수만 곱하는 답이 흔하다. 서버 뒤에서 모두가 함께 쓰는 것(DB가 동시에 처리하는 질의 수, DB가 받는 연결 수, 외부 API의 한도)이 그보다 먼저 막히면 서버를 늘려도 소용없다(문제 1).
    • 서버를 늘리기 전에 그 서버가 무상태인지 묻는다. 로그인이나 장바구니를 메모리에 두는 서버는 늘리는 순간 고장 난다(문제 2).
    • 좋은 답은 "어디가 먼저 막히는지 재 보자"로 시작한다. 측정 없이 숫자를 정하는 답은 받아들이지 않는다.

    더 알아보기¶

    손님이 기다리는 시간: 리틀의 법칙

    시스템 안에 있는 요청 수(L)는 처리량(λ)과 요청 하나가 머무는 시간(W)의 곱이다(L = λW). 이 항목의 측정에서는 손님 64명이 늘 요청을 하나씩 보내 놓고 기다리므로 L = 64다. 그래서 한 사람이 기다리는 시간은 64 ÷ 처리량이다. 서버 한 대가 동시에 1개만 처리하면(1초에 19개) 손님 한 명이 3초 넘게 기다리고, 처리량이 늘수록 기다림이 준다. DB에서 막힌 뒤로는 서버를 늘려도 처리량이 그대로라 기다림도 그대로다.

    Python의 GIL과 이 실험

    이 실험은 요청 처리 시간 대부분이 기다림이라, 한 프로세스 안에서 스레드로 동시 처리 수를 늘려도 처리량이 잘 늘었다. CPU 계산이 대부분인 일은 다르다. 이 PC에서 같은 계산 4개를 스레드 1개로 하면 1.05~1.07초, 스레드 4개로 나눠도 1.05~1.20초였고, 프로세스 4개로 나누면 0.28~0.29초였다(아래 프로그램으로 5번 잰 범위). 기본 Python은 한 프로세스에서 한 번에 한 스레드만 Python 코드를 실행하기 때문이다(GIL). Python 3.14부터 GIL을 없앤 빌드도 정식으로 지원하지만, 따로 골라 설치해야 한다. 기다림 4개(0.2초씩)는 스레드 1개로 0.80초, 4개로 0.20초였다. 그래서 CPU를 많이 쓰는 Python 서버는 프로세스를 여러 개 띄운다(33번(동시성과 병렬성)).

    # 65번 GIL 확인: CPU 계산을 스레드 4개와 프로세스 4개로 나눠 할 때, 기다림을 스레드 4개로 나눠 할 때
import time
from concurrent.futures import ProcessPoolExecutor, ThreadPoolExecutor


def work(_):                       # CPU만 쓰는 계산
    s = 0
    for i in range(10_000_000):
        s += i * i
    return s


def wait(_):                       # 기다리기만 하는 일
    time.sleep(0.2)


def timed(pool_cls, fn, n):
    with pool_cls(max_workers=n) as pool:
        list(pool.map(fn, range(n)))          # 데우기(스레드나 프로세스 n개를 미리 띄운다)
        t = time.perf_counter()
        list(pool.map(fn, range(4)))
        return time.perf_counter() - t


if __name__ == "__main__":
    print(f"계산 4개, 스레드 1개: {timed(ThreadPoolExecutor, work, 1):.2f}초")
    print(f"계산 4개, 스레드 4개: {timed(ThreadPoolExecutor, work, 4):.2f}초")
    print(f"계산 4개, 프로세스 4개: {timed(ProcessPoolExecutor, work, 4):.2f}초")
    print(f"기다림 4개, 스레드 1개: {timed(ThreadPoolExecutor, wait, 1):.2f}초")
    print(f"기다림 4개, 스레드 4개: {timed(ThreadPoolExecutor, wait, 4):.2f}초")

    이 항목의 측정 프로그램

    2절과 문제 1의 값은 이 PC(Core i9-14900KF, DDR5 64GB, Windows 11, Python 3.14.0)에서 아래 프로그램을 5번 실행한 범위다. DB 서버, 주문 서버, 부하를 주는 쪽을 다른 프로세스로 띄워 127.0.0.1에서 HTTP로 주고받는다. 부하를 주는 쪽은 손님 64명이 쉬지 않고 요청하고, 서버가 여럿이면 차례로 고른다(로드밸런서 역할). 처음에는 Python 서버의 접속 대기열이 기본값(5)이라 손님 64명이 한꺼번에 접속할 때 연결이 끊겼다. 대기열을 128로 늘려 오류 없이 쟀다.

    # 65번 측정: 주문 서버를 늘리면 처리량이 어떻게 바뀌나
# DB 서버(동시에 처리하는 질의 수 한도가 있고, 질의마다 50ms를 기다린다), 주문 서버(동시에 처리하는 요청 수 한도),
# 부하를 주는 쪽(스레드 여럿이 주문 서버들에 차례로 요청)을 따로 띄운다. 모두 이 PC(127.0.0.1)에서 돈다.
# 실행: python scale_measure.py
import http.client
import subprocess
import sys
import threading
import time
from http.server import BaseHTTPRequestHandler, ThreadingHTTPServer


def serve(port, handle):                 # 요청마다 handle()을 부르는 HTTP/1.1 서버(연결을 이어 쓴다)
    class H(BaseHTTPRequestHandler):
        protocol_version = "HTTP/1.1"
        def do_GET(self):
            body = handle().encode()
            self.send_response(200)
            self.send_header("Content-Length", str(len(body)))
            self.end_headers()
            self.wfile.write(body)
        def log_message(self, *a):
            pass
    class S(ThreadingHTTPServer):
        request_queue_size = 128         # 기본값 5면 손님 64명이 한꺼번에 접속할 때 넘친 연결이 끊긴다
    S(("127.0.0.1", port), H).serve_forever()


def db(port, limit):                     # DB: 질의를 limit개까지 동시에 처리하고, 질의마다 50ms
    slots = threading.Semaphore(limit)
    def handle():
        with slots:
            time.sleep(0.05)
        return "row"
    serve(port, handle)


def app(port, db_port, workers):         # 주문 서버: 요청을 workers개까지 동시에 처리하고, 처리마다 DB에 한 번 묻는다
    slots = threading.Semaphore(workers)
    local = threading.local()
    def handle():
        with slots:
            if not hasattr(local, "c"):
                local.c = http.client.HTTPConnection("127.0.0.1", db_port)
            local.c.request("GET", "/")
            local.c.getresponse().read()
        return "ok"
    serve(port, handle)


def load(ports, seconds=3.0, clients=64):   # 부하: 손님 64명이 쉬지 않고 요청한다. 서버는 차례로 고른다
    done, errors, stop = [0], [0], time.perf_counter() + seconds
    lock = threading.Lock()
    def client(k):
        conns = {p: http.client.HTTPConnection("127.0.0.1", p) for p in ports}
        i = k
        while time.perf_counter() < stop:
            p = ports[i % len(ports)]
            i += 1
            try:
                conns[p].request("GET", "/")
                conns[p].getresponse().read()
                with lock:
                    done[0] += 1
            except OSError:                  # 연결이 끊기면 세고 새로 잇는다
                with lock:
                    errors[0] += 1
                conns[p] = http.client.HTTPConnection("127.0.0.1", p)
    ts = [threading.Thread(target=client, args=(k,)) for k in range(clients)]
    t0 = time.perf_counter()
    for t in ts: t.start()
    for t in ts: t.join()
    assert errors[0] == 0, f"연결 오류 {errors[0]}번"
    return done[0] / (time.perf_counter() - t0)


def run(servers, workers, limit):
    procs = [subprocess.Popen([sys.executable, __file__, "db", "18600", str(limit)])]
    ports = [18601 + k for k in range(servers)]
    procs += [subprocess.Popen([sys.executable, __file__, "app", str(p), "18600", str(workers)]) for p in ports]
    time.sleep(1.0)                      # 서버가 뜰 때까지
    try:
        load(ports, seconds=1.0)         # 데우기
        return load(ports)
    finally:
        for p in procs:
            p.kill()
            p.wait()


if __name__ == "__main__":
    if sys.argv[1:2] == ["db"]:
        db(int(sys.argv[2]), int(sys.argv[3]))
    elif sys.argv[1:2] == ["app"]:
        app(int(sys.argv[2]), int(sys.argv[3]), int(sys.argv[4]))
    else:
        for w in [1, 2, 4, 8, 16]:
            print(f"서버 1대, 동시 처리 {w:2}개, DB 동시 처리 100개: {run(1, w, 100):6.1f} 요청/초")
        print(f"서버 2대, 동시 처리  4개, DB 동시 처리 100개: {run(2, 4, 100):6.1f} 요청/초")
        for n in [1, 2, 4, 8]:
            print(f"서버 {n}대, 동시 처리  4개, DB 동시 처리  10개: {run(n, 4, 10):6.1f} 요청/초")

    문제 3의 CPU 시간은 같은 폴더에 둔 아래 프로그램으로 쟀다. 주문 서버 프로세스가 6초 동안 쓴 CPU 시간을 그동안 처리한 요청 수로 나눈다.

    # 65번 측정 2: 주문 서버가 요청 하나에 CPU를 얼마나 쓰나 (scale_measure.py와 같은 폴더에 둔다)
# 주문 서버(동시 16개)와 DB(동시 처리 100개)를 띄우고 부하를 준 뒤, 6초 동안 주문 서버 프로세스가 쓴 CPU 시간 ÷ 처리한 요청 수를 찍는다
# (Windows는 프로세스의 CPU 시간을 15.6ms 눈금으로 세므로 요청을 많이 처리하게 해 눈금의 영향을 줄인다)
import subprocess
import sys
import threading
import time

import scale_measure as m

if sys.argv[1:2] == ["app"]:              # 주문 서버: 2초 뒤부터 6초 동안의 CPU 시간과 요청 수를 잰다
    count = [0]
    original = m.serve
    def counting_serve(port, handle):        # 요청마다 수를 센 뒤 원래 서버로 띄운다
        def h():
            r = handle()
            count[0] += 1
            return r
        original(port, h)
    m.serve = counting_serve
    def report():
        time.sleep(2.0)
        c0, p0 = count[0], time.process_time()
        time.sleep(6.0)
        c1, p1 = count[0], time.process_time()
        print(f"요청 {c1 - c0}개, CPU {(p1 - p0) * 1000:.0f} ms, 요청 하나에 {(p1 - p0) * 1000 / (c1 - c0):.2f} ms", flush=True)
    threading.Thread(target=report, daemon=True).start()
    m.app(int(sys.argv[2]), int(sys.argv[3]), int(sys.argv[4]))
else:
    db = subprocess.Popen([sys.executable, m.__file__, "db", "18600", "100"])
    app = subprocess.Popen([sys.executable, __file__, "app", "18601", "18600", "16"])
    time.sleep(1.0)
    try:
        m.load([18601], seconds=8.5)
        time.sleep(0.5)
    finally:
        app.kill(); db.kill(); app.wait(); db.wait()

    정리¶

    • 수직 확장은 코드를 거의 그대로 두지만 상한과 단일 장애점이 있다. 수평 확장은 늘린 만큼 받지만 상태를 서버 밖에 두고 요청을 나눠 줄 장치가 있어야 한다.
    • 처리량은 가장 좁은 곳에서 정해진다. 기다림이 많은 서버는 동시 처리 수만큼 빨라지다가, 함께 쓰는 DB 같은 곳에서 막힌다. 막힌 뒤에는 서버를 늘려도 그대로다.
    • 서버를 늘리기 전에 어디가 먼저 막히는지 재고, 서버가 무상태인지 확인한다.
