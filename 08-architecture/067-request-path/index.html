    67. 요청 경로의 구성 요소: 웹 서버와 WAS, 로드밸런서(L4/L7), API 게이트웨이¶

    원리 동작을 예측하고 이상을 알아챌 수 있어야 하는 항목

    브라우저의 요청은 주문 서버에 바로 닿지 않는다. 브라우저가 DNS로 찾은 주소(42번(DNS))는 보통 로드밸런서의 것이고, 요청은 로드밸런서, 웹 서버, 애플리케이션 서버(WAS)를 차례로 지난다. 서비스가 여럿이면 서비스 앞에서 API 게이트웨이를 지난다. 이 항목은 그 길의 구성 요소가 저마다 무엇을 맡는지 보고, 로드밸런서와 게이트웨이의 핵심 동작을 Python으로 작게 짜서 확인한다. 65번(수직 확장 vs 수평 확장)에서 서버를 여러 대로 늘릴 때 요청을 나눠 준 것이 로드밸런서다.

    이 항목에서 배우는 것¶

    • 요청이 지나는 로드밸런서, 웹 서버, WAS, DB가 저마다 맡는 일을 설명할 수 있다.
    • L4와 L7 로드밸런서의 차이와, 나누는 방법에 따라 응답 시간이 어떻게 달라지는지 예측할 수 있다.
    • API 게이트웨이가 한곳에서 하는 일과 속도 제한의 동작을 설명할 수 있다.

    1. 요청은 로드밸런서, 웹 서버, WAS를 차례로 지난다¶

    • 로드밸런서는 요청을 받을 서버를 고르고, 헬스 체크로 죽은 서버를 뺀다(71번(이중화와 무중단 배포)). 손님은 서버가 몇 대인지 모른다.
    • 웹 서버는 이미지, CSS 같은 정적 파일을 바로 주고, TLS를 풀고(45번(HTTPS와 TLS), L7 로드밸런서가 대신 풀기도 한다), 응답을 압축한다. 이런 일은 빠르게 많이 하도록 만든 제품이 따로 있다.
    • WAS는 주문 처리처럼 매번 계산해야 하는 애플리케이션 코드를 돌린다. 정적 파일까지 WAS가 주면 비싼 일꾼이 쉬운 일에 묶인다.

    2. L4는 연결을 나누고, L7은 요청을 나눈다¶

    직접 해 보기로드밸런서가 요청을 나누는 방법나누는 방법(L4 연결 단위 라운드 로빈, L7 요청 단위 라운드 로빈, L7 최소 연결)과 느린 요청의 자리를 골라, 서버 셋이 요청을 언제 처리하는지와 평균 응답 시간을 본다
    새 창에서 크게 열기
    • L4 로드밸런서는 전송 계층(TCP)에서 일한다. 연결이 들어올 때 서버를 고르고, 그 연결의 바이트는 내용을 보지 않고 그대로 잇는다. 빠르고 단순하지만 HTTP 요청이 무엇인지 모른다.
    • L7 로드밸런서는 HTTP 요청을 하나씩 열어 본다. 요청마다 서버를 고를 수 있고, 주소나 머리에 따라 다른 서버로 보낼 수 있다. 대신 TLS를 풀어야 내용을 볼 수 있어 일이 많다.
    • 고르는 방법도 다르다. 라운드 로빈은 차례대로 나누고, 최소 연결은 지금 맡은 요청이 가장 적은 서버로 보낸다. 느린 요청이 섞이면 차이가 커진다(위젯, 문제 3).

    3. API 게이트웨이는 서비스 앞에서 공통의 일을 한곳에서 한다¶

    • 서비스가 여럿이면(66번(모놀리식 vs 마이크로서비스)) 손님이 서비스마다 주소를 알 필요 없이 API 게이트웨이 하나로 보낸다. 게이트웨이는 주소를 보고 서비스로 보내는 L7 장치다.
    • 인증 확인, 속도 제한, 기록처럼 모든 서비스가 해야 하는 일을 한곳에서 한다. 속도 제한은 손님마다 일정한 빠르기를 넘는 요청을 429(Too Many Requests)로 돌려보내 서비스를 지킨다(문제 2).

    예측해 보기¶

    문제 1. 서버 A, B 앞에 L4 로드밸런서와 L7 로드밸런서를 Python으로 짰다. 둘 다 서버를 차례로 고른다. 손님 하나가 연결 하나로 요청 넷을 보내면, 각각 어느 서버가 답할까?

    import http.client
import itertools
import socket
import threading
from http.server import BaseHTTPRequestHandler, ThreadingHTTPServer


def backend(name):                               # 주문 서버: 자기 이름을 답한다
    class H(BaseHTTPRequestHandler):
        protocol_version = "HTTP/1.1"            # 연결을 이어 쓴다
        def do_GET(self):
            body = name.encode()
            self.send_response(200)
            self.send_header("Content-Length", str(len(body)))
            self.end_headers()
            self.wfile.write(body)
        def log_message(self, *a):
            pass
    s = ThreadingHTTPServer(("127.0.0.1", 0), H)
    threading.Thread(target=s.serve_forever, daemon=True).start()
    return s


def l4_proxy(ports):                             # L4: 연결이 들어오면 서버를 하나 골라 바이트를 그대로 잇는다
    pick = itertools.cycle(ports)
    lsock = socket.create_server(("127.0.0.1", 0))
    def pipe(a, b):                              # a에서 받은 것을 b로 보낸다. a가 끝나면 b에 보내는 쪽만 닫는다
        try:
            while data := a.recv(65536):
                b.sendall(data)
            b.shutdown(socket.SHUT_WR)
        except OSError:
            pass
    def accept():
        while True:
            client, _ = lsock.accept()
            server = socket.create_connection(("127.0.0.1", next(pick)))   # 연결마다 한 번 고른다
            threading.Thread(target=pipe, args=(client, server), daemon=True).start()
            threading.Thread(target=pipe, args=(server, client), daemon=True).start()
    threading.Thread(target=accept, daemon=True).start()
    return lsock.getsockname()[1]


def l7_proxy(ports):                             # L7: HTTP 요청을 하나씩 열어 보고 요청마다 서버를 고른다
    pick = itertools.cycle(ports)
    class H(BaseHTTPRequestHandler):
        protocol_version = "HTTP/1.1"
        def do_GET(self):
            c = http.client.HTTPConnection("127.0.0.1", next(pick))      # 요청마다 고른다
            c.request("GET", self.path)
            body = c.getresponse().read()
            c.close()
            self.send_response(200)
            self.send_header("Content-Length", str(len(body)))
            self.end_headers()
            self.wfile.write(body)
        def log_message(self, *a):
            pass
    s = ThreadingHTTPServer(("127.0.0.1", 0), H)
    threading.Thread(target=s.serve_forever, daemon=True).start()
    return s.server_address[1]


servers = [backend("A"), backend("B")]
ports = [s.server_address[1] for s in servers]
for name, port in [("L4", l4_proxy(ports)), ("L7", l7_proxy(ports))]:
    conn = http.client.HTTPConnection("127.0.0.1", port)          # 손님 하나가 연결 하나로 요청 넷을 보낸다
    answers = []
    for _ in range(4):
        conn.request("GET", "/orders")
        answers.append(conn.getresponse().read().decode())
    conn.close()
    print(name, answers)
    정답과 해설 
    L4 ['A', 'A', 'A', 'A']
L7 ['A', 'B', 'A', 'B']

    L4는 연결이 들어올 때 한 번 서버를 고르고, 그 뒤로는 바이트를 그대로 이을 뿐이다. 손님이 연결을 이어 쓰면(HTTP/1.1) 요청 넷이 모두 A로 간다. L7은 요청을 하나씩 읽어 그때마다 고르므로 A와 B가 번갈아 답했다. 브라우저와 앱은 연결을 오래 이어 쓰므로, 손님이 적고 연결이 오래가면 L4는 서버 사이가 고르지 않다. 이 PC에서 8번 실행해 모두 같았다.

    문제 2. 게이트웨이가 손님마다 아래 토큰 버킷으로 속도를 제한한다. 통에는 토큰이 5개까지 들어가고 1초에 1개씩 다시 찬다. 요청 하나가 토큰 하나를 쓴다. 무엇이 출력될까?

    class TokenBucket:                                # 손님마다 하나씩 둔다
    def __init__(self, size, per_second):
        self.size = size                          # 통에 담을 수 있는 토큰 수(한꺼번에 받아 주는 요청 수)
        self.per_second = per_second              # 1초에 다시 채워지는 토큰 수
        self.tokens = size
        self.last = 0.0

    def allow(self, now):                         # now: 요청이 온 시각(초)
        self.tokens = min(self.size, self.tokens + (now - self.last) * self.per_second)
        self.last = now
        if self.tokens >= 1:
            self.tokens -= 1
            return 200                            # 서비스로 보낸다
        return 429                                # Too Many Requests


bucket = TokenBucket(size=5, per_second=1)
print([bucket.allow(0.0) for _ in range(8)])      # 처음(0초)에 한꺼번에 8번
print([bucket.allow(2.5) for _ in range(3)])      # 그 뒤 2.5초에 3번
    정답과 해설 
    [200, 200, 200, 200, 200, 429, 429, 429]
[200, 200, 429]

    0초에는 통에 있던 5개로 다섯 요청을 받고, 나머지 셋은 429다. 2.5초 동안 토큰이 2.5개 찼으므로 두 요청을 받고 셋째는 429다. 토큰 버킷은 잠깐 몰리는 요청(통의 크기만큼)은 받아 주고, 오래 이어지는 빠르기는 다시 차는 속도로 묶는다. 429를 받은 클라이언트는 바로 다시 보내지 말고 기다렸다가 보낸다(응답의 Retry-After 머리가 기다릴 시간을 알려 주기도 한다).

    문제 3. 위젯에서 느린 요청을 1번에 두고 세 방법을 고른다. 평균 응답 시간이 긴 차례대로 적어 본다. 누르기 전에 먼저 적는다.

    정답과 해설

    L4 라운드 로빈(675ms), L7 라운드 로빈(466.7ms), L7 최소 연결(216.7ms) 차례다. 위젯의 손님은 HTTP/2처럼 한 연결에 앞 응답을 기다리지 않고 요청을 겹쳐 보낸다. L4는 그 연결을 통째로 한 서버에 붙이므로 연결 2의 요청이 모두 B로 가서, 1.5초 걸리는 1번 뒤에 줄을 섰다. 연결이 둘뿐이라 C는 놀았다. L7 라운드 로빈은 셋에 고르게 나누지만 B가 바쁜지 보지 않고 4번, 7번, 10번을 보내 그 요청들이 기다렸다. 최소 연결은 느린 요청을 맡은 서버를 피해 다른 요청이 기다리지 않았다. 다만 최소 연결도 "요청 수"만 보므로, 요청마다 걸리는 시간이 크게 다르면 완전하지 않다. 위젯의 시간은 이 규칙으로 계산한 값이다.

    AI와 함께 확인하기¶

    AI 활용 과제: AI가 짠 속도 제한 검증하기

    1. AI에게 "Python으로 사용자마다 1분에 60번까지만 받는 속도 제한 함수를 짜 줘"라고 한다.
    2. 실행하기 전에, 0초에 100번이 몰려올 때와 59초에 60번, 61초에 60번이 올 때 각각 몇 번을 받는지 예측해 적는다.
    3. 시각을 인자로 넘겨 그 상황을 실행해 보고, 예측과 다르면 왜 다른지 AI에게 묻는다.
    확인할 점
    • "1분마다 세는 수를 0으로 되돌리는" 고정 창 방식이 흔하다. 59초에 60번, 61초에 60번을 보내면 둘 다 받아 2초 사이에 120번을 받는다. 창의 경계에서 두 배가 새는 것이다. 토큰 버킷(통 60개, 1초에 1개)은 경계에서 두 배가 새지는 않지만, 통이 가득 찬 채 시작하면 어느 60초 동안 "통의 크기 + 그동안 다시 찬 만큼"까지 받는다(0초에 60번, 그 뒤 1초마다 1번이면 60초 안에 119번). 어느 60초든 60번을 넘기지 않으려면 최근 60초의 요청을 미끄러지며 센다.
    • 시각을 time.time()으로 함수 안에서 읽으면 이런 상황을 시험하기 어렵다. 문제 2처럼 시각을 인자로 받으면 시험할 수 있다(84번(테스트 설계)).
    • 서버가 여러 대면 서버마다 세는 수가 따로라, 실제 한도가 서버 수만큼 커진다. 여러 서버가 함께 세려면 함께 쓰는 저장소가 필요하다(65번(수직 확장 vs 수평 확장)의 상태 이야기와 같다).

    더 알아보기¶

    고정 세션: 같은 손님을 같은 서버로

    L7 로드밸런서는 쿠키를 보고 같은 손님을 늘 같은 서버로 보낼 수 있다(고정 세션, sticky session). 65번(수직 확장 vs 수평 확장)처럼 상태를 서버 메모리에 둔 서비스를 늘릴 때 쓰는 임시방편이다. 그 서버가 죽거나 배포로 내려가면 그 손님들의 상태가 사라지고, 손님이 고르게 나뉘지 않는다. 상태를 서버 밖에 두는 것이 근본적인 해결이다.

    L4와 L7은 OSI 7계층의 번호다

    L4는 전송 계층(TCP, UDP), L7은 응용 계층(HTTP)이다(39번(네트워크 계층 모델), 41번(전송 계층 (TCP·UDP))). L4 장치는 IP 주소와 포트만 보고 패킷의 주소를 바꿔 넘기거나 문제 1처럼 연결을 받아 서버로 새 연결을 이을 뿐이라 아주 빠르고, L7 장치는 메시지를 다 받아 읽은 뒤 다시 보내므로 일이 많지만 똑똑하게 나눈다. 클라우드의 로드밸런서도 두 종류를 따로 판다(네트워크 로드밸런서, 애플리케이션 로드밸런서).

    정리¶

    • 요청은 로드밸런서(서버 고르기), 웹 서버(정적 파일, TLS), WAS(애플리케이션 코드)를 차례로 지나 DB에 닿는다.
    • L4는 연결 단위로 내용을 보지 않고 나누고, L7은 요청을 열어 요청마다 나눈다. 느린 요청이 섞이면 서버의 바쁨을 보는 방법(최소 연결)이 낫다.
    • API 게이트웨이는 인증, 속도 제한, 경로 나누기, 기록을 서비스 앞 한곳에서 한다. 모든 요청이 지나므로 게이트웨이도 여러 대로 둔다.
