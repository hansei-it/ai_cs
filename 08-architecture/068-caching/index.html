    68. 캐싱 전략과 캐시 무효화 (Redis 등은 사례로)¶

    원리 동작을 예측하고 이상을 알아챌 수 있어야 하는 항목

    65번(수직 확장 vs 수평 확장)에서 서버를 늘려도 DB가 막히면 소용없었다. DB에 묻는 일 자체를 줄이는 가장 흔한 방법이 캐시다. 한 번 읽은 값을 빠른 곳(메모리, Redis 같은 캐시 서버)에 두고 다음에는 거기서 읽는다. 캐시는 빠르지만 원본과 어긋날 수 있다. "컴퓨터 과학에서 어려운 것은 캐시 무효화와 이름 짓기 두 가지뿐"이라는 농담(필 칼턴)이 있을 정도다. 이 항목은 캐시가 얼마나 빨라지게 하는지, 언제 낡은 값을 주는지, 언제 오히려 DB를 무너뜨리는지 본다. CPU 안의 캐시(5번(메모리 계층 구조))와 생각은 같다.

    이 항목에서 배우는 것¶

    • 캐시를 먼저 보는 읽기 방식과 적중률이 평균 시간과 DB 부하에 주는 영향을 설명할 수 있다.
    • TTL과 무효화 방법에 따라 낡은 값이 언제 생기는지 예측할 수 있다.
    • 인기 키가 만료될 때 생기는 캐시 쇄도와 막는 방법을 설명할 수 있다.

    1. 캐시를 먼저 보고, 없으면 DB에서 읽어 넣는다¶

    • 가장 흔한 방식은 서버가 캐시에 먼저 묻고, 없으면 DB에서 읽어 캐시에 넣는 것이다(cache-aside). 캐시에서 찾은 비율이 적중률이다.
    • 적중률이 평균 시간과 DB 부하를 함께 정한다. 적중률을 조금만 올려도 DB에 가는 질의가 크게 준다(문제 1).
    • 자주 읽고 드물게 바뀌는 데이터(상품 정보, 설정, 화면 조각)가 캐시에 잘 맞는다. 잔액이나 재고처럼 늘 정확해야 하는 값은 캐시에서 읽은 것을 그대로 믿으면 안 된다.

    2. 캐시는 원본과 어긋날 수 있다: TTL과 무효화¶

    직접 해 보기캐시가 낡은 값을 줄 때캐시를 쓰는 방법(캐시 없음, TTL만, 쓸 때 캐시 지우기, 지우기와 읽기가 겹칠 때)과 TTL을 골라, 4초마다 읽는 가격이 DB에서 왔는지, 캐시에서 맞게 왔는지, 낡은 값이었는지를 시간 줄에서 본다
    새 창에서 크게 열기
    • 캐시에 넣은 값에 수명(TTL)을 준다. TTL이 길수록 DB 질의는 줄지만, 원본이 바뀌어도 그동안 옛 값을 준다(위젯의 "TTL만").
    • 원본을 바꿀 때 캐시를 함께 지우면(무효화) 다음 읽기가 새 값을 가져온다. 다만 쓰는 코드마다 지우는 것을 잊지 않아야 한다.
    • 지우는 차례도 중요하다. 캐시를 먼저 지우고 DB를 고치면, 그 사이에 끼어든 읽기가 캐시에서 찾지 못해 DB의 옛 값을 다시 넣는다(위젯의 "지우기와 읽기가 겹칠 때"). DB를 먼저 고치고 지우면 괜찮은지는 문제 2에서 본다.
    • 무효화와 함께 TTL도 둔다. TTL은 "최악의 경우 이만큼까지 낡을 수 있다"는 약속이다.

    3. 인기 키가 만료되는 순간 읽기가 DB로 몰린다¶

    • 손님이 많이 읽는 키의 TTL이 끝나면, 그 순간 들어온 읽기가 모두 캐시에서 찾지 못하고 한꺼번에 DB로 간다(캐시 쇄도). 평소 캐시 덕분에 버티던 DB가 갑자기 몇십 배의 질의를 받는다.
    • 한 요청만 DB에서 읽어 채우게 하고 나머지는 기다렸다 캐시를 읽게 하면 막을 수 있다. 다만 자물쇠를 어떻게 거느냐에 따라 결과가 크게 달라진다(문제 3).

    예측해 보기¶

    문제 1. 주문 서버가 상품 정보를 1초에 1,000번 읽는다. 캐시 적중률이 90%면 DB는 1초에 질의를 몇 번 받을까? 99%면? 65번(수직 확장 vs 수평 확장)의 DB가 1초에 196번까지 받을 수 있다면, 적중률이 몇 %를 넘어야 버틸까?

    정답과 해설

    90%면 100번, 99%면 10번이다. 적중률이 80.4%를 넘어야 버틴다. 캐시에서 찾지 못한 읽기만 DB로 간다. 1,000 × (1 − 적중률) ≤ 196이어야 하므로 적중률은 0.804 이상이어야 한다. 적중률 90%에서 99%로 9%포인트 올렸을 뿐인데 DB 질의는 10분의 1이 되었다. 거꾸로, 캐시가 비거나 적중률이 갑자기 떨어지면 DB가 받는 질의가 순식간에 몇 배가 된다. 캐시 서버를 다시 띄운 직후나 인기 키가 만료된 순간이 그렇다(3절).

    문제 2. 손님 A가 가격을 읽는 사이에 관리자 B가 가격을 바꾸고 캐시를 지웠다. 일이 아래 차례로 일어났다면 무엇이 출력될까?

    db = {"price": 1000}
cache = {}

# A: 캐시에 없어서 DB에서 읽었다. 아직 캐시에 넣기 전이다
a_value = cache.get("price") or db["price"]

# B: 가격을 바꾸고 캐시를 지운다(무효화)
db["price"] = 1200
cache.pop("price", None)

# A: 아까 읽은 값을 캐시에 넣는다
cache["price"] = a_value

print(db["price"], cache["price"])
    정답과 해설

    1200 1000. B는 캐시를 제대로 지웠지만, B가 쓰기 전에 DB에서 옛 값을 읽어 둔 A가 지운 뒤에 그 값을 캐시에 넣었다. 이제 캐시는 TTL이 다할 때까지 낡은 1000원을 준다. DB를 먼저 고치고 지우는 차례에서도 이렇게 겹칠 수 있다. 다만 A의 읽기가 B의 쓰기보다 앞서고 A의 넣기가 B의 지우기보다 늦어야 해서, 캐시를 먼저 지울 때(위젯의 "지우기와 읽기가 겹칠 때")보다 틈이 훨씬 좁다. 그래서 DB를 먼저 고치고 지운다. 두 요청이 거의 같은 순간에 오가야 일어나서 시험에서는 잘 안 보이고, 손님이 많아지면 가끔 나타난다. 그래서 무효화와 함께 TTL을 짧게 두고, 더 막아야 하면 지운 뒤 조금 있다 한 번 더 지우거나, 지우는 대신 새 판 번호를 남겨 두어 그보다 옛 판은 넣지 못하게 한다.

    문제 3. 인기 상품의 캐시가 막 만료된 순간 50명이 함께 읽는다. 쇄도를 막으려고 자물쇠를 걸었다. DB 질의는 몇 번이고, 50명이 모두 읽기까지 몇 초(0.1초 단위로 반올림)가 걸릴까?

    import threading
import time

db_calls = 0


def db_read(key):                                # DB에서 읽는다(50ms)
    global db_calls
    db_calls += 1
    time.sleep(0.05)
    return f"{key}의 값"


lock = threading.Lock()


def get(cache, key):                             # 자물쇠를 걸어 한 번에 한 스레드만 DB에 가게 했다
    if key not in cache:
        with lock:
            cache[key] = db_read(key)
    return cache[key]


cache = {}                                       # 인기 상품의 캐시가 막 만료되었다
start = threading.Barrier(50)


def reader():
    start.wait()                                 # 50명이 같은 순간에 읽는다
    get(cache, "상품 7")


t = time.perf_counter()
threads = [threading.Thread(target=reader) for _ in range(50)]
for th in threads: th.start()
for th in threads: th.join()
print(db_calls, round(time.perf_counter() - t, 1))
    정답과 해설

    50 2.5. 50명이 모두 캐시가 빈 것을 본 뒤 자물쇠 앞에 줄을 섰다. 자물쇠를 얻은 스레드마다 캐시를 다시 보지 않고 DB를 읽어, 질의는 그대로 50번이고 한 번에 하나씩 하느라 2.5초가 걸렸다. 자물쇠 없이 50번이 한꺼번에 가는 것보다 더 느리다. 자물쇠를 얻은 뒤 캐시를 한 번 더 확인하면 된다(이 PC에서 10번 모두 같았다).

    def get(cache, key):
    if key not in cache:
        with lock:
            if key not in cache:                 # 기다리는 동안 다른 스레드가 채웠는지 다시 본다
                cache[key] = db_read(key)
    return cache[key]


cache, db_calls = {}, 0
start = threading.Barrier(50)
t = time.perf_counter()
threads = [threading.Thread(target=reader) for _ in range(50)]
for th in threads: th.start()
for th in threads: th.join()
print(db_calls, round(time.perf_counter() - t, 1))

    1 0.1

    이제 DB 질의는 1번이고 0.1초 안에 모두 읽었다. 서버가 여러 대면 이 자물쇠는 서버마다 따로라 서버 수만큼 질의가 간다. 서버 사이에 함께 거는 자물쇠가 필요하면 캐시 서버의 기능을 쓴다.

    AI와 함께 확인하기¶

    AI 활용 과제: AI가 붙인 캐시에서 낡은 값 찾기

    1. AI에게 "상품 조회 API(get_product)와 상품 수정 API(update_product)가 있다. 조회가 느리니 Python으로 캐시를 붙여 줘"라고 한다.
    2. 받은 코드에서 캐시에 넣는 곳, 지우는 곳, TTL을 표시한다. 수정 API가 캐시를 지우는지, 가격 목록 같은 다른 캐시도 그 상품을 담고 있지 않은지 본다.
    3. 수정한 직후에 조회하는 시험을 짜서 새 값이 나오는지 확인한다. 낡은 값이 나오면 AI에게 결과를 보여 주고 고치게 한다.
    확인할 점
    • 조회에만 캐시를 붙이고 수정 API는 그대로 두는 답이 흔하다. TTL이 다할 때까지 수정이 반영되지 않는다(위젯의 "TTL만").
    • 상품 하나의 캐시는 지웠는데 그 상품이 들어 있는 목록 캐시("인기 상품 10개")는 그대로인 경우가 있다. 한 데이터가 여러 캐시에 들어가면 지울 곳도 여럿이다.
    • TTL이 없는 캐시는 무효화를 한 번 놓치면 영원히 낡는다. 함수 결과를 메모리에 두는 functools.lru_cache도 TTL이 없고 서버마다 따로라, 여러 서버에서 바뀌는 데이터에는 맞지 않는다.

    더 알아보기¶

    쓸 때도 캐시를 거치는 방식

    이 항목은 읽을 때 캐시를 채우는 방식(cache-aside)을 다뤘다. 쓸 때 캐시와 DB를 함께 고치는 방식(write-through), 캐시에만 쓰고 DB에는 나중에 몰아 쓰는 방식(write-back)도 있다. write-back은 빠르지만 캐시가 DB에 쓰기 전에 죽으면 쓴 것을 잃는다. 어느 방식이든 "캐시와 원본이 언제 어긋날 수 있나"를 따져 보고 고른다.

    3절 그림의 실험: 자물쇠가 없을 때와 다시 확인하는 자물쇠

    인기 키가 만료된 순간 50명이 함께 읽는 실험이다. 자물쇠 없이 두면(get_plain) 50명이 모두 캐시가 빈 것을 보고 DB로 가고, 자물쇠를 얻은 뒤 다시 확인하면(get_single) 한 번만 간다. 이 PC에서 15번 실행해 모두 같았다.

    import threading
import time

db_calls = 0
count_lock = threading.Lock()


def db_read(key):                                # DB에서 읽는다(50ms)
    global db_calls
    with count_lock:
        db_calls += 1
    time.sleep(0.05)
    return f"{key}의 값"


def get_plain(cache, key):                       # 캐시에 없으면 DB에서 읽어 넣는다
    if key not in cache:
        cache[key] = db_read(key)
    return cache[key]


fill_lock = threading.Lock()


def get_single(cache, key):                      # 없으면 한 스레드만 DB에 가고, 나머지는 기다렸다가 캐시에서 읽는다
    if key not in cache:
        with fill_lock:
            if key not in cache:                 # 기다리는 동안 다른 스레드가 채웠는지 다시 본다
                cache[key] = db_read(key)
    return cache[key]


for get in [get_plain, get_single]:
    cache, db_calls = {}, 0                       # 인기 상품의 캐시가 막 만료되었다
    start = threading.Barrier(50)
    def reader():
        start.wait()                             # 50명이 같은 순간에 읽는다
        get(cache, "상품 7")
    threads = [threading.Thread(target=reader) for _ in range(50)]
    for t in threads: t.start()
    for t in threads: t.join()
    print(get.__name__, db_calls)               # 이 PC에서 15번 모두 get_plain 50, get_single 1


    get_plain 50
get_single 1
    캐시는 어디에나 있다

    브라우저는 HTTP 응답을 Cache-Control 머리에 따라 캐시에 두어 다시 열 때 빠르고(44번(URL 입력부터 렌더링까지)), DNS 리졸버는 TTL 동안 답을 둔다(42번(DNS)). CDN은 손님 가까운 곳에 정적 파일을 두고, DB도 자주 읽는 페이지를 메모리에 둔다. CPU에는 L1, L2, L3 캐시가 있다(5번(메모리 계층 구조)). 모두 "가까운 곳에 복사해 두고, 원본과 어긋나는 것을 감수한다"는 같은 거래다.

    정리¶

    • 캐시는 한 번 읽은 값을 빠른 곳에 두는 것이다. 적중률이 평균 시간과 DB 부하를 정한다.
    • 캐시는 원본과 어긋날 수 있다. TTL은 낡을 수 있는 최대 시간을 정하고, 무효화는 바뀔 때 지운다. 읽기와 쓰기가 겹치면 지운 뒤에도 낡은 값이 들어갈 수 있어 둘을 함께 쓴다.
    • 인기 키가 만료되면 읽기가 DB로 몰린다. 한 요청만 채우게 하되, 자물쇠를 얻은 뒤 다시 확인한다.
