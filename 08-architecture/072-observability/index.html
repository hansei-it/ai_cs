    72. 관측성: 로그, 메트릭, 분산 추적을 읽고 문제의 원인 찾기¶

    직접 AI 없이 직접 할 수 있어야 하는 항목

    서비스가 여럿으로 나뉘면(66번(모놀리식 vs 마이크로서비스)) "주문이 느리다"는 말만으로는 어디를 고칠지 알 수 없다. 관측성은 밖에서 볼 수 있는 신호(메트릭, 로그, 추적)만으로 시스템 안에서 무슨 일이 있었는지 알아내는 능력이다. 직접형 항목이므로 서비스 셋이 남긴 로그를 직접 모아 읽고, 느린 요청이 어디서 시간을 썼는지 찾는다. AI가 원인을 짚어 줄 때도 그 말이 맞는지 로그로 확인할 수 있어야 한다.

    이 항목에서 배우는 것¶

    • 메트릭, 로그, 추적이 저마다 무엇을 알려 주는지 설명하고, 셋을 이어 원인을 좁힐 수 있다.
    • 응답 시간을 평균이 아니라 분위수(p50, p99)로 읽을 수 있다.
    • 추적 ID를 실어 보내는 로그를 남기고, 그 로그를 묶어 느린 요청의 원인을 찾을 수 있다.

    1. 메트릭은 무엇이, 로그는 무슨 일이, 추적은 어디서인지 알려 준다¶

    • 메트릭은 숫자를 시간에 따라 모은 것이다(응답 시간, 오류율, 큐 길이). 싸게 오래 모을 수 있어 경보를 울리는 데 쓴다.
    • 로그는 일이 있을 때마다 남기는 한 줄이다. 무슨 일이 있었는지 자세히 알려 주지만 양이 많다. 사람이 아니라 프로그램이 읽기 쉽게 한 줄에 JSON 하나로 남긴다.
    • 추적은 요청 하나가 지난 서비스와 걸린 시간이다. 서비스들이 같은 추적 ID를 실어 보내고 로그에 남겨야 이을 수 있다(3절).

    2. 응답 시간은 평균이 아니라 분위수로 본다¶

    직접 해 보기평균이 숨기는 느린 요청느린 요청의 비율과 걸리는 시간, 화면 하나가 보내는 요청 수를 골라, 요청 1,000개의 평균과 p50, p95, p99, 그리고 손님이 화면을 열 때 느린 요청을 만날 확률을 본다
    새 창에서 크게 열기
    • 응답 시간을 작은 것부터 늘어놓았을 때 가운데 값이 p50, 99% 자리의 값이 p99다. 요청 100개 가운데 많아야 1개가 p99보다 오래 걸린다.
    • 평균은 드문 느린 요청에 끌려가 "모두가 조금 느리다"처럼 보이게 한다. 실제로는 대부분 빠르고 일부가 아주 느린 경우가 많다. 그래서 p50으로 보통의 요청을, p99로 느린 쪽 꼬리를 본다.
    • 화면 하나가 요청 여러 개를 보내면, 그 가운데 하나만 느려도 화면이 느리다. 드문 느림이 손님에게 얼마나 자주 보이는지는 문제 2에서 계산한다.

    3. 추적 ID를 실어 보내 요청 하나를 서비스 사이에서 잇는다¶

    • 맨 앞(게이트웨이)이 요청마다 추적 ID를 만들고, 다음 서비스를 부를 때 머리(X-Trace-Id 등)에 실어 보낸다. 서비스마다 로그에 그 ID를 남기면, 흩어진 로그에서 같은 요청의 줄을 모을 수 있다.
    • 모은 줄을 시간 막대로 겹치면 어디서 시간을 썼는지 보인다. 다른 서비스를 하나씩 불러 기다렸다면, 자기 일에 쓴 시간은 자기 시간에서 부른 서비스의 시간을 뺀 것이다(직접 해보기).

    예측해 보기¶

    문제 1. 요청 1,000개 가운데 5개(0.5%)가 2초 걸리고, 나머지는 50~70ms다. p99는 얼마쯤일까? 위젯을 누르기 전에 적어 본다.

    정답과 해설

    70ms쯤이다(위젯에서 69.9ms). 작은 것부터 늘어놓으면 느린 5개는 996~1,000번째다. p99는 990번째 값이라 아직 빠른 요청 쪽에 있다. 0.5%만 느릴 때는 p99도 그 느림을 보여 주지 못한다. 더 드문 느림은 p99.9나 가장 느린 값으로 보고, 그 요청이 무엇인지는 로그와 추적으로 찾는다. 평균은 69.7ms로 이 경우에도 느림을 거의 드러내지 않았다. 지표 하나만 보면 놓치는 것이 생긴다.

    문제 2. 요청 하나가 느릴 확률이 2%다. 화면 하나가 요청 1개, 5개, 20개를 보낼 때, 그 화면을 연 손님이 느린 요청을 하나라도 만날 확률은?

    slow = 0.02                                      # 요청 하나가 느릴 확률
for k in [1, 5, 20]:                             # 화면 하나가 보내는 요청 수
    print(k, round(1 - (1 - slow) ** k, 2))
    정답과 해설 
    1 0.02
5 0.1
20 0.33

    요청 20개가 모두 빠를 확률은 0.98²⁰ ≈ 0.67이므로, 손님 셋 가운데 하나는 느린 화면을 본다. 서버 쪽에서 보면 "98%가 빠르다"지만 손님 쪽에서는 그렇지 않다. 그래서 p99 같은 꼬리를 줄이는 일이 평균을 줄이는 일만큼 중요하다. 66번(모놀리식 vs 마이크로서비스)에서 서비스 여러 개를 차례로 부를 때 성공률을 곱한 것과 같은 계산이다.

    직접 해보기¶

    실습: 서비스 셋의 로그로 느린 주문의 원인 찾기

    1. 아래 shop.py를 실행한다. 게이트웨이, 주문, 결제 서비스를 띄우고 주문 50개를 보낸 뒤 shop.log에 150줄을 남긴다(6초쯤 걸린다).
    2. shop.log를 읽어 게이트웨이 줄(손님이 기다린 시간)의 평균, p50, p99를 구한다. 평균과 p50이 얼마나 다른지 본다.
    3. 게이트웨이에서 200ms를 넘긴 요청을 추적 ID로 묶어, 어떤 상품이었는지, 어느 서비스가 자기 일에 가장 오래 걸렸는지 찾는다.
    4. 무엇을 고치면 좋을지 로그를 근거로 한 문장으로 적는다. 그다음 shop.py의 코드에서 그 까닭을 확인한다.
    # shop.py: 게이트웨이 → 주문 → 결제 서비스를 띄우고 주문 50개를 보낸다. 서비스마다 한 줄짜리 JSON 로그를 shop.log에 남긴다
import http.client
import json
import threading
import time
import uuid
from datetime import datetime
from http.server import BaseHTTPRequestHandler, ThreadingHTTPServer
from urllib.parse import parse_qs, quote, urlparse

log_lock = threading.Lock()
open("shop.log", "w", encoding="utf-8").close()


def log(service, trace, item, ms, status=200):   # 로그 한 줄: 언제, 어느 서비스, 어느 요청(추적 ID), 얼마나
    line = json.dumps({"time": datetime.now().astimezone().isoformat(timespec="milliseconds"), "service": service,
                       "trace": trace, "item": item, "status": status, "ms": round(ms, 1)}, ensure_ascii=False)
    with log_lock, open("shop.log", "a", encoding="utf-8") as f:
        f.write(line + "\n")


def call(port, item, trace):                     # 다음 서비스를 부른다. 추적 ID를 머리에 실어 넘긴다
    c = http.client.HTTPConnection("127.0.0.1", port, timeout=5)
    c.request("GET", f"/?item={quote(item)}", headers={"X-Trace-Id": trace})   # 주소의 한글은 %로 바꿔 보낸다
    status = c.getresponse().status
    c.close()
    return status


def service(name, work):
    class H(BaseHTTPRequestHandler):
        def do_GET(self):
            t = time.perf_counter()
            item = parse_qs(urlparse(self.path).query)["item"][0]
            trace = self.headers.get("X-Trace-Id") or uuid.uuid4().hex[:8]   # 없으면 여기서 새로 만든다
            work(item, trace)
            log(name, trace, item, (time.perf_counter() - t) * 1000)   # 답하기 전에 남긴다(부른 쪽이 먼저 끝나 줄이 빠지지 않게)
            self.send_response(200)
            self.end_headers()
        def log_message(self, *a):
            pass
    s = ThreadingHTTPServer(("127.0.0.1", 0), H)
    threading.Thread(target=s.serve_forever, daemon=True).start()
    return s.server_address[1]


def pay(item, trace):                            # 결제 서비스가 하는 일
    time.sleep(0.03)
    if item == "노트북":
        time.sleep(0.3)


payment = service("결제", pay)
order = service("주문", lambda item, trace: (time.sleep(0.02), call(payment, item, trace)))
gateway = service("게이트웨이", lambda item, trace: call(order, item, trace))

items = ["우유", "빵", "노트북", "사과", "라면"]
for i in range(50):
    call(gateway, items[i % 5], "")              # 손님은 추적 ID 없이 보낸다(게이트웨이가 만든다)
print(sum(1 for _ in open("shop.log", encoding="utf-8")))   # 150
    확인할 점

    한 예다. 로그를 줄마다 JSON으로 읽고, 추적 ID로 묶은 뒤 서비스마다 자기 일에 쓴 시간을 구한다.

    import json
import math
from collections import defaultdict

lines = [json.loads(line) for line in open("shop.log", encoding="utf-8")]


def percentile(values, p):                       # 가까운 순위 방식: 작은 것부터 p% 자리의 값
    xs = sorted(values)
    return xs[math.ceil(len(xs) * p / 100) - 1]


whole = [x["ms"] for x in lines if x["service"] == "게이트웨이"]   # 손님이 기다린 시간은 게이트웨이의 시간이다
print(len(whole))                                # 50
print(round(sum(whole) / len(whole)), round(percentile(whole, 50)), round(percentile(whole, 99)))   # 평균, p50, p99(ms)

traces = defaultdict(dict)                       # 추적 ID로 같은 요청의 줄을 묶는다
for x in lines:
    traces[x["trace"]][x["service"]] = x
calls = {"게이트웨이": "주문", "주문": "결제"}       # 누가 누구를 불렀나
slow = [s for s in traces.values() if s["게이트웨이"]["ms"] > 200]
print(len(slow), {s["게이트웨이"]["item"] for s in slow})   # 10 {'노트북'}

where = defaultdict(int)
for s in slow:                                   # 서비스마다 자기 일에 쓴 시간 = 자기 시간 − 부른 서비스의 시간
    own = {name: s[name]["ms"] - (s[calls[name]]["ms"] if name in calls else 0) for name in s}
    where[max(own, key=own.get)] += 1
print(dict(where))                               # {'결제': 10}
    • 이 PC(Core i9-14900KF, DDR5 64GB, Windows 11, Python 3.14.0)에서 5번 실행하니 평균 124~130ms, p50 66~76ms, p99 370~394ms였다(요청이 50개뿐이라 p99는 가장 느린 값이다). 평균이 p50의 두 배 가까이 된다. 평균만 보면 모든 주문이 120ms쯤 걸리는 것처럼 보이지만, 실제로는 대부분 50~70ms대이고 10개가 350ms를 넘는다.
    • 200ms를 넘긴 10개는 모두 노트북이고, 10개 모두 결제 서비스가 자기 일에 가장 오래 걸렸다(330ms쯤). 게이트웨이와 주문 서비스는 결제를 기다렸을 뿐이다. 고칠 곳은 결제 서비스가 노트북을 처리하는 부분이다(코드를 보면 노트북일 때만 0.3초를 더 쓴다). 주문 서비스를 늘리거나 게이트웨이를 고쳐도 빨라지지 않는다.
    • 추적 ID가 없었다면 같은 요청의 세 줄을 시각으로 짐작해 맞춰야 했다. 요청이 동시에 많으면 그것도 할 수 없다.

    AI와 함께 확인하기¶

    AI 활용 과제: AI가 짚은 원인을 로그로 확인하기

    1. shop.log의 앞 30줄을 AI에게 주고 "주문이 가끔 느리다. 원인이 무엇인가?"라고 묻는다.
    2. AI가 내세운 근거(어느 줄, 어느 숫자)를 적고, 그 주장이 로그 전체에서도 맞는지 실습의 분석으로 확인한다.
    3. AI에게 결제 서비스에 로그를 더 남기는 코드를 짜게 하고, 남기는 내용에 추적 ID가 있는지, 남기면 안 되는 것(카드 번호, 비밀번호, 개인정보)이 없는지 본다.
    확인할 점
    • 30줄 안에는 노트북 주문이 두 개뿐이라, AI가 "가끔 300ms가 넘는다"는 것만 보고 "네트워크 문제"나 "서버가 부족하다"처럼 넓게 답하기 쉽다. 근거가 되는 줄을 짚지 못하는 답은 받아들이지 않는다.
    • 원인이 "노트북일 때 결제 서비스"라는 것은 전체 로그를 묶어야 확실해진다. 일부만 보고 내린 결론은 전체로 다시 확인한다.
    • 로그를 더 남기는 코드에 요청 본문 전체나 카드 번호를 그대로 찍는 경우가 흔하다. 로그는 많은 사람이 오래 보는 곳이라 개인정보와 비밀은 남기지 않는다(99번(책임과 윤리)). 남길 것은 추적 ID, 무엇을 했는지, 걸린 시간, 결과다.

    더 알아보기¶

    OpenTelemetry와 traceparent

    이 항목은 추적 ID를 X-Trace-Id 머리로 직접 넘겼다. 실제로는 W3C의 traceparent 머리 형식과 OpenTelemetry 같은 도구를 많이 쓴다. 서비스마다 같은 형식으로 추적 ID와 구간(span) ID를 넘기므로, 언어와 회사가 달라도 추적을 이을 수 있다. 모은 추적은 Jaeger 같은 도구에서 이 항목의 폭포 그림처럼 본다. 생각은 이 항목의 실습과 같다.

    로그는 공짜가 아니다

    요청마다 서비스마다 로그를 남기면 양이 금방 커진다. 그래서 로그에 수준(DEBUG, INFO, WARNING(줄여서 WARN), ERROR)을 두어 평소에는 INFO 이상만 남기고, 추적은 요청의 일부만 골라(표본) 모으기도 한다. 표본만 모으면 드문 느린 요청을 놓칠 수 있어, 느리거나 실패한 요청은 꼭 남기는 방법을 함께 쓴다.

    정리¶

    • 메트릭은 무엇이 이상한지, 로그는 무슨 일이 있었는지, 추적은 어디서 시간을 썼는지 알려 준다. 로그와 추적을 같은 추적 ID로 잇는다.
    • 응답 시간은 평균이 아니라 p50과 p99로 본다. 드문 느림도 화면 하나가 요청을 여럿 보내면 손님에게 자주 보인다.
    • 로그는 한 줄에 JSON 하나로, 추적 ID와 걸린 시간을 남긴다. 묶고 빼서 원인을 좁히고, AI의 주장도 그렇게 확인한다.
