    69. 비동기 메시징: 메시지 큐를 통한 결합도 완화 (RabbitMQ, Kafka 등은 사례로)¶

    원리 동작을 예측하고 이상을 알아챌 수 있어야 하는 항목

    주문을 받으면 확인 메일을 보내고, 포인트를 쌓고, 배송을 요청한다. 이 일을 주문 서버가 모두 직접 부르면, 하나가 느리거나 멈출 때 주문도 느려지거나 실패한다. 메시지 큐는 "해야 할 일"을 메시지로 남겨 두고, 그 일을 맡은 쪽이 따로 꺼내 처리하게 한다. 이 항목은 큐가 무엇을 풀어 주고, 어떤 새 문제를 가져오는지 Python으로 작게 짜서 본다. RabbitMQ, Kafka, 클라우드의 큐 서비스는 같은 생각을 제품으로 만든 것이다.

    이 항목에서 배우는 것¶

    • 동기 호출과 메시지 큐의 차이, 큐가 결합도를 낮추는 방식을 설명할 수 있다.
    • 들어오는 속도와 처리하는 속도에 따라 큐가 어떻게 쌓이고 비는지 예측할 수 있다.
    • 확인(ack)을 보내는 시점에 따라 메시지를 잃거나 두 번 처리하는 경우를 설명하고, 멱등한 소비자로 대비할 수 있다.

    1. 큐에 넣고 바로 답하면, 느린 일은 따로 한다¶

    • 동기 호출에서는 주문 서버가 메일 서버의 답을 기다린다. 메일 서버가 느리면 손님도 기다리고, 멈추면 주문까지 실패한다(문제 1).
    • 큐를 두면 주문 서버는 메시지를 넣기만 하고 바로 답한다. 소비자가 큐에서 꺼내 메일을 보낸다. 주문 서버는 메일 서버가 어디 있는지, 지금 살아 있는지 몰라도 된다. 이것을 결합도가 낮다고 한다.
    • 메일처럼 조금 늦어도 되는 일에 맞는다. 결제 승인처럼 손님에게 바로 결과를 보여 줘야 하는 일은 큐에 넣고 끝낼 수 없다.

    2. 들어오는 속도가 처리 속도보다 빠르면 큐는 끝없이 길어진다¶

    직접 해 보기큐가 쌓이는 속도1초에 들어오는 주문 수와 메일을 보내는 소비자 수, 소비자가 잠깐 멈추는 장애를 골라, 60초 동안 큐에 쌓인 메시지 수와 마지막 손님이 메일을 받기까지 기다리는 시간을 본다
    새 창에서 크게 열기
    • 큐는 잠깐 몰리는 일이나 소비자의 짧은 장애를 흡수한다. 그동안 쌓였다가, 소비자에게 남는 힘이 있으면 다시 줄어든다(위젯의 장애).
    • 들어오는 수가 처리하는 수보다 계속 많으면 큐는 줄지 않고 길어지기만 한다. 큐는 일을 미뤄 줄 뿐 없애 주지 않는다. 소비자를 늘리거나 일을 가볍게 해야 한다(문제 3).
    • 그래서 운영할 때는 큐의 길이와 메시지가 기다린 시간을 지켜본다(72번(관측성)). 큐가 줄지 않고 계속 길어지면 소비자가 모자라거나 멈춘 것이다.

    3. 확인을 보내는 때에 따라 메시지를 잃거나 두 번 처리한다¶

    • 큐는 소비자가 "처리했다"는 확인(ack)을 보낼 때 메시지를 지운다. 꺼내자마자 확인하면 처리하다 죽을 때 잃고, 처리한 뒤 확인하면 확인 전에 죽을 때 다시 받는다.
    • 보통은 잃지 않는 쪽(처리한 뒤 확인, 적어도 한 번)을 고르고, 같은 메시지를 두 번 받아도 한 번만 처리되게 소비자를 멱등하게 만든다. 처리한 메시지 번호를 적어 두고 이미 있으면 건너뛴다. 다만 적는 때와 처리하는 때 사이에도 함정이 있다(문제 2).

    예측해 보기¶

    문제 1. 주문 저장에 50ms, 확인 메일에 200ms가 걸린다. 메일까지 보내고 답하는 함수와, 메일을 큐에 넣고 답하는 함수가 손님에게 답하기까지 걸린 시간(10ms 단위로 반올림한 ms)은?

    import queue
import threading
import time


def save_order(order):                           # DB에 주문을 저장한다(50ms)
    time.sleep(0.05)


def send_mail(order):                            # 메일 서버에 확인 메일을 보낸다(200ms)
    time.sleep(0.2)


def place_order_sync(order):                     # 메일까지 보내고 답한다
    save_order(order)
    send_mail(order)


mails = queue.Queue()


def place_order_async(order):                    # 메일은 큐에 넣고 바로 답한다
    save_order(order)
    mails.put(order)


def mail_worker():                               # 큐에서 꺼내 메일을 보내는 소비자(따로 돈다)
    while True:
        send_mail(mails.get())
        mails.task_done()


threading.Thread(target=mail_worker, daemon=True).start()

for place in [place_order_sync, place_order_async]:
    t = time.perf_counter()
    place({"id": 7})
    print(place.__name__, round((time.perf_counter() - t) * 1000, -1))
mails.join()                                     # 큐에 넣은 메일까지 다 보낼 때를 기다린다
    정답과 해설 
    place_order_sync 250.0
place_order_async 50.0

    동기 함수는 저장(50ms)과 메일(200ms)을 모두 기다려 250ms, 큐를 쓰는 함수는 저장만 기다려 50ms였다(이 PC에서 15번 모두 같았다). 메일은 소비자 스레드가 그 뒤에 따로 보냈다. 손님이 기다리는 시간은 줄었지만 일이 없어진 것은 아니다. 소비자가 1초에 보낼 수 있는 수보다 주문이 많이 들어오면 큐가 쌓인다(2절). 마지막 줄의 mails.join()은 넣은 메시지마다 소비자가 task_done()을 부를 때까지, 곧 메일을 다 보낼 때까지 기다린다. 이 줄이 없으면 프로그램이 끝나며 아직 보내지 않은 메일이 사라진다. 큐가 메모리에만 있으면 서버가 죽을 때 메시지도 함께 사라지므로, 실제 메시지 큐는 메시지를 디스크에 남기도록 설정해 쓴다.

    문제 2. 소비자를 멱등하게 만들려고 처리한 주문 번호를 적어 둔다. 큐는 처리한 뒤에 확인을 받는다. 첫 소비자가 7번을 받아 번호를 적은 뒤, 메일을 보내기 직전에 죽었다. 무엇이 출력될까?

    class Broker:                                    # 확인(ack)을 받기 전에는 메시지를 지우지 않는다
    def __init__(self, messages):
        self.waiting = list(messages)

    def receive(self):
        return self.waiting[0] if self.waiting else None

    def ack(self, msg):
        self.waiting.remove(msg)


sent, done = [], set()


def consume(broker, crash_at=None):              # 처리한 번호를 적어 두는 멱등한 소비자
    while (msg := broker.receive()) is not None:
        if msg not in done:
            done.add(msg)                        # 처리했다고 먼저 적고
            if msg == crash_at:
                return                           # 메일을 보내기 직전에 소비자가 죽었다
            sent.append(f"주문 {msg} 메일")       # 메일을 보낸다
        broker.ack(msg)


broker = Broker([7, 8])
consume(broker, crash_at=7)                      # 첫 소비자
consume(broker)                                  # 다시 띄운 소비자
print(sent)
    정답과 해설

    ['주문 8 메일']. 확인을 받지 못한 7번은 큐에 남아 다시 띄운 소비자에게 갔다. 그런데 7번은 이미 "처리했다"고 적혀 있어 건너뛰고 확인만 보냈다. 7번 손님의 메일은 끝내 가지 않았다. 순서를 바꿔 메일을 먼저 보내고 적으면, 이번에는 보낸 뒤 적기 전에 죽을 때 두 번 보낸다. 적는 일과 처리하는 일이 따로 일어나는 한 그 사이가 늘 남는다. 처리가 DB를 고치는 일(포인트 적립)이면 번호를 적는 일과 한 DB 트랜잭션으로 묶으면 된다(53번(트랜잭션과 락)). 메일처럼 바깥으로 보내는 일은 DB 트랜잭션에 넣을 수 없으므로, 그림의 셋째 줄처럼 먼저 보내고 나중에 적어 잃지 않게 하고(가끔 두 번 보낸다), 받는 쪽(메일 서비스)이 같은 메시지 번호를 알아보고 두 번째를 무시하게 한다(70번(분산 시스템의 근본 문제)의 멱등 키).

    문제 3. 위젯에서 1초에 주문 8개, 소비자 1명(1초에 5개)으로 놓는다. 60초 뒤 큐에는 메시지가 몇 개 있고, 그때 들어온 주문의 손님은 메일을 몇 초 뒤에 받을까? 위젯으로 확인하기 전에 계산해 본다.

    정답과 해설

    180개, 36초 뒤다. 1초에 8개가 들어오고 5개만 나가므로 1초에 3개씩 쌓여 60초 뒤 180개다. 그때 들어온 메시지는 큐의 맨 뒤라, 180개가 1초에 5개씩 빠지는 36초 뒤에야 처리된다. 시간이 갈수록 큐도 기다림도 계속 는다. 소비자를 2명(1초에 10개)으로 늘리면 쌓이지 않는다. 메일이 하루 늦어져도 괜찮은 일이고 밤에는 주문이 1초에 5개보다 적게 들어온다면, 밤에 비우는 것으로 충분할 수도 있다. 큐가 쌓이는 것이 문제인지는 그 일이 얼마나 늦어도 되는지로 정한다.

    AI와 함께 확인하기¶

    AI 활용 과제: AI가 짠 소비자의 전달 보장 확인하기

    1. AI에게 "Python으로 메시지 큐에서 주문 메시지를 꺼내 포인트를 적립하는 소비자를 짜 줘. 소비자가 죽었다 다시 떠도 괜찮게 해 줘"라고 한다.
    2. 받은 코드에서 메시지를 꺼내는 곳, 포인트를 쌓는 곳, 확인(ack)을 보내는 곳의 차례를 적는다.
    3. 각 줄 사이에서 소비자가 죽는다고 가정하고, 포인트가 빠지거나 두 번 쌓이는 경우가 있는지 따진다. 있으면 AI에게 그 경우를 보여 주고 고치게 한다.
    확인할 점
    • 메시지를 꺼내자마자 확인하는 코드(자동 확인 설정을 켜 둔 코드 포함)는 처리 중에 죽으면 포인트가 빠진다.
    • 처리한 뒤 확인하는데 멱등하지 않으면 다시 받을 때 포인트가 두 번 쌓인다. "처리한 메시지 번호"와 "포인트 적립"을 같은 DB 트랜잭션에 넣어야 둘이 함께 남거나 함께 사라진다(문제 2).
    • 몇 번을 다시 받아도 계속 실패하는 메시지(형식이 틀린 메시지)가 큐 맨 앞을 막는 경우도 있다. 정해진 횟수를 넘으면 따로 모아 두는 곳(데드 레터 큐)으로 옮기는지 본다.

    더 알아보기¶

    큐와 로그: RabbitMQ와 Kafka의 차이

    RabbitMQ 같은 큐는 소비자가 확인한 메시지를 지운다. 한 메시지는 소비자 하나가 처리한다. Kafka 같은 로그는 소비자가 읽어도 메시지를 지우지 않고 차례대로 쌓아 두었다가, 정한 보관 기간(기본 7일)이나 크기를 넘으면 지운다. 소비자 무리(consumer group)마다 "어디까지 읽었는지"를 따로 기록하므로, 여러 무리가 같은 메시지를 저마다 처음부터 다시 읽을 수 있다. 주문 이벤트를 메일, 포인트, 통계가 모두 따로 읽는 경우가 그렇다. 어느 쪽이든 이 항목의 문제(쌓임, 적어도 한 번, 멱등)는 같다.

    메시지의 차례

    큐 하나에서 소비자가 여럿이면 나중에 넣은 메시지가 먼저 처리될 수 있다. "주문 취소"가 "주문 생성"보다 먼저 처리되면 곤란하다. 차례가 중요한 메시지는 같은 키(주문 번호)끼리 한 줄로 보내거나, 소비자가 차례를 확인하게 한다.

    정리¶

    • 메시지 큐는 해야 할 일을 메시지로 남겨, 보내는 쪽과 처리하는 쪽을 떼어 놓는다. 보내는 쪽은 기다리지 않고, 처리하는 쪽이 멈춰도 메시지는 남는다.
    • 큐는 일을 미룰 뿐 없애지 않는다. 처리하는 속도가 들어오는 속도보다 빨라야 큐가 쌓이지 않는다.
    • 확인을 보내는 때에 따라 잃거나 두 번 처리한다. 적어도 한 번 받게 하고 소비자를 멱등하게 만들되, 처리한 기록과 처리를 한 트랜잭션으로 묶거나 받는 쪽이 두 번째를 무시하게 한다.
