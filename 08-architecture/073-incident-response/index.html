    73. 장애 대응과 사후 분석(포스트모템): 원인 추적, 재발 방지, 비난 없는 회고¶

    직접 AI 없이 직접 할 수 있어야 하는 항목

    장애는 일어난다. 실력은 장애가 없는 것보다, 났을 때 피해를 빨리 멈추고 같은 장애가 다시 나지 않게 만드는 데서 드러난다. 직접형 항목이므로 주문 서비스의 장애 로그를 직접 읽어 시간표를 만들고, 원인을 좁히고, 포스트모템을 쓴다. AI가 만든 코드든 사람이 만든 코드든 운영하는 사람이 결과를 책임진다. 72번(관측성)에서 로그와 추적을 읽은 것을 실제 장애에 써 보는 항목이다.

    이 항목에서 배우는 것¶

    • 장애가 났을 때 무엇을 먼저 하는지(피해 멈추기 → 원인 찾기)의 차례를 설명할 수 있다.
    • 로그와 변경 기록으로 장애의 시간표를 만들고, 원인을 좁힐 수 있다.
    • 사람이 아니라 구조를 고치는 포스트모템을 쓸 수 있다.

    1. 먼저 피해를 멈추고, 원인은 그다음에 찾는다¶

    • 장애를 알아채면 먼저 이끌 사람을 정하고 알린다. 여럿이 따로 손대면 서로의 변경이 섞여 더 헷갈린다.
    • 원인을 다 알기 전이라도 피해부터 멈춘다. 최근 배포가 의심되면 되돌리고(71번(이중화와 무중단 배포)), 기능 하나가 문제면 그 기능만 끈다. 손님이 기다리는 동안 원인을 찾는 것은 나중 일이다.
    • 알아채기까지 걸린 시간과 되돌리기까지 걸린 시간을 잰다. 앞의 것은 경보와 지표가(72번(관측성)), 뒤의 것은 되돌리기 쉬운 배포가 줄인다.

    2. 변경 기록과 로그로 시간표를 만들어 원인을 좁힌다¶

    직접 해 보기장애 로그 읽기14:00~14:20 주문 서비스 로그를 수준, 서비스, 찾을 말, 분으로 걸러 읽으며, 언제 무엇이 바뀌었고 언제부터 경고와 오류가 났는지 시간표를 만든다
    새 창에서 크게 열기
    • 장애 분석은 시간표에서 시작한다. 언제 무엇이 바뀌었고(배포, 설정, 트래픽), 언제부터 경고와 오류가 났고, 언제 멈췄는지 한 줄에 놓는다.
    • 오류가 처음 난 때와 그 직전의 변경을 견준다. 바로 이어진다고 원인이라고 단정하지는 않지만, 가장 먼저 의심할 곳이다.
    • 오류가 나기 전의 경고(WARN)도 본다. 실제 장애는 조용히 쌓이다가 한꺼번에 터지는 일이 많다. 그 조짐을 일찍 알릴 경보가 있었는지가 포스트모템의 질문이 된다(직접 해보기).

    3. 비난 없는 포스트모템: 사람이 아니라 구조를 고친다¶

    • 포스트모템은 장애가 끝난 뒤 무슨 일이 왜 일어났고, 다시 나지 않게 무엇을 바꿀지 적는 문서다. 요약, 영향, 시간표, 원인, 잘한 것과 아쉬운 것, 할 일(담당과 기한)을 담는다.
    • "누가 실수했나"가 아니라 "그 실수가 왜 가능했고 왜 늦게 알았나"를 묻는다(비난 없는 회고). 사람을 탓하면 다음 장애를 숨기게 되고, 같은 자리에 선 다른 사람이 같은 실수를 한다. 할 일을 어떻게 적어야 하는지는 문제 2에서 본다.

    예측해 보기¶

    문제 1. 15:20에 상품 검색의 오류율 경보가 울렸다. 변경 기록을 보니 15:12에 검색 서비스 v3를 배포했고, 오류는 15:13부터 났다. 오류 메시지는 "색인을 읽지 못함"인데, 색인을 둔 서버는 멀쩡해 보인다. 원인을 다 찾을 때까지 v3를 그대로 두고 살펴볼까, 먼저 v2로 되돌릴까?

    정답과 해설

    먼저 v2로 되돌린다. 오류가 배포 뒤에 시작되었고 되돌릴 수 있는 변경이라면, 원인이 확실하지 않아도 되돌리는 비용은 작고 그대로 두는 비용(손님이 상품을 찾지 못한다)은 크다. 되돌려서 오류가 멈추면 원인이 그 배포에 있다는 강한 증거도 된다. 되돌린 뒤 로그와 코드에서 원인을 찾는다. 다만 데이터의 모양을 바꾼 배포는 옛 판이 새 데이터를 읽지 못할 수 있어 되돌리기도 위험하다. 그래서 배포를 되돌릴 수 있게 나눠 한다(71번(이중화와 무중단 배포)의 넓히기와 좁히기).

    문제 2. 설정 파일에 주문 한 건의 최대 수량을 1000으로 적으려다 100으로 적어, 큰 주문이 모두 거절된 장애가 있었다. 포스트모템의 할 일 칸에 "설정을 바꿀 때 더 꼼꼼히 확인한다"라고 적었다. 이 할 일의 문제는 무엇이고, 어떻게 바꾸면 좋을까?

    정답과 해설

    사람의 주의에 기대는 할 일이라 다시 나지 않는다는 보장이 없다. 다음에 바쁜 사람, 새로 온 사람이 같은 실수를 한다. 실수를 할 수 없게 하거나, 해도 바로 알게 하는 할 일로 바꾼다. 예를 들어 설정 값이 이전과 크게 달라지면(예: 10분의 1로) 배포를 멈추고 확인을 받게 하고, 설정을 바꾸는 일도 코드처럼 검토를 받고 일부 서버에 먼저 내보내게 하고(71번(이중화와 무중단 배포)), 주문 거절 비율이 갑자기 오르면 경보를 울리게 한다. 할 일마다 담당과 기한을 적고, 끝났는지 다음 회의에서 확인한다. "더 조심한다"는 할 일이 아니다.

    직접 해보기¶

    실습: 장애 로그로 시간표를 만들고 포스트모템 쓰기

    1. 아래 incident.py를 실행해 incident.log(어느 날 14:00~14:20 주문 서비스의 로그 630줄)를 만든다. 위젯도 같은 로그다.
    2. 로그를 읽어 시간표를 만든다. 첫 오류가 난 때와 그 메시지, 그 직전의 변경, 오류가 멈춘 때, 장애로 실패한(ERROR) 주문 수를 찾는다.
    3. 원인을 좁힌다. 배포 전과 뒤에 카드 거절이 난 다음 줄의 pool(빌려 간 연결 수 / 10)이 어떻게 다른지 본다.
    4. 아래 틀로 포스트모템을 쓴다. 할 일은 사람의 주의가 아니라 구조를 바꾸는 것으로 적는다.
    # incident.py: 어느 날 14:00~14:20 주문 서비스의 로그를 incident.log에 만든다(실제 서버 없이 같은 일을 흉내 낸다)
# 2초마다 주문이 하나 온다. 주문마다 DB 커넥션 풀(10개)에서 연결을 하나 빌렸다 돌려준다. 스무 번째마다 카드가 거절된다.
# 주문을 마친 뒤에도 빌려 간 채인 연결이 8개 이상이면 그 줄을 WARN으로 남긴다
import json
from datetime import datetime, timedelta

start = datetime(2026, 10, 15, 14, 0, 0)
events = {120: ("배포", "INFO", "주문 서비스 v2 배포 끝"),          # 14:02:00
          580: ("경보", "ERROR", "경보: 주문 오류율 5% 넘음(1분)"),   # 14:09:40
          660: ("배포", "INFO", "주문 서비스 v1으로 되돌림")}          # 14:11:00
version, in_use, lines = "v1", 0, []


def log(sec, service, level, msg, **extra):
    t = (start + timedelta(seconds=sec)).strftime("%H:%M:%S")
    lines.append(json.dumps({"time": t, "service": service, "level": level, "msg": msg, **extra}, ensure_ascii=False))


for sec in range(0, 1200, 2):
    if sec in events:
        service, level, msg = events[sec]
        log(sec, service, level, msg)
        if "v2" in msg:
            version = "v2"
        if "되돌림" in msg:
            version, in_use = "v1", 0                  # 다시 띄우며 풀도 새로 만든다
    order = sec // 2 + 1
    if in_use >= 10:
        log(sec, "주문", "ERROR", "DB 연결을 얻지 못함: 커넥션 풀이 비었다", order=order, pool=f"{in_use}/10")
        continue
    in_use += 1                                    # 연결을 빌린다
    if order % 20 == 13:
        log(sec, "결제", "INFO", "카드 거절", order=order)
        if version == "v1":
            in_use -= 1                            # v1은 거절된 경우에도 연결을 돌려준다
        log(sec, "주문", "WARN" if in_use >= 8 else "INFO", "주문 실패: 카드 거절", order=order, pool=f"{in_use}/10")
        continue
    in_use -= 1                                    # 연결을 돌려준다
    log(sec, "주문", "WARN" if in_use >= 8 else "INFO", "주문 완료", order=order, pool=f"{in_use}/10")

open("incident.log", "w", encoding="utf-8").write("\n".join(lines) + "\n")
print(len(lines))                                # 630

    포스트모템의 틀이다.

    요약: (한두 문장)
영향: 누가, 얼마나, 얼마 동안
시간표: 변경, 첫 조짐, 첫 오류, 알아챔, 피해 멈춤
원인: 무엇이 왜 ("왜"를 다섯 번쯤 물어 구조까지)
잘한 것 / 아쉬운 것:
할 일: 무엇을, 누가, 언제까지
    확인할 점

    한 예다. 로그를 줄마다 JSON으로 읽고, 오류와 변경을 시간으로 견준다.

    import json
from collections import Counter

logs = [json.loads(line) for line in open("incident.log", encoding="utf-8")]

errors = [x for x in logs if x["level"] == "ERROR" and x["service"] == "주문"]
first = errors[0]
print(first["time"], first["msg"])               # "14:08:26 DB 연결을 얻지 못함: 커넥션 풀이 비었다"
changes = [x for x in logs if x["service"] == "배포" and x["time"] < first["time"]]
print(changes[-1]["time"], changes[-1]["msg"])   # 14:02:00 주문 서비스 v2 배포 끝
print(len(errors), errors[-1]["time"])           # 77 14:10:58

per_minute = Counter(x["time"][:5] for x in errors)   # 1분마다 실패한 주문 수
print(dict(per_minute))                          # {'14:08': 17, '14:09': 30, '14:10': 30}

# 배포 뒤 카드가 거절될 때마다 풀에서 빌려 간 연결 수가 어떻게 바뀌나
declined = [x["pool"] for x in logs if x["msg"] == "주문 실패: 카드 거절" and "14:02:00" < x["time"] < "14:11:00"]
print(declined)                                  # ['1/10', '2/10', '3/10', '4/10', '5/10', '6/10', '7/10', '8/10', '9/10', '10/10']
    • 시간표: 14:02:00 v2 배포 → 14:07:04 첫 WARN(빌려 간 연결 8개) → 14:08:26 첫 오류 → 14:09:40 경보 → 14:11:00 v1으로 되돌림, 오류 멈춤. 주문 77개가 실패했다(14:08:26~14:10:58). 첫 오류부터 알아채기까지 1분 14초, 알아챈 뒤 되돌리기까지 1분 20초였다.
    • 원인: 배포 전에는 카드가 거절되어도 pool이 0으로 돌아갔다. 배포 뒤에는 거절이 날 때마다 1/10, 2/10, …로 하나씩 늘어 10번째 거절(14:08:24)에 10/10이 되었다. v2가 카드 거절 경로에서 연결을 돌려주지 않아 풀이 샜다. 되돌리며 서비스를 다시 띄우자 풀이 새로 만들어져 나았다. 로그만으로 세운 가설이므로 v2의 코드에서 그 경로를 확인한다.
    • 왜를 이어 묻는다. 왜 돌려주지 않았나? 거절 경로에서 일찍 return하며 돌려주는 줄을 건너뛰었다. 왜 시험에서 안 잡혔나? 시험이 성공 경로만 지났다. 왜 배포 뒤 6분 넘게 풀이 새는 것을 몰랐나? 풀 사용량에 경보가 없었다. 첫 WARN부터 오류까지 1분 22초가 있었다.
    • 할 일 예: 연결은 with 문으로만 빌린다(구조), 실패 경로 시험을 더한다, 풀 사용량 80% 경보를 둔다, 카나리 배포로 일부에만 먼저 내보낸다(71번(이중화와 무중단 배포)). 잘한 것으로는 되돌리기가 1분 20초 만에 된 것을 적는다.

    AI와 함께 확인하기¶

    AI 활용 과제: AI가 쓴 포스트모템 검토하기

    1. 실습의 incident.log에서 WARN 이상인 줄과 배포 줄을 AI에게 주고 "이 장애의 포스트모템을 써 줘"라고 한다.
    2. AI의 시간표와 숫자(첫 오류 시각, 실패한 주문 수, 장애 시간)를 실습에서 직접 구한 값과 견준다.
    3. 원인과 할 일이 로그에 근거하는지, 사람을 탓하는 말이나 "더 조심한다" 같은 할 일이 있는지 표시하고, 고쳐 쓰게 한다.
    확인할 점
    • WARN 이상만 주면 배포 전의 카드 거절(INFO)은 보이지 않는다. AI는 "배포 뒤 거절이 늘었다"처럼 로그에 없는 사실을 지어낼 수 있다. 거절은 배포 전과 뒤가 같은 빈도였다. 근거 줄을 대지 못하는 주장은 지운다.
    • 실패한 주문 수를 오류 줄 수(경보 줄까지 78줄)로 세는 실수가 흔하다. 주문의 오류 줄은 77줄이다. 숫자는 직접 센 것으로 쓴다.
    • "개발자의 실수", "주의 부족" 같은 말이 원인에 있으면 구조의 원인(시험이 지나지 않은 경로, 없던 경보, 돌려주기를 잊을 수 있는 코드)으로 바꾸게 한다.

    더 알아보기¶

    장애의 등급과 연락 체계

    많은 팀이 장애에 등급을 매긴다. 손님 전체가 주문을 못 하면 가장 높은 등급, 일부 기능이 느리면 낮은 등급처럼 정해 두고, 등급마다 누구를 깨우고 얼마 안에 알릴지 약속한다. 밤에 경보를 받는 당번(온콜)을 돌아가며 맡기도 한다. 경보가 너무 자주 울리면 사람들이 무시하게 되므로, 손님에게 실제로 영향이 있을 때만 깨우도록 경보를 다듬는 것도 운영의 일이다.

    시간표에는 시계가 중요하다

    여러 서버의 로그를 시간으로 견주려면 서버들의 시계가 맞아야 한다. 시계가 1초 어긋나 있으면, 1초보다 가깝게 일어난 원인과 결과는 차례가 뒤바뀌어 보일 수 있다. 그래서 서버들은 NTP로 시계를 맞추고, 로그에 시간대가 붙은 시각을 남긴다(63번(JSON과 직렬화)). 추적 ID가 있으면 시계가 어긋나도 같은 요청의 줄을 묶을 수 있다(72번(관측성)). 이 항목 실습의 로그는 서버 한 대의 20분이라 읽기 쉽게 시각만 남겼다.

    정리¶

    • 장애가 나면 이끌 사람을 정하고, 원인을 다 알기 전이라도 피해부터 멈춘다. 최근 변경이 의심되면 되돌린다.
    • 변경 기록과 로그로 시간표를 만든다. 첫 오류와 그 직전의 변경을 견주고, 오류 전의 조짐(경고)도 본다.
    • 포스트모템은 사람을 탓하지 않고, 실수를 할 수 없게 하거나 바로 알게 하는 구조의 할 일을 담당과 기한과 함께 적는다.
