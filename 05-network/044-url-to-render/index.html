    44. URL 입력부터 화면 렌더링까지의 네트워크 흐름¶

    원리 동작을 예측하고 이상을 알아챌 수 있어야 하는 항목

    주소창에 https://www.python.org/를 넣고 Enter를 누르면 1초도 안 되어 화면이 뜬다. 그사이 42번(DNS)의 DNS, 41번(전송 계층 (TCP·UDP))의 TCP, 45번(HTTPS와 TLS)의 TLS, 43번(HTTP)의 HTTP가 차례로 일하고, 브라우저는 받은 HTML을 읽어 필요한 것을 더 받은 뒤 화면을 그린다. 이 항목은 이 흐름을 한 번에 꿰고, 단계마다 걸린 시간을 이 PC에서 잰다. 웹이 느릴 때 어디를 볼지 아는 것이 목표다.

    이 항목에서 배우는 것¶

    • 주소를 넣은 뒤 화면이 뜨기까지의 차례(DNS, TCP, TLS, HTTP, HTML 읽기, 더 받기, 배치, 그리기)를 말할 수 있다.
    • 처음 들어갈 때와 다시 들어갈 때 어느 단계를 건너뛰는지 예측할 수 있다.
    • <script>를 둔 자리가 첫 화면에 주는 영향을 설명하고, curl과 개발자 도구로 느린 단계를 찾을 수 있다.

    1. 이름, 연결, 암호, 요청을 거쳐 HTML을 받는다¶

    • 브라우저는 주소를 나눠 읽는다. https는 443번 포트와 TLS를, www.python.org는 찾아갈 서버의 이름을, /는 서버 안의 경로를 뜻한다.
    • 이름을 IP 주소로 바꾸고(42번(DNS)), TCP 연결을 맺고(41번(전송 계층 (TCP·UDP))), TLS로 암호 열쇠를 정한 뒤(45번(HTTPS와 TLS)), HTTP 요청을 보낸다(43번(HTTP)). 이 PC에서 example.com은 TCP, TLS, 요청이 저마다 왕복 한 번씩 33~47ms였다.
    • 그래서 처음 들어갈 때는 HTML 하나를 받는 데만 서버와 왕복 세 번이 든다. 서버가 멀면 그만큼 곱해진다. 이 PC에서 가까운 www.python.org는 DNS를 빼면 이 과정이 40ms 안쪽이었다.

    2. HTML은 시작일 뿐, 화면은 요청 수십 개로 그려진다¶

    • 브라우저는 HTML을 읽어 태그를 나무 모양(DOM)으로 만들면서 CSS, JS, 그림을 찾아 더 요청한다. www.python.org는 HTML 말고도 30번 안팎, www.naver.com은 100번 넘게 더 요청했다(열 때마다 조금씩 다르다).
    • CSS를 받아야 무엇을 어떻게 그릴지 안다. 그래서 브라우저는 CSS를 기다린 뒤 배치(어디에 얼마나 크게)와 그리기를 한다. 글꼴처럼 CSS 안에서 부르는 것은 CSS를 받은 뒤에야 요청한다.
    • 이 PC에서 www.python.org의 첫 화면은 308~640ms였다(캐시 없이 5번). 곧바로 다시 읽으면 52~176ms로 줄었다(문제 1).

    3. 그냥 둔 스크립트는 HTML 읽기를 멈춘다¶

    직접 해 보기스크립트가 첫 화면을 막을 때script 태그를 머리에 그냥 두기, defer, async, 본문 끝에 두기로 바꿔 가며, 이 PC에서 잰 첫 화면, DOMContentLoaded, load 시각이 어떻게 달라지는지 본다
    새 창에서 크게 열기
    • <script>를 만나면 브라우저는 HTML 읽기를 멈추고 JS를 받아 실행한다. JS가 문서를 바꿀 수 있기 때문이다. 머리에 둔 JS가 느리면 본문을 읽지 못해 첫 화면도 늦다.
    • defer(다 읽은 뒤 실행)나 async(받는 대로 실행)를 붙이면 읽기가 막히지 않는다. 본문 끝에 두면 본문을 먼저 다 읽는다. 어느 쪽이든 CSS가 오면 바로 그릴 수 있다(위젯, 문제 2).
    • 페이지가 느리면 짐작하기 전에 잰다. curl로 네트워크 단계를, 개발자 도구의 네트워크 탭으로 무엇을 기다리는지를 본다(직접 해보기).

    예측해 보기¶

    문제 1. www.python.org를 연 탭에서 몇 초 뒤 새로 고침한다. 그림 1의 ①~⑨ 가운데 어느 단계를 건너뛰거나 짧게 끝낼까?

    정답과 해설

    ②~④를 건너뛰고, ⑦은 대부분 캐시에서 꺼낸다. 이름은 DNS 캐시에 있고(42번(DNS)), 연결은 열어 둔 것을 다시 쓰니(43번(HTTP)) TCP와 TLS가 없다. 이 PC에서 다시 읽을 때 DNS, TCP, TLS 시간이 모두 0이었다. CSS, JS, 그림은 받아 둔 것을 쓴다. 그래서 첫 화면이 308~640ms에서 52~176ms로 줄었다. HTML 자체는 바뀌었을 수 있으므로 서버에 다시 물었다.

    문제 2. 같은 PC 안의 서버가 CSS는 100ms, JS는 500ms 늦게 준다. 머리에 <script src="/slow.js">를 그냥 두면 첫 화면은 언제쯤일까? defer를 붙이면?

    정답과 해설

    그냥 두면 500ms 뒤, defer면 100ms 뒤쯤이다. 이 PC에서 5번씩 재니 그냥 둔 것은 544~564ms, defer는 192~204ms였다. 그냥 둔 스크립트는 HTML 읽기를 멈추게 해서, 본문을 읽지 못한 채 JS(500ms)를 기다린다. defer는 읽기를 멈추지 않으므로 CSS(100ms)가 오는 대로 그린다. async는 200~260ms, 본문 끝에 둔 것은 188~200ms로 defer와 비슷했다.

    문제 3. 왕복에 200ms가 드는 먼 서버(다른 대륙)에 처음 들어간다. HTML을 받기까지 얼마나 걸릴까? DNS는 빼고 센다. 서버가 협상에 왕복이 두 번 드는 TLS 1.2를 쓰면?

    정답과 해설

    600ms, TLS 1.2면 800ms. TCP 연결, TLS 협상(TLS 1.3), HTTP 요청과 응답이 저마다 왕복 한 번이라 3 × 200 = 600ms다. TLS 1.2는 왕복이 하나 더 든다. 이 PC에서 example.com은 왕복이 33~47ms라 셋을 더해 120ms 안팎이었다. 서버가 멀수록 왕복 수가 그대로 시간에 곱해지므로, 서버를 사용자 가까이에 두는 CDN이나 연결을 다시 쓰는 일이 빠르기를 크게 바꾼다.

    직접 해보기¶

    실습: 느린 단계 찾기

    1. 명령 프롬프트에서 아래 줄을 www.python.org, example.com, www.naver.com에 실행해, 단계마다 끝난 시각(초)을 적는다. 앞 값과의 차가 그 단계의 시간이다(PowerShell에서는 curl 대신 curl.exe).

      curl -s -o NUL -w "DNS %{time_namelookup}  TCP %{time_connect}  TLS %{time_appconnect}  first %{time_starttransfer}  total %{time_total}\n" https://www.python.org/

    2. 브라우저 개발자 도구(F12)의 네트워크 탭 위쪽에서 캐시를 끄는 체크 상자를 켜고 www.python.org를 새로 고침한다. 요청 개수와 폭포 모양의 막대를 보고, 가장 늦게 끝난 요청을 찾는다. 캐시를 다시 켜고 새로 고침해 견준다.

    3. 콘솔 탭에서 아래 두 줄로 첫 화면 시각과 요청 개수를 읽는다. 처음 붙여 넣을 때 Chrome이 경고하며 막으면, 안내에 나온 문구를 입력해 허용하거나 직접 입력한다.

      performance.getEntriesByName("first-contentful-paint")[0].startTime
performance.getEntriesByType("resource").length

    4. "더 알아보기"의 측정 2를 파일(예: blocking_server.py)로 저장해 python blocking_server.py로 띄운다. 브라우저에서 http://127.0.0.1:8044/block, /defer, /async, /end를 차례로 열어 3의 첫 줄로 첫 화면 시각을 잰다. 서버는 Ctrl+C로 멈춘다.

    확인할 점
    • 1에서 이 PC는 www.python.org의 DNS, TCP, TLS, 첫 바이트, 끝의 시각이 대략 0.038, 0.053, 0.065, 0.069, 0.075초였다. example.com은 TCP, TLS, 첫 바이트까지가 저마다 33~47ms씩 늘었다(그림 1). 서버까지의 왕복이 길기 때문이다.
    • DNS 값에는 이름을 찾는 시간보다 curl을 띄울 때마다 처음 이름을 찾는 준비(이 PC에서 약 10ms)가 많이 들어 있다. 같은 프로그램이 다시 찾으면 Windows 캐시에서 0.2ms 안팎이었다(42번(DNS)).
    • 2와 3에서 이 PC는 www.python.org의 요청이 30개 안팎이었다. 네트워크 탭은 문서 자신까지 세므로 하나 더 많고, 확장 프로그램이나 여는 때에 따라서도 조금 다르다.
    • 4는 위젯의 값과 비슷하게 나온다. /block만 500ms를 넘는다.

    AI와 함께 확인하기¶

    AI 활용 과제: \"주소를 입력하면 일어나는 일\" 검증하기

    1. AI에게 "브라우저 주소창에 https://www.python.org/ 를 입력하면 화면이 뜨기까지 일어나는 일을 단계별로 설명해 줘. 단계마다 시간도 대략 알려 줘"라고 한다.
    2. 그림 1의 ①~⑨와 짝짓고, 빠졌거나 차례가 다른 단계를 적는다.
    3. 실습 1, 2에서 잰 값과 AI가 말한 시간을 견주고, 크게 다르면 근거를 묻는다.
    확인할 점
    • 캐시 확인, TLS 협상, CSS·JS를 더 받는 단계를 빠뜨리는 답이 흔하다. HTML을 받으면 끝나는 것처럼 말하면, 이 PC에서 HTML 뒤에 30번을 더 요청했다는 것을 보여 준다.
    • "DNS가 수백 ms 걸린다"처럼 단정하는 시간은 내 PC의 측정과 다르다. 이 PC에서 DNS는 캐시 덕에 대부분 1ms 안쪽이었고(42번(DNS)), 시간을 가장 많이 쓴 것은 HTML 뒤의 CSS, JS, 글꼴이었다.
    • TLS 1.3은 협상에 왕복 한 번, TLS 1.2는 두 번이 든다. 어느 판을 말하는지 본다(45번(HTTPS와 TLS)).

    이 항목의 측정 프로그램

    1절의 시간은 이 PC(학교 유선망)에서 아래 측정 1을 5번 실행한 범위다. Windows에 들어 있는 curl.exe를 불러 단계마다 끝난 시각을 받고, 앞 단계와의 차를 그 단계의 시간으로 삼아 5번의 중앙값을 찍는다.

    # 44번 측정 1: curl로 HTML 하나를 받을 때 단계별 시간(ms)을 5번 재어 중앙값을 찍는다
import statistics
import subprocess

FMT = "%{time_namelookup} %{time_connect} %{time_appconnect} %{time_starttransfer} %{time_total}"
for url in ["https://www.python.org/", "https://example.com/"]:
    runs = []
    for _ in range(5):
        out = subprocess.run(["curl.exe", "-s", "-o", "NUL", "-w", FMT, url], capture_output=True, text=True).stdout
        dns, tcp, tls, first, total = (float(x) * 1000 for x in out.split())
        runs.append([dns, tcp - dns, tls - tcp, first - tls, total - first])   # 끝난 시각의 차가 그 단계의 시간
    med = [statistics.median(r[k] for r in runs) for k in range(5)]
    print(url, "DNS {:.1f}, TCP {:.1f}, TLS {:.1f}, wait {:.1f}, download {:.1f} ms".format(*med))

    2절과 3절의 브라우저 시간은 헤드리스 Chrome을 새 프로필(캐시 없음)로 띄워 페이지를 열고 2.5초 기다린 뒤, 페이지 안에서 아래 측정 3의 코드로 읽었다(실습 3처럼 콘솔에 넣어도 된다). 3절의 실험은 아래 측정 2의 서버로 했다. 새로 고침 없이 5번씩 열었다.

    # 44번 측정 2: CSS는 100ms, JS는 500ms 늦게 주는 작은 서버. 머리의 <script>를 그냥 두거나 defer, async로 바꾼 페이지를 준다
#   http://127.0.0.1:8044/block  /defer  /async  /end (본문 끝에 둔 그냥 <script>)
import http.server
import sys
import time

PAGE = """<!doctype html>
<html lang="ko"><head><meta charset="utf-8"><title>{mode}</title>
<link rel="stylesheet" href="/style.css">
{head}</head><body><h1>{mode}: 글자가 언제 보이나</h1><p>본문</p>
{tail}</body></html>"""


class Handler(http.server.BaseHTTPRequestHandler):
    def do_GET(self):
        if self.path == "/style.css":
            time.sleep(0.1)
            self.reply("text/css", "h1 { color: navy; }")
        elif self.path == "/slow.js":
            time.sleep(0.5)
            self.reply("text/javascript", "window.ran = performance.now();")
        else:
            mode = self.path.strip("/") or "block"
            tag = {"block": "<script src=/slow.js></script>", "defer": "<script src=/slow.js defer></script>",
                   "async": "<script src=/slow.js async></script>", "end": ""}.get(mode, "")
            tail = "<script src=/slow.js></script>" if mode == "end" else ""      # end: 본문 끝에 둔다
            self.reply("text/html; charset=utf-8", PAGE.format(mode=mode, head=tag + "\n" if tag else "", tail=tail))

    def reply(self, ctype, text):
        body = text.encode("utf-8")
        self.send_response(200)
        self.send_header("Content-Type", ctype)
        self.send_header("Content-Length", str(len(body)))
        self.send_header("Cache-Control", "no-store")            # 늘 서버에서 새로 받게 한다
        self.end_headers()
        self.wfile.write(body)

    def log_message(self, *args):
        pass


port = int(sys.argv[1]) if len(sys.argv) > 1 else 8044
http.server.ThreadingHTTPServer(("127.0.0.1", port), Handler).serve_forever()


    // 44번 측정 3: 페이지를 연 뒤 페이지 안에서 실행해, HTML을 받기까지의 단계 시간과 첫 화면, 요청 수를 읽는다(ms)
const n = performance.getEntriesByType("navigation")[0];
const fcp = performance.getEntriesByName("first-contentful-paint")[0];
({
  dns: n.domainLookupEnd - n.domainLookupStart,
  tcp: (n.secureConnectionStart || n.connectEnd) - n.connectStart,
  tls: n.secureConnectionStart ? n.connectEnd - n.secureConnectionStart : 0,
  wait: n.responseStart - n.requestStart,
  html: n.responseEnd - n.responseStart,
  fcp: fcp && fcp.startTime,
  dcl: n.domContentLoadedEventEnd,
  load: n.loadEventEnd,
  resources: performance.getEntriesByType("resource").length,   // 그림 2의 막대는 이 항목들의 startTime과 responseEnd
})

    정리¶

    • 주소를 넣으면 DNS, TCP 연결, TLS 협상, HTTP 요청을 거쳐 HTML을 받는다. 처음에는 서버와 왕복 세 번이 들고, 서버가 멀수록 길어진다.
    • 브라우저는 HTML을 읽으며 CSS, JS, 그림, 글꼴을 더 받고, CSS가 오면 배치하고 그린다. 페이지 하나에 요청이 수십~백여 개다. 다시 들어가면 캐시와 열어 둔 연결로 많은 단계를 건너뛴다.
    • 그냥 둔 <script>는 HTML 읽기를 멈추게 해 첫 화면을 늦춘다. defer, async, 본문 끝에 두기로 피한다. 느릴 때는 curl -w와 네트워크 탭으로 먼저 잰다.
