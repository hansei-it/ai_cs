    43. HTTP: 무상태·비연결성의 특성, 요청과 응답을 직접 읽고 분석하기(개발자 도구, curl)¶

    직접 AI 없이 직접 할 수 있어야 하는 항목

    웹 브라우저와 웹 서버는 HTTP로 이야기한다. 요청 한 줄과 머리 몇 줄을 보내면 상태 줄과 머리, 본문이 돌아온다. 웹이 안 될 때 원인은 대개 이 글자 안에 있다. 404인지 500인지, 쿠키가 실렸는지, 주소를 옮기라고 했는지가 다 보인다. 직접형 항목이므로 요청과 응답을 직접 만들고, 개발자 도구와 curl로 읽을 수 있어야 한다. HTTP는 TCP 연결 위에서 오간다(41번(전송 계층 (TCP·UDP))).

    이 항목에서 배우는 것¶

    • HTTP 요청과 응답을 줄 단위로 나눠 읽고(요청 줄, 상태 줄, 머리, 빈 줄, 본문), 직접 만들어 보낼 수 있다.
    • 메서드와 상태 코드를 보고 무엇을 하려 했고 어떻게 됐는지 말할 수 있다.
    • 개발자 도구와 curl로 실제 요청과 응답을 찾아 읽을 수 있다.
    • 무상태와 연결 다시 쓰기가 무엇이고 왜 그렇게 하는지 설명할 수 있다.

    1. 요청과 응답은 줄로 된 글자다¶

    import socket

with socket.create_connection(("example.com", 80)) as s:     # TCP 연결
    s.sendall(b"GET / HTTP/1.1\r\nHost: example.com\r\nConnection: close\r\n\r\n")
    data = b""
    while chunk := s.recv(4096):                               # 서버가 연결을 닫을 때까지 읽는다
        data += chunk
head, _, body = data.partition(b"\r\n\r\n")                   # 빈 줄 앞이 머리, 뒤가 본문
print(head.decode().split("\r\n")[0])                      # "HTTP/1.1 200 OK"
    • 요청의 첫 줄은 메서드(GET), 경로(/), 버전이다. 그 아래는 "이름: 값"으로 된 머리(헤더)가 한 줄에 하나씩 온다. 빈 줄 하나가 머리의 끝이고, 그 뒤가 본문이다.
    • 응답의 첫 줄은 버전, 상태 코드(200), 이유(OK)다. 머리에는 본문의 종류(Content-Type)와 길이 같은 정보가 있다.
    • 줄 끝은 \r\n 두 바이트다. Host 머리는 한 IP 주소에 사이트가 여럿일 때 어느 사이트인지 알린다(문제 2).

    2. 메서드는 뜻을, 상태 코드는 결과를 말한다¶

    직접 해 보기HTTP 요청과 응답메서드와 경로, 쿠키를 골라 요청을 보내고, 작은 서버가 돌려준 응답의 상태 줄, 머리, 빈 줄, 본문을 날것 그대로 읽는다
    새 창에서 크게 열기
    • 메서드: GET은 가져오기, POST는 보내서 처리하기(로그인, 글쓰기), HEAD는 머리만 가져오기다. PUT, DELETE 같은 것도 있다.
    • 상태 코드는 첫 자리로 나뉜다. 2xx 성공, 3xx 다른 곳으로 가라(Location 머리. 304는 가진 것을 그대로 써라), 4xx 요청 쪽 잘못(404 없음, 401 누구인지 밝혀라), 5xx 서버 쪽 잘못이다. http://www.python.org/는 이 PC에서 301과 함께 https://로 옮기라고 답했다.
    • 문제가 생기면 상태 코드부터 본다. 4xx면 내가 보낸 요청(경로, 머리, 쿠키)을, 5xx면 서버의 로그를 본다.

    3. 서버는 요청 사이를 기억하지 않고, 연결은 다시 쓴다¶

    • HTTP는 무상태(stateless)다. 서버는 요청 하나에 응답 하나를 돌려주고 잊는다. 방금 로그인한 사람의 다음 요청도 처음 보는 요청이다. 그래서 브라우저는 서버가 준 쿠키를 요청마다 실어 누구인지 밝힌다(위젯의 /mypage, 47번(쿠키, 세션, 토큰(JWT))).
    • 처음의 HTTP는 요청 하나마다 연결을 맺고 끊었다(비연결성). 지금의 HTTP/1.1은 연결을 열어 두고 다시 쓴다. 이 PC에서 example.com에 요청 10번을 보내니, 매번 새로 연결하면 847~1,286ms, 연결 하나를 다시 쓰면 434~532ms였다.
    • 무상태라서 서버 여러 대가 요청을 나눠 받기 쉽다. 요청마다 누구인지(쿠키)를 실어 오므로, 로그인 정보만 서버들이 함께 보면 어느 서버가 받아도 된다(47번(쿠키, 세션, 토큰(JWT))).

    예측해 보기¶

    문제 1. 같은 PC 안에 Python의 작은 웹 서버를 띄우고 hello.txt(내용 hello)를 둔다. 요청 셋을 직접 보낸다. 무엇이 출력될까?

    import functools
import http.server
import pathlib
import socket
import tempfile
import threading

class Quiet(http.server.SimpleHTTPRequestHandler):
    def log_message(self, *args):                              # 요청마다 찍는 기록을 끈다
        pass

root = pathlib.Path(tempfile.mkdtemp())
(root / "hello.txt").write_bytes(b"hello")
srv = http.server.ThreadingHTTPServer(("127.0.0.1", 0), functools.partial(Quiet, directory=root))
threading.Thread(target=srv.serve_forever, daemon=True).start()

def send(raw):
    with socket.create_connection(srv.server_address) as s:
        s.sendall(raw)
        data = b""
        while chunk := s.recv(4096):
            data += chunk
    return data

r = send(b"GET /hello.txt HTTP/1.0\r\n\r\n")
print(r.split(b"\r\n")[0])
print(r.split(b"\r\n\r\n")[1])
print(send(b"GET /nope HTTP/1.0\r\n\r\n").split(b"\r\n")[0])
print(send(b"POST /hello.txt HTTP/1.0\r\nContent-Length: 0\r\n\r\n").split(b"\r\n")[0])
    정답과 해설 
    b'HTTP/1.0 200 OK'
b'hello'
b'HTTP/1.0 404 File not found'
b"HTTP/1.0 501 Unsupported method ('POST')"

    있는 파일은 200과 본문 hello, 없는 파일은 404다. 이 서버는 파일을 내주기만 해서 POST를 받지 않는다. 501은 "서버가 이 메서드를 할 줄 모른다"는 5xx다. 이유 부분(File not found)은 서버마다 다르게 쓸 수 있으므로, 프로그램은 숫자만 보고 판단한다.

    문제 2. example.com에 Host 머리를 빼고 GET / HTTP/1.1만 보내면 어떻게 될까?

    정답과 해설

    HTTP/1.1 400 Bad Request. 이 PC에서 그렇게 답했다. HTTP/1.1은 Host 머리를 반드시 보내야 한다. example.com의 IP 주소는 Cloudflare의 것이라 수많은 사이트가 함께 쓴다. Host가 없으면 어느 사이트에 온 요청인지 알 수 없다.

    문제 3. 연결을 매번 새로 맺으면 요청 하나에 왕복이 몇 번 들까? 연결 하나를 다시 쓰면? 3절 그림의 측정값과 맞춰 본다.

    정답과 해설

    두 번과 한 번. 새로 연결하면 연결을 맺는 데 한 번(41번(전송 계층 (TCP·UDP))), 요청과 응답에 한 번이 든다. 연결을 다시 쓰면 처음 한 번만 맺으므로 요청마다 한 번이다. 이 PC에서 요청 10번이 847~1,286ms와 434~532ms로 절반 가까이 차이 났다. HTTPS라면 암호 협상에 왕복이 더 들어(45번(HTTPS와 TLS)) 다시 쓰는 이득이 더 크다.

    직접 해보기¶

    실습: 실제 요청과 응답 읽기

    1. 브라우저에서 https://example.com을 열고 F12로 개발자 도구를 연다. 네트워크 탭을 연 채 Ctrl+Shift+R로 캐시를 쓰지 않고 새로 고친 뒤 맨 위 줄(문서)을 눌러, 상태 코드, 응답 머리의 Content-Type, 요청 머리의 User-Agent를 찾는다.
    2. 명령 프롬프트에서 curl -v http://example.com/을 실행한다(PowerShell에서는 curl이 다른 명령의 별명이라 curl.exe로 쓴다). >로 시작하는 줄이 보낸 요청, <로 시작하는 줄이 받은 응답이다. 요청 줄, Host, 상태 줄, 빈 줄을 찾는다.
    3. curl -I http://www.python.org/로 머리만 받아 상태 코드와 Location을 본다. curl -IL로 바꿔 옮겨 간 곳까지 따라간다.
    4. AI 없이, 소켓만으로 요청을 보내 상태 코드와 머리를 돌려주는 함수 fetch_head(host, port, path)를 짠다. 문제 1의 서버와 example.com으로 시험한다.
    확인할 점
    • 1에서 상태 코드는 200이고, Content-Type은 text/html로 시작한다. 그냥 새로 고치면 304가 올 수 있다. 브라우저가 받아 둔 것이 바뀌었는지만 물어서, 서버가 "가진 것을 그대로 써라"고 답한 것이다. 브라우저의 User-Agent는 curl보다 훨씬 길다. 서버는 이 머리로 어떤 프로그램이 보냈는지 짐작한다.
    • 2에서 이 PC의 curl(8.21.0)은 요청 머리 셋(Host, User-Agent, Accept)을 보냈고, 상태 줄 아래 응답 머리는 12줄이었다.
    • 3에서 이 PC는 301 Moved Permanently와 Location: https://www.python.org/를 받았고, -L로 따라가니 200 OK였다.
    • 4는 예를 들어 다음과 같다. Connection: close를 보내야 서버가 응답 뒤에 연결을 닫아 읽기 반복이 끝난다.
    def fetch_head(host, port, path):
    with socket.create_connection((host, port)) as s:
        s.sendall(f"GET {path} HTTP/1.1\r\nHost: {host}\r\nConnection: close\r\n\r\n".encode())
        data = b""
        while chunk := s.recv(4096):
            data += chunk
    lines = data.split(b"\r\n\r\n")[0].decode("latin-1").split("\r\n")
    status = int(lines[0].split()[1])                     # "HTTP/1.0 200 OK"의 둘째 칸
    headers = {k.lower(): v for k, v in (line.split(": ", 1) for line in lines[1:])}
    return status, headers

status, headers = fetch_head(*srv.server_address, "/hello.txt")
print(status, headers["content-length"])   # "200 5"

    AI와 함께 확인하기¶

    AI 활용 과제: 소켓으로 웹 페이지 받기

    1. AI에게 "requests 같은 라이브러리 없이 Python 소켓으로 http://example.com/ 의 HTML을 받아 파일로 저장하는 코드"를 짜 달라고 한다.
    2. 실행하기 전에 프로그램이 끝날지, 저장된 파일이 브라우저의 "페이지 소스 보기"와 같을지 예측한다.
    3. 실행해서 걸린 시간과 파일 앞부분을 확인하고, 이상하면 받은 머리를 보여 주며 AI에게 고치게 한다.
    확인할 점
    • Connection: close를 보내지 않는 코드는 오래 멈춘다. HTTP/1.1은 연결을 열어 두는 것이 기본이라, 서버가 응답을 다 보낸 뒤에도 닫지 않는다. 이 PC에서 933바이트를 다 받고도 30초 넘게 recv에서 기다렸다. 닫지 않을 거라면 Content-Length만큼, chunked(아래)면 길이가 0인 조각이 올 때까지 읽어야 한다.
    • example.com의 응답은 Transfer-Encoding: chunked였다. 본문이 241\r\n처럼 16진수 길이와 조각으로 나뉘어 온다. 이것을 풀지 않고 저장하면 파일 맨 앞에 241 같은 숫자가 섞인다.
    • Host 머리를 빼먹으면 400을 받는다. 이런 일을 대신 해 주는 것이 urllib.request나 requests 같은 라이브러리다. 직접 짜 보면 라이브러리가 무엇을 해 주는지 보인다.

    더 알아보기¶

    HTTP/2와 HTTP/3

    HTTP/2는 같은 의미의 요청과 응답을 글자 대신 바이너리 조각(프레임)으로 보내고, 연결 하나에서 요청 여러 개를 섞어 동시에 주고받는다. HTTP/3은 이것을 TCP 대신 UDP 위의 QUIC으로 보낸다. 패킷 하나를 잃어도 다른 요청이 기다리지 않게 하려는 것이다(41번(전송 계층 (TCP·UDP))의 head-of-line blocking). 이 PC에서 example.com의 응답 머리에는 alt-svc: h3=":443"이 있었다. "443번 포트에서 HTTP/3도 된다"는 알림이라, 브라우저는 다음부터 HTTP/3으로 연결할 수 있다. 메서드, 상태 코드, 머리의 뜻은 판이 달라도 같다.

    이 항목의 측정 프로그램

    3절과 그림의 값은 이 PC(학교 유선망)에서 아래 프로그램을 5번 실행한 범위다. 이름은 미리 IP 주소로 바꿔 두어 DNS 시간(42번(DNS))을 뺐다. HTTPS가 아니라 HTTP(포트 80)로 쟀다.

    # 43번 측정: example.com에 HTTP 요청 10번을, 연결을 매번 새로 맺어 보낼 때와 연결 하나를 다시 쓸 때 걸린 시간
import http.client
import socket
import time

ip = socket.gethostbyname("example.com")      # 이름은 미리 찾아 둔다


def get(conn):
    conn.request("GET", "/", headers={"Host": "example.com"})
    r = conn.getresponse()
    r.read()                                  # 본문까지 다 읽어야 연결을 다시 쓸 수 있다
    return r.status


t = time.perf_counter()
for _ in range(10):
    conn = http.client.HTTPConnection(ip, 80, timeout=5)
    get(conn)
    conn.close()
new = (time.perf_counter() - t) * 1000

t = time.perf_counter()
conn = http.client.HTTPConnection(ip, 80, timeout=5)
for _ in range(10):
    get(conn)
conn.close()
reuse = (time.perf_counter() - t) * 1000
print(f"new connection each time {new:.0f} ms, one connection {reuse:.0f} ms")

    정리¶

    • HTTP 요청은 요청 줄(메서드, 경로, 버전)과 머리, 빈 줄, 본문이고, 응답은 상태 줄(버전, 상태 코드, 이유)과 머리, 빈 줄, 본문이다. 줄 끝은 \r\n이다.
    • 메서드는 요청의 뜻을, 상태 코드의 첫 자리는 결과(2xx 성공, 3xx 옮김, 4xx 요청 잘못, 5xx 서버 잘못)를 말한다. 개발자 도구의 네트워크 탭과 curl -v로 실제 요청과 응답을 읽는다.
    • 서버는 요청 사이를 기억하지 않으므로(무상태) 상태는 쿠키처럼 요청마다 실어 보낸다. 연결은 열어 두고 다시 써서 연결 맺는 왕복을 아낀다.
