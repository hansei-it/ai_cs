    41. 전송 계층: 포트와 소켓, TCP(3-way Handshake) vs UDP¶

    원리 동작을 예측하고 이상을 알아챌 수 있어야 하는 항목

    IP는 패킷을 목적지 컴퓨터까지 데려다준다(40번(IP 주소 체계와 NAT)). 하지만 그 컴퓨터에서는 브라우저, 메신저, 게임이 동시에 돈다. 받은 데이터를 어느 프로그램에 줄지, 길에서 잃은 패킷은 어떻게 할지를 정하는 것이 전송 계층이다. 이 항목은 포트로 프로그램과 연결을 가리는 방법, TCP가 연결을 맺고 빠짐없이 전하는 방법, UDP가 그 일을 하지 않는 대신 얻는 것을 이 PC에서 확인한다.

    이 항목에서 배우는 것¶

    • 포트와 소켓이 무엇인지, 연결 하나를 무엇으로 가리는지 설명할 수 있다.
    • TCP 3-way handshake의 순서와, 그 때문에 데이터를 보내기 전에 드는 시간을 설명할 수 있다.
    • 같은 데이터를 TCP와 UDP로 보낼 때 잃은 패킷과 기다리는 시간이 어떻게 다른지 예측하고, 일에 맞는 쪽을 고를 수 있다.

    1. 포트는 프로그램을, 네 값은 연결을 가린다¶

    • IP 주소가 컴퓨터를 가리킨다면 포트(0~65535)는 그 컴퓨터의 어느 프로그램인지를 가리킨다. 서버는 정해진 포트에서 기다린다(HTTP 80, HTTPS 443, DNS 53). 클라이언트는 운영체제가 남는 포트(임시 포트)를 골라 준다.
    • 프로그램이 주소와 포트를 붙잡고 데이터를 주고받는 창구가 소켓이다(31번(프로세스 간 통신(IPC))).
    • TCP 연결은 보내는 IP, 보내는 포트, 받는 IP, 받는 포트의 네 값으로 가린다. 그래서 서버는 443 하나로 손님 수천 명과 따로따로 연결을 유지한다(문제 1).

    2. TCP는 연결을 맺고 빠짐없이 차례대로 준다¶

    • TCP는 먼저 SYN, SYN+ACK, ACK를 주고받아 연결을 맺는다(3-way handshake). 데이터를 보내기 전에 왕복 한 번이 든다. 이 PC에서 www.google.com과 연결을 맺는 데 41~53ms, 같은 PC 안에서는 1ms 미만이 걸렸다.
    • 연결한 뒤에는 보내는 바이트에 순서 번호를 붙이고, 받는 쪽은 어디까지 받았는지(ACK) 알린다. 알림이 오지 않으면 다시 보낸다. 그래서 받는 프로그램은 빠짐없이 차례대로 바이트의 흐름을 받는다. 다만 보낸 단위의 경계는 남지 않는다(31번(프로세스 간 통신(IPC))).
    • 아무도 기다리지 않는 포트로 연결하면 거절당한다. 이 PC에서는 오류가 나기까지 생각보다 오래 걸렸다(문제 2).

    3. UDP는 잃어도 다시 보내지 않는 대신 기다리지 않는다¶

    직접 해 보기패킷을 잃을 때 TCP와 UDP패킷을 잃는 비율을 고르고 무작위 순서를 바꿔 가며, 같은 패킷 10개를 UDP와 TCP로 보낼 때 언제 무엇을 받는지와 TCP의 다시 보내기, 차례 기다리기를 본다
    새 창에서 크게 열기
    • UDP는 연결을 맺지 않고, 보낸 덩어리(데이터그램)를 하나씩 그대로 보낸다. 경계는 지키지만 잃거나 차례가 바뀌어도 알려 주지 않는다. 한 번에 65,507바이트까지만 보낼 수 있었다.
    • TCP는 잃은 것을 다시 보내 모두 받지만, 앞 번호가 올 때까지 뒤 번호를 프로그램에 넘기지 않는다. 위젯의 20%, 무작위 순서 2번은 첫 패킷 하나만 잃었는데도, TCP는 1번을 다시 받을 때까지 나머지 9개를 프로그램에 넘기지 않았다. UDP는 나머지 9개를 먼저 받았다.
    • 그래서 빠짐없어야 하는 일(웹 페이지, 파일)은 TCP를 쓴다. 조금 잃어도 늦지 않는 것이 중요한 일(영상 통화, 게임)은 UDP를 쓴다. DNS는 질문 하나에 답 하나라 연결을 맺는 왕복이 아까워 UDP로 묻고, 답이 없으면 다시 묻는다(42번(DNS)).
    • HTTP/3은 UDP 위의 QUIC을 쓴다. QUIC은 다시 보내기와 차례 맞추기를 요청마다 따로 해서, 한 요청의 패킷을 잃어도 다른 요청은 기다리지 않는다(43번(HTTP)).

    예측해 보기¶

    문제 1. 같은 서버 포트로 연결을 둘 맺는다. 무엇이 출력될까?

    import socket

ls = socket.create_server(("127.0.0.1", 0))   # 포트 0: 운영체제가 남는 포트를 준다
port = ls.getsockname()[1]
c1 = socket.create_connection(("127.0.0.1", port))
s1, a1 = ls.accept()
c2 = socket.create_connection(("127.0.0.1", port))
s2, a2 = ls.accept()
print(s1.getsockname()[1] == s2.getsockname()[1] == port)
print(a1[1] == a2[1])
print(a1[1] == c1.getsockname()[1])
    정답과 해설 
    True
False
True

    accept가 돌려준 두 소켓은 서버 쪽 포트가 둘 다 port로 같다. 상대(클라이언트)의 포트 a1[1], a2[1]이 다르므로 다른 연결이다. 서버가 본 상대의 포트는 클라이언트 소켓이 운영체제에서 받은 임시 포트와 같다.

    문제 2. 아무도 기다리지 않는 포트로 TCP 연결을 걸고, UDP 데이터그램을 보낸다. 무엇이 출력될까? 첫 줄의 수는 오류가 나기까지 걸린 초다.

    import time

s = socket.socket()
s.bind(("127.0.0.1", 0))
closed = s.getsockname()[1]   # 잠깐 받았다가 닫아서, 아무도 기다리지 않는 포트
s.close()
t = time.perf_counter()
try:
    socket.create_connection(("127.0.0.1", closed))
except OSError as e:
    print(type(e).__name__, round(time.perf_counter() - t))
u = socket.socket(socket.AF_INET, socket.SOCK_DGRAM)
print(u.sendto(b"hi", ("127.0.0.1", closed)))
    정답과 해설 
    ConnectionRefusedError 2
2

    TCP는 연결을 맺으려다 거절당해 ConnectionRefusedError(Windows 오류 10061)가 난다. 이 PC에서는 같은 PC 안인데도 오류가 나기까지 2.05~2.07초가 걸렸다(5번). Windows는 거절을 받아도 바로 포기하지 않고 연결을 몇 번 더 시도한 뒤에 오류를 낸다. 다시 시도하는 시간을 1초로 줄이니(TCP_MAXRT) 거절 대신 0.5초 만에 TimeoutError가 났다. 서버가 떠 있는지 확인하는 코드가 생각보다 오래 멈추는 까닭이다. UDP는 연결이 없어서 sendto가 보낸 바이트 수 2를 돌려주고 끝난다. 받을 프로그램이 있는지는 보내는 쪽이 알 수 없다. 이 PC에서는 그 뒤에 같은 소켓으로 recvfrom을 부르자 ConnectionResetError(10054)가 났다. 상대 컴퓨터가 "그 포트는 없다"고 알려 온 것을 Windows가 다음 받기에서 오류로 알린다.

    문제 3. 위젯에서 잃는 비율이 0%일 때 UDP와 TCP가 마지막 패킷을 받는 때는 각각 몇 ms일까? 20%의 무작위 순서 2번에서 TCP 프로그램은 2번 패킷을 언제 받을까?

    정답과 해설

    65ms와 105ms, 그리고 140ms. 10번째 패킷은 45ms에 보내 20ms 뒤에 닿는다. TCP는 연결을 맺느라 40ms 늦게 보내기 시작하므로 105ms다. 무작위 순서 2번에서는 40ms에 처음 보낸 1번 패킷을 잃어 80ms 뒤인 120ms에 다시 보내고 140ms에 닿는다. 2번 패킷은 65ms에 와 있었지만 1번이 오기 전에는 프로그램에 넘기지 않는다. 앞이 막히면 뒤가 모두 기다리는 이 일을 head-of-line blocking이라 한다.

    직접 해보기¶

    실습: 내 PC의 연결과 UDP 보기

    1. 명령 프롬프트에서 netstat -an -p tcp를 실행한다. 상태가 LISTENING인 줄(기다리는 서버)과 ESTABLISHED인 줄(맺은 연결)을 찾는다. 브라우저로 처음 여는 웹 페이지를 연 뒤 다시 실행해, 외부 주소가 :443인 연결이 늘었는지 본다.
    2. netsh int ipv4 show dynamicport tcp로 내 PC의 임시 포트 범위를 본다.
    3. UDP 소켓 둘을 한 프로그램에 만들어 a, bb, ccc를 따로 보내고, 받는 쪽에서 몇 번에 나눠 받는지 본다. 31번(프로세스 간 통신(IPC))의 TCP와 견준다. 받는 버퍼를 보낸 것보다 작게 주면 어떻게 되는지도 본다.
    4. 위젯에서 잃는 비율 10%와 30%를 무작위 순서 몇 개로 돌려 보고, TCP가 다시 보낸 횟수와 다 받은 때를 적는다.
    확인할 점
    • netstat의 열은 "프로토콜, 로컬 주소, 외부 주소, 상태"다. 0.0.0.0:445처럼 외부 주소가 0.0.0.0:0(상대 없음)인 LISTENING 줄이 이 PC에서 기다리는 서버다. Chrome은 HTTP/3을 쓴다고 알린 사이트에는 다음부터 UDP(QUIC)로 연결하기도 해서, 다시 여는 사이트는 TCP 줄이 늘지 않을 수 있다(43번(HTTP)).
    • Windows의 임시 포트 기본값은 49152부터 16,384개다. 이 PC는 TCP만 1024부터 13,977개로 바뀌어 있었다. 설치한 프로그램이 바꿔 둔 PC도 있으니 직접 확인한다.
    • 3은 아래처럼 세 번 보내면 세 번에 나눠 받는다. 받는 버퍼가 작으면 OSError(Windows 오류 10040)가 나고, 그 데이터그램은 버려진다. 다음 recvfrom은 다음 데이터그램을 받는다.
    srv = socket.socket(socket.AF_INET, socket.SOCK_DGRAM)
srv.bind(("127.0.0.1", 0))
cli = socket.socket(socket.AF_INET, socket.SOCK_DGRAM)
for m in [b"a", b"bb", b"ccc"]:
    cli.sendto(m, srv.getsockname())
print([srv.recvfrom(100)[0] for _ in range(3)])   # [b'a', b'bb', b'ccc']

cli.sendto(b"hello", srv.getsockname())
try:
    srv.recvfrom(2)                                # 버퍼가 2바이트뿐
except OSError as e:
    print(e.winerror)                              # 10040
cli.sendto(b"next", srv.getsockname())
print(srv.recvfrom(100)[0].decode())               # next

    AI와 함께 확인하기¶

    AI 활용 과제: UDP로 파일 보내기

    1. AI에게 "Python으로 UDP를 써서 파일을 보내고 받는 프로그램"을 짜 달라고 한다.
    2. 실행하기 전에, 100KB 파일을 보낼 때와 패킷을 잃을 때 어떻게 될지 예측한다.
    3. 같은 PC 안에서 100KB 파일로 시험하고, 받은 파일이 보낸 파일과 같은지 비교한다. 다르면 이유를 AI에게 묻는다.
    확인할 점
    • 파일을 한 번에 sendto하는 답이면 100KB에서 OSError(10040)가 난다. 이 PC에서 UDP 데이터그램은 65,507바이트까지 보낼 수 있었고 65,508바이트부터 이 오류가 났다(IPv4 패킷 최대 65,535바이트에서 IP와 UDP 머리 28바이트를 뺀 값).
    • 조각으로 나눠 보내는 답이라도, 순서 번호와 받았다는 알림, 다시 보내기가 없으면 잃거나 차례가 바뀐 조각을 알아챌 수 없다. 같은 PC 안에서는 잘 되다가 실제 네트워크에서 깨진다. 이것을 다 넣으면 TCP를 다시 만드는 셈이다.
    • 파일처럼 빠짐없어야 하는 데이터는 TCP를 쓰라고 답하는지, UDP를 고집한다면 그 까닭(예: QUIC 같은 라이브러리)을 대는지 본다.

    이 항목의 측정 프로그램

    2절과 그림의 연결 시간은 이 PC(Core i9-14900KF, 학교 유선망)에서 아래 프로그램을 5번 실행한 범위다. 한 번 실행할 때 서버마다 30번 연결을 맺고 중앙값을 찍는다. 이름은 미리 IP 주소로 바꿔 두어 DNS 시간(42번(DNS))을 뺐다. 같은 학교망 안에서도 실행할 때마다 흔들림이 컸다.

    # 41번 측정: TCP 연결을 맺는 데(3-way handshake) 걸린 시간의 중앙값
import socket
import statistics
import time

def connect_ms(ip, port):
    ms = []
    for _ in range(30):
        t = time.perf_counter()
        with socket.create_connection((ip, port), timeout=5):
            ms.append((time.perf_counter() - t) * 1000)
    return statistics.median(ms)

with socket.create_server(("127.0.0.1", 0)) as ls:   # 같은 PC 안의 서버
    print("127.0.0.1", f"{connect_ms('127.0.0.1', ls.getsockname()[1]):.2f} ms")
for host in ["www.naver.com", "www.google.com"]:
    print(host, f"{connect_ms(socket.gethostbyname(host), 80):.2f} ms")
    끊은 뒤에도 남는 연결: TIME_WAIT

    연결을 먼저 끊은 쪽은 그 연결의 기록을 한동안 TIME_WAIT 상태로 남겨 둔다. 길에서 늦게 도착한 옛 패킷이, 같은 네 값으로 새로 맺은 연결에 섞이지 않게 하려는 것이다. 이 PC에서 같은 PC 안의 서버와 연결을 50번 맺고 클라이언트가 먼저 끊었더니, netstat에 TIME_WAIT 연결 50개가 110초까지 남아 있다가 120초에는 사라졌다(아래 프로그램). 짧은 연결을 아주 많이 맺는 프로그램은 TIME_WAIT가 쌓여 임시 포트가 모자랄 수 있다. 이 항목의 연결 시간 측정을 돌린 직후 이 PC에는 TIME_WAIT 연결이 302개 있었다.

    # 41번 측정: 연결을 50번 맺고 끊은 뒤, 그 서버 포트의 TIME_WAIT 연결이 몇 초 동안 남는지 10초마다 센다
import socket
import subprocess
import time

ls = socket.create_server(("127.0.0.1", 0))
port = ls.getsockname()[1]
for _ in range(50):
    c = socket.create_connection(("127.0.0.1", port))
    s, _a = ls.accept()
    c.close()          # 클라이언트가 먼저 끊는다
    s.close()
t0 = time.time()
while True:
    out = subprocess.run(["netstat", "-an", "-p", "tcp"], capture_output=True, text=True, encoding="cp949").stdout
    n = sum(1 for line in out.splitlines() if f":{port} " in line and "TIME_WAIT" in line)
    print(f"{time.time() - t0:5.0f} s  TIME_WAIT {n}", flush=True)
    if n == 0:
        break
    time.sleep(10)

    정리¶

    • 포트는 컴퓨터 안의 프로그램을 가리키고, TCP 연결은 보내는 IP·포트와 받는 IP·포트의 네 값으로 가린다. 서버는 정해진 포트에서 기다리고 클라이언트는 임시 포트를 받는다.
    • TCP는 3-way handshake로 연결을 맺느라 왕복 한 번이 더 들고, 잃은 것을 다시 보내 차례대로 넘긴다. 앞이 빠지면 뒤가 기다린다.
    • UDP는 연결 없이 데이터그램을 그대로 보낸다. 잃어도 다시 보내지 않지만 기다리지도 않는다. 일의 성격에 맞춰 고른다.
