    39. 네트워크 계층 모델: OSI 7계층과 TCP/IP 4계층, 데이터 링크 계층 개요(MAC 주소, 스위치)¶

    원리 동작을 예측하고 이상을 알아챌 수 있어야 하는 항목

    브라우저에 주소를 넣으면 요청 몇 줄이 랜선이나 전파를 타고 멀리 있는 서버까지 간다. 그 사이에서 케이블, 스위치, 라우터, 운영체제, 프로그램이 함께 일한다. 이 일을 계층으로 나눠 두었기 때문에 각자 자기 일만 하면 된다. 이 항목은 계층이 어떻게 나뉘는지, 데이터가 계층을 지나며 어떻게 포장되는지, 그리고 가장 아래에서 같은 네트워크의 장치끼리 프레임을 주고받는 방법(MAC 주소와 스위치)을 본다. 섹션 5의 예제는 Python이다.

    이 항목에서 배우는 것¶

    • OSI 7계층과 TCP/IP 4계층을 짝짓고, 계층마다 쓰는 주소(포트, IP 주소, MAC 주소)를 말할 수 있다.
    • 계층마다 머리(헤더)가 붙는 캡슐화를 설명하고, 선 위에 실리는 바이트 수를 계산할 수 있다.
    • 스위치가 MAC 주소를 배워 프레임을 보낼 포트를 고르는 과정을 예측할 수 있다.

    1. 계층마다 한 가지 일을 맡는다¶

    • 인터넷은 TCP/IP 4계층으로 돈다. 링크 계층은 같은 네트워크 안의 바로 옆 장치로, 인터넷 계층(IP)은 여러 네트워크를 건너 목적지 컴퓨터로 보낸다. 전송 계층(TCP, UDP)은 그 컴퓨터의 어느 프로그램에게 줄지를 맡는다. 응용 계층은 프로그램끼리 주고받는 내용의 약속이다(DNS 42번(DNS), HTTP 43번(HTTP)).
    • OSI 7계층은 같은 일을 더 잘게 나눈 참조 모델이다. 장애를 말할 때 "1계층 문제(케이블)", "2계층 장비(스위치)", "3계층 장비(라우터)"처럼 이 번호를 쓴다.
    • 계층은 바로 위아래와만 이야기한다. 그래서 유선을 Wi-Fi로 바꿔도 브라우저는 고칠 것이 없다.

    2. 내려갈 때마다 머리를 붙인다¶

    import struct

payload = b"GET / HTTP/1.1\r\nHost: example.com\r\n\r\n"                    # 응용: HTTP 요청
tcp = struct.pack("!HHIIBBHHH", 50000, 80, 1, 0, 5 << 4, 0x18, 64240, 0, 0)   # 보내는 포트, 받는 포트, 순서 번호, …
ip = struct.pack("!BBHHHBBH4s4s", 0x45, 0, 20 + len(tcp) + len(payload), 1, 0x4000, 128, 6, 0,
                 bytes([192, 0, 2, 10]), bytes([203, 0, 113, 5]))           # …, 보내는 IP 주소, 받는 IP 주소
eth = bytes.fromhex("020000000001" "02000000000a" "0800")                    # 받는 MAC, 보내는 MAC, 종류(IPv4)
frame = eth + ip + tcp + payload
print(len(payload), len(tcp), len(ip), len(eth), len(frame))

    37 20 20 14 91
    • 보내는 쪽은 아래 계층으로 내려가며 자기 계층의 머리(헤더)를 앞에 붙인다(캡슐화). 받는 쪽은 올라가며 하나씩 떼어 읽는다. 위 코드는 머리를 손으로 만들어 이어 붙인 것이다(검사합은 0으로 두었다). 실제로는 운영체제와 랜 카드가 붙이고, 랜 카드가 끝에 오류 검사용 FCS 4바이트를 더 붙여 그림의 95바이트가 된다.
    • 장비는 대개 자기 계층의 머리까지만 본다. 스위치는 이더넷 머리의 MAC 주소를, 라우터는 IP 머리의 IP 주소를 보고 보낼 곳을 고른다. 집의 공유기는 NAT를 하느라 포트까지 보고 고친다(40번(IP 주소 체계와 NAT)).
    • 이더넷이 한 번에 싣는 크기(MTU)는 1,500바이트다. 이 PC의 이더넷도 1,500이었다. IP와 TCP 머리 40바이트를 빼면, TCP가 한 프레임에 싣는 데이터는 많아야 1,460바이트다.

    3. 스위치는 MAC 주소를 배워서 보낼 포트를 고른다¶

    직접 해 보기스위치가 MAC 주소를 배운다보내는 컴퓨터와 받는 컴퓨터를 골라 프레임을 보내며, 스위치가 MAC 주소 표를 채우고 보낼 포트를 고르는 과정과 허브와의 차이를 본다
    새 창에서 크게 열기
    • MAC 주소는 랜 카드마다 붙은 48비트(6바이트) 주소로, 34-5A-60-…처럼 쓴다. 앞 세 바이트는 IEEE가 제조사에 나눠 준 번호다. 같은 네트워크 안에서 "누구에게"를 가리킨다.
    • 스위치는 프레임이 들어온 포트와 보낸 쪽 MAC을 짝지어 표에 적는다. 받는 쪽 MAC이 표에 있으면 그 포트로만 보낸다. 없으면 들어온 포트를 뺀 모든 포트로 보낸다(플러딩). 받는 쪽이 FF-FF-FF-FF-FF-FF(브로드캐스트)여도 모두에게 보낸다.
    • 받는 MAC이 자기 것이 아닌 프레임은 랜 카드가 버린다. 옛 장비인 허브는 늘 모든 포트로 보냈지만, 스위치는 배운 뒤에는 필요한 선에만 보낸다(위젯의 "허브"와 비교).

    예측해 보기¶

    문제 1. 이더넷 프레임의 앞 14바이트를 나눠 읽는다. 무엇이 출력될까? 이 프레임은 누구에게 가는 것일까?

    frame = bytes.fromhex("ffffffffffff" "02000000000a" "0806") + bytes(46)
print(frame[0:6].hex("-"))
print(frame[6:12].hex("-"))
print(frame[12:14].hex())
print(len(frame))
    정답과 해설 
    ff-ff-ff-ff-ff-ff
02-00-00-00-00-0a
0806
60

    받는 MAC이 모두 1인 브로드캐스트라서 같은 네트워크의 모든 장치에게 간다. 종류 0x0806은 ARP다. IP 주소만 아는 상대의 MAC을 모두에게 묻는 ARP 요청이 이런 모양이다(40번(IP 주소 체계와 NAT)). IPv4 패킷이면 0x0800이다. 내용이 46바이트라 프레임은 60바이트(FCS 4바이트를 붙이면 64바이트)다.

    문제 2. TCP로 1바이트를 보낸다. 머리 크기는 그림 2를 본다. 이더넷 프레임은 FCS를 뺀 길이가 60바이트보다 짧으면 뒤를 0으로 채운다. 선 위의 프레임(FCS 포함)은 몇 바이트일까? 1,460바이트를 보내면?

    정답과 해설

    64바이트와 1,518바이트. 1바이트면 14 + 20 + 20 + 1 = 55바이트라 60바이트로 채우고 FCS 4바이트를 붙여 64바이트다. 1,460바이트면 14 + 20 + 20 + 1,460 + 4 = 1,518바이트다. 1바이트를 보내는 데 64바이트가 선에 실린다. 그래서 작은 데이터를 자주 따로 보내면 머리가 대부분을 차지한다.

    문제 3. 스위치를 켠 직후 A가 B에게, B가 A에게, 다시 A가 B에게 보낸다. 세 프레임은 각각 몇 개의 포트로 나갈까? D는 프레임을 몇 개 받을까?

    정답과 해설

    3개, 1개, 1개. D는 1개를 받아 버린다. 첫 프레임 때 스위치는 A의 자리(포트 1)를 배우지만 B는 모르므로 포트 2, 3, 4로 보낸다. C와 D는 자기 MAC이 아니라서 버린다. 두 번째에 B의 자리(포트 2)를 배우고, A는 이미 알므로 포트 1로만 보낸다. 세 번째는 포트 2로만 간다. 위젯에서 같은 차례로 눌러 확인할 수 있다.

    직접 해보기¶

    실습: 내 PC의 MAC 주소와 이웃 보기

    1. 명령 프롬프트에서 ipconfig /all을 실행해 어댑터마다 "물리적 주소"를 적는다. 실제 랜 카드 말고 가상 어댑터도 있는지 본다.
    2. Python에서 아래 코드로 uuid.getnode()가 알려 주는 주소를 찍고, 1에서 적은 주소 중 어느 것인지 찾는다.
    3. arp -a를 실행해 같은 네트워크에서 알아 둔 IP 주소와 MAC 주소의 짝을 본다. ipconfig의 "기본 게이트웨이" 주소가 있는지 찾는다.
    4. 위젯에서 A→B, B→A, A→B, C→D 차례로 보내고 "장비가 내보낸 프레임" 수를 적는다. "허브"로 바꿔 같은 차례로 보내고 견준다.
    import uuid

mac = uuid.getnode().to_bytes(6, "big")
print("-".join(f"{b:02X}" for b in mac))
    확인할 점
    • 이 PC에는 유선 랜 카드(34-5A-60-…), Wi-Fi(9C-65-EB-…), 블루투스 말고도 Wi-Fi Direct 가상 어댑터 둘과 Hyper-V 가상 어댑터 둘이 있었다. Hyper-V 가상 어댑터의 MAC은 00-15-5D-…로 시작했다. 랜 카드에 새긴 것이 아니라 소프트웨어가 Microsoft의 번호로 만든 주소다.
    • uuid.getnode()는 이 PC에서 지금 통신에 쓰는 유선 랜 카드가 아니라 블루투스 어댑터의 주소(9C-65-EB-…)를 돌려주었다. 어댑터가 여럿이면 그중 하나를 줄 뿐이다.
    • arp -a에는 "인터넷 주소", "물리적 주소", "유형" 열이 있고, 기본 게이트웨이의 IP 옆에 MAC이 "동적"으로 올라 있었다. 이 PC가 ARP로 물어 알아낸 짝이다(40번(IP 주소 체계와 NAT)).
    • 위젯에서 스위치가 내보낸 프레임은 8개(3 + 1 + 1 + 3), 허브는 12개(3개씩 네 번)였다. 스위치도 처음 보는 D에게 보낼 때는 모두에게 보낸다.

    AI와 함께 확인하기¶

    AI 활용 과제: OSI 7계층 표와 MAC 주소

    1. AI에게 "OSI 7계층을 계층마다 하는 일, 프로토콜과 장비의 예와 함께 표로 정리해 줘"와 "MAC 주소는 바뀔 수 있나?"를 묻는다.
    2. 표에서 TLS, ARP, 스위치가 어느 계층에 있는지 적고, 실습에서 본 내 PC의 어댑터와 MAC 주소로 두 번째 답을 판정한다.
    3. 다르게 말하는 곳이 있으면 근거를 묻는다.
    확인할 점
    • TLS를 6계층, ARP를 2계층이나 3계층에 놓는 등 자료마다 자리가 다르다. OSI는 나눠 생각하는 틀이고, 인터넷의 프로토콜은 TCP/IP 4계층에 맞춰 만들어졌다. 한 칸에 단정하는 답이면 근거를 묻는다.
    • "MAC 주소는 랜 카드에 새겨져 바뀌지 않고 전 세계에 하나뿐이다"는 이 PC에서도 맞지 않았다. 가상 어댑터는 소프트웨어가 주소를 만들었다(00-15-5D-…). Wi-Fi Direct 가상 어댑터 둘 중 하나는 Wi-Fi 주소에서 첫 바이트만 9C를 9E로 바꾼 주소를 썼다. 첫 바이트의 둘째 비트(0x02)가 1이면 제조사 번호가 아니라 직접 정한 주소라는 뜻이다. 위젯의 02-00-…도 그렇다.
    • "스위치는 IP 주소를 보고 보낸다"는 틀렸다. 보통의 스위치는 이더넷 머리의 MAC 주소만 본다. IP 주소를 보는 것은 라우터다(40번(IP 주소 체계와 NAT)).

    더 알아보기¶

    MSS: TCP가 한 번에 싣는 크기는 상대마다 다르다

    TCP는 연결을 맺을 때 서로 "한 번에 이만큼까지 받는다"(MSS)를 알리고 작은 쪽을 쓴다. MTU 1,500에서 머리 40바이트를 빼면 1,460이지만, 이 PC에서 서버 다섯 곳과 연결을 맺고 읽어 보니 1,400~1,460이었다. 서버나 길 중간의 장비(터널, VPN)가 작게 정해 알리기도 한다. 같은 PC 안(루프백)은 MTU에 한계가 없어서, IPv4 패킷의 최대 크기 65,535에서 머리 40바이트를 뺀 65,495였다.

    # 39번 측정: 서버마다 TCP 연결을 맺고, 이 연결의 MSS(한 번에 싣는 데이터의 최대 크기)를 읽는다
import socket

for host in ["example.com", "www.google.com", "www.naver.com", "www.microsoft.com", "www.python.org"]:
    try:
        with socket.create_connection((host, 80), timeout=5) as s:
            print(host, s.getsockopt(socket.IPPROTO_TCP, socket.TCP_MAXSEG))
    except OSError as e:
        print(host, "연결 실패:", e)

with socket.create_server(("127.0.0.1", 0)) as ls, socket.create_connection(ls.getsockname()) as c:
    print("127.0.0.1", c.getsockopt(socket.IPPROTO_TCP, socket.TCP_MAXSEG))   # 같은 PC 안

    이 PC에서 2026-10-14에 여러 번 실행한 결과다. www.naver.com은 DNS가 알려 준 서버에 따라 1,440일 때도, 1,460일 때도 있었다(42번(DNS)).

    example.com 1400
www.google.com 1412
www.naver.com 1460
www.microsoft.com 1460
www.python.org 1460
127.0.0.1 65495
    선 위에는 프레임 말고도 더 실린다

    이더넷은 프레임마다 앞에 맞춤 신호(프리앰블) 8바이트를 보내고, 프레임 사이를 12바이트만큼 비운다. 그래서 1,518바이트 프레임 하나가 선을 1,538바이트만큼 차지한다. 이 PC의 유선 연결(1Gbps)에서 1,460바이트짜리 데이터를 가득 실어 보내도 데이터만 세면 1,460 ÷ 1,538 ≈ 95%, 약 949Mbps다. 1Gbps 회선에서 받는 데이터가 1Gbps에 못 미치는 까닭 중 하나다.

    정리¶

    • 인터넷은 TCP/IP 4계층(링크, 인터넷, 전송, 응용)으로 돌고, OSI 7계층은 같은 일을 더 잘게 나눈 참조 모델이다. 계층마다 쓰는 주소가 다르다(MAC 주소, IP 주소, 포트).
    • 보내는 쪽은 내려가며 머리를 붙이고(캡슐화), 받는 쪽은 올라가며 뗀다. 이더넷 MTU는 1,500바이트이고, 작은 데이터일수록 머리의 몫이 크다.
    • 스위치는 보낸 쪽 MAC과 들어온 포트를 배워, 아는 곳에는 그 포트로만, 모르는 곳과 브로드캐스트는 모두에게 보낸다.
