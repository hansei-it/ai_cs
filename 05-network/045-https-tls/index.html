    45. HTTPS: TLS 핸드셰이크와 대칭키·공개키 암호화의 조합¶

    원리 동작을 예측하고 이상을 알아챌 수 있어야 하는 항목

    HTTP 요청은 글자 그대로 오간다(43번(HTTP)). 같은 와이파이의 누군가나 길 중간의 장비가 비밀번호와 쿠키를 읽을 수 있다. HTTPS는 HTTP를 TLS로 감싸, 길에서 읽지도 바꾸지도 못하게 하고 상대가 진짜 그 사이트인지 확인한다. 이 항목은 TLS가 대칭키와 공개키를 어떻게 함께 쓰는지, 처음 만난 두 컴퓨터가 어떻게 같은 열쇠를 갖게 되는지, 인증서가 무엇을 보증하는지를 이 PC에서 확인한다.

    이 항목에서 배우는 것¶

    • 대칭키와 공개키의 차이와, TLS가 둘을 함께 쓰는 까닭을 설명할 수 있다.
    • 공개된 조각만 주고받아 같은 열쇠를 정하는 과정을 작은 수로 따라갈 수 있다.
    • TLS 1.3 핸드셰이크의 차례와 인증서 사슬을 설명하고, 인증서 오류의 뜻을 읽을 수 있다.

    1. 대칭키는 빠르고, 공개키는 열쇠를 건넬 수 있다¶

    • 대칭키 암호(AES)는 같은 열쇠로 잠그고 연다. 이 PC는 AES-128-GCM으로 1초에 10.1~11.1GB를 암호화했다. 하지만 처음 만난 상대와 그 열쇠를 어떻게 나눌지가 문제다.
    • 공개키 암호는 열쇠가 한 쌍이다. 공개 열쇠는 누구에게나 주고, 개인 열쇠는 나만 갖는다. 이것으로 열쇠를 정하거나(X25519) 서명한다(RSA, ECDSA). 대신 느리다. 이 PC에서 RSA-2048 서명은 1초에 3,107~3,191번이었다.
    • 그래서 TLS는 처음에만 공개키로 대칭 열쇠를 정하고 상대를 확인한다. 그 뒤의 데이터는 모두 대칭키로 암호화한다(문제 3).

    2. 공개된 조각만 주고받아 같은 열쇠를 만든다¶

    직접 해 보기열쇠 정하기와 중간자브라우저와 서버의 비밀 수를 바꿔 가며 작은 수로 열쇠를 정해 보고, 도청자가 열쇠를 찾는 일과 중간자가 끼어드는 일, 인증서 서명이 그것을 막는 모습을 본다
    새 창에서 크게 열기
    • 브라우저와 서버는 저마다 비밀 수를 고르고, 그 비밀로 만든 조각만 주고받는다. 상대의 조각에 자기 비밀을 한 번 더 쓰면 양쪽이 같은 열쇠를 얻는다(Diffie-Hellman, 문제 1). 열쇠 자체는 선에 한 번도 나가지 않는다.
    • 도청자는 조각을 다 보지만, 수가 크면 비밀을 거꾸로 찾을 수 없다. TLS 1.3이 쓰는 X25519는 수가 2^255 가까이다.
    • 하지만 가운데서 조각을 바꿔치는 중간자는 양쪽과 따로 열쇠를 정해 모든 내용을 읽는다. 이것을 막는 것이 서버의 서명과 인증서다(위젯의 서명 상자).

    3. 인증서가 상대가 진짜인지 보증한다¶

    • 서버는 인증서(사이트 이름, 공개 열쇠, 유효 기간, 발급자의 서명)를 보내고, 인증서의 개인 열쇠로 협상 내용에 서명한다. 브라우저는 발급자의 서명을 따라 올라가 브라우저나 운영체제에 미리 든 뿌리 인증서까지 확인하고, 이름과 기간도 본다.
    • TLS 1.3은 이 모든 일을 왕복 한 번에 끝낸다. 이 PC에서 www.python.org는 TCP 연결 5.1~20.5ms 뒤 TLS 협상에 7.7~9.3ms, www.google.com은 54.3~58.8ms가 더 들었다. 둘 다 TLS 1.3, AES-GCM이었다. 예전 판인 TLS 1.2는 협상에 왕복이 두 번이라, www.google.com에 TLS 1.2로만 협상하게 하니 92.1~95.9ms였다.
    • 인증서가 맞지 않으면 브라우저는 경고하고 Python은 연결을 끊는다(문제 2). 경고를 넘기거나 확인을 끄는 것은 중간자에게 문을 여는 일이다.

    예측해 보기¶

    문제 1. 작은 수로 열쇠를 정한다. 무엇이 출력될까?

    p, g = 467, 2                          # 모두에게 공개된 수
a, b = 97, 158                         # 브라우저와 서버의 비밀(선에 나가지 않는다)
A, B = pow(g, a, p), pow(g, b, p)      # 선에 나가는 조각
print(A, B)
print(pow(B, a, p), pow(A, b, p))      # 브라우저가 계산한 열쇠, 서버가 계산한 열쇠
    정답과 해설 
    82 163
206 206

    브라우저는 서버의 조각 B에 자기 비밀 a를, 서버는 A에 b를 거듭제곱했다. 둘 다 g^(a×b) mod p라서 같은 206이 나온다. 선에 나간 것은 82와 163뿐이다. 도청자는 2^x mod 467 = 82인 x를 찾아야 하는데, 467은 작아서 하나씩 해 보면 97번째에 찾는다(위젯). 실제로는 수가 너무 커서 이렇게 찾을 수 없다.

    문제 2. www.google.com의 서버에 연결하면서, 한 번은 제 이름으로, 한 번은 남의 이름(www.example.org)으로 TLS 협상을 한다. 무엇이 출력될까?

    import socket
import ssl

ctx = ssl.create_default_context()                      # 인증서를 확인하는 기본 설정
ip = socket.gethostbyname("www.google.com")
for name in ["www.google.com", "www.example.org"]:      # 같은 서버에 이름만 바꿔 묻는다
    try:
        with socket.create_connection((ip, 443), timeout=10) as raw, ctx.wrap_socket(raw, server_hostname=name) as s:
            print(name, s.version())
    except ssl.SSLCertVerificationError as e:
        print(name, e.verify_message)
    정답과 해설 
    www.google.com TLSv1.3
www.example.org Hostname mismatch, certificate is not valid for 'www.example.org'.

    둘째에도 서버는 자기 인증서(Google의 이름이 적힌 것)를 내민다. Python은 그 이름이 접속하려던 www.example.org와 다르다며 협상 중에 연결을 끊는다. 중간자가 다른 사이트의 인증서를 내밀 때도 이렇게 걸린다. 브라우저라면 경고 화면이 나온다.

    문제 3. 1MB를 RSA-2048로 직접 암호화해 보내면, 받는 쪽이 개인 열쇠로 다 푸는 데 얼마나 걸릴까? RSA는 한 번에 190바이트까지 담고, 개인 열쇠로 한 번 푸는 데 서명 한 번만큼 든다고 하자. 그림 1의 값으로 AES와 견준다.

    정답과 해설

    RSA로 푸는 데 2초 가까이, AES는 0.1ms쯤이다. 1,048,576 ÷ 190 ≈ 5,519번을 풀어야 한다. 이 PC의 RSA 개인 열쇠 연산이 1초에 3,107~3,191번이니 1.7~1.8초다. AES는 1초에 10.1~11.1GB라 1MB에 약 0.1ms다. 1만 배가 넘게 차이 난다. 그래서 데이터는 늘 대칭키로 암호화하고, 공개키는 열쇠를 정하고 서명하는 데만 쓴다.

    직접 해보기¶

    실습: 인증서와 협상 결과 보기

    1. 브라우저로 https://www.python.org를 열고 주소창 왼쪽의 사이트 정보 아이콘을 눌러, 연결이 안전하다는 항목에서 인증서를 연다. 발급 대상, 발급자, 유효 기간, 인증서 사슬(계층)을 적는다.
    2. Python으로 같은 사이트에 TLS로 연결해 version(), cipher(), getpeercert()의 발급자와 만료일을 찍는다. 1에서 본 것과 견준다.
    3. 브라우저로 https://expired.badssl.com, https://wrong.host.badssl.com, https://self-signed.badssl.com을 열어 경고 화면의 설명을 읽는다. 경고를 넘기는 버튼은 누르지 않는다.
    4. 위젯에서 중간자를 끼워 두 쪽의 열쇠가 어떻게 되는지 보고, 서명 상자를 켜 결과를 견준다.
    확인할 점
    • 1과 2에서 이 PC는 발급자가 GlobalSign Atlas R3 DV TLS CA 2025 Q4, 그 위가 GlobalSign Root CA - R3이었다. 뿌리 인증서는 이름(CN)이 GlobalSign이고 GlobalSign Root CA - R3은 조직 단위(OU)라, 화면에 GlobalSign으로만 보일 수 있다. 만료일은 2027년 2월 14일이었다. 협상 결과는 TLS 1.3, TLS_AES_128_GCM_SHA256이었다.
    import socket
import ssl

ctx = ssl.create_default_context()
with socket.create_connection(("www.python.org", 443)) as raw, ctx.wrap_socket(raw, server_hostname="www.python.org") as s:
    cert = s.getpeercert()
    print(s.version(), s.cipher()[0])
    print(dict(x[0] for x in cert["issuer"])["commonName"], cert["notAfter"])
    • 3의 세 사이트는 Python으로 접속하면 certificate has expired, Hostname mismatch, …, self-signed certificate를 냈다. 스스로 서명한 인증서는 누구도 보증하지 않았다는 뜻이다. 이 PC에서는 badssl.com의 답이 가끔 10초 넘게 오지 않았다.
    • 인증서의 유효 기간은 길어야 1년 남짓이라(www.python.org는 397일, www.google.com은 84일), 사이트는 만료 전에 새 인증서로 바꿔야 한다. 이 PC에서 본 www.google.com의 인증서는 2026년 12월 21일까지였다.

    AI 활용 과제: 인증서 오류 \"고치기\"

    1. AI에게 "Python에서 ssl.SSLCertVerificationError: certificate verify failed가 나는데 고쳐 줘"라고 한다.
    2. 받은 코드가 무엇을 바꾸는지 적고, 그 방법을 문제 2의 코드에 넣어 www.example.org로 협상해 본다.
    3. 왜 위험한지, 진짜 원인을 찾는 방법은 무엇인지 AI에게 다시 묻는다.
    확인할 점
    • ssl._create_unverified_context(), verify=False, CERT_NONE처럼 확인을 끄는 답이 흔하다. 이 PC에서 문제 2의 코드를 _create_unverified_context()로 바꾸니 www.example.org로도 오류 없이 연결됐다. 인증서를 확인하지 않으면 중간자의 인증서도 받아들인다는 뜻이다(위젯).
    • 진짜 원인은 대개 따로 있다. PC의 날짜가 틀렸거나, 서버가 중간 인증서를 빠뜨렸거나(브라우저는 채워 넣지만 Python은 못 한다), 회사·학교가 쓰는 자체 뿌리 인증서를 프로그램이 모르거나(requests는 Windows 저장소 대신 certifi의 목록을 쓴다), 접속한 이름이 인증서의 이름과 다르다. 오류 메시지의 verify_message를 보고 원인에 맞게 고친다.
    • 시험용 서버의 인증서라면 확인을 끄지 말고 그 인증서를 믿게 한다(ssl.create_default_context(cafile="그 인증서.pem")). 그러면 다른 서버의 인증서는 여전히 걸러진다.

    더 알아보기¶

    양자 컴퓨터를 대비한 열쇠 정하기

    큰 양자 컴퓨터가 생기면 지금의 X25519나 RSA를 풀 수 있다는 걱정이 있다. 그래서 브라우저와 서버는 X25519에 새 방식(ML-KEM)을 함께 쓰는 열쇠 정하기를 쓰기 시작했다. 이 PC에서 OpenSSL 3.5로 www.python.org에 연결하니 X25519MLKEM768로 정했다. Python에 든 OpenSSL은 3.0이라 이 방식을 몰라 X25519를 썼다. 같은 서버라도 클라이언트가 아는 방식에 따라 결과가 다르다.

    이 항목의 측정 프로그램

    그림 1의 빠르기는 이 PC(Core i9-14900KF)에서 Git for Windows에 든 OpenSSL 3.5.4로 아래 명령을 Git Bash에서 3번씩 실행한 범위다. AES는 16KB 블록의 값이다.

    openssl speed -seconds 2 -evp aes-128-gcm
openssl speed -seconds 2 rsa2048 ecdhx25519 ecdsap256

    3절과 그림 2의 시간은 이 PC(학교 유선망)에서 아래 프로그램을 5번 실행한 범위다. 이름은 미리 IP 주소로 바꿔 두어 DNS 시간을 뺐다. TLS 시간에는 인증서 사슬을 확인하는 시간도 들어 있다. TLS 1.2의 값은 ctx.maximum_version = ssl.TLSVersion.TLSv1_2를 넣어 www.google.com에만 같은 방법으로 쟀다.

    # 45번 측정: TCP 연결을 맺는 시간과 그 위에서 TLS 협상을 마치는 시간(10번의 중앙값), 정한 TLS 판과 암호
import socket
import ssl
import statistics
import time

ctx = ssl.create_default_context()
for host in ["www.python.org", "www.google.com"]:
    ip = socket.gethostbyname(host)                 # 이름은 미리 찾아 둔다
    tcp, tls = [], []
    for _ in range(10):
        t0 = time.perf_counter()
        raw = socket.create_connection((ip, 443), timeout=5)
        t1 = time.perf_counter()
        s = ctx.wrap_socket(raw, server_hostname=host)   # 여기서 TLS 협상(인증서 확인 포함)을 한다
        t2 = time.perf_counter()
        tcp.append((t1 - t0) * 1000)
        tls.append((t2 - t1) * 1000)
        version, cipher = s.version(), s.cipher()[0]
        s.close()
    print(f"{host}: TCP {statistics.median(tcp):.1f} ms, TLS {statistics.median(tls):.1f} ms, {version}, {cipher}")

    정리¶

    • 대칭키는 빠르지만 열쇠를 건네기 어렵고, 공개키는 건넬 수 있지만 같은 양을 암호화하면 1만 배 넘게 느리다. TLS는 처음에 공개키로 대칭 열쇠를 정하고 상대를 확인한 뒤, 데이터는 대칭키로 암호화한다.
    • 열쇠 정하기(Diffie-Hellman, X25519)는 공개된 조각만 주고받아 같은 열쇠를 만든다. 도청자는 막지만 중간자는 막지 못해, 서명과 인증서가 필요하다.
    • 인증서 사슬은 뿌리 인증서까지 서명으로 이어진다. TLS 1.3은 왕복 한 번에 협상한다. 인증서 오류는 끄지 말고 원인을 찾는다.
