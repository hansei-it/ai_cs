    46. 브라우저 보안 정책: 동일 출처 정책(SOP)과 CORS¶

    원리 동작을 예측하고 이상을 알아챌 수 있어야 하는 항목

    내가 로그인해 둔 은행 사이트의 쿠키가 브라우저에 있다. 이때 다른 사이트에 들어갔는데, 그 페이지의 JS가 은행의 API로 요청을 보낸다. 브라우저가 쿠키를 실어 보내고 그 응답을 그 JS가 읽을 수 있다면, 내 계좌 정보가 다른 사이트로 새어 나간다. 이것을 막는 브라우저의 규칙이 동일 출처 정책이고, 서버가 "이 출처는 읽어도 된다"고 허락하는 방법이 CORS다. 이 항목은 이 PC의 Chrome에서 직접 실험한 결과로 규칙을 확인한다. 브라우저의 일이라 페이지 쪽 코드는 JavaScript 몇 줄을 쓴다.

    이 항목에서 배우는 것¶

    • 두 주소가 같은 출처인지 판단할 수 있다.
    • 브라우저가 무엇을 막고 무엇을 막지 않는지(보내기는 되고 읽기가 막힌다) 설명할 수 있다.
    • CORS 머리와 사전 요청의 규칙으로, 요청이 읽히는지와 서버가 무엇을 받는지 예측할 수 있다.

    1. 출처는 스킴, 호스트, 포트 셋이다¶

    • 출처(origin)는 주소의 스킴, 호스트, 포트 셋이다. 셋이 모두 같아야 같은 출처다. 이 PC의 Chrome에서는 같은 컴퓨터를 가리키는 http://localhost:8001과 http://127.0.0.1:8001도 다른 출처로 막혔다.
    • 동일 출처 정책: 페이지의 JS는 다른 출처에서 받은 응답을 읽지 못한다. 같은 출처의 것은 자유롭게 읽는다.
    • 막는 것은 읽기다. 단순한 요청은 다른 출처로 보내는 것을 막지 않는다(3절의 사전 요청은 예외). 링크, 폼, 이미지가 원래 다른 사이트로 가듯이, 이 PC의 실험에서도 막힌 요청이 서버에는 닿았다.

    2. CORS는 서버가 읽기를 허락하는 머리다¶

    직접 해 보기CORS: 브라우저가 막는 것요청의 메서드와 머리, 쿠키, 서버가 붙이는 Access-Control 머리를 골라 보내고, 사전 요청이 가는지, 서버가 무엇을 받았는지, 페이지의 JS가 응답을 읽을 수 있는지 본다
    새 창에서 크게 열기
    • 브라우저는 다른 출처로 보내는 요청에 Origin 머리를 붙인다. 응답의 Access-Control-Allow-Origin이 그 출처나 *일 때만 JS에 넘긴다. 없으면 콘솔에 CORS 오류를 찍고 fetch는 TypeError: Failed to fetch로 실패한다.
    • 쿠키를 함께 보내면(credentials: "include") 더 엄격하다. *는 안 되고, 출처를 그대로 적고 Access-Control-Allow-Credentials: true를 붙여야 했다.
    • CORS로 막혀도 서버는 요청을 받아 처리하고 응답까지 했다(위젯의 "서버가 받아 처리하고"). CORS는 서버를 지키는 장치가 아니라, 다른 사이트의 JS가 내 브라우저로 받은 응답을 읽지 못하게 하는 장치다.

    3. 단순하지 않은 요청은 먼저 물어본다¶

    • PUT, DELETE 같은 메서드, JSON 본문(Content-Type: application/json), 직접 만든 머리를 쓰는 요청은 보내기 전에 OPTIONS로 허락을 묻는다(사전 요청). 서버가 사전 요청의 응답에도 Access-Control-Allow-Origin을 붙이고, Access-Control-Allow-Methods, Access-Control-Allow-Headers로 허락해야 실제 요청을 보낸다.
    • 허락하지 않으면 실제 요청은 아예 가지 않았다. 서버 기록에는 OPTIONS만 남았다.
    • 서버를 만드는 쪽의 일은 허락할 출처를 정확히 적는 것이다. *는 누구나 읽어도 되는 공개 데이터에만 쓴다.

    예측해 보기¶

    문제 1. https://shop.example/cart의 페이지에서 본 다섯 주소가 같은 출처인지 확인한다. 무엇이 출력될까?

    from urllib.parse import urlsplit

def origin(url):
    u = urlsplit(url)
    port = u.port or {"http": 80, "https": 443}[u.scheme]   # 포트를 생략하면 기본 포트
    return (u.scheme, u.hostname, port)

base = origin("https://shop.example/cart")
for url in ["https://shop.example/api/items", "http://shop.example/api", "https://api.shop.example/",
            "https://shop.example:8443/", "https://SHOP.example:443/x"]:
    print(origin(url) == base)
    정답과 해설 
    True
False
False
False
True

    경로는 출처가 아니다. 둘째는 스킴(http), 셋째는 호스트(api.shop.example), 넷째는 포트(8443)가 다르다. 다섯째는 호스트의 대소문자가 다르고 포트를 적었지만, 호스트 이름은 대소문자를 가리지 않고 https의 기본 포트가 443이라 같은 출처다.

    문제 2. 페이지 http://127.0.0.1:8001의 JS가 http://127.0.0.1:8002/data로 fetch를 보낸다. 세 경우에 JS가 응답을 읽을 수 있을까? 8002 서버는 무엇을 받을까?

    1. GET, 서버가 CORS 머리를 하나도 붙이지 않는다.
    2. PUT, 서버가 Access-Control-Allow-Origin: *만 붙인다.
    3. 쿠키를 함께 보내는 GET, 서버가 Access-Control-Allow-Origin: *만 붙인다.
    정답과 해설

    셋 다 읽지 못한다. 서버는 1과 3에서 GET을 받아 처리했고, 2에서는 OPTIONS만 받았다. 이 PC의 Chrome이 콘솔에 찍은 까닭은 다음과 같다.

    1. No 'Access-Control-Allow-Origin' header is present on the requested resource. 응답은 왔지만 허락 머리가 없다.
    2. Method PUT is not allowed by Access-Control-Allow-Methods in preflight response. 사전 요청에서 PUT을 허락받지 못해 PUT은 보내지 않았다.
    3. The value of the 'Access-Control-Allow-Origin' header in the response must not be the wildcard '*' when the request's credentials mode is 'include'. 쿠키를 실었으니 *로는 안 된다.

    문제 3. 문제 2의 1에서 막힌 http://127.0.0.1:8002/data를 명령 프롬프트에서 curl로 받으면 어떻게 될까?

    정답과 해설

    그대로 읽힌다. CORS는 브라우저만 지키는 규칙이라, curl이나 Python 프로그램은 Access-Control-Allow-Origin을 보지 않는다. CORS가 막는 것은 "내 브라우저에 든 쿠키와 내 자리(사내망 등)를 빌려, 다른 사이트의 JS가 응답을 읽는 일"이다. 서버의 데이터를 아무나 못 가져가게 하려면 로그인 확인 같은 서버 쪽 검사가 따로 있어야 한다(47번(쿠키, 세션, 토큰(JWT))).

    직접 해보기¶

    실습: 내 PC의 Chrome으로 CORS 실험하기

    1. "더 알아보기"의 실험 서버 코드를 파일(예: cors_servers.py)로 저장해 python cors_servers.py로 실행한다. 8001이 시험 페이지를, 8002가 데이터를 준다. 멈출 때는 Ctrl+C를 누른다.
    2. Chrome으로 http://127.0.0.1:8001/?url=http://127.0.0.1:8002/data를 연다. 개발자 도구의 콘솔에서 오류를 읽고, window.result를 입력해 결과를 본다.
    3. 주소 끝에 &acao=origin을 붙여 다시 연다. 이어서 &method=PUT을 붙이고, 네트워크 탭에서 OPTIONS 요청을 찾는다. 마지막으로 &acam=PUT까지 붙인다. 열 때마다 명령 프롬프트에서 curl http://127.0.0.1:8002/log로 8002 서버가 받은 요청을 본다(읽으면 기록을 비운다).
    4. 명령 프롬프트에서 curl http://127.0.0.1:8002/data를 실행한다.
    확인할 점
    • 2에서 콘솔에는 문제 2의 1과 같은 오류가 찍혔고, window.result는 "TypeError: Failed to fetch"였다.
    • 3에서 acao=origin이면 read(cors, 200): secret data가 됐다. method=PUT을 붙이면 다시 막히고, 서버는 OPTIONS만 받았다. acam=PUT까지 붙이면 OPTIONS, PUT 차례로 받고 다시 읽혔다.
    • 4는 CORS 머리가 없어도 secret data가 그대로 나온다.

    AI와 함께 확인하기¶

    AI 활용 과제: \"CORS 오류가 나요\"

    1. 문제 2의 3처럼 쿠키를 실은 요청이 막힌 콘솔 오류를 AI에게 보여 주고 고치는 방법을 묻는다.
    2. 답이 서버를 고치라는지, 페이지의 fetch를 고치라는지 적는다.
    3. 실험 서버의 주소 값(cred=1, acao, acac, mode)으로 그 방법을 흉내 내 결과를 확인한다.
    확인할 점
    • 페이지의 fetch에 mode: "no-cors"를 넣으라는 답이 있다. 이 PC에서 그렇게 하자 오류는 사라졌지만, 응답의 종류가 opaque, 상태가 0, 본문이 빈 문자열이라 아무것도 읽지 못했다. 오류만 숨긴 것이다.
    • Access-Control-Allow-Origin: *을 붙이라는 답은 쿠키를 실은 요청에는 통하지 않는다(문제 2의 3). 요청한 출처를 정확히 적고 Access-Control-Allow-Credentials: true를 붙여야 읽혔다.
    • 받은 Origin을 아무 확인 없이 그대로 돌려주면서 Access-Control-Allow-Credentials: true를 붙이는 서버는 모든 사이트에 쿠키 실은 읽기를 허락하는 셈이다. 허락할 출처의 목록과 견주는지 본다.

    더 알아보기¶

    동일 출처 정책이 막지 않는 것: CSRF

    다른 사이트의 페이지가 내 은행으로 송금 폼을 보낼 때, 은행의 쿠키에 SameSite=None이 붙어 있으면 브라우저는 그 쿠키를 실어 보낸다. 응답은 읽지 못해도 송금은 이미 처리됐다. 1절의 "보내기는 막지 않는다"가 이런 공격(CSRF)이 되는 까닭이다. 그래서 서버는 폼마다 예측할 수 없는 값을 넣어 확인하고(74번(웹 취약점과 방어)), 쿠키에는 다른 사이트에서 온 요청에 싣지 않게 하는 SameSite 속성을 붙인다(47번(쿠키, 세션, 토큰(JWT))).

    이 항목의 실험 서버

    2절, 3절, 위젯, 문제 2의 결과는 아래 서버를 띄우고 헤드리스 Chrome으로 시험 페이지를 열어 기록한 것이다. 페이지마다 window.result(JS가 읽은 것), 콘솔의 CORS 오류, 8002 서버가 받은 요청(/log)을 모았다. 8002는 주소의 값으로 CORS 머리를 정한다. acao는 none, star, origin 중 하나이고, acac=1, acam=PUT, acah=content-type을 붙일 수 있다. 시험 페이지는 url(대상 주소), method, ct, cred=1, mode와 함께 이 네 값을 받아 대상 주소로 옮긴다.

    # 46번 측정: 출처가 다른 두 서버. 8001은 시험 페이지를, 8002는 데이터를 준다.
# 8002는 주소의 물음표 뒤 값으로 CORS 머리를 정한다: acao=none|star|origin, acac=1, acam=PUT, acah=content-type
# 시험 페이지: http://127.0.0.1:8001/?url=<대상 주소>&method=PUT&ct=application/json&cred=1&mode=no-cors&acao=origin ...
# 8002가 받은 요청(메서드와 경로)은 /log 로 볼 수 있다
import http.server
import threading
import urllib.parse

LOG = []
PAGE = """<!doctype html><meta charset="utf-8"><title>cors</title>
<script>
const q = new URLSearchParams(location.search);
const target = new URL(q.get("url"));
for (const k of ["acao", "acac", "acam", "acah"]) if (q.get(k)) target.searchParams.set(k, q.get(k));   // 서버에 줄 값은 대상 주소로 옮긴다
const opt = { method: q.get("method") || "GET", headers: {}, credentials: q.get("cred") ? "include" : "same-origin" };
if (q.get("ct")) opt.headers["Content-Type"] = q.get("ct");
if (q.get("mode")) opt.mode = q.get("mode");
if (opt.method !== "GET") opt.body = "x";
fetch(target, opt)
  .then(r => r.text().then(t => { window.result = `read(${r.type}, ${r.status}): ` + t; }))
  .catch(e => { window.result = e.name + ": " + e.message; });
</script>"""


class Page(http.server.BaseHTTPRequestHandler):
    def do_GET(self):
        body = PAGE.encode()
        self.send_response(200)
        self.send_header("Content-Type", "text/html; charset=utf-8")
        self.send_header("Content-Length", str(len(body)))
        self.end_headers()
        self.wfile.write(body)

    def log_message(self, *args):
        pass


class Data(http.server.BaseHTTPRequestHandler):
    def handle_any(self):
        u = urllib.parse.urlsplit(self.path)
        if u.path == "/log":
            body = "\n".join(LOG).encode()
            LOG.clear()
            self.send_response(200)
            self.send_header("Content-Length", str(len(body)))
            self.end_headers()
            self.wfile.write(body)
            return
        LOG.append(f"{self.command} {u.path}")
        n = int(self.headers.get("Content-Length") or 0)
        if n:
            self.rfile.read(n)
        q = dict(urllib.parse.parse_qsl(u.query))
        self.send_response(200 if self.command != "OPTIONS" else 204)
        acao = q.get("acao", "none")
        if acao == "star":
            self.send_header("Access-Control-Allow-Origin", "*")
        elif acao == "origin":
            self.send_header("Access-Control-Allow-Origin", self.headers.get("Origin", ""))
        if q.get("acac"):
            self.send_header("Access-Control-Allow-Credentials", "true")
        if q.get("acam"):
            self.send_header("Access-Control-Allow-Methods", q["acam"])
        if q.get("acah"):
            self.send_header("Access-Control-Allow-Headers", q["acah"])
        body = b"" if self.command == "OPTIONS" else b"secret data"
        self.send_header("Content-Length", str(len(body)))
        self.end_headers()
        self.wfile.write(body)

    do_GET = do_POST = do_PUT = do_OPTIONS = handle_any

    def log_message(self, *args):
        pass


threading.Thread(target=http.server.ThreadingHTTPServer(("127.0.0.1", 8001), Page).serve_forever, daemon=True).start()
http.server.ThreadingHTTPServer(("127.0.0.1", 8002), Data).serve_forever()

    정리¶

    • 출처는 스킴, 호스트, 포트 셋이다. 브라우저는 다른 출처의 응답을 페이지의 JS가 읽지 못하게 한다(동일 출처 정책). 단순한 요청은 보내는 것을 막지 않는다.
    • 서버가 Access-Control-Allow-Origin으로 읽기를 허락하는 것이 CORS다. 쿠키를 실으면 출처를 정확히 적고 Access-Control-Allow-Credentials: true를 붙인다.
    • PUT, JSON 본문 같은 요청은 OPTIONS로 먼저 묻고(사전 요청), 허락이 없으면 실제 요청을 보내지 않는다. CORS는 브라우저의 규칙이라 서버의 데이터를 지키는 검사는 따로 해야 한다.
