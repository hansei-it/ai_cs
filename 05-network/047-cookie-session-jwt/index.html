    47. 상태 유지와 인증 수단: 쿠키, 세션, 토큰(JWT)¶

    원리 동작을 예측하고 이상을 알아챌 수 있어야 하는 항목

    HTTP는 요청을 서로 잇지 않는다(43번(HTTP)). 그런데 로그인한 뒤에는 페이지를 옮겨 다녀도 로그인이 유지된다. 브라우저가 요청마다 "나는 아까 로그인한 사람이다"라는 출입증을 내밀기 때문이다. 그 출입증을 담는 그릇이 쿠키이고, 출입증을 만드는 방법이 세션과 토큰(JWT)이다. 이 항목은 쿠키가 오가는 규칙을 이 PC의 Chrome에서 확인하고, 세션과 JWT가 무엇을 기억하고 무엇을 맞바꾸는지 견준다.

    이 항목에서 배우는 것¶

    • 쿠키가 오가는 차례와 HttpOnly, Secure, SameSite 속성의 뜻을 설명할 수 있다.
    • 세션과 JWT가 로그인 상태를 각각 어디에 두는지, 로그아웃과 도난에서 어떻게 다른지 예측할 수 있다.
    • JWT의 세 부분을 나눠 읽고, 서명이 무엇을 막고 무엇을 막지 않는지 말할 수 있다.

    1. 쿠키는 서버가 맡기고 브라우저가 매번 돌려준다¶

    • 서버가 응답에 Set-Cookie로 작은 값을 맡기면, 브라우저는 저장해 두었다가 그 쿠키를 준 서버(호스트)로 가는 요청마다 Cookie 머리로 돌려준다. 프로그램이 따로 하지 않아도 브라우저가 알아서 싣는다.
    • 속성으로 쓰임을 좁힌다. 이 PC의 Chrome에서 HttpOnly 쿠키는 페이지의 JS(document.cookie)에 보이지 않았고 JS로 덮어쓰지도 못했지만, 요청에는 실렸다. 악성 스크립트가 로그인 쿠키를 읽어 가지 못하게 하는 장치다. 다만 그 페이지 안에서 악성 스크립트가 요청을 보내는 것까지 막지는 못한다.
    • SameSite=Lax 쿠키는 다른 사이트에서 GET으로 페이지를 옮길 때(링크, GET 폼)만 실리고, 폼 POST와 fetch에는 실리지 않았다. 다른 사이트가 내 이름으로 요청을 보내는 일(CSRF, 46번(동일 출처 정책과 CORS), 74번(웹 취약점과 방어))을 대부분 막는다. GET 이동에는 실리므로 상태를 바꾸는 일은 GET으로 받지 않는다.

    2. 세션은 서버가 기억하고, JWT는 토큰이 기억한다¶

    직접 해 보기세션과 JWT로그인, 요청, 로그아웃, 훔치기, 서버 다시 켜기, 시간 보내기, 내용 바꾸기를 눌러, 세션 방식과 JWT 방식에서 서버와 브라우저가 무엇을 갖고 요청이 어떻게 되는지 나란히 본다
    새 창에서 크게 열기
    • 세션: 로그인하면 서버가 표에 "s1 → student, 30분"을 적고, 쿠키에는 번호 s1만 준다. 요청마다 서버가 번호로 표를 찾는다. 실제 번호는 짐작할 수 없는 긴 무작위 값이다(secrets.token_urlsafe(32) 등). s1, s2처럼 차례로 매기면 남의 번호를 짐작해 쓸 수 있다. 로그아웃하면 표에서 지우므로 그 번호는 즉시 쓸모가 없어진다.
    • JWT(JSON Web Token): 누구인지와 만료 시각을 토큰 안에 적고 서버의 열쇠로 서명해 준다. 서버는 표 없이 서명과 만료만 확인한다. 서버를 여러 대로 늘려도 열쇠만 나누면 된다. 이 항목의 HS256은 같은 열쇠로 서명하고 확인하므로 열쇠를 가진 서버는 토큰을 만들 수도 있다. 공개키 서명(RS256, ES256, 45번(HTTPS와 TLS))을 쓰면 다른 서버는 공개 열쇠로 확인만 한다.
    • 대신 JWT는 서버가 기억하는 것이 없어서, 로그아웃해도 미리 훔친 토큰은 만료까지 통한다(위젯). 반대로 세션은 서버를 다시 켜면 메모리에 둔 표가 사라지므로 따로 두는 저장소(Redis 등)에 둔다.

    3. JWT의 내용은 누구나 읽고, 서명은 바꾸지 못하게 한다¶

    • JWT는 점으로 나뉜 세 부분(머리, 내용, 서명)이다. 머리와 내용은 JSON을 base64url로 바꿔 쓴 것일 뿐이라 열쇠 없이 누구나 읽는다(문제 1). 비밀번호나 개인 정보를 넣으면 안 된다.
    • 서명은 머리와 내용을 서버의 비밀 열쇠로 HMAC-SHA256 한 값이다. 내용을 바꾸면 서명이 맞지 않는다(문제 2).
    • 서명 확인은 이 PC에서 한 번에 2µs 안팎, 메모리의 세션 표 찾기는 0.03µs였다. 둘 다 네트워크 왕복(수~수십 ms)에 비하면 작다. 세션을 따로 두는 저장소에 두면 요청마다 그 저장소를 한 번 오가는 시간이 더 든다. 두 방식의 차이는 빠르기보다 "서버가 기억하느냐"다.

    예측해 보기¶

    문제 1. JWT를 만들고, 가운데 부분을 열쇠 없이 풀어 본다. 무엇이 출력될까?

    import base64
import hashlib
import hmac
import json

SECRET = b"server-secret-key"                  # 서버만 아는 열쇠

def b64(data):
    return base64.urlsafe_b64encode(data).rstrip(b"=").decode()

def make_token(payload):
    head = b64(json.dumps({"alg": "HS256", "typ": "JWT"}, separators=(",", ":")).encode())
    body = b64(json.dumps(payload, separators=(",", ":")).encode())
    sig = hmac.new(SECRET, f"{head}.{body}".encode(), hashlib.sha256).digest()
    return f"{head}.{body}.{b64(sig)}"

token = make_token({"sub": "student", "role": "user", "exp": 1798761600})
print(token.count("."), len(token))
body = token.split(".")[1]
print(json.loads(base64.urlsafe_b64decode(body + "=" * (-len(body) % 4))))   # 열쇠 없이 푼다
    정답과 해설 
    2 145
{'sub': 'student', 'role': 'user', 'exp': 1798761600}

    토큰은 점 두 개로 나뉜 145자다. 가운데 부분은 열쇠 없이 그대로 풀린다. base64url은 암호가 아니라 글자를 바꿔 쓰는 방법이기 때문이다. exp의 1798761600은 2027년 1월 1일 0시(UTC)를 1970년부터 센 초다.

    문제 2. 문제 1의 토큰에서 내용만 "role":"admin"으로 바꿔 끼우고 서명은 그대로 둔다. 서버의 확인 함수는 두 토큰을 받아 줄까?

    def verify(token):
    head, body, sig = token.split(".")
    good = b64(hmac.new(SECRET, f"{head}.{body}".encode(), hashlib.sha256).digest())
    return hmac.compare_digest(sig, good)

head, body, sig = token.split(".")
fake = b64(json.dumps({"sub": "student", "role": "admin", "exp": 1798761600}, separators=(",", ":")).encode())
print(verify(token), verify(f"{head}.{fake}.{sig}"))
    정답과 해설

    True False. 서버는 받은 머리와 내용으로 서명을 다시 계산해 받은 서명과 견준다. 내용이 바뀌었으니 다시 계산한 서명이 다르다. 열쇠가 없는 사람은 바꾼 내용에 맞는 서명을 만들 수 없다. hmac.compare_digest는 견주는 데 걸리는 시간으로 서명을 짐작하지 못하게, 다른 곳을 찾아도 끝까지 견준다.

    문제 3. 로그인한 뒤 공격자가 쿠키(세션)와 토큰(JWT)을 몰래 복사해 갔다. 내가 곧바로 로그아웃하면, 공격자가 복사한 것으로 보낸 요청은 각각 어떻게 될까? 위젯으로 확인한다.

    정답과 해설

    세션은 거절되고 JWT는 받아 준다. 세션은 로그아웃할 때 서버의 표에서 지웠으므로 그 번호를 찾을 수 없다. JWT는 서버가 기억하는 것이 없어서, 서명이 맞고 만료되지 않은 토큰이면 받아 준다. 그래서 JWT는 만료 시간을 짧게(몇 분~몇십 분) 두고, 새 토큰을 받는 데만 쓰는 토큰을 따로 두거나, 끊어야 할 토큰의 목록을 서버에 둔다. 그만큼 서버가 다시 무언가를 기억하게 된다.

    직접 해보기¶

    실습: 쿠키와 토큰을 직접 보기

    1. 로그인해 둔 사이트에서 브라우저 개발자 도구(F12)를 열고 그 사이트의 쿠키 목록을 찾는다(Chrome은 애플리케이션(Application) 탭). 쿠키마다 HttpOnly, Secure, SameSite 칸을 본다.
    2. 같은 페이지의 콘솔에서 document.cookie를 입력해 1의 목록과 견준다.
    3. "더 알아보기"의 첫 번째 실험 서버를 파일로 저장해 python 파일이름.py로 띄우고, Chrome으로 http://127.0.0.1:8047/set을 연다. 콘솔에서 window.result를 본다.
    4. 문제 1의 make_token에 exp가 지난 값을 넣어 만들고, verify가 받아 주는지 본다. 만료를 확인하도록 verify를 고친다.
    확인할 점
    • 1과 2에서 HttpOnly 칸이 켜진 쿠키는 document.cookie에 나오지 않는다. 로그인 쿠키는 대개 HttpOnly다.
    • 3은 이 PC에서 {js: "theme=dark", server: "theme=dark; session=abc123"}이었다. JS에는 HttpOnly인 session이 보이지 않지만, 서버는 둘 다 받았다. 쿠키는 포트를 가리지 않으므로, 전에 다른 실험 서버가 127.0.0.1에 준 쿠키가 더 보일 수 있다.
    • 4에서 문제 2의 verify는 서명만 보므로 만료된 토큰도 받아 준다. 내용을 풀어 exp가 지금(time.time())보다 큰지도 확인해야 한다.
    import time

def verify_all(token):
    if not verify(token):
        return False
    body = token.split(".")[1]
    payload = json.loads(base64.urlsafe_b64decode(body + "=" * (-len(body) % 4)))
    return payload["exp"] > time.time()            # 만료 시각이 지나면 받지 않는다

print(verify_all(make_token({"sub": "student", "exp": 1000})))   # False

    AI와 함께 확인하기¶

    AI 활용 과제: JWT 로그인 코드 검토하기

    1. AI에게 "Python 웹 서버에서 JWT로 로그인을 구현하는 코드와, 브라우저에서 토큰을 저장하고 보내는 JavaScript"를 짜 달라고 한다.
    2. 아래 확인할 점을 기준으로 코드를 읽고, 문제 2의 위조 토큰과 실습 4의 만료 토큰을 넣어 시험한다. AI 코드의 서명 열쇠를 SECRET과 같게 맞춰야, 만료 토큰이 서명이 아니라 만료 때문에 거절되는지 볼 수 있다.
    3. 고칠 곳을 AI에게 보여 주고 이유를 설명하게 한다.
    확인할 점
    • 서명을 확인하지 않고 내용만 풀어 쓰는 코드가 있다. 문제 2의 위조 토큰을 넣어 admin으로 통하면 큰 구멍이다.
    • exp를 확인하지 않으면 영원히 쓰는 토큰이 된다(실습 4).
    • 토큰 머리의 alg를 그대로 믿는 코드가 있다. alg를 none으로 바꾼 토큰을 받아 주면 서명이 없어도 통한다. 확인할 알고리즘을 서버가 정해 두는지 본다(PyJWT라면 algorithms=["HS256"]).
    • 토큰을 localStorage에 두면 페이지의 JS가 언제든 읽는다. 악성 스크립트 하나가 토큰을 가져갈 수 있다. HttpOnly 쿠키에 두면 JS에서 보이지 않았다(1절). 대신 쿠키는 브라우저가 알아서 실으므로 SameSite를 붙여 CSRF를 막는다.
    • 내용에 비밀번호나 주민등록번호 같은 것을 넣는 코드는 틀렸다. 내용은 누구나 읽는다(문제 1).

    이 항목의 실험과 측정

    1절의 결과는 아래 서버를 띄우고 헤드리스 Chrome으로 /set을 열어 기록했다. 페이지는 열리자마자 /echo로 요청을 보내 서버가 받은 Cookie 머리를 돌려받고, 그것을 document.cookie와 함께 window.result에 둔다. SameSite는 같은 방식으로 localhost:8048의 페이지에서 127.0.0.1:8047로 링크 이동, 폼 POST, fetch(쿠키 포함)를 보내 서버가 받은 Cookie를 견줬다. localhost와 127.0.0.1은 브라우저에게 서로 다른 사이트다. 포트만 다른 주소는 출처(46번(동일 출처 정책과 CORS))는 달라도 같은 사이트라, SameSite가 막지 않는다. 그래서 포트가 아니라 이름을 달리했다. 속성을 적지 않은 쿠키(plain)는 이 PC의 Chrome에서 Lax처럼 다른 사이트의 fetch에는 실리지 않고 링크 이동에는 실렸다. Chrome은 http://127.0.0.1과 localhost에서는 HTTPS가 아니어도 Secure 쿠키를 주고받았다.

    # 47번 측정: /set에서 쿠키 둘(보통, HttpOnly)을 주고, /echo는 받은 Cookie 머리를 그대로 돌려준다
import http.server

PAGE = """<!doctype html><meta charset="utf-8"><title>cookie</title>
<script>
fetch("/echo").then(r => r.text()).then(t => { window.result = {js: document.cookie, server: t}; });
</script>"""


class H(http.server.BaseHTTPRequestHandler):
    def do_GET(self):
        if self.path == "/set":
            body = PAGE.encode()
            self.send_response(200)
            self.send_header("Set-Cookie", "theme=dark; Path=/")
            self.send_header("Set-Cookie", "session=abc123; Path=/; HttpOnly")
        else:
            body = (self.headers.get("Cookie") or "").encode()
            self.send_response(200)
        self.send_header("Content-Type", "text/html; charset=utf-8")
        self.send_header("Content-Length", str(len(body)))
        self.end_headers()
        self.wfile.write(body)

    def log_message(self, *args):
        pass


http.server.HTTPServer(("127.0.0.1", 8047), H).serve_forever()


    # 47번 측정: SameSite 확인. 127.0.0.1:8047이 쿠키 셋(Lax, Strict, SameSite 없음)을 주고, /echo는 받은 Cookie를 기록한다.
# localhost:8048의 페이지가 링크 이동, 폼 POST, fetch(쿠키 포함)로 127.0.0.1:8047/echo에 요청한다
import http.server
import threading

LOG = []


class A(http.server.BaseHTTPRequestHandler):
    def any(self):
        if self.path.startswith("/set"):
            self.send_response(200)
            self.send_header("Set-Cookie", "lax=1; Path=/; SameSite=Lax")
            self.send_header("Set-Cookie", "strict=1; Path=/; SameSite=Strict")
            self.send_header("Set-Cookie", "plain=1; Path=/")
            body = b"set"
        elif self.path.startswith("/log"):
            self.send_response(200)
            body = "\n".join(LOG).encode()
            LOG.clear()
        else:
            n = int(self.headers.get("Content-Length") or 0)
            if n:
                self.rfile.read(n)
            LOG.append(f"{self.command} {self.path} cookie=[{self.headers.get('Cookie') or ''}]")
            self.send_response(200)
            self.send_header("Access-Control-Allow-Origin", "http://localhost:8048")
            self.send_header("Access-Control-Allow-Credentials", "true")
            body = b"echo"
        self.send_header("Content-Length", str(len(body)))
        self.end_headers()
        self.wfile.write(body)

    do_GET = do_POST = any

    def log_message(self, *a):
        pass

    3절의 시간은 이 PC(Core i9-14900KF, Python 3.14)에서 아래 프로그램을 5번 실행한 범위다. JWT 확인은 2.08~2.16µs, 세션 10만 개가 든 사전에서 찾기는 28.5~30.2ns였다.

    # 47번 측정: 요청 한 번마다 서버가 하는 확인의 비용. JWT 서명 확인과, 메모리에 둔 세션 표 찾기
import base64
import hashlib
import hmac
import json
import timeit

SECRET = b"server-secret-key"


def b64(data):
    return base64.urlsafe_b64encode(data).rstrip(b"=").decode()


def make_token(payload):
    head = b64(json.dumps({"alg": "HS256", "typ": "JWT"}, separators=(",", ":")).encode())
    body = b64(json.dumps(payload, separators=(",", ":")).encode())
    sig = hmac.new(SECRET, f"{head}.{body}".encode(), hashlib.sha256).digest()
    return f"{head}.{body}.{b64(sig)}"


def verify(token):
    head, body, sig = token.split(".")
    good = b64(hmac.new(SECRET, f"{head}.{body}".encode(), hashlib.sha256).digest())
    return hmac.compare_digest(sig, good)


token = make_token({"sub": "student", "role": "user", "exp": 1798761600})
sessions = {f"s{i}": {"user": f"user{i}"} for i in range(100_000)}   # 세션 10만 개
jwt_us = timeit.timeit(lambda: verify(token), number=100_000) / 100_000 * 1e6
session_ns = timeit.timeit(lambda: sessions.get("s50000"), number=1_000_000) / 1_000_000 * 1e9
print(f"JWT verify {jwt_us:.2f} us, session lookup {session_ns:.1f} ns")

    정리¶

    • 서버가 Set-Cookie로 맡긴 쿠키를 브라우저가 요청마다 돌려준다. HttpOnly는 JS에서 숨기고, Secure는 HTTPS로만 보내고, SameSite는 다른 사이트에서 오는 요청에 싣는 것을 막는다.
    • 세션은 서버가 표에 기억하고 쿠키에는 번호만 준다. JWT는 내용을 토큰에 담아 서명하고 서버는 서명만 확인한다. 세션은 즉시 끊을 수 있고, JWT는 서버가 기억하지 않는 대신 만료까지 끊기 어렵다.
    • JWT의 내용은 누구나 읽는다. 서명은 바꾸지 못하게 할 뿐 숨기지 않는다. 서명과 만료를 모두 확인한다.
