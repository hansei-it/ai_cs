    48. 실시간 양방향 통신: 폴링, Long-Polling, SSE, 웹소켓¶

    원리 동작을 예측하고 이상을 알아챌 수 있어야 하는 항목

    HTTP는 브라우저가 물어야 서버가 답한다(43번(HTTP)). 그런데 채팅 메시지, 주문 상태, 주가, 게임의 상대 움직임처럼 서버에서 먼저 생기는 일을 브라우저가 바로 알아야 할 때가 많다. 이 항목은 그 일을 하는 네 가지 방법(폴링, 롱 폴링, SSE, 웹소켓)이 무엇을 주고받는지 보고, 같은 PC 안에 서버를 띄워 받기까지 걸리는 시간과 요청 수를 잰다. 웹소켓은 표준 라이브러리만으로 직접 구현해 Chrome과 통하는 것까지 확인했다.

    이 항목에서 배우는 것¶

    • 폴링, 롱 폴링, SSE, 웹소켓에서 오가는 요청과 응답의 모양을 설명할 수 있다.
    • 네 방법의 지연과 요청 수를 예측하고, 일에 맞는 방법을 고를 수 있다.
    • 웹소켓이 HTTP에서 시작해 연결을 바꾸는 과정과 프레임의 모양을 설명할 수 있다.

    1. 브라우저가 묻는 방법과, 서버가 붙잡아 두는 방법¶

    • 폴링은 브라우저가 정해 둔 간격으로 계속 묻는다. 가장 간단하지만, 사건이 없어도 묻고 사건이 생겨도 다음 물음까지 늦게 안다.
    • 롱 폴링은 물음을 받은 서버가 사건이 생길 때까지 답을 미뤄 둔다. 사건이 생기면 바로 답하고, 브라우저는 받자마자 다시 묻는다. 빠르지만 사건마다 요청이 하나씩 든다.
    • 둘 다 보통의 HTTP 요청과 응답이라 어느 서버와 장비에서나 통한다. 대신 브라우저가 서버로 무언가를 보낼 때는 따로 요청을 보내야 한다.

    2. 연결을 열어 두면 서버가 바로 보낸다¶

    직접 해 보기서버가 먼저 알리는 네 가지 방법폴링 간격을 바꿔 가며, 같은 사건 여섯 개를 폴링, 롱 폴링, SSE, 웹소켓이 각각 언제 받고 HTTP 요청을 몇 번 보내는지 시간 줄 위에서 견준다
    새 창에서 크게 열기
    • SSE(Server-Sent Events)는 응답 하나를 끝내지 않고, 사건마다 data: … 한 줄과 빈 줄을 이어 보낸다(Content-Type: text/event-stream). 브라우저의 EventSource가 받아 주고, 끊기면 다시 연결한다. 서버에서 브라우저 쪽으로만 보낸다.
    • 웹소켓은 Upgrade: websocket을 붙인 HTTP 요청으로 시작해, 서버가 101로 답하면 같은 TCP 연결(41번(전송 계층 (TCP·UDP)))을 웹소켓으로 바꾼다. 그 뒤로는 양쪽이 아무 때나 작은 머리(2바이트부터)의 프레임을 주고받는다.
    • 위젯에서 폴링 간격을 줄이면 빨리 받지만 요청이 늘고, 늘리면 요청은 줄지만 늦게 받는다. 연결을 열어 두는 둘은 사건 즉시 받는다.

    3. 이 PC에서 재면 폴링만 수백 ms 늦었다¶

    • 같은 PC 안의 서버가 정해 둔 때에 사건 6개를 일으키고, 네 방법으로 받았다. 1초 간격의 폴링은 평균 527~535ms 늦게 받았고 요청을 9번 보냈다. 롱 폴링, SSE, 웹소켓은 평균 1ms 안팎이었다.
    • 폴링 간격을 0.2초로 줄이자 평균 104~124ms로 빨라졌지만 요청이 41번으로 늘었다. 사건이 없는 동안의 요청은 모두 헛걸음이다.
    • 고르는 법: 가끔 바뀌는 값(예: 몇 분마다 바뀌는 날씨)은 폴링으로 충분하다. 서버가 알리기만 하면 되는 일(알림, 진행 상황)은 SSE, 채팅과 게임처럼 양쪽이 자주 보내는 일은 웹소켓이 맞다.

    예측해 보기¶

    문제 1. 웹소켓을 열 때 브라우저는 무작위 값 Sec-WebSocket-Key를 보내고, 서버는 그 값에 정해진 문자열을 붙여 SHA-1과 base64로 만든 Sec-WebSocket-Accept를 돌려준다. 무엇이 출력될까?

    import base64
import hashlib

GUID = "258EAFA5-E914-47DA-95CA-C5AB0DC85B11"          # 웹소켓 규약(RFC 6455)에 정해진 문자열
key = base64.b64encode(b"0123456789abcdef").decode()    # 브라우저가 보낸 키라고 하자
print(key)
print(base64.b64encode(hashlib.sha1((key + GUID).encode()).digest()).decode())
    정답과 해설 
    MDEyMzQ1Njc4OWFiY2RlZg==
BACScCJPNqyz+UBoqMH89VmURoA=

    16바이트를 base64로 바꾸면 24글자다. 서버가 이 키로 계산한 값을 돌려주면, 서버가 이 요청을 정말 웹소켓으로 알아듣고 답했다는 증거가 된다. 웹소켓을 모르는 서버나, 예전 응답을 저장해 두었다 돌려주는 중간 장비(캐시)의 답을 웹소켓 연결로 잘못 믿는 일을 막는 장치다. 암호나 인증이 아니다. 누구인지 확인하는 일은 쿠키나 토큰(47번(쿠키, 세션, 토큰(JWT)))으로 따로 한다.

    문제 2. 서버가 웹소켓으로 {"id":0}(8바이트)를 보내는 프레임은 몇 바이트일까? 같은 내용을 폴링으로 받으려고 측정 프로그램이 보내는 요청 GET /poll?since=0 HTTP/1.1은 머리 Host: 127.0.0.1:포트와 Accept-Encoding: identity까지 포트가 다섯 자리면 80바이트다.

    data = '{"id":0}'.encode()
frame = bytes([0x81, len(data)]) + data       # 0x81: 마지막 조각인 글자 프레임, 다음 바이트: 길이
print(frame, len(frame))
    정답과 해설

    b'\x81\x08{"id":0}' 10. 머리 2바이트에 내용 8바이트다. 폴링은 요청 80바이트를 보내고, 응답의 상태 줄과 머리까지 받아야 한다. 메시지가 작고 잦을수록 웹소켓이 덜 싣는다. 내용이 126바이트 이상이면 길이를 담는 칸이 늘고, 브라우저가 서버로 보내는 프레임에는 4바이트 가리개(mask)가 더 붙는다.

    문제 3. 위젯에서 폴링 간격을 2초로 바꾸면 사건 6개를 받는 평균 지연과 요청 수는 어떻게 될까? 1초일 때(평균 516.7ms, 9번)와 견준다.

    정답과 해설

    평균 1,183.3ms, 요청 5번. 사건이 0.3초에 생겨도 다음 물음인 2초에야 받는다. 간격을 두 배로 늘리니 요청은 거의 반이 되고 지연은 두 배 넘게 늘었다. 폴링은 지연과 요청 수를 맞바꾸는 방법이고, 둘을 함께 줄이려면 연결을 열어 두는 방법으로 바꿔야 한다.

    직접 해보기¶

    실습: 내 PC에서 네 방법 재 보기

    1. "더 알아보기"의 측정 프로그램을 실행해 네 방법의 평균 지연과 요청 수를 적는다.
    2. 프로그램의 INTERVAL = 1.0을 0.2로 바꾸기 전에, 평균 지연과 요청 수를 예측한다. 바꿔서 실행한다.
    3. websocket 함수를 고쳐, 사건을 받을 때마다 서버로 "ok"를 보내도록 해 본다. 클라이언트가 보내는 프레임에는 가리개가 있어야 한다는 것을 RFC 6455의 5.3절에서 확인하고, 서버 쪽도 그 프레임을 읽도록 고친다.
    4. 위젯에서 폴링 간격 0.5초, 5초를 눌러 지연과 요청 수가 어떻게 바뀌는지 적는다.
    확인할 점
    • 1은 이 PC에서 그림 3의 값이었다.
    • 2는 이 PC에서 평균 104~124ms, 요청 41번이었다(3번 실행한 범위). 8초 남짓 동안 0.2초마다 물었기 때문이다. 위젯의 0.5초는 평균 266.7ms에 17번, 5초는 평균 2,350ms에 3번이다.
    • 3은 웹소켓 규약을 직접 읽어야 하는 어려운 과제다. 클라이언트가 보내는 프레임은 둘째 바이트의 맨 앞 비트를 1로 두고, 4바이트 가리개를 붙인 뒤 내용을 그 가리개로 XOR 해서 보낸다. 서버는 같은 가리개로 다시 XOR 해서 읽는다.

    AI와 함께 확인하기¶

    AI 활용 과제: 실시간 알림 설계 검토하기

    1. AI에게 "웹 쇼핑몰에서 주문 상태가 바뀌면 사용자 화면에 바로 알리는 기능을 만들려 한다. 어떤 방법을 쓰고, 서버와 브라우저 코드는 어떻게 짜야 하나?"라고 묻는다.
    2. 답이 고른 방법과 이유를 적고, 1~3절의 측정과 맞는지 판단한다.
    3. 아래 확인할 점이 빠졌으면 AI에게 다시 묻는다.
    확인할 점
    • 서버에서 브라우저로 알리기만 하는 일이라면 SSE가 알맞다. 웹소켓을 고르는 답이 많은데, 브라우저가 보낼 것이 없다면 더 무거운 선택이다. 이유를 대는지 본다.
    • 연결은 끊긴다(와이파이 바뀜, 서버 재시작). 다시 연결하고, 끊긴 동안 놓친 사건을 다시 받는 방법(마지막으로 받은 번호를 보내기 등)이 있는지 본다. 측정 프로그램의 폴링과 롱 폴링에서는 since=n이 그 역할이다. SSE는 사건마다 id: 줄을 붙여 보내면, EventSource가 다시 연결할 때 마지막 번호를 Last-Event-ID 머리로 보낸다.
    • 롱 폴링, SSE, 웹소켓은 사용자마다 서버가 연결 하나(이 프로그램에서는 스레드 하나)를 붙잡아 둔다. 사용자가 많으면 스레드 대신 비동기 I/O로 많은 연결을 함께 기다리는지 본다(36번(I/O 모델)).
    • 웹소켓은 CORS의 대상이 아니다(46번(동일 출처 정책과 CORS)). 이 PC의 Chrome은 웹소켓을 열 때 Origin 머리에 페이지의 출처를 담아 보냈다. 쿠키도 실었는데, 다른 사이트의 페이지에서 열면 SameSite=None 쿠키만, 포트나 하위 도메인만 다른 같은 사이트의 페이지에서 열면 모든 쿠키를 실었다(47번(쿠키, 세션, 토큰(JWT))). 서버가 Origin을 허락할 출처의 목록과 견주지 않으면, 그런 페이지가 로그인한 사용자의 이름으로 웹소켓을 열 수 있다.

    더 알아보기¶

    이 항목의 측정 프로그램

    3절과 그림의 값은 이 PC(Core i9-14900KF)에서 아래 프로그램을 5번 실행한 범위다. 서버와 네 클라이언트가 한 프로그램 안에서 돌고, 서버가 0.3, 1.7, 2.1, 4.4, 4.5, 7.9초에 사건을 일으킨다. 사건마다 일어난 때와 클라이언트가 받은 때의 차를 지연으로 삼았다. 같은 PC 안이라 네트워크가 걸리지 않으므로, 실제 서비스에서는 여기에 왕복 시간이 더해진다. 1초 폴링이 위젯의 모형(516.7ms)보다 10~20ms 늦은 것은, 첫 물음이 스레드를 띄우느라 몇 ms 늦고 물을 때마다 답을 받는 시간만큼 조금씩 밀려 1, 2, 3초가 아니라 1.007, 2.008, 3.009초…에 물었기 때문이다. 2절의 0.2초 폴링은 INTERVAL만 바꿔 3번 실행한 범위다. 같은 서버에 시험 페이지를 더해 Chrome의 EventSource와 WebSocket으로 연결해 보니 사건 6개를 모두 받았다.

    # 48번 측정: 같은 PC 안의 서버가 정해 둔 때에 사건 6개를 일으킨다. 네 방식의 클라이언트가 각 사건을 받기까지 걸린 시간과
# 서버가 받은 HTTP 요청 수를 잰다. 폴링은 INTERVAL초마다 묻는다. 웹소켓은 표준 라이브러리로 직접 구현했다
import base64
import hashlib
import http.client
import http.server
import json
import socket
import statistics
import threading
import time

AT = [0.3, 1.7, 2.1, 4.4, 4.5, 7.9]            # 사건이 일어나는 때(초)
INTERVAL = 1.0                                 # 폴링 간격(초)
events, cond = [], threading.Condition()       # 일어난 사건: (번호, 일어난 때)
count = {"poll": 0, "long": 0, "sse": 0, "ws": 0}
T0 = time.perf_counter()
GUID = "258EAFA5-E914-47DA-95CA-C5AB0DC85B11"   # 웹소켓 규약에 정해진 문자열


def since(n):
    return [{"id": i, "t": t} for i, t in events[n:]]


class H(http.server.BaseHTTPRequestHandler):
    protocol_version = "HTTP/1.1"

    def do_GET(self):
        path, _, q = self.path.partition("?")
        n = int(q.split("=")[1]) if q else 0
        if path == "/poll":                     # 폴링: 지금 있는 것만 바로 답한다
            count["poll"] += 1
            self.reply(json.dumps(since(n)))
        elif path == "/long":                   # 롱 폴링: 새 사건이 생길 때까지 붙잡고 있다가 답한다
            count["long"] += 1
            with cond:
                cond.wait_for(lambda: len(events) > n, timeout=20)
            self.reply(json.dumps(since(n)))
        elif path == "/sse":                    # SSE: 응답 하나를 끝내지 않고 사건마다 한 덩어리씩 보낸다
            count["sse"] += 1
            self.send_response(200)
            self.send_header("Content-Type", "text/event-stream")
            self.end_headers()
            sent = 0
            while sent < len(AT):
                with cond:
                    cond.wait_for(lambda: len(events) > sent)
                    batch = since(sent)             # 보낼 것을 잠근 채 꺼내 둔다(보내는 사이에 생긴 사건도 놓치지 않게)
                for e in batch:
                    self.wfile.write(f"data: {json.dumps(e)}\n\n".encode())
                    self.wfile.flush()
                sent += len(batch)
            self.close_connection = True            # 이 연결로 다음 HTTP 요청을 읽지 않는다
        elif path == "/ws":                     # 웹소켓: HTTP로 시작해 101로 바꾼 뒤 프레임을 주고받는다
            count["ws"] += 1
            accept = base64.b64encode(hashlib.sha1((self.headers["Sec-WebSocket-Key"] + GUID).encode()).digest()).decode()
            self.send_response(101)
            self.send_header("Upgrade", "websocket")
            self.send_header("Connection", "Upgrade")
            self.send_header("Sec-WebSocket-Accept", accept)
            self.end_headers()
            sent = 0
            while sent < len(AT):
                with cond:
                    cond.wait_for(lambda: len(events) > sent)
                    batch = since(sent)
                for e in batch:
                    data = json.dumps(e).encode()
                    self.wfile.write(bytes([0x81, len(data)]) + data)   # 0x81: 마지막 조각인 글자 프레임, 다음 바이트: 길이(125바이트까지)
                    self.wfile.flush()
                sent += len(batch)
            self.close_connection = True            # 웹소켓으로 바꾼 연결이라 HTTP 요청을 더 읽지 않는다

    def reply(self, text):
        body = text.encode()
        self.send_response(200)
        self.send_header("Content-Type", "application/json")
        self.send_header("Content-Length", str(len(body)))
        self.end_headers()
        self.wfile.write(body)

    def log_message(self, *args):
        pass


srv = http.server.ThreadingHTTPServer(("127.0.0.1", 0), H)
srv.daemon_threads = True
PORT = srv.server_address[1]
threading.Thread(target=srv.serve_forever, daemon=True).start()
got = {k: [] for k in count}                    # 방식별: 사건마다 받기까지 걸린 시간(ms)


def note(kind, e):
    got[kind].append((time.perf_counter() - T0 - e["t"]) * 1000)


def polling():
    c, n = http.client.HTTPConnection("127.0.0.1", PORT), 0
    while n < len(AT):
        c.request("GET", f"/poll?since={n}")
        for e in json.loads(c.getresponse().read()):
            note("poll", e)
            n += 1
        time.sleep(INTERVAL)


def long_polling():
    c, n = http.client.HTTPConnection("127.0.0.1", PORT), 0
    while n < len(AT):
        c.request("GET", f"/long?since={n}")
        for e in json.loads(c.getresponse().read()):
            note("long", e)
            n += 1


def sse():
    c = http.client.HTTPConnection("127.0.0.1", PORT)
    c.request("GET", "/sse")
    r = c.getresponse()
    for _ in AT:
        line = r.fp.readline()                  # "data: {...}" 한 줄과 빈 줄 하나가 사건 하나
        r.fp.readline()
        note("sse", json.loads(line[len("data: "):]))


def websocket():
    s = socket.create_connection(("127.0.0.1", PORT))
    key = base64.b64encode(b"0123456789abcdef").decode()
    s.sendall(f"GET /ws HTTP/1.1\r\nHost: 127.0.0.1\r\nUpgrade: websocket\r\nConnection: Upgrade\r\n"
              f"Sec-WebSocket-Key: {key}\r\nSec-WebSocket-Version: 13\r\n\r\n".encode())
    f = s.makefile("rb")
    while f.readline() != b"\r\n":              # 101 응답의 머리를 건너뛴다
        pass
    for _ in AT:
        head = f.read(2)
        note("ws", json.loads(f.read(head[1] & 0x7F)))   # 길이가 125바이트까지일 때만 맞다(126 이상이면 길이 칸이 늘어난다)


workers = [threading.Thread(target=w) for w in (polling, long_polling, sse, websocket)]
for w in workers:
    w.start()
for t in AT:                                    # 정해 둔 때에 사건을 일으킨다
    time.sleep(max(0, t - (time.perf_counter() - T0)))
    with cond:
        events.append((len(events), time.perf_counter() - T0))
        cond.notify_all()
for w in workers:
    w.join()
for k, name in [("poll", f"polling ({INTERVAL:g} s)"), ("long", "long polling"), ("sse", "SSE"), ("ws", "WebSocket")]:
    d = got[k]
    print(f"{name}: delay mean {statistics.mean(d):.1f} ms, max {max(d):.1f} ms, HTTP requests {count[k]}")

    정리¶

    • HTTP는 브라우저가 물어야 서버가 답한다. 폴링은 계속 묻고, 롱 폴링은 서버가 답을 사건이 생길 때까지 미룬다.
    • SSE는 응답 하나를 끝내지 않고 사건을 이어 보내고(서버 → 브라우저), 웹소켓은 HTTP로 시작해 101로 바꾼 연결에서 양쪽이 프레임을 주고받는다.
    • 폴링은 지연과 요청 수를 맞바꾼다. 연결을 열어 두는 방법은 사건 즉시 받는다. 알리기만 하면 SSE, 양쪽이 자주 보내면 웹소켓을 쓴다.
