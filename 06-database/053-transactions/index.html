    53. 트랜잭션: ACID 원칙과 비관적/낙관적 락¶

    원리 동작을 예측하고 이상을 알아챌 수 있어야 하는 항목

    계좌 이체는 "보내는 쪽에서 빼기"와 "받는 쪽에 더하기" 두 문장이다. 그 사이에 서버가 멈추면 돈이 사라진다. 마지막 좌석을 두 사람이 동시에 예약하면 한 좌석이 두 번 팔릴 수 있다. 이 항목은 여러 문장을 한 덩어리로 다루는 트랜잭션과, 동시에 같은 행을 고칠 때 쓰는 두 가지 락을 MySQL에서 직접 써 본다. 실습은 MySQL 접속 창 둘(세션 A, B)로 한다(실습 환경의 6절).

    이 항목에서 배우는 것¶

    • 트랜잭션과 ACID의 뜻을 이체의 예로 설명할 수 있다.
    • 읽고 계산해서 쓰는 코드가 동시에 돌 때 갱신 손실이 생기는 까닭과, 비관적 락과 낙관적 락이 그것을 막는 방법을 설명할 수 있다.
    • 경합 정도에 따라 어느 방법을 쓸지 고를 수 있다.

    1. 트랜잭션은 여러 문장을 한 덩어리로 다룬다¶

    • START TRANSACTION부터 COMMIT까지의 문장은 모두 확정되거나, ROLLBACK하거나 도중에 끊기면 모두 없던 일이 된다. 이것이 트랜잭션이다.
    • MySQL의 접속 창은 따로 시작하지 않으면 문장마다 바로 확정한다(자동 커밋). 이체의 첫 UPDATE 뒤에 연결이 끊기면 빠진 10만 원만 확정되어 돈이 사라진다(그림).
    • 트랜잭션이 지켜야 할 네 성질을 ACID라 한다. 원자성, 제약을 지키는 일관성(49번(RDBMS의 장점과 데이터 독립성)의 CHECK), 동시에 도는 트랜잭션끼리의 격리성(54번(트랜잭션 격리 수준)), 커밋한 것이 남는 지속성(58번(백업과 복구))이다.

    2. 읽고 계산해서 쓰면 동시에 고칠 때 하나를 잃는다¶

    직접 해 보기마지막 좌석을 두 사람이 동시에락 없음, 비관적 락(FOR UPDATE), 낙관적 락(version)을 골라 두 세션의 문장을 한 단계씩 실행하며, 누가 기다리고 좌석이 몇 번 팔리는지 본다
    새 창에서 크게 열기
    • 프로그램이 SELECT로 남은 좌석을 읽고, 계산하고, UPDATE로 쓰면 그 사이에 다른 세션이 끼어든다. 둘 다 "1석 남음"을 보고 둘 다 예약한다(위젯의 "락 없이"). DBMS를 써도 읽기와 쓰기를 따로 보내면 갱신 손실(49번(RDBMS의 장점과 데이터 독립성))이 생긴다.
    • 비관적 락은 먼저 잠그고 읽는다. SELECT … FOR UPDATE는 그 행을 트랜잭션이 끝날 때까지 잠근다. 다른 세션의 FOR UPDATE와 UPDATE는 기다렸다가 새 값을 읽는다.
    • 낙관적 락은 잠그지 않고 읽되, 쓸 때 "그사이 아무도 안 고쳤으면"이라는 조건을 붙인다. 행마다 version 열을 두고 WHERE version = 읽은 값으로 고치면서 1을 올린다. 맞는 행이 0이면 누가 먼저 고친 것이니 다시 읽어 다시 한다.

    3. 무엇을 쓸지는 얼마나 몰리느냐에 달렸다¶

    • 한 상품에 몰리게 하니 락 없이 읽고 고친 쪽은 빨랐지만, 4,000개를 팔고도 재고가 3,490~3,499개 남았다. 여덟 연결이 같은 값을 읽고 같은 값을 써서, 4,000번의 UPDATE 가운데 값이 실제로 바뀐 것이 501~510번뿐이었다. 일을 덜 하고 틀린 것이다. 비관적 락과 낙관적 락은 둘 다 맞았는데, 낙관적 락은 다시 시도를 2만 5천 번 넘게 해서 비관적 락보다 빠르지 않았다. 몰리지 않을 때는 낙관적 락이 조금 빨랐다.
    • 먼저 한 문장으로 쓸 수 있는지 본다. UPDATE product SET stock = stock - 1 WHERE id = 1 AND stock > 0은 DBMS가 읽기와 쓰기를 한 번에 하고 행을 잠가 줄을 세운다. 그래서 맞는 방법 가운데 가장 빨랐다.
    • 잠금은 짧게 잡는다. 트랜잭션 안에서 사용자 입력이나 바깥 API를 기다리지 않는다. 여러 행을 잠그는 차례가 세션마다 엇갈리면 어떻게 되는지는 문제 3에서 본다.

    예측해 보기¶

    문제 1. 김하나(300,000원)가 이두리(50,000원)에게 100,000원을 보낸다. 이번에는 START TRANSACTION 뒤에 두 UPDATE를 다 했고, SELECT로 보니 200,000원과 150,000원이었다. 그런데 COMMIT을 하지 않은 채 exit로 접속을 끊었다. 다시 접속해 보면 두 잔액은 얼마일까?

    START TRANSACTION;
UPDATE account SET balance = balance - 100000 WHERE id = 1;
UPDATE account SET balance = balance + 100000 WHERE id = 2;
SELECT * FROM account;
-- 여기서 exit로 접속을 끊었다. COMMIT은 하지 않았다
    정답과 해설

    300,000원과 50,000원이다. 이 PC의 MySQL 8.4에서 확인했다. 내 창의 SELECT에는 고친 값이 보였지만 아직 확정된 것은 아니었다. COMMIT 전에 연결이 끊기자 MySQL이 트랜잭션 전체를 되돌렸다. 두 UPDATE를 다 했어도 COMMIT하지 않으면 없던 일이 된다. 그래서 함께 되거나 함께 안 되어야 하는 문장은 한 트랜잭션에 넣고, 다 한 뒤에 반드시 COMMIT한다.

    문제 2. 세션 A가 START TRANSACTION, SELECT remaining FROM seat WHERE id = 1 FOR UPDATE, UPDATE seat SET remaining = 0 WHERE id = 1까지 하고 아직 커밋하지 않았다. 이때 세션 B가 FOR UPDATE 없이 SELECT remaining FROM seat WHERE id = 1을 하면 기다릴까? 무엇을 읽을까?

    정답과 해설

    기다리지 않고 1을 읽는다. 이 PC에서 1ms 안팎에 1이 나왔다. MySQL(InnoDB)의 기본 격리 수준(REPEATABLE READ)에서 평범한 SELECT는 잠금을 보지 않고, 커밋된 값을 읽는다(54번(트랜잭션 격리 수준)의 스냅숏). 그래서 비관적 락은 읽는 쪽도 모두 FOR UPDATE로 읽어야 효과가 있다. 한 곳이라도 평범한 SELECT로 읽고 그 값으로 계산하면 위젯의 "락 없이"와 같아진다.

    문제 3. 좌석 행 1과 2가 있다. 세션 A는 1을, 세션 B는 2를 FOR UPDATE로 잠갔다. 이어서 A가 2를, B가 1을 FOR UPDATE로 잠그려 하면 어떻게 될까?

    정답과 해설

    둘이 서로를 기다리는 교착 상태(35번(교착 상태))가 되고, MySQL이 한쪽을 되돌린다. 이 PC에서는 고리를 닫은 B가 곧바로 ERROR 1213 (40001): Deadlock found when trying to get lock; try restarting transaction을 받았고, B의 트랜잭션은 통째로 되돌려졌다. 기다리던 A는 그제야 행 2를 잠갔다. 어느 쪽을 되돌릴지는 MySQL이 고른다. 넣고 고친 행이 적은 쪽을 고르므로, B가 먼저 다른 표에 행 셋을 넣어 두었을 때는 A가 1213을 받았다. 프로그램은 이 오류를 받으면 트랜잭션을 처음부터 다시 해야 한다. 여러 행을 잠글 때는 모두 같은 차례(예: id 순)로 잠그면 이 고리가 생기지 않는다.

    직접 해보기¶

    실습: 두 세션으로 마지막 좌석 예약하기

    1. MySQL 접속 창을 둘 연다(실습 환경의 6절). 한 창에서 아래 SQL로 표를 만든다. 두 창 모두 USE lab53;을 실행한다.
    2. 위젯의 "비관적 락" 차례대로 두 창에 번갈아 입력한다. B의 FOR UPDATE에서 커서가 멈추는지, A가 COMMIT한 순간 B에 무엇이 나오는지 본다.
    3. UPDATE seat SET remaining = 1, version = 7 WHERE id = 1;과 DELETE FROM booking;으로 되돌리고 "낙관적 락" 차례대로 해 본다. B의 UPDATE 뒤에 나오는 Rows matched를 본다.
    4. 3처럼 되돌린 뒤 "비관적 락"의 처음 네 단계(B의 FOR UPDATE가 멈춘 데까지)를 다시 하고, A를 아무것도 하지 않고 두면 어떻게 되는지 1분쯤 지켜본다.
    CREATE DATABASE lab53;
USE lab53;
CREATE TABLE seat (id INT PRIMARY KEY, remaining INT NOT NULL, version INT NOT NULL);
CREATE TABLE booking (id INT AUTO_INCREMENT PRIMARY KEY, seat_id INT NOT NULL, who CHAR(1) NOT NULL);
INSERT INTO seat VALUES (1, 1, 7);
    확인할 점
    • 2에서 B의 SELECT … FOR UPDATE는 결과 없이 멈춰 있다가, A의 COMMIT이 끝나자마자 remaining이 0인 결과를 낸다. 좌석 표와 예약 표를 보면 예약은 A 하나다.
    • 3에서 B의 UPDATE는 Query OK, 0 rows affected와 함께 Rows matched: 0 Changed: 0을 낸다. 조건 version = 7에 맞는 행이 없다는 뜻이다. "락 없이"의 B처럼 같은 값으로 고치면 Rows matched: 1 Changed: 0이 나온다. 낙관적 락은 맞은 행이 0인지를 본다.
    • 4에서 B는 50초 뒤 ERROR 1205 (HY000): Lock wait timeout exceeded; try restarting transaction을 받는다. 이 PC의 innodb_lock_wait_timeout은 기본값 50초였다. 잠금을 오래 쥐면 다른 요청이 줄줄이 이렇게 실패한다. 시간 초과는 그 문장만 되돌리고 B의 트랜잭션은 열린 채 남으므로, 두 창 모두 ROLLBACK;한다.
    • 실습이 끝나면 두 창 모두 트랜잭션을 끝낸 뒤 DROP DATABASE lab53;으로 지운다. 열린 트랜잭션이 남아 있으면 DROP이 끝나지 않고 기다린다.

    AI와 함께 확인하기¶

    AI 활용 과제: 재고 차감 코드 검토하기

    1. AI에게 "Python과 MySQL로, 주문이 들어오면 상품 재고를 하나 줄이고 주문을 기록하는 함수를 짜 줘. 동시에 주문이 많이 들어온다"라고 한다.
    2. 받은 코드에서 재고를 읽는 문장, 고치는 문장, 트랜잭션의 시작과 끝을 표시한다.
    3. 같은 상품을 둘이 동시에 주문할 때 무슨 일이 생길지 위젯의 세 방식 가운데 어디에 해당하는지 적고, 아래 확인할 점을 AI에게 물어 고친다.
    확인할 점
    • SELECT stock으로 읽고 Python에서 1을 뺀 값을 UPDATE로 쓰는 코드는 "락 없이"와 같다. 이 PC의 측정에서 4,000개를 팔고도 재고가 3,490개 넘게 남았다.
    • FOR UPDATE를 쓰면서 자동 커밋인 채로 두면 문장이 끝나자마자 잠금이 풀려 효과가 없다. 같은 트랜잭션 안에서 읽고 고친 뒤 커밋하는지 본다.
    • 재고 차감과 주문 기록이 한 트랜잭션에 있는지 본다. 따로 커밋하면 재고는 줄었는데 주문이 없는 일이 생긴다(1절 그림의 자동 커밋).
    • UPDATE … SET stock = stock - 1 WHERE id = ? AND stock > 0 한 문장과, 맞은 행이 0이면 품절로 처리하는 방법을 제안하는지 본다. 가장 짧고, 측정에서도 맞는 방법 가운데 가장 빨랐다.
    • 낙관적 락으로 다시 시도한다면, 트랜잭션을 끝내고(COMMIT이나 ROLLBACK) 새로 읽는지 본다. PyMySQL은 기본이 자동 커밋 꺼짐이라 한 트랜잭션 안에서 다시 읽게 되기 쉽다. 이 PC에서 그렇게 하니 다른 세션이 version을 8로 고친 뒤에도 계속 7을 읽어, 몇 번을 다시 해도 맞은 행이 0이었다(54번(트랜잭션 격리 수준)의 스냅숏). ROLLBACK한 뒤에야 8이 보였다.
    • 교착 상태(오류 1213)를 받으면 다시 시도하는지 본다(문제 3).

    더 알아보기¶

    MySQL과 SQLite의 잠금 단위

    MySQL의 InnoDB는 행 단위로 잠근다. WHERE가 기본 키나 인덱스로 행을 찾으면 그 행만 잠그므로, 다른 좌석이나 다른 상품을 고치는 세션은 기다리지 않는다(3절 그림의 "저마다 다른 상품"). 인덱스 없는 열로 찾으면 훑은 행을 모두 잠근다. 이 PC에서 인덱스 없는 name 열을 더한 상품 표로 해 보니, A가 WHERE name = 'a'로 고치고 커밋하지 않자, id 2를 고치려는 B도 기다렸다. WHERE id = 1로 고칠 때는 기다리지 않았다. 49번(RDBMS의 장점과 데이터 독립성)의 SQLite는 쓰는 동안 데이터베이스 파일 전체를 잠근다. 쓰는 사람이 한 번에 하나뿐이라, 서로 다른 행을 고쳐도 줄을 선다. 여러 사용자가 동시에 쓰는 서버에 MySQL 같은 DBMS를 쓰는 까닭 중 하나다.

    이 항목의 측정 프로그램

    3절의 값과 그림은 이 PC(Core i9-14900KF, DDR5 64GB, NVMe SSD, Windows 11)의 Docker Desktop(WSL 2)에서 띄운 MySQL 8.4.11에, 같은 PC의 Python 3.14와 PyMySQL로 연결 8개를 열어 잰 것이다(5번 실행한 범위). 연결마다 스레드 하나가 500번 산다. MySQL의 설정은 바꾸지 않았다(커밋마다 로그를 디스크에 쓴다). 한 문장 UPDATE도 4,000번 커밋하느라 5초 남짓 걸렸다. 값을 바꾸지 않는 UPDATE(SET stock = stock, 프로그램의 unchanged)를 같은 방법으로 4,000번 하니 0.33~0.45초였다. 락 없이 읽고 고친 쪽이 빨랐던 것은 값이 바뀐 UPDATE가 500여 번뿐이었기 때문이다. 위젯의 각 단계도 같은 방법으로 연결 둘을 열어 실행했고, 0.5초 안에 끝나지 않은 문장을 "기다린다"로 보았다. PyMySQL은 pip install pymysql로 설치한다.

    # 53번 측정: 재고 4,000개를 연결 8개가 500번씩 동시에 하나씩 산다
import threading
import time

import pymysql

CFG = dict(host="127.0.0.1", port=3306, user="root", password="비밀번호", database="lab53m", autocommit=True)
WORKERS, BUYS, STOCK = 8, 500, 4000


def reset():
    c = pymysql.connect(**{k: v for k, v in CFG.items() if k != "database"})
    cur = c.cursor()
    cur.execute("CREATE DATABASE IF NOT EXISTS lab53m")
    cur.execute("USE lab53m")
    cur.execute("DROP TABLE IF EXISTS product")
    cur.execute("CREATE TABLE product (id INT PRIMARY KEY, stock INT NOT NULL, version INT NOT NULL)")
    cur.execute("INSERT INTO product VALUES (1, %s, 0)", (STOCK,))
    c.close()


def naive(cur, stats):                     # 읽고, 계산하고, 쓴다
    cur.execute("SELECT stock FROM product WHERE id = 1")
    s = cur.fetchone()[0]
    stats["changed"] += cur.execute("UPDATE product SET stock = %s WHERE id = 1", (s - 1,))   # 값이 실제로 바뀐 행 수(같은 값을 쓰면 0)


def atomic(cur, stats):                    # 한 문장으로 뺀다
    cur.execute("UPDATE product SET stock = stock - 1 WHERE id = 1 AND stock > 0")


def pessimistic(cur, stats):               # 잠그고 읽는다
    cur.execute("START TRANSACTION")
    cur.execute("SELECT stock FROM product WHERE id = 1 FOR UPDATE")
    s = cur.fetchone()[0]
    cur.execute("UPDATE product SET stock = %s WHERE id = 1", (s - 1,))
    cur.execute("COMMIT")


def optimistic(cur, stats):                # 읽은 version이 그대로일 때만 고친다
    while True:
        cur.execute("SELECT stock, version FROM product WHERE id = 1")
        s, v = cur.fetchone()
        if cur.execute("UPDATE product SET stock = %s, version = %s WHERE id = 1 AND version = %s", (s - 1, v + 1, v)) == 1:
            return
        stats["retry"] += 1                # 그사이 다른 쪽이 먼저 고쳤다. 다시 읽는다


def unchanged(cur, stats):                 # 견주어 보기: 값을 바꾸지 않는 UPDATE(바뀐 행 0)
    cur.execute("UPDATE product SET stock = stock WHERE id = 1")


def bench(fn):
    reset()
    stats = {"retry": 0, "changed": 0}
    lock = threading.Lock()

    def worker():
        con = pymysql.connect(**CFG)
        cur = con.cursor()
        local = {"retry": 0, "changed": 0}
        for _ in range(BUYS):
            fn(cur, local)
        con.close()
        with lock:
            for k in stats:
                stats[k] += local[k]

    ths = [threading.Thread(target=worker) for _ in range(WORKERS)]
    t = time.perf_counter()
    for th in ths:
        th.start()
    for th in ths:
        th.join()
    ms = (time.perf_counter() - t) * 1000
    c = pymysql.connect(**CFG)
    cur = c.cursor()
    cur.execute("SELECT stock FROM product WHERE id = 1")
    left = cur.fetchone()[0]
    c.close()
    return left, ms, stats


for name, fn in [("naive", naive), ("atomic", atomic), ("pessimistic", pessimistic), ("optimistic", optimistic), ("unchanged", unchanged)]:
    left, ms, stats = bench(fn)
    if fn is unchanged:
        print(f"{name}: {ms:.0f} ms")
        continue
    extra = f", UPDATE that changed the row {stats['changed']}" if name == "naive" else ""
    print(f"{name}: left {left} (should be 0), {ms:.0f} ms, retries {stats['retry']}{extra}")

    3절 그림의 "저마다 다른 상품"은 상품을 8개 두고 연결마다 자기 상품만 사게 바꿔 잰 것이다.

    정리¶

    • 트랜잭션은 여러 문장을 모두 되거나 모두 안 되게 묶는다. 자동 커밋에서는 문장마다 확정되어 이체 도중에 끊기면 돈이 사라진다. ACID는 원자성, 일관성, 격리성, 지속성이다.
    • 읽고 계산해서 쓰면 동시에 고칠 때 하나를 잃는다. 비관적 락은 FOR UPDATE로 먼저 잠그고, 낙관적 락은 version을 견주며 고쳐 맞은 행이 0이면 다시 한다.
    • 한 문장으로 쓸 수 있으면 그것이 맞는 방법 가운데 가장 빠르고 안전하다. 몰리는 곳에는 비관적 락, 드물게 겹치는 곳에는 낙관적 락이 맞다. 잠금은 짧게, 같은 차례로 잡는다.
