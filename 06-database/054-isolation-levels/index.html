    54. 트랜잭션 격리 수준과 동시성 문제(Dirty Read, Non-Repeatable Read, Phantom Read)¶

    원리 동작을 예측하고 이상을 알아챌 수 있어야 하는 항목

    트랜잭션 여럿이 동시에 돌면, 한쪽이 고치는 중인 데이터를 다른 쪽이 읽게 된다. 이때 무엇을 보여 줄지를 정하는 것이 격리 수준이다. 완전히 떼어 놓을수록 안전하지만 서로 기다리는 일이 늘어난다. 이 항목은 세 가지 이상 현상을 MySQL의 네 격리 수준에서 직접 일으켜 보고, 기본값인 REPEATABLE READ가 실제로 무엇을 막고 무엇을 막지 않는지 확인한다. 실습은 53번(트랜잭션과 락)처럼 MySQL 접속 창 둘로 한다.

    이 항목에서 배우는 것¶

    • Dirty Read, Non-Repeatable Read, Phantom Read를 두 트랜잭션의 차례로 설명할 수 있다.
    • 네 격리 수준에서 각 이상 현상이 일어나는지 예측하고, MySQL에서 확인할 수 있다.
    • 스냅숏으로 읽는 평범한 SELECT와 잠그며 읽는 SELECT … FOR UPDATE가 다른 값을 내는 까닭을 설명할 수 있다.

    1. 동시에 돌면 세 가지 이상한 일이 생길 수 있다¶

    • Dirty Read: 다른 트랜잭션이 고쳤지만 아직 커밋하지 않은 값을 읽는다. 그쪽이 되돌리면 없던 값을 믿은 셈이다.
    • Non-Repeatable Read: 한 트랜잭션 안에서 같은 행을 두 번 읽었는데, 그사이 다른 쪽이 고쳐 커밋해서 값이 다르다.
    • Phantom Read: 같은 조건으로 두 번 셌는데, 그사이 다른 쪽이 행을 넣어 커밋해서 개수가 다르다. 고친 행이 아니라 새로 생긴 행이 문제다.

    2. 격리 수준은 무엇을 막을지 고르는 것이다¶

    직접 해 보기격리 수준마다 B가 보는 것격리 수준(네 가지)과 이상 현상(Dirty, Non-Repeatable, Phantom Read)을 골라 두 세션의 문장을 한 단계씩 실행하며, B가 무엇을 읽고 누가 기다리는지 본다
    새 창에서 크게 열기
    • SQL 표준은 네 격리 수준을 정한다. READ UNCOMMITTED는 아무것도 막지 않고, READ COMMITTED는 Dirty Read를, REPEATABLE READ는 Non-Repeatable Read까지 막는다. SERIALIZABLE은 셋 다 막는다.
    • MySQL은 격리 수준을 연결마다 정한다(SET SESSION TRANSACTION ISOLATION LEVEL …). 기본값은 REPEATABLE READ다. 위젯에서 B의 수준을 바꿔 가며 같은 차례를 실행해 본다.
    • 낮은 수준일수록 기다리는 일이 적고, 높은 수준일수록 안전하다. MySQL의 SERIALIZABLE은 트랜잭션 안의 평범한 SELECT도 잠그며 읽어서, 상대를 기다리게 하는 방법으로 막았다(위젯의 SERIALIZABLE).

    3. MySQL의 REPEATABLE READ는 스냅숏으로 읽는다¶

    • 표준은 REPEATABLE READ에서 Phantom Read를 허용한다. 그런데 MySQL(InnoDB)에서는 평범한 SELECT로 다시 셀 때 막혔다. 트랜잭션 안에서 데이터의 스냅숏을 찍어 두고, 그 뒤의 평범한 SELECT는 모두 그 스냅숏을 읽기 때문이다(MVCC). 스냅숏을 언제 찍는지는 문제 1에서 본다.
    • 잠그며 읽는 SELECT … FOR UPDATE와 UPDATE는 스냅숏이 아니라 지금 커밋된 최신 값을 읽는다. 그래서 평범한 SELECT로 3개를 센 트랜잭션이 FOR UPDATE로 다시 세니 4개였다(그림의 ※). 처음부터 잠그며 세면 어떻게 되는지는 문제 2에서 본다.
    • 스냅숏으로 읽은 값으로 계산해 쓰면 53번(트랜잭션과 락)의 갱신 손실이 그대로 생긴다. 읽고 쓸 행은 FOR UPDATE로 읽거나, 한 문장으로 고친다(문제 3).

    예측해 보기¶

    문제 1. B는 기본값인 REPEATABLE READ다. B가 START TRANSACTION만 하고 아직 아무것도 읽지 않았을 때, A가 김하나의 잔액(100)을 50으로 고쳐 커밋했다. 그 뒤 B가 두 번 읽는다. B가 읽는 두 값은?

    -- 세션 B
START TRANSACTION;
-- 세션 A (자동 커밋)
UPDATE account SET balance = 50 WHERE id = 1;
-- 세션 B
SELECT balance FROM account WHERE id = 1;
SELECT balance FROM account WHERE id = 1;
COMMIT;
    정답과 해설

    50과 50이다. 이 PC의 MySQL 8.4에서 그렇게 나왔다. START TRANSACTION만으로는 스냅숏을 찍지 않는다. B가 처음 읽을 때 스냅숏을 찍으므로 그 전에 커밋된 50이 보이고, 그 뒤로는 그 스냅숏을 읽는다. 시작하는 순간의 데이터를 읽어야 하면 START TRANSACTION WITH CONSISTENT SNAPSHOT으로 시작한다. 그렇게 하니 100, 100이었다. B가 READ COMMITTED라면 문장마다 그 순간 커밋된 값을 읽는다(위젯의 Non-Repeatable Read).

    문제 2. B는 기본값인 REPEATABLE READ다. 이번에는 B가 처음부터 FOR UPDATE로 잔액 100 이상인 계좌를 센다. 그다음 A가 500원 계좌를 넣으려 하고, B가 다시 FOR UPDATE로 센 뒤 커밋한다. A의 INSERT는 바로 끝날까? B가 센 두 개수는?

    -- 세션 B
START TRANSACTION;
SELECT COUNT(*) FROM account WHERE balance >= 100 FOR UPDATE;
-- 세션 A (자동 커밋)
INSERT INTO account VALUES (4, '최네오', 500);
-- 세션 B
SELECT COUNT(*) FROM account WHERE balance >= 100 FOR UPDATE;
COMMIT;
    정답과 해설

    A의 INSERT는 B가 COMMIT할 때까지 기다리고, B는 두 번 다 3을 센다. 이 PC의 MySQL 8.4에서 그렇게 나왔다. 잠그며 읽을 때 InnoDB는 읽은 행뿐 아니라 행 사이의 틈까지 잠근다(넥스트키 락). 그래서 그 틈에 새 행을 넣는 INSERT가 기다리고, 잠그며 세는 쪽에는 Phantom Read가 생기지 않는다. balance에 인덱스가 없어 표 전체를 훑었으므로, 조건 밖인 50원 계좌를 넣어도 기다렸다. 새 행이 보이는 것은 3절처럼 평범한 SELECT로 센 뒤 FOR UPDATE로 다시 셀 때, 두 읽기 방법을 섞을 때다.

    문제 3. B(REPEATABLE READ)가 잔액 100을 읽은 뒤, A가 50으로 고쳐 커밋했다. B는 다시 읽어 100을 보고, UPDATE account SET balance = balance + 10 WHERE id = 1을 한 뒤 또 읽는다. 마지막에 B가 읽는 값은 110일까?

    정답과 해설

    60이다. 이 PC에서 B는 100, 100을 읽은 뒤 UPDATE를 했고, 그다음 읽은 값은 60이었다. UPDATE는 스냅숏이 아니라 최신 커밋 값(50)에 10을 더한다. 그리고 자기가 고친 행은 스냅숏 대신 자기 값을 보여 준다. 만약 B의 프로그램이 읽은 100에 10을 더해 SET balance = 110으로 썼다면, A가 줄인 50은 사라졌을 것이다(53번(트랜잭션과 락)의 갱신 손실). 이것은 MySQL의 동작이다. PostgreSQL 문서는 같은 차례에서 REPEATABLE READ인 B의 UPDATE를 오류(could not serialize access due to concurrent update)로 되돌린다고 적는다.

    직접 해보기¶

    실습: 두 세션으로 이상 현상 일으키기

    1. MySQL 접속 창을 둘 연다(실습 환경의 6절). 한 창에서 아래 SQL로 표를 만들고, 두 창 모두 USE lab54;를 실행한다. 한 창이 A, 다른 창이 B다.
    2. B에서 SET SESSION TRANSACTION ISOLATION LEVEL READ UNCOMMITTED;를 실행하고, 위젯의 Dirty Read 차례대로 두 창에 번갈아 입력한다. B가 0을 읽는지 본다.
    3. 표를 처음 값으로 되돌리고(UPDATE account SET balance = 100 WHERE id = 1; DELETE FROM account WHERE id = 4;), B의 수준을 SERIALIZABLE로 바꿔 Phantom Read 차례를 해 본다. A의 INSERT가 멈추는지, B가 커밋한 순간 풀리는지 본다.
    4. B의 수준을 SELECT @@transaction_isolation;으로 확인한다. 다른 수준으로 바꾼 창에서 exit로 접속을 끊고 다시 접속하면 어떻게 되는지도 본다.
    CREATE DATABASE lab54;
USE lab54;
CREATE TABLE account (id INT PRIMARY KEY, owner VARCHAR(10) NOT NULL, balance INT NOT NULL);
INSERT INTO account VALUES (1, '김하나', 100), (2, '이두리', 200), (3, '박세나', 300);
    확인할 점
    • 2에서 B는 0을 읽는다. A가 ROLLBACK하면 표에는 다시 100이 있다. B가 읽은 0은 한 번도 확정된 적이 없는 값이다.
    • 3에서 A의 INSERT는 B가 COMMIT할 때까지 멈춘다. SERIALIZABLE에서 B의 SELECT가 읽은 행과 그 사이의 틈에 잠금을 걸었기 때문이다. balance에 인덱스가 없어 표 전체를 훑었으므로, 조건 밖인 50원 계좌를 넣어도 기다린다. 이 PC에서 잔액이 10원에서 10,000원인 1,000행 표에 balance 인덱스를 두고 balance >= 9000을 인덱스로 세게 하니, 조건에서 먼 5원과 8,000원의 INSERT는 기다리지 않았다. 조건 안의 9,500원과, 조건에 맞는 첫 행(9,000원) 바로 앞 틈에 들어가는 8,995원은 기다렸다(55번(인덱스와 실행 계획)). 오래 두면 53번(트랜잭션과 락)의 실습처럼 50초 뒤 ERROR 1205가 난다.
    • 4에서 SET SESSION으로 바꾼 수준은 그 접속에만, 그 접속이 끝날 때까지만 간다. 다시 접속하면 REPEATABLE-READ로 돌아온다.
    • 실습이 끝나면 두 창 모두 트랜잭션을 끝낸 뒤 DROP DATABASE lab54;로 지운다. 열린 트랜잭션이 있으면 DROP이 기다린다.

    AI 활용 과제: 격리 수준에 대한 설명 검증하기

    1. AI에게 "MySQL의 기본 격리 수준에서 Phantom Read가 일어나나? 예를 SQL로 보여 줘"라고 묻는다.
    2. 실행하기 전에 3절과 문제 2의 결과에 견주어 답이 맞는지 적는다.
    3. AI가 준 SQL을 두 창에서 실제로 실행해, 평범한 SELECT와 FOR UPDATE의 결과를 따로 확인하고 AI에게 보여 준다.
    확인할 점
    • "REPEATABLE READ는 Phantom Read를 막지 못한다"는 SQL 표준의 설명이다. 이 PC의 MySQL에서 평범한 SELECT끼리는 스냅숏으로, 잠그며 읽는 문장끼리는 넥스트키 락으로 막았다. 평범한 SELECT로 센 뒤 FOR UPDATE나 UPDATE로 다시 읽을 때만 새 행이 보였다. 어느 쪽 이야기인지 가려 달라고 한다.
    • "격리 수준을 높이면 다 해결된다"는 답이면 비용을 묻는다. SERIALIZABLE에서는 읽기만 해도 상대를 기다리게 했다(위젯). 기다림이 길어지면 시간 초과나 교착 상태(53번(트랜잭션과 락)의 문제 3)가 는다.
    • 같은 이름의 격리 수준도 DBMS마다 동작이 다르다. 설명이 어느 DBMS의 이야기인지 묻고, 쓰는 DBMS에서 직접 확인한다.

    더 알아보기¶

    MVCC: 행마다 옛 판을 남겨 둔다

    InnoDB는 행을 고칠 때 옛 값을 지우지 않고 되돌리기 기록(undo log)에 남긴다. 스냅숏으로 읽는 트랜잭션은 "스냅숏을 찍은 뒤에 커밋된 것은 안 보인다"는 규칙으로, 필요하면 옛 판을 찾아 읽는다. 스냅숏은 REPEATABLE READ면 트랜잭션에서 처음 읽을 때, READ COMMITTED면 문장마다 찍는다. 그래서 읽는 쪽이 고치는 쪽을 기다리지 않고, 고치는 쪽도 읽는 쪽을 기다리지 않는다(53번(트랜잭션과 락) 문제 2에서 평범한 SELECT가 기다리지 않은 까닭). 이처럼 판을 여럿 두고 읽는 방식을 MVCC(다중 버전 동시성 제어)라 한다. 오래 열어 둔 트랜잭션이 있으면 그 스냅숏 때문에 옛 판을 지우지 못해 저장 공간이 늘어난다.

    이 항목의 실험 방법

    위젯과 3절 그림, 문제의 결과는 이 PC(Core i9-14900KF, DDR5 64GB, NVMe SSD, Windows 11)의 Docker Desktop(WSL 2)에서 띄운 MySQL 8.4.11에, 같은 PC의 Python 3.14와 PyMySQL로 연결 둘(A, B)을 열어 위젯과 같은 차례로 실행해 얻었다. 문장마다 0.5초 안에 끝나지 않으면 잠금을 기다리는 것으로 보고, 상대가 커밋하거나 되돌린 뒤에 끝난 결과를 적었다. 격리 수준은 B에만 정했고 A는 기본값이다. 조합마다 표를 처음 상태(100, 200, 300원)로 새로 만들었다.

    정리¶

    • Dirty Read는 커밋 안 된 값을, Non-Repeatable Read는 그사이 바뀐 값을, Phantom Read는 그사이 생긴 행을 보는 일이다.
    • 격리 수준은 READ UNCOMMITTED, READ COMMITTED, REPEATABLE READ, SERIALIZABLE 차례로 더 많이 막는 대신 더 많이 기다린다. MySQL의 기본값은 REPEATABLE READ다.
    • MySQL의 REPEATABLE READ에서 평범한 SELECT는 처음 읽을 때 찍은 스냅숏을, FOR UPDATE와 UPDATE는 최신 값을 읽고 행 사이의 틈까지 잠근다. 읽은 값으로 계산해 쓸 때는 잠그며 읽거나 한 문장으로 고친다.
