    58. 데이터 영속성과 복구: 백업 전략(전체/증분)과 WAL 기반 복구¶

    원리 동작을 예측하고 이상을 알아챌 수 있어야 하는 항목

    커밋했다는 응답을 받은 데이터는 서버가 갑자기 꺼져도 남아 있어야 하고(53번(트랜잭션과 락)의 지속성), 디스크가 통째로 망가져도 되살릴 수 있어야 한다. 앞의 일은 DBMS가 로그를 먼저 쓰는 방식(WAL)으로 하고, 뒤의 일은 사람이 백업 계획으로 한다. 이 항목은 이 PC의 SQLite에서 프로세스를 강제로 끝내 보며 WAL이 무엇을 지키는지 확인하고, 커밋을 디스크에 확실히 쓰는 비용을 재고, 백업 방식마다 되살리는 길을 견준다.

    이 항목에서 배우는 것¶

    • 전체, 증분, 차등 백업의 차이와 되살릴 때 필요한 것을 설명할 수 있다.
    • WAL(Write-Ahead Log)이 갑작스러운 종료 뒤에 커밋한 데이터를 되살리는 방법을 설명할 수 있다.
    • 커밋을 디스크에 확실히 쓰는 비용과, 그 설정을 낮출 때 잃을 수 있는 것을 말할 수 있다.

    1. 백업은 전체와 그 뒤의 변경으로 나눠 둔다¶

    직접 해 보기장애가 난 날, 무엇으로 되살릴까증분 백업과 차등 백업, 로그 보관을 골라 장애가 난 요일을 바꿔 보며, 되살리는 데 필요한 백업 파일과 읽을 양, 잃는 데이터를 견준다
    새 창에서 크게 열기
    • 전체 백업은 DB 전부를 복사한다. 되살리기는 가장 쉽지만 크고 오래 걸려서 자주 하기 어렵다.
    • 증분 백업은 바로 전 백업 뒤에 바뀐 것만, 차등 백업은 마지막 전체 백업 뒤에 바뀐 것을 모두 담는다. 증분은 작지만 되살릴 때 전체 위에 그 뒤의 증분을 빠짐없이 차례로 적용해야 하고, 차등은 날이 갈수록 커지지만 전체와 마지막 차등 하나면 된다(위젯).
    • 어느 쪽이든 마지막 백업 뒤에 바뀐 것은 백업에 없다. 얼마나 잃어도 되는지(RPO)와 얼마나 빨리 되살려야 하는지(RTO)를 먼저 정하고, 마지막 백업과 장애 사이는 로그로 메운다(3절).

    2. WAL은 데이터를 고치기 전에 로그부터 쓴다¶

    • WAL은 바뀐 내용을 로그 파일 끝에 먼저 이어 쓰고, 그것이 디스크에 닿으면 커밋을 끝낸다. SQLite는 바뀐 페이지를 통째로 하나씩(프레임) 붙인다. 데이터 파일의 제자리는 나중에(체크포인트) 한꺼번에 고친다.
    • 갑자기 꺼진 뒤 다시 열면, 로그를 읽어 커밋까지 된 것은 살리고 커밋 안 된 것은 버린다. 이 PC에서 커밋한 행이 아직 로그에만 있을 때 프로세스를 강제로 끝냈는데, 다시 열자 그 행이 있었다(문제 1).
    • SQLite는 PRAGMA journal_mode = WAL로 켠다. 그러면 파일이름-wal 파일이 로그다. MySQL(InnoDB)의 redo log, PostgreSQL의 WAL도 같은 생각이다.

    3. 커밋을 디스크에 확실히 쓰는 데 비용이 든다¶

    • 운영체제는 쓰기를 메모리에 모아 두었다가 디스크에 쓴다. 커밋한 것이 남으려면 디스크에 닿을 때까지 기다려야 한다. 이 PC에서 그 기다림까지 포함한 커밋 하나가 WAL 모드에서 0.23~0.25ms, SQLite의 기본값인 롤백 저널(DELETE 모드)에서 1.3~1.5ms였다. 롤백 저널은 고치기 전 내용을 따로 적어 두고 본 파일을 제자리에서 고친다.
    • 기다림을 줄이는 설정(synchronous = NORMAL)은 커밋을 13~17µs로 줄였지만, 전원이 꺼지면 마지막 체크포인트 뒤에 커밋한 것이 되돌려질 수 있다. 빠르기와 지속성을 맞바꾸는 설정이다(문제 3).
    • 디스크가 망가지는 일은 WAL로 막지 못한다. 백업을 다른 곳에 두고, 로그도 따로 보관하면 마지막 백업 뒤의 변경까지 다시 적용해 장애 직전이나 원하는 시점으로 되살린다(위젯의 "로그를 따로 보관한다").

    예측해 보기¶

    문제 1. WAL 모드의 DB에서 한 행은 커밋하고, 다음 트랜잭션은 커밋 전에 프로세스를 정리 없이 끝낸다. 다시 열면 무엇이 출력될까? WAL 파일은 머리 32바이트 뒤에, 프레임(머리 24바이트 + 페이지 4,096바이트)을 하나씩 이어 쓴다.

    import os
import sqlite3
import subprocess
import sys
import tempfile

work = tempfile.mkdtemp()
path = os.path.join(work, "bank.db")
con = sqlite3.connect(path, isolation_level=None)  # 자동 커밋: 문장마다 바로 커밋한다
con.execute("PRAGMA journal_mode = WAL")
con.execute("CREATE TABLE account (id INTEGER PRIMARY KEY, owner TEXT, balance INTEGER)")
con.execute("INSERT INTO account VALUES (1, '김하나', 300000)")
con.execute("PRAGMA wal_checkpoint(TRUNCATE)")            # 여기까지는 본 파일에 옮겨 둔다
con.close()

child = os.path.join(work, "crash.py")                  # 쓰다가 갑자기 끝나는 프로그램
with open(child, "w", encoding="utf-8") as f:
    f.write(f"""import os, sqlite3
con = sqlite3.connect({path!r}, isolation_level=None)
con.execute("INSERT INTO account VALUES (2, '이두리', 50000)")  # 자동 커밋으로 확정
con.execute("BEGIN")
con.execute("UPDATE account SET balance = balance - 100000 WHERE id = 1")  # 아직 커밋 전
os._exit(1)  # 정리 없이 끝낸다
""")
subprocess.run([sys.executable, child])

con = sqlite3.connect(path)
print(con.execute("SELECT * FROM account ORDER BY id").fetchall())
print(os.path.getsize(path + "-wal"))
    정답과 해설 
    [(1, '김하나', 300000), (2, '이두리', 50000)]
4152

    커밋한 이두리의 행은 남고, 커밋 전이던 10만 원 출금은 사라졌다. 4,152는 WAL의 머리 32바이트에 프레임 하나(24 + 4,096바이트)를 더한 크기다. 커밋 하나가 페이지 하나를 바꿨다는 뜻이다. 이두리의 행은 본 파일이 아니라 WAL에만 있었다. 다시 열 때 SQLite는 WAL에서 커밋 표시가 있는 프레임까지를 찾아 두고, 그 페이지는 WAL에서 읽는다. 본 파일로 옮기는 것은 다음 체크포인트 때라서, 다시 연 뒤에도 WAL은 4,152바이트 그대로였다. 커밋 전의 UPDATE는 WAL에 닿지도 않았다. 이 PC에서 UPDATE 직후의 WAL도 4,152바이트였다.

    문제 2. 위젯에서 목요일 오후 3시에 DB가 든 디스크가 망가졌다. 로그는 보관하지 않았다. 월~토에 증분으로 백업했다면 되살릴 때 백업 파일이 몇 개 필요할까? 차등이라면? 잃는 데이터는?

    정답과 해설

    증분이면 4개, 차등이면 2개다. 어느 쪽이든 16시간치를 잃는다. 증분은 일요일 전체와 월, 화, 수요일 밤의 증분 셋을 차례로 적용한다. 하나라도 깨지면 그 뒤를 쓸 수 없다. 차등은 일요일 전체와 수요일 밤의 차등이면 된다. 이 모형에서 읽는 양은 둘 다 112GB로 같고, 한 주에 드는 공간은 증분 124GB, 차등 184GB다. 수요일 밤 11시부터 목요일 오후 3시까지의 변경은 어느 백업에도 없다.

    문제 3. 커밋을 빠르게 하려고 WAL 모드에서 PRAGMA synchronous = NORMAL;로 바꿨다. 주문을 받고 "결제 완료"라고 응답한 직후 서버의 전원이 나갔다. 다시 켜면 그 주문은 있을까?

    정답과 해설

    없을 수도 있다. SQLite 문서에 따르면 WAL 모드의 NORMAL은 DB를 깨뜨리지는 않지만, 전원이 꺼지거나 운영체제가 멈추면 커밋한 트랜잭션이 되돌려질 수 있다. 커밋마다 WAL을 디스크에 밀어 넣지 않고 체크포인트 때만 하므로, 마지막 체크포인트 뒤의 커밋이 그 대상이다. 이 PC에서 커밋은 0.23~0.25ms에서 13~17µs로 빨라졌지만, 사용자에게 "완료"라고 말한 것이 사라질 수 있다. 프로그램만 죽는 경우(문제 1)에는 NORMAL이라도 남는다. 무엇을 잃어도 되는지 정한 뒤에 고른다.

    직접 해보기¶

    실습: 돌고 있는 DB를 제대로 백업하기

    1. 문제 1에 이어서 실행한다(work, os, sqlite3를 그대로 쓴다). 아래 코드는 WAL 모드의 DB에 주문 100건을 하나씩 커밋한 뒤, 같은 DB를 두 가지로 백업한다. 하나는 .db 파일만 복사하고, 하나는 SQLite의 온라인 백업(backup)을 쓴다. 실행하기 전에 두 백업에 주문이 몇 건씩 있을지 적는다.
    2. 실행해 결과를 확인하고, 까닭을 WAL로 설명한다.
    3. 백업 파일을 열어 PRAGMA integrity_check;가 ok인지 본다. 백업은 되살려 봐야 쓸모를 안다.
    import shutil

src = os.path.join(work, "shop.db")
con = sqlite3.connect(src, isolation_level=None)
con.execute("PRAGMA journal_mode = WAL")
con.execute("CREATE TABLE orders (id INTEGER PRIMARY KEY, item TEXT)")
con.execute("PRAGMA wal_checkpoint(TRUNCATE)")
con.executemany("INSERT INTO orders (item) VALUES (?)", [(f"주문 {i}",) for i in range(100)])
print(os.path.getsize(src + "-wal"))
shutil.copyfile(src, os.path.join(work, "copy.db"))            # .db 파일만 복사
dst = sqlite3.connect(os.path.join(work, "backup.db"))
con.backup(dst)                                                # 온라인 백업
dst.close()
for name in ["copy.db", "backup.db"]:
    c = sqlite3.connect(os.path.join(work, name))
    print(name, c.execute("SELECT COUNT(*) FROM orders").fetchone()[0], c.execute("PRAGMA integrity_check").fetchone()[0])
    c.close()
    확인할 점 
    412032
copy.db 0 ok
backup.db 100 ok
    • 100건은 모두 커밋했지만 아직 WAL에만 있었다(412,032바이트 = 머리 32 + 프레임 100개 × 4,120). .db 파일만 복사한 백업에는 한 건도 없다. 파일은 멀쩡해서 integrity_check도 ok라, 되살려 세어 보지 않으면 모른다.
    • 온라인 백업은 DB를 통해 읽으므로 WAL에 있는 것까지 담는다. 쓰는 중에도 할 수 있다. SQLite에는 VACUUM INTO '파일이름'도 있다. 파일을 복사하려면 모든 연결을 닫은 뒤에 하고, -wal 파일이 남아 있으면 함께 복사한다. 체크포인트를 해도 복사하는 사이에 쓰기가 들어오면 깨진 사본이 생긴다.
    • 같은 일이 MySQL이나 PostgreSQL에서도 생긴다. 데이터 파일만 복사하지 말고, 그 DB의 백업 도구를 쓴다.

    AI와 함께 확인하기¶

    AI 활용 과제: 백업 스크립트 검토하기

    1. AI에게 "운영 중인 SQLite DB를 매일 밤 백업하는 Python 스크립트를 짜 줘. 일주일치를 보관한다"라고 한다.
    2. 받은 스크립트가 어떻게 복사하는지, 백업이 제대로 되었는지 어떻게 확인하는지, 어디에 두는지 적는다.
    3. 실습처럼 WAL에만 있는 데이터를 만들어 두고 그 스크립트로 백업해 본다. 되살린 DB의 행 수를 원본과 견준다.
    확인할 점
    • shutil.copy로 .db 파일만 복사하는 답이 흔하다. WAL 모드라면 커밋한 데이터가 빠진다(실습). Connection.backup()이나 VACUUM INTO를 쓰는지 본다.
    • 백업을 만들기만 하고 되살려 보지 않는 스크립트가 많다. 백업 파일을 열어 행 수와 integrity_check를 확인하는 단계를 넣게 한다.
    • 백업을 같은 디스크에 두면 디스크가 망가질 때 함께 잃는다. 다른 장치나 다른 곳에 한 벌을 둔다.
    • 마지막 백업 뒤의 변경을 어떻게 할지(얼마나 잃어도 되는지) 묻는다. 하루치를 잃으면 안 된다면 로그를 따로 보관하거나 백업을 더 자주 한다(위젯). SQLite에는 WAL을 따로 쌓아 두는 기능이 없어서, 백업을 더 자주 하거나 그 기능이 있는 서버 DB를 쓴다(더 알아보기).

    더 알아보기¶

    원하는 시점으로 되살리기 (PITR)

    서버 DB는 전체 백업과 함께 그 뒤의 로그를 계속 다른 곳에 보관한다. MySQL은 바이너리 로그, PostgreSQL은 WAL 파일을 쌓는다. 되살릴 때는 전체 백업을 놓고 로그를 차례로 다시 적용하는데, 원하는 시각에서 멈출 수 있다. 누가 실수로 DELETE를 한 직전으로 되돌리는 일도 이렇게 한다. 이것을 PITR(point-in-time recovery)이라 한다. 위젯의 "로그를 따로 보관한다"가 이 방식이다.

    이 항목의 측정 프로그램

    3절의 시간과 그림은 이 PC(Core i9-14900KF, DDR5 64GB, NVMe SSD, Windows 11)에서 아래 프로그램을 5번 실행한 범위다. TEMP 폴더에 DB를 만들고, 행 하나를 넣고 커밋하는 트랜잭션 2,000개의 평균을 잰다. 저널 모드와 synchronous만 바꾼다.

    # 58번 측정: 작은 트랜잭션 2,000개(행 하나 넣고 커밋)를 저널 모드와 synchronous 설정을 바꿔 가며 넣는다
import os
import shutil
import sqlite3
import tempfile
import time

N = 2000
work = tempfile.mkdtemp(dir=os.environ.get("TEMP"))
for journal, sync in [("DELETE", "FULL"), ("WAL", "FULL"), ("WAL", "NORMAL"), ("WAL", "OFF")]:
    path = os.path.join(work, f"{journal}-{sync}.db")
    con = sqlite3.connect(path, isolation_level=None)
    con.execute(f"PRAGMA journal_mode = {journal}")
    con.execute(f"PRAGMA synchronous = {sync}")
    con.execute("CREATE TABLE log (id INTEGER PRIMARY KEY, msg TEXT)")
    t = time.perf_counter()
    for i in range(N):
        con.execute("INSERT INTO log (msg) VALUES (?)", (f"주문 {i}",))      # 자동 커밋: 문장마다 트랜잭션 하나
    us = (time.perf_counter() - t) / N * 1e6
    con.close()
    print(f"{journal:6} {sync:6}: {us:7.1f} us per commit")
shutil.rmtree(work)

    정리¶

    • 전체 백업에 증분이나 차등을 더해 둔다. 증분은 작지만 되살릴 때 모두 필요하고, 차등은 크지만 마지막 하나면 된다. 마지막 백업 뒤의 변경은 로그로 메운다.
    • WAL은 바뀐 내용을 로그에 먼저 쓰고 커밋한다. 갑자기 꺼져도 다시 열 때 커밋한 것은 살리고 커밋 안 된 것은 버린다.
    • 커밋을 디스크에 확실히 쓰려면 기다려야 한다. 그 설정을 낮추면 빨라지지만 잃을 수 있는 것이 생긴다. 돌고 있는 DB는 파일 복사가 아니라 백업 도구로 백업하고, 되살려 확인한다.
