    55. 인덱스: B-Tree 동작 원리, 복합 인덱스 설계, 실행 계획(EXPLAIN) 읽기¶

    직접 AI 없이 직접 할 수 있어야 하는 항목

    학생 100만 명 가운데 한 명을 이름으로 찾을 때, DBMS는 100만 행을 다 읽을 수도 있고 몇 페이지만 읽을 수도 있다. 그 차이를 만드는 것이 인덱스다. 이 항목은 인덱스가 B-Tree로 어떻게 생겼는지 보고, 복합 인덱스를 어떤 차례로 만들지 정하고, DBMS가 실제로 인덱스를 쓰는지 실행 계획으로 확인하고 시간을 잰다. 직접형 항목이므로 인덱스를 직접 만들고 실행 계획으로 검증한다.

    이 항목에서 배우는 것¶

    • B-Tree 인덱스가 몇 번의 페이지 읽기로 키를 찾는 까닭을 설명할 수 있다.
    • 질의에 맞춰 복합 인덱스의 열 차례를 정하고, 인덱스를 쓰지 못하는 조건을 알아볼 수 있다.
    • EXPLAIN QUERY PLAN의 SCAN, SEARCH, COVERING INDEX, TEMP B-TREE를 읽고, 인덱스의 읽기 이득과 쓰기 비용을 잴 수 있다.

    이 항목의 SQL은 아래 표로 한다. python -m sqlite3 school55.db에 붙여 넣으면 학생 10만 명이 만들어진다. 이름은 겹치지 않는다.

    CREATE TABLE student (id INTEGER PRIMARY KEY, name TEXT NOT NULL, dept INTEGER NOT NULL, year INTEGER NOT NULL, score INTEGER NOT NULL);
WITH RECURSIVE n(i) AS (SELECT 1 UNION ALL SELECT i + 1 FROM n WHERE i < 100000)
INSERT INTO student SELECT i, printf('학생%07d', (i * 7919) % 1000003), i % 50 + 1, i % 4 + 1, (i * 37) % 101 FROM n;
SELECT COUNT(*), COUNT(DISTINCT name) FROM student;

    (100000, 100000)

    1. 인덱스는 정렬해 둔 B-Tree라서 몇 층만 내려가면 찾는다¶

    직접 해 보기B-Tree에 키를 넣고 찾기키를 하나씩 넣으며 노드가 넘쳐 나뉘고 층이 늘어나는 것을 보고, 키를 골라 찾을 때 읽는 노드와 키 수를 처음부터 훑을 때와 견준다
    새 창에서 크게 열기
    • 인덱스는 열의 값을 정렬해 두고 그 행의 자리를 함께 적은 목록이다. 정렬된 목록은 B-Tree라는 나무로 둔다. 노드 하나가 디스크의 페이지 하나이고, 노드마다 키가 여럿 들어간다. 위젯은 DBMS가 흔히 쓰는 변형인 B+Tree라서, 모든 키를 잎에 두고 위 노드에는 길잡이로 복사해 둔다.
    • 찾을 때는 뿌리에서 시작해 "이 키보다 작은가"를 견주며 자식 하나만 골라 내려간다. 층 수만큼만 페이지를 읽는다. 키가 넘치면 노드가 나뉘고, 뿌리까지 넘치면 위로 한 층 자란다(위젯).
    • 이 PC에서 학생 100만 명의 이름 인덱스는 3층이었다. 페이지(4KB) 하나에 이름 키가 150~190개 들어가서, 3층이면 수백만 개까지 담는다. 인덱스로 찾는 데 0.05ms, 없이 다 읽는 데 37ms였다(3절 그림).

    2. 복합 인덱스는 앞 열부터 쓴다¶

    • 여러 열로 만든 복합 인덱스 (dept, year)는 dept로 먼저, 같은 dept 안에서 year로 정렬한다. 그래서 dept만, 또는 dept와 year를 함께 주면 붙어 있는 덩어리를 바로 찾는다. year만 주면 흩어져 있어 다 훑는다.
    • 열의 차례는 질의를 보고 정한다. 같다(=)로 거르는 열을 앞에, 범위(>, BETWEEN)나 정렬에 쓰는 열을 뒤에 둔다(문제 1).
    • 열에 함수를 씌우거나(substr(name, 3)) 앞을 모르는 LIKE '%7777'로 찾으면 정렬된 차례를 쓸 수 없어 인덱스가 있어도 다 훑는다(문제 2). SQLite의 LIKE는 대소문자를 가리지 않아서, 앞이 정해진 LIKE '학생0777%'도 이름 인덱스를 쓰지 못하고 다 훑었다. 앞부분으로 찾을 때는 name >= '학생0777' AND name < '학생0778'처럼 범위로 쓴다.

    3. 실행 계획으로 확인하고, 읽기 이득과 쓰기 비용을 잰다¶

    • 질의 앞에 EXPLAIN QUERY PLAN을 붙이면 DBMS가 고른 방법이 나온다. SCAN은 표나 인덱스를 처음부터 다 읽는 것, SEARCH … USING INDEX는 인덱스로 찾아 들어가는 것이다. COVERING INDEX는 인덱스만 읽고 표는 읽지 않는다는 뜻이고, USE TEMP B-TREE FOR ORDER BY는 정렬을 따로 했다는 뜻이다.
    • 질의에 필요한 열이 모두 인덱스에 있으면(커버링 인덱스) 표를 다시 읽지 않아 더 빠르다. 이 PC에서 (dept, year) 인덱스로 dept = 7 AND year = 2를 찾을 때 name까지 가져오면 9.5~10.4ms, 인덱스에 든 열만 가져오면 1.4~1.9ms였다.
    • 인덱스마다 쓰기가 늘어난다. 행을 넣을 때마다 그 표의 B-Tree를 모두 고치기 때문이다. 10만 행을 넣는 시간이 보조 인덱스(기본 키 말고 따로 만든 인덱스) 0개 67~72ms, 3개 571~685ms였다. 느린 질의를 실행 계획으로 확인하고, 필요한 인덱스만 만든다.

    예측해 보기¶

    문제 1. (dept, year)로 복합 인덱스를 만들었다. 그림의 세 조건과 조금 다른 세 질의다. 실행 계획은 각각 어떻게 나올까? 둘째는 인덱스의 두 열을 다 쓸까?

    CREATE INDEX student_dept_year ON student(dept, year);
EXPLAIN QUERY PLAN SELECT name FROM student WHERE year = 3 AND dept = 7;
EXPLAIN QUERY PLAN SELECT name FROM student WHERE dept BETWEEN 7 AND 8 AND year = 3;
EXPLAIN QUERY PLAN SELECT name FROM student WHERE dept = 7 ORDER BY year;
    정답과 해설 
    (3, 0, 61, 'SEARCH student USING INDEX student_dept_year (dept=? AND year=?)')
(3, 0, 164, 'SEARCH student USING INDEX student_dept_year (dept>? AND dept<?)')
(4, 0, 62, 'SEARCH student USING INDEX student_dept_year (dept=?)')

    python -m sqlite3는 실행 계획을 행마다 괄호 하나로 찍는다. 첫 칸은 단계 번호, 둘째 칸은 위 단계의 번호다. 셋째 칸은 SQLite 문서가 "지금은 쓰지 않는 칸"이라고 적은 내부 값이라 버전마다 다를 수 있다. 넷째 칸의 설명을 읽는다.

    첫째는 WHERE에 쓴 차례와 상관없이 두 열을 다 쓴다. 차례는 인덱스를 만들 때 정해진다. 둘째는 앞 열 dept가 범위라서 dept>? AND dept<?로만 찾는다(SQLite는 경계를 포함하는 범위도 >, <로 적는다). dept가 7인 덩어리와 8인 덩어리 안에서 year는 따로따로 정렬되어 있어, year = 3은 찾아 들어가는 데 쓰지 못하고 찾은 항목을 하나씩 견준다. 그래서 범위에 쓰는 열을 뒤에 둔다. 셋째는 dept = 7 덩어리 안이 이미 year 차례라 따로 정렬하지 않는다(TEMP B-TREE가 없다). year만 주면 다 훑는 것은 그림과 같다. year로 찾는 일이 잦다면 (year)나 (year, dept) 인덱스를 따로 둔다.

    문제 2. 이름의 앞 두 글자를 뺀 부분으로 찾는다. 이름 인덱스가 있어도 실행 계획은 어떻게 나올까? 이 질의도 빠르게 하려면 어떻게 할까?

    CREATE INDEX student_name ON student(name);
EXPLAIN QUERY PLAN SELECT * FROM student WHERE name = '학생0777777';
EXPLAIN QUERY PLAN SELECT * FROM student WHERE substr(name, 3) = '0777777';
CREATE INDEX student_name_tail ON student(substr(name, 3));
EXPLAIN QUERY PLAN SELECT * FROM student WHERE substr(name, 3) = '0777777';
    정답과 해설 
    (3, 0, 62, 'SEARCH student USING INDEX student_name (name=?)')
(2, 0, 216, 'SCAN student')
(3, 0, 61, 'SEARCH student USING INDEX student_name_tail (<expr>=?)')

    이름 인덱스는 이름 전체의 차례로 정렬되어 있어서, substr(name, 3)의 값으로는 어디서 찾을지 알 수 없다. 그래서 둘째는 다 읽는다. SQLite는 식에도 인덱스를 만들 수 있어서, 같은 식으로 인덱스를 만들면 셋째처럼 찾아 들어간다. 이 PC의 100만 행에서 함수를 씌운 질의는 56~57ms였다.

    문제 3. 점수가 가장 높은 학생 10명을 찾는다. 점수 인덱스를 만들기 전과 뒤의 실행 계획은? 뒤의 계획에도 SCAN이 있는데 왜 빠를까?

    EXPLAIN QUERY PLAN SELECT name, score FROM student ORDER BY score DESC LIMIT 10;
CREATE INDEX student_score ON student(score);
EXPLAIN QUERY PLAN SELECT name, score FROM student ORDER BY score DESC LIMIT 10;
    정답과 해설 
    (4, 0, 216, 'SCAN student')
(16, 0, 0, 'USE TEMP B-TREE FOR ORDER BY')
(5, 0, 223, 'SCAN student USING INDEX student_score')

    앞은 표를 다 읽고 점수로 따로 정렬한다(TEMP B-TREE). 뒤는 점수 인덱스를 큰 쪽부터 차례로 읽는데, 이미 정렬되어 있으니 10개를 읽고 멈춘다. SCAN이라도 LIMIT 덕분에 끝까지 읽지 않는다. 이 PC의 100만 행에서 40~42ms가 0.05ms로 줄었다. 실행 계획의 단어 하나만 보지 말고, 무엇을 읽고 언제 멈추는지를 함께 본다.

    1. 위의 표를 만든 school55.db에서, 예측해 보기에서 만든 인덱스 가운데 이 질의들에 쓰일 두 개를 아래 SQL로 지운다. 그다음 아래 Python 코드로 세 질의의 시간을 잰다(python -m sqlite3에는 시간을 재는 기능이 없다).
    2. 세 질의마다 EXPLAIN QUERY PLAN을 붙여 실행 계획을 적는다.
    3. 세 질의를 모두 빠르게 하는 인덱스를 만든다. 만든 뒤 다시 실행 계획과 시간을 본다.
    4. 인덱스마다 쓰기 비용이 있으므로, 인덱스 하나로 세 질의를 다 도울 수 있는지 보고 둘로 할 때와 시간을 견준다.
    DROP INDEX IF EXISTS student_dept_year;
DROP INDEX IF EXISTS student_score;


    import sqlite3
import time

con = sqlite3.connect("school55.db")
for sql in ["SELECT COUNT(*) FROM student WHERE dept = 7 AND score >= 90",
            "SELECT name FROM student WHERE dept = 7 ORDER BY score DESC LIMIT 5",
            "SELECT COUNT(*) FROM student WHERE score >= 100"]:
    t = time.perf_counter()
    con.execute(sql).fetchall()
    print(f"{(time.perf_counter() - t) * 1000:.2f} ms", sql)

    확인할 점

    인덱스 (dept, score)로 앞의 둘이, (score)로 셋째가 빨라진다. 한 예와 실행 계획이다.

    CREATE INDEX student_dept_score ON student(dept, score);
CREATE INDEX student_score ON student(score);
EXPLAIN QUERY PLAN SELECT COUNT(*) FROM student WHERE dept = 7 AND score >= 90;
EXPLAIN QUERY PLAN SELECT name FROM student WHERE dept = 7 ORDER BY score DESC LIMIT 5;
EXPLAIN QUERY PLAN SELECT COUNT(*) FROM student WHERE score >= 100;

    (3, 0, 46, 'SEARCH student USING COVERING INDEX student_dept_score (dept=? AND score>?)')
(5, 0, 62, 'SEARCH student USING INDEX student_dept_score (dept=?)')
(3, 0, 189, 'SEARCH student USING COVERING INDEX student_score (score>?)')
    • (dept, score)는 같다로 거르는 dept를 앞에, 범위와 정렬에 쓰는 score를 뒤에 두었다. 둘째 질의는 dept = 7 덩어리 안이 이미 점수 차례라 따로 정렬하지 않는다(TEMP B-TREE가 없다).
    • 셋째의 score >= 100은 (score) 인덱스로 찾는다. 표시가 score>?인 것은 SQLite가 범위의 시작을 그렇게 적기 때문이다.
    • (score, dept) 하나로도 세 질의가 모두 인덱스를 쓴다. 다만 첫째는 점수 90 이상인 약 1만 항목을 다 훑으며 dept를 골라야 해서, 이 PC에서 0.19~0.21ms로 (dept, score)의 0.05ms보다 4배쯤 느렸다. 둘째는 점수가 높은 쪽부터 훑다가 dept = 7인 학생 다섯을 찾으면 멈춘다(0.07ms 안팎). 행이 늘면 차이도 커진다. 하나로 줄일지는 이 차이와 쓰기 비용을 견줘 정한다. 앞 열이 무엇이냐가 인덱스의 쓰임을 정한다.
    • 이 PC에서 10만 행의 세 질의가 인덱스 없이는 저마다 2.7~3.8ms, 두 인덱스를 만든 뒤에는 0.05ms 안팎이었다(5번 실행). 그런데 둘째 질의가 돌려준 다섯 명이 인덱스 전후로 달랐다. 점수가 같은 학생이 많아서, 동점끼리의 차례는 읽는 길에 따라 달라진다. 결과가 늘 같아야 하면 ORDER BY score DESC, id처럼 동점을 가를 열을 더한다.
    • 실행 계획은 데이터의 양과 통계에 따라 바뀔 수 있다. 실제 데이터에 가까운 양으로 확인하고, ANALYZE로 통계를 모으면 DBMS가 더 나은 계획을 고른다. 예를 들어 문제 1의 (dept, year) 인덱스가 있을 때 ANALYZE를 하면, year만 준 SELECT COUNT(*) … WHERE year = 2가 (ANY(dept) AND year=?)로 바뀌었다(실습 1에서 지웠다면 CREATE INDEX student_dept_year ON student(dept, year);로 다시 만든다). dept의 값마다 그 덩어리 안의 year = 2로 건너뛰며 찾는 것(skip-scan)이다. name을 가져오는 질의는 그대로 SCAN이었다.

    AI와 함께 확인하기¶

    AI 활용 과제: AI가 추천한 인덱스를 실행 계획으로 검증하기

    1. 위 표의 CREATE TABLE과 실습의 세 질의를 AI에게 주고 "이 질의들을 빠르게 하는 인덱스를 추천해 줘"라고 한다.
    2. 추천받은 인덱스를 만들기 전에, 각 질의가 그 인덱스를 쓸지 앞 열 규칙으로 예측한다.
    3. 인덱스를 만들고 EXPLAIN QUERY PLAN과 시간으로 확인한다. 쓰이지 않는 인덱스가 있으면 AI에게 실행 계획을 보여 주고 이유를 묻는다.
    확인할 점
    • 질의에 나오는 열마다 하나씩 인덱스(dept, score 따로)를 만드는 답이 흔하다. 대개 DBMS는 표 하나를 읽을 때 인덱스 하나를 고른다. 복합 인덱스 하나가 더 낫다(실습).
    • 복합 인덱스의 열 차례가 질의와 맞는지 본다. (score, dept)라면 WHERE dept = 7 …에서 앞 열을 쓰지 못한다.
    • 인덱스의 쓰기 비용(이 PC에서 보조 인덱스 3개면 넣는 시간이 8~10배)을 말하지 않는다면 묻는다. 거의 읽지 않는 표나, 값이 몇 가지뿐인 열(예: 성별)의 인덱스는 이득이 적다.
    • 실행 계획을 확인하지 않고 "이 인덱스면 빨라진다"고만 하면 믿지 않는다. 확인은 내가 한다.

    더 알아보기¶

    인덱스 파일을 열어 층 수를 세기

    SQLite 파일은 같은 크기의 페이지로 나뉘고, 인덱스의 B-Tree 노드가 페이지 하나씩이다. 페이지 맨 앞의 한 바이트가 종류(0x02는 가운데, 0x0a는 잎)이고, 가운데 페이지의 칸마다 앞 4바이트가 자식 페이지 번호다. 아래 프로그램은 뿌리 페이지에서 가장 왼쪽 자식을 따라 잎까지 내려가며 층 수와 페이지마다 든 키 수를 센다. 이 PC에서 학생 100만 명(측정 프로그램의 표)의 이름 인덱스는 (3, [33, 157, 186], 4096)이었다. 뿌리에 33칸, 그 아래 157칸, 잎에 186칸이고 페이지는 4096바이트다. 위의 school55.db(10만 명)에서는 (3, [3, 159, 188], 4096)이었다. SQLite의 인덱스는 위젯과 달리 위 노드에 둔 키를 잎에 다시 두지 않는다. 10만 행의 이름 인덱스에서 모든 페이지의 칸을 더하면 정확히 10만이다.

    import sqlite3
import struct


def depth(path, index):
    con = sqlite3.connect(path)
    root = con.execute("SELECT rootpage FROM sqlite_master WHERE name = ?", (index,)).fetchone()[0]
    con.close()
    with open(path, "rb") as f:
        data = f.read()
    size = struct.unpack(">H", data[16:18])[0]          # 파일 머리의 페이지 크기
    levels, page, cells = 0, root, []
    while True:
        base = (page - 1) * size
        h = base + (100 if page == 1 else 0)              # 첫 페이지는 파일 머리 100바이트 뒤
        kind, ncell = data[h], struct.unpack(">H", data[h + 3:h + 5])[0]
        levels += 1
        cells.append(ncell)
        if kind in (0x0a, 0x0d):                          # 잎 페이지에 닿았다
            return levels, cells, size
        first = struct.unpack(">H", data[h + 12:h + 14])[0]
        page = struct.unpack(">I", data[base + first:base + first + 4])[0]


print(depth("school55.db", "student_name"))

    이 항목의 측정 프로그램

    1절과 3절의 시간, 3절 그림은 이 PC(Core i9-14900KF, DDR5 64GB, NVMe SSD, Windows 11, SQLite 3.50.4)에서 아래 프로그램을 5번 실행한 범위다. TEMP 폴더의 SQLite 파일에 학생 100만 명을 넣고, 같은 질의를 여러 번 실행한 중앙값을 찍는다. 처음 한 번은 파일을 메모리에 올리는 시간이 섞이므로 중앙값을 쓴다.

    # 55번 측정: 학생 100만 행에서 인덱스가 하는 일
import os
import random
import shutil
import sqlite3
import statistics
import tempfile
import time

random.seed(55)
N = 1_000_000
work = tempfile.mkdtemp(dir=os.environ.get("TEMP"))
con = sqlite3.connect(os.path.join(work, "school.db"))
con.execute("CREATE TABLE student (id INTEGER PRIMARY KEY, name TEXT NOT NULL, dept INTEGER NOT NULL, year INTEGER NOT NULL, score INTEGER NOT NULL)")
order = list(range(N))
random.shuffle(order)
con.executemany("INSERT INTO student VALUES (?, ?, ?, ?, ?)",
                ((i + 1, f"학생{order[i]:07d}", random.randrange(1, 51), random.randrange(1, 5), random.randrange(0, 101)) for i in range(N)))
con.commit()


def show(tag, sql, n=7):
    ts = []
    for _ in range(n):
        t = time.perf_counter()
        con.execute(sql).fetchall()
        ts.append((time.perf_counter() - t) * 1000)
    plan = " / ".join(r[3] for r in con.execute("EXPLAIN QUERY PLAN " + sql))
    print(f"{tag}: {statistics.median(ts):.3f} ms | {plan}")


show("name, no index", "SELECT * FROM student WHERE name = '학생0777777'")
con.execute("CREATE INDEX student_name ON student(name)")
show("name, index", "SELECT * FROM student WHERE name = '학생0777777'", 51)
show("name, function", "SELECT * FROM student WHERE substr(name, 3) = '0777777'")
con.execute("CREATE INDEX student_dept_year ON student(dept, year)")
show("dept+year, name", "SELECT name FROM student WHERE dept = 7 AND year = 2")
show("dept+year, covering", "SELECT dept, year FROM student WHERE dept = 7 AND year = 2")
show("year only", "SELECT COUNT(*) FROM student WHERE year = 2")
show("top10, no index", "SELECT name, score FROM student ORDER BY score DESC LIMIT 10")
con.execute("CREATE INDEX student_score ON student(score)")
show("top10, index", "SELECT name, score FROM student ORDER BY score DESC LIMIT 10", 51)
con.commit()
for k in (0, 1, 3):                        # 쓰기: 보조 인덱스 0개, 1개, 3개인 표에 10만 행 넣기
    con.execute("DROP TABLE IF EXISTS s2")
    con.execute("CREATE TABLE s2 (id INTEGER PRIMARY KEY, name TEXT NOT NULL, dept INTEGER NOT NULL, year INTEGER NOT NULL, score INTEGER NOT NULL)")
    for j, col in enumerate(["name", "dept, year", "score"][:k]):
        con.execute(f"CREATE INDEX s2_{j} ON s2({col})")
    rows = [(i, f"새학생{random.randrange(10**9):09d}", random.randrange(1, 51), random.randrange(1, 5), random.randrange(0, 101)) for i in range(1, 100_001)]
    t = time.perf_counter()
    con.executemany("INSERT INTO s2 VALUES (?, ?, ?, ?, ?)", rows)
    con.commit()
    print(f"insert 100k, {k} index: {(time.perf_counter() - t) * 1000:.0f} ms")
con.close()
shutil.rmtree(work)

    정리¶

    • 인덱스는 값을 정렬해 둔 B-Tree다. 층 수만큼만 페이지를 읽어 찾는다. 100만 행의 이름 인덱스는 3층이었고, 찾는 시간이 37ms에서 0.05ms로 줄었다.
    • 복합 인덱스는 앞 열부터 쓴다. 같다로 거르는 열을 앞에, 범위와 정렬에 쓰는 열을 뒤에 둔다. 열에 함수를 씌우거나 앞을 모르는 LIKE는 인덱스를 쓰지 못한다(SQLite에서는 앞이 정해진 LIKE도 그랬다).
    • EXPLAIN QUERY PLAN으로 SCAN과 SEARCH, COVERING INDEX, TEMP B-TREE를 확인한다. 인덱스마다 쓰기가 느려지므로, 잰 뒤에 필요한 것만 만든다.
