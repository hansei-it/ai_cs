    51. 정규화(1NF~3NF, BCNF)와 실무적 반정규화¶

    직접 AI 없이 직접 할 수 있어야 하는 항목

    50번(데이터 모델링과 ERD)에서 개체마다 표를 만들었다. 그런데 표를 어떻게 나눠야 충분한지는 따로 따져 봐야 한다. 한 표에 너무 많이 적으면 같은 사실을 여러 번 적게 되고, 고칠 때마다 어긋난다. 이 항목은 그 문제를 이 PC의 SQLite에서 일으켜 보고, 함수 종속을 따라 표를 나누는 정규화와, 일부러 되돌리는 반정규화의 값을 잰다. 직접형 항목이므로 표 하나를 직접 정규화하고 검증한다.

    이 항목에서 배우는 것¶

    • 한 표에 다 적을 때 생기는 수정, 삽입, 삭제 이상을 예로 설명할 수 있다.
    • 함수 종속을 찾아 표를 1NF, 2NF, 3NF, BCNF로 나눌 수 있다.
    • 나눈 표가 원래 데이터를 잃지 않았는지 SQL로 확인하고, 반정규화의 값과 비용을 견줄 수 있다.

    1. 한 표에 다 적으면 같은 사실을 되풀이한다¶

    직접 해 보기표를 나누면 무엇이 달라질까수강 기록을 한 표, 2NF, 3NF로 바꿔 가며 사무실 옮기기, 새 강좌 열기, 수강 취소를 해 보고, 고친 행 수와 사라지는 정보를 본다
    새 창에서 크게 열기
    • 수강 기록을 한 표에 적으면, 김하나가 두 강좌를 들을 때 이름과 학과가 두 번 적히고 "컴퓨터공학의 사무실은 공학관 301"은 네 번 적힌다(위젯의 주황 칸).
    • 되풀이는 이상 현상을 부른다. 사무실 하나를 옮기는데 4행을 고쳐야 하고(수정 이상), 수강생이 없는 강좌는 열 수 없으며(삽입 이상), 수강 한 건을 지우면 학생과 학과의 정보까지 사라진다(삭제 이상).
    • 정규화는 같은 사실을 한 곳에만 적도록 표를 나누는 일이다. 위젯에서 3NF로 나누면 세 가지 일이 모두 행 하나로 끝난다.

    2. 함수 종속을 따라 표를 나눈다¶

    • 열 A의 값이 같으면 열 B의 값도 늘 같을 때 "A가 B를 정한다"고 하고 A → B로 쓴다(함수 종속). 학번이 같으면 이름도 같다. 이 규칙은 요구사항에서 찾는다. 데이터는 반례를 보여 줄 수 있을 뿐이다(문제 1).
    • 1NF는 칸 하나에 값 하나다(문제 2). 2NF는 키의 일부에만 딸린 열을, 3NF는 키에 들지 않은 열이 키가 아닌 다른 열에 딸린 것(이행 종속)을 떼어 낸다. BCNF는 다른 열을 정하는 열(결정자)이 모두 후보 키여야 한다(문제 3). 후보 키는 행 하나를 가려낼 수 있는 열 묶음 가운데 열을 하나라도 빼면 가려낼 수 없게 되는 것이고, 기본 키는 그중 고른 하나다.
    • 나눈 표를 조인하면 원래 표가 그대로 나와야 한다. 행이 빠지거나 늘면 나누는 방법이 틀린 것이다(직접 해보기).

    3. 반정규화는 읽기를 빠르게 하는 대신 맞춰 둘 일을 만든다¶

    • 정규화하면 읽을 때 조인과 계산이 늘어난다. 자주 읽는 값을 미리 계산해 표에 두는 것이 반정규화다. 이 PC에서 주문 표에 합계 열을 두고 그 열에 인덱스(55번(인덱스와 실행 계획))를 거니, 합계가 큰 주문 10건을 찾는 시간이 120~121ms에서 0.05ms로 줄었다. 인덱스 없이 합계 열만 두면 6.4~6.9ms였다.
    • 대신 품목이 바뀔 때마다 합계도 고쳐야 한다. 트리거로 맞추니 품목 10만 행을 넣는 시간이 68~72ms에서 431~459ms로 늘었다. 맞추는 일을 빠뜨리면 두 값이 어긋난다.
    • 그래서 정규화한 설계에서 출발하고, 느린 질의를 잰 뒤에 그 질의에 필요한 곳만 반정규화한다. 어긋남을 찾는 질의도 함께 둔다.

    예측해 보기¶

    문제 1. 수강 기록 다섯 행에서 몇 가지 함수 종속이 성립하는지 데이터로 확인한다. 무엇이 출력될까?

    ROWS = [  # 학번, 이름, 학과, 사무실, 강좌번호, 강좌명, 학점, 성적
    (1, "김하나", "컴퓨터공학", "공학관 301", 101, "데이터베이스", 3, "A"),
    (1, "김하나", "컴퓨터공학", "공학관 301", 102, "네트워크", 3, "B"),
    (2, "이두리", "경영", "상경관 105", 102, "네트워크", 3, "A"),
    (3, "박세나", "컴퓨터공학", "공학관 301", 101, "데이터베이스", 3, "B"),
    (3, "박세나", "컴퓨터공학", "공학관 301", 103, "운영체제", 3, "A"),
]
COLS = ["학번", "이름", "학과", "사무실", "강좌번호", "강좌명", "학점", "성적"]


def holds(x, y):                       # 데이터에서 x 열들이 같으면 y 열들도 늘 같은가
    seen = {}
    for r in ROWS:
        a = tuple(r[COLS.index(c)] for c in x)
        b = tuple(r[COLS.index(c)] for c in y)
        if seen.setdefault(a, b) != b:
            return False
    return True


print(holds(["학번"], ["이름", "학과"]))
print(holds(["학과"], ["사무실"]))
print(holds(["학번"], ["성적"]))
print(holds(["이름"], ["학번"]))
    정답과 해설 
    True
True
False
True

    김하나는 강좌마다 성적이 달라서 학번 → 성적은 성립하지 않는다. 성적은 학번과 강좌번호를 함께 써야 정해진다. 넷째 줄의 이름 → 학번은 이 다섯 행에서는 성립하지만, 동명이인이 들어오면 깨진다. 데이터로는 종속이 틀렸다는 것만 보일 수 있고, 맞다는 것은 "이름이 같은 학생이 있을 수 있나" 같은 요구사항으로 정한다.

    문제 2. 1NF를 어겨 학생이 듣는 강좌를 칸 하나에 쉼표로 적었다. 네트워크를 듣는 학생을 찾으면 무엇이 출력될까?

    CREATE TABLE student_flat (sid INTEGER PRIMARY KEY, name TEXT, courses TEXT);
INSERT INTO student_flat VALUES (1, '김하나', '데이터베이스, 네트워크'), (2, '이두리', '네트워크보안'), (3, '박세나', '운영체제');
SELECT name FROM student_flat WHERE courses LIKE '%네트워크%';
    정답과 해설 
    ('김하나',)
('이두리',)

    이두리는 네트워크보안을 듣는데 함께 걸렸다. 칸 안의 글자를 뒤지는 것 말고는 강좌를 가릴 방법이 없어서다. 강좌 이름을 바꾸거나 한 강좌만 빼는 일도 글자를 잘라 붙여야 한다. 칸 하나에 값 하나씩 두는 수강 표(50번(데이터 모델링과 ERD))로 나누고 강좌 표와 조인하면 WHERE c.title = '네트워크'처럼 정확히 찾는다.

    문제 3. 표 (학생, 과목, 교수)가 있다. 교수 한 명은 과목 하나만 가르치고, 학생은 과목마다 교수 한 명에게 듣는다. 기본 키는 (학생, 과목)이다. 이 표는 3NF일까? BCNF일까?

    정답과 해설

    3NF지만 BCNF는 아니다. 교수 → 과목인데 교수는 후보 키가 아니다(교수 한 명에게 여러 학생이 듣는다). 3NF는 정해지는 쪽(과목)이 키의 일부이면 봐주므로 3NF는 만족한다. 이 표에서는 어떤 교수가 무슨 과목을 가르치는지를 학생이 듣고 있어야만 적을 수 있다. BCNF로 나누면 담당(교수, 과목)과 수강(학생, 교수)이 된다. 대신 "학생은 과목마다 교수 한 명"이라는 규칙은 두 표를 조인해야만 확인할 수 있게 된다.

    확인할 점

    함수 종속은 주문번호 → 주문일, 고객번호(2NF 위반), 고객번호 → 고객 이름, 주소(3NF 위반), 상품번호 → 상품명(2NF 위반), (주문번호, 상품번호) → 단가, 수량이다. 이 데이터에서는 상품번호가 같으면 단가도 같지만, 단가는 그 주문 때의 가격이라 상품번호가 정하지 않는다(아래 둘째 점). 나눈 한 예와 확인 결과다.

    CREATE TABLE customer (customer_id INTEGER PRIMARY KEY, name TEXT NOT NULL, address TEXT);
CREATE TABLE product (product_id INTEGER PRIMARY KEY, name TEXT NOT NULL);
CREATE TABLE orders (order_id INTEGER PRIMARY KEY, ordered_on TEXT NOT NULL,
                     customer_id INTEGER NOT NULL REFERENCES customer(customer_id));
CREATE TABLE order_item (order_id INTEGER NOT NULL REFERENCES orders(order_id),
                         product_id INTEGER NOT NULL REFERENCES product(product_id),
                         unit_price INTEGER NOT NULL, qty INTEGER NOT NULL, PRIMARY KEY (order_id, product_id));
INSERT INTO customer SELECT DISTINCT customer_id, customer_name, address FROM order_flat;
INSERT INTO product SELECT DISTINCT product_id, product_name FROM order_flat;
INSERT INTO orders SELECT DISTINCT order_id, ordered_on, customer_id FROM order_flat;
INSERT INTO order_item SELECT order_id, product_id, unit_price, qty FROM order_flat;
CREATE VIEW joined AS
  SELECT o.order_id, o.ordered_on, c.customer_id, c.name, c.address, p.product_id, p.name, i.unit_price, i.qty
    FROM order_item i JOIN orders o USING (order_id) JOIN customer c USING (customer_id) JOIN product p USING (product_id);
SELECT count(*) FROM (SELECT * FROM joined EXCEPT SELECT * FROM order_flat);
SELECT count(*) FROM (SELECT * FROM order_flat EXCEPT SELECT * FROM joined);
SELECT (SELECT count(*) FROM joined), (SELECT count(*) FROM order_flat);
SELECT (SELECT count(*) FROM customer), (SELECT count(*) FROM product), (SELECT count(*) FROM orders), (SELECT count(*) FROM order_item);

    (0,)
(0,)
(4, 4)
(2, 3, 3, 4)
    • joined EXCEPT order_flat은 조인이 잘못 만든 행을, 반대쪽은 잃은 행을 찾는다. 다만 EXCEPT는 같은 행을 하나로 쳐서, 조인이 같은 행을 여러 번 만들어도 0이 나온다. 이 PC에서 고객 표에 키를 두지 않고 DISTINCT 없이 옮기니 조인 결과가 10행이 되었는데도 두 EXCEPT는 모두 0이었다. 그래서 행 수 (4, 4)까지 같아야 원래 표를 그대로 되살린 것이다.
    • 단가(unit_price)는 상품 표가 아니라 주문 품목에 두었다. 상품의 지금 가격과 "그 주문 때 받은 가격"은 다른 사실이라, 나중에 가격이 바뀌어도 지난 주문의 금액이 그대로여야 한다. 상품 표에 지금 가격 열을 따로 둘 수 있다.
    • 고객이 이사하면 customer 한 행만 고치면 된다. 원래 표에서는 김하나의 행 셋을 다 고쳐야 했다.

    AI와 함께 확인하기¶

    AI 활용 과제: AI가 나눈 표를 조인으로 검증하기

    1. 실습의 order_flat 정의를 AI에게 주고 "3NF로 정규화한 SQLite 스키마와, 데이터를 옮기는 SQL을 만들어 줘"라고 한다.
    2. 실행하기 전에 함수 종속을 내가 찾은 것과 견준다.
    3. 새 파일(python -m sqlite3 shop_ai.db)에 실습의 order_flat을 다시 만든 뒤 받은 SQL을 실행하고, 실습 4의 EXCEPT 두 개와 행 수로 원래 표가 그대로 되살아나는지 확인한다. 다르면 다른 행을 AI에게 보여 주고 고치게 한다.
    확인할 점
    • 단가를 상품 표로 옮기고 주문 품목에서 빼는 답이 흔하다. 가격이 바뀌면 지난 주문의 금액까지 바뀐다. "같은 값처럼 보여도 다른 사실인가"를 묻는다.
    • 데이터를 옮길 때 DISTINCT를 빼면 고객과 주문이 여러 번 들어가 기본 키 오류가 나거나, 키가 없으면 그대로 중복된다. 중복은 EXCEPT로는 보이지 않고 행 수로 드러난다.
    • 정규화 단계 이름보다 결과를 본다. 같은 사실이 한 곳에만 있는지, 조인하면 원래대로 돌아오는지가 기준이다.

    더 알아보기¶

    SQLite의 기본 키는 NULL을 받기도 한다

    표준 SQL에서 기본 키 열은 NULL이 될 수 없다. SQLite는 예전 버전과 맞추느라, INTEGER PRIMARY KEY가 아닌 기본 키 열에 NOT NULL을 따로 적지 않으면 NULL을 받는다(STRICT 표와 WITHOUT ROWID 표는 막는다). 위젯의 한 표에서 학번을 비우고 강좌를 여는 것이 막힌 까닭은 학번 열에 NOT NULL을 적었기 때문이다. 적지 않으면 학번이 NULL인 이상한 행이 들어간다. 이 PC에서 확인했다.

    CREATE TABLE record (sid INTEGER, cid INTEGER, title TEXT, PRIMARY KEY (sid, cid));
INSERT INTO record VALUES (NULL, 104, '컴퓨터구조');
SELECT * FROM record;


    (None, 104, '컴퓨터구조')
    4NF와 5NF

    BCNF까지 나눠도 남는 되풀이가 있다. 한 학생이 취미 여럿과 외국어 여럿을 갖는데 둘이 서로 무관하다면, (학생, 취미, 외국어) 표는 모든 짝을 적어야 해서 되풀이가 생긴다. 이런 다치 종속을 떼는 것이 4NF, 셋 이상의 표로 나눠야만 풀리는 경우를 다루는 것이 5NF다. 실무에서는 50번(데이터 모델링과 ERD)처럼 개체와 관계를 제대로 찾으면 대개 BCNF에서 끝난다.

    이 항목의 측정 프로그램

    3절의 시간과 그림은 이 PC(Core i9-14900KF, DDR5 64GB, NVMe SSD, Windows 11)에서 아래 프로그램을 5번 실행한 범위다. 주문 20만 건과 품목 약 100만 행을 TEMP 폴더의 SQLite 파일(약 37MB)에 만들고, 같은 데이터로 읽기와 쓰기를 잰다. 읽기는 처음 한 번 실행해 캐시를 채운 뒤의 값이다. 여기의 트리거는 품목을 넣을 때만 합계를 고친다. 실제로 쓰려면 품목을 고치거나 지울 때의 트리거도 두어야 합계가 어긋나지 않는다.

    # 51번 측정: 주문 합계를 매번 조인해 계산할 때와, 주문 표에 합계 열을 두고(반정규화) 트리거로 맞춰 둘 때
# 읽기: 합계가 가장 큰 주문 10건. 쓰기: 품목 10만 행 넣기(트리거가 없을 때와 있을 때)
import os
import random
import shutil
import sqlite3
import statistics
import tempfile
import time

random.seed(51)
work = tempfile.mkdtemp(dir=os.environ.get("TEMP"))
con = sqlite3.connect(os.path.join(work, "shop.db"))
con.executescript("""
    CREATE TABLE orders (id INTEGER PRIMARY KEY, customer_id INTEGER NOT NULL, total INTEGER NOT NULL DEFAULT 0);
    CREATE TABLE order_item (order_id INTEGER NOT NULL REFERENCES orders(id), product_id INTEGER NOT NULL,
                             price INTEGER NOT NULL, qty INTEGER NOT NULL);
""")
N = 200_000
con.executemany("INSERT INTO orders (id, customer_id) VALUES (?, ?)", ((i, random.randrange(1, 20_001)) for i in range(1, N + 1)))
items = [(o, random.randrange(1, 5001), random.randrange(10, 1001) * 100, random.randrange(1, 4))
         for o in range(1, N + 1) for _ in range(random.randrange(1, 10))]
con.executemany("INSERT INTO order_item VALUES (?, ?, ?, ?)", items)
con.execute("CREATE INDEX order_item_order ON order_item(order_id)")
con.execute("UPDATE orders SET total = (SELECT SUM(price * qty) FROM order_item WHERE order_id = orders.id)")   # 반정규화한 합계 열
con.execute("CREATE INDEX orders_total ON orders(total)")
con.commit()

JOIN = """SELECT o.id, SUM(i.price * i.qty) AS total FROM orders o JOIN order_item i ON i.order_id = o.id
          GROUP BY o.id ORDER BY total DESC LIMIT 10"""
STORED = "SELECT id, total FROM orders ORDER BY total DESC LIMIT 10"
assert [r[1] for r in con.execute(JOIN)] == [r[1] for r in con.execute(STORED)]   # 두 방법의 답이 같다


def median_ms(sql, n):
    ts = []
    for _ in range(n):
        t = time.perf_counter()
        con.execute(sql).fetchall()
        ts.append((time.perf_counter() - t) * 1000)
    return statistics.median(ts)


NOIDX = "SELECT id, total FROM orders NOT INDEXED ORDER BY total DESC LIMIT 10"   # 합계 열은 두되 그 인덱스는 쓰지 않는다
print(f"read: join {median_ms(JOIN, 5):.1f} ms, stored {median_ms(STORED, 50):.3f} ms, stored without index {median_ms(NOIDX, 20):.2f} ms")

new = [(N + 1 + k // 10, random.randrange(1, 5001), random.randrange(10, 1001) * 100, random.randrange(1, 4)) for k in range(100_000)]
con.executemany("INSERT INTO orders (id, customer_id) VALUES (?, 1)", ((N + 1 + k,) for k in range(10_000)))
con.commit()
t = time.perf_counter()
con.executemany("INSERT INTO order_item VALUES (?, ?, ?, ?)", new)
con.commit()
plain = (time.perf_counter() - t) * 1000
con.execute("DELETE FROM order_item WHERE order_id > ?", (N,))
con.commit()
con.execute("""CREATE TRIGGER order_item_total AFTER INSERT ON order_item BEGIN
                 UPDATE orders SET total = total + NEW.price * NEW.qty WHERE id = NEW.order_id;
               END""")
t = time.perf_counter()
con.executemany("INSERT INTO order_item VALUES (?, ?, ?, ?)", new)
con.commit()
trig = (time.perf_counter() - t) * 1000
print(f"write 100k items: plain {plain:.0f} ms, with trigger {trig:.0f} ms")
bad = con.execute("""SELECT count(*) FROM orders o
                     WHERE total <> (SELECT COALESCE(SUM(price * qty), 0) FROM order_item WHERE order_id = o.id)""").fetchone()[0]
print("mismatch:", bad)                           # 어긋난 주문 수. 트리거가 맞춰 두었으면 0
con.close()
shutil.rmtree(work)

    정리¶

    • 한 표에 다 적으면 같은 사실을 되풀이해 수정, 삽입, 삭제 이상이 생긴다. 정규화는 같은 사실을 한 곳에만 적도록 표를 나누는 일이다.
    • 함수 종속(A → B)을 요구사항에서 찾고, 키의 일부에 딸린 열(2NF), 키에 들지 않은 열이 키가 아닌 열에 딸린 것(3NF)을 떼어 낸다. BCNF는 결정자가 모두 후보 키다. 나눈 표는 조인하면 원래대로 돌아와야 한다.
    • 반정규화는 읽기를 크게 줄이지만 쓰기와 맞추는 일을 늘린다. 잰 뒤에 필요한 곳만 하고, 어긋남을 찾는 질의를 함께 둔다.
