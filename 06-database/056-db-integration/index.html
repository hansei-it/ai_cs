    56. 애플리케이션과 DB 연동: 커넥션 풀, ORM, N+1 문제¶

    원리 동작을 예측하고 이상을 알아챌 수 있어야 하는 항목

    웹 서버의 요청 하나는 대개 DB에 질의 몇 개를 보낸다. 질의를 보내려면 먼저 연결이 있어야 하고, 요즘 프로그램은 SQL을 직접 쓰는 대신 ORM이 객체에서 SQL을 만들어 보내는 일이 많다. 이 항목은 연결을 다시 쓰는 커넥션 풀, 객체와 행을 잇는 ORM, 그리고 ORM을 쓸 때 가장 흔한 성능 문제인 N+1을 이 PC의 SQLite에서 재 본다. 예제는 Python의 sqlite3만으로 한다.

    이 항목에서 배우는 것¶

    • 연결을 요청마다 맺지 않고 풀에서 빌려 쓰는 까닭을 설명할 수 있다.
    • ORM이 객체와 행을 어떻게 잇는지, 지연 로딩이 언제 SQL을 보내는지 설명할 수 있다.
    • 질의 수를 세어 N+1을 찾고, JOIN이나 IN으로 묶어 고칠 수 있다.

    1. 연결은 만들기 비싸서 풀에 두고 빌려 쓴다¶

    • DB에 연결하면 파일이나 소켓을 열고, 로그인하고, 연결마다 메모리를 잡는다. 이 PC의 SQLite에서 요청마다 연결을 새로 맺으면 요청 하나에 224~234µs, 하나를 다시 쓰면 46~57µs였다. 서버 DB라면 여기에 TCP 연결과 암호화 협상(41번(전송 계층 (TCP·UDP)), 45번(HTTPS와 TLS))이 더해진다.
    • 커넥션 풀은 연결을 몇 개 미리 만들어 두고, 요청이 오면 빌려 주고, 끝나면 돌려받는다. 연결을 닫지 않고 다시 쓴다.
    • 풀은 크다고 좋지 않다. 서버 여러 대의 풀을 합쳐도 DB의 최대 연결 수를 넘지 않게 하고, DB가 실제로 동시에 처리할 수 있는 만큼으로 작게 둔다. 연결을 빌리고 돌려주지 않으면 풀이 비어 다음 요청이 기다리다 실패한다(문제 2).

    2. ORM은 객체와 행을 잇고, 보이지 않게 SQL을 보낸다¶

    • ORM(객체-관계 매핑)은 표의 행 하나를 프로그램의 객체 하나로 바꿔 준다. post.title처럼 속성으로 읽고, 고치고 저장하면 ORM이 SQL을 만들어 보낸다.
    • 다른 표에 있는 값(post.author)은 처음 쓸 때 가져오는 일이 많다(지연 로딩, lazy loading). 속성을 읽는 코드에는 SQL이 없는데, 글마다 그 속성을 처음 쓸 때 질의가 하나씩 나간다(문제 1).
    • 그래서 ORM을 쓸 때는 질의 기록을 켜서 실제로 나가는 SQL을 본다. SQLite에서는 con.set_trace_callback(print)로 볼 수 있다.

    3. N+1은 질의 수를 세어 찾고, 한 번에 묶어 고친다¶

    직접 해 보기N+1 질의는 얼마나 느릴까글 수와 DB까지의 거리(질의 하나의 비용)를 골라, 글마다 작성자를 따로 묻는 N+1과 JOIN, IN으로 묶은 방법의 질의 수와 시간을 견준다
    새 창에서 크게 열기
    • 목록 하나(1번)를 받은 뒤 항목마다 질의를 하나씩(N번) 더 보내는 것이 N+1이다. 이 PC에서 글 1,000개의 작성자를 이렇게 읽으니 질의 1,001번에 48~50ms가 들었다. JOIN 한 번은 0.39~0.42ms, IN으로 두 번은 0.52~0.60ms였다.
    • 같은 PC 안의 SQLite에서도 질의 하나에 50µs쯤이 고정으로 들었다(파일 DB에 자동 커밋으로 하나씩 보낼 때다. 까닭은 더 알아보기에 있다). 서버 DB라면 질의마다 네트워크 왕복이 붙어서, 위젯처럼 질의의 수가 곧 시간이 된다.
    • 고치는 방법은 질의를 묶는 것이다. JOIN으로 한 번에 잇거나, 목록의 번호를 모아 WHERE id IN (…)으로 한꺼번에 묻는다. ORM에는 이 일을 해 주는 기능(미리 함께 읽기, 즉시 로딩 eager loading)이 있다.

    예측해 보기¶

    문제 1. 행을 객체로 바꾸고, 작성자는 처음 쓸 때 가져와 그 객체에 담아 두는 작은 ORM을 만들었다. 반복문은 글마다 p.author를 두 번 쓴다. 실제로 보낸 SQL을 함께 찍으면 무엇이 출력될까? 질의는 모두 몇 번 나갈까?

    import functools
import sqlite3

con = sqlite3.connect(":memory:")
con.executescript("""
    CREATE TABLE user (id INTEGER PRIMARY KEY, name TEXT NOT NULL);
    CREATE TABLE post (id INTEGER PRIMARY KEY, user_id INTEGER NOT NULL REFERENCES user(id), title TEXT NOT NULL);
    INSERT INTO user VALUES (1, '김하나'), (2, '이두리'), (3, '박세나');
    INSERT INTO post VALUES (1, 1, '첫 글'), (2, 2, '안녕'), (3, 1, '질문'), (4, 3, '답변');
""")


class Post:                                 # 행 하나를 객체 하나로. 작성자는 처음 쓸 때 가져온다(지연 로딩)
    def __init__(self, row):
        self.id, self.user_id, self.title = row

    @functools.cached_property              # 처음 쓸 때 한 번 계산해 이 객체에 담아 둔다
    def author(self):
        return con.execute("SELECT name FROM user WHERE id = ?", (self.user_id,)).fetchone()[0]


con.set_trace_callback(print)              # DB에 보내는 SQL을 찍는다
posts = [Post(r) for r in con.execute("SELECT id, user_id, title FROM post ORDER BY id")]
for p in posts:
    print(p.title, p.author, len(p.author))
    정답과 해설 
    SELECT id, user_id, title FROM post ORDER BY id
SELECT name FROM user WHERE id = 1
첫 글 김하나 3
SELECT name FROM user WHERE id = 2
안녕 이두리 3
SELECT name FROM user WHERE id = 1
질문 김하나 3
SELECT name FROM user WHERE id = 3
답변 박세나 3

    글 4개에 질의 5번이다. print의 인자를 계산할 때 p.author가 처음 쓰이며 질의를 하나 보내고, 같은 줄의 len(p.author)는 객체에 담아 둔 값을 써서 질의가 나가지 않았다. 그래도 1번 작성자는 글 1과 글 3에서 따로 물었다. 객체마다 따로 담아 두기 때문이다. 반복문에는 SQL이 없어서, 기록을 켜지 않으면 보이지 않는다. 실제 ORM은 한 번 읽은 객체를 세션 전체에서 기억해 두기도 하지만(SQLAlchemy), 그래도 서로 다른 작성자 수만큼은 묻는다. 작성자가 모두 다르면 글 수만큼이다.

    문제 2. 연결 둘짜리 풀에서 셋째 요청이 연결을 빌리려 한다. 무엇이 출력될까?

    import queue
import sqlite3

pool = queue.Queue()
for _ in range(2):
    pool.put(sqlite3.connect(":memory:"))  # 연결 둘을 미리 만들어 둔다

a = pool.get()
b = pool.get()
try:
    c = pool.get(timeout=0.1)              # 셋째 요청: 0.1초만 기다린다
except queue.Empty:
    print("빈 연결이 없다")
pool.put(a)                                # 첫째 요청이 연결을 돌려준다
c = pool.get(timeout=0.1)
print(c is a)
    정답과 해설 
    빈 연결이 없다
True

    둘을 빌려 간 뒤에는 풀이 비어, 셋째 요청은 기다리다 실패한다. 첫째가 돌려주자 셋째는 그 연결(a)을 그대로 받았다. 새로 만든 것이 아니라 다시 쓴 것이다. 예외가 나서 연결을 돌려주는 코드를 건너뛰면 풀이 조금씩 비어 간다. 그래서 풀이 주는 with(예: SQLAlchemy의 with engine.connect() as conn:)나 try … finally로 반드시 돌려준다. sqlite3 연결의 with는 트랜잭션을 커밋할 뿐 연결을 닫거나 돌려주지 않는다.

    문제 3. DB 서버까지 질의 하나에 왕복 0.5ms가 든다고 하자. 글 1,000개의 목록 화면을 N+1로 만들면 질의에만 얼마나 걸릴까? JOIN 한 번이면?

    정답과 해설

    N+1은 약 0.5초, JOIN은 약 0.5ms다. 질의 1,001번 × 0.5ms ≈ 500ms이고, JOIN은 한 번이다. 한 사람의 화면 하나가 0.5초를 질의를 기다리는 데 쓰고, 그동안 연결 하나를 붙잡는다. 사용자가 많으면 풀의 연결이 모자라 다른 요청까지 기다린다(문제 2). 위젯에서 거리를 바꿔 보면, DB가 멀수록 질의의 수가 시간을 정한다(위젯은 행을 읽는 시간까지 더해 JOIN이 0.85ms로 나온다).

    직접 해보기¶

    실습: 질의 수를 세고 N+1 고치기

    1. 문제 1에 이어서 실행한다(con과 표를 그대로 쓴다). 아래 report()는 글마다 작성자와 댓글 수를 따로 묻는다. 실행해 결과와 질의 수를 적는다.
    2. 같은 결과를 내는 report2()를 질의 한 번으로 짠다. 결과가 같은지 ==로 확인하고 질의 수를 센다.
    3. 글이 1,000개라면 두 함수의 질의 수가 각각 몇이 될지 적는다.
    con.set_trace_callback(None)                 # 문제 1에서 켠 기록을 끈다
con.executescript("""
    CREATE TABLE comment (id INTEGER PRIMARY KEY, post_id INTEGER NOT NULL REFERENCES post(id), body TEXT NOT NULL);
    INSERT INTO comment VALUES (1, 1, '좋다'), (2, 1, '나도'), (3, 3, '답');
""")
count = [0]
con.set_trace_callback(lambda sql: count.__setitem__(0, count[0] + 1))   # 보낸 SQL을 센다


def report():                              # 글마다 작성자와 댓글 수를 따로 묻는다
    out = []
    for pid, uid, title in con.execute("SELECT id, user_id, title FROM post ORDER BY id").fetchall():
        name = con.execute("SELECT name FROM user WHERE id = ?", (uid,)).fetchone()[0]
        n = con.execute("SELECT COUNT(*) FROM comment WHERE post_id = ?", (pid,)).fetchone()[0]
        out.append((title, name, n))
    return out


print(report())

    AI와 함께 확인하기¶

    AI 활용 과제: ORM 코드의 질의 수 확인하기

    1. AI에게 "Python ORM(SQLAlchemy나 Django)으로 글 목록 페이지를 만들어 줘. 글마다 제목, 작성자 이름, 댓글 수를 보여 준다"라고 한다.
    2. 받은 코드에서 글 목록을 읽는 곳과, 반복문 안에서 작성자나 댓글에 접근하는 곳을 표시하고, 글이 N개일 때 질의가 몇 번 나갈지 적는다.
    3. 그 ORM에서 실제로 나가는 SQL을 기록하는 방법과, 미리 함께 읽게 하는 방법을 AI에게 묻고, 고친 뒤 질의 수가 어떻게 되는지 확인한다.
    확인할 점
    • 반복문 안에서 post.author.name이나 post.comments를 쓰는 코드는 대개 N+1이다. 코드에 SQL이 없어도 질의가 나간다(문제 1).
    • 질의 기록을 켜는 방법을 묻는다. SQLAlchemy는 엔진에 echo=True, Django는 DEBUG = True일 때 connection.queries나 디버그 도구로 본다. 기록 없이 "이제 빨라졌다"는 말은 믿지 않는다.
    • 미리 함께 읽는 기능(SQLAlchemy의 joinedload, selectinload, Django의 select_related, prefetch_related)을 쓰면 JOIN이나 IN으로 묶인다. 고친 뒤에도 결과가 같은지(댓글 없는 글이 0인지) 확인한다.
    • 연결을 열고 닫는 코드가 요청마다 있다면 풀을 쓰는지 묻는다. SQLAlchemy는 엔진이 풀을 기본으로 두지만, Django는 기본 설정(CONN_MAX_AGE = 0)이면 요청이 끝날 때마다 연결을 닫는다. 쓰는 도구의 설정을 확인한다.

    더 알아보기¶

    SQLite에서 질의 하나에 50µs쯤 드는 까닭

    이 PC에서 글 1,000개의 N+1은 48~50ms였는데, 같은 질의들을 트랜잭션 하나 안에서 보내니 1.5~1.6ms, 메모리 DB에서는 1.2~1.3ms였다(측정 프로그램의 마지막 두 줄). 파일 DB에서 자동 커밋으로 질의를 하나씩 보내면, 질의마다 읽기를 새로 시작하며 파일에 공유 잠금을 걸고 풀기 때문이다. 같은 PC 안에서도 질의마다 드는 몫이 있다. 서버 DB에서는 이 자리를 네트워크 왕복이 차지하고, 보통 훨씬 크다.

    이 항목의 측정 프로그램

    1절과 3절, 위의 값은 이 PC(Core i9-14900KF, DDR5 64GB, NVMe SSD, Windows 11)에서 아래 프로그램을 5번 실행한 범위다. TEMP 폴더의 SQLite 파일에 사용자 100명과 글 1,000개를 두고, 질의 수는 set_trace_callback으로 실제로 실행된 SQL을 세었다.

    # 56번 측정: (1) 요청마다 연결을 새로 맺을 때와 하나를 다시 쓸 때 (2) 글 1,000개의 작성자 이름을 읽는 세 방법
import os
import random
import shutil
import sqlite3
import statistics
import tempfile
import time

random.seed(56)
work = tempfile.mkdtemp(dir=os.environ.get("TEMP"))
path = os.path.join(work, "board.db")
con = sqlite3.connect(path)
con.executescript("""
    CREATE TABLE user (id INTEGER PRIMARY KEY, name TEXT NOT NULL);
    CREATE TABLE post (id INTEGER PRIMARY KEY, user_id INTEGER NOT NULL REFERENCES user(id), title TEXT NOT NULL);
""")
con.executemany("INSERT INTO user VALUES (?, ?)", ((i, f"사용자{i}") for i in range(1, 101)))
con.executemany("INSERT INTO post VALUES (?, ?, ?)", ((i, random.randrange(1, 101), f"글 {i}") for i in range(1, 1001)))
con.commit()
con.close()
REQ = 2000


def fresh():                               # 요청마다 연결을 맺고 닫는다
    for i in range(REQ):
        c = sqlite3.connect(path)
        c.execute("SELECT name FROM user WHERE id = ?", (i % 100 + 1,)).fetchone()
        c.close()


def reuse():                               # 연결 하나를 다시 쓴다
    c = sqlite3.connect(path)
    for i in range(REQ):
        c.execute("SELECT name FROM user WHERE id = ?", (i % 100 + 1,)).fetchone()
    c.close()


def us_per(fn, n=5):
    ts = []
    for _ in range(n):
        t = time.perf_counter()
        fn()
        ts.append((time.perf_counter() - t) / REQ * 1e6)
    return statistics.median(ts)


print(f"connect each request: {us_per(fresh):.1f} us/request, reuse: {us_per(reuse):.1f} us/request")

c = sqlite3.connect(path)
count = [0]
c.set_trace_callback(lambda sql: count.__setitem__(0, count[0] + 1))


def n_plus_1(db=None):
    db = db or c
    out = []
    for pid, uid, title in db.execute("SELECT id, user_id, title FROM post ORDER BY id").fetchall():   # 목록을 먼저 다 받는다(ORM처럼)
        out.append((title, db.execute("SELECT name FROM user WHERE id = ?", (uid,)).fetchone()[0]))      # 글마다 한 번
    return out


def join():
    return c.execute("SELECT p.title, u.name FROM post p JOIN user u ON u.id = p.user_id ORDER BY p.id").fetchall()


def in_batch():
    posts = c.execute("SELECT id, user_id, title FROM post ORDER BY id").fetchall()
    ids = sorted({uid for _, uid, _ in posts})
    names = dict(c.execute(f"SELECT id, name FROM user WHERE id IN ({','.join('?' * len(ids))})", ids))
    return [(title, names[uid]) for _, uid, title in posts]


def median_ms(fn, n=7):
    ts = []
    for _ in range(n):
        t = time.perf_counter()
        fn()
        ts.append((time.perf_counter() - t) * 1000)
    return statistics.median(ts)


assert n_plus_1() == join() == in_batch()   # 세 방법의 결과가 같다
for name, fn in [("N+1", n_plus_1), ("JOIN", join), ("IN", in_batch)]:
    count[0] = 0
    fn()
    print(f"{name}: {count[0]} queries, {median_ms(fn):.2f} ms")
c.execute("BEGIN")                         # 더 알아보기: 같은 N+1을 트랜잭션 하나 안에서
print(f"N+1 in one transaction: {median_ms(n_plus_1):.2f} ms")
c.execute("COMMIT")
m = sqlite3.connect(":memory:")
c.backup(m)                                # 같은 데이터를 메모리 DB에 옮겨서
print(f"N+1 on memory DB: {median_ms(lambda: n_plus_1(m)):.2f} ms")
m.close()
c.close()
shutil.rmtree(work)

    정리¶

    • 연결은 맺는 데 비용이 들어서, 커넥션 풀에 두고 빌려 쓰고 돌려준다. 돌려주지 않으면 풀이 비어 다른 요청이 기다린다.
    • ORM은 행을 객체로 바꾸고 SQL을 대신 만든다. 지연 로딩은 속성을 처음 쓸 때 보이지 않게 질의를 보내므로, 질의 기록을 켜서 실제 SQL을 본다.
    • N+1은 목록 하나에 항목마다 질의를 하나씩 더 보내는 것이다. 질의 수를 세어 찾고, JOIN이나 IN으로 묶는다. 고친 뒤에는 결과가 같은지 견준다.
