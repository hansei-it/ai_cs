    57. NoSQL 데이터베이스: Key-Value, Document, Wide-Column 모델¶

    원리 동작을 예측하고 이상을 알아챌 수 있어야 하는 항목

    관계형 DB는 데이터를 겹치지 않게 표로 나누고, 질의할 때 조인으로 잇는다. 그런데 자주 함께 읽는 것을 미리 모아 두면 잇는 일이 필요 없고, 여러 서버에 나눠 담기도 쉽다. 이렇게 정규화한 표와 조인이 아닌 모양으로 저장하는 DB를 묶어 NoSQL이라 부른다. 이 항목은 키-값, 문서, 와이드 컬럼 세 모델에 같은 주문 데이터를 담아 보고, 어떤 질의에 무엇이 맞는지 견준다. 키-값은 Python에 든 dbm으로, 문서는 SQLite의 JSON 함수로 직접 해 본다.

    이 항목에서 배우는 것¶

    • 키-값, 문서, 와이드 컬럼 모델이 데이터를 어떤 모양으로 두는지 설명할 수 있다.
    • 질의를 보고 모델마다 읽어야 할 양을 예측하고, 모델을 고를 수 있다.
    • 미리 모아 둔 데이터(중복)가 쓰기와 일관성에 주는 비용을 설명할 수 있다.

    1. 같은 데이터를 다른 모양으로 담는다¶

    • 키-값은 키 하나에 값 하나를 둔다. 값의 속은 DB가 모른다. 키로 넣고 꺼내는 것만 하므로 가장 단순하고 빠르다. 대신 키를 모르면 값으로 찾을 길이 따로 없다(문제 1).
    • 문서는 JSON 같은 문서를 통째로 둔다. 고객 문서 안에 그 고객의 주문을 넣어 두면 한 번에 읽는다. 문서마다 필드가 달라도 된다. 문서 안의 필드로 찾거나 인덱스를 만들 수 있다.
    • 와이드 컬럼은 행을 파티션 키로 나누고, 파티션 안은 정렬해 둔다. "고객 1의 최근 주문"처럼 파티션 하나를 차례로 읽는 질의에 맞는다. 파티션마다 다른 서버에 둘 수 있어 아주 많은 데이터를 나눠 담는다. 파티션 하나가 열을 아주 많이 가질 수 있어서 와이드 컬럼이라 부른다. 열 단위로 저장하는 분석용 DB(열 지향 DB)와는 다르다.

    2. 무엇이 맞는지는 질의가 정한다¶

    직접 해 보기같은 주문, 네 가지 모델같은 주문 6건을 표, 키-값, 문서, 와이드 컬럼으로 저장해 두고, 질의를 골라 모델마다 몇 개를 읽고 고치는지, 전체를 훑는지 견준다
    새 창에서 크게 열기
    • 위젯에서 "김하나의 주문 목록"은 문서 모델이 문서 하나로, 와이드 컬럼이 파티션 하나로 끝냈다. 고객 단위로 모아 두었기 때문이다. "주문 o4 하나"는 주문 번호를 키로 둔 키-값이 가장 적게 읽었다. 같은 모델이 질의에 따라 가장 빠르기도, 전체를 훑기도 한다.
    • 그래서 NoSQL, 특히 키-값과 와이드 컬럼은 자주 쓰는 질의를 먼저 정하고 그에 맞춰 데이터를 둔다. 관계형이 데이터를 먼저 정하고 질의를 나중에 쓰는 것과 반대다(3절 그림).
    • "NoSQL이 더 빠르다"는 질의에 맞게 둔 경우에만 맞다. 묶어서 세는 질의(상품별 판매 수량)는 어느 모델이든 전체를 읽었다.

    3. 미리 모아 두면 같은 값을 여러 곳에 쓴다¶

    • 질의마다 맞춘 표를 하나씩 두면 읽기는 파티션 하나로 끝나지만, 주문 하나를 두 표에 써야 한다. 함께 읽으려고 상품 이름을 주문마다 복사해 두면, 이름을 바꿀 때 복사본을 모두 찾아 고쳐야 한다(위젯의 "상품 502 이름 바꾸기", 문제 2).
    • 이것은 51번(정규화와 반정규화)의 반정규화와 같은 맞바꿈이다. 관계형은 정규화를 기본으로 두고 필요한 곳만 반정규화하고, 많은 NoSQL은 반정규화를 기본으로 둔다.
    • 고를 때는 질의의 모양, 데이터의 양과 늘어나는 속도, 여러 문서를 함께 고칠 일(트랜잭션, 53번(트랜잭션과 락))이 얼마나 되는지를 본다. 한 서비스 안에서 둘을 함께 쓰는 일도 흔하다(로그인 세션은 키-값, 주문은 관계형).

    예측해 보기¶

    문제 1. 사용자 셋을 user:번호 키로 키-값 저장소에 넣었다. 키로 하나를 꺼내고, 이메일로 한 명을 찾는다. 무엇이 출력될까?

    import dbm
import json
import os
import tempfile

path = os.path.join(tempfile.mkdtemp(), "users")
with dbm.open(path, "c") as db:                          # Python에 든 키-값 저장소(이 PC에서는 SQLite 파일)
    for uid, name, email in [(1, "김하나", "hana@school.example"), (2, "이두리", "duri@school.example"), (3, "박세나", "sena@school.example")]:
        db[f"user:{uid}"] = json.dumps({"name": name, "email": email}, ensure_ascii=False)
    print(json.loads(db["user:2"])["name"])
    reads = 0
    for key in db.keys():                                # 이메일로 찾을 길은 키를 모두 열어 보는 것뿐이다
        reads += 1
        if json.loads(db[key])["email"] == "sena@school.example":
            break
    print(reads)
    정답과 해설 
    이두리
3

    키를 알면 한 번에 꺼낸다. 이메일로 찾을 때는 값의 속을 DB가 모르기 때문에, 프로그램이 키를 하나씩 열어 값을 풀어 봐야 했다. 사용자가 100만 명이면 100만 번이다. 그래서 키-값 저장소에서는 찾을 길마다 키를 따로 만든다. 예를 들어 email:sena@school.example → user:3을 함께 넣어 두고, 사용자를 넣고 지울 때 둘을 함께 고친다. 키를 꺼내는 차례는 저장소가 정하므로, 셋째에 찾은 것은 이 PC에서 그 차례였다는 뜻이다.

    문제 2. 주문 문서마다 상품 이름을 복사해 두었다. 한 문서에서만 이름을 바꾼 뒤, 상품 502의 이름을 문서들에서 모아 본다. 무엇이 출력될까?

    CREATE TABLE orders (doc TEXT NOT NULL);
INSERT INTO orders VALUES
  ('{"id": "o2", "customer": 1, "product": {"id": 502, "name": "마우스"}, "qty": 2}'),
  ('{"id": "o6", "customer": 2, "product": {"id": 502, "name": "마우스"}, "qty": 1}');
UPDATE orders SET doc = json_set(doc, '$.product.name', '무선 마우스') WHERE json_extract(doc, '$.id') = 'o2';
SELECT json_extract(doc, '$.id'), json_extract(doc, '$.product.name') FROM orders WHERE json_extract(doc, '$.product.id') = 502 ORDER BY 1;
    정답과 해설 
    ('o2', '무선 마우스')
('o6', '마우스')

    같은 상품이 문서마다 다른 이름을 갖게 되었다. 복사해 둔 값은 바꿀 때 모두 찾아 고쳐야 한다. 문서가 많으면 이 일이 무겁고, 도중에 멈추면 어긋난 채로 남는다. 상품 이름처럼 자주 바뀌는 값은 복사하지 않고 상품 번호만 두는 편이 낫다. 반대로 주문할 때의 가격처럼 그때의 값을 남겨야 하는 것은 복사가 맞다(51번(정규화와 반정규화)의 실습).

    문제 3. 센서 1,000개의 측정값을 와이드 컬럼 DB에 (센서 번호)를 파티션 키, (시각)을 정렬 키로 두었다. "센서 7의 최근 한 시간"과 "오늘 모든 센서의 평균"은 각각 파티션을 몇 개 읽을까?

    정답과 해설

    앞은 하나, 뒤는 1,000개 전부다. 센서 7의 파티션 안은 시각 차례라 끝에서부터 한 시간만 읽으면 된다. "모든 센서"는 파티션 키를 하나로 정할 수 없으니 전부 연다. 뒤의 질의가 잦으면 그 질의에 맞춘 표를 하나 더 두고 측정값을 두 번 쓰거나, 측정값이 들어올 때 평균을 미리 계산해 둔다. 3절 그림처럼 질의마다 표를 맞추는 것이다. 이때 날짜만 파티션 키로 하면 하루치 측정값이 모두 파티션 하나에 몰려, 그날의 쓰기를 서버 하나가 다 받는다. (날짜, 센서 번호를 10으로 나눈 나머지)처럼 날짜에 묶음 번호를 더해 나눈다.

    직접 해보기¶

    실습: 키-값으로 장바구니 만들기

    1. 문제 1처럼 dbm을 열고, 사용자마다 cart:번호 키에 장바구니를 JSON 목록으로 둔다. 상품을 넣고 빼는 함수 add(uid, product), remove(uid, product)를 짠다.
    2. 사용자 셋의 장바구니를 채우고, 한 사용자의 장바구니를 키 하나로 꺼낸다.
    3. "키보드를 담은 사용자가 몇 명인가"를 구하고, 그러려고 몇 개의 키를 읽었는지 센다.
    4. 3이 잦은 질의라면 키를 어떻게 더 두면 될지, 그때 add와 remove가 무엇을 더 해야 하는지 적는다.
    확인할 점
    • 2는 사용자 수와 상관없이 키 하나다. 장바구니처럼 한 사람의 것을 통째로 읽고 쓰는 데이터는 키-값에 잘 맞는다. 로그인 세션도 그렇다.
    • 3은 모든 cart: 키를 열어 봐야 한다. 사용자가 늘면 그만큼 늘어난다.
    • 4는 product:키보드:carts처럼 상품마다 담은 사용자의 목록 키를 둔다. 그러면 add와 remove는 장바구니와 그 목록 둘을 함께 고쳐야 하고, 하나만 고치고 멈추면 둘이 어긋난다. 관계형이라면 cart_item(user_id, product) 표 하나에 인덱스를 두고 COUNT로 끝난다(55번(인덱스와 실행 계획)).

    AI와 함께 확인하기¶

    AI 활용 과제: DB 고르기에 대한 조언 검증하기

    1. AI에게 "회원, 주문, 상품 리뷰가 있는 쇼핑몰을 만든다. MongoDB와 MySQL 중 무엇을 써야 하나?"라고 묻는다.
    2. 답이 근거로 드는 것을 적는다. 질의의 모양, 데이터의 양, 일관성과 트랜잭션, 운영 경험 가운데 무엇을 말하는지 본다.
    3. 그 쇼핑몰에서 가장 자주 쓸 질의 셋을 내가 정해 AI에게 주고, 모델마다 그 질의가 어떻게 되는지 다시 묻는다. 위젯처럼 "몇 개를 읽는가"로 견주게 한다.
    확인할 점
    • "NoSQL은 빠르고 확장이 쉽다"만 말하는 답은 반쪽이다. 질의에 맞게 둔 경우에만 빠르고, 맞지 않는 질의는 전체를 읽는다(위젯의 "주문 o4 하나"에서 문서와 와이드 컬럼). 위젯은 인덱스 없이 세었다. 문서 DB는 문서 안의 필드(orders.id)에도 인덱스를 둘 수 있으니, 그 질의가 잦으면 인덱스를 두는지 본다.
    • 주문과 결제처럼 여러 데이터를 함께 고쳐야 하는 일에 트랜잭션이 필요한지 묻는다. 관계형은 이 일이 기본이다(53번(트랜잭션과 락)). "NoSQL에는 트랜잭션이 없다"도 틀린 말이다. MongoDB는 여러 문서에 걸친 트랜잭션을 지원한다. 다만 문서 하나 안에서 끝나게 설계하는 것을 기본으로 권한다.
    • 리뷰처럼 필드가 제각각이고 글 단위로 통째로 읽는 데이터는 문서 모델이 잘 맞을 수 있다. 한 서비스 안에서 데이터마다 다른 DB를 쓰는 답도 근거가 맞다면 괜찮다.
    • 질의를 먼저 정하지 않고 모델부터 고르는 답이면, 질의를 정하고 다시 고르게 한다.

    더 알아보기¶

    와이드 컬럼을 SQLite로 흉내 내기

    와이드 컬럼의 "파티션 키로 나누고 안은 정렬"은 기본 키가 (파티션 키, 정렬 키)인 표와 같다. SQLite의 WITHOUT ROWID 표는 행을 기본 키 차례로 B-Tree에 둔다(55번(인덱스와 실행 계획)). 그래서 한 고객의 주문은 붙어 있고 날짜 차례다. 진짜 와이드 컬럼 DB는 파티션마다 다른 서버에 두는 일까지 한다.

    CREATE TABLE orders_by_customer (customer INTEGER, day TEXT, order_id TEXT, product TEXT, PRIMARY KEY (customer, day, order_id)) WITHOUT ROWID;
INSERT INTO orders_by_customer VALUES (1, '10-01', 'o1', '키보드'), (1, '10-01', 'o2', '마우스'), (2, '10-02', 'o3', '키보드'), (1, '10-04', 'o5', '모니터');
EXPLAIN QUERY PLAN SELECT order_id FROM orders_by_customer WHERE customer = 1 ORDER BY day DESC, order_id DESC;
SELECT order_id FROM orders_by_customer WHERE customer = 1 ORDER BY day DESC, order_id DESC;

    (3, 0, 56, 'SEARCH orders_by_customer USING PRIMARY KEY (customer=?)')

    흩어 둔 데이터의 일관성

    많은 NoSQL은 데이터를 여러 서버에 복사해 둔다. 한 서버에 쓴 값이 다른 서버에 닿기 전에 읽으면 옛 값이 보일 수 있다. 잠시 뒤에는 모두 같아지는 이 성질을 최종 일관성(eventual consistency)이라 한다. 대신 한 서버가 멈춰도 읽고 쓸 수 있다. 어디까지 같아야 하는지를 DB마다, 질의마다 고르게 하는 경우도 많다. 여러 서버에 나눠 담는 일의 근본 문제는 70번(분산 시스템의 근본 문제)에서 다룬다.

    정리¶

    • 키-값은 키로만, 문서는 묶어 둔 문서로, 와이드 컬럼은 파티션과 그 안의 차례로 데이터를 둔다. 자주 함께 읽는 것을 미리 모아 두어 조인 없이 읽는다.
    • 어느 모델이 맞는지는 질의가 정한다. 질의를 먼저 정하고 그에 맞춰 데이터를 두며, 맞지 않는 질의는 전체를 읽는다.
    • 미리 모아 두면 같은 값을 여러 곳에 쓴다. 쓰기가 늘고, 바꿀 때 복사본이 어긋날 수 있다. 관계형과 섞어 쓰는 일도 흔하다.
