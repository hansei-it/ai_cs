    50. 데이터 모델링: 개체, 속성, 관계의 식별과 ERD 작성¶

    직접 AI 없이 직접 할 수 있어야 하는 항목

    데이터베이스를 만들기 전에 무엇을 어떤 표에 둘지 정한다. 이 설계가 틀리면 SQL을 아무리 잘 써도 담을 수 없는 데이터가 생긴다. 이 항목은 요구사항 문장에서 개체, 속성, 관계를 찾아 ERD로 그리고, 그것을 SQLite의 표로 옮긴다. 직접형 항목이므로 작은 요구사항을 직접 설계하고 데이터를 넣어 검증한다.

    이 항목에서 배우는 것¶

    • 요구사항 문장에서 개체, 속성, 관계를 찾아 ERD로 그릴 수 있다.
    • 관계의 수(1:1, 1:N, N:M)에 따라 외래 키와 연결 표를 정할 수 있다.
    • ERD를 CREATE TABLE로 옮기고, 데이터를 넣어 설계가 요구사항을 담는지 확인할 수 있다.

    1. 요구사항의 명사와 동사에서 개체, 속성, 관계를 찾는다¶

    • 개체는 따로 기억해야 하는 것(학생, 강좌, 교수)이다. 요구사항의 명사 가운데 저마다 여러 정보를 갖고 하나하나를 가려야 하는 것이 개체가 되고, 개체 하나가 표 하나가 된다.
    • 속성은 개체를 설명하는 값(이름, 학점)이고 표의 열이 된다. 하나하나를 가리는 속성(학번)이 기본 키(PK)다.
    • 관계는 개체 사이의 동사(수강한다, 맡는다)다. 한쪽 하나에 다른 쪽이 몇 개 이어지는지(1:1, 1:N, N:M)를 함께 적는데, 이것을 카디널리티라 한다. 이것을 그린 그림이 ERD(개체-관계 다이어그램)다.

    2. 관계의 수가 외래 키를 둘 자리를 정한다¶

    직접 해 보기관계를 어디에 담을까학생과 강좌의 관계를 담는 설계 세 가지를 골라 수강 신청을 하나씩 넣고, 표에 무엇이 남고 무엇이 덮이는지 본다
    새 창에서 크게 열기
    • 다른 표의 기본 키를 가리키는 열이 외래 키(FK)다. 1:N이면 N쪽 표에 1쪽의 키를 둔다. 강좌 표의 professor_id가 그렇다.
    • 학생과 강좌처럼 N:M이면 어느 한쪽에 둘 수 없다. 위젯에서 "학생 표에 강좌 번호"는 김하나의 두 번째 신청이 첫 번째를 덮었다. 두 번호를 함께 적는 연결 표(수강)를 따로 둔다.
    • 관계에만 붙는 속성(성적)은 연결 표에 둔다. 학생 표나 강좌 표에 두면 위젯처럼 신청과 함께 덮인다.

    3. ERD를 표로 옮기고, DBMS가 관계를 지키게 한다¶

    • 개체는 표로, 속성은 열로, 관계는 외래 키나 연결 표로 옮긴다. REFERENCES로 외래 키를 적어 두면, 없는 학생의 수강 같은 데이터를 DBMS가 막는다.
    • 단, REFERENCES를 적어 두었다고 DBMS가 늘 검사하는 것은 아니다. SQLite에서 어떻게 되는지 문제 1에서 본다.
    • 설계는 데이터를 넣어 검증한다. 요구사항의 문장마다 그 상황을 행으로 넣어 보고, 들어가야 할 것은 들어가고 막혀야 할 것은 막히는지 본다(직접 해보기).

    예측해 보기¶

    문제 1. 외래 키를 적은 표에 없는 학생의 수강을 넣는다. 한 번은 그대로, 한 번은 PRAGMA foreign_keys = ON; 뒤에 넣는다. 무엇이 출력될까?

    CREATE TABLE student (id INTEGER PRIMARY KEY, name TEXT NOT NULL);
CREATE TABLE enrollment (
  student_id INTEGER NOT NULL REFERENCES student(id),
  course_id INTEGER NOT NULL,
  grade TEXT,
  PRIMARY KEY (student_id, course_id)
);
INSERT INTO student VALUES (1, '김하나');
INSERT INTO enrollment VALUES (99, 101, 'A');
PRAGMA foreign_keys = ON;
INSERT INTO enrollment VALUES (98, 101, 'A');
SELECT * FROM enrollment;
    정답과 해설 
    IntegrityError (SQLITE_CONSTRAINT_FOREIGNKEY): FOREIGN KEY constraint failed
(99, 101, 'A')

    처음 넣은 99번 학생의 수강은 오류 없이 들어갔다. 검사가 꺼져 있었기 때문이다. 검사를 켠 뒤의 98번은 막혔지만, 먼저 들어간 99번 행은 그대로 남는다. 켜는 것을 잊은 사이에 들어간 잘못된 행은 나중에 켜도 지워지지 않는다. PRAGMA foreign_key_check;로 이런 행을 찾을 수 있다.

    SQLite는 외래 키 검사가 기본으로 꺼져 있고, 켜는 설정은 연결마다 따로다. 그래서 DB에 연결할 때마다 PRAGMA foreign_keys = ON;을 실행한다. MySQL(InnoDB)은 켜지 않아도 검사하지만, 8.4까지는 위처럼 열 정의 안에 쓴 REFERENCES를 오류 없이 무시한다(9.0부터는 이 형식도 검사한다고 릴리스 노트에 적혀 있다). 이 PC의 MySQL 8.4.11에서 위 표를 그대로 만들면 없는 학생의 수강이 들어갔고, FOREIGN KEY (student_id) REFERENCES student(id)처럼 따로 적으니 ERROR 1452로 막혔다. DBMS가 바뀌면 막혀야 할 데이터를 넣어 다시 확인한다.

    문제 2. 문제 1의 수강 표에 김하나가 같은 강좌를 두 번 신청한다. 무엇이 출력될까? 재수강을 허락하려면 설계를 어떻게 바꿔야 할까?

    DELETE FROM enrollment;
INSERT INTO enrollment VALUES (1, 101, 'C');
INSERT INTO enrollment VALUES (1, 101, 'A');
SELECT * FROM enrollment;
    정답과 해설 
    IntegrityError (SQLITE_CONSTRAINT_PRIMARYKEY): UNIQUE constraint failed: enrollment.student_id, enrollment.course_id
(1, 101, 'C')

    기본 키가 (학생, 강좌)라서 같은 짝은 한 번만 들어간다. "같은 강좌를 두 번 신청할 수 없다"는 규칙을 기본 키가 지킨 것이다. 재수강을 허락하려면 학기 열(term)을 더하고 기본 키를 (학생, 강좌, 학기)로 바꾼다. 기본 키를 무엇으로 하느냐가 곧 업무 규칙이다.

    문제 3. 요구사항이 "강좌 하나를 교수 여럿이 함께 맡을 수 있다"로 바뀌었다. 강좌 표의 professor_id 열로 충분할까?

    정답과 해설

    충분하지 않다. 교수와 강좌가 N:M이 되었으므로, 강좌 표의 열 하나에는 교수를 한 명만 적을 수 있다. 위젯의 "강좌 표에 학생 번호"처럼 둘째 교수가 첫째를 덮는다. course_professor(course_id, professor_id) 같은 연결 표를 두고, 강좌 표의 professor_id는 뺀다. 요구사항의 "한 명", "여러"가 바뀌면 표가 바뀐다.

    직접 해보기¶

    실습: 동아리 관리 DB 설계하기

    요구사항은 다음과 같다.

    • 학생은 여러 동아리에 가입할 수 있고, 동아리에는 여러 학생이 있다. 가입할 때 가입일을 남긴다.
    • 동아리에는 이름과 동아리방이 있다. 동아리 이름은 겹치지 않는다.

    • 동아리마다 회장이 한 명 있고, 회장은 그 동아리에 가입한 학생이어야 한다.

    • 개체, 속성, 관계와 관계의 수를 적고 ERD를 그린다. 종이에 그려도 된다.

    • 명령 프롬프트에서 python -m sqlite3 club.db를 열고, PRAGMA foreign_keys = ON;부터 실행한 뒤 표를 만든다.
    • 학생 셋과 동아리 셋, 가입 몇 건을 넣는다. 같은 동아리에 두 번 가입, 없는 학생의 가입, 같은 이름의 동아리가 막히는지 본다.
    • 회장이 그 동아리에 가입하지 않은 동아리를 찾는 SELECT를 쓴다.
    확인할 점

    개체는 학생과 동아리, 관계는 가입(N:M, 속성 가입일)과 회장(동아리 하나에 학생 한 명)이다. 설계의 한 예와 시험 데이터다.

    PRAGMA foreign_keys = ON;
CREATE TABLE student (id INTEGER PRIMARY KEY, name TEXT NOT NULL);
CREATE TABLE club (
  id INTEGER PRIMARY KEY,
  name TEXT NOT NULL UNIQUE,
  room TEXT,
  president_id INTEGER REFERENCES student(id)
);
CREATE TABLE membership (
  student_id INTEGER NOT NULL REFERENCES student(id),
  club_id INTEGER NOT NULL REFERENCES club(id),
  joined_on TEXT NOT NULL,
  PRIMARY KEY (student_id, club_id)
);
INSERT INTO student VALUES (1, '김하나'), (2, '이두리'), (3, '박세나');
INSERT INTO club VALUES (10, '사진', 'B103', 1), (20, '밴드', 'B201', 2), (30, '바둑', 'B105', 3);
INSERT INTO membership VALUES (1, 10, '2026-03-02'), (2, 10, '2026-03-05'), (2, 20, '2026-03-02');
INSERT INTO membership VALUES (1, 10, '2026-04-01');
INSERT INTO membership VALUES (9, 20, '2026-04-01');
INSERT INTO club VALUES (40, '사진', 'B107', 2);
SELECT c.name, s.name FROM club c JOIN student s ON s.id = c.president_id
 WHERE NOT EXISTS (SELECT 1 FROM membership m WHERE m.student_id = c.president_id AND m.club_id = c.id);


    IntegrityError (SQLITE_CONSTRAINT_PRIMARYKEY): UNIQUE constraint failed: membership.student_id, membership.club_id
IntegrityError (SQLITE_CONSTRAINT_FOREIGNKEY): FOREIGN KEY constraint failed
IntegrityError (SQLITE_CONSTRAINT_UNIQUE): UNIQUE constraint failed: club.name
('바둑', '박세나')
    • 막혀야 할 셋(같은 동아리에 두 번, 없는 학생, 같은 이름)이 기본 키, 외래 키, UNIQUE로 막혔다.
    • 바둑 동아리의 회장 박세나는 가입하지 않았는데도 들어갔다. 이 설계는 "회장은 회원"이라는 규칙을 지키지 못하고, 4의 질의로 찾아야만 한다. DBMS가 막게 하는 방법은 "더 알아보기"에 있다.
    • 가입일을 학생 표나 동아리 표에 두었다면, 한 학생이 여러 동아리에 가입할 때 하나만 남는다(위젯).

    AI와 함께 확인하기¶

    AI 활용 과제: AI가 만든 설계를 데이터로 시험하기

    1. AI에게 실습의 요구사항 세 줄을 주고 "SQLite용 CREATE TABLE을 만들어 줘"라고 한다.
    2. 실행하기 전에, 받은 설계가 요구사항의 문장마다 그 상황을 담는지 적는다.
    3. 실습의 club.db와 표 이름이 겹치지 않게 새 파일(python -m sqlite3 club_ai.db)에서 받은 SQL을 실행한다. 실습의 시험 데이터를 넣어 들어가야 할 것과 막혀야 할 것을 확인하고, 다른 점을 AI에게 보여 주고 고치게 한다.
    확인할 점
    • N:M을 1:N으로 만든 설계가 흔하다. 학생 표에 동아리 번호 열 하나를 두면 한 학생의 둘째 가입이 첫째를 덮고, 동아리 표에 student_id 열 하나를 두면 한 동아리의 둘째 회원이 첫째를 덮는다(위젯의 "학생 표에 강좌 번호", "강좌 표에 학생 번호"와 같다).
    • REFERENCES는 적었지만 PRAGMA foreign_keys = ON;이 없는 코드가 흔하다. SQLite에서는 없는 학생의 가입이 그대로 들어간다(문제 1).
    • "회장은 회원"이라는 규칙은 대개 빠진다. 설명만 붙이고 표로는 지키지 않는다면, 무엇으로 지킬지(질의로 찾기, 더 알아보기의 복합 외래 키, 프로그램에서 검사) 정하게 한다.

    더 알아보기¶

    '회장은 그 동아리의 회원'을 DBMS가 지키게 하기

    회장 열을 (회장 번호, 동아리 번호)의 짝으로 보면, 그 짝이 가입 표에 있어야 한다는 외래 키로 적을 수 있다. 외래 키가 여러 열을 함께 가리키는 복합 외래 키다. 동아리가 먼저 있어야 가입할 수 있으므로, 동아리는 회장 없이(NULL) 만든 뒤 가입하고 나서 회장을 정한다. 외래 키의 열 가운데 NULL이 있으면 SQLite는 검사하지 않는다.

    PRAGMA foreign_keys = ON;
CREATE TABLE student (id INTEGER PRIMARY KEY, name TEXT NOT NULL);
CREATE TABLE club (
  id INTEGER PRIMARY KEY,
  name TEXT NOT NULL UNIQUE,
  president_id INTEGER,
  FOREIGN KEY (president_id, id) REFERENCES membership(student_id, club_id)
);
CREATE TABLE membership (
  student_id INTEGER NOT NULL REFERENCES student(id),
  club_id INTEGER NOT NULL REFERENCES club(id),
  joined_on TEXT NOT NULL,
  PRIMARY KEY (student_id, club_id)
);
INSERT INTO student VALUES (1, '김하나'), (3, '박세나');
INSERT INTO club (id, name) VALUES (10, '사진'), (30, '바둑');
INSERT INTO membership VALUES (1, 10, '2026-03-02');
UPDATE club SET president_id = 1 WHERE id = 10;
UPDATE club SET president_id = 3 WHERE id = 30;
SELECT * FROM club;


    IntegrityError (SQLITE_CONSTRAINT_FOREIGNKEY): FOREIGN KEY constraint failed
(10, '사진', 1)
(30, '바둑', None)

    가입한 김하나는 사진 동아리의 회장이 되고, 가입하지 않은 박세나는 바둑 동아리의 회장이 되지 못했다. 다만 회장이 동아리를 탈퇴하려 하면 이번에는 가입 표의 행을 지울 수 없게 막힌다. 규칙을 DB에 넣을수록 데이터는 안전하지만 바꾸는 차례가 까다로워진다.

    ERD를 그리는 여러 방법

    이 항목의 그림은 선 끝에 세 갈래(여럿), 동그라미(없어도 됨), 두 줄(꼭 하나)을 그리는 까마귀발 표기다. 데이터베이스 설계 도구와 현업 문서에서 많이 쓴다. 교재에서는 개체를 사각형, 관계를 마름모, 속성을 타원으로 그리는 첸(Chen) 표기도 자주 나온다. 표기는 달라도 찾는 것(개체, 속성, 관계와 그 수)은 같다. 도구로는 표를 만드는 SQL에서 ERD를 그려 주는 것도 많아서, AI가 만든 CREATE TABLE을 그림으로 바꿔 요구사항과 견주기 좋다.

    정리¶

    • 요구사항의 명사에서 개체와 속성을, 동사에서 관계를 찾는다. 관계마다 1:1, 1:N, N:M을 정해 ERD로 그린다.
    • 1:N은 N쪽 표에 외래 키를, N:M은 두 번호를 함께 적는 연결 표를 둔다. 관계에만 붙는 속성은 연결 표에 둔다.
    • 표로 옮긴 뒤에는 데이터를 넣어 검증한다. SQLite는 PRAGMA foreign_keys = ON;을 켜야 외래 키를 검사한다. 기본 키와 제약이 곧 업무 규칙이다.
