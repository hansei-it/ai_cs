    52. SQL 작성과 검증: 조인, 집계, 서브쿼리. AI가 만든 쿼리의 결과가 맞는지 확인하기¶

    직접 AI 없이 직접 할 수 있어야 하는 항목

    SQL은 틀려도 오류 없이 결과를 낸다. 행 하나가 빠지거나 합계가 두 배가 되어도 겉보기에는 멀쩡하다. AI가 만든 쿼리도 마찬가지라서, 결과가 맞는지 확인하는 힘이 SQL을 쓰는 힘만큼 중요하다. 이 항목은 조인과 집계가 틀리는 대표적인 길을 이 PC의 SQLite에서 직접 일으켜 보고, 결과를 검증하는 방법을 익힌다. 직접형 항목이므로 질의를 직접 쓰고 다른 방법으로 대조한다.

    이 항목에서 배우는 것¶

    • INNER JOIN과 LEFT JOIN의 결과를 예측하고, 조건을 ON과 WHERE 중 어디에 둘지 고를 수 있다.
    • GROUP BY, HAVING, 집계 함수가 NULL과 빈 묶음을 어떻게 다루는지 설명할 수 있다.
    • 결과를 다른 방법으로 쓴 질의와 대조하고, 경계 사례로 시험해 틀린 질의를 찾을 수 있다.

    이 항목의 예제는 아래 표로 한다. 명령 프롬프트에서 python -m sqlite3 school52.db를 열고 붙여 넣는다. 수강이 없는 학생(최네오), 수강생이 없는 강좌(컴퓨터구조), 아직 점수가 없는 수강(박세나의 데이터베이스)을 일부러 넣었다.

    CREATE TABLE student (id INTEGER PRIMARY KEY, name TEXT NOT NULL, dept TEXT NOT NULL, mentor_id INTEGER REFERENCES student(id));
CREATE TABLE course (id INTEGER PRIMARY KEY, title TEXT NOT NULL, credit INTEGER NOT NULL);
CREATE TABLE enrollment (student_id INTEGER NOT NULL REFERENCES student(id), course_id INTEGER NOT NULL REFERENCES course(id),
                         score INTEGER, PRIMARY KEY (student_id, course_id));
CREATE TABLE club_member (student_id INTEGER NOT NULL REFERENCES student(id), club TEXT NOT NULL, PRIMARY KEY (student_id, club));
INSERT INTO student VALUES (1, '김하나', '컴퓨터공학', NULL), (2, '이두리', '경영', 1), (3, '박세나', '컴퓨터공학', 1), (4, '최네오', '경영', NULL);
INSERT INTO course VALUES (101, '데이터베이스', 3), (102, '네트워크', 3), (103, '운영체제', 3), (104, '컴퓨터구조', 2);
INSERT INTO enrollment VALUES (1, 101, 90), (1, 102, 85), (2, 102, 70), (3, 101, NULL), (3, 103, 95);
INSERT INTO club_member VALUES (1, '사진'), (1, '밴드'), (3, '사진');

    1. 조인은 짝을 맞춰 행을 잇고, 짝 없는 행은 종류에 따라 버리거나 남긴다¶

    직접 해 보기조인 결과에서 누가 빠지나학생과 수강 표를 INNER, LEFT, 조건을 WHERE와 ON에 둔 LEFT, COUNT(*)와 COUNT(열)로 묶어 보고, 결과 행과 빠진 학생을 본다
    새 창에서 크게 열기
    • INNER JOIN은 양쪽에 짝이 있는 행만 남긴다. 수강이 없는 최네오는 결과에서 사라진다. "학생마다"를 묻는 질의라면 틀린 답이다.
    • LEFT JOIN은 왼쪽 표의 행을 모두 남기고, 짝이 없으면 오른쪽 열을 NULL로 채운다.
    • LEFT JOIN을 했어도 오른쪽 열에 e.score >= 80처럼 NULL이면 참이 되지 않는 조건을 WHERE에 두면, NULL로 채운 행이 걸러져 INNER JOIN에 같은 조건을 건 것과 같아진다. 짝을 고르는 조건은 ON에 둔다(위젯의 "LEFT + WHERE 점수"와 "LEFT + ON 점수"). 거꾸로 WHERE e.student_id IS NULL은 짝이 없는 행만 남길 때 쓴다(직접 해보기 4).

    2. SQL의 결과는 쓴 차례가 아니라 처리 차례를 따른다¶

    SELECT s.name, AVG(e.score)
  FROM student s LEFT JOIN enrollment e ON e.student_id = s.id
 WHERE e.score IS NOT NULL
 GROUP BY s.id
HAVING AVG(e.score) >= 80
 ORDER BY AVG(e.score) DESC;

    ('박세나', 95.0)
('김하나', 87.5)
    • WHERE는 묶기 전의 행을, HAVING은 GROUP BY로 묶은 뒤의 묶음을 거른다. 이 차례는 결과가 그렇게 처리한 것과 같다는 뜻이고, 실제로 어느 표부터 읽을지는 DBMS가 정한다(55번(인덱스와 실행 계획)의 실행 계획).
    • 집계 함수는 NULL을 건너뛴다. COUNT(*)는 행을, COUNT(열)은 NULL이 아닌 값을 센다. LEFT JOIN 뒤에 COUNT(*)를 쓰면 짝이 없는 학생도 1이 된다(위젯). 더할 값이 하나도 없으면 SUM은 0이 아니라 NULL이다(3절의 최네오).
    • AVG도 NULL을 빼고 나눈다. 점수가 없는 수강을 0점으로 볼지 뺄지는 질의를 쓰는 사람이 정해야 한다(문제 2).

    3. 결과는 다른 방법과 경계 사례로 검증한다¶

    SELECT s.name, SUM(e.score) FROM student s
  JOIN enrollment e ON e.student_id = s.id
  JOIN club_member c ON c.student_id = s.id
 GROUP BY s.id ORDER BY s.id;
SELECT s.name, (SELECT SUM(score) FROM enrollment WHERE student_id = s.id),
       (SELECT COUNT(*) FROM club_member WHERE student_id = s.id)
  FROM student s ORDER BY s.id;

    ('김하나', 350)
('박세나', 95)
('김하나', 175, 2)
('이두리', 70, 0)
('박세나', 95, 1)
('최네오', None, 0)
    • 첫 질의는 김하나의 점수 합계를 350으로 냈다. 수강 2건과 동아리 2개를 한 번에 이어 행이 넷이 되었기 때문이다. 수강과 동아리를 각각 서브쿼리로 따로 계산한 둘째 질의가 맞다. 이두리와 최네오가 첫 결과에서 빠진 것도 INNER JOIN 탓이다.
    • 결과를 믿기 전에 확인한다. 행 수를 먼저 예측한다. 작은 데이터로 손으로 계산해 본다. 짝 없는 행, NULL, 중복이 든 경계 사례를 넣는다. 다른 방법(조인 대 서브쿼리)으로 한 번 더 써서 EXCEPT(앞 결과에서 뒤 결과에 있는 행을 뺀다)로 대조한다. EXCEPT는 같은 행이 여러 번 나와도 하나로 쳐서, 집계하지 않은 결과라면 조인이 행을 부풀려도 놓치므로 행 수도 견준다(직접 해보기).

    예측해 보기¶

    문제 1. 누구의 멘토도 아닌 학생을 두 가지로 찾는다. 무엇이 출력될까?

    SELECT name FROM student WHERE id NOT IN (SELECT mentor_id FROM student);
SELECT name FROM student s WHERE NOT EXISTS (SELECT 1 FROM student m WHERE m.mentor_id = s.id);
    정답과 해설 
    ('이두리',)
('박세나',)
('최네오',)

    세 줄은 모두 둘째 질의의 결과이고, 첫 질의는 한 줄도 내지 않았다. 서브쿼리의 결과에 NULL(김하나와 최네오의 멘토)이 섞여 있어서, 2 NOT IN (NULL, 1, 1, NULL)은 "2는 NULL과 다른가?"를 알 수 없어 참이 되지 않는다. NOT IN의 목록에 NULL이 하나라도 있으면 결과가 비어 버린다. NOT EXISTS를 쓰거나 WHERE mentor_id IS NOT NULL로 NULL을 뺀다.

    문제 2. 강좌별로 행 수, 점수 수, 평균 점수를 구한다. 무엇이 출력될까?

    SELECT c.title, COUNT(*), COUNT(e.score), AVG(e.score)
  FROM course c JOIN enrollment e ON e.course_id = c.id
 GROUP BY c.id ORDER BY c.id;
    정답과 해설 
    ('데이터베이스', 2, 1, 90.0)
('네트워크', 2, 2, 77.5)
('운영체제', 1, 1, 95.0)

    데이터베이스는 수강이 둘인데 점수는 하나(90)뿐이라 평균이 90.0이다. NULL을 0으로 보면 45.0이다. 어느 쪽이 맞는지는 "아직 채점하지 않은 수강"을 어떻게 볼지에 달렸다. 수강생이 없는 컴퓨터구조는 INNER JOIN이라 아예 빠졌다.

    문제 3. 평균 점수가 80 이상인 학생을 찾는다. 첫 질의는 WHERE, 둘째는 HAVING에 조건을 두었다. 무엇이 출력될까?

    SELECT s.name, AVG(e.score) FROM student s JOIN enrollment e ON e.student_id = s.id WHERE AVG(e.score) >= 80 GROUP BY s.id;
SELECT s.name, AVG(e.score) FROM student s JOIN enrollment e ON e.student_id = s.id GROUP BY s.id HAVING AVG(e.score) >= 80 ORDER BY s.id;
    정답과 해설 
    OperationalError (SQLITE_ERROR): misuse of aggregate: AVG()
('김하나', 87.5)
('박세나', 95.0)

    WHERE는 묶기 전에 행 하나씩 거르므로 묶음의 평균을 알 수 없어 오류가 난다(그림의 차례). 집계(AVG, COUNT)로 거르려면 HAVING에 쓴다. 박세나의 평균은 NULL을 뺀 95.0이다. 오류가 나는 질의는 차라리 낫다. 고치게 되기 때문이다. 문제 1처럼 조용히 틀린 결과를 내는 질의가 더 위험하다.

    직접 해보기¶

    실습: 질의를 쓰고 다른 방법으로 대조하기

    school52.db에서 아래 넷을 질의로 쓴다. 실행하기 전에 결과의 행 수와 값을 손으로 먼저 적는다.

    1. 학과별 학생 수
    2. 강좌별 수강생 수. 수강생이 없는 강좌는 0으로 나온다.
    3. 점수가 있는 수강만으로 평균을 내어, 평균 80 이상인 학생과 그 평균
    4. 어떤 강좌도 듣지 않는 학생

    다 썼으면 2와 4를 다른 방법(조인 대 서브쿼리)으로 한 번 더 쓰고, 두 결과를 EXCEPT로 양쪽에서 대조하고 행 수도 견준다. EXCEPT는 양쪽 다 0행, 행 수는 같아야 같다.

    확인할 점

    한 예와 이 PC의 결과다. 마지막 세 줄은 2를 두 방법으로 쓴 결과를 양쪽에서 EXCEPT로 대조하고 행 수를 견준 것이다.

    SELECT dept, COUNT(*) FROM student GROUP BY dept ORDER BY dept;
SELECT c.title, COUNT(e.student_id) FROM course c LEFT JOIN enrollment e ON e.course_id = c.id GROUP BY c.id ORDER BY c.id;
SELECT s.name, AVG(e.score) FROM student s JOIN enrollment e ON e.student_id = s.id
 WHERE e.score IS NOT NULL GROUP BY s.id HAVING AVG(e.score) >= 80 ORDER BY s.id;
SELECT name FROM student s WHERE NOT EXISTS (SELECT 1 FROM enrollment e WHERE e.student_id = s.id);
SELECT s.name FROM student s LEFT JOIN enrollment e ON e.student_id = s.id WHERE e.student_id IS NULL;
CREATE VIEW by_join AS SELECT c.id, COUNT(e.student_id) AS n FROM course c LEFT JOIN enrollment e ON e.course_id = c.id GROUP BY c.id;
CREATE VIEW by_sub AS SELECT c.id, (SELECT COUNT(*) FROM enrollment WHERE course_id = c.id) AS n FROM course c;
SELECT COUNT(*) FROM (SELECT * FROM by_join EXCEPT SELECT * FROM by_sub);
SELECT COUNT(*) FROM (SELECT * FROM by_sub EXCEPT SELECT * FROM by_join);
SELECT (SELECT COUNT(*) FROM by_join), (SELECT COUNT(*) FROM by_sub);

    ('경영', 2)
('컴퓨터공학', 2)
('데이터베이스', 2)
('네트워크', 2)
('운영체제', 1)
('컴퓨터구조', 0)
('김하나', 87.5)
('박세나', 95.0)
('최네오',)
('최네오',)
(0,)
(0,)
(4, 4)
    • 2에서 INNER JOIN을 쓰면 컴퓨터구조가 빠지고, LEFT JOIN에 COUNT(*)를 쓰면 컴퓨터구조가 1이 된다. 수강생이 없는 강좌를 일부러 넣어 두었기 때문에 이 실수가 드러난다.
    • 4의 두 방법이 같은 답을 냈다. NOT IN (SELECT student_id FROM enrollment)도 이 데이터에서는 맞지만, student_id에 NULL이 들어올 수 있는 열이라면 문제 1처럼 비어 버린다.
    • 경계 사례가 없는 데이터로 시험하면 틀린 질의도 맞는 답을 낸다. 데이터를 만들 때 "짝 없는 행, NULL, 중복"을 하나씩 넣는다.

    AI와 함께 확인하기¶

    AI 활용 과제: AI가 만든 집계 쿼리 검증하기

    1. 예제 데이터의 CREATE TABLE 문장 넷을 AI에게 주고 "강좌별 수강생 수와 평균 점수를 구하는 SQL. 수강생이 없는 강좌도 나오게"라고 한다.
    2. 실행하기 전에 강좌 넷의 수강생 수와 평균을 손으로 적는다. 점수가 없는 수강을 어떻게 볼지도 정한다.
    3. 받은 SQL을 실행해 손으로 적은 값과 대조한다. 다르면 어느 행이 다른지 보여 주고 고치게 한다.
    확인할 점
    • 손으로 적은 값은 데이터베이스 2명(평균 90.0, 점수가 있는 1명 기준), 네트워크 2명(77.5), 운영체제 1명(95.0), 컴퓨터구조 0명(평균 NULL)이다.
    • INNER JOIN이면 컴퓨터구조가 빠진다. LEFT JOIN에 COUNT(*)를 쓰면 컴퓨터구조가 0이 아니라 1명이 된다(위젯).
    • 평균에 대해 아무 말 없이 AVG(score)만 쓰는 답이 많다. 데이터베이스가 90.0인 까닭(NULL은 빠진다)을 설명하게 하고, 0점으로 볼지 정한다. 0점으로 볼 때 AVG(COALESCE(e.score, 0))만 쓰면, LEFT JOIN이 NULL로 채운 컴퓨터구조의 행까지 0점 하나로 세어 평균이 0.0이 된다(이 PC에서 확인). 짝이 있는 행만 0점으로 바꾸려면 AVG(CASE WHEN e.student_id IS NOT NULL THEN COALESCE(e.score, 0) END)라야 데이터베이스 45.0, 컴퓨터구조 NULL이 나온다.
    • 질의가 길어지면 AI에게 "이 질의가 틀린 답을 낼 데이터를 만들어 줘"라고 시켜 경계 사례를 늘린다.

    더 알아보기¶

    NULL과 견주면 참도 거짓도 아니다

    SQL의 조건은 참, 거짓 말고 하나가 더 있다. NULL과 견주면 결과는 "알 수 없음"(UNKNOWN)이고, WHERE와 ON은 참인 행만 통과시킨다. score = NULL은 늘 알 수 없음이라 아무 행도 고르지 못한다. NULL은 IS NULL, IS NOT NULL로 가린다. 아래 셋째 줄의 1은 참이고(SQLite는 참을 1, 거짓을 0으로 낸다), None은 알 수 없음이다. 위젯의 "LEFT + WHERE 점수"와 문제 1이 모두 이 규칙에서 나온다.

    SELECT COUNT(*) FROM enrollment WHERE score = NULL;
SELECT COUNT(*) FROM enrollment WHERE score IS NULL;
SELECT NULL = NULL, NULL IS NULL, 2 NOT IN (1, NULL);

    (0,)
(1,)
(None, 1, None)
    서브쿼리와 CTE

    질의 안의 질의(서브쿼리)는 3절처럼 행마다 값을 하나 계산하거나, IN, EXISTS로 조건을 만들거나, FROM 안에서 표처럼 쓴다. 길어지면 WITH 절(CTE)로 이름을 붙여 위에서 아래로 읽히게 쓴다. 단계마다 이름이 있으면 그 단계만 따로 실행해 행 수를 확인하기도 쉽다.

    WITH scored AS (SELECT student_id, AVG(score) AS avg FROM enrollment WHERE score IS NOT NULL GROUP BY student_id)
SELECT s.name, a.avg FROM scored a JOIN student s ON s.id = a.student_id WHERE a.avg >= 80 ORDER BY s.id;

    ('김하나', 87.5)
('박세나', 95.0)
    SQLite가 오류 없이 받아 주는 것

    SQLite는 다른 DBMS가 오류로 막는 질의 몇 가지를 받아 준다. 처리 차례로는 WHERE가 SELECT보다 먼저라서 SELECT에서 붙인 별명을 모르는 것이 맞는데, SQLite는 WHERE big > 20처럼 별명을 써도 돌린다. GROUP BY dept로 묶고 묶지 않은 name을 고르면, 묶음 하나에 이름이 여럿인데도 그중 하나를 골라 낸다. 이 PC의 MySQL 8.4(기본 설정)는 두 질의를 모두 오류(ERROR 1054, ERROR 1055)로 막았다. "오류 없이 틀린 결과"가 되기 쉬우니, 묶지 않은 열은 집계로 감싸서 쓴다.

    SELECT name, id * 10 AS big FROM student WHERE big > 20;
SELECT dept, name, COUNT(*) FROM student GROUP BY dept ORDER BY dept;

    ('박세나', 30)
('최네오', 40)
('경영', '이두리', 2)
('컴퓨터공학', '김하나', 2)

    정리¶

    • INNER JOIN은 짝이 있는 행만, LEFT JOIN은 왼쪽 행을 모두 남긴다. 짝을 고르는 조건은 ON에, 결과를 거르는 조건은 WHERE에 둔다.
    • SQL의 결과는 FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY 차례로 처리한 것과 같다(실제 읽는 차례는 DBMS가 정한다). 집계 함수는 NULL을 건너뛰고, NOT IN은 목록의 NULL 하나로 비어 버린다.
    • 오류 없이 틀린 결과가 가장 위험하다. 행 수를 예측하고, 경계 사례를 넣고, 다른 방법으로 쓴 질의와 EXCEPT와 행 수로 대조한다.
