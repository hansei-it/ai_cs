    49. 파일 시스템 대비 관계형 데이터베이스(RDBMS)의 장점과 데이터 독립성¶

    원리 동작을 예측하고 이상을 알아챌 수 있어야 하는 항목

    학생 명단이나 주문 내역은 파일에 바로 써도 된다. 그런데 그 데이터를 쓰는 프로그램이 늘고 여럿이 동시에 고치기 시작하면 문제가 생긴다. 이 항목은 파일에 직접 둘 때 생기는 문제와, 데이터베이스 관리 시스템(DBMS)이 그 일을 맡으면 무엇이 달라지는지 이 PC에서 확인한다. 섹션 6의 예제는 Python에 든 SQLite로 하고, 락과 격리 수준(53·54번)만 MySQL을 쓴다. SQL은 설치 없이 python -m sqlite3로 실행한다(직접 해보기).

    이 항목에서 배우는 것¶

    • 파일에 직접 둘 때 생기는 중복, 불일치, 동시 수정의 문제를 설명할 수 있다.
    • DBMS가 맡는 일(동시 수정, 규칙 검사, 복구, 권한)을 말할 수 있다.
    • 데이터 독립성을 예로 설명하고, 저장 방식이 바뀔 때 어떤 프로그램이 깨지는지 예측할 수 있다.

    1. 파일에 두면 프로그램마다 모양을 알고, 같은 데이터가 여러 곳에 생긴다¶

    • 파일에 직접 저장하면 읽는 프로그램이 파일의 모양(열의 차례, 구분자)을 알아야 한다. 프로그램이 늘수록 그 모양에 기댄 코드가 곳곳에 퍼진다.
    • 프로그램마다 자기 파일을 두면 같은 학생의 이름과 학과가 여러 파일에 들어간다(중복). 하나만 고치면 서로 다른 값이 남는다(불일치).
    • DBMS는 데이터를 한곳에 두고, 프로그램은 SQL로 표와 열의 이름만 써서 묻는다. 데이터를 행과 열로 된 표에 두고 표끼리는 키 값으로 잇는 것이 관계형 DBMS(RDBMS)다.

    2. 동시에 고칠 때 DBMS는 한쪽을 기다리게 한다¶

    • 파일의 값을 읽고, 바꾸고, 다시 쓰는 사이에 다른 프로세스가 끼어들면 한쪽의 수정이 사라진다(갱신 손실, 34번(스레드 동기화)의 경쟁 상태). 이 PC에서 얼마나 잃는지는 문제 2에서 본다.
    • DBMS는 UPDATE 하나를 읽기와 쓰기까지 한 덩어리(트랜잭션)로 처리하고, 고치는 동안 잠가 다른 쪽을 기다리게 한다. 다만 SELECT로 읽어 프로그램에서 계산한 값을 UPDATE로 쓰면, 그 사이에 끼어든 수정은 DBMS에서도 사라진다(53번(트랜잭션과 락)).
    • 규칙도 DBMS가 지킨다. "잔액은 0 이상" 같은 제약을 표에 적어 두면 어느 프로그램이 넣든 어기는 값은 거절한다(문제 1). 고장 뒤의 복구(58번(백업과 복구))도 DBMS가 맡는다. 사용자별 권한은 MySQL 같은 서버형 DBMS의 일이고, 파일 하나인 SQLite는 운영체제의 파일 권한에 맡긴다.

    3. 저장 방식이 바뀌어도 SQL 프로그램은 그대로다¶

    직접 해 보기저장 방식을 바꾸면 어느 프로그램이 멈출까저장 방식 바꾸기(열 추가, 저장 형식, 표 나누기)를 골라, CSV를 위치로 읽는 프로그램과 SQL 프로그램을 실제로 돌린 결과를 견준다
    새 창에서 크게 열기
    • 저장하는 모양이 바뀌어도 프로그램을 고치지 않아도 되는 성질이 데이터 독립성이다. 파일 안의 배치나 인덱스처럼 저장하는 방법이 바뀌어도 프로그램이 그대로인 것이 물리적 독립성, 표를 나누거나 열을 더하는 것처럼 표의 구성이 바뀌어도 프로그램이 그대로인 것이 논리적 독립성이다.
    • 위젯의 CSV 프로그램은 "셋째 칸이 학과"라는 모양에 기대고 있어서, 열 하나를 끼우자 틀린 값을 냈다. SQL 프로그램은 열의 이름으로 묻기 때문에 그대로 돌았다.
    • SQL이라도 SELECT *의 결과를 위치로 풀거나 INSERT에 열 이름을 쓰지 않으면, 위젯처럼 열이 늘자 멈춘다. 쓰는 열의 이름을 적는다. 열의 이름이 바뀌면 어떻게 될지는 문제 3에서 본다.

    예측해 보기¶

    문제 1. 잔액이 0 이상이어야 한다는 제약을 둔 표에서 300원 있는 계좌의 잔액을 500원 줄인다. 무엇이 출력될까?

    CREATE TABLE account (id INTEGER PRIMARY KEY, balance INTEGER NOT NULL CHECK (balance >= 0));
INSERT INTO account VALUES (1, 300);
UPDATE account SET balance = balance - 500 WHERE id = 1;
SELECT * FROM account;
    정답과 해설 
    IntegrityError (SQLITE_CONSTRAINT_CHECK): CHECK constraint failed: balance >= 0
(1, 300)

    UPDATE는 제약에 걸려 거절되고, 잔액은 300 그대로다. 규칙이 표에 있으므로 어느 프로그램이 이 표를 고치든 똑같이 막힌다. 파일이라면 이 검사를 그 파일을 고치는 모든 프로그램이 저마다 해야 하고, 하나라도 빠뜨리면 -200이 저장된다.

    문제 2. 두 프로세스가 같은 잔액(처음 0)에 1을 1,000번씩 더한다. 한 번은 텍스트 파일의 값을 읽고 써서, 한 번은 SQLite의 UPDATE account SET balance = balance + 1로 더한다. 마지막 값은 각각 얼마쯤일까?

    정답과 해설

    파일은 2,000보다 한참 작고, SQLite는 정확히 2,000이다. 이 PC에서 5번 실행하니 파일은 1,040~1,122, SQLite는 매번 2,000이었다. 두 프로세스가 거의 같은 때에 돌면서 2절 그림의 왼쪽 같은 일이 계속 일어나 절반 가까이를 잃었다. SQLite는 한쪽이 고치는 동안 다른 쪽이 기다렸다가 새 값을 읽는다. 측정 프로그램은 "더 알아보기"에 있다.

    문제 3. 이번에는 열을 더하지 않고 학년 열의 이름을 year에서 grade_year로 바꾼다. SELECT *를 넷으로 푸는 코드와 열 이름을 쓴 질의는 각각 어떻게 될까?

    import sqlite3

con = sqlite3.connect(":memory:")
con.execute("CREATE TABLE student (id INTEGER PRIMARY KEY, name TEXT, dept TEXT, year INTEGER)")
con.execute("INSERT INTO student VALUES (2, '이두리', '경영', 1)")
con.execute("ALTER TABLE student RENAME COLUMN year TO grade_year")
sid, name, dept, year = con.execute("SELECT * FROM student").fetchone()
print(name, year)
print(con.execute("SELECT name, year FROM student").fetchone())
    정답과 해설 
    이두리 1

    이번에는 SELECT *를 푸는 쪽이 돌고, 열 이름을 쓴 질의가 sqlite3.OperationalError: no such column: year로 멈춘다. SELECT *는 열을 차례대로 돌려줄 뿐이라 이름이 바뀌어도 넷으로 풀린다. 위치에 기댄 코드는 열이 늘거나 차례가 바뀔 때 깨지고(위젯), 이름에 기댄 코드는 이름이 바뀔 때 깨진다. 다만 이름이 틀리면 오류로 바로 멈추고, 위치가 틀리면 CSV 프로그램처럼 틀린 값을 조용히 낼 수 있다. 이름을 꼭 바꿔야 하면 표 이름도 함께 바꾸고, 옛 표 이름(student)으로 옛 열 이름을 보여 주는 뷰를 남겨 두어(위젯의 "학과를 따로 된 표로") 프로그램을 그대로 둔다.

    • 1의 마지막 줄은 학년 5가 제약에 걸려 거절된 것이다. school.db는 파일 하나이고, .quit로 나간 뒤 다시 열어도 표와 행이 남아 있다.
    • 2에서 파일을 읽을 때 open("students.csv", encoding="utf-8")처럼 인코딩을 밝힌다. 이 PC의 open은 기본이 cp949라서, 밝히지 않으면 UnicodeDecodeError가 났다.
    • 2에서 위치로 읽는 프로그램(line.split(",")[2])은 이메일을 학과로 세었다. 3의 SQL 프로그램은 ALTER TABLE 뒤에도 그대로였다.

    AI와 함께 확인하기¶

    AI 활용 과제: 파일로 만든 학생 관리 프로그램 검토하기

    1. AI에게 "학생 추가, 학과 바꾸기, 학과별 인원 세기를 하는 Python 프로그램을 CSV 파일로 만들어 줘. 여러 직원이 동시에 쓴다"라고 한다.
    2. 받은 코드에서 동시에 고칠 때, 열이 늘 때, 같은 정보가 두 파일에 있을 때 무슨 일이 생길지 적는다.
    3. 같은 기능을 SQLite로 다시 짜게 하고, 2에서 찾은 문제가 어떻게 바뀌는지 견준다.
    확인할 점
    • 파일 전체를 읽고 고쳐 다시 쓰는 코드를 둘이 동시에 돌리면 한쪽의 수정이 사라진다(문제 2). 파일 잠금을 쓴다면 읽기부터 쓰기까지 한 번에 잠그는지 본다.
    • row[2]처럼 위치로 읽는 코드는 열이 늘거나 차례가 바뀌면 틀린 값을 낸다(위젯). csv.DictReader처럼 머리줄의 이름으로 읽으면 덜하지만, 모든 프로그램이 같은 머리줄을 지켜야 한다.
    • SQLite판에서 SELECT *를 위치로 풀거나 INSERT INTO student VALUES (...)처럼 열 이름을 빼면 SQL이라도 열이 늘 때 멈춘다(위젯). 열 이름을 바꿔야 할 때는 이름으로 묻는 쪽이 멈추므로, 옛 이름의 뷰를 남기는지 본다(문제 3).

    더 알아보기¶

    세 단계 스키마

    데이터 독립성은 데이터를 세 겹으로 나눠 보는 생각에서 나왔다. 프로그램이나 사용자가 보는 외부 스키마(뷰), 표와 관계 전체인 개념 스키마, 파일과 인덱스로 저장하는 내부 스키마다. 내부 스키마가 바뀌어도 개념 스키마와 프로그램을 고치지 않아도 되면 물리적 독립성, 개념 스키마가 바뀌어도 외부 스키마(뷰)와 프로그램을 고치지 않아도 되면 논리적 독립성이다. 위젯의 "학과를 따로 된 표로"는 개념 스키마를 바꾸고 옛 모양의 뷰를 남긴 경우다.

    이 항목의 측정 프로그램

    문제 2의 값은 이 PC(Core i9-14900KF, DDR5 64GB, NVMe SSD, Windows 11)에서 아래 프로그램을 5번 실행한 범위다. 두 프로세스가 같은 파일과 같은 SQLite 파일을 함께 고친다. 파일 쪽은 다른 프로세스가 쓰는 중이라 글자가 덜 찬 값을 읽으면 다시 읽게 했는데, 이 PC에서는 그런 일이 없었다. 파일은 TEMP 폴더에 만든다.

    # 49번 측정: 두 프로세스가 잔액에 1을 1,000번씩 더한다. 텍스트 파일과 SQLite를 견준다
import multiprocessing
import os
import sqlite3
import tempfile

N = 1000


def add_file(path):
    bad = 0
    for _ in range(N):
        while True:
            try:
                with open(path, "r+") as f:
                    n = int(f.read())          # 읽고
                    f.seek(0)
                    f.write(str(n + 1))        # 1을 더해 다시 쓴다
                    f.truncate()
                break
            except ValueError:                 # 다른 프로세스가 쓰는 중이라 글자가 덜 찼다
                bad += 1
    return bad


def add_db(path):
    con = sqlite3.connect(path, isolation_level=None)   # 문장 하나가 트랜잭션 하나
    for _ in range(N):
        con.execute("UPDATE account SET balance = balance + 1 WHERE id = 1")
    con.close()
    return 0


if __name__ == "__main__":
    d = tempfile.mkdtemp(dir=os.environ.get("TEMP"))
    file, db = os.path.join(d, "balance.txt"), os.path.join(d, "bank.db")
    with open(file, "w") as f:
        f.write("0")
    con = sqlite3.connect(db)
    con.execute("CREATE TABLE account (id INTEGER PRIMARY KEY, balance INTEGER NOT NULL)")
    con.execute("INSERT INTO account VALUES (1, 0)")
    con.commit()
    con.close()
    with multiprocessing.Pool(2) as pool:
        bad = pool.map(add_file, [file, file])
        pool.map(add_db, [db, db])
    with open(file) as f:
        print("file:", f.read(), "bad reads:", sum(bad))
    con = sqlite3.connect(db)
    print("sqlite:", con.execute("SELECT balance FROM account").fetchone()[0])
    con.close()

    위젯의 결과는 아래 프로그램이 낸 것이다. 같은 학생 세 명을 CSV 파일과 SQLite에 두고, 저장 방식을 바꾼 뒤 세 프로그램을 돌려 맞는 값(ok), 틀린 값(wrong), 멈춤(error)을 가린다.

    # 49번 위젯의 실험: 저장 방식을 바꾼 뒤 CSV 프로그램과 SQL 프로그램을 그대로 돌린다
import os
import sqlite3
import tempfile
from collections import Counter

ROWS = [(1, "김하나", "컴퓨터공학", 2), (2, "이두리", "경영", 1), (3, "박세나", "컴퓨터공학", 3)]
NEW = (4, "최네오", "경영", 1)
TRUTH = [{"컴퓨터공학": 2, "경영": 1}, 1, {"컴퓨터공학": 2, "경영": 2}]


def csv_count(path):                       # CSV: 처음 모양(학번,이름,학과,학년)을 믿고 위치로 읽는다
    with open(path, encoding="utf-8") as f:
        return dict(Counter(line.rstrip("\n").split(",")[2] for line in f))


def csv_find(path, name):
    with open(path, encoding="utf-8") as f:
        for line in f:
            r = line.rstrip("\n").split(",")
            if r[1] == name:
                return int(r[3])


def csv_add(path, row):
    with open(path, "a", encoding="utf-8") as f:
        f.write(",".join(map(str, row)) + "\n")
    return csv_count(path)


def sql_count(con):                        # SQL: 열 이름을 쓴다
    return dict(con.execute("SELECT dept, COUNT(*) FROM student GROUP BY dept").fetchall())


def sql_find(con, name):
    return con.execute("SELECT year FROM student WHERE name = ?", (name,)).fetchone()[0]


def sql_add(con, row):
    con.execute("INSERT INTO student (id, name, dept, year) VALUES (?, ?, ?, ?)", row)
    return sql_count(con)


def star_count(con):                       # SQL이지만 SELECT *를 넷으로 풀고, INSERT에 열 이름을 안 쓴다
    return dict(Counter(dept for sid, name, dept, year in con.execute("SELECT * FROM student")))


def star_find(con, name):
    for sid, n, dept, year in con.execute("SELECT * FROM student"):
        if n == name:
            return year


def star_add(con, row):
    con.execute("INSERT INTO student VALUES (?, ?, ?, ?)", row)
    return star_count(con)


def make_csv(d, change):
    path = os.path.join(d, f"student-{change}.csv")
    with open(path, "w", encoding="utf-8") as f:
        for sid, name, dept, year in ROWS:
            if change == "addcol":             # 이름 뒤에 이메일 열
                f.write(f"{sid},{name},{name}@school.example,{dept},{year}\n")
            elif change == "format":           # 구분자를 탭으로
                f.write(f"{sid}\t{name}\t{dept}\t{year}\n")
            elif change == "split":            # 학과는 따로 된 파일로 옮기고 번호만 남긴다
                f.write(f"{sid},{name},{ {'컴퓨터공학': 1, '경영': 2}[dept] },{year}\n")
            else:
                f.write(f"{sid},{name},{dept},{year}\n")
    return path


def make_db(d, change, tag):
    con = sqlite3.connect(os.path.join(d, f"student-{change}-{tag}.db"))
    con.execute("CREATE TABLE student (id INTEGER PRIMARY KEY, name TEXT, dept TEXT, year INTEGER)")
    con.executemany("INSERT INTO student VALUES (?, ?, ?, ?)", ROWS)
    con.commit()
    if change == "addcol":
        con.execute("ALTER TABLE student ADD COLUMN email TEXT")
    elif change == "format":                   # 파일 안의 페이지 크기를 바꾸고 다시 짠다
        con.execute("PRAGMA page_size = 8192")
        con.commit()
        con.execute("VACUUM")
    elif change == "split":                    # 학과 표를 따로 두고, 옛 모양은 뷰로 남긴다
        con.executescript("""
            CREATE TABLE dept (id INTEGER PRIMARY KEY, name TEXT UNIQUE);
            INSERT INTO dept (name) SELECT DISTINCT dept FROM student ORDER BY dept;
            CREATE TABLE student_base (id INTEGER PRIMARY KEY, name TEXT, dept_id INTEGER REFERENCES dept(id), year INTEGER);
            INSERT INTO student_base SELECT s.id, s.name, d.id, s.year FROM student s JOIN dept d ON d.name = s.dept;
            DROP TABLE student;
            CREATE VIEW student AS
                SELECT s.id, s.name, d.name AS dept, s.year FROM student_base s JOIN dept d ON d.id = s.dept_id;
            CREATE TRIGGER student_insert INSTEAD OF INSERT ON student BEGIN
                INSERT OR IGNORE INTO dept (name) VALUES (NEW.dept);
                INSERT INTO student_base VALUES (NEW.id, NEW.name, (SELECT id FROM dept WHERE name = NEW.dept), NEW.year);
            END;
        """)
    con.commit()
    return con


def judge(fn, truth):
    try:
        return "ok" if fn() == truth else "wrong"
    except Exception:
        return "error"


d = tempfile.mkdtemp(dir=os.environ.get("TEMP"))
for change in ["none", "addcol", "format", "split"]:
    p = make_csv(d, change)
    kinds = [judge(lambda: csv_count(p), TRUTH[0]), judge(lambda: csv_find(p, "이두리"), TRUTH[1]), judge(lambda: csv_add(p, NEW), TRUTH[2])]
    print("csv", change, *kinds)
    for side, (count, find, add) in [("sql", (sql_count, sql_find, sql_add)), ("star", (star_count, star_find, star_add))]:
        con = make_db(d, change, side)
        kinds = [judge(lambda: count(con), TRUTH[0]), judge(lambda: find(con, "이두리"), TRUTH[1]), judge(lambda: add(con, NEW), TRUTH[2])]
        print(side, change, *kinds)
        con.close()

    정리¶

    • 파일에 직접 두면 프로그램마다 파일의 모양을 알아야 하고, 같은 데이터가 여러 파일에 생겨 어긋난다. 여럿이 동시에 고치면 수정이 사라진다.
    • DBMS는 데이터를 한곳에 두고 동시 수정, 제약 검사, 복구, 권한을 맡는다. 프로그램은 SQL로 표와 열의 이름만 쓴다.
    • 저장 방식이 바뀌어도 프로그램을 고치지 않아도 되는 것이 데이터 독립성이다. SQL이라도 SELECT *를 위치로 풀면 잃는다.
