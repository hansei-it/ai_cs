    75. 인증과 인가의 구분, 최소 권한 원칙¶

    원리 동작을 예측하고 이상을 알아챌 수 있어야 하는 항목

    로그인했다는 것과 그 일을 해도 된다는 것은 다른 질문이다. 47번(쿠키, 세션, 토큰(JWT))에서 본 수단은 "누구인가"를 확인하고, 67번(요청 경로의 구성 요소)의 API 게이트웨이는 그 확인을 한곳에서 한다. 이 항목은 섹션 8의 주문 서비스를 이어 써서, "해도 되나"를 어디서 확인해야 하는지와 권한을 얼마나 줄지를 본다. 원리형 항목이므로 코드를 돌리기 전에 결과를 예측해 본다. 계정과 주문은 모두 이 강의가 만든 가짜 데이터다.

    이 항목에서 배우는 것¶

    • 인증과 인가를 구분하고, 각각 실패했을 때의 응답(401, 403)을 설명할 수 있다.
    • 인가를 자원마다 서버에서 확인해야 하는 까닭을 말하고, 확인이 빠진 코드의 결과를 예측할 수 있다.
    • 최소 권한이 계정을 잃었을 때의 피해를 어떻게 줄이는지 설명할 수 있다.

    1. 인증은 누구인지, 인가는 해도 되는지를 묻는다¶

    • 인증(authentication)은 요청을 보낸 이가 누구인지 확인하는 일이다. 비밀번호, 세션, 토큰이 그 수단이다. 확인하지 못하면 401(Unauthorized)로 답한다. 이름은 "인가되지 않았다"로 읽히지만, 뜻은 "인증되지 않았다"이다.
    • 인가(authorization)는 확인된 그 사람이 이 자원에 이 일을 해도 되는지 정하는 일이다. 누군지는 알지만 허락하지 않으면 403(Forbidden)이다. HTTP 명세는 자원이 있는지조차 알리지 않으려면 404로 답해도 된다고 적는다(문제 2).

    2. 인가는 자원을 아는 서버가 자원마다 확인한다¶

    • 게이트웨이는 로그인을 확인하지만, 1002번 주문이 누구의 것인지는 모른다. 자원을 아는 주문 서비스가 요청마다 "이 주문의 주인인가"를 확인한다. 확인은 허락하는 경우만 적고 나머지는 모두 거절하게 짠다(기본 거절, 실습). 문제 1에서 주문 서비스의 코드를 읽고 결과를 예측해 본다.
    • 화면에서 버튼이나 링크를 숨기는 것은 인가가 아니다. 요청은 화면을 거치지 않고도 보낼 수 있다(43번(HTTP)). 웹 보안 단체 OWASP가 웹 애플리케이션의 가장 중대한 보안 위험 열 가지를 꼽은 Top 10(2025)에서, 인가를 빠뜨리거나 잘못한 것(접근 통제 실패)이 1위다.

    3. 권한은 맡은 일에 필요한 만큼만 준다¶

    직접 해 보기계정마다 권한을 얼마나 줄까주문 서비스의 계정 넷에 권한을 켜고 끄며, 맡은 일이 되는지와 그 계정을 잃었을 때 생기는 일을 본다
    새 창에서 크게 열기
    • 최소 권한(least privilege)은 사람이든 프로그램이든 맡은 일에 필요한 권한만 주는 원칙이다. 계정은 언젠가 남의 손에 넘어갈 수 있다고 보고, 그때 그 계정으로 할 수 있는 일을 줄인다. 위젯은 "모두에게 전부"로 시작하는데, 이때는 어느 계정 하나만 잃어도 피해가 전부다. "맡은 일만큼"을 누르기 전에, 그때도 잃으면 가장 큰 피해가 남는 계정이 어느 것일지 적어 보고 견준다.
    • 프로그램과 AI 에이전트도 같다. 매출만 읽는 보고서 프로그램에는 읽기만 준다(문제 3). 에이전트에게 주는 권한도 같은 원칙으로 정한다(98번(AI 에이전트 감독)).

    예측해 보기¶

    문제 1. 주문 서비스의 주문 보기 함수다. 인증은 게이트웨이가 했다고 하자. 세 줄은 각각 무엇을 찍을까?

    # orders.py: 주문 보기. user는 게이트웨이가 확인한 사용자, 로그인하지 않았으면 None
ORDERS = {
    1001: {"owner": "kim", "total": 28000},
    1002: {"owner": "lee", "total": 54000},
}


def get_order(user, order_id):
    if user is None:
        return 401, None
    order = ORDERS.get(order_id)
    if order is None:
        return 404, None
    return 200, order


print(get_order(None, 1001))
print(get_order("kim", 1001))
print(get_order("kim", 1002))
    정답과 해설 
    (401, None)
(200, {'owner': 'kim', 'total': 28000})
(200, {'owner': 'lee', 'total': 54000})

    kim이 lee의 1002번 주문을 받는다. 로그인했는지(인증)만 보고, 이 주문의 주인인지(인가)는 보지 않았다. 주인 확인을 더하면 이렇다.

    def get_order_fixed(user, order_id):
    if user is None:
        return 401, None
    order = ORDERS.get(order_id)
    if order is None or order["owner"] != user:      # 남의 주문은 없는 주문처럼 답한다
        return 404, None
    return 200, order


print(get_order_fixed("kim", 1002), get_order_fixed("kim", 9999))

    (404, None) (404, None)

    남의 주문과 없는 주문에 같은 404로 답하면 1002번이 있다는 것도 알려 주지 않는다. 주문 번호를 1001, 1002처럼 차례로 매기면 남의 번호를 짐작하기 쉽다. 짐작하기 어려운 번호를 써도 그것이 인가를 대신하지는 않는다.

    문제 2. 주문 서비스가 아래 네 요청을 받았다. 남의 주문은 있는지도 알리지 않기로 했고, 환불은 상담원만 한다. 서버는 각각 몇 번으로 답해야 할까?

    • (가) 로그인하지 않은 채 1001번 주문 보기
    • (나) 손님 kim이 1002번(lee의 주문) 보기
    • (다) 손님 kim이 자기 1001번 주문을 환불하기
    • (라) 상담원 park이 없는 9999번 주문 보기
    정답과 해설

    (가) 401, (나) 404, (다) 403, (라) 404. (가)는 누구인지 모르므로 인증에서 막힌다. (나)는 누군지 알지만 남의 주문이고, 있는지도 숨기기로 했으므로 없는 주문과 같은 404다(숨기지 않기로 했다면 403). (다)는 자기 주문이라 숨길 까닭이 없고, 누군지 알지만 손님에게 환불은 허락하지 않으므로 403이다. (라)는 정말 없는 주문이다.

    (다)를 막는 것은 서버의 환불 함수다. 화면이 손님에게 환불 버튼을 그리지 않아도, 같은 요청은 개발자 도구나 명령줄 도구로 만들어 보낼 수 있다(43번(HTTP)). 같은 까닭으로 요청 본문이나 주소에 실려 온 "role": "admin" 같은 값도 믿지 않는다. 역할은 서버가 인증한 사용자로 서버의 표에서 찾는다. 47번(쿠키, 세션, 토큰(JWT))에서 본 서명한 토큰에 든 역할은 서명을 확인한 뒤에만 쓴다.

    문제 3. 하루 매출을 내는 보고서 프로그램이 주문 DB를 읽기 전용으로 연다. 이 프로그램에 실수로 주문을 지우는 문장이 들어가면 어떻게 될까?

    import sqlite3

db = sqlite3.connect("orders75.db")                   # 이 문제만 쓰는 DB(51번의 shop.db와 따로 둔다)
db.execute("DROP TABLE IF EXISTS orders")
db.execute("CREATE TABLE orders (id INTEGER PRIMARY KEY, owner TEXT, total INTEGER)")
db.executemany("INSERT INTO orders VALUES (?, ?, ?)", [(1001, "kim", 28000), (1002, "lee", 54000)])
db.commit()
db.close()

report = sqlite3.connect("file:orders75.db?mode=ro", uri=True)   # 보고서 프로그램은 읽기 전용으로 연다
print(report.execute("SELECT SUM(total) FROM orders").fetchone())
try:
    report.execute("DELETE FROM orders")              # 실수로 들어간 문장
except sqlite3.Error as e:
    print(type(e).__name__, e)
print(report.execute("SELECT COUNT(*) FROM orders").fetchone())
    정답과 해설 
    (82000,)
OperationalError attempt to write a readonly database
(2,)

    지우지 못하고 오류가 난다. 읽기 전용으로 연 연결로는 매출 합계를 읽을 수 있지만 쓰지 못한다. 그래서 이 프로그램의 실수로는 주문이 지워지지 않는다. 다만 mode=ro는 프로그램이 스스로 거는 제한이라, 이 프로그램을 손에 넣은 사람은 mode=ro를 빼고 다시 열 수 있다. 그것까지 막으려면 권한을 프로그램 밖에서 준다. MySQL 같은 서버 DB에서는 프로그램마다 DB 계정을 따로 만들고 필요한 표에 읽기(SELECT)만 허락한다. 위젯의 보고서 프로그램이 "모든 주문 읽기" 하나만 가지는 것과 같다.

    직접 해보기¶

    실습: 역할을 더해 인가 고치기

    1. 문제 1의 코드에서 끝의 print 세 줄을 지우고, 역할 표 ROLES = {"kim": "customer", "lee": "customer", "park": "agent"}를 더한다.
    2. 상담원(agent)은 모든 주문을 보고, 손님(customer)은 자기 주문만 보는 get_order_v2(user, order_id)를 짠다. 허락하는 경우만 적고, 나머지는 모두 404로 답한다.
    3. 아래 네 줄의 결과를 먼저 적고, 실행해 맞춰 본다.

    print(get_order_v2("park", 1002))
print(get_order_v2("lee", 1002))
print(get_order_v2("lee", 1001))
print(get_order_v2("ghost", 1001))                # 게이트웨이는 통과했지만 역할 표에 없는 사용자

    확인할 점 
    ROLES = {"kim": "customer", "lee": "customer", "park": "agent"}


def get_order_v2(user, order_id):
    if user is None:
        return 401, None
    order = ORDERS.get(order_id)
    role = ROLES.get(user)                            # 표에 없는 사용자는 역할이 없다
    if order is None:
        return 404, None
    if role == "agent" or (role == "customer" and order["owner"] == user):
        return 200, order
    return 404, None                                  # 허락한 경우가 아니면 모두 거절한다


print(get_order_v2("park", 1002))
print(get_order_v2("lee", 1002))
print(get_order_v2("lee", 1001))
print(get_order_v2("ghost", 1001))

    AI와 함께 확인하기¶

    AI 활용 과제: AI가 짠 API의 인가 확인하기

    1. AI에게 "Python으로 주문 보기, 환불, 쿠폰 만들기 함수를 짜 줘. 손님, 상담원, 관리자 역할이 있다"고 맡긴다.
    2. 함수마다 인증을 확인하는 줄과 인가를 확인하는 줄을 따로 찾아 적는다. 자원의 주인을 확인하는 줄이 있는지 본다.
    3. 남의 주문 번호, 역할에 없는 일로 함수를 부르는 시험을 만들고, 결과를 먼저 적은 뒤 실행해 맞춰 본다.
    확인할 점
    • 사용자 이름이나 역할을 요청 본문이나 주소에 실려 온 값에서 꺼내 그대로 믿는 코드가 흔하다. 문제 1처럼 함수가 user를 인자로 받는 것은 괜찮지만, 그 값은 인증(세션, 토큰)이 정한 것이어야 한다. 역할은 그 사용자로 서버의 표에서 찾거나, 서버가 서명한 토큰에서 서명을 확인한 뒤 읽는다(문제 2).
    • "관리자면 통과"만 있고 손님의 주인 확인이 빠진 코드가 흔하다(문제 1).
    • 허락하는 경우만 적고 나머지를 거절하는지 본다(실습).
    • 화면에서 버튼을 숨긴 것을 "권한 처리"라고 설명하면 틀렸다.

    더 알아보기¶

    역할로 줄까, 속성으로 줄까

    역할 기반 접근 통제(RBAC)는 사람에게 역할을 주고 역할에 권한을 준다. 이 항목의 손님과 상담원이 그렇다. 속성 기반 접근 통제(ABAC)는 "주문의 주인과 같으면", "근무 시간 안이면"처럼 사용자와 자원의 속성, 시각 같은 환경 조건으로 정한다. 문제 1의 주인 확인은 속성 쪽이다(OWASP는 이렇게 사용자와 자원의 관계로 정하는 것을 관계 기반 접근 통제, ReBAC로 따로 부른다). 실제 서비스는 둘을 섞어 쓴다. 클라우드의 계정 권한 정책도 "누가, 어떤 자원에, 무엇을"을 적는 같은 생각이다(90번(클라우드 서비스 모델)).

    비밀번호는 어떻게 저장하나

    비밀번호는 그대로 저장하지 않는다. 열쇠로 되돌릴 수 있는 암호화가 아니라 되돌릴 수 없는 해시로 바꿔 저장하고, 로그인할 때 받은 비밀번호를 같은 방법으로 바꿔 견준다. 사용자마다 다른 무작위 값(솔트, salt)을 섞으면 같은 비밀번호도 다른 값이 되어, 미리 계산해 둔 표로 한꺼번에 찾거나 같은 비밀번호를 쓰는 사람을 알아낼 수 없다. 또 일부러 느린 함수를 써서, 저장된 값이 새어 나가도 하나씩 맞혀 보는 데 오래 걸리게 한다. OWASP는 Argon2id를 먼저 권하고, 쓸 수 없으면 scrypt를, FIPS-140 인증이 필요하면 PBKDF2-HMAC-SHA256을 60만 번 이상 돌려 쓰라고 한다. Argon2id는 Python 표준 라이브러리에 없다. 여기서는 반복 횟수 하나로 느리기를 정하는 PBKDF2로 원리를 본다(표준 라이브러리의 hashlib.scrypt도 OWASP가 권하는 값으로 쓸 수 있다). 이 PC(Core i9-14900KF)에서 한 번 계산에 0.148~0.156초 걸렸다(5번 잰 범위). 견줄 때는 47번(쿠키, 세션, 토큰(JWT))처럼 hmac.compare_digest를 쓴다.

    import hashlib
import hmac
import secrets


def hash_password(password, salt=None):
    salt = salt or secrets.token_bytes(16)            # 사용자마다 다른 무작위 값(솔트)
    return salt, hashlib.pbkdf2_hmac("sha256", password.encode(), salt, 600_000)   # 일부러 느리게


def check_password(password, salt, stored):
    return hmac.compare_digest(hash_password(password, salt)[1], stored)


salt, stored = hash_password("correct horse")
print(len(salt), len(stored))
print(check_password("correct horse", salt, stored), check_password("correct hose", salt, stored))
print(hmac.compare_digest(hash_password("correct horse")[1], stored))   # 솔트가 다르면 같은 비밀번호도 다른 값이 된다

    다른 앱에 내 권한을 일부만 맡기기(OAuth)

    "이 앱이 내 캘린더를 읽게 허락하시겠습니까?" 같은 화면 뒤에는 OAuth 2.0이 있다. 앱에 비밀번호를 주지 않고, 허락한 범위(scope) 안에서만 쓸 수 있는 토큰을 준다. 읽기만 허락한 토큰으로는 쓰지 못하고, 허락은 앱마다 거둘 수 있다. 다른 앱에 권한을 맡길 때도 최소 권한을 지키는 방식이다.

    정리¶

    • 인증은 누구인지, 인가는 그 사람이 이 자원에 이 일을 해도 되는지 확인한다. 실패하면 각각 401, 403(숨길 때는 404)이다.
    • 인가는 자원을 아는 서버가 요청마다 확인한다. 화면에서 숨기는 것은 인가가 아니다. 허락하는 경우만 적고 나머지는 거절한다.
    • 사람, 프로그램, 에이전트 모두 맡은 일에 필요한 권한만 준다. 계정을 잃었을 때의 피해가 그만큼 줄어든다.
