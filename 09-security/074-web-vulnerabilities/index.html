    74. 웹 애플리케이션 취약점과 방어: SQL Injection, XSS, CSRF. AI 생성 코드에서 취약점 찾기¶

    원리 동작을 예측하고 이상을 알아챌 수 있어야 하는 항목

    웹의 흔한 취약점 셋은 뿌리가 둘이다. 사용자가 보낸 글이 코드(SQL, HTML)로 읽히는 것(SQL Injection, XSS)과, 브라우저가 저절로 하는 일(쿠키 싣기)을 남이 이용하는 것(CSRF)이다. 데이터와 명령이 한곳에 섞여 생기는 문제는 2번(소프트웨어 동작의 물리적 본질)에서 본 폰 노이만 구조와 같은 뿌리다. 이 항목은 공격을 재현하지 않고, 정상 입력으로 원리를 보이고 막는 법을 익힌다. 원리형 항목이므로 코드를 돌리기 전에 결과를 예측해 본다. 코드와 데이터는 이 강의가 만든 예다.

    이 항목에서 배우는 것¶

    • SQL Injection과 XSS가 "데이터가 코드로 읽혀" 생긴다는 것을 설명하고, 매개변수 쿼리와 이스케이프가 왜 막는지 말할 수 있다.
    • CSRF가 브라우저가 쿠키를 저절로 싣는 성질에서 생긴다는 것과 막는 방법을 설명할 수 있다.
    • AI가 짠 코드에서 세 취약점이 생기는 자리를 찾아 고칠 수 있다.

    1. 문자열로 이어 붙인 SQL은 입력을 SQL로 읽는다¶

    • 입력을 SQL 문자열에 이어 붙이면, 입력 속 따옴표가 SQL의 문법으로 읽힐 수 있다. 정상인 이름 O'Brien을 넣으면 어떻게 되는지는 문제 1에서 예측해 본다. 입력이 SQL의 구조를 바꿀 수 있다면, 이를 노리는 공격이 SQL Injection이다.
    • 매개변수 쿼리는 SQL과 값을 따로 넘긴다. DB는 SQL을 먼저 읽고, 값은 끝까지 값으로 다룬다. 섹션 6에서 값을 늘 자리 표시자(SQLite는 ?, 53번(트랜잭션과 락)의 PyMySQL은 %s)로 넘긴 까닭이다. ORM(56번(애플리케이션과 DB 연동))도 안에서 같은 일을 하지만, ORM에서도 SQL을 직접 쓰는 기능에 문자열을 이어 붙이면 같은 문제가 생긴다. 표 이름이나 열 이름은 자리 표시자로 넘길 수 없으므로, 정해 둔 목록에서 고른다.

    2. HTML에 넣는 글은 이스케이프해 글자로 남긴다¶

    직접 해 보기글이 HTML로 읽히면글을 써 넣거나 예를 눌러, innerHTML, textContent, html.escape로 넣었을 때 생기는 요소와 글을 견준다
    새 창에서 크게 열기
    • 59번(HTML, CSS, JavaScript)에서 innerHTML로 넣은 글이 요소가 되고 onerror 같은 속성의 코드가 도는 것을 봤다. 서버가 HTML을 만들 때도 같고, 서버가 보낸 HTML에서는 <script> 요소도 돈다. 손님이 쓴 글로 남의 화면에서 스크립트가 돌게 하는 이 공격이 XSS(크로스 사이트 스크립팅)다.
    • 그래서 넣기 전에 <, >, &, 따옴표를 글자로 바꾼다(이스케이프, 문제 2). 손으로 하면 빠뜨리기 쉬우므로, 값을 채울 때 자동으로 이스케이프해 주는 템플릿(HTML의 틀에 값을 채워 페이지를 만드는 도구. Python의 Jinja 등)을 쓰고 자동 이스케이프가 켜져 있는지 본다. 이 이스케이프는 요소 안의 글과 따옴표로 감싼 속성 값을 위한 것이다. 주소(href)와 <script> 안은 규칙이 달라, 주소는 https:로 시작하는지 따로 확인하고 스크립트 안에는 손님의 글을 넣지 않는다.

    3. 쿠키가 실렸다고 손님이 보낸 요청이라 믿지 않는다¶

    • 47번(쿠키, 세션, 토큰(JWT))에서 본 대로 브라우저는 쿠키를 준 서버로 가는 요청마다 쿠키를 싣는다. SameSite로 막지 않은 쿠키라면, 다른 사이트의 페이지가 내 쇼핑몰로 보내게 한 요청에도 실린다(속성을 적지 않았을 때의 처리는 브라우저마다 다르다). 그래서 서버는 쿠키만 보고는 손님이 보낸 요청인지 알 수 없다. 이 점을 노려 다른 사이트가 손님 몰래 손님의 이름으로 요청을 보내게 하는 공격이 CSRF(사이트 간 요청 위조)다.
    • 막는 법은 겹쳐 쓴다. SameSite 쿠키, 상태를 바꾸는 일을 GET으로 받지 않기(문제 3), 폼마다 넣는 CSRF 토큰(실습)이다.

    예측해 보기¶

    문제 1. 손님 이름으로 손님을 찾는 두 함수다. 세 줄은 각각 무엇을 찍을까?

    import sqlite3

db = sqlite3.connect(":memory:")
db.execute("CREATE TABLE customer (id INTEGER PRIMARY KEY, name TEXT)")
db.executemany("INSERT INTO customer (name) VALUES (?)", [("kim",), ("lee",), ("O'Brien",)])


def find_concat(name):                                # 이름을 SQL 문자열에 이어 붙인다
    return db.execute("SELECT id, name FROM customer WHERE name = '" + name + "'").fetchall()


def find_param(name):                                 # 이름을 매개변수로 따로 넘긴다
    return db.execute("SELECT id, name FROM customer WHERE name = ?", (name,)).fetchall()


print(find_concat("kim"))
print(find_param("O'Brien"))
try:
    print(find_concat("O'Brien"))
except sqlite3.Error as e:
    print(type(e).__name__, e)
    정답과 해설 
    [(1, 'kim')]
[(3, "O'Brien")]
OperationalError near "Brien": syntax error

    이어 붙인 함수는 정상인 이름에서도 깨진다. DB에 간 문장은 ... WHERE name = 'O'Brien'이다. 이름 속 따옴표가 문자열을 닫고, 남은 Brien'을 SQL 문법으로 읽다가 멈췄다. 정상인 이름이 문장을 깨뜨릴 수 있다면, 일부러 만든 입력은 문장의 뜻을 바꿀 수도 있다. 매개변수로 넘기면 DB는 SQL을 먼저 읽고 값은 따로 받으므로, 따옴표도 이름의 한 글자일 뿐이다. 둘째 줄의 큰따옴표는 Python이 작은따옴표가 든 문자열을 큰따옴표로 감싸 보여 주는 것이고, 값은 O'Brien 그대로다. 입력에서 따옴표를 지우는 방법은 O'Brien 같은 진짜 이름을 망가뜨린다. 따옴표를 두 개로 바꾸는 것처럼 직접 바꿔 넣는 방법은 DB마다 규칙이 달라 빠뜨리기 쉬워, 웹 보안 단체 OWASP도 권하지 않는다. 값은 매개변수로 넘긴다.

    문제 2. 서버가 손님 이름을 넣어 HTML 한 줄을 만든다. 셋째 줄은 템플릿이 이스케이프할 값을 코드에서 한 번 더 바꾼 경우다. 세 줄은 각각 무엇을 찍고, 셋째 줄은 화면에 어떻게 보일까?

    import html

name = '<i>Kim</i> & "Lee"'                          # 손님이 이름 칸에 쓴 글
print(f"<p>{name}님</p>")
print(f"<p>{html.escape(name)}님</p>")
print(f"<p>{html.escape(html.escape(name))}님</p>")
    정답과 해설 
    <p><i>Kim</i> & "Lee"님</p>
<p>&lt;i&gt;Kim&lt;/i&gt; &amp; &quot;Lee&quot;님</p>
<p>&amp;lt;i&amp;gt;Kim&amp;lt;/i&amp;gt; &amp;amp; &amp;quot;Lee&amp;quot;님</p>

    첫 줄은 손님의 글이 그대로 HTML이 되고, 둘째 줄은 글자로 남고, 셋째 줄은 바꾼 기호까지 글자로 보인다. 첫 줄을 브라우저가 읽으면 <i> 요소가 생겨 기울인 글씨가 된다. 손님이 쓴 글이 페이지의 구조를 바꾼 것이다. html.escape는 <를 &lt;로, &를 &amp;로, 큰따옴표를 &quot;로 바꾸므로(작은따옴표는 &#x27;로 바꾼다. 이런 &…; 꼴을 문자 참조라 한다) 브라우저는 이것을 글자 <, &, "로 보여 준다. 따옴표까지 바꾸는 것은 속성 값 안에 넣을 때 따옴표가 속성을 닫지 않게 하려는 것이다. 셋째 줄은 두 번째 html.escape가 첫 이스케이프가 만든 &lt;의 &도 손님이 쓴 &와 똑같이 보고 다시 &amp;로 바꾼다. 브라우저는 한 번만 풀므로 화면에는 &lt;i&gt;Kim&lt;/i&gt; &amp; &quot;Lee&quot;님이 글자로 보인다. 안전하지만 이름이 깨져 보이므로, 이스케이프는 넣는 자리에서 한 번만 한다(템플릿을 쓰면 템플릿에 맡긴다). 위젯에 이 글을 넣고 세 칸을 견줘 본다.

    문제 3. 주문 취소를 GET /cancel?order=1001로 받고, 로그인 쿠키는 SameSite=Lax다. 다른 사이트의 페이지가 이 주소로 (가) 링크 이동을 시키거나 (나) 폼 POST를 보내면, 각각 쇼핑몰의 쿠키가 실릴까?

    정답과 해설

    (가)에는 실리고, (나)에는 실리지 않는다. 47번(쿠키, 세션, 토큰(JWT))에서 이 PC의 Chrome으로 확인한 대로, Lax 쿠키는 다른 사이트에서 오는 링크 이동(GET)에는 실리고 폼 POST와 fetch에는 실리지 않는다. 그래서 취소를 GET으로 받으면, 손님이 다른 사이트의 링크를 누르거나 그 사이트가 이 주소로 옮겨 가게 하기만 해도 로그인한 손님의 이름으로 취소가 된다. 상태를 바꾸는 일은 POST로 받고, SameSite에만 기대지 않고 CSRF 토큰도 함께 확인한다(실습). SameSite는 같은 사이트(하위 도메인 등)에서 오는 요청은 막지 않고, 오래된 브라우저나 설정에 따라 다르게 동작할 수 있기 때문이다.

    직접 해보기¶

    실습: AI가 짠 코드에서 취약점 찾아 고치기

    AI에게 "주문 취소 기능을 짜 줘"라고 해서 받은 코드다(흔한 실수를 담아 이 강의가 쓴 예). 웹 프레임워크는 빼고 함수만 남겼다.

    1. 줄마다 읽고, SQL Injection, XSS, CSRF가 생길 수 있는 자리를 표시한다.
    2. 고친 판을 cancel_order(method, form)으로 짠다. method는 "GET"이나 "POST", form은 요청에 실려 온 값이고, 손님과 CSRF 토큰은 로그인할 때 만든 session에서 읽는다. 고친 함수는 (상태 번호, 응답 HTML)을 돌려준다. GET이면 405, 토큰이 없거나 틀리면 403, 남의 주문이나 없는 주문이면 있는지도 알리지 않게 404로 답한다(75번(인증과 인가)). 아래 시작 코드에 붙여, 네 요청의 결과를 먼저 적은 뒤 실행해 견준다.
    # cancel.py: AI가 짠 주문 취소(예). 요청 주소가 /cancel?order=1001이면 params는 {"order": "1001"}
def cancel_order(db, user, params):
    order_id = params["order"]
    row = db.execute(f"SELECT owner FROM orders WHERE id = '{order_id}'").fetchone()
    if row and row[0] == user:
        db.execute(f"UPDATE orders SET status = 'cancelled' WHERE id = '{order_id}'")
        return f"<p>{order_id}번 주문을 취소했다</p>"
    return f"<p>{order_id}번 주문은 취소할 수 없다</p>"

import hmac
import html
import secrets
import sqlite3

db = sqlite3.connect(":memory:")
db.execute("CREATE TABLE orders (id TEXT PRIMARY KEY, owner TEXT, status TEXT)")
db.executemany("INSERT INTO orders VALUES (?, ?, ?)", [("1001", "kim", "paid"), ("1002", "lee", "paid")])
session = {"user": "kim", "csrf": secrets.token_urlsafe(16)}   # 로그인할 때 만든 세션(예)

# 여기에 고친 cancel_order(method, form)을 짠다

print(cancel_order("GET", {"order": "1001"}))
print(cancel_order("POST", {"order": "1001"}))
print(cancel_order("POST", {"order": "1002", "csrf": session["csrf"]}))
print(cancel_order("POST", {"order": "1001", "csrf": session["csrf"]}))
print(db.execute("SELECT id, status FROM orders").fetchall())

    확인할 점
    • SQL Injection: 두 SQL이 f-string으로 order_id를 이어 붙인다. 주소에 실려 온 값이 SQL의 일부가 된다.
    • XSS: 응답 HTML에 order_id를 그대로 넣는다(두 return 모두). 주소에 실려 온 글이 페이지의 HTML이 된다.
    • CSRF: 취소처럼 상태를 바꾸는 일을 주소의 값(GET)으로 받고, 이 요청이 내 페이지에서 왔는지 확인하는 것이 없다.

    고친 한 예와, 네 요청을 보낸 결과다. 주인 확인은 75번(인증과 인가)과 같다.

    import hmac
import html
import secrets
import sqlite3

db = sqlite3.connect(":memory:")
db.execute("CREATE TABLE orders (id TEXT PRIMARY KEY, owner TEXT, status TEXT)")
db.executemany("INSERT INTO orders VALUES (?, ?, ?)", [("1001", "kim", "paid"), ("1002", "lee", "paid")])
session = {"user": "kim", "csrf": secrets.token_urlsafe(16)}   # 로그인할 때 만든 세션(예)


def cancel_order(method, form):
    if method != "POST":                              # 상태를 바꾸는 일은 GET으로 받지 않는다
        return 405, "<p>POST로만 받는다</p>"
    if not hmac.compare_digest(form.get("csrf", "").encode(), session["csrf"].encode()):   # 내 페이지가 넣어 준 토큰인가
        return 403, "<p>요청을 확인할 수 없다</p>"
    order_id = form.get("order", "")
    row = db.execute("SELECT owner FROM orders WHERE id = ?", (order_id,)).fetchone()   # 값은 매개변수로
    if row is None or row[0] != session["user"]:      # 주인 확인
        return 404, "<p>그런 주문이 없다</p>"
    db.execute("UPDATE orders SET status = 'cancelled' WHERE id = ?", (order_id,))
    return 200, f"<p>{html.escape(order_id)}번 주문을 취소했다</p>"   # 넣는 값은 이스케이프


print(cancel_order("GET", {"order": "1001"}))
print(cancel_order("POST", {"order": "1001"}))
print(cancel_order("POST", {"order": "1002", "csrf": session["csrf"]}))
print(cancel_order("POST", {"order": "1001", "csrf": session["csrf"]}))
print(db.execute("SELECT id, status FROM orders").fetchall())

    (405, '<p>POST로만 받는다</p>')
(403, '<p>요청을 확인할 수 없다</p>')
(404, '<p>그런 주문이 없다</p>')
(200, '<p>1001번 주문을 취소했다</p>')
[('1001', 'cancelled'), ('1002', 'paid')]
    • CSRF 토큰은 로그인할 때 만들어 세션에 두고, 내 페이지의 폼에 숨은 칸으로 넣어 준다. 다른 사이트의 페이지는 요청을 보낼 수는 있어도 내 페이지의 내용을 읽지 못하므로(46번(동일 출처 정책과 CORS)) 이 값을 알 수 없다. 그래서 토큰이 맞는 요청은 내 페이지에서 온 것이다. 다만 내 페이지에 XSS가 있으면 끼어든 스크립트가 토큰을 읽을 수 있으므로, 2절의 이스케이프가 먼저다. 견줄 때는 47번(쿠키, 세션, 토큰(JWT))처럼 hmac.compare_digest를 쓰고, 한글처럼 ASCII가 아닌 글자가 와도 오류 없이 견주도록 바이트로 바꿔 넘긴다.
    • 실제 웹 프레임워크에는 CSRF 토큰과 템플릿의 자동 이스케이프가 들어 있는 경우가 많다. 그 기능을 끄는 설정이 있는지 본다.

    AI와 함께 확인하기¶

    AI 활용 과제: AI에게 묻고, AI의 코드를 검토하기

    1. AI에게 "매개변수 쿼리가 SQL Injection을 막는 까닭을, DB가 SQL을 받는 차례로 설명해 줘"라고 묻는다. 1절 그림과 견주어 설명이 맞는지 본다.
    2. AI에게 "http.server로, 손님 이름과 댓글을 받는 폼과, 댓글을 SQLite에 저장하고 목록을 HTML로 보여 주는 Python 서버를 짜 줘"라고 한다. 실습의 세 자리를 찾아 표시한다.
    3. 찾은 곳을 AI에게 보여 주고, 왜 위험한지와 어떻게 고칠지 설명하게 한다. 설명이 이 항목의 원리와 맞는지 본다.
    확인할 점
    • f-string이나 +로 SQL을 만드는 코드가 흔하다. 값이 숫자여도 매개변수로 넘긴다.
    • 목록을 innerHTML +=이나 f-string으로 만드는 코드가 흔하다. 템플릿을 쓰더라도 자동 이스케이프를 끄는 표시(예: Jinja의 |safe)가 붙어 있는지 본다. Flask 없이 Jinja를 바로 쓰면 자동 이스케이프가 꺼진 것이 기본이다(autoescape=False).
    • 지우기, 취소하기 같은 일을 GET 주소로 받는 코드, 폼에 토큰이 없는 코드를 본다.
    • "입력에서 위험한 글자를 지운다"는 방어를 권하면 되묻는다. 지울 글자를 빠뜨리기 쉽고 정상인 입력도 망가뜨린다. 값을 다른 통로로 보내거나(매개변수) 코드로 읽히지 않는 글자로 바꾸는(이스케이프) 방법이 바른 길이다.

    더 알아보기¶

    56번의 기록에는 값이 채워져 보였다

    56번(애플리케이션과 DB 연동)에서 set_trace_callback(print)로 찍은 SQL에는 ? 자리에 값이 채워져 있었다. 문제 1의 db에 db.set_trace_callback(print)를 걸고 find_param("O'Brien")을 부르면 SELECT id, name FROM customer WHERE name = 'O''Brien'이 찍힌다. 사람이 읽기 쉽게 값을 채워 보여 준 것이고, DB는 SQL을 먼저 읽은 뒤 값을 따로 받는다. 드라이버에 따라서는(MySQL용 PyMySQL 등) 라이브러리가 값을 규칙대로 바꿔 넣은 문장 하나를 보내기도 한다. 어느 쪽이든 값이 SQL의 구조를 바꾸지 못하게 하는 일은 라이브러리가 맡으므로, 내 코드는 값을 매개변수로 넘기기만 한다.

    한 겹 더: 콘텐츠 보안 정책(CSP)

    이스케이프를 빠뜨렸을 때 피해를 줄이는 장치도 있다. 콘텐츠 보안 정책(CSP)은 서버가 Content-Security-Policy 머리로 "이 페이지는 정한 출처의 스크립트 파일만 돌리고, 그림은 정한 출처에서만 불러온다"처럼 브라우저에 알리는 방법이다. 스크립트를 정한 출처의 파일로만 한정하면(페이지 안에 적은 스크립트를 허락하지 않으면) 페이지에 끼어든 글 속에 바로 적힌 코드(<script> 안의 코드와 on 속성)는 돌지 않는다. HttpOnly 쿠키는 페이지의 스크립트가 읽지 못한다(47번(쿠키, 세션, 토큰(JWT))). 둘 다 이스케이프를 대신하지 않고 겹쳐 쓴다.

    같은 뿌리: 데이터와 명령을 다른 통로로

    명령줄 문자열에 입력을 이어 붙여 운영체제 명령을 돌리는 코드도 같은 문제를 가진다. Python이라면 subprocess.run(["git", "log", "--oneline", "--", path])처럼 명령과 값을 목록으로 따로 넘기고, 문자열 하나를 셸에 맡기는 shell=True는 피한다(--는 그 뒤를 옵션이 아닌 값으로 읽게 한다). AI 모델이 문서 속 글을 지시로 따르는 프롬프트 인젝션도 뿌리는 같지만, 모델에는 지시와 데이터를 나눌 통로가 없어 막는 법이 다르다(79번(AI 시스템 고유의 보안 위협)).

    정리¶

    • SQL Injection과 XSS는 사용자의 글이 SQL이나 HTML로 읽혀 생긴다. 값은 매개변수로 넘기고, HTML에 넣는 글은 이스케이프한다. 지울 글자를 고르는 방식은 쓰지 않는다.
    • CSRF는 브라우저가 쿠키를 저절로 싣는 성질에서 생긴다. SameSite 쿠키, 상태를 바꾸는 일은 POST로만 받기, CSRF 토큰을 겹쳐 쓴다.
    • AI가 짠 코드에서는 f-string으로 만든 SQL과 HTML, 상태를 바꾸는 GET을 먼저 찾는다.
