    76. 비밀 정보 관리: API 키, 환경 변수, 저장소 유출 방지¶

    직접 AI 없이 직접 할 수 있어야 하는 항목

    API 키, DB 비밀번호, 토큰 같은 비밀값은 그것만 있으면 누구든 내 이름으로 쓴다. 코드에 적어 커밋하면 저장소를 볼 수 있는 사람 모두가 그 값을 갖는다. 이 항목은 비밀값을 코드 밖에 두는 법, 한 번 커밋한 비밀값이 어디까지 남는지, 커밋하기 전에 걸러 내는 법을 본다. 직접형 항목이므로 임시 저장소에서 직접 해 본다. 키는 모두 이 강의가 만든 가짜다. 주문 서비스가 결제 대행사를 부를 때 쓰는 결제 API 키(shop_live_FAKE…)라고 하자. 원격에는 올리지 않는다.

    이 항목에서 배우는 것¶

    • 비밀값을 코드 밖(환경 변수, 커밋하지 않는 .env)에 두고 읽을 수 있다.
    • 커밋한 비밀값이 기록에 남는 것을 확인하고, 새어 나갔을 때 무엇부터 하는지 말할 수 있다.
    • 커밋하기 전에 비밀값을 걸러 내는 검사를 만들고, 그 검사가 놓치는 것을 설명할 수 있다.

    1. 비밀값은 코드 밖에 두고, 실행할 때 넣는다¶

    • 코드에는 비밀값의 이름만 두고, 값은 실행할 때 환경 변수(운영체제가 프로그램을 실행할 때 넘겨주는 이름=값 목록)로 넣는다. 내 PC에서는 .env 파일에 적어 두고 읽되, .gitignore에 적어 커밋하지 않는다. 서버와 CI(커밋마다 검사를 자동으로 돌리는 곳, 89번(CI/CD))에서는 그곳의 비밀값 설정에 넣는다.
    • 비밀값은 화면이나 로그에도 통째로 찍지 않는다. 로그는 여러 사람이 오래 본다(72번(관측성)).

    2. 커밋한 비밀값은 지워도 기록에 남는다¶

    직접 해 보기커밋한 키는 어디에 남을까가짜 키를 커밋하고, 지우고, push하고, 기록을 다시 쓰고, 폐기하는 버튼을 눌러 키가 어디에 남고 아직 통하는지 본다
    새 창에서 크게 열기
    • 키를 지운 커밋을 해도, 키를 적은 커밋은 기록에 그대로 있다(문제 1). push하면 원격으로, 누가 복제하면 그 저장소로 퍼진다. 기록을 다시 써도 이미 퍼진 것은 지우지 못한다. 키를 적은 커밋을 고쳐 만들고 강제 push해도(83번(Git 실천)) 남이 복제한 저장소에는 그대로 있고, GitHub에도 옛 커밋이 남아 그 커밋 번호(해시)를 아는 사람은 열어 볼 수 있다. GitHub 지원팀에 지워 달라고 할 수는 있지만, 키를 바꿔서 막을 수 있는 경우에는 돕지 않는다고 GitHub 문서는 적는다. 포크에 남은 것은 지원팀도 지우지 못한다.
    • 그래서 새어 나간 키는 먼저 폐기하고 새로 발급한다. 폐기한 키는 어디에 남든 쓸모없는 글자다. 그다음 키가 새어 있던 동안 누가 그 키로 무엇을 했는지 결제 대행사의 사용 기록에서 확인한다(72번(관측성)). GitHub의 문서도 키를 즉시 폐기하는 것을 가장 먼저 하라고 하고, 그 뒤 권한 없는 사용이 있었는지 기록을 보라고 하며, 기록을 다시 쓰는 일은 파괴적이라 신중히 하라고 적는다.

    3. 커밋하기 전에 걸러 낸다¶

    • 기록에 남기 전에 막는 것이 가장 싸다. .gitignore로 .env를 빼고, 커밋할 때마다 도는 pre-commit 훅으로 비밀값처럼 보이는 줄을 찾아 막는다(실습).
    • 이런 검사는 정해 둔 형식만 찾는다(문제 3). .gitignore가 언제 듣는지도 따져 봐야 한다(문제 2). 검사를 통과했다고 비밀값이 없다는 뜻은 아니므로, 사람이 diff를 읽는다(83번(Git 실천)).

    예측해 보기¶

    문제 1. 새 폴더의 저장소에서 가짜 키를 config.py에 적어 커밋하고, 다음 커밋에서 그 줄을 지웠다. 지금 config.py에는 키가 없다. git grep 글자는 지금 파일에서 그 글자를 찾고, git log -S 글자는 그 글자가 들어오거나 나간 커밋을 찾는다. 아래 두 명령은 각각 무엇을 찾을까?

    git grep shop_live_FAKE
git log --oneline -S shop_live_FAKE5d2k9q7w1x8z3c6v4b0n
    정답과 해설

    git grep은 아무것도 찾지 못하고, git log -S는 커밋 둘을 찾는다. git grep은 지금 파일만 뒤진다. git log -S 글자는 그 글자가 들어오거나 나간 커밋을 찾으므로, 키를 적은 커밋과 지운 커밋이 나온다. 이 PC에서는 이랬다(커밋 해시는 저마다 다르다).

    f76856b 키 지움
fd58e1f 설정 추가

    git show fd58e1f를 하면 키가 그대로 보인다. 저장소를 받은 사람은 누구나 이렇게 찾을 수 있다. 위젯에서 "키를 코드에 적어 커밋", "키를 지우고 커밋"을 차례로 눌러 보면 같은 결과다.

    직접 확인하려면 훅을 걸지 않은 새 폴더에서 아래를 실행한 뒤 위 두 명령을 한다.

    git init -b main leak-test
cd leak-test
Set-Content config.py 'API_KEY = "shop_live_FAKE5d2k9q7w1x8z3c6v4b0n"'
git add config.py
git commit -m "설정 추가"
Set-Content config.py 'API_KEY = os.environ["SHOP_API_KEY"]'
git commit -am "키 지움"

    문제 2. .env를 실수로 커밋한 뒤에야 .gitignore에 .env를 적었다. 이제 .env의 키를 바꾸고 git status --short를 하면 .env가 보일까?

    정답과 해설

    보인다. 이 PC에서는 M .env(추적하는 파일, 곧 한 번 커밋해 git이 바뀜을 지켜보는 파일이 바뀌었다)가 나왔다. .gitignore를 아직 커밋하지 않았다면 ?? .gitignore도 함께 나온다. .gitignore는 아직 추적하지 않는 파일에만 듣는다. 이미 추적하는 파일은 git rm --cached .env로 추적을 끊고, 그 바뀜을 커밋해야 한다(파일은 작업 폴더에 남는다). 그래도 커밋했던 키는 기록에 남으므로(문제 1), 그 키는 폐기하고 새로 발급한다.

    문제 3. 아래 check_secrets.py는 커밋할 변경에서 비밀값처럼 보이는 줄을 찾는다(실습에서 pre-commit 훅으로 쓴다). 네 줄을 더한 변경을 검사하면 무엇을 찾고, 무엇을 놓칠까? 두 코드를 한 폴더(실습의 shop-secret과는 다른 폴더)에 check_secrets.py, try_scan.py로 저장하고 python try_scan.py로 실행한다.

    # check_secrets.py: 커밋하려는 변경에서 비밀값처럼 보이는 것을 찾으면 커밋을 막는다
import re
import subprocess
import sys

PATTERNS = [
    ("결제 API 키", r"shop_live_[A-Za-z0-9]{24}"),
    ("비밀번호나 키를 글자로 적은 줄", r"(?i)(password|secret|api_key)\s*=\s*['\"][^'\"]{8,}['\"]"),
]


def scan(names, diff):
    """names: 커밋할 파일 이름들, diff: 커밋할 변경(git diff --cached). 찾은 것의 목록을 돌려준다."""
    found = [f"{n}: .env 파일은 커밋하지 않는다" for n in names if n.split("/")[-1] == ".env"]
    file = ""
    for line in diff.splitlines():
        if line.startswith("+++ b/"):
            file = line[6:]
        elif line.startswith("+") and not line.startswith("+++"):
            found += [f"{file}: {name}" for name, p in PATTERNS if re.search(p, line)]
    return found


if __name__ == "__main__":
    def git(*args):
        return subprocess.run(["git", *args], capture_output=True, text=True,
                              encoding="utf-8", errors="replace").stdout   # UTF-8이 아닌 파일도 멈추지 않게

    names = git("diff", "--cached", "--name-only", "--diff-filter=ACMR").split()   # 지운 파일은 빼고 본다
    found = scan(names, git("diff", "--cached", "-U0", "--no-color"))
    for f in found:
        print("막음", f)                                 # 키 값은 찍지 않고 어디서 무엇을 찾았는지만 찍는다
    sys.exit(1 if found else 0)                       # 0이 아니면 git이 커밋을 멈춘다

    # try_scan.py: 문제 3의 시험
from check_secrets import scan

diff = """+++ b/config.py
+API_KEY = os.environ["SHOP_API_KEY"]
+DB_PASSWORD = "correct-horse-battery"
+TOKEN = "shop_live_FAKE5d2k9q7w1x8z3c6v4b0n"
+pw = "hunter2hunter2"
"""
for f in scan(["config.py"], diff):
    print(f)
    정답과 해설 
    config.py: 비밀번호나 키를 글자로 적은 줄
config.py: 결제 API 키

    둘째 줄과 셋째 줄을 찾고, 넷째 줄 pw = "hunter2hunter2"를 놓친다. 첫째 줄은 이름만 두고 값은 환경 변수에서 읽으므로 맞다. 넷째 줄은 변수 이름 pw가 정해 둔 낱말(password, secret, api_key)에 없어 지나간다. 형식으로 찾는 검사는 아는 형식만 찾는다(99번(책임과 윤리)의 형식으로 가리기와 같다). 그래서 검사를 두고도 diff를 사람이 읽고, 새어 나갔으면 키를 바꾼다.

    직접 해보기¶

    실습: 키를 코드 밖에 두고, 커밋 전에 막기

    Git을 처음 쓴다면 실습 환경 8절대로 설치하고 이름과 메일을 정한다. 정하지 않으면 커밋이 Author identity unknown으로 멈춘다. git 명령은 83번(Git 실천)에서 자세히 다룬다.

    1. 새 폴더 shop-secret에서 git init -b main으로 저장소를 만든다. 아래 app.py를 저장하고, 문제 3의 check_secrets.py를 이 폴더로 복사한다(문제 3을 푼 폴더에서 하면 __pycache__와 시험 파일도 git add .에 들어간다).

    2. PowerShell에서 .gitignore와 가짜 키를 적은 .env를 만든다. git add . 뒤 git status --short로 .env가 빠졌는지 보고, git commit -m "앱과 비밀값 검사"로 커밋한다. python app.py로 키를 읽는지 본다.

      Set-Content .gitignore ".env"
Set-Content .env "SHOP_API_KEY=shop_live_FAKE5d2k9q7w1x8z3c6v4b0n"

    3. 검사를 pre-commit 훅으로 건다. 훅은 git이 커밋할 때마다 돌리는 프로그램이고, 0이 아닌 값으로 끝나면 커밋을 멈춘다.

      Set-Content .git\hooks\pre-commit "#!/bin/sh", "exec python check_secrets.py"

    4. 일부러 실수한다. config.py에 API_KEY = "shop_live_FAKE5d2k9q7w1x8z3c6v4b0n" 한 줄을 적고 git add config.py, git commit -m "설정"을 한다. 커밋이 되었는지 git log --oneline으로 본다.

    # app.py: 비밀값은 코드 밖(.env나 환경 변수)에서 읽는다
import os


def load_env(path=".env"):
    """KEY=VALUE 줄을 읽어, 환경 변수에 아직 없는 것만 채운다(작은 .env 읽기)."""
    if os.path.exists(path):
        with open(path, encoding="utf-8") as f:
            for line in f:
                line = line.strip()
                if line and not line.startswith("#") and "=" in line:
                    name, value = line.split("=", 1)
                    os.environ.setdefault(name.strip(), value.strip())


load_env()
key = os.environ.get("SHOP_API_KEY")
if key is None:
    raise SystemExit("SHOP_API_KEY가 없다. .env 파일이나 환경 변수로 넣는다")
print("키를 읽었다:", key[:10] + "…")                # 키를 통째로 찍지 않는다

    확인할 점

    이 PC의 PowerShell에서 차례대로 한 결과다.

    • 2단계: git status --short에는 A .gitignore, A app.py, A check_secrets.py만 나오고 .env는 없다. python app.py는 키를 읽었다: shop_live_…를 찍었다. 환경 변수로 넣어도 된다. $env:SHOP_API_KEY = "shop_test_1234"처럼 넣고 실행하면 키를 읽었다: shop_test_…가 나온다. 그 창에서만 쓰이고, 환경 변수가 .env보다 먼저다(setdefault).

    • 4단계: 커밋이 멈추고 아래처럼 나왔다. git log --oneline에는 2단계의 커밋 하나뿐이다.

      막음 config.py: 결제 API 키
막음 config.py: 비밀번호나 키를 글자로 적은 줄

      키를 지우고 os.environ으로 읽게 고친 뒤 git add config.py를 다시 하고 커밋하면 통과한다. 훅은 git add로 올려 둔 판(스테이지)을 검사하므로, 다시 올리지 않으면 같은 두 줄이 나온다.

    • 훅은 .git 폴더 안에 있어 저장소에 함께 올라가지 않는다. 팀원도 저마다 걸어야 하고, git commit --no-verify로 건너뛸 수도 있다. 그래서 원격에서 한 번 더 막는다(3절 그림). GitHub의 push protection은 알려진 회사의 키 형식만 찾으므로, 내가 만든 형식(shop_live_…)은 CI에서 같은 검사를 돌려 막는다(89번(CI/CD)).

    AI와 함께 확인하기¶

    AI 활용 과제: AI가 짠 코드에서 비밀값 찾기

    1. AI에게 "Python으로 결제 API를 부르는 코드를 짜 줘. API 키가 필요하다"고 맡긴다. 진짜 키는 주지 않는다(99번(책임과 윤리)).
    2. 받은 코드에서 키가 어디서 오는지, 키를 찍거나 로그에 남기는 줄이 있는지, 예외 메시지에 키가 섞이지 않는지 본다.
    3. 받은 코드를 실습의 shop-secret 저장소에 pay.py처럼 파일로 저장하고 git add pay.py, git commit -m "AI가 짠 결제 코드"를 해 본다. -m을 빼면 훅을 통과한 뒤 메시지를 적을 편집기가 열린다. 훅이 막은 것과 내가 찾은 것을 견준다.
    확인할 점
    • API_KEY = "여기에_키를_넣으세요"처럼 코드에 적게 하는 예가 흔하다. 예제 그대로 진짜 키를 넣고 커밋하는 일이 많으니, 처음부터 환경 변수로 읽게 고친다.
    • 디버깅용으로 요청 머리 전체를 찍는 줄이 있으면 키가 로그에 남는다. 키는 앞 몇 글자만 찍는다.
    • ".env에 두면 안전하다"는 설명은 반쪽이다. .gitignore에 적지 않았거나 이미 커밋했다면 그대로 새어 나간다(문제 2).
    • AI 에이전트에게 이 폴더를 맡길 때는 .env도 읽힐 수 있으니, 맡기기 전에 치우거나 읽기를 막는다(98번(AI 에이전트 감독)).

    더 알아보기¶

    서버와 CI에서는 비밀값을 어디에 두나

    GitHub Actions 같은 CI는 저장소 설정에 비밀값을 넣어 두고, 워크플로 파일에서 그 이름을 불러 환경 변수로 넘긴다(89번(CI/CD)). 환경 변수는 코드에 적는 것보다 낫지만, 같은 PC의 다른 프로그램이 읽거나 오류 덤프와 로그에 섞일 수 있다. 그래서 OWASP의 비밀 관리 치트 시트는 컨테이너에 비밀값을 넣을 때, 파일로 붙이거나 비밀 저장소에서 꺼내는 방법을 쓸 수 없을 때만 환경 변수를 쓰라고 한다. 클라우드에는 비밀값을 따로 맡아 두고 권한이 있는 프로그램만 꺼내게 하는 비밀 관리 서비스가 있다. 쿠버네티스의 Secret은 값을 base64로 적을 뿐이고, 기본 설정에서는 암호화하지 않은 채 저장된다. 그래서 저장 암호화를 켜고, 꺼낼 수 있는 권한을 최소로 줄인다(92번(쿠버네티스와 서버리스)). 어디에 두든 그 비밀값을 꺼낼 수 있는 계정을 줄이는 것이 핵심이다(75번(인증과 인가)).

    자주 바꾸고, 짧게 쓰는 키

    오래 쓰는 키일수록 새어 나갔을 때 오래 쓰인다. 그래서 키를 정해진 때마다 바꾸거나, 몇 분에서 몇 시간 뒤에 저절로 끝나는 짧은 토큰을 쓴다(47번(쿠키, 세션, 토큰(JWT))의 JWT 만료와 같은 생각이다). 키마다 할 수 있는 일을 좁혀 두면, 새어 나가도 그 일로 그친다.

    정리¶

    • 비밀값은 코드와 커밋하는 파일에 두지 않는다. 코드에는 이름만 두고, 값은 환경 변수나 커밋하지 않는 .env로 넣는다.
    • 커밋한 비밀값은 지워도 기록에 남고, push하면 퍼진다. 새어 나간 키는 먼저 폐기하고 새로 발급한다.
    • .gitignore와 pre-commit 훅으로 커밋 전에 막고, 원격(push protection, CI)에서 한 번 더 막는다. 검사는 아는 형식만 찾으므로 사람이 diff를 읽는다.
