    77. 의존성 공급망 보안: AI가 추천한 패키지의 실재 여부, 유지보수 상태, 라이선스 확인¶

    직접 AI 없이 직접 할 수 있어야 하는 항목

    17번(패키지 생태계와 의존성 관리)에서 설치 명령 한 줄이 여러 패키지를 끌어오는 것을 봤다. 설치한 패키지는 내 프로그램 안에서 내 권한으로 돈다. 그래서 내 코드만큼 그 패키지도 믿을 수 있어야 한다. AI는 그럴듯한 이름의 없는 패키지를 추천하기도 하고, 그런 이름이나 유명 패키지의 오타 이름을 누군가 먼저 등록해 둘 수 있다. 이 항목은 설치하기 전에 무엇을 확인하는지 PyPI의 공개 정보로 직접 확인한다. 직접형 항목이다. 패키지는 설치하지 않고, 정보를 읽거나 미리 만들어 둔 파일(휠)을 내려받기만 한다.

    이 항목에서 배우는 것¶

    • 패키지의 실재, 유지보수 상태, 라이선스, 알려진 취약점을 설치하기 전에 확인할 수 있다.
    • 유명 패키지의 오타를 노린 이름을 이름 사이의 거리로 찾아낼 수 있다.
    • 잠금 파일에 해시를 적어, 받은 파일이 처음 확인한 그 파일인지 확인할 수 있다.

    1. 설치하기 전에 넷을 확인한다¶

    • 있나: 이름과 버전이 PyPI에 있는지 본다. 없는 이름은 설치하지 않는다. 지금 없는 이름은 누구든 나중에 등록할 수 있다. 거꾸로, 있다고 진짜라는 뜻도 아니다. AI가 지어낸 이름을 누가 먼저 등록해 두었다면 PyPI에 있고 마지막 배포도 최근이다. 배포한 판이 한두 개뿐인 새 이름이면 저장소부터 본다.
    • 돌보나: 마지막 배포가 오래되었거나 저장소 주소가 없으면, 문제가 생겨도 고쳐지지 않을 수 있다. pycrypto는 2014년 뒤로 배포가 없고, 알려진 취약점 2건에 고친 버전이 없다.
    • 써도 되나: 라이선스가 팀이 써도 된다고 정해 둔 목록(허용 목록)에 있는지 본다. MIT, BSD, Apache-2.0은 고지를 지키면 제품에 넣기 쉽다. GPL 코드가 든 프로그램을 남에게 배포하면 전체를 GPL로 주고 소스도 받을 수 있게 해야 하므로(99번(책임과 윤리)), 그 조건을 지킬 수 있는지 먼저 정한다.
    • 알려진 취약점이 있나: 알려진 취약점에는 공개 번호가 붙는다. CVE는 공개된 취약점마다 붙는 공통 번호이고, GHSA와 PYSEC는 GitHub와 Python 패키지 취약점 데이터베이스가 붙인 번호다. 취약점은 버전마다 다르다. requests 2.31.0에는 3건이 있고 2.33.0까지 모두 고쳤다.

    웹 보안 단체 OWASP가 꼽은 Top 10(2025)은 이런 소프트웨어 공급망 실패를 3위에 둔다.

    2. 이름은 한 글자까지 본다¶

    직접 해 보기이 패키지 이름은 믿을 만할까패키지 이름을 써 넣거나 예를 눌러, 널리 쓰는 패키지 이름과 몇 글자 다른지 보고 오타를 노린 이름인지 가린다
    새 창에서 크게 열기
    • 유명 패키지 이름에서 한두 글자 바꾼 이름을 등록해 두고, 잘못 친 사람이 설치하기를 기다리는 공격이 있다(타이포스쿼팅). AI가 지어낸 그럴듯한 이름을 먼저 등록해 두는 일도 같은 길을 노린다.
    • PyPI는 이름의 대소문자와 -, _, .를 가리지 않는다. python_dateutil은 python-dateutil과 같은 이름이다. 그렇게 맞춘 뒤에도 한두 글자 다르면 의심한다(문제 2). 다만 가깝다고 모두 가짜는 아니다. 널리 쓰는 pip과 six도 2글자 다르다. 짧은 이름일수록 가깝게 나오므로, 거리는 의심할 까닭이지 판정이 아니다.

    3. 받은 파일이 그 파일인지 해시로 확인한다¶

    • 17번(패키지 생태계와 의존성 관리)의 잠금 파일은 버전을 고정한다. 여기에 파일의 해시(sha256)를 함께 적는다. sha256은 파일 내용 전체로 계산한 64자리 16진수다. 22번(해시 테이블)의 해시 함수와 달리 같은 값을 내는 다른 파일을 일부러 만들 방법이 알려져 있지 않고, 한 비트만 바꿔도 값의 비트가 절반쯤 바뀌어 전혀 다른 값이 된다. pip은 받은 파일의 해시를 견주어 다르면 멈추므로(실습), 미러나 프록시를 거쳐 받아도 처음 확인한 그 파일만 받는다. 91번(가상머신과 컨테이너)의 이미지 다이제스트도 같은 생각이다.
    • --require-hashes에서는 의존성까지 모두 ==로 고정하고 해시를 적어야 한다. 모르는 패키지가 몰래 끼어들지 못한다. 의존성이 적을수록 확인할 것도 적으니, 표준 라이브러리로 되는 일에는 패키지를 더하지 않는다.

    예측해 보기¶

    문제 1. 실습의 check_pkg.py로 읽은 정보를 간단한 규칙으로 판정한다. 세 줄은 각각 무엇을 찍을까?

    from datetime import date

ALLOWED = {"MIT", "BSD-3-Clause", "Apache-2.0"}      # 우리 팀의 라이선스 허용 목록(예)


def assess(meta, today=date(2026, 10, 16)):
    if meta is None:
        return ["PyPI에 없다: 이름을 다시 확인하고 설치하지 않는다"]
    warn = []
    last = date.fromisoformat(meta["last_upload"])
    if (today - last).days > 2 * 365:
        warn.append(f"마지막 배포가 {last}이다")
    if meta["license"] not in ALLOWED:
        warn.append(f"허용 목록에 없는 라이선스: {meta['license']}")
    if meta["vulns"]:
        warn.append(f"이 버전에 알려진 취약점 {len(meta['vulns'])}건")
    return warn


requests_meta = {"last_upload": "2026-05-14", "license": "Apache-2.0", "vulns": []}       # requests 2.34.2
pycrypto_meta = {"last_upload": "2014-06-20", "license": "Public domain", "vulns": ["CVE-2013-7459", "CVE-2018-6594"]}
print(assess(requests_meta))
print(assess(pycrypto_meta))
print(assess(None))                                   # PyPI에 없는 이름
    정답과 해설 
    []
['마지막 배포가 2014-06-20이다', '허용 목록에 없는 라이선스: Public domain', '이 버전에 알려진 취약점 2건']
['PyPI에 없다: 이름을 다시 확인하고 설치하지 않는다']

    requests는 규칙에 걸리지 않고, pycrypto는 셋 다 걸린다. 규칙에 걸리지 않았다고 안전하다는 뜻은 아니다. 저장소와 의존성은 사람이 한 번 본다. "Public domain"은 나쁜 라이선스라서가 아니라 허용 목록에 없어서 걸렸고, 이런 것은 사람이 읽고 정한다. 라이선스 칸은 자유롭게 쓰는 글이라 같은 requests도 2.31.0에서는 "Apache 2.0", 2.34.2에서는 "Apache-2.0"이었다. 글자 그대로 견주면 틀리기 쉽다.

    문제 2. 위젯과 같은 계산으로, 다섯 이름을 유명 패키지 이름과 견준다. 무엇이 찍히고, 어느 이름이 의심스러울까? 마지막 cs77-no-such-pkg는 손으로 세기 어려우니 가까운 이름이 있는지만 적는다.

    import re


def normalize(name):
    return re.sub(r"[-_.]+", "-", name).lower()       # PyPI는 대소문자와 - _ . 를 가리지 않는다


def distance(a, b):
    """a를 b로 바꾸는 데 드는 최소 편집 수(한 글자 넣기, 빼기, 바꾸기)."""
    row = list(range(len(b) + 1))
    for i, ca in enumerate(a, 1):
        prev, row[0] = row[0], i
        for j, cb in enumerate(b, 1):
            prev, row[j] = row[j], min(row[j] + 1, row[j - 1] + 1, prev + (ca != cb))
    return row[-1]


POPULAR = ["requests", "numpy", "pandas", "urllib3", "python-dateutil"]
for name in ["Requests", "reqeusts", "python_dateutil", "numpyy", "cs77-no-such-pkg"]:
    n = normalize(name)
    near = min(POPULAR, key=lambda p: distance(n, p))
    print(name, near, distance(n, near))
    정답과 해설 
    Requests requests 0
reqeusts requests 2
python_dateutil python-dateutil 0
numpyy numpy 1
cs77-no-such-pkg numpy 13

    reqeusts(2글자)와 numpyy(1글자)가 의심스럽다. Requests와 python_dateutil은 PyPI에서 같은 이름이라 0이다. reqeusts는 두 글자의 자리를 바꿨을 뿐인데, 바꾸기가 두 번이라 2다. cs77-no-such-pkg는 목록의 이름과 가깝지 않아 그 이름들의 오타는 아니지만, PyPI에 없는 이름이다(실습). AI가 지어낸 이름이 이렇게 보인다. 그래서 오타 검사와 실재 확인은 따로 한다. distance는 28번(최적화 기법 (DP·그리디))의 동적 계획법이다. 표의 칸 (i, j)는 a의 앞 i글자를 b의 앞 j글자로 바꾸는 최소 편집 수이고, 위 줄만 있으면 다음 줄을 채울 수 있어 한 줄만 들고 간다.

    실습: 설치하기 전에 패키지 확인하기

    1. 아래 check_pkg.py를 저장하고 네 번 돌린다: python check_pkg.py requests, python check_pkg.py requests 2.31.0, python check_pkg.py pycrypto, python check_pkg.py cs77-no-such-pkg. 1절 그림의 값(2026-10-16)과 견주어 오늘 달라진 값이 있는지 적는다.

    2. 빈 폴더에서 requests 파일 하나를 내려받아(설치하지 않는다) 해시를 구한다.

      python -m pip download requests==2.34.2 --no-deps --only-binary :all: -d dl
python -m pip hash dl\requests-2.34.2-py3-none-any.whl

    3. 나온 해시로 requests==2.34.2 --hash=sha256:… 한 줄을 req.txt에 적고 python -m pip download --no-deps --only-binary :all: --require-hashes -r req.txt -d dl2를 한다. 해시의 한 글자를 바꾸고, 새 폴더 -d dl3로 다시 한다.

    4. 해시를 되돌리고, --no-deps를 빼고 3의 명령을 다시 한다.

    # check_pkg.py: 설치하지 않고 PyPI의 공개 정보로 패키지를 확인한다. 실행: python check_pkg.py 이름 [버전]
import json
import string
import sys
import urllib.error
import urllib.request


def fetch(path):
    try:
        with urllib.request.urlopen(f"https://pypi.org/pypi/{path}/json", timeout=20) as r:
            return json.load(r)
    except urllib.error.HTTPError as e:
        if e.code == 404:                            # 그런 이름이나 버전이 없다
            return None
        raise


def known_vulns(records):
    """같은 취약점이 여러 번호(GHSA, PYSEC, CVE)로 실려 오므로, 서로 별칭인 것을 하나로 센다."""
    groups = []
    for v in records:
        ids = {v["id"], *v.get("aliases", [])}
        for g in groups:
            if g["ids"] & ids:
                g["ids"] |= ids
                break
        else:
            groups.append({"ids": ids, "fixed": v.get("fixed_in") or []})
    return [(label(g["ids"]), g["fixed"]) for g in groups]


def label(ids):
    cves = sorted(i for i in ids if i.startswith("CVE"))   # CVE 번호가 있으면 그것으로 부른다
    return cves[0] if cves else sorted(ids)[0]


def repo_url(info):
    """주소 이름표는 문장 부호와 빈칸을 빼고 소문자로 맞춰 견준다(Source Code → sourcecode)."""
    drop = str.maketrans("", "", string.punctuation + string.whitespace)
    urls = {k.translate(drop).lower(): v for k, v in (info.get("project_urls") or {}).items()}
    repo = next((urls[k] for k in ("source", "repository", "sourcecode", "github", "code") if k in urls), None)
    return repo or f"적혀 있지 않다(홈페이지: {urls.get('homepage', '없음')})"


def license_of(info):
    classes = [c.split(" :: ")[-1] for c in info.get("classifiers", []) if c.startswith("License ::")]
    first = (info.get("license") or "").split("\n")[0][:60]    # 칸에 전문을 넣은 패키지도 있어 첫 줄의 앞 60자만 본다
    return info.get("license_expression") or first or ", ".join(classes) or "적혀 있지 않다"


def report(name, version=None):
    project = fetch(name)
    if project is None:
        print(name, "PyPI에 없다. 이름을 다시 확인하고, 설치하지 않는다")
        return
    version = version or project["info"]["version"]
    release = fetch(f"{name}/{version}")
    if release is None:
        print(name, version, "그런 버전이 없다")
        return
    info = release["info"]                           # 라이선스와 저장소는 그 버전의 것을 본다
    # releases는 PyPI 문서가 앞으로 Index API로 옮기라고 한 칸이다. 지금은 배포 기록을 여기서 읽는다
    uploads = [f["upload_time_iso_8601"][:10] for files in project["releases"].values() for f in files]
    vulns = known_vulns(release.get("vulnerabilities", []))
    print(name, version + ("  (철회된 버전: " + (info.get("yanked_reason") or "까닭 없음") + ")" if info.get("yanked") else ""))
    print("  이 패키지의 마지막 배포:", max(uploads, default="파일 없음"), f"(배포한 판 {len(project['releases'])}개)")
    print("  라이선스:", license_of(info))
    print("  저장소:", repo_url(info))
    print(f"  알려진 취약점: {len(vulns)}건")
    for vid, fixed in vulns:
        print("   ", vid, "고친 버전: " + ", ".join(fixed) if fixed else "고친 버전 없음")


if __name__ == "__main__":
    report(*sys.argv[1:3])

    • PyPI는 requests 2.31.0의 취약점을 6개 기록으로 돌려주었다. 같은 취약점이 GHSA와 PYSEC 번호로 두 번씩 실려 오기 때문이다. 그래서 known_vulns가 별칭을 묶어 3건으로 센다.
    • 고친 버전은 고침이 처음 들어간 버전이다. 올릴 때는 그 뒤의 최신 버전으로 올린다. requests 2.32.0은 철회(yanked)된 버전이라 python check_pkg.py requests 2.32.0이 그렇다고 알린다. 철회는 배포한 사람이 "이 버전은 쓰지 말라"고 표시한 것이다. pip은 범위로 고를 때는 건너뛰지만, ==로 적으면 경고만 내고 그대로 받는다(이 PC의 pip 25.2, requests 2.32.0). 그래서 AI가 ==로 적은 버전은 사람이 확인해 바꾼다.
    • 저장소 주소의 이름표는 패키지마다 다르게 적는다(Source, source, Repository, GitHub 등). 그래서 문장 부호와 빈칸을 빼고 소문자로 맞춰 견준다. 라이선스 칸에 전문을 넣은 패키지는 첫 줄의 앞 60자만 찍히니, 이상하면 PyPI 페이지의 분류(Classifiers)와 저장소의 LICENSE 파일을 본다.
    • 2단계: pip hash는 --hash=sha256:2a0d60c172f83ac6ab31e4554906c0f3b3588d37b5cb939b1c061f4907e278e0을 찍었다. PyPI의 정보에 적힌 그 파일의 sha256과 같다.
    • 3단계: 맞는 해시로는 내려받았고, 한 글자를 바꾸자 이 PC의 pip 25.2가 ERROR: THESE PACKAGES DO NOT MATCH THE HASHES FROM THE REQUIREMENTS FILE.과 함께 기대한 값(Expected)과 받은 값(Got)을 찍고 멈췄다.
    • 4단계: ERROR: In --require-hashes mode, all requirements must have their versions pinned with ==.가 나왔다. requests가 끌어오는 의존성(charset_normalizer 등)에 버전과 해시가 없기 때문이다. 의존성까지 모두 적어야 해시 확인이 된다.
    • pip보다 새 판이 나와 있으면 끝에 [notice] A new release of pip is available 두 줄이 붙는다. 실습과 상관없는 안내다.

    AI와 함께 확인하기¶

    AI 활용 과제: AI가 추천한 패키지를 설치하기 전에 확인하기

    17번(패키지 생태계와 의존성 관리)에서 손으로 본 것을 이번에는 도구로, 버전까지 본다.

    1. AI에게 "PDF에서 표를 뽑는 프로그램의 requirements.txt를 버전까지 적어 줘"라고 맡긴다. 아직 설치하지 않는다.
    2. 적힌 이름마다 위젯으로 이름을 보고, python check_pkg.py 이름 버전으로 그 버전의 실재, 배포 기록, 라이선스, 알려진 취약점을 본다. 줄에 camelot-py[base]==0.11.0처럼 대괄호(추가 기능 표시)나 ==가 붙어 있으면 python check_pkg.py camelot-py 0.11.0처럼 이름과 버전만 띄어 넣는다. 그대로 넣으면 실제 패키지도 없다고 나온다.
    3. AI가 적은 설명(유지보수, 라이선스, 인기)과 실제 정보가 다른 곳을 적는다.
    확인할 점
    • 없는 이름이 섞여 나오면 설치하지 않는다. 설치 명령을 그대로 붙여 넣었다면, 그 이름을 누가 등록해 두었을 때 그 코드가 내 PC에서 돈다. 에이전트가 스스로 설치하려 할 때도 먼저 묻게 해 두고 이 확인을 한다(98번(AI 에이전트 감독)).
    • AI는 학습한 글에서 본 것을 바탕으로 말하므로, 마지막 배포나 라이선스가 그 뒤에 바뀌었을 수 있다(93번(LLM의 동작 원리)). 검색을 붙인 도구라도 오늘의 값은 PyPI에서 본다.
    • 적어 준 버전에 알려진 취약점이 있거나 철회된 버전이면, 고친 뒤의 최신 버전으로 바꾼다. 고친 버전이 그 패키지에 없으면, 이름을 바꿔 옮겨 간 패키지가 있는지 저장소를 본다.
    • 위젯의 20개에는 PDF 패키지가 없어 pdfplumber도 "가까운 이름이 없다"로 나온다. 거리 검사는 견줄 목록에 있는 이름만 지킨다.
    • pdfplumber처럼 저장소 주소를 홈페이지 칸에만 적은 패키지도 있다. 홈페이지가 github.com 같은 저장소 주소면 그곳에서 최근 커밋과 이슈를 본다. "적혀 있지 않다"는 돌보지 않는다는 뜻이 아니라 직접 찾아보라는 뜻이다.
    • PyMuPDF처럼 AGPL(GNU Affero GPL)과 상용 라이선스 가운데 고르게 한 패키지도 있다(check_pkg.py에는 Dual Licensed - GNU AFFERO GPL 3.0 or Artifex Commercial Lic로 나온다). 상용 라이선스 없이 AGPL로 쓰면서 그 코드를 고쳐 네트워크 서비스로 내놓으면 배포하지 않아도 서비스를 쓰는 사람에게 고친 판 전체의 소스를 받을 수 있게 해야 한다(AGPL 13절). 서비스에 넣기 전에 그 조건을 지킬 수 있는지 정한다(99번(책임과 윤리)).
    • 같은 일을 표준 라이브러리로 할 수 있는지도 묻는다. 패키지를 하나 더할 때마다 확인할 것이 는다.

    더 알아보기¶

    설치하는 동안에도 코드가 돈다

    pip의 문서는 기본 설정의 pip이 배포된 파일의 코드를 돌릴 수 있다고 적는다. 소스 배포(.tar.gz)를 설치하면 그 패키지의 빌드 코드를 내 PC에서 돌려 설치할 파일을 만들기 때문이다. 이미 만들어 둔 휠(.whl)만 받게 하려면 --only-binary :all:을 쓴다. pip download도 마찬가지로, 소스 배포만 있는 패키지는 정보(의존성 목록)를 얻으려고 그 빌드 코드를 돌린다. 그래서 실습의 내려받기에도 --only-binary :all:을 붙였다. "일단 설치해 보고 확인한다"는 확인이 아니다. 확인은 설치하기 전에 한다.

    의존성 전체의 알려진 취약점을 한꺼번에 보기

    check_pkg.py는 패키지를 하나씩 본다. 잠금 파일에 적힌 패키지 전체를 견주는 도구로 pip-audit이 있고, GitHub의 Dependabot은 저장소의 의존성에 알려진 취약점이 생기면 알려 준다. 이런 검사를 CI에 넣어 두면(89번(CI/CD)) 취약점이 알려진 버전이 커밋에 섞여 들어오는 것을 막는다. 새 취약점은 코드를 고치지 않은 날에도 알려지므로, 이미 쓰는 패키지는 Dependabot 알림처럼 새 취약점이 등록될 때 알려 주는 방법으로 본다. 두 도구 모두 이 강의에서는 설치하지 않고 이름과 링크만 든다.

    정리¶

    • 설치하기 전에 있나, 돌보나, 써도 되나, 알려진 취약점이 있나를 PyPI의 공개 정보로 본다. 없는 이름은 설치하지 않고, 있다고 진짜라는 뜻도 아니다.
    • 이름은 한 글자까지 본다. PyPI가 같은 이름으로 보는 차이(대소문자, -_.)를 맞춘 뒤 한두 글자 다르면 오타를 노린 이름일 수 있다.
    • 잠금 파일에 해시를 적으면 처음 확인한 그 파일만 받는다. 의존성까지 모두 고정해야 하고, 패키지를 줄일수록 확인할 것이 준다.
