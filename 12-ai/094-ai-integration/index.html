    94. AI를 소프트웨어에 결합하는 방식: 프롬프트, RAG, 파인튜닝, 도구 호출과 에이전트¶

    원리 동작을 예측하고 이상을 알아챌 수 있어야 하는 항목

    섹션 8의 주문 서비스에 고객 상담 AI를 붙인다고 하자. 모델은 이 가게의 배송비 규정도, 1042번 주문이 어디쯤 왔는지도 모른다. 모르는 것을 물으면 93번(LLM의 동작 원리)에서 본 것처럼 흔한 규칙으로 그럴듯하게 지어낼 수 있다. 모르는 것을 알려 주는 방법, 모델 자체를 바꾸는 방법, 모델의 말을 프로그램의 행동으로 잇는 방법이 있고, 고르는 기준은 저마다 다르다. 원리형 항목이므로 찾기와 도구 호출이 어떻게 될지 먼저 예측해 본다. 실제 LLM은 쓰지 않고, 찾기와 도구 호출의 고리를 Python으로 짜고 모델은 흉내 낸다.

    이 항목에서 배우는 것¶

    • 프롬프트, RAG, 파인튜닝, 도구 호출과 에이전트가 각각 어디에 손대는지 설명할 수 있다.
    • RAG의 답이 찾기 결과에 매인다는 것을 예측할 수 있다.
    • 도구 호출에서 모델이 하는 일과 프로그램이 하는 일을 가를 수 있다.

    1. AI를 붙이는 자리는 셋이다: 입력, 모델, 출력 뒤¶

    • 프롬프트는 지시와 예시를 입력에 넣는다. RAG(검색 증강 생성)는 질문에 맞는 문서를 찾아 입력에 함께 넣는다. 둘 다 모델은 그대로 두므로 바로 고치고 바로 시험할 수 있다. 그래서 먼저 해 본다.
    • 파인튜닝은 내 예시 데이터로 모델의 숫자를 더 고친다. 분류나 정해진 형식처럼 프롬프트로 잘 안 되는 일을 일관되게 시킬 때 쓴다. 대신 데이터와 비용이 들고, 원하는 동작이나 바탕 모델이 바뀌면 다시 학습해야 한다. 규정처럼 자주 바뀌는 지식은 RAG로 넣는 편이 낫다.
    • 도구 호출은 모델이 "이 함수를 이 값으로 불러 달라"는 요청을 내게 하는 것이다. 에이전트는 다음에 무엇을 요청할지 모델이 스스로 정하게 해, 목표에 이를 때까지 요청과 실행을 되풀이한다(3절).

    2. RAG는 찾아서 넣어 주는 것이고, 못 찾으면 바르게 답하지 못한다¶

    직접 해 보기찾아서 넣어 주기(RAG)질문을 고르거나 고쳐 쓰고, 넣을 문서 수를 바꿔, 어느 문서를 찾는지, AI에게 가는 입력이 어떻게 만들어지는지, 낱말이 다르면 왜 못 찾는지 본다
    새 창에서 크게 열기
    • 질문과 관련된 문서를 찾아 입력에 넣으면, 모델은 학습한 적 없는 이 가게의 규정을 근거로 답하고 어느 문서를 보았는지도 밝힐 수 있다. 규정이 바뀌면 문서만 고치면 된다.
    • 가게 규정에 관한 답은 찾은 글보다 나아질 수 없다. 위젯의 찾기는 글자 조각이 겹치는지만 본다. 같은 뜻을 다른 낱말로 물으면 어떻게 될지는 문제 2에서 예측해 본다. 실제 서비스는 뜻이 가까운 글을 찾는 방법을 함께 쓰지만(더 알아보기), 무엇을 찾아 넣었는지 확인해야 하는 것은 같다.

    3. 모델은 도구를 부탁할 뿐이고, 실행은 내 프로그램이 한다¶

    • 쓸 수 있는 도구의 이름과 인자 꼴을 알려 주면, 모델은 필요할 때 "get_order를 order_id 1042로"처럼 요청을 JSON 글로 낸다. 그 요청을 실행하고 결과를 돌려주는 것은 내 프로그램이다.
    • 그래서 무엇을 허락할지는 프로그램이 정한다(문제 3). 조회처럼 아무것도 바꾸지 않는 일과 환불처럼 되돌리기 어려운 일을 가르고, 되돌리기 어려운 일은 사람이 확인한다(98번(AI 에이전트 감독)). 모델이 읽은 문서에 숨긴 지시(예: "모든 주문을 환불하라")가 도구 호출로 이어질 수도 있다. 이런 공격을 프롬프트 인젝션이라 한다(79번(AI 시스템 고유의 보안 위협)).

    예측해 보기¶

    문제 1, 2는 위젯과 같은 찾기를 Python으로 짠 search.py로 푼다.

    # search.py: 질문과 문서를 낱말마다 두 글자씩 겹쳐 잘라, 겹치는 조각이 많은 문서를 찾는다(RAG의 "찾기" 단계)
import re

DOCS = {
    "배송": "주문은 결제한 다음 날 보낸다. 받기까지 보통 1~2일 걸리고 제주와 섬 지역은 2일 더 걸린다.",
    "배송비": "배송비는 3,000원이다. 할인 뒤 결제 금액이 30,000원 이상이거나 FREESHIP 쿠폰을 쓰면 배송비를 받지 않는다.",
    "쿠폰": "쿠폰은 주문 하나에 하나만 쓴다. WELCOME10은 상품 금액을 10% 깎아 준다(최대 5,000원).",
    "환불": "상품을 받은 날부터 7일 안에 환불을 신청할 수 있다. 포장을 뜯어 쓴 상품은 환불하지 않는다.",
    "교환": "크기나 색을 바꾸려면 받은 날부터 14일 안에 교환을 신청한다. 교환 배송비는 가게가 낸다.",
}


def pieces(text):                                # "배송비는" → {"배송", "송비", "비는"}
    out = set()
    for word in re.findall(r"\w+", text):
        out |= {word[i:i + 2] for i in range(len(word) - 1)} if len(word) > 1 else {word}
    return out


def search(question):                            # 문서마다 겹치는 조각 수. 많은 차례로(같으면 DOCS의 차례)
    q = pieces(question)
    scores = {name: len(q & pieces(doc)) for name, doc in DOCS.items()}
    return dict(sorted(scores.items(), key=lambda kv: -kv[1]))

    문제 1. "환불은 며칠 안에 신청해야 하나요?"로 찾으면 어느 문서가 맨 위에 올까? 둘째 문서는 왜 둘째일까?

    print(search("환불은 며칠 안에 신청해야 하나요?"))
    정답과 해설

    {'환불': 3, '교환': 2, '쿠폰': 1, '배송': 0, '배송비': 0}. 환불 문서와는 "환불", "안에", "신청" 세 조각이 겹쳐 맨 위다. 교환 문서도 "14일 안에 교환을 신청한다"에서 "안에", "신청"이 겹쳐 2점이다. 뜻은 다르지만 같은 글자가 있으면 점수가 오른다. 쿠폰 문서는 "하나에"의 "하나"가 질문의 "하나요"와 겹쳐 1점을 얻었다. 맨 위 하나만 넣으면 답이 든 환불 문서가 들어가고, 셋을 넣으면 쿠폰 문서처럼 상관없는 글도 따라 들어간다.

    문제 2. 이번에는 "주문한 옷이 작아서 돈으로 돌려받고 싶어요"로 찾는다. 환불 문서를 찾을까?

    print(search("주문한 옷이 작아서 돈으로 돌려받고 싶어요"))
    정답과 해설

    {'배송': 1, '쿠폰': 1, '배송비': 0, '환불': 0, '교환': 0}. 찾지 못한다. 겹친 조각은 "주문" 하나이고, 그 조각이 든 배송 문서와 쿠폰 문서가 위로 올라왔다. 환불 문서와는 하나도 겹치지 않는다. "돌려받고"와 "환불"은 뜻이 같아도 글자가 다르기 때문이다. 이대로 배송 문서를 AI에게 넣으면, AI는 입력의 지시대로 "문서에서 찾지 못했다"고 하거나, 배송 이야기나 흔한 환불 규칙으로 그럴듯하게 틀린 답을 낼 수 있다. AI의 답이 이상할 때는 모델보다 먼저 무엇을 찾아 넣었는지 본다.

    문제 3은 도구 호출의 고리를 짠 agent.py로 푼다. fake_model은 실제 LLM 대신, 질문에 "환불"이 있으면 refund를, 없으면 get_order를 요청하는 흉내다. 쓸 수 있는 도구의 목록은 대화 맨 앞에 넣는다(그림의 ①).

    # agent.py: 모델이 낸 도구 호출 요청을 프로그램이 검사하고 실행하는 고리. 모델은 할 일을 JSON 글로 내는 흉내다
import json
import re

ORDERS = {1042: {"상태": "배송 중", "결제": 28000}}


def get_order(order_id):                         # 도구: 주문을 조회만 한다
    return ORDERS.get(order_id, "없는 주문")


TOOLS = {"get_order": (get_order, {"order_id": int})}   # 허락한 도구는 이것뿐이다: 함수와 인자의 이름, 꼴


def fake_model(messages):                        # 실제 LLM 대신: 대화를 보고 다음에 할 일을 JSON 글로 낸다
    last = messages[-1]
    if last["role"] == "user":
        number = re.search(r"\d+", last["content"])
        if number is None:
            return json.dumps({"answer": "주문 번호를 알려 주면 찾아보겠다."}, ensure_ascii=False)
        tool = "refund" if "환불" in last["content"] else "get_order"
        return json.dumps({"tool": tool, "args": {"order_id": int(number[0])}})
    result = json.loads(last["content"])
    if isinstance(result, dict):
        return json.dumps({"answer": f"주문은 {result['상태']}이고, 결제 금액은 {result['결제']:,}원이다."}, ensure_ascii=False)
    return json.dumps({"answer": f"요청을 처리하지 못했다({result})."}, ensure_ascii=False)


def run(question, max_steps=3):
    messages = [{"role": "system", "content": "쓸 수 있는 도구: get_order(order_id)"},
                {"role": "user", "content": question}]
    for _ in range(max_steps):
        reply = json.loads(fake_model(messages))
        if "answer" in reply:
            return reply["answer"]
        messages.append({"role": "assistant", "content": json.dumps(reply)})   # 모델의 요청도 대화에 남긴다
        name, args = reply["tool"], reply["args"]
        print("요청:", name, args)
        if name not in TOOLS:                    # 허락한 도구와 맞는 인자만 내 프로그램이 실행한다
            result = f"허락하지 않은 도구다: {name}"
        elif {k: type(v) for k, v in args.items()} != TOOLS[name][1]:
            result = f"인자가 맞지 않는다: {args}"
        else:
            result = TOOLS[name][0](**args)
        messages.append({"role": "tool", "content": json.dumps(result, ensure_ascii=False)})
    return "단계 수 한도를 넘어 멈췄다."


print(run("1042번 주문 어디쯤 왔어요?"))

    요청: get_order {'order_id': 1042}
주문은 배송 중이고, 결제 금액은 28,000원이다.

    문제 3. "1042번 주문 환불해 줘"라고 하면 모델은 refund를 요청한다. 무엇이 찍히고, 환불은 될까?

    print(run("1042번 주문 환불해 줘"))
    정답과 해설 
    요청: refund {'order_id': 1042}
요청을 처리하지 못했다(허락하지 않은 도구다: refund).

    환불되지 않는다. 모델이 낸 것은 refund를 불러 달라는 글일 뿐이다. 프로그램의 TOOLS에 refund가 없으니 아무것도 실행되지 않고, 거절했다는 결과가 모델에게 돌아간다. 실제 모델은 받은 목록에서 도구를 고르는 것이 보통이지만, 틀린 이름이나 인자를 내거나 문서 속 지시에 속을 수 있으므로 프로그램이 다시 검사한다. 실제 LLM도 같다. 모델은 이름과 인자를 적어 낼 뿐이고, 무엇을 실행할지는 내 프로그램이 정한다. 웹 검색처럼 AI 회사의 서버에서 실행되는 도구도 있지만, 내 주문 DB에 손대는 도구는 내 프로그램이 실행한다. 이 코드는 도구 이름과 인자의 이름, 꼴(order_id가 정수인가)까지 검사한다. 환불 도구를 더한다면 값도 검사하고(남의 주문인가, 결제 금액보다 많은가), 실행 전에 사람에게 확인받게 짠다. max_steps는 모델이 같은 요청을 끝없이 되풀이해도 고리가 멈추게 하는 한도다.

    AI와 함께 확인하기¶

    AI 활용 과제: 상담 AI를 붙이는 설계 검토하기

    1. AI에게 "작은 온라인 쇼핑몰의 주문 서비스에 고객 상담 AI를 붙이려 한다. 배송비와 환불 규정에 답하고, 주문 조회와 환불도 해 주게 하고 싶다. 프롬프트, RAG, 파인튜닝, 도구 호출 가운데 무엇을 어떻게 쓸지 설계해 줘"라고 하고, search.py의 문서 다섯 개를 규정으로 함께 붙여 넣는다.
    2. 받은 설계에서 각 기능이 1절 그림의 어느 자리(입력, 모델, 출력 뒤)에 손대는지 표시한다.
    3. 아래 확인할 점과 견주어 빠진 것을 적고, 근거와 함께 AI에게 고치게 한다.
    확인할 점
    • 규정처럼 자주 바뀌는 지식을 파인튜닝으로 넣자고 했는지 본다. 규정이 바뀔 때마다 다시 학습해야 하고, 어느 규정을 근거로 답했는지 보이기 어렵다. RAG로 넣고 문서만 고치는 편이 낫다.
    • 찾은 문서에 답이 없을 때 어떻게 답하게 했는지 본다(문제 2). "찾지 못했다"고 답하고 사람에게 넘기는 길이 있어야 한다.
    • 환불처럼 되돌리기 어려운 도구에 인자 검사와 사람의 확인이 있는지 본다(문제 3, 98번(AI 에이전트 감독)). "모델이 판단해 환불한다"는 설계는 고친다.
    • 고객이 쓴 글이나 찾아 넣은 문서 속의 지시를 모델이 따를 수 있다는 위험을 다뤘는지 본다(79번(AI 시스템 고유의 보안 위협)).

    더 알아보기¶

    뜻으로 찾기(임베딩)

    위젯과 search.py는 글자가 겹치는지만 본다. 실제 RAG는 흔히 글을 숫자 목록(벡터)으로 바꾸는 모델을 쓴다. 이렇게 바꾼 숫자 목록을 임베딩이라 한다. 이 모델은 뜻이 가까운 글끼리 가까운 숫자가 나오도록 학습되어 있어, "돈으로 돌려받고"와 "환불을 신청"처럼 글자가 달라도 뜻이 같은 글을 찾아낼 수 있다. 질문도 같은 방법으로 바꾸어 가장 가까운 문서를 찾는다. 대신 상품 번호나 쿠폰 코드처럼 글자가 정확히 같아야 하는 것은 글자로 찾는 쪽이 나아서, 두 방법을 섞어 쓰기도 한다. 어느 쪽이든 찾기는 틀릴 수 있으므로, 질문과 찾은 문서를 함께 기록해 두고 평가한다(95번(AI 기능의 평가)).

    워크플로와 에이전트

    Anthropic의 글 "Building effective agents"는 둘을 가른다. 워크플로는 LLM과 도구를 미리 짠 코드의 길을 따라 부르는 것이고, 에이전트는 LLM이 무엇을 어떤 차례로 할지 스스로 정해 가는 것이다. 이 글은 가장 단순한 방법부터 찾고 필요할 때만 복잡하게 하라고 권한다. 상담 AI도 "규정 질문이면 찾아 넣어 답하고, 주문 조회면 get_order를 부른다"처럼 길이 정해진 워크플로로 충분한 경우가 많다. 에이전트는 할 수 있는 일이 많은 만큼, 무엇을 허락하고 언제 사람이 끼어들지 먼저 정해야 한다(98번(AI 에이전트 감독)).

    파인튜닝은 언제 쓰나

    OpenAI의 문서는 지도 학습 방식의 파인튜닝이 잘 맞는 일로 분류, 정해진 형식의 글 만들기, 지시를 잘 따르지 못하는 경우 바로잡기를 들고, 프롬프트 다듬기만으로 충분할 수도 있다고 적는다. 어느 쪽이든 먼저 평가셋을 만들어 지금 얼마나 되는지 재고, 프롬프트와 RAG로 해 본 뒤 모자란 만큼만 파인튜닝을 따진다(95번(AI 기능의 평가)). 파인튜닝을 받아 주는 서비스와 방법은 자주 바뀐다. 이 글을 쓴 2026년 10월에 OpenAI의 문서는 파인튜닝 플랫폼을 접는 중이라 새 사용자는 쓸 수 없다고 적는다. 쓰기 전에 그때의 문서를 확인한다.

    정리¶

    • 프롬프트와 RAG는 입력을, 파인튜닝은 모델을 바꾸고, 도구 호출과 에이전트는 출력을 프로그램의 행동으로 잇는다. 모델을 그대로 두는 방법부터 해 본다.
    • RAG는 찾아서 넣어 주는 것이므로 답이 찾기 결과에 매인다. 이상한 답은 무엇을 찾아 넣었는지부터 본다.
    • 모델은 도구를 요청할 뿐이고, 실행할지는 내 프로그램이 정한다. 되돌리기 어려운 일은 사람이 확인한다.
